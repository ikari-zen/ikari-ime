# ikari の検討履歴

ikari は、作者が自分で使うために作っている日本語入力（IME）です。この文書は、ikari の設計がどの順番で決まってきたかを、日付つきでまとめたものです。何を試し、何を決め、何をやめたかを残します。

対象は、ikari を使ってみたい人と、コードや設計を読んで手を入れたい開発者です。細かい経緯は各 ADR（設計判断の記録）にあります。この文書は、その入口になることを目指しています。

## 読み方

1. まずこの README で、全体の流れ（下の年表）をつかむ。
2. [decisions.md](decisions.md) で、設計の大きな選択 10 個と、ADR の一覧を読む。
3. [lessons.md](lessons.md) で、指摘を受けて方針が変わった例と、やめた案や計測で覆った仮説を読む。

用語は次の意味で使っています。

- **ADR**: 設計の判断を 1 件ずつ残した記録。[ADR の索引](../adr/README.md) にまとめてあります。
- **評価セット**: 同じ入力を毎回流して、正解の候補が 1 位に来た割合を測るための入力と正解の一覧です。数値は、どのセットで測ったかを一緒に読んでください。
- **LM（言語モデル）**: 候補の順番を並べ替えるために使う小さな AI モデルです。ikari では、候補を作るのは辞書で、LM は並べ替えにだけ使います。
- **学習**: 選んだ候補を覚えて、次回以降の順番に効かせる仕組みです。

## 注記

- 段階の名前と区切りは、ADR と PR の日付から整理したものです。名前は整理した人が付けました。
- 日付は、各 ADR の記載（承認日、実装日、停止日）で確かめました。
- 2026-10-25 時点の状態です。ADR は 34 本（0001〜0035。0022 は欠番）あり、0033 は提案のまま、0025 と 0028 は停止しています。0031 は方式を決めたもので、実装は含みません。

## 年表

### 段階 1: 土台と CLI の実験（2026-10-11）

- **試したこと**: 辞書の形式、文脈を読んで解析する仕組み、話題の情報（chiVe）と LM（zenz）の比較を、コマンドラインで動かしました。
- **決めたこと**: 辞書の行は消さず、ペナルティで後ろに回す（[ADR 0002](../adr/0002-phase1-architecture.md)）。話題の情報と LM を組み合わせる（[ADR 0003](../adr/0003-topic-ranker-decision.md)）。
- **やめたこと**: 長文向けに LM を使い分ける案。LM は小さいモデル 1 つにしました（ADR 0003）。辞書の解析に外部のライブラリを使う案（sudachi.rs）。
- **元になった ADR**: 0001、0002、0003。

### 段階 2: macOS の入力の殻（2026-10-11〜10-12）

- **試したこと**: 入力メソッドの殻（Swift）と、変換を担うエンジン（Rust）を分けて、macOS で動かしました。
- **決めたこと**: エンジンは殻の中に同梱した XPC サービスとして動かす（[ADR 0004](../adr/0004-phase2-macos.md)）。ON/OFF の表示や設定は別のアプリに分ける（[ADR 0005](../adr/0005-macos-settings-and-indicator.md)）。
- **やめたこと**: 辞書とモデルをアプリに同梱する案（約 340MB になり、更新で入れ替えられない）。設定画面を入力メソッドの中で開く案（開いた瞬間に、入力中の文字が確定されてしまう）。
- **実機**: 10-12 に実装が済み、実機で使えるようになりました（ADR 0004 の実装日）。

### 段階 3: 使い心地（2026-10-12〜10-13）

- **試したこと**: 実機で使って見つかった不具合を直しました。候補ウィンドウの位置（別の画面に出た）、かなキーの切り替えで見えない空白が入る、などです。
- **決めたこと**: 文節の移動、区切り直し、確定後の再変換（[ADR 0006](../adr/0006-segment-editing.md)）。最初の Space は読み全体の候補を出し、文節の操作は ←/→ を押したときだけ（ADR 0006）。
- **やめたこと**: 選択がないときに直前の語を自動で選ぶ案（意図を推測することになる）。最初から文節モードにする案（2 文節の入力で数字キーが使えず、打鍵が増えた）。

### 段階 4: 誤変換を原因ごとに直す（2026-10-13〜10-16）

実機で見つかった誤変換を、原因ごとに測って直しました。規則は 1 つずつ、最も狭い層に足しています。直さないと決めた例もあります。

- **10-13**: 助詞の「か」などが、1 語の複合語に負ける問題（[ADR 0007](../adr/0007-left-context-compound.md)）。副詞の直後の名詞（[ADR 0008](../adr/0008-adverb-noun-connection.md)）。
- **10-14**: 異字同訓の表記（「直った」が「治った」になる。[ADR 0009](../adr/0009-verb-notation.md)）。本動詞の漢字の加点の範囲（[ADR 0010](../adr/0010-verb-kanji-bonus-scope.md)）。1 語で入っている熟語を優先（「携帯素解析」を直す。[ADR 0011](../adr/0011-compound-over-affix-split.md)）。文脈のない学習の効き方（[ADR 0013](../adr/0013-learning-without-context.md)）。
- **10-15**: 新語の層と IT の語彙集（[ADR 0012](../adr/0012-new-word-dictionary.md)）。候補ウィンドウを縦一列にする（[ADR 0014](../adr/0014-candidate-window-layout.md)）。まれな同音語（[ADR 0016](../adr/0016-rare-homophones.md)）。形式名詞の加点（[ADR 0017](../adr/0017-formal-noun-kanji-bonus-scope.md)）。「さいかい」→「最下位」は直さないと決めた（[ADR 0018](../adr/0018-frequent-compound-homophone.md)）。残りの誤りは 2 群だけを規則で直した（[ADR 0019](../adr/0019-remaining-conversion-errors.md)）。
- **10-16**: 文脈をできるだけ広く読む。ただし保存はしない（[ADR 0015](../adr/0015-context-sources.md)）。英字が 1 位に来たら、カタカナを 1 位に繰り上げる（[ADR 0020](../adr/0020-english-spelling-first-candidate.md)）。LM が規則を覆さないように、最後の段で戻す（[ADR 0024](../adr/0024-lm-keeps-rule-s.md)）。

### 段階 5: 試して止めた実験（2026-10-16〜10-18）

- **先読みの測り方を見直した**: LM は締め切りに間に合わないと思われていたが、実機のログでは約 87% の変換に付いていた。新しい仕組みは作らず、まずログで測ることにした（[ADR 0021](../adr/0021-lm-lookahead.md)）。
- **先読みの生成（停止 10-17）**: ローカルの LLM で左文脈の続きを作って順位に使う試作。基準から外れた 51 件のうち、生成文に正解が出たのは 0〜2 件でした。全部直っても 0.8 ポイント程度なので、止めました（[ADR 0025](../adr/0025-pregen-prototype.md)）。
- **事前の好みの差し引き（停止 10-18）**: 文脈なしの LM の加点を引く案。シミュレーションでは効いたが、実装で AJIMEE の評価が 17 件下がり、止める線に当たりました（[ADR 0028](../adr/0028-lm-prior-subtraction.md)）。
- **先読みキャッシュの構想**: 新しい仕組みとしては作らないと決めました。確定した文章を保存することは、原文を持たないという方針に反するためです（[ADR 0023](../adr/0023-speculative-cache-stage1-2.md)）。

### 段階 6: 機能の追加（2026-10-18）

- **英語のモード**: 英数キーで入る、打鍵をそのままアプリに渡すモード。統計は既定でオフ（[ADR 0026](../adr/0026-english-mode-and-key-stats.md)）。
- **絵文字の入力**: `:eyes:` の形で候補を出す（[ADR 0027](../adr/0027-emoji-input.md)）。この機能は後に既定オフになりました（方針の 3 本柱を受けた判断。[spec](../ikari-ime_spec.md) の基本原則）。

### 段階 7: 方針の整理（2026-10-19〜10-22）

- **方針の 3 本柱（10-20）**: ユーザーの思考を止めない、意図に忠実（補完をしない。入力の結果を変える機能は既定でオフ）、速さは補完ではなく入力配列とショートカットで出す。spec の基本原則に入りました。
- **人名と地名の重さを分ける（10-21〜22）**: 地名は多くの人が多くの場面で使うので、人名より軽く扱う（[user-feedback](../user-feedback.md) の 2 節）。
- **複合語の左の語と、接尾辞の増幅を見直す（10-22）**（[ADR 0029](../adr/0029-compound-adjectival-left-and-noun-suffix-amplification.md)）。
- **地名の語彙を辞書に足す（10-22）**: 丁目つきの語は作らず、町名と丁目と数詞で出す。小字と通り名は入れない（[ADR 0030](../adr/0030-abr-town-vocabulary.md)）。
- **モデルの使い分け（10-22）**: 調査、設計、実装で使うモデルを分けると決めました（開発の進め方）。

### 段階 8: 入力配列と住所（2026-10-23）

- **入力配列の方式**: キーの入れ替えは OS の仕組み（hidutil）で行い、薙刀式などは別の常駐プログラムで行う（[ADR 0031](../adr/0031-keymap-engine.md)。方式を決めたもので、実装は含まない）。
- **住所と郵便番号**: 辞書の行にはせず、読み全体が住所の並びか郵便番号の形のときだけ候補を出す（[ADR 0032](../adr/0032-postal-code.md)）。町名だけから郵便番号を出すことは、入力していない内容を足すことになるので入れない前提です。

### 段階 9: 診断と仕上げ（2026-10-24〜10-25）

- **地名データの配布（提案のまま）**: 地名データを GitHub Actions で作って配る案（[ADR 0033](../adr/0033-place-data-distribution.md)）。殻とエンジンは通信しない、という前提は変えない。作者の判断待ちです。
- **診断ログ**: 文字を書かないログを、常に取るようにしました。原因を推測ではなく、ログで確かめるためです（[ADR 0034](../adr/0034-diagnostic-log.md)）。
- **経路が負ける型の補正**: 辞書を作るときのコストを調整して直す。値は掃引で決める（[ADR 0035](../adr/0035-path-loses-cost-adjust.md)）。
- **動物名のひらがな（10-25）**: LM なしでひらがなを優先する規則は残します。LM の後でひらがなに戻す案は、表記の正解が文脈と書き手で変わるため取りやめました（[lessons.md](lessons.md) の 2 節）。
