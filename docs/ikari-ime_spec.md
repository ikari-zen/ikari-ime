# ikari-ime 要件定義書 v0.1

Oct 10, 2026 · [@ikari-zen](https://github.com/ikari-zen)

## 概要と目的

文脈に応じて同音異義語を正しく選び分ける日本語IMEを作る（もともと自分用に作り始めたが、公開していて、ほかの人が使うことを前提にする。2026-10-28）。きっかけは、IMEについての文章で「ひんし」を変換すると「品詞」ではなく「瀕死」が出たこと。

- **利用者**：作者と、公開のソースやバイナリを使うほかの人（2026-10-28 に変更。もとは作者本人だけ）。方針の決定は作者が行うが、既定値や配布は多くの利用者を想定して決める
- **核となる価値**：文脈（周辺テキストと確定履歴）と属性プロファイルを使った候補の順位付け
- **方針**：変換はすべてローカルで行う。外部との通信は辞書の自動更新（ダウンロードのみ）に限る。文章の取り込みでクラウドLLMを使うのは、ユーザー自身の操作（NFR-21）
- **実装体制**：要件と設計を本書で固め、実装はClaude Codeに任せる

## 基本原則

### 方針の3本柱（2026-10-20 ユーザー決定）

1. **ユーザーの思考を止めない**。ライブ変換のように、変換や入力に失敗すると手戻りが起き、思考が止まる。こまめに確定しながら書き進める。
2. **ユーザーの意図に忠実**。入力の補完はしない。文字をつけ足さない。必要のない機能は既定でオフにする。
   - 「補完」とは、入力していない文字を、ユーザーが選ばずに足すこと。読みから漢字・日付・絵文字などに**変わる候補**（ユーザーが選ぶもの）は、全く別のものに変わる**変換**であって、補完ではない。
   - 入力の結果を変える機能（ショートコード、括弧の自動補完など）は、既定でオフにする。ユーザーが設定で入れる。
3. **少ない打鍵で速く入力したい要求には、補完ではなく、入力配列の変更とショートカットで応える**。入力配列（ローマ字表、かな配列、同時打鍵の配列。大西配列や薙刀式など）と、ユーザーが明示的にキーを押したときだけ働くショートカット（テンプレート、字種変換など）で速くする。予測変換・サジェストは取り入れない。

以下の2つの原則は、柱 2 の中身にあたる。

### ユーザーの入力を正とする

ikari-imeは、ユーザーが入力した文字列を起点として変換候補を推論する。文脈は候補の生成・順位付けを支援するために用いるが、ユーザーが入力していない内容を先回りして補完したり、確定した文字列をユーザーの意図に反して変更したりしない。最終的な表現の選択権は常にユーザーにある。

### 学習と変換精度に関する原則

ikari-imeは、ユーザーの過去の文章や変換履歴を活用し、利用を重ねるほど変換精度が向上することを目指す。

過去のユーザーと現在のユーザーは連続している。過去の文章や選択履歴は、現在の入力意図を推定するための有用な情報である。

ただし、過去の選択は現在の意図を決定するものではない。学習結果は変換候補の生成・順位付けを支援するために用い、ユーザーの入力と現在の文脈を優先する。

また、学習によって候補の選択肢を不当に制限せず、最終的な表現の選択権をユーザーに残す。

## 名前とモチーフ

名前は **ikari-ime**、モチーフは「錨」とする。「いかり」は怒りにも錨にも碇にもなり、文脈がなければ決められない。名前そのものが、このIMEが解く問題になっている。

### 由来

- **怒り**：既存IMEの誤変換への怒りが開発の動機。こまめに確定する書き方では左文脈が渡らず、毎回文脈なしで変換させられる
- **錨**：確定した語が錨になり、文脈をつなぎ止めて、次の変換を正しい方向へ引っ張る
- **ケッジング**：錨を前方に下ろし、鎖を巻き上げて船を引き寄せる操船術。確定した語を足がかりに次の語へ進む書き方は、これと同じ

### 設計への落とし込み

| モチーフ | 設計 | 関連する節 |
| --- | --- | --- |
| 投錨（確定） | 確定したテキストを左文脈として、次の変換に必ず渡す | [文脈を使った変換](#medx261jtz0.1066) |
| 停泊しながら進む | ライブ変換はしない。一語ずつ確定しながら書き進める | [変換方式](#medx261jtz0.7884) |
| 爪が海底をつかむ | 学習は「左文脈＋読み→語」で持ち、文脈の違う選択で上書きしない | [学習](#medx261jtz0.1808) |

### 怒りの記録

Google日本語入力が実際に起こした誤変換。確定済みの左文脈を使えば避けられるはずのもので、評価セットに回帰ケースとして入れる。怒りは見つけ次第ここに足していく。

| 読み | 期待 | 実際の変換 | 原因（推定） |
| --- | --- | --- | --- |
| ひんし | 品詞 | 瀕死 | 同音異義語を文脈なしで選んだ |
| はじめてしった | 初めて知った | 始めて知った | 学習が文脈を見ず、別の文での選択が残った |
| （〜に）なった | なった | 鳴った | 確定で左文脈が切れ、「に」の後ろだと分からない |
| かきすすめる | 書き進める | 下記進める | 辞書にない複合動詞を、名詞＋動詞に分けた |
| （〜と）しよう | しよう | 仕様 | 助詞の後ろの意志形を名詞で上書きした |

### 表記とアイコン

リポジトリ名とcrate名は ikari-ime とする。英語圏で「Ikari」と検索するとアニメの人名や同名のゲームエンジンが上位に出るため、接尾辞で区別する。

アイコンは、錨の軸をテキストカーソル（Iビーム）に見立てる案とする。macOSの入力ソースアイコンは16pt前後の単色画像なので、錨の輪郭だけで判別できる太さにする。入力モードはリングの中の「あ」「A」で示す。

## 便利な変換（Google日本語入力から取り入れる）

Google日本語入力（Mozc）の便利な機能のうち、「入力した読みに完全一致する候補だけを出す」方針（FR-06）と矛盾しないものを取り入れる。中心になるのは、読みから動的に候補を作る機能と、ローマ字表の拡張。

### 機能一覧

| 状態 | 機能 | 例 |
| --- | --- | --- |
| 決定 | 今日の日付を候補に出す | 「きょう」→ 2026/10/10、2026年10月10日 など |
| 決定 | 日付・時刻の候補を広げる | 「あした」「きのう」「ことし」「いま」 |
| 決定 | z＋キーで記号を出す | zh ←、zj ↓、zk ↑、zl → |
| 決定 | z＋キーの記号を広げる | z. …、z- 〜、z/ ・、z\[ 『、z\] 』 |
| 決定 | 読みから記号を出す | 「やじるし」→ ←→↑↓、「ほし」→ ★☆、「おなじ」→ 々 |
| 決定 | 数字の変換 | 「1234」→ 1,234、千二百三十四、１２３４ |
| 決定 | 電卓 | 「1+2=」→ 3 |
| 決定 | キーでの字種変換 | F6 ひらがな、F7 全角カタカナ、F8 半角カタカナ、F9 全角英数、F10 半角英数。F6〜F10がないキーボード向けに、別のキーにも割り当てられるようにする |
| 決定 | キー割り当てのプリセットを選べる | MS-IME風：Ctrl+U ひらがな、Ctrl+I 全角カタカナ、Ctrl+O 半角カタカナ、Ctrl+P 全角英数、Ctrl+T 半角英数。ATOK風：MS-IME風と同じで、半角英数が Ctrl+@、再変換が Ctrl+Shift+Y。macOS風：Ctrl+J ひらがな、Ctrl+K カタカナ、Ctrl+; 半角カタカナ、Ctrl+L 全角英字 |
| 決定 | Shift＋英字で一時的に英数入力 | 「API」「Kubernetes」をモードを切り替えずに打てる |
| 決定 | 顔文字・絵文字の候補 | 「かお」→ 顔文字 |

Google日本語入力のサジェスト（入力途中の予測候補）は、FR-06とFR-08に反するため取り入れない。

### 実装方針

- **Rewriterとして実装する**：変換結果に後から候補を足す部品（Rewriter）にする。日付・記号・数字・電卓をそれぞれ独立したRewriterにして、追加や削除をしやすくする。Mozcと同じ考え方
- **値が変わる候補は書式を学習する**：日付のような候補は、文字列ではなく「どの書式を選んだか」を学習する。「2026/10/10」という文字列そのものを学習すると、翌日以降に古い日付が上位に出てしまうため
- **辞書の候補を押しのけない**：動的な候補は、辞書の上位候補（「今日」など）より後ろに入れる
- **ローマ字表はデータファイルにする**：z＋キーの記号はローマ字表の行として持つ。ローマ字表はユーザーが編集できる設定ファイルにする。かな入力ではz＋キーは使えない（JISかな配列でzは「つ」のキーのため）
- **キー割り当ても設定ファイルにする**：字種変換などのキー割り当てを変更できるようにする。プリセットとして「MS-IME風」と「macOS風」を同梱し、設定で選べるようにする。プリセットを選んだ上で、個別のキーを上書きできるようにする

## 文脈を使った変換

こまめに確定する使い方では、左側の文脈はIME自身の確定履歴として必ず手元にある。これを主軸にし、OSから周辺テキストが取れるときはそれで補強する。

### 文脈の取得元

1. **入力欄の周辺テキスト**：OSのAPIで取れる場合に使う。カーソルの前を優先し、後ろは補助的に使う
2. **IMEの確定履歴**：同じ入力欄・同じセッションで確定した文字列。どのアプリでも必ず使える

取得の制約：

- 見るのはフォーカス中の入力欄の中だけ。別ウィンドウや画面全体は見ない
- パスワード欄（secure field）では、文脈も学習も使わない

| OS | 周辺テキストの取得API | 取れない主な場面 |
| --- | --- | --- |
| macOS | IMKのクライアントへの問い合わせ（選択範囲、範囲指定での文字列取得） | ターミナル、一部のElectron/Webアプリ |
| Windows | TSFの ITfContext → ITfRange::GetText | TSFに完全対応していないアプリ（IMM32系） |
| Linux | Fcitx5の surrounding text | ターミナル。Waylandのtext-input-v3は取得量に上限あり |

### 順位付けの構成

- **ベース**：単語コストと連接コスト（ラティス＋Viterbi）
- **文書内キャッシュ**：周辺テキストや確定履歴にすでに出ている語を加点する。最も安く、効果も大きい
- **話題スコア**：差し替え可能なRankerインターフェースとして実装する。候補はWord2Vecなどの単語ベクトルの類似度と、小型LMによる再ランキング。どちらにするかは評価セットでの実験で決める
- **小型LMを採用する場合**：左文脈の計算結果をキャッシュし、確定で伸びた分だけ差分計算する

### 学習

学習は文脈付きにする。「最後に選んだ候補を1位にする」だけの学習は採用しない。技術文書で「品詞」を選んだ後に小説で「瀕死」が出なくなるような、文脈を無視した上書きを防ぐため。

## 属性プロファイル

ユーザーがよく書く分野（例：IT）を登録し、文脈がまだ少ないときの「事前情報」として使う。文脈が溜まるほど文脈を優先し、プロファイルの影響は小さくする。

### 位置づけ

- **プロファイル＝事前情報、文脈＝証拠**：文書の書き出しなど文脈が少ないときはプロファイルが効き、文脈が増えるにつれて文脈の判定が勝つ
- **学習との関係**：プロファイルは使い始めの初期値。使い込むほど学習の比重が大きくなる

### 入力方法

- 分野をプリセットから複数選ぶ（例：IT・ソフトウェア、インフラ・クラウド）。分野ごとに「よく使う／たまに使う」の重みを付ける
- 自分が書いた文章を取り込んで、分野ベクトルを自動で作る（「文章の取り込み」の節を参照）

### 効果

- **分野別の語彙パック**：基本辞書にない専門語を有効にする
- **候補の加点**：分野ベクトルと候補語の近さに応じて加点する

### 制約：文法で決まる箇所は上書きしない

分野で加点すると、文法的に誤った候補が勝つおそれがある。例：IT分野を強めると、「ドキュメント化しよう」の「しよう」が「仕様」に化ける。これを防ぐため、次のルールを設ける。

- 加点は内容語（名詞など）同士の比較にだけ適用する
- 品詞と連接で文法的に決まる箇所（動詞の意志形「しよう」、助動詞など）は、加点で覆さない
- 加点には上限を設け、ベースのコスト差が大きい場合は覆らないようにする
- 評価セットに否定ケースを必ず入れる（「ドキュメント化しよう」→しよう、「APIの」の後の「しよう」→仕様）

### 保存と範囲

- 端末ごとに設定し、同期しない（端末ごとに使うシーンが違う、という方針に合わせる）
- エクスポート/インポートの対象に含める
- （候補）アプリごとにプロファイルを切り替える。macOSはクライアントのバンドルID、Windowsはプロセス名で判別できる

## 文章の取り込み（初期学習）

自分が過去に書いた文章を取り込み、書き方のクセを初期学習データとして持たせる。使い始めから自分向けの変換になるようにするため。データは学習データと同じ形式に変換するので、新しいデータの種類は増やさない。

### 学べるもの

| 学べるもの | 例 | 反映先 |
| --- | --- | --- |
| 表記の好み | 「ユーザ／ユーザー」「行う／行なう」「こと／事」 | 学習データ（候補の順位） |
| 文脈ごとの同音異義語の選び方 | 技術文書では「品詞」 | 学習データ（文脈付き） |
| よく使う分野 | IT、インフラ | 属性プロファイルの分野ベクトル |
| 辞書にない語 | 社内用語、製品名 | ユーザー辞書の登録候補（ユーザーが確認） |

区切り方（どこで確定するか）は学べない。普通の文章には確定した位置が残っていないため。

### 処理の流れ

1. IMEが同梱するプロンプトと自分の文章（.txt、.md）を、ユーザーがクラウドLLMに入力する。Markdownのコードブロック、インラインコード、URLは除外するよう、プロンプトで指示する。技術記事のコードで学習が汚れるのを防ぐため
2. LLMが返した「文単位の表記と読み」のファイルを、IMEに渡す
3. IMEが辞書で表記と読みを照合し、単語に分割する。辞書で読みを再現できない組は捨て、件数を報告する
4. 文脈の特徴量付きで初期学習データを作る。同じファイルをLoRA学習の教師データにも使う。IMEの内部データには原文を持たない
5. 辞書にない語は読みが確定できないので、推定した読みと一緒に「登録候補」として一覧表示する。ユーザーが確認したものだけをユーザー辞書に入れる

### ルール

- 初期学習は、実際の使用による学習とは別の層として持ち、重みを低くする。使い込むほど実際の学習が優先される
- 初期学習の層だけを削除・やり直しできる。実際の学習は残す
- エクスポート/インポートの対象に含める
- IME自体の処理はローカルで行う。クラウドLLMへの入力はユーザー自身が行う（NFR-21）
- コマンドラインで先に実装し（フェーズ1）、画面からの取り込みと取り込み元の一覧（NFR-26）はフェーズ3で作る（CLI で先に行う）。ユーザー辞書の画面は前倒しして、フェーズ3a で作る（[ADR 0005](adr/0005-macos-settings-and-indicator.md) §15.1-7）

### 効果の測り方

取り込む文章の一部（例：2割）を評価用に取り分け、その読みを入力して元の表記に戻るかを測る。取り込みの前後で1位の正解率を比べる。自分の文章そのものが、自分専用の評価セットになる。

## ユーザー辞書・学習・エクスポート/インポート

データは端末ごとに独立させ、同期はしない。端末間の移行はエクスポートとインポート（上書き）で行う。

### ユーザー辞書

- 読み・表記・品詞を登録する
- 画面には簡略化した品詞を出し、内部の細かい品詞IDに対応付ける。例：名詞、固有名詞（人名・地名・組織名）、動詞、形容詞、副詞、短縮よみ
- 動詞を登録するときは活用型（例：五段・ラ行）を指定する

### 学習

- 端末ごとに独立させ、同期しない。端末ごとに使うシーンが違うため
- 文脈の生テキストは保存しない。ハッシュ化した語や話題ベクトルなどの特徴量だけを保存する。エクスポートファイルが漏れても、書いた文章が復元されないようにするため

### エクスポート/インポート

- **対象**：ユーザー辞書、学習データ、属性プロファイル
- **インポート**：既存データを上書きする（マージはしない）
- **形式**：ファイルにスキーマのバージョンを入れる。辞書やモデルを更新した後でも、インポート時に変換または検証できるようにする
- ユーザー辞書の形式は、Mozc/MS-IME互換のTSVを候補とする（未決）

## 非機能要件

## アーキテクチャと辞書のデータ構造

変換と順位付けは共通コア（Rust）に集約する。OSごとの実装は、キー入力の受け取り、周辺テキストの取得、候補の表示だけを担う薄い殻にする。

&#91;embedded content: 構成 · OSの殻、ime-core、データファイル\]

デスクトップ版では、変換エンジン（ime-core）を常駐の別プロセスとして動かし、OSの殻とはプロセス間通信でつなぐ（NFR-14）。エンジンが落ちても、殻だけで最低限の入力を続ける（NFR-16）。外部と通信するのは辞書の更新プロセスだけで、殻と変換エンジンは通信しない。スマホ版は別プロセスを常駐させにくい（特にiOSのキーボード拡張）ため、同じコアをライブラリとして組み込む。そのため、コアはプロセスとしてもライブラリとしても動く形にしておく。データファイルは全OSで共通のバイナリを使う。

### プロセス間通信

殻と変換エンジンの間には全アプリのキー入力が流れるため、セキュリティを最優先に方式を選ぶ。別ユーザーや外部からの接続はどの方式でも防げるので、守る相手は同じユーザー権限で動く悪意あるプロセスとする。具体的には、エンジンになりすましてキー入力を受け取る攻撃と、サンドボックス内のアプリなどから接続して学習データを引き出す攻撃。

| OS | 方式 | 必須の対策 |
| --- | --- | --- |
| macOS | XPC | サービス名はlaunchdに管理させ、アプリに同梱したサービスだけが待ち受けられるようにする。殻とエンジンは互いのコード署名を検証する。XPCサービスはSwiftの薄い殻にし、中でRustのコアをライブラリとして呼ぶ |
| Windows | 名前付きパイプ | 最初のインスタンスとして作成し、同じ名前が先に作られていたら起動を失敗させる（FILE\_FLAG\_FIRST\_PIPE\_INSTANCE）。ACLで接続できる相手を自分のユーザーと、必要ならストアアプリに絞る。リモートからの接続を拒否する（PIPE\_REJECT\_REMOTE\_CLIENTS）。殻は接続先のプロセスIDから実行ファイルのパスと署名を確認する（GetNamedPipeServerProcessId）。殻からの接続のなりすましレベルは「識別のみ」にする |
| Linux | Unixドメインソケット | ソケットファイルは $XDG\_RUNTIME\_DIR に置く。SO\_PEERCRED で接続相手のUIDとプロセスIDを確認する。抽象名前空間のソケットは使わない |

全OS共通：

- 通信路はRust側でtraitとして抽象化し、OSごとに実装を差し替える
- メッセージはprotobufで定義し、スキーマのバージョンで殻とエンジンの互換性を管理する
- 接続は張りっぱなしにし、エンジンが再起動したら自動で再接続する（NFR-02、NFR-16）
- 受け取ったメッセージは両側で信用しない入力として扱い、ファジングでテストする
- エンジンは最小権限で動かす。macOSではApp Sandboxに入れ、ネットワークの権限を与えない（NFR-17）
- パスワード欄の入力は送らない（NFR-18）

### 辞書のデータ構造（スマホ版でも使える形にする）

- **索引**：FSTまたはダブル配列トライ。完全一致と前方一致の両方に対応する。PCでは完全一致だけを使い、前方一致はスマホ版の補完用に残す。Rustの候補クレートは fst、crawdad
- **読み込み**：読み取り専用のバイナリをmmapで開く。常駐メモリを抑え、iOSのキーボード拡張のメモリ上限に備える
- **システム辞書とユーザー辞書を分ける**：システム辞書は変更しないバイナリ、ユーザー辞書は小さく書き換え可能な別ファイル。引くときに両方の結果を合わせる
- **バイナリ形式**：リトルエンディアン固定。ヘッダにマジックナンバー、バージョン、品詞表のバージョンを入れる。ARM64とx86\_64で同じファイルを使う
- **エントリ**：表記、左右の品詞ID、コスト、語ID
- **単語ベクトル**：語IDで引く別ファイルにする。Rankerの方式を変えても、辞書本体を作り直さない
- **分割**：基本語彙と拡張語彙（分野別の語彙パックを含む）を別ファイルにする。スマホでは容量に応じて選ぶ
- **連接コスト表**：品詞同士のつながりやすさの表も、mmapで開くバイナリにする

## 辞書の更新

辞書はできるだけ大きいもの（SudachiDictのFull版）を使い、最新版に自動で追従する。自動更新するかどうかはユーザーが選べる。通信はダウンロードだけで、ユーザーのデータは送らない。

### 方針

| 状態 | 内容 |
| --- | --- |
| 決定 | 辞書は可能な限り大きいもの（SudachiDict Full）を使う |
| 決定 | 最新版を常に追う |
| 決定 | 辞書の更新は自動で行う。自動更新するかどうかはユーザーが選べる |
| 決定 | 通信はダウンロードのみ。入力内容、学習データ、ユーザー辞書などのユーザーのデータは送らない |
| 決定 | 自動更新は初期値で有効にする |

### 安全策

ダウンロードだけでも、取得したファイルが壊れていたり改ざんされていたりすると、全アプリのキー入力を扱うIMEに影響する。次の対策で、通信する部分とキー入力を扱う部分を切り離す。

| 状態 | 内容 |
| --- | --- |
| 決定 | 通信するのは独立した更新用プロセスだけにする。キー入力を扱う殻と変換エンジンには、通信する機能を持たせない |
| 決定 | 取得元はSudachiDictの公式リリースに固定し、HTTPSで取得する。取得元をユーザーデータや外部の入力から変えられないようにする |
| 決定 | ダウンロードしたファイルは信用しない入力として扱い、形式を検証してからビルドする |
| 決定 | 新版の確認は定期的（例：週1回）に行い、ダウンロードと辞書のビルドはアイドル時かつ電源接続中に行う |
| 決定 | 送るのは「最新版の確認とダウンロード」のリクエストだけにし、利用状況などの情報を付けない |
| 決定 | 自動更新を無効にした場合でも、ユーザーが手動で新版を置いて同じ手順で更新できる |

### 切り替えと互換性

| 状態 | 内容 |
| --- | --- |
| 決定 | 切り替える前に評価セットを実行する。正解率が下がったら切り替えずに旧版を使い続け、ユーザーに知らせる |
| 決定 | 新しい辞書は別ファイルに作り、入力中ではないときに一度に切り替える。旧版は残し、いつでも戻せる |
| 決定 | 学習データとユーザー辞書は、内部の語IDではなく表記・読み・品詞（文字列）で保存する。辞書を更新しても壊れないようにするため。単語ベクトルなど語IDで引くデータは辞書と同じバージョンで作り直し、ヘッダのバージョンが合わなければ読み込まない |
| 決定 | Full版は雑多な固有名詞が多く、珍しい固有名詞が一般的な語より上に出るおそれがある。固有名詞のコストを調整し、評価セットで確認する |

モデル（zenz）の更新は、これまでどおり手動とする。再学習が必要になるため（NFR-33、NFR-38）。辞書の更新では再学習は不要。

## OS別の実装メモ

macOSを最初に、次にWindowsを作る。開発の間は、どちらもローカルでビルドしてインストールする。配布の形は NFR-41、NFR-42。

### macOS（InputMethodKit）

- インストール先は `~/Library/Input Methods`。入れた後、システム設定で入力ソースを追加する
- 自分でビルドしたものは、Xcodeが付ける簡易署名（ad-hoc）で動く
- 開発中は古いIMEプロセスが残りやすい。ビルド → killall → 入力ソースの再選択、をスクリプトにしておく
- 周辺テキストはクライアントへの問い合わせで取得する。取れないアプリでは確定履歴を使う
- アプリごとのプロファイル切り替えには、クライアントのバンドルIDが使える
- 候補ウィンドウの位置は、IMKのクライアントからキャレットの矩形を取得して決める。フォールバックでアクセシビリティAPIを使う場合は、IMEにアクセシビリティ権限を与える必要がある

### Windows（TSF）

- COMのDLLとして実装し、管理者権限の `regsvr32` で登録する。自分で使うだけなら署名は不要だが、配るなら署名の要否を確かめる（#81）
- **x64用とx86用の両方のDLLが必要**。32bitアプリにはx86版が読み込まれるため。ARM版Windowsで使うならARM64版も作る
- ストアアプリ（UWP）でも使うには、DLLのファイル権限に「ALL APPLICATION PACKAGES」を付ける
- 周辺テキストは ITfRange::GetText で取得する。IMM32系の古いアプリでは取れないことがある
- 候補ウィンドウの位置は ITfContextView::GetTextExt で取得する

### Linux（Fcitx5）

- Fcitx5のアドオンとして実装する。着手はWindowsの後

## 評価計画

同音異義語の評価セットを最初に作り、変換品質の回帰テストと、ランキング方式を決める実験の両方に使う。Claude Codeに実装を任せるときの完了条件にもなる。

### 評価セットの形式

実際の使い方（短い単位でこまめに確定）に合わせ、1件を「確定済みの文脈＋短い読み→期待する表記」で表す。

| 確定済みの文脈 | 読み | 期待する表記 | 種別 |
| --- | --- | --- | --- |
| ユーザー辞書に単語を登録するときは | ひんし | 品詞 | 話題 |
| 敵の攻撃を受けて兵士は | ひんし | 瀕死 | 話題 |
| システムの | こうせい | 構成 | 話題 |
| 原稿の誤字を | こうせい | 校正 | 話題 |
| 質問への | かいとう | 回答 | 話題 |
| 冷凍した肉を | かいとう | 解凍 | 話題 |
| 要件をまとめてドキュメント化 | しよう | しよう | 否定（文法優先） |
| 外部APIの | しよう | 仕様 | プロファイル |
| この | の | の | 機能語 |

### 指標

- 1位の正解率（全体、種別ごと）
- 平均逆順位（MRR）
- p99と最悪値の応答時間、常駐メモリ
- プロファイルあり・なしでの差分。否定ケースの正解率が下がらないことを必須とする

### 運用

- CLIから実行し、レポートを出力する
- テストとして毎回実行し、正解率が下がる変更を検知する
- 実際に誤変換に気づいたら、そのケースを追加する（例：「ひんし」→「瀕死」）

## 実装の進め方（Claude Code向け）

Claude Codeには1フェーズずつ依頼し、各フェーズの完了条件をテストで示す。まずはフェーズ0から始める。

### リポジトリ構成

決着した。現在の構成は [docs/architecture.md](architecture.md)、決めた経緯は [ADR 0001 §2](adr/0001-phase0-architecture.md) と [ADR 0004 §3、§6](adr/0004-phase2-macos.md)。`windows/`（TSFの殻、C++）は Windows 版の段で足す。

### フェーズ0の作業

- [ ] core：ローマ字・かな入力から読みへの変換
- [ ] core：辞書引き（完全一致と語分割）、ラティス＋Viterbiでの候補生成
- [ ] core：Rankerをtraitとして定義し、ベース実装（コストのみ）を入れる
- [ ] dict-builder：辞書ソースからバイナリ辞書（FSTまたはダブル配列、mmap、ヘッダ付き）を作る
- [ ] cli：文脈と読みを渡すと候補をN件出す
- [ ] eval：評価セットを読み込み、正解率とMRRのレポートを出す

### フェーズ0の完了条件

- テストがすべて通る
- CLIで「ひんし」を変換すると「品詞」と「瀕死」が候補に出る
- 評価スクリプトがレポートを出力する（この時点では正解率は問わない）

### 依頼するときの原則

- 依頼時に本書を渡し、該当フェーズと完了条件を明示する
- Rankerは差し替え可能に保つ。実装方式（Word2Vecか小型LMか）をコアに埋め込まない
- 辞書ソースのライセンス確認は人間が行う。Claude Codeには確認済みのソースだけを使わせる
