## 0. 現状の把握

コードと手元の環境で確かめた事実と、推測を分けて書く。推測には「（推測）」、確かめていないことには「（未確認）」を付ける。

### 0.1 モードと入力ソース（コード）
- ikari の入力モードは日本語の 1 つだけ（`ikari.Info.plist` の `ComponentInputModeDict` は `io.github.ikari-zen.inputmethod.ikari.Japanese` だけ。モードの辞書のキーも TISInputSourceID も同じ値）。英数モードは 911242d で消した（ADR 0005 §15.2-1）。
- 消す前の英数モードは、辞書のキー `io.github.ikari-zen.inputmethod.ikari.Roman`、`tsInputModeScriptKey = smRoman`、`TISIntendedLanguage = en`、`tsInputModePrimaryInScriptKey = false` だった。**`tsInputModeJISKeyboardShortcutKey` はなかった**（git の 911242d の差分）。
- 殻は `setValue(_:forTag:)`（モードの変化の通知）を上書きしていない。モードが 1 つなので要らない。
- 英数キー（0x66）とかなキー（0x68）は、`handle(_:client:)` の先頭で受け止めて何もしない（`absorbedKeyCodes`。ADR 0005 §15.2-5）。
- ADR 0005 §15.2 の S0-2（2026-10-12、実機）: かなキーの keyDown は入力ソースが切り替わったあと殻にも届く。**英数キーは、ABC が有効だと macOS が ABC に切り替え、殻には届かない（0 回）**。このとき ikari の英数モード（上の形）がシステム設定で有効になっていたかは記録がない（未確認）。

### 0.2 キーの受け取り方（コード）
- `handle(_:client:)` は keyDown だけを見る。打鍵のたびに `IsSecureEventInputEnabled()` を読んで状態機械に渡す（変わったら `BeginSession` を送り直す。secure の間は文脈を取らず、先行計算も確定の通知も送らない。NFR-18）。**secure でも変換はする**（日本語モードのまま。アプリに素通しにはしない）。
- 文字は `event.characters`（Ctrl / Option / Command があるときは `charactersIgnoringModifiers`）から取る。`KeyCodes.keyInput` は、特別なキー（Space、Enter、矢印など）、F キー、**かな入力の設定なら JIS の位置にあるキーコードを `.jis(番号)` に**、それ以外は `.character(文字)` にする。
- **かな入力（`input.method = kana`）では、キーコードだけで文字を決め、`characters` を見ない**。キーコードが JIS の位置表（A〜Z、数字、記号の 48 キー）にあれば、届いた文字が何であっても JIS のかなになる。
- ローマ字入力では、`.character` の文字を Unicode のスカラーごとに `ikari_composer_push_char` へ渡す。Rust の `RomajiComposer::push` は、表にない文字（ASCII 以外）を**そのまま読み（`kana`）に足す**（規則 3 の `p.is_empty()` の枝）。
- `isPrintable` は、制御文字、私用領域（矢印キーの U+F700 台）、サロゲート、未割り当て以外を「打てる文字」とする。絵文字、漢字、かなは打てる文字。
- 変換中（`converting`）に打てる文字が来ると、1〜9 の半角数字は候補の選択、それ以外は今の表示を確定してから、その文字で新しい合成を始める（`continueAfterCommit`）。
- 確定は `client.insertText(text, replacementRange: NSNotFound)`（`ClientAccess.insert`）。文字列をそのまま渡すので、絵文字や結合文字も壊さない（コードから。実機の表示は未確認）。

### 0.3 直接入力の Unicode が今どうなるか（コードから推せること。実機は未確認）
| 届き方 | ローマ字入力の ikari | かな入力の ikari |
| --- | --- | --- |
| 漢字・絵文字が `characters` に入り、キーコードが JIS の位置表の外 | 読みに足され、**変換中の文字列（下線）になる**。Enter で確定するまで残る。Space を押すと、その文字を読みとして変換しようとする（エンジンは読みの文字を検証していない。何が返るかは未確認） | 同じ（`.character` になる） |
| 漢字・絵文字が `characters` に入り、キーコードが JIS の位置表の中（例: キーコード 0 = A の位置） | 同上 | **キーコードで JIS のかなになり、届いた文字は捨てられる**（キーコード 0 なら「ち」）。合成した Unicode の打鍵はキーコード 0 で届くことが多い、というのは推測（未確認） |
| かな（「か」）が `characters` に入る | 読みに足される。かな漢字変換できる | キーコード次第（上の 2 行） |
| `¥`（JIS の ¥ キー、ABC の配列） | 読みに `¥` が足される（今の動き） | JIS の位置表（93）で「ー」 |

- 自作キーボードが Unicode をどう送るか（ファームウェアが Option＋16 進で送る、ホストのツールが合成の打鍵を送る、独自のキー配列ファイル、貼り付け、など）は、下書きの時点で**分からなかった**（Q10）。方法によって、IME に届くか、どのキーコードで届くかが変わる。
- 2026-10-18 のユーザーの答え: 直接入力の Unicode は**今は使っていない。将来できるようにしたい**。送るなら **ZMK**（QMK ではない）の予定。ZMK の送り方が ikari にどう届くかは §8.5。

### 0.4 文脈と確定履歴（コード。ADR 0015 の実装後）
- `CommitText { session_id, reading, surface }` はエンジンの確定履歴（`push_history`）に入るだけで、**学習はしない**（`engine/src/convert.rs` の `commit_text`）。secure と休止中のセッションでは何もしない。`share` のセッションなら、アプリをまたぐ「最近の確定」にも入る（ADR 0015 D5、D6）。
- 除外の設定 `context.shared_exclude` の既定は、パスワード管理（1Password、Bitwarden、キーチェーンアクセス）とターミナル（Terminal、iTerm2、WezTerm、Ghostty）。判定は殻の中だけ（`Settings.sharesContext`）。意味は「ほかのアプリと文脈を貸し借りしない」で、**記録しない、という意味ではない**。
- 殻からエンジンへの片道の送信（`post`）は返事を待たない。つながっていなければ捨てる。再接続のときも hello と `BeginSession` を待たずに送り直す（`XPCEngineClient.prepare`）。打鍵の経路を止めない。

### 0.5 手元の macOS 27 の入力ソース（読み取りだけで調べた。付録 A）
`TISCreateInputSourceList` で、入っている入力ソースの属性を読んだ（2026-10-17）。

| 入力ソース | モードの ID（`kTISPropertyInputModeID`） | ASCII を打てる | 有効 |
| --- | --- | --- | --- |
| ABC（`com.apple.keylayout.ABC`） | ― | ○ | ○ |
| ikari（`io.github.ikari-zen.inputmethod.ikari.Japanese`） | `io.github.ikari-zen.inputmethod.ikari.Japanese` | × | ○ |
| Google 日本語入力の英数（`com.google.inputmethod.Japanese.Roman`） | `com.apple.inputmethod.Roman` | ○ | × |
| azooKey の英数（`dev.ensan.inputmethod.azooKeyMac.Roman`） | `com.apple.inputmethod.Roman` | ○ | × |
| ことえりの英字（`com.apple.inputmethod.Kotoeri.RomajiTyping.Roman`） | `com.apple.inputmethod.Roman` | ○ | × |
| Google、azooKey、ことえりの日本語のモード | `com.apple.inputmethod.Japanese` | × | ○（3 つとも） |

- **今、ASCII を打てる入力ソースで有効なのは ABC だけ**。
- ほかの IME の英数のモードは、どれもモードの ID が `com.apple.inputmethod.Roman` で、ASCII を打てる（`kTISPropertyInputSourceIsASCIICapable = true`）。ikari の日本語のモードは独自の ID。
- ikari のほかに、ことえり・Google・azooKey の日本語のモードも有効になっている。かなキーでどれが選ばれるかに関わりうる（§7 の前提に書く）。
- **2026-10-18 に読み直した結果**（`TISCreateInputSourceList(nil, false)`。読み取りだけ）: 有効な入力ソースは ABC と ikari（と、文字ビューアなどのパレット類）だけになっていた。ことえり・Google・azooKey の日本語のモードは有効でない（10-17 のあとでユーザーが外したと思われる。推測）。**「Unicode 16 進入力」（`com.apple.keylayout.UnicodeHexInput`）も有効でない**（§8.5 に関わる）。

### 0.6 ほかの IME の Info.plist（`/Library/Input Methods/` の azooKey と Google 日本語入力）
- モードの辞書の**キーに Apple の決まった名前**（`com.apple.inputmethod.Japanese`、`com.apple.inputmethod.Roman`、Google は `…Japanese.Katakana` なども）を使い、`TISInputSourceID` に自分の ID を入れている。
- 各モードに `tsInputModeJISKeyboardShortcutKey` がある。azooKey は日本語 = 1、英数 = 3。Google は日本語 = 1、英数（`com.apple.inputmethod.Roman`）= 3、全角英数 = 0、カタカナ = 2。
- 推測: `tsInputModeJISKeyboardShortcutKey` は、JIS のかなキー（1）と英数キー（3）でどのモードを選ぶかを macOS（TSM）に伝える値。**以前の ikari の英数モードには、この値も Apple の決まったモードの名前もなかった。S0-2 で英数キーが ABC に行ったのはこのためかもしれない**（未確認。スパイク S-A の T1 で確かめる）。
- SDK（MacOSX 27.0）の HIToolbox に `TextInputSources.h` のヘッダはなく、これらのキーの説明は手元で読めなかった。
- 2026-10-18 に Info.plist を読み直した。Google の英数（`com.apple.inputmethod.Roman`）は `tsInputModeIsVisibleKey = true`、`smRoman`、`JISKeyboardShortcut = 3`。全角英数（`com.apple.inputmethod.Japanese.FullWidthRoman`）は `smJapanese`、`JISKeyboardShortcut = 0`。azooKey の英数も `IsVisible = true`、`JISKeyboardShortcut = 3`。
- **ユーザーの観察（2026-10-18）**: 「ほかの IME には半角英数モードがない。Google 日本語入力は全角英数の入力モードはある。このモードは ikari 独自の機能になる」。Info.plist には半角英数のモードが宣言され、TIS の一覧にも出る（§0.5。有効でない）のに、ユーザーからは選べるモードとして見えていない。**システム設定が、ほかの IME の `com.apple.inputmethod.Roman` のモードを一覧に出していない（有効にできない）可能性がある**（推測。未確認）。そうなら、ikari が同じ名前で英語のモードを宣言しても、有効にできないかもしれない。以前の ikari の英数モード（辞書のキーは独自の `io.github.ikari-zen.inputmethod.ikari.Roman`）はユーザーから見えていた（user-feedback.md §3 の「英数モード（A）は要るのか」）。名前の違いで見え方が変わるのかは、S-A の T1 と T8 で確かめる。

### 0.7 打鍵の統計に関わる今の仕組み
- 打鍵を数える仕組みはない。エンジンのログ（`logs/engine.log`）は変換ごとの時間と固定の注記だけで、読みや文字は書かない（NFR-19）。
- ユーザーデータはエンジンが書く（`learning.tsv` など。`~/Library/Application Support/ikari-ime/`。エンジンの Sandbox はこのフォルダの読み書きだけを一時例外で許す）。学習はエンジンのメモリが正で、5 秒ごとと `EndSession` で保存する。設定アプリからの消去とエクスポートは管理のメッセージ（engine.proto の 40〜53）と自動のバックアップで行う（ADR 0005 §8）。
- `learning.tsv` は、読みと表記の組（語の単位）とその回数を平文で持つ（文はない）。NFR-19 の「原文を持たない」は、この粒度を許すものとして運用している。

## 1. 要望（2026-10-17。原文に近い形）
1. 英語版の IME（英語モード）を入れたい。**目的は打鍵の統計の記録**（各キーの打鍵数、連続する n 文字（n ≤ 3）の頻度）。文脈が取れたら取る（今の LM は英語に弱いが、将来、英語も解釈できる AI に替えたときに文脈に使える）。
2. 英語モードでは**変換を挟まず、記録して、確定した状態でアプリに渡す**。
3. 英数キーを押すと macOS が ABC に切り替えて IME を止めてしまう。それをやめて、**ikari の英語モードにできないか**。ABC は macOS が必須にしていて外せない（user-feedback.md §3）。
4. モードの遷移: IME OFF → ikari 日本語 → ikari 英語 → ikari 日本語（の順で循環できる形が望ましい）。キー（英数、かな、Ctrl+Space など。自作キーボード）ごとに何が起きるかを設計する。
5. **パスワード入力欄（セキュア入力）のときだけ IME OFF**。そのとき打鍵は記録しない。
6. 漢直や JIS のかな配列で**かな・漢字を直接打ったとき**と、自作キーボードが送る**絵文字などの Unicode** を、ikari が壊さずに出力する。
7. （2026-10-18 の追加）統計は、**日本語のローマ字の打鍵でも取る**。さらに、**最終的に入力された文字（確定した文字列。ひらがな、カタカナ、漢字など）でも取る**。統計は**既定でオフ**にし、設定アプリからオンにする（§11.1）。

## 2. ADR 0015 D9 と ADR 0005 §15.2 を改める理由

### 2.1 再検討の条件（ADR 0015 §6.6）との照合
| 条件 | 今の状態 |
| --- | --- |
| 1. 英語を含む左文脈で効く LM を使える | 満たさない（zenz small のまま。§0.6 の 32 件で +1） |
| 2. S1 で、周辺テキストを返さないアプリで英語と日本語を行き来する変換が多いと分かった | 分からない（S1 の集計はまだ） |
| 3. ユーザーが、ABC の機能を使わず、英語の入力ソースを ikari に一本化したいと決めた | **満たす**。要望 3（英数キーで ikari の英語モードに入りたい）と 4（OFF はパスワード欄だけ）は、ふだんの英語を ikari で打つという決定にあたる |

加えて、**D9 の判断の根拠は「英語の文脈の効きが小さい」だけ**で、要望 1 の目的（打鍵の統計）は D9 のときに考えていなかった新しい目的である。D9 の「得るものが小さい」は、統計という目的には当てはまらない。危険（ADR 0015 §6.4〜6.5: すべての英語の打鍵が ikari を通る、秘密を拾う、ABC の機能を失う）は残るので、§9 で軽減を決める。

### 2.2 改める点
| 決定 | 今 | 改めたあと（提案） |
| --- | --- | --- |
| ADR 0015 D9 | 英語モードは今は作らない | 作る。目的は打鍵の統計で、文脈はついで（§3 の D1、D6） |
| ADR 0005 §15.2-1 | 英数モード（.Roman）をなくす。英語は ABC に任せる | ikari に英語のモードを足す。ただし「英数」（全角・半角の英数を打つ変換のモード）ではなく、**打鍵をそのままアプリに渡し、記録だけする**モード。ABC は残す（§3 の D3） |
| ADR 0005 §15.2-5 | 英数・かなキーは受け止めるだけで何もしない | 英数キーで英語のモード、かなキーで日本語のモード（macOS が切り替える。届いた打鍵は今どおり受け止める） |
| ADR 0005 §15.2-2 | 独自のモード表示は作らない | 変えない（macOS の表示に任せる）。メニューバーのアイコンは英語のモードの分を足す（ADR 0005 §3 の「A」のアイコンを使う） |

## 3. 決定の要約（2026-10-18 承認。[S-A] の印の項目は、スパイク S-A の結果で確定する）

| # | 項目 | 提案 |
| --- | --- | --- |
| D1 | 英語のモード | ikari の Info.plist に 2 つ目のモードを足す。`TISInputSourceID` は `io.github.ikari-zen.inputmethod.ikari.Roman`、`smRoman`、`tsInputModeJISKeyboardShortcutKey = 3`。日本語のモードには `tsInputModeJISKeyboardShortcutKey = 1` を足す。[S-A] モードの辞書のキー（`com.apple.inputmethod.Roman` にするか、独自の名前のままか）は T1・T8 で決める（§5.1）。このモードの殻は、**打鍵をすべてアプリに素通しにする**（`handle` が false を返す）。変換中の文字列も候補も出さない。**例外は ADR 0027 のショートコードの状態だけ**: その状態に入る `:` の打鍵と、状態の中の打鍵は `ShortcodeMachine` に渡し、ikari が受け止めて変換中の文字列と候補（第 1 候補はそのままの入力 `:eyes:`、第 2 候補以降は絵文字）を出す。状態の動きは ADR 0027 §3 が書く。`handle` の順は §5.2 |

| ― | 変えないもの | 日本語のモードの変換、Shift＋英字の一時的な英字（spec）、文脈の量（ADR 0015 D7）、学習の作り方、LM（zenz small のみ） |

## 4. 選択肢と比較

### 4.1 英数キーで ikari の英語のモードに入る方法（要望 3）
前提（事実）: IMK の `handle(_:client:)` は、英数キーを macOS が処理したあとでしか受け取れない（S0-2 で 0 回）。IME の側から英数キーを先に横取りする IMK の口はない（InputMethodKit のヘッダに、それにあたるものはない）。だから、どの案も「macOS がどこへ切り替えるか」を変えるか、「英数キーを別のキーにする」かのどちらかになる。

### 4.3 パスワード欄の OFF（要望 5）
事実: 殻が知れるのは `IsSecureEventInputEnabled()`（システム全体の secure の状態）だけ。パスワード欄（`NSSecureTextField`）は secure を入れる。ターミナルの「セキュアなキーボード入力」も secure を入れる（その間ずっと）。パスワード欄で macOS が入力ソースを ASCII を打てるものに替えることは知られている（Apple の日本語入力で、パスワード欄が英字になる）が、ikari の英語のモードがあるときに、macOS が ABC と ikari の英語のどちらを選ぶかは**未確認**（S-A の T3）。

| 案 | 内容 | 判断 |
| --- | --- | --- |
| **O1** | secure の間、ikari はどのモードでも打鍵を素通しにする（変換しない。変換中の文字列も出さない）。記録も文脈も送らない。入力ソースは替えない | **推奨**。確実に「何もしない」状態にでき、元に戻す処理が要らない（secure が外れたら次の打鍵から元どおり）。ikari の英語のモードがパスワード欄で選ばれても、拾わない |

| O3 | 今のまま（secure でも日本語に変換する。文脈と学習だけ止める） | 要望 5 に合わない。ただし、ターミナルで「セキュアなキーボード入力」を常に入れている場合、O1 だとそのターミナルで日本語が打てなくなる（Q4） |

## 5. 設計: モード、キー、パスワード欄、英語の文脈

### 5.1 Info.plist のモード（D1）
- 日本語: 今のモードに `tsInputModeJISKeyboardShortcutKey = 1` を足す。
- 英語: 新しいモード。`TISInputSourceID = io.github.ikari-zen.inputmethod.ikari.Roman`、`TISIntendedLanguage = en`、`tsInputModeScriptKey = smRoman`、`tsInputModePrimaryInScriptKey = false`、`tsInputModeJISKeyboardShortcutKey = 3`、`tsInputModeIsVisibleKey = true`、アイコンは ADR 0005 §3 の「A」（輪郭の円。`ikari-roman.pdf` は 911242d の前の版に残っている）。表示名は「ikari（A）」（ADR 0005 §15.1-2 の案）。
- **モードの辞書のキー**（`kTISPropertyInputModeID` になる値）: ほかの IME は `com.apple.inputmethod.Japanese` / `com.apple.inputmethod.Roman` を使う（§0.6）。英数キーの行き先がこのキーで決まるなら、ikari もこれに合わせる。ただし、**日本語のモードのキーを `io.github.ikari-zen.inputmethod.ikari.Japanese` から変えると、システム設定の「有効な入力ソース」から ikari が外れ、追加し直しが要る可能性がある**（有効な入力ソースはモードの ID で覚えている、というのは推測）。S-A の T1 と T8 で、(a) 英数キーの行き先に辞書のキーが効くか、(b) キーを変えたときに有効な一覧から外れるか、を確かめてから決める。
- `tsVisibleInputModeOrderedArrayKey` は 日本語、英語 の順。

### 5.2 殻のモードの扱い（`IkariInputController`）
- `setValue(_:forTag:client:)` を上書きし、`kTextServiceInputModePropertyTag` の値（モードの ID）から今のモード（日本語／英語）を決める。日本語 → 英語のときは、合成中なら今の表示のまま確定し（変換しない）、候補ウィンドウを閉じる。どちらの向きでも、英語の文脈のたまり（§5.5）を送る。
- **英語のモードでも、変換中の文字列（ADR 0027 のショートコード。`:ey` や選んでいる候補）があれば、モードの切り替え、secure になったとき（D5）、`deactivateServer`、`commitComposition`（クリックなど）で、今の表示のまま確定する**（日本語のモードの合成の扱いと同じ。ADR 0027 §3.3・§3.4 の最後の行）。確定した文字列はたまり（§5.5）と確定文字列の統計（§6.3）に入る。
- コントローラはクライアントごとに 1 つのまま。モードが替わってもセッション ID は変えず、`BeginSession` も送り直さない（確定履歴を切らさない。ADR 0015 D1）。`activateServer` / `deactivateServer` がモードの切り替えで呼ばれるかは未確認（S-A の T1 で記録する）。
- `handle(_:client:)` の順番:
  1. keyDown 以外は今どおり false。
  2. 英数・かなキー（0x66、0x68）は今どおり受け止める（切り替えたあとに届く打鍵の空白を防ぐ。S0-2）。
  3. `IsSecureEventInputEnabled()` を読み、状態機械に渡す（今どおり）。
  4. **secure なら**（D5。決定）: 合成中・変換中（英語のモードのショートコードを含む）なら今の表示のまま確定し、**打鍵はアプリに素通しにする**（false）。記録しない。文脈を送らない。
  5. **英語のモードなら**、次の順:
     1. 記録の判定（§6.7）を通ったら、打鍵を記録に回す（ショートコードの状態の中の打鍵も、物理的に打ったキーなので数える。§6.2）。
     2. キー割り当ての `mode.toggle` / `mode.japanese` なら、ショートコードの表示があれば確定してから、`client.selectMode` で日本語にして true。
     3. `ShortcodeMachine.handle` に渡す（ADR 0027 §3。入る `:` の判定に、たまりの最後の文字を渡す）。受け止めたら true。打ち直しや確定で文字列をアプリに入れたら、それをたまりに足す。
     4. 何も返さなければ、打鍵の文字をたまりに足して **false（素通し）**。
  6. 日本語のモードなら今の経路（`InputStateMachine`。日本語のモードのショートコードの状態も、ADR 0027 でこの中に入る）。記録の判定（§6.7）を通ったら、打鍵を記録に回す（Q5 の決定）。読みに入ったキーか、操作として使われたキーかは状態機械の結果で決まるので、記録は状態機械が返したあとに行う（§6.2 の区切り）。
  7. どちらのモードでも、確定（`insertText`）のたびに、判定を通ったら `RecordCommitted` を送る（§4.4 の C2）。
- 英語のモードの経路は、エンジンを同期で呼ばない（記録と文脈は `post`。§0.4）。**ショートコードもこの約束を守る**: 名前と絵文字の表はセッションの開始時に非同期で受け取り（ADR 0027 §9.2 の `EmojiTableRequest`）、打鍵の経路では殻のメモリの表だけを引く。表が届いていなければショートコードの状態に入らない（素通し）。殻の中の判断は AppKit に依存しない純関数（`IkariShellCore`）に置き、`swift test` で確かめる。

### 5.3 キーと遷移（D4）
| キー | OFF（ABC） | ikari 日本語 | ikari 英語 | 確かさ |
| --- | --- | --- | --- | --- |
| かな（0x68） | ikari 日本語へ（macOS が切り替える） | そのまま（届いた打鍵は受け止める） | ikari 日本語へ（macOS。`JISKeyboardShortcut = 1`） | ABC → 日本語は今の動き。日本語の IME が複数有効なとき（§0.5）にどれへ行くかは未確認 |
| 英数（0x66） | ABC のまま（推測） | **ikari 英語へ**（K1） | そのまま | 未確認（S-A の T1） |
| `mode.toggle` に割り当てたキー（Q2） | アプリに渡る（ikari は受け取れない） | ikari 英語へ | ikari 日本語へ | ikari の中の動き。`selectMode` が効くかは S-A の T1 |
| Ctrl+Space（macOS の「前の入力ソースを選択」） | 直前に使った入力ソースへ | 同左 | 同左 | ユーザーの環境では、ikari と ikari (English) の間を行き来できた（2026-10-18。設定の影響かもしれない。理由は未確認）。macOS の標準の動きとして保証はしない。確実に切り替えるキーは、地球儀キー、英数・かなキー、`mode.toggle` |
| パスワード欄に入る | ― | 機能として OFF（素通し。D5）。macOS が ABC に切り替えるなら ABC | 同左 | 未確認（S-A の T3） |

- 要望 4 の「OFF → 日本語 → 英語 → 日本語」の循環: **1 つのキーで日本語 ⇄ 英語を行き来することはできる**（`mode.toggle`）。OFF（ABC）では ikari にキーが届かないので、**OFF → 日本語は、かなキー（または macOS のショートカット）で行う**。OFF に入るのは、パスワード欄（macOS が切り替える場合）と入力メニューで ABC を選んだときだけになる。OFF の間も ikari にキーを届ける方法は、権限が要る K5・K6 しかない（採らない）。
- 自作キーボードでは、英数とかなの 2 つのキーを「英語」「日本語」の決まった状態にするのが、macOS の慣例と同じで迷いが少ない（推奨）。1 つのキーで切り替えたい場合は Q2 で決める。

### 5.4 パスワード欄（D5）の詳しい動き
- secure の判定は打鍵ごとに `IsSecureEventInputEnabled()`（今と同じ）。secure の間は、日本語でも英語でも、ikari は「何もしない入力ソース」になる。
- secure に入った瞬間に合成中なら、今の表示のまま確定する（変換しない）。パスワード欄に日本語の合成中の文字列が残るのを防ぐ。
- エンジンの側でも、secure のセッションの打鍵の記録と `CommitText` は捨てる（二重の守り。今の `push_history` と同じ）。
- **secure にならないパスワードの入力**（ターミナルの `sudo` で「セキュアなキーボード入力」が切のとき、Web のパスワード欄以外に貼るトークンなど）は、殻には区別できない。統計の除外（D8、既定でターミナル）と一時停止で守る（§6.5）。各ターミナルで `sudo` のプロンプトが secure になるかは未確認（S-A の T3）。
- ターミナルの「セキュアなキーボード入力」: ユーザーは「使っていないと思う」（2026-10-18）。O1 でそのターミナルの日本語が打てなくなる心配は、今は小さい。入れていた場合は、入れている間そのターミナルでは ikari が素通しになる（日本語が打てない）。

### 5.5 英語の文脈（D6）
- 英語のモードで、印字できる文字の打鍵をたまりに足す。ショートコード（ADR 0027）で確定した文字列（`:eyes:` のままでも絵文字でも）もたまりに足す（ショートコードの状態の中の打鍵そのものは足さない。確定した結果だけを足す）。**たまりの最後の文字は `ShortcodeMachine` が読める**（語の頭の判定。ADR 0027 §3.2。たまりが空なら「直前が分からない」）。Backspace は末尾の 1 文字を消す。区切り（Return、Tab、矢印、Ctrl・Option・Command 付きのキー、モードの切り替え、`deactivateServer`、たまりが 2000 文字）でたまりを 1 件の `CommitText`（`reading` は空、`surface` はたまり）として送り、空にする。クリックでのカーソル移動は殻に見えないので、区切りにならない（ADR 0015 §8.2 の「カーソルを動かしたのに履歴を使う」と同じ割り切り）。
- エンジンは今どおり確定履歴と（共有のセッションなら）「最近の確定」に入れるだけで、学習しない。secure と休止中は捨てる。メモリだけ。
- `reading` が空の `CommitText` を、文書内キャッシュなど履歴の読みを使う部品がどう扱うかは、契約のコミットで確かめる（空の読みは「読みなし」として飛ばす、を契約にする）。
- 効き: 今の zenz small では英語の左文脈はほとんど効かない（ADR 0015 §0.6。32 件で +1）。害も測れる範囲で見えない。将来の LM のための通り道として入れる（要望 1）。

### 5.6 殻と Rust の境界、契約（追加だけ。`schema_version` は 1 のまま）
**proto（engine.proto）**

## 6. 入力の統計（D7、D8、D10）と、記録の中身の評価

### 6.1 2 種類の統計
| 種類 | 数えるもの | どこで取るか | 既定 |
| --- | --- | --- | --- |
| 打鍵の統計（`keys`） | キーごとの回数と、連続する 1〜3 打鍵の文字の並びの回数。**英語・日本語の両方のモード**で取り、モードの列で分ける | 殻の `handle`（キーを受けたとき） | **オフ** |
| 確定文字列の統計（`text`） | ikari が確定してアプリに入れた文字列（表記）と、その読み（かな）の、文字ごとの回数と、連続する 2・3 文字の並びの回数。並びは確定をまたいでつなげる。表記は文字の種類（ひらがな、カタカナ、漢字など）の内訳が出せる形 | 殻の確定（`insertText` を呼ぶところ） | **オフ** |

- どちらも**変換には使わない**。学習、順位、文脈の特徴量に入れない。ユーザーが自分の入力を見るための記録で、spec の「学習は支援であって決定ではない」には関わらない。
- 既定はどちらもオフ。設定アプリの「学習とデータ」でオンにする（Q7、Q12 の決定。§11.1）。**2 つは別々のスイッチ**（Q14 の決定）。

### 6.2 打鍵の統計で数えるもの
- **キーごとの回数**: （モード、キーコード、修飾キーのビット）ごとの回数。自作キーボードのどのキーをどれだけ押したか。キーコードは macOS の仮想キーコード（ファームウェアが送る HID のコードを macOS が直した値）。
- **連続する 1〜3 個の打鍵の文字列**: 1 打鍵の文字（`text`。複数のスカラーでも 1 つ）を 1 単位とし、同じセッションで続けて打った単位の 1・2・3 個の並びを、モードごとに数える。書記素の分割は使わない（1 打鍵 = 1 単位）。
  - 英語のモード: アプリに素通しにした打鍵の文字（ABC の配列が出した文字。Shift のかかった文字）。Space も文字として並びに入れる（語の境目も配列の分析に要る）。
  - 日本語のモード: **読みに入ったキーの文字**（ローマ字入力なら `k`、`a`。かなではない）。かな入力の設定でも、キーの文字（ABC の配列の文字）を単位にし、かなには直さない（かなの頻度は確定文字列の統計と、Q16 の読みで見る）。
- **並びの区切り**（そこで並びを切り、次の打鍵から数え直す）: `text` が空の打鍵（矢印、Return、Esc、Ctrl・Option・Command 付き）、Backspace、セッションの切り替え、モードの切り替え、secure、記録しない場面に入ったとき。**日本語のモードでは、ikari が操作として使うキー**（変換の Space、Enter、Esc、Tab、矢印、候補の番号の選択）もキーの回数には数え、並びはそこで切る（Q17）。Backspace、Return、Tab はキーの回数に数え、並びを切る（Q6 の決定）。
- **キーリピート（Q6 の決定: 数えない。OS がリピートだと判別できるなら）**:
  - 判別の根拠（一次資料）: AppKit の `NSEvent.isARepeat` は「ユーザーがキーを押し続けたことによる繰り返しなら true」（Apple の文書）。SDK の `NSEvent.h` にも `isARepeat` があり、keyDown・keyUp で使える。Apple の文書は、キーのイベント以外（`flagsChanged` など）で読むと例外になると書く。殻の `handle` は keyDown だけを見る（§0.2）ので、keyDown のときだけ読む。
  - IMK が殻に渡す `NSEvent` で `isARepeat` が正しく立つかは**未確認**。S-A の T1・T5 のログ（`isARepeat` の列。§7.1）で、キーを押し続けたときに 2 回目以降が true になるかを確かめる。
  - **判別できる場合**: `isARepeat` が true の打鍵は送らない（キーの回数にも並びにも入れない）。押し続けた 1 回は、最初の 1 回（false）として数える。
  - **判別できない場合**（IMK で常に false になる、など）: 繰り返しを除かずに数える。時間の間隔で推し量ること（同じキーが数十 ms ごとに続いたらリピートとみなす）はしない。ふつうの速い打鍵（`ll`、`ss`）と区別できず、本当に押した打鍵を捨ててしまうため。この場合、押し続けた分だけ回数が膨らむことを、設定アプリの統計の説明に 1 行書く。
  - ファームウェアが自分で繰り返しを作る場合（キーを押し続けると、押す・離すを繰り返して送る作り）は、OS から見ると別々の打鍵なので、`isARepeat` は立たず、数える（OS では判別できない）。
- 持たないもの: 時刻、日付ごとの内訳、アプリ、打鍵の順序、セッションの ID。持つのは、数え始めた日（`since`）と合計だけ。
- **ショートコードの状態（ADR 0027）での数え方**（英語・日本語の両方のモード。日本語はローマ字入力でもかな入力でも）: 状態の中の打鍵（`:`、英字、Backspace）は、そのモードの打鍵として、ふだんと同じに数える（モードの列は今のモード。`text` は届いたキーの文字で、かな入力の設定でもかなには直さない。並びも同じ規則）。候補を選ぶ・確定するキー（Space、Enter、矢印、番号など、ADR 0027 が操作として使うキー）は、キーの回数には数えて並びを切る（Q17）。確定した結果（`:eyes:` のままか、絵文字か）は確定文字列の統計に入る（§6.3）。打鍵の統計に「ショートコードの状態だったか」の印は持たない（YAGNI）。

### 6.3 確定文字列の統計で数えるもの
- **対象**: ikari が確定してアプリに入れた（`insertText` を呼んだ）文字列のすべて。日本語のモードの変換の確定、文節ごとの確定、変換しないかなの確定、Shift の英字、候補の番号での確定、直接入力の Unicode（§8）と、ショートコードの確定（ADR 0027。英語・日本語の両方のモード）。英語のモードのふつうの打鍵は素通しで ikari が確定しないので対象外（打った文字は打鍵の統計に出る）。定義を「ikari が入れた文字列」の 1 つにして、モードで分けない（確定文字列の統計にモードの列は持たない）。
- **単位**: Swift の `Character`（拡張書記素クラスタ）。殻が分けて送る。絵文字の結合の列（ZWJ、肌の色）も 1 文字になる。Rust に書記素の分割の依存を足さない。
- **数えるもの**: 表記と読み（かな）のそれぞれで、文字ごとの回数（1 文字）と、連続する 2・3 文字の並びの回数。
- **読み（Q16 の決定: 数える）**: 変換の確定（文節ごとの確定を含む）は、確定した文節の読みをつないだもの。変換しないかなの確定は、そのかな。読みのない確定（直接入力の Unicode、ショートコード、Shift の英字、英数字と記号だけの確定）は、読みを空で送る。読みの単位も `Character`。読みは表記と同じ確定から取るので、`stats.text.enabled` の 1 つのスイッチで表記と一緒に記録する。
- **並びは確定をまたいでつなげる（Q15 の決定）**。理由（ユーザー）: 「もともと統計を取るための機能なので、必要」。確定の境目（「今日は」＋「雨」の「は雨」）も数える。殻は、前の確定のあとに次の区切りがなかったときだけ `joins_previous = true` を送る:
  - 区切り: ikari が確定せずにアプリに渡したキー（素通しのキー。英語のモードの打鍵、日本語のモードで何もないときの矢印・Return・Backspace・修飾キー付きのキーなど）（アプリに渡した Backspace は、確定した文字を消すので必ず区切りになる）、Esc、モードの切り替え、セッションの切り替え（アプリやフォーカスの移動）、secure、記録しない場面（§6.7）に入ったとき、`deactivateServer`、`commitComposition`（クリック）。
  - 読みの並びは、読みが空の確定でも切る（読みのない確定をはさんでつなげない）。
  - 区切りにできないもの: 殻に見えないカーソル移動（ほかの入力ソースやマウスでの操作のうち、`commitComposition` にならないもの）。そのとき実際にはない並びが混ざる（回数の少ない並びが少し増えるだけで、統計としての害は小さい）。
- **文字の種類の内訳**: ひらがな、カタカナ（半角を含む）、漢字、ASCII の英数字、ASCII の記号と空白、全角の英数字と記号、絵文字、その他。種類は保存せず、1 文字の回数から core が求めて、状態の返事とエクスポートに出す。分け方は Unicode のブロックと一般カテゴリの表で決め、単体テストに表を置く（境目の細かい扱いは実装の判断。絵文字の判定は近似でよい）。
- 持たないもの: 確定の順序と区切り（つながりのための末尾 2 文字はメモリだけ。§5.6）、時刻、アプリ。表記と読みの対応（どの表記にどの読みだったか）も持たない（それぞれ別に数える。対応は学習ファイルが持つ）。

### 6.4 記録から何が復元できるか（率直な評価）
| 記録 | 復元できること | 復元できないこと |
| --- | --- | --- |
| キーごとの回数 | 打鍵の量、英語と日本語の割合、よく使うショートカット、記号の癖 | 文字の並び |
| 打鍵の 1 文字の回数 | 文字の頻度（どの言語をどれだけ書くか） | 並び |
| 英語の打鍵の 2・3 文字（よく出る並び） | 書く分野の傾向（`ing`、`the`、`fn `、`::`、`git` のような、よく使う語の断片） | 文。よく出る並びは多くの文に共通するので、どの文を書いたかは決まらない |
| **英語の打鍵の 2・3 文字（まれな並び）** | **1 回しか打たなかったまれな文字列（パスワード、API キー、トークン、メールアドレス、固有名詞、URL の一部）は、その 3 文字の並びが回数 1〜2 で残る。2 文字ずつ重なる並びを、回数の少ないものどうしでつなぐと、元の文字列をかなりの確率で組み立て直せる**（遺伝子の断片をつなぐのと同じ考え方）。でたらめな文字の列ほど、並びが他と重ならないので組み立てやすい | 多くの人が打つような普通の文字列 |
| 日本語のローマ字の打鍵の 2・3 文字 | よく使う音の並び。まれな固有名詞のローマ字は、英語と同じ理屈でつなげられる | 文。単位は英字 26 とわずかな記号で、ローマ字は `ka`、`shi`、`nn` のような同じ並びを繰り返す。3 打鍵の並びの多くは多くの語に共通し、回数 1〜2 の並びは英語より少ない（推測。実データでは測っていない）。**組み立て直しは英語の打鍵より難しい** |
| 確定文字列の 1 文字（表記・読み） | 書く文字の傾向、漢字の頻度、文字の種類の割合、かなの頻度 | 並び |
| 確定文字列の 2・3 文字（よく出る並び） | 「ます。」「した」「って」のような並び。文体の傾向 | 文 |
| **確定文字列の 2・3 文字（まれな並び）** | **日本語の文字の種類は数千あり、漢字を含む 3 文字の並びは英字の並びよりずっと重なりにくい。回数 1 の並びが 2 文字ずつ重なってつながれば、ほぼ一意に元の文字列に戻る**。**並びを確定をまたいでつなげる（Q15 の決定）ので、区切り（§6.3）から区切りまでの文が、確定の境目も含めてそのまま戻る**。人の名前、住所、電話番号、メッセージの文面、仕事の固有の語が対象になる | 区切りをまたぐつながり。よく出る並びだけでできた部分の、どの文に属していたか |
| **読みの 2・3 文字（まれな並び）** | 表記と同じ理屈で、文のかなの形が戻る。かなは表記より文字の種類が少ない（約 90）ので、表記よりは重なりやすいが、まれな固有名詞の読み（名前、地名）はつながる。表記と読みの両方が残るので、一方で曖昧な部分を他方で補える（推測。表記と読みの対応は持たないが、長さと位置で合わせられる場合がある） | 表記と読みの対応そのもの |

- **結論**: 確定文字列（表記と読み）の 2・3 文字の並びは、確定をまたいでつなげるので、**まれな部分については、確定した文を持つのとほぼ同じ**と考える。ローマ字の打鍵の並びよりずっと原文に近い。英語の打鍵の並びとは危険の中身が違う（英語は秘密の文字列、確定文字列は文面）。数え始めのうちは、まれでない文もつなげやすい。
- **Q15 の推奨（1 回の確定の中だけ）からの変化**: 推奨の形でも確定の単位（文節から短い句）の中身は戻った。つなげる形で新しく戻るようになるのは、確定と確定のつながり（語の境目をまたぐ順序、文の全体）。差は「句が戻る」から「文が戻る」で、ファイルが外に出たときの害は大きくなる。統計としては、確定の境目の並び（助詞と次の語の頭など）が取れる。ユーザーは目的（統計）のためにこれを選んだ（Q15。§11.1）。手当ては §6.5（とくに、オンにするところの警告）。
- **学習ファイルとの重なりと違い**:

| 点 | 学習（`learning.tsv`。ADR 0002 §8、ADR 0013） | 確定文字列の統計 |
| --- | --- | --- |
| 持つもの | 変換で確定した語の（読み, 表記）と回数を平文で。文脈の特徴量（`Prev`、`PrevContent`、`Bag`）はソルト付きのハッシュ（ソルトもファイルにあり、辞書の語彙の総当たりで「直前の語」「近くの内容語の集合」には戻りうる。`core/src/user/features.rs` の注記）。語の順序と文は持たない | 表記と読みの、文字ごとと、連続する 2・3 文字の回数を平文で。語の境目は持たないが、**確定をまたぐ 3 文字までの局所的な順序**を持つ（つなげると文になる） |
| 入るもの | 変換して確定した語。変換しない確定（`CommitText`）は学習しない（§0.4） | 変換しない確定（かなのまま、Shift の英字、直接入力の Unicode）も含む、確定した文字のすべて |
| 古くなるか | 半減期 90 日で弱まる | 弱めない（数え始めた日からの合計。§6.6 の上限で、回数の少ない行から捨てる） |
| 使い道 | 変換の順位 | 使わない（記録だけ） |
| エクスポートとバックアップ | 学習のエクスポートと自動のバックアップに入る | 入れない（別に書き出す。§6.6） |

  - 重なり: 1 文字の回数と、語の中の並びの多くは、学習ファイルの（読み, 表記）からも分かる。
  - 新しく増えるもの: (1) 語と確定の境目をまたぐ局所的な順序（「田中さ」「中さん」から、名前と敬称のつながり。つなげると文）、(2) 変換しない確定の中身、(3) 弱まらないこと。学習ファイルより復元できるものは明らかに多い。
- **NFR-19（原文を持たない）との関係**: 打鍵の列そのもの（T3）と確定した文そのものは持たない。しかし、n ≤ 3 の回数を確定をまたいでつなげるので、まれな部分では原文を持つのとほぼ同じになる。この ADR では「NFR-19 を守る」とは言わない。**確定文字列の統計は NFR-19 の例外**で、ユーザーが既定オフ、別のスイッチ（Q14）、オンにするときの警告（§6.5）を条件に、この危険を受け入れた（Q7、Q15。§11.1）。spec の NFR-19 の文言に例外を書き足すかは、B45 の統合のときにリードが決める。

### 6.5 危険を下げる手当て（Q7 の決定: 推奨の手当てをすべて入れる）
| 手当て | 効くもの | 決定 |
| --- | --- | --- |
| **既定でオフ**（打鍵と確定文字列の両方） | オンにしたつもりのない記録 | 入れる（Q7、Q12 の決定）。設定アプリでオンにする。オンにするときの説明と警告は §6.5.1 |
| secure では記録しない（D5） | パスワード欄 | 入れる（要望 5）。secure の間は素通しなので、確定も起きない |
| 統計の除外アプリ `stats.exclude` | パスワード管理、ターミナル（パスワードのプロンプト、トークンを打つ場） | 入れる。既定は `context.shared_exclude` の既定と同じ 7 つ。打鍵と確定文字列の両方に効く |
| 入力メニューの「入力の記録を一時停止」 | 秘密を secure でない欄に打つとき | 入れる。打鍵と確定文字列の両方を止める。止めた状態はメモリだけ（殻を再起動すると記録に戻る）。どちらの統計もオフなら、項目を出さない |
| 時刻・日付ごとの内訳を持たない（T1） | 「その日だけ打った文字列」の切り出し | 入れる |
| 学習のエクスポートとバックアップに含めない | 学習のファイルを渡すときの巻き込み | 入れる |
| 打鍵と確定文字列を別々にオン・オフ | 危険の大きい確定文字列だけを切る | 入れる（Q14 の決定。2 つのスイッチ） |
| 確定文字列の並びを 1 回の確定の中だけで作る | 文がそのまま戻ること | **入れない**（Q15 の決定。確定をまたいでつなげる）。代わりに、確定文字列のスイッチをオンにするところで、文が復元できることを警告する（§6.5.1）。つながりの末尾はメモリだけに持ち、区切り（§6.3）で切る |
| エクスポートで、回数が k 未満の 2・3 文字の並びを除く選択 | ファイルを人に渡すとき | 今は付けない（Q8 の決定） |
| ファイルの暗号化 | ファイルのコピー・バックアップからの漏れ | しない（Q8 の決定。確定文字列（表記と読み）も同じ。2026-10-18 に確かめた。§6.6） |

#### 6.5.1 設定アプリの文言（案。B45 のレーン S が使う。言い回しは実装で整えてよいが、警告の中身は減らさない）
「学習とデータ」の「入力の統計」の欄に、2 つのスイッチを置く。どちらも既定はオフ。

- **打鍵の統計**（`stats.keys.enabled`）
  - スイッチの下の説明: 「キーごとの回数と、続けて打った 1〜3 文字の並びの回数を数えます（英語と日本語のモード）。時刻やアプリは記録しません。」
  - オンにするときの確認: 「1 回だけ打った文字列（パスワード、トークンなど）は、並びをつなぎ合わせると戻せることがあります。パスワード欄、パスワード管理、ターミナルでは記録しません。秘密を打つときは、入力メニューの『入力の記録を一時停止』を使ってください。」［オンにする］［やめる］
  - キーリピートを判別できない場合（§6.2）は、説明に「キーを押し続けた分も数えます。」を足す。
- **確定した文字の統計**（`stats.text.enabled`）
  - スイッチの下の説明: 「ikari で確定した文字（表記と読み）の回数と、1〜3 文字の並びの回数を数えます。**並びは確定をまたいでつなげるので、打った文が復元できる記録になります。**」
  - オンにするときの警告（`NSAlert` の警告の形。既定のボタンは［やめる］）:
    - 見出し: 「確定した文字の統計をオンにしますか？」
    - 本文: 「確定した文字と読みを、確定をまたいで 3 文字までつなげて数えます。回数の少ない並びをつなぎ合わせると、打った文（人の名前、住所、メッセージの文面など）がほぼそのまま戻せます。ファイル（textstats.tsv）は暗号化しません。パスワード欄、パスワード管理、ターミナルでは記録しません。人に見せたくない文を打つときは、入力メニューの『入力の記録を一時停止』を使ってください。」
    - ボタン: ［やめる］（既定）［オンにする］
  - オフにするとき: 「これまでの記録を消去しますか？」［消去する］［残す］（§6.6）。
- 2 つの「消去…」「書き出す…」はスイッチごとに置く（§6.6）。

### 6.6 保存先、暗号化、消去、エクスポート
- 保存先: `~/Library/Application Support/ikari-ime/keystats.tsv`（打鍵）と `textstats.tsv`（確定文字列）。学習と同じフォルダ（エンジンの Sandbox の例外の範囲）。権限 0600。保存の間隔は学習と同じ仕組み（汚れていれば 5 秒ごとと `EndSession`）。2 つに分けるのは、別々に消し、別々にオン・オフできるようにするため（Q14 の 2 つのスイッチ）。`textstats.tsv` は表記と読みを 1 つのファイルに持ち、行の `layer` の列（`surface` / `reading`）で分ける。
- 暗号化: **しない**（Q8 の決定）。理由: (1) 鍵を同じユーザーのキーチェーンに置くことになり、守れるのは「ファイルだけが外に出たとき」に限られる。(2) Sandbox のエンジンからキーチェーンを使う権限が増える（NFR-20）。(3) `learning.tsv` も平文で、FileVault に任せている。確定文字列（表記と読み）の統計にも同じ扱いを当てはめる（2026-10-18 にユーザーが推奨どおりと確かめた。確定をまたいでつなげる決定のあとも変えない）。
- 消去: 設定アプリの「学習とデータ」に「入力の統計」の欄を足し、打鍵と確定文字列それぞれに「消去…」（確認のダイアログ）。統計をオフにしても、既にあるファイルは自動では消さない（オフにするときのダイアログで「消去する」を選べるようにする）。消去の前のバックアップは取らない（Q8 の決定）。
- エクスポート: 「書き出す…」で TSV（`kind`、`mode`、`n` または `key_code`、`modifiers`、文字列、回数。確定文字列は `layer`（表記・読み）の列と、表記の種類の内訳の行も）。設定アプリが `NSSavePanel` で選んだファイルに、エンジンから受け取ったバイト列を書く（ADR 0005 §8 と同じ形）。
- 行数の上限: 3 文字の並びの種類は、ふだんの英語で数万程度、日本語の確定文字列ではそれより多い見込み（推測）。上限はファイルごとに学習と同じ 200,000 行を仮に置き（`textstats.tsv` は表記と読みの合計）、超えたら回数の少ない古い行から捨てる（実装で測って見直す。ユーザーの判断は要らない技術的な上限として扱う）。

### 6.7 記録するかの判定（殻。打鍵ごと、確定ごと）
次の全部を満たすときだけ送る（打鍵は `RecordKeys`、確定は `RecordCommitted`）。
1. その種類の統計がオン（`stats.keys.enabled` / `stats.text.enabled`。どちらも既定 off。読みは `stats.text.enabled` に含む）。
2. 一時停止していない。
3. secure でない。
4. クライアントの Bundle ID が `stats.exclude` にない（Bundle ID が取れないときは記録しない）。
5. 打鍵なら、キーリピートでない（Q6 の決定。`isARepeat` で判別できる場合。§6.2）。

モードは条件にしない（Q5 の決定。英語・日本語の両方で取る）。エンジンも、secure のセッションの `RecordKeys`、`RecordCommitted` を捨てる（二重の守り）。送らなかった確定のあとは、次の確定の `joins_previous` を false にする（記録しない場面の前後をつなげない）。

## 7. スパイク S-A（捨てるコード）: 英数キーの行き先、パスワード欄、Unicode の届き方

### 7.1 目的と、作るもの
- **目的**: §3 の D1〜D5、D9 の前提のうち、実機でしか分からないことを確かめる。結果で、K1 か K3 か、モードの辞書のキーの名前、O1 の妥当さ、直接入力の判定の規則を決める。
- **作るもの**: ikari とは別の、小さな入力メソッド `IkariModeSpike.app`（ブランチ `spike/adr-0026-mode`。main に入れない）。
  - Bundle ID `io.github.ikari-zen.inputmethod.ikarispike`、接続名も別。**ユーザーの ikari、エンジン、ユーザーデータ（`~/Library/Application Support/ikari-ime/`）には触れない**。エンジンを起動しないので、学習ファイルのロックも取らない（smoke と違い、ikari の変換は止まらない）。
  - モードは 2 つ: 辞書のキー `com.apple.inputmethod.Japanese`（`JISKeyboardShortcut = 1`）と `com.apple.inputmethod.Roman`（`smRoman`、`JISKeyboardShortcut = 3`）。§5.1 の形。
  - **どちらのモードでも、すべての打鍵を素通しにする**（`handle` は記録してから false）。変換はしない。
  - 入力メニューに「英語のモードにする」「日本語のモードにする」（`client.selectMode` を呼ぶ）。キー割り当ては F18（`selectMode` で日本語 ⇄ 英語）。
- **ログ**: `~/Library/Logs/IkariModeSpike/spike.log`（ikari のフォルダとは別）。1 行 1 出来事、文字の中身は書かない:
  - 打鍵: 時刻、モード、キーコード、修飾キーのビット、`isARepeat`、`characters` と `charactersIgnoringModifiers` の**種類だけ**（空／ASCII の英字／ASCII の数字／ASCII の記号／ASCII 以外）、ASCII 以外なら**スカラーの数と、各スカラーの Unicode の区分（`generalCategory`）とブロック**（例: `So/Misc Symbols and Pictographs`、`Lo/CJK Unified`、`Lo/Hiragana`）。コードポイントそのものは書かない。`IsSecureEventInputEnabled()`、クライアントの Bundle ID、`handle` にかかった時間（µs）。
  - 出来事: `activateServer`、`deactivateServer`、`setValue`（モードの ID）、`inputControllerWillClose`、`kTISNotifySelectedKeyboardInputSourceChanged`（そのときの入力ソースの ID と、`TISCopyCurrentASCIICapableKeyboardLayoutInputSource` の ID）。
  - 起動時: 自分の 2 つのモードの `kTISPropertyInputSourceIsASCIICapable`、`IsEnabled`、`IsSelectCapable`。
- 入れる前に `swift build` と、ログの書き出しの単体テストを通す（handoff-2026-10-17 §2.3 の教訓。落ちうる呼び出し（`string(from:)` など）は使わない）。

### 7.2 手順（ユーザーが行う。合わせて 30〜45 分の見込み）
前提: 2026-10-18 の時点で、有効な入力ソースは ABC と ikari だけ（§0.5）。ほかの日本語の IME が有効になっていたら、かなキーの行き先を揃えるため、T1〜T6 の間だけ外してもらうかをユーザーに聞く（外さないなら、そのまま記録する）。終わったら元に戻す。

**下書きにあった T0（Google か azooKey の英数のモードで英数キーを試す）は消した**（2026-10-18）。ユーザーの指摘のとおり、ユーザーから見て選べるのは Google の全角英数のモードだけで（§0.6）、そのモードは `JISKeyboardShortcut = 0`（英数キーの 3 ではない）。全角英数で試しても、英数キーが `JISKeyboardShortcut = 3` のモードに行くかは分からない。英数キーの行き先は、スパイクが自分で宣言した英語のモードで T1 で確かめる。

## 8. 直接入力の Unicode（D9）

**位置づけ（2026-10-18）**: 今は使っていない。将来、ZMK で Unicode を送るときに備える設計として残す。§8.1〜8.3 は「文字（ASCII 以外）が `characters` に入って届く」送り方（ホストのツールが合成した打鍵など）の扱い。ZMK の macOS のモードはこの形では届かない（§8.5）。どの送り方にするかが決まるまで実装しない（§10 の B43）。

### 8.1 判定（殻。`KeyCodes`）
打鍵を `KeyInput` に直すとき、**JIS の位置表を引く前に**、次を全部満たせば `.direct(文字)` にする。
1. Ctrl・Option・Command がない（Shift はあってよい）。
2. `characters` が空でなく、打てる文字だけ（今の `isPrintable` と同じ）。
3. **ASCII 以外のスカラーを 1 つ以上含む**。
4. 例外: ABC の配列で JIS のキーが出す ASCII 以外の文字（¥ キー（93）の `¥`）は今どおり（ローマ字は読みに、かな入力は JIS のキー）。例外の一覧は S-A の T4 の結果で足す。
5. **ASCII の文字（`:` を含む）は `.direct` にしない**。だから「読みにならない文字はそのまま確定」（§8.2）には入らない。かな入力の設定では、JIS の位置表にあるキーコードは今どおりキーコードで扱う（ADR 0027 のショートコードの入り口は Shift+けのキー）。`:` が JIS の位置表の外のキーコードで文字として届いたときだけ、`.character(":")` として状態機械に渡す（ADR 0027 §3.2 のかな入力の (b)。ショートコードに入れるかは ADR 0027 が決める）。

- 根拠: ikari が使っている間の配列は ASCII を打てるもの（ABC）なので、ふつうの打鍵の `characters` は ASCII になる。ASCII 以外が届いたら、配列の外から来た文字（自作キーボードやツールが送った Unicode）と見なせる（推測。T4 で確かめる）。
- かな入力の設定でも、この判定を先に行う。今は、キーコード 0 で届いた絵文字が「ち」になる（§0.3）。

### 8.2 日本語のモードでの扱い（状態機械）
| 今の状態 | 読みにならない文字（漢字、絵文字、記号、全角の英数） | かな（ひらがな・カタカナ・長音）（Q10） |
| --- | --- | --- |
| 何もない | その文字をそのまま確定（`insertText`）。`CommitText`（読みは空）で確定履歴に送る。学習しない | 読みに足して合成を始める（ローマ字入力は今も同じ。かな入力の合成器に、文字を足す口を足す） |
| 合成中・英字の合成中 | 今の表示を確定してから、その文字を確定 | 読みに足す |
| 変換中 | 今の選択を確定してから、その文字を確定 | 今の選択を確定してから、その文字で新しい合成を始める（今の `continueAfterCommit` と同じ） |

- **確定するときに文字を変えない**（全角・半角の変換、正規化をしない）。`insertText` には届いた `characters` をそのまま渡す。絵文字の結合の列（ZWJ、肌の色）も 1 つの打鍵の文字列として渡すので切れない。
- かなが文字として届いたら読みに足す（Q10 の決定 (a)。2026-10-18。かな配列はこれから使う）。かなを「そのまま確定」する設定（`input.direct_kana = commit`）は作らない（要るとわかったら足す）。

### 8.3 英語のモード
- 素通しなので、アプリが届いた文字をそのまま入れる。ikari は何もしない（記録と文脈のたまりには、届いた文字を 1 単位として足す）。

### 8.4 文字ビューアと貼り付け
- 文字ビューアや貼り付けは、IME を通らずアプリに入る（推測）。ikari は壊さないが、記録と文脈には入らない。

### 8.5 ファームウェアの Unicode の機能（ZMK。将来）
**一次資料で確かめたこと**（2026-10-18）:
- ZMK 本体の文書のビヘイビアの一覧（zmk.dev/docs/keymaps/behaviors）には Unicode の項目がない。ZMK で Unicode を送るのは、外部のモジュール（例: `urob/zmk-unicode`。`&uc` のビヘイビア）を使う形になる。ユーザーがどのモジュールを使うかは未定。
- `urob/zmk-unicode` の README: macOS のモード（`UC_MODE_MACOS`）は、**システム設定で「Unicode 16 進入力」を入力ソースに足し、メニューバーで選んでおく**ことを前提にする。動きは (1) `macos-key`（既定は左 Option）を押したままにし、(2) コードポイントの 16 進を打ち、(3) `macos-key` を離す。Option を使うショートカット（Option+←/→ など）が効かなくなることがある、とも書いている。U+FFFF を超える文字（多くの絵文字）をどう送るか（サロゲートの組にするか）は README からは読み取れない（未確認）。
- 参考に QMK（ユーザーは使わない）も同じ形だった: 文書（docs.qmk.fm/features/unicode）は「Unicode 16 進入力」を足して選ぶことを求め、ソース（`quantum/unicode/unicode.c`）は既定で左 Option（`UNICODE_KEY_MAC = KC_LEFT_ALT`）を押したまま 16 進を打ち、U+FFFF を超える文字は UTF-16 のサロゲートの組で送る。
- キーボード（HID）が送るのはキーの番号で、文字そのものは送れない。だから、ファームウェアの Unicode の機能は、ホストの入力の仕組み（macOS では「Unicode 16 進入力」）に頼る（上の 2 つの文書の説明と一致する）。
- 手元の Mac では、「Unicode 16 進入力」は有効になっていない（§0.5）。

**ikari にどう届くか（場合分け。実機は未確認）**

**ZMK で送るときの選択肢（ユーザーが送り方を決めたときに選ぶ。今は決めない）**

- **`handle` の順**（統計は B45 で足すので 5-1、6、7 は入れていない）: keyDown 以外 → 英数・かな（受け止める）→ secure の更新 → 英語なら（secure は素通しでたまりを捨てる → `mode.*` → ショートコードの口（B48。今は何も受け止めない）→ たまりに足して素通し）、日本語なら（`mode.*` → 今の状態機械）。

- **決めたこと**: (1) たまりの上限は文字数ではなく Unicode のスカラーの数で数える（エンジンの上限と同じ数え方。家族の絵文字のような 1 文字が複数のスカラーのときに、エンジンに断られない）。(2) 英語のモードは、かな入力の設定でも `.jis` にせず文字で読む。(3) secure のときは、英語のたまりを送らずに捨てる（secure の前後を 1 件につなげない）。(4) `mode.*` は日本語のモードでも効かせる（`mode.toggle` が日本語から英語へも使えるように）。(5) 設定アプリのキー割り当ての一覧に `mode.*` の 3 行が出る（`allCases` から作るため。表示名だけ足した）。
- **日本語のモードの secure（D5、§5.2-4、§5.4。リードの指示で B44 に含めた）**: `InputStateMachine.handle` の先頭で、secure なら、idle はそのまま素通し（`.passThrough`）、合成中・変換中・ショートコードの表示は今の表示のまま確定してから素通しにする（secure なので `CommitText` も `Commit` も学習も送らない）。secure でなくなれば、次の打鍵から元の動作に戻る。直した既存のテスト（期待が「secure でも変換する」から D5 に変わったもの）: `SecureAndHistoryTests`（secure の間は変換・文脈・確定をしない → すべて素通し。secure になる途中の確定、secure が外れたら元に戻ることを足した）、`ShortcodeTests` の secure の入口と「secure になったら確定してキーを素通し」、`SegmentEditingTests.aSecureSessionCommitsWithoutTellingTheEngine`（変換中に secure になった場合に直した）、`ReconversionTests.refusesInASecureSessionWithoutReadingTheSelection`（`.consume` → `.passThrough`）。
- **やっていないこと**:入力メニューの「入力の記録を一時停止」（B45）。ショートコードの英語への配線（B48）。
