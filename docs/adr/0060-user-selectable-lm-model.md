# ADR 0060: LM のモデルを利用者が選ぶ（候補から選ぶ、またはファイル・URL を指定する）。モデルごとの差は「モデルの記述（profile）」1 か所にまとめる

- 状態: 提案
- 日付: 2026-11-13
- 対象: `lm`（`config.rs`、`prompt.rs`、`ranker.rs`、`llama.rs`）、`ikari-resource`（既知のモデルの表、manifest）、`engine`（`lib.rs` のモデルの解決、`settings.rs`）、`ikari-data`（後で）、設定アプリ（UI）
- 前提: ADR 0058（承認。この ADR は 0058 を補い、§5.2 と §6.1 の 4（モデル）、§7.2 のモデルの行、§11 を改める）、ADR 0003 §7.1、ADR 0042、ADR 0057、spec NFR-17・NFR-33〜38
- 判断の置き場所: すべて Rust（形式、検査、解決、取得）。Swift は、ファイルを選ぶダイアログ、一覧、選ぶ操作、警告の表示だけ（OS の API と UI であるため）

## 1. 背景（分かったこと）

- モデルは配布物に入れず、ユーザーが取得する（作者の提案 2026-11-13）。理由は 3 つ。(1) zenz のライセンス表示が変わった（10-26 は Apache-2.0、11-09 は CC BY-SA 4.0）。(2) zenz の保守が止まったときに逃げ道が要る。(3) 署名に使う SignPath の「OSS でないものを含めない」という条件に合う。
- モデルごとの差を持っているのは、今は `ModelKind`（ZenzV3 / KanakanjiEdge）、`build_prompt_for`、`ranker.rs` の `uses_conditions` だけ。終端の記号（`</s>` を文字列で探す）、BOS、トークナイザの上書き（失敗したら `default`）は、どのモデルにも同じ処理をしている。
- 製品が `model_kind` を読む経路はない（CLI の `--ranker-config` と eval だけ）。ファイル名は `MODEL_FILE_NAME` に固定で、既知の sha256 の表（`KNOWN_MODELS`）にないモデルは拒む（0058 §6.1）。
- 形式の合わないモデルは、エラーを出さずに誤った NLL を返す（推測。根拠は、形式の検査が無く、読み込みが通れば使う作りであること）。そうなると LM なしより悪くなる。細工された GGUF は llama.cpp のパーサに渡る。
- NFR-33〜38 の「再学習」は、アダプタ（ユーザー向けの微調整）の話で、アダプタは未実装。learning.tsv は表記の選択だけを持ち、モデルに依存しない。

## 2. 決定の要約

| 項目 | 決定 |
| --- | --- |
| 差の吸収 | `lm` に `ModelProfile` を置き、モデルごとの差はここにだけ書く。`ModelKind` は `PromptFormat` に改名して profile の中に入れる（§3） |
| 尺度 | `max_total`（6000）は全モデルで共通。差は `alpha` だけで吸収する。ADR 0057、0020 の値がこの上限を前提にしているため |
| 候補（プリセット） | `ikari-resource` の表（`MODEL_PRESETS`）。アプリの更新でだけ増える。最初は zenz-v3.2 small だけ（§5） |
| 自由指定 | ユーザーが**形式を選ぶ**。GGUF のメタデータで推定はしない。読み込んだあとに**試しの採点**で確かめ、通らなければ使わない（§4） |
| 0058 との関係 | 「既知の sha256 だけ」を「既知の sha256、または `origin = user` で、試しの採点に通ったもの」に改める（§6） |
| 取得 | ファイルの指定と、URL からの取得。URL は `ikari-data` が、**ユーザーがボタンを押したときだけ**行う（ユーザー決定）。sha256 なしは**警告を出して許可**（ユーザー決定） |
| 檻 | モデルを動かす部分は、ネットワークとローカルのファイルから隔離する（§4.1、Q4） |
| 設定 | settings.tsv の `lm.model = <id>`。無いときは `zenz-v3.2-small`（今と同じ）。取り込んでも自動では切り替えない（NFR-38） |

## 3. モデルの記述（profile）

- `lm` の型（契約）: `ModelProfile { id, format: PromptFormat, alpha, limits: LmLimits, adapter_base: Option<String> }`。`PromptFormat` は `#[non_exhaustive]` の enum（`ZenzV3`、`KanakanjiEdge`）。新しい形式は、enum の値と `build_prompt_for` の腕を 1 つずつ足して加える。
- 条件（プロフィール、話題、右文脈）を使うかどうかは、`ranker.rs` で種類を比べず、`PromptFormat::uses_conditions()` に聞く。差を持つのは `prompt.rs` の 1 か所だけにする。
- `LmLimits`（プロンプトの上限 512、候補 96 トークン、文脈の文字数）は profile から持つ。KV 4096 とバッチ 1024 は llama.rs の定数のまま（モデルに依らない資源の上限のため）。
- 特殊トークン、BOS、終端、トークナイザの上書きは profile に持たない。今の汎用の処理で足りている。合わないモデルは §4 の検査で落とす（使われない柔軟性を足さない）。
- `adapter_base` は、NFR-35・37 の元モデルの ID。アダプタができたときに、照合と再学習を促す処理が読む。今は書くだけ。
- 優先の順: profile の値 < `--ranker-config` の `zenz.*`（開発と評価だけ。製品は `zenz.*` を読まない）。

## 4. 自由指定のモデルの守り

- 形式: ユーザーは一覧（今は「zenz-v3 形式」「kanakanji-edge 形式」）から選ぶ。`alpha` は、その形式の基準のプリセットから借り、UI に「未調整」と出す。メタデータで推定しない理由: zenz 自身でもメタデータが食い違い（EOS=2 と `</s>`=3）、`general.architecture` では形式を見分けられない。
- **語彙の検査**: EE00〜EE07 がそれぞれ 1 トークンになること、`</s>` があること、語彙の大きさが上限以下であること。
- **試しの採点**: `lm` に固定の組（左文脈、読み、正解、誤り。評価セットから十数件）を持ち、正解の NLL が誤りより小さい件数が N 件以上であることを求める。N と件数は、zenz small、xsmall、edge が通り、**形式を取り違えた組**（edge に zenz のプロンプトを渡すなど）が落ちるように、掃引して決める（値は計測で決める）。落ちたら、ほかの形式でも採点し、「この形式なら通る」と知らせる。勝手に形式を変えはしない。
- 検査をするのは、取り込みのスレッド（0058 §8.1）。sha256 のあとに、別の llama の文脈で行う。プリセットも同じ検査を通す（ビルドの取り違えを防ぐ）。
- **落ち続けを防ぐ**: LM のワーカーは、読み込む前に `models/.loading` を書き、読み終えたら消す。起動のときにこの印が残っていたら、そのモデルで落ちたと見なす。選択を既定に戻し、`status.json` に理由を書く。細工された GGUF で落ちても、エンジンが落ちて再起動して、また落ちるのを繰り返さない。
- 大きさの上限を持つ（性能とメモリのため。値は実測して決める）。

### 4.1 檻（ユーザー決定 2026-11-13。要件）

- 要件: **モデルを動かす部分は、ネットワークに出られず、決まったファイル以外のローカルのファイルに触れない。** 入るのは採点の要求（文字列）、出るのは数値（NLL）だけ。同じことをひたすら繰り返す、閉じた部品にする。
- 事実: GGUF は重みのデータで、それ自体は通信もファイル操作もしない。起きうるのは、llama.cpp の読み込み・推論の不具合を、細工されたファイルが突くことだけ。檻は、その場合に被害を、そのプロセスの中に閉じ込めるための備え。
- 今: LM はエンジンのプロセスの中のワーカーのスレッドで動く。macOS のエンジンは App Sandbox（network なし、ユーザーデータのディレクトリだけ読み書き可）の中だが、学習・ユーザー辞書も同じプロセスにある。Windows は隔離が未確認（§10）。
- 案（Q4）: 推論を別の小さなプロセス `ikari-lm-host` に分け、OS の仕組みで禁じる。入出力はパイプだけ。落ちても、エンジンは LM なしで動き続け（今の読み込み失敗と同じ扱い）、§4 の `.loading` の印と合わせて、落ち続けを防ぐ。
- 檻に入れても、URL の取得（`ikari-data`）は別の部品で、取得してから検査と推論に渡す。取得する部品と、モデルを動かす部品は、混ぜない。

## 5. 候補（プリセット）の表

- `ikari-resource` の `KNOWN_MODELS` を `MODEL_PRESETS: &[ModelPreset { id, file_name, sha256, size, url, model_card_url, license_seen: (SPDX, 確かめた日), profile_id }]` に広げる。xtask の `fetch.rs` も、この表を読む（0058 §5.2 の 1 か所に集める方針の続き）。
- ライセンスは「記録した日の表示」として出し、配布元のページへのリンクを添える。ikari はライセンスを保証しない（表示が変わりうるため）。
- 表は、アプリを更新しない限り変わらない（遠くから表を取らない）。理由: profile の `alpha` は実測とコードの変更を伴う。遠くから取る表は、新しい通信と、信じる根拠の置き場所を増やす（NFR-17）。アプリの更新より先に新しいモデルを使いたいときは、自由指定で足りる。
- プリセットを足すのは、全セットの評価で 1 位が悪化しないことを確かめ、ユーザーに聞いてから（CLAUDE.md の「モデルを足す・替える」）。

## 6. ADR 0058 の改め

- **§6.1 の 4（モデル）**: 「既知の表にあるもの、または manifest の部品に `origin = user` と `profile`（形式）があり、§4 の検査に通ったもの」。脅威の評価: inbox に置ける人は `models/` にも直接書ける（0058 §6.2 と同じ考え）。新しく増える危険は「ユーザーがだまされて細工されたファイルを選ぶ」ことで、確認の画面と §4 の印で受ける。
- **§5.2**: `KNOWN_MODELS` を `MODEL_PRESETS` に替える。manifest のモデルの部品に、任意の欄 `profile { format, base_preset }` と `source`（ファイル、または URL）を足す。schema は 1 のまま（足す欄は任意）。
- **§7.2 のモデルの行**: `models/` に複数のモデルを置けるようにし、ファイル名は `<id>.gguf`（プリセットは今の `file_name` のまま。移し替えは要らない）。`models/MANIFEST.json` に、入っているモデルの一覧を持つ。`.new` から rename、`.prev` 1 世代は同じ。取り込んでも `lm.model` は変えない。
- **§11**: URL からの取得は Q1 の決定で上書きする。
- 自由指定の束は、Rust が作る: `ikari-data model import --file <path> --format <f>`。設定アプリはファイルを選ばせ、`inbox/<名前>.partial/` にコピーしてから、それを呼ぶ。sha256 と manifest は Rust が書く。URL のときは `ikari-data model fetch --url <u> [--sha256 <h>] --format <f>`。sha256 は任意で、指定すれば照合する。

## 7. 設定と切り替え（macOS と Windows で共通）

- engine に `resolve_model(&Settings, &ModelsManifest) -> Option<ResolvedModel { path, profile }>` を足す（`lib.rs:206-215` の固定名を置き換える）。windows/engine-host も同じ `Engine::open` を通るので、OS ごとのコードは要らない。
- `lm.model` が変わったら、エンジンは LM のワーカーを作り直す（新しい path と profile で）。要求と要求の間で切り替え、その間は LM なしで動く。
- 切り替えの画面に「候補の並び順が変わります」と出す。アダプタがある場合の「再学習を促す」（NFR-38）は、アダプタの ADR で `adapter_base` を見て行う。今は対象がない。
- Windows の設定画面は Windows の ADR で決める。それまでは、`ikari-data model import` と settings.tsv で使える。

## 8. 段階（1 タスク 1 ブランチ。Windows の実機確認のあと）

1. **契約**: `ModelProfile`、`PromptFormat`、`LmLimits`、`MODEL_PRESETS`、manifest の任意の欄、`resolve_model` と `check_model(path, format) -> ModelCheck` のシグネチャとスタブ。判断の置き場所: Rust（lm、ikari-resource、engine）。
2. **lm の profile 化**（ふるまいは変えない。`eval/scripts/snapshot.sh` で差 0）と、試しの採点の実装と、閾値の掃引。判断の置き場所: Rust（lm）。
3. **engine**: `lm.model` の解決、ワーカーの作り直し、`.loading` の印、0058 の取り込みが `origin = user` を受けること（#246-2 のあと）。判断の置き場所: Rust（engine）。
4. **ファイルからの取り込み**: `ikari-data model import`（Rust）と、設定アプリの一覧・選ぶ操作・警告（Swift。UI のみ）。
5. **URL からの取得**（ボタンを押したときだけ。#248 のあと）: `ikari-data model fetch`。判断の置き場所: Rust（ikari-data）。
6. **プリセットを足す**（Q3。1 つずつ実測して聞く）。

1 と 2 は製品のふるまいを変えないので、Windows の作業の合間に進めてよい。3 から先は、Windows の実機確認のあとにする。

## 9. 検討して採らなかった案

- **GGUF のメタデータで形式を推定する**: 信用できる欄がない（§4）。推定が外れると、気づかないまま精度が落ちる。
- **形式の検査なしで使い、悪化を許す**: LM なしより悪くなっても、ユーザーには原因が見えない（柱 1「思考を止めない」に反する）。
- **プロンプトの形をテンプレートの文字列で持つ（設定で書ける）**: 使われない柔軟性で、検査の範囲が際限なく広がる。形式は enum で足す。
- **モデルごとに `max_total` も変える**: 学習と規則の段の値（ADR 0057、0020）を、モデルごとに調整し直すことになる。
- **プリセットの表を遠くから取る**: §5 のとおり。

## 10. 懸念・要確認

- 試しの採点で、xsmall と edge と、形式を取り違えた組が分かれるかは、まだ測っていない（段階 2 で測る。分かれなければ §4 を見直す）。
- 検査の間は、モデルの大きさの分だけメモリが一時的に増える。モデルの大きさの上限の値は未定。
- Windows の engine-host が、Sandbox に相当する隔離の中で動いているかは、まだ確かめていない（細工された GGUF の影響の範囲が macOS と違う）。
- spec を直す（承認されたら）: NFR-17（Q1 の範囲）と、「辞書の更新」の節にある「モデルは手動で置く」。

## ユーザーに聞くこと（推奨つき）

### 決定済み（ユーザー、2026-11-13）

- **URL からの取得はアプリの中でやってよい。ただし、ユーザーが明示的にボタンを押したときだけ**（自動では取らない。NFR-17 の例外は、この範囲に限る）。担い手は `ikari-data`。プリセットは表の固定の URL、自由指定はユーザーが入力した https の URL。確認の画面でホストを出し、http への転送は拒む。
- **sha256 が無い URL・ファイルは、警告を出して許可する。** 理由: ユーザーが自主開発したモデルを使いやすくするため。sha256 を指定したときは照合する。
- **モデルの実行は檻に閉じ込める**（§4.1）。モデルが勝手に通信したり、ローカルのファイルを触ったりすることは許さない。

### 決定済み（ユーザー、2026-11-14）

- **Q2: 試しの採点に通らないモデルは、拒まず、警告を出して使えるようにする。** sha256 なしを警告で許可するのと同じ考え方にそろえる。
- **Q3: 最初のプリセットは、今と同じ zenz-v3.2 small だけ。**
- **Q4: 檻の作り方は、計測してから決める。** 推論を別プロセス（`ikari-lm-host`）に分けるべきかは、スパイクで次を測って判断する: 別プロセスの起動の時間、1 回の往復の時間（エンジンの中のスレッドとの差）、採点の p99 への影響、メモリ。N150 の VM（Windows）と Mac の両方。数字は参考値として記録し、結果を ADR に足してからユーザーが決める。それまでは今のまま（エンジンの中のスレッド）。
- **Q4 の方向（ユーザー、2026-11-14）: Mac も別プロセスにして良さそう。安定性のメリットがあるなら。** 安定性の理由: 推論（GPU ドライバ、llama.cpp）の中で落ちたりハングしたりしても、エンジンは生き残り、LM なしで動き続けられる（今はエンジンごと落ちる）。Mac のスパイク（PR #355）では、往復の追加は p50 で 0.1ms 以下、起動は約 80〜130ms、メモリは子に移るだけで全体はほぼ同じ、NLL は全件一致だった（参考値）。**確定の条件**: Windows（N150 の VM）の計測と、「LM のプロセスを落としたとき、エンジンが生き残って LM なしで動き続けるか」の確認を済ませること。そのうえで本決定にする。Mac の別プロセスでは、Sandbox の設定、署名、入れ方（InputMethod のバンドルの中の置き場所）を設計で扱う。
- **Windows の計測（N150 の VM、2 vCPU、CPU のみ、zenz small。参考値）**: 往復の追加はほぼ無い（1 回の p50: 別プロセス 171.5ms、直接 171.8ms。p95 212〜240ms 対 214〜216ms。順序を替えても同じ）。NLL は全件一致。起動から準備完了まで: 初回は 901ms（ビルド直後。ウイルス対策の走査か冷えたファイルと推測）、以後は約 97〜99ms。直接の読み込みは約 84ms。メモリは子が約 222〜226MB で、親に同じモデルを読んだ場合（約 219〜221MB）と同じ（子に移るだけ）。要求の間を 200ms 空けたとき、別プロセスの p99 が 284ms 対 245ms とやや悪いが、件数が少なくばらつく。**未確認**: 隔離（AppContainer）をかけたときの起動と往復、LM のプロセスを落としたときにエンジンが生き残ること（試作にエンジンがないので、本実装のテストで確かめる）。

### （記録）Q2. 試しの採点に通らない自由指定のモデルを、どう扱うか

- 推奨: **使わない（拒んで、通る形式があればそれを知らせる）。** 理由: 通らないモデルは、LM なしより並べ替えが悪くなる恐れが高く、ユーザーには原因が見えない。
- 別の案: 警告を出したうえで使えるようにする（試したい人は試せる。悪化は自己責任）。上の「sha256 なしは警告で許可」と同じ考え方にそろえる案でもある。
- 注: 自主開発のモデルを使いやすくする意図なら、後者のほうが合うかもしれない。要判断。

### （記録）Q4. 檻の作り方（§4.1。新しい論点）

- 推奨: **LM の推論を、エンジンとは別の小さなプロセス（`ikari-lm-host`）に分け、OS の仕組みで、通信とファイルアクセスを禁じる。** macOS は Sandbox（network なし、読めるのは `models/<id>.gguf` だけ）、Windows は AppContainer か制限つきトークンと Job Object。入出力は、パイプ（標準入出力）で、採点の要求（文字列）と結果（数値）だけを渡す。
- 別の案: 今のとおり、エンジンの中のスレッドで動かす（エンジンはすでに macOS の Sandbox の中で、network なし。ただしユーザーデータ全体が同じプロセスの中にある。Windows は隔離が未確認）。作業は少ないが、檻は弱い。

### （記録）Q3. 最初のプリセットに何を入れるか

- 推奨: **zenz-v3.2 small だけ（今と同じ）。** xsmall と kanakanji-edge は、全セットで実測してから、1 つずつ聞く（ADR 0003 §7.1、user-feedback「長文向けの使い分けは採らない」）。
- 別の案: edge も最初から入れる（実装がすでにあり、ライセンスの事情が zenz と違う逃げ道になる。ただし `alpha` の調整と評価が先に要る）。

### Q2. 試しの採点に通らない自由指定のモデルを、どう扱うか

- 推奨: **使わない（拒んで、通る形式があればそれを知らせる）。** 理由: 通らないモデルは、LM なしより並べ替えが悪くなる恐れが高く、ユーザーには原因が見えない。
- 別の案: 警告を出したうえで使えるようにする（試したい人は試せる。悪化は自己責任）。
