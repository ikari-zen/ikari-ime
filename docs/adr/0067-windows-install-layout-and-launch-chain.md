# ADR 0067: Windows の置き場所・登録・起動の連鎖。インストール先を信頼の根にし、だれがだれをどこから起動するかを決め、TIP が入る先のプロセスの種類ごとの動きを決める

- 状態: 承認（2026-11-16 ユーザー決定。質問はすべて推奨どおり。実機などの確認が済んでいない決定は、確認が済むまで仮。末尾の「決定済み」を見る）
- 日付: 2026-11-16（2026-11-17 に §4.5 の VC++ の再頒布パッケージの決定を足した）
- 対象: W5 のインストーラ（未作成。`windows/installer/`）、`windows/tip/src/com/`（プロセスの種類の判定、起動、登録）、`windows/engine-host/src/main.rs`・`run.rs`（起動の条件）、`lm/src/host/os.rs`（子の起動）、ビルドの設定（C の実行時ライブラリ、開発用の口）、`windows/dev/`（開発用の導入）。この ADR ではコードを変えない
- 前提: main = 94f65ae。[ADR 0066](0066-security-premises.md)（P1〜P6、R1〜R6）、ADR 0040 §2.2・§2.3・§2.7・§7（W5）、ADR 0062 §5.4（候補窓は engine-host が起動する）、ADR 0063（版ごとのフォルダ。Q2: Program Files、Q3: データは既定で残す）、ADR 0064 §6.2（エンジンを止めてよい者）、ADR 0060 Q4（LM の子）
- 判断の置き場所: Rust（プロセスの種類の判定と「素通し」は `windows/tip` の純粋な部分。Mac でテストする。OS から値を取るのは `com` の層）とインストーラ（置く、登録する、規則を入れる、確かめる）。Swift は関わらない
- ADR 0063 が待っている「W5 のインストーラの ADR」のうち、セキュリティに関わる部分を決める。インストーラの画面や文言は扱わない

---

## 1. 現状（分かったこと）

- 製品のインストーラは無い。開発用の導入（`windows/dev/`）は、`%LOCALAPPDATA%\ikari-ime-dev\install`（利用者が書ける場所）に置き、`regsvr32` で HKLM に登録する。配置の形は製品と同じ（`common.ps1`）:
  `<インストール先>\ikari-engine-host.exe`、その隣に `llama*.dll`・`ggml*.dll`・`backends\`、`<インストール先>\tip\<版>\ikari_tip.dll` と `resources\`。
- TIP は、エンジンの場所を自分の DLL の場所から決め、つないだ相手の実行ファイルのパスと照らす（`windows/tip/src/peer.rs`。S1）。LM の子は、エンジンの実行ファイルの隣の絶対パスから起動する（`lm/src/host/`）。どちらも R2 の形。
- 登録（`windows/tip/src/com/register.rs`）は HKLM（`HKCR\CLSID`、TSF のプロファイルとカテゴリ）。カテゴリに `GUID_TFCAT_TIPCAP_IMMERSIVESUPPORT` があるので、**ストアのアプリ（AppContainer）にも読み込まれる**。
- 高い権限のアプリの中の TIP は「素通し」にする、という決定がある（2026-11-15）。その実装の状態は、ここには書かない（番号つきの issue で追う）。
- エンジンの自動起動は未実装（`windows/tip/src/transport.rs` の `TODO(W5)`。開発では `start-engine.ps1`）。ADR 0040 §2.2 の方針は「HKCU の Run を基本、TIP がつながらなければデスクトップアプリからに限って起動」。
- パイプの DACL は、自分のユーザーと SYSTEM だけ。AppContainer は許していない（`pipe/src/os/mod.rs`）。
- TIP の DLL が、OS の標準でない DLL に依存しているかどうかは、確かめていない（§4.4 で検査にする）。
- 子の起動（`lm/src/host/os.rs`）は Rust の標準の `Command`。継承できるハンドルを限定していない（S5）。

## 2. 問題

- R1（実行物は管理者だけが書ける場所）を、だれが、いつ、どう成り立たせて確かめるかが決まっていない。S1 の照合は、これが崩れると意味を失う。
- TIP は管理者のアプリ、ストアのアプリ、サインイン画面にも入りうる。そこで設定を読み、エンジンにつなぐと、P1・P2 に反する。
- 起動の連鎖（ログオン → エンジン → 候補窓・LM の子、TIP → エンジン、TIP → 設定画面）のどこかが、利用者が書ける値（HKCU、環境変数、カレントディレクトリ）を通ると、R2 が崩れる。
- 管理者として実行されるインストーラは、利用者と別のアカウントで動くことがある（標準ユーザーが管理者の資格情報を入れる場合）。そのとき HKCU と `%LOCALAPPDATA%` は管理者のもので、利用者のものではない。

## 3. 決定 1: 置き場所と、インストーラが守ること

### 3.1 配置
```
C:\Program Files\ikari-ime\            （固定。インストーラで選ばせない）
  ikari-engine-host.exe                 エンジン（決まったパス。ADR 0063 §3 の 5）
  ikari-lm-host.exe、llama*.dll、ggml*.dll、backends\
  candidate\ikari-candidate.exe …       候補窓（.NET と Windows App SDK の一式。ADR 0062）
  settings\…                            設定画面（方式は ADR 0071）
  ikari-data.exe                        取得する部品（ADR 0071。入れるとき）
  tip\<版>\ikari_tip.dll、resources\     TIP（版ごと。ADR 0063）
```
- **インストール先は固定にする。** 別のドライブや利用者のフォルダを選べると、そこが利用者に書ける場所かどうかで R1 が決まってしまう。
- **ACL は Program Files から継承したままにし、インストーラが最後に確かめる。** 確かめること: インストール先とその下のどのファイル・フォルダにも、管理者・SYSTEM・TrustedInstaller 以外に書き込みを許す項目が無い。満たさなければ、登録せずに失敗で終わる。自前の ACL に付け替えない理由: Program Files の既定は、ストアのアプリ（ALL APPLICATION PACKAGES）に読み取りを許している。TIP の DLL はそこにも読み込まれるので、読み取りは残す必要がある。
- インストール先が既にあるときも、同じ検査を先に行う（管理者でないと作れない場所だが、前の版や手作業の変更を拾う）。
- データ（`%LOCALAPPDATA%\ikari-ime\`）は実行物を置かない（P5）。インストーラはここに触れない（§3.3）。

### 3.2 インストーラが行うこと（順）
1. 自分が管理者で動いていることを確かめる。
2. 動いているエンジンを止める（止める口。ADR 0068）。
3. ファイルを置く（エンジンと候補窓は上書き、TIP は新しい版のフォルダ）。§3.1 の検査。
4. **Program Files に置いた DLL** の `DllRegisterServer` を呼ぶ（一時の場所の DLL を登録しない）。
5. ファイアウォールの送信ブロックの規則を、実行ファイルのパスごとに入れる（ADR 0066 §6.2）。規則の名前に版を入れず、入れ直しで重ならないようにする。
6. エンジンの自動起動を登録する（§4.1）。
7. 古い版の `tip\<版>\` を消す（ADR 0063 §3 の 4）。再起動の予約（`MOVEFILE_DELAY_UNTIL_REBOOT`）は、管理者だけが書ける場所のファイルにしか使わない。
- 削除は逆順: 自動起動 → 規則 → `DllUnregisterServer` → エンジンを止める → ファイル。

### 3.3 インストーラが行わないこと
- **利用者ごとのものに触れない**: HKCU、`%LOCALAPPDATA%`、利用者の入力方式の一覧と既定の入力方式。理由は §2 の 4 つ目（別のアカウントで動きうる）と、P1（管理者の権限で、利用者が書ける場所のファイルを読み書きしない。リンクで行き先を曲げられる）。入力方式の追加は、インストーラの最後の案内で利用者にしてもらう。
- 削除のとき、既定ではデータを消さない（ADR 0063 Q3）。「データも消す」は、**その利用者の権限で動く部分**（削除の前に設定画面から、など）で行い、管理者の権限のインストーラからは消さない。形は W5 の実装で決める。
- 通信しない（ランタイムを落としてこない。要るものは同梱する）。
- 一時の場所に実行物を展開して、管理者の権限で実行しない（展開するなら、管理者だけが書ける場所へ）。

### 3.4 インストーラの道具
- 道具に求める条件: 管理者で動く、インストール先を固定できる、一時の場所を管理者だけが書けるように作る、署名なしで作れる、CI で作れる。
- **MSI（WiX）は勧めない。** MSI の「修復」は標準ユーザーが起こせて、SYSTEM で動く。修復の中の独自の処理が利用者に書ける場所に触れると、昇格の穴になる（よく知られた型）。ikari は登録と規則のために独自の処理が要るので、この危険を持ち込むことになる。
- 推奨は Inno Setup（azooKey-Windows の前例。ADR 0063 §1.3）。一時の場所の扱いは、採る版の文書で確かめてから決める（推測のままにしない）。

## 4. 決定 2: 起動の連鎖

| 起動する者 → 起動されるもの | きっかけ | 規則 |
| --- | --- | --- |
| ログオン → `ikari-engine-host.exe` | **HKLM の Run**（§4.1） | 値は Program Files の絶対パス（引用符つき）、引数なし |
| TIP → `ikari-engine-host.exe` | つながらないとき（§4.2） | §4.3 の条件のときだけ |
| engine-host → `ikari-candidate.exe` | engine-host の起動のとき（ADR 0062 §5.4） | Job Object。§4.3 |
| engine-host → `ikari-lm-host.exe` | LM が要るとき（ADR 0060 Q4） | Job Object。渡すハンドルを限定する（S5）。隔離は ADR 0072 |
| 入力メニュー（TIP）・スタートメニュー → 設定画面 | 利用者の操作 | TIP からは §4.3 の条件のときだけ |
| 設定画面 → `ikari-data.exe` | ボタン（ADR 0071） | §4.3 |
| インストーラ → DLL の登録、エンジンの停止 | 導入・更新・削除 | §3.2 |

### 4.1 エンジンの自動起動は HKLM の Run にする（ADR 0040 §2.2 の「HKCU の Run」を改める）
- 理由: (1) HKCU の値は利用者の権限のプログラムが書き換えられる（引数 `--data-dir` を足して、本物のエンジンを偽のデータの場所で動かせる。S1 の照合は通る）。(2) インストーラは利用者の HKCU に触れない（§3.3）。HKLM は管理者だけが書ける（R1・R2）。
- 代わりに、その機械のすべての利用者のログオンでエンジンが起動する。ikari を使わない利用者の分は無駄になる。受け入れる（辞書は使うまで読み込みが進まない。メモリの実測は W5 で取り、大きければ「入力方式に ikari が無ければ、すぐ終わる」を足す）。

### 4.2 TIP からの起動も残す
- 更新や異常終了でエンジンがいないとき、次のログオンまで漢字に変換できないのは、方針の 1 本目（思考を止めない）に反する。つながらないとき、TIP が §4.3 の条件で起動を試みる。続けて失敗したら休止する（今の再接続の休止と同じ数え方。値は新しく決めない）。

### 4.3 起動の共通の規則
- 実行ファイルは、自分のモジュールのパスから決めた絶対パス（R2）。`CreateProcessW` に実行ファイルのパスを明示し、コマンドラインは引用符で囲む。PATH から探さない。
- カレントディレクトリはインストール先にする（利用者が書ける場所にしない）。
- ハンドルは継承させない。要るもの（LM の子の標準入出力）だけを、一覧で渡す（`PROC_THREAD_ATTRIBUTE_HANDLE_LIST`）。
- 引数は固定の語だけ。利用者のデータの場所や設定の値を、引数で渡さない（子が自分で既定の場所から読む）。
- **TIP が起動してよいのは、ふつうの権限のデスクトップのアプリの中だけ**（§5 の表の 1 行目）。それ以外では起動しない。
- **engine-host、候補窓、設定画面、取得する部品は、高い権限で起動されたら、何もせずに終わる**（「管理者として実行」されたエンジンが、ふつうの権限の TIP の相手になるのを防ぐ。P1・R4）。

### 4.4 DLL の探索
- **TIP の DLL は、C の実行時ライブラリを静的に入れる（`crt-static`）。** TIP はほかのアプリのプロセスに読み込まれるので、OS の標準でない DLL に依存すると、そのアプリのフォルダにある同じ名前の DLL が読まれる。CI で、TIP の DLL が取り込む DLL の一覧を、OS の標準のものだけの許可リストと照らす。
  - 実装での追記（2026-11-16）: `crt-static` は `.cargo/config.toml` で Windows の全体に効く。LM の子を `llama`（llama.cpp を静的に入れる）で作るときは、llama.cpp が動的な C の実行時ライブラリ（/MD）で作られて混ざり、リンクできない（`LLAMA_STATIC_CRT=1` でも /MT にならなかった）。**LM の子は全アプリに入らない別プロセスなので、動的な C の実行時ライブラリでよい**とし、`llama` のビルドだけ `RUSTFLAGS` で crt-static を外す（CI の windows ジョブ、`windows/dev/build.ps1 -Lm`）。`vulkan` では llama.cpp と ggml が DLL になり、その DLL は動的な C の実行時ライブラリのまま。LM の子は、製品の検査 `scan-product` の対象外（TIP とエンジンが対象）。
- TIP は名前だけで DLL を読み込まない（`LoadLibrary` に相対の名前を渡さない）。
- engine-host と LM の子は、起動の最初に、DLL の探索を「system32 と自分のフォルダだけ」にする（`SetDefaultDllDirectories`）。`backends\` は今のとおり絶対パスで読む。

### 4.5 LM の子の C の実行時ライブラリ（VC++ の再頒布パッケージ）（2026-11-17 ユーザー決定（Fable の指摘つき））
- 前提（分かったこと）: §4.4 の追記のとおり、LM の子（`ikari-lm-host.exe`）と llama の DLL は、動的な C の実行時ライブラリ（`VCRUNTIME140.dll` など）に依存する。`LLAMA_STATIC_CRT` は効かなかった。OpenMP の `VCOMP140.dll` には静的版が無い。
- **決定: (a) 再頒布パッケージ（`vc_redist`）を同梱して入れる。** 条件:
  1. 同梱する `vc_redist` は、ビルドのときに、固定した sha256 と、Authenticode の署名者（Microsoft）で確かめる。合わなければビルドを止める。
  2. インストーラは、入っていない・古いときだけ `/quiet /norestart` で入れる。入れるのに失敗しても IME は入れ、LM なしで動く（LM の子が起動できないときと同じ。ADR 0072 §5）。
  3. アンインストールでは消さない（ほかのアプリも使う、機械で共有の部品のため）。
  - §3.3 の「通信しない（ランタイムを落としてこない。要るものは同梱する）」と合う。
- **足す守り**:
  - `ikari-lm-host.exe` と llama の DLL に、リンカの `/DEPENDENTLOADFLAG:0x1000`（取り込む DLL の探索を system32 に限る）を付ける。**要検証**: llama の DLL（`backends\` などの隣の DLL）を読む形と両立するか、VM で確かめる。
  - `scan-product` に、LM の子が取り込む DLL の許可リスト（OS の標準のものと、VC++ の実行時ライブラリと、ikari が同梱する DLL だけ）を足す。今は LM の子は対象外（§4.4）。
- **(b) 静的リンクは今は採らない。** `LLAMA_STATIC_CRT` が効かず、`VCOMP140` に静的版が無いため。将来、OpenMP なしで速さが変わらないと測れたら見直す。
- **(c) 放置（何もしない）は採らない。** 動かない機械が出るうえに、セキュリティでも最悪。推測: 実行時ライブラリが機械に無いと、PATH に入っている利用者の書ける場所の同名の DLL が、左文脈を見る LM の子に読まれうる（`SetDefaultDllDirectories` は、実行ファイルの取り込みの表で読む DLL の探索には、起動の最初の時点では効かないため。確かめていない）。
- 実装の課題（issue はリードが切る）: インストーラの同梱と確かめ（ビルドの検査）、入れる条件と失敗のときの動き、`/DEPENDENTLOADFLAG` とその VM での確認、`scan-product` の LM の子の許可リスト。

## 5. 決定 3: TIP が入る先のプロセスの種類ごとの動き

TIP は、有効になるときに 1 回、自分のプロセスのトークンを見て、種類を決める。判定は純粋な関数にし（入力は整合性のレベルと AppContainer かどうか）、Mac でテストする。

| 種類 | 見分け方 | 動き |
| --- | --- | --- |
| ふつうのデスクトップのアプリ | 整合性が中、AppContainer でない | 通常どおり |
| 高い権限（管理者として実行、サービス、サインイン画面や UAC の画面のプロセス） | 整合性が高以上 | **素通し**（決定済み）。エンジンにつながない、設定・ログ・計測の印を読まない・書かない、何も起動しない、候補窓に送らない。キーはすべてアプリに渡す |
| ストアのアプリ、低い整合性のプロセス | AppContainer、または整合性が中より低い | **1.0.0 は素通し**（ADR 0040 §2.3 でストアのアプリは 1.0.0 の後。パイプの DACL も許していない）。失敗するまで試すのでなく、最初から試さない |
| 判定できない（トークンを読めない） | — | 素通し（安全な側） |

- 素通しのとき、入力メニューの表示は英語のモードと同じにする（利用者に「今は変換できない」が見える）。文は出さない。
- 「素通し」は、`shell-core` の secure の扱い（合成しない、周辺テキストを読まない、学習と診断に回さない）より強い。`Shell` を作らない（設定ファイルを読む前に決める）。
- 高い権限のアプリで変換できるようにする条件（署名でエンジンの身元を確かめる、など）は、1.0.0 の後に別の ADR で決める。ふつうの権限のエンジンは E3 が手を入れられるので、署名の照合だけでは足りない点を、そのとき扱う。
- 別の利用者、別のセッション: パイプの名前に SID とセッションが入っているので、エンジンは利用者とセッションごとに別（今のまま）。

## 6. 決定 4: 開発用の経路を、製品に残さない

- 開発用の導入（`windows/dev/register.ps1`）は、利用者が書ける場所の DLL を HKLM に登録する。**開発の VM 専用**とし、スクリプトの最初の表示と README に「この機械では、利用者の権限のプログラムが ikari の DLL を差し替えられる」と書く。日常で使う機械には入れない。
- 製品のビルドと開発用のビルドを、cargo の feature で分ける（名前は実装で決める。例 `dev-knobs`。既定はオフ）。開発用の口は、この feature のときだけ入れる: 環境変数（`IKARI_USER_DIR`、`IKARI_TIP_LATENCY`、`IKARI_LM_GPU`）、計測の印のファイル（`latency.on`）、平らな配置の照合（`peer.rs` の開発用の形）。
- リリースのビルドは feature なしで作り、できた実行ファイルに開発用の環境変数の名前の文字列が入っていないことを、CI で確かめる。
- `OutputDebugString` の扱いは ADR 0073。

## 7. 複数の利用者がいる機械

- 実行物、登録、規則、自動起動は機械全体。エンジン、候補窓、データは利用者とセッションごと。
- 更新と削除のとき、ほかの利用者のセッションのエンジンも止める必要がある（決まったパスの exe を置き換えるため）。止め方は ADR 0068。止められた利用者は、次の入力で TIP が起動し直す（§4.2）。
- 削除しても、ほかの利用者のデータは残る（§3.3）。文書に書く。

## 8. 検討した案

- **インストール先を選べるようにする**: 選んだ先の ACL を付け替えれば R1 は保てるが、付け替えの誤り、ネットワークのドライブ、取り外せるドライブの扱いが増える。得るものが小さい。採らない。
- **管理者なしで `%LOCALAPPDATA%` に入れる（HKCU の登録）**: 高い権限のアプリに読み込まれる DLL が、利用者に書ける場所にあることになる（P1 に反する。ADR 0063 §5）。§5 の素通しがあっても、DLL そのものが差し替えられれば意味がない。採らない。
- **エンジンの起動を TIP だけにする**: 使う人の分だけ起動する利点がある。ただし、アプリが子のプロセスを道連れにする設定（Job Object）だと、エンジンがそのアプリと一緒に終わる。起動を 1 つの道に頼らない方を採る。
- **エンジンをサービス（SYSTEM）にする**: 利用者のデータを SYSTEM が読み書きすることになり、P1 の危険が増える。採らない。
- **高い権限のアプリでも、かな候補だけ出す**: 状態機械を動かすには設定を読む必要がある（R4）。既定値だけで動かす形も考えられるが、1.0.0 は素通しで足りる（ADR 0040 §2.3）。

## 9. 結果

- S1 の前提（インストール先に書けるのは管理者だけ）を、インストーラの検査が保証する。
- ADR 0063 の `TODO(S9)`（HKCU の登録を試すか）は、試さないで閉じられる。
- 実装の issue（承認のあとに切る）: プロセスの種類の判定と素通し、起動の共通の規則とハンドルの限定（S5）、`crt-static` と取り込む DLL の検査、開発用の口の feature、インストーラ、engine-host などが高い権限で終わること。
- 失うもの: インストールに管理者が要る。管理者のアプリとストアのアプリでは、1.0.0 は変換できない。ikari を使わない利用者のログオンでもエンジンが起動する。

## 10. 推測（確かめていないもの。実機の項目にする）

- TIP がサインイン画面や UAC の画面のプロセスに読み込まれるか。読み込まれても、§5 で素通しになる。
- Rust の msvc の既定のビルドは、`vcruntime140.dll` に動的に依存する見込み。`crt-static` で消えることを、取り込む DLL の一覧で確かめる。
- Inno Setup が管理者で動くとき、一時の場所をどう作るか。
- ストアのアプリの中で、TIP の DLL の読み込みと、素通しの動きが期待どおりか。
- ほかの利用者のセッションのエンジンを、インストーラからどこまで行儀よく止められるか（ADR 0068）。

## 11. ユーザーに聞くこと

### 決定済み（ユーザー、2026-11-16。すべて推奨どおり）

- **Q1**: エンジンの自動起動は HKLM の Run（ADR 0040 §2.2 の「HKCU の Run」を改める）。TIP からの起動も §4.2 のとおり残す。
- **Q2**: インストール先は固定。インストーラは利用者ごとのもの（入力方式の一覧、データ）に触れない。
- **Q3**: インストーラの道具は Inno Setup を第一候補にし、MSI は採らない。**本決定は、W5 で一時の場所の扱いを確かめてから（それまで仮）。**
- **確認が済むまで仮のもの**: インストーラの道具（Inno Setup）は、一時の場所の扱いを W5 で確かめてから本決定。§10 の推測（素通しの実機の動き、`crt-static`、ストアのアプリ）は、実装の中で確かめる。

### 決定済み（ユーザー（Fable の指摘つき）、2026-11-17）

- **VC++ の再頒布パッケージ**: (a) 同梱して入れる（sha256 と署名者の確かめ、無い・古いときだけ入れる、失敗しても IME は入れて LM なし、アンインストールで消さない）。足す守りは `/DEPENDENTLOADFLAG:0x1000`（要検証）と `scan-product` の LM の子の許可リスト。(b) 静的リンクと (c) 放置は採らない。→ §4.5。

### （記録）決定の前の問い

- **Q1. エンジンの自動起動を HKLM の Run にする（§4.1）。** その機械のすべての利用者のログオンでエンジンが起動する。**推奨: HKLM。** 利用者に書ける値を起動の連鎖に入れないため。
- **Q2. インストール先を固定にし、インストーラは利用者ごとのもの（入力方式の一覧、データ）に触れない（§3.1、§3.3）。** 入力方式の追加は、案内を見て利用者が行う。**推奨: 固定・触れない。**
- **Q3. インストーラの道具は Inno Setup を第一候補にし、MSI は採らない（§3.4）。** **推奨: Inno Setup。** 本決定は、W5 で一時の場所の扱いを確かめてから。
