## 0. 結論の要約

1. **ショートコードは、英語のモード、日本語のモードのローマ字入力、かな入力のどれでも使える**（Q1 決定）。どのモードでも「頭の `:` で `shortcode` の状態に入り、打った名前を変換中の文字列（`:ey`）として持つ」。頭とは、英語のモードでは語の頭（直前が空白か、分からない）、日本語のモードでは合成の先頭（何も打っていないとき）。`10:30`、`https://`、`Note:`、`chuui:` の `:` は頭でないので、今どおり。
2. **閉じの `:` で名前が完全に一致したら、候補を出す。第 1 候補はそのままの入力（`:eyes:`）、第 2 候補が絵文字（👀）**（Q3 決定）。選んでいるのは第 1 候補なので、**候補を無視して打ち続ければ、そのモードの今の動きと同じ結果になる**。絵文字にするときは ↓ か Tab で選んで確定する（日本語のモードでは Space でも選べる）。
3. **名前として完結しなかったら、ここまでの打鍵を、そのモードのふつうの経路で処理した結果にする（打ち直し）**。英語のモードでは文字列をそのまま確定してキーをアプリに渡す。ローマ字入力では かなの合成に戻る（`:ashita` は `：あした`）。かな入力では かなの合成に戻る。
4. かな入力（JIS）では `:` のキーが「け」なので、**Shift+けのキー（今は何も出ないキー）で `shortcode` に入る**ことを推奨する。入ったあとは、キーの刻印の英字（JIS 配列の ASCII）として名前を読む。キーボードが かなを文字として送る場合（0026 D9）、`:` が文字として届けばそれで入る（Q15 決定）。
5. 前方一致の候補（Q4 決定。FR-06 の例外）は、`shortcode` の状態で Tab か ↓（日本語のモードでは Space も）を押したときだけ出す。サジェストはしない。
6. 候補は殻が作る。殻はセッションの開始時に「名前と絵文字の表」をエンジンから非同期で受け取る。英語のモードの経路でエンジンを同期で呼ばない（0026 §9）。段階1 は学習を使わない。
7. 名前の体系は emoji-data（Slack と同じ。Q6 決定）。データは `fetch-data.sh` で取り、`dict-builder` で `emoji.tsv` を作って配置する（Q7 決定。ADR 0002 §12.2 の例外）。
8. **パレットは macOS 標準の文字ビューアを使う**。何も打っていないときの Ctrl+Cmd+Space と 地球儀キー+E は効いた（S1-0）。**変換中の Ctrl+Cmd+Space は確定されるだけで文字ビューアが出ない**。原因の仮説と確かめ方は §6.2（スパイク S1-1 で確かめる）。
9. 日本語の読みから絵文字（め → 👀）は段階2。CLDR の tts だけ、既定オフ。位置は 3 つ目以降、学習でも 2 位まで（Q8・Q9 決定）。

## 1. 背景と現状

### 1.1 コードで確かめた事実
- **絵文字の候補はすでに少しある**。`core/assets/emoticons.tsv`（自作。324 行）を `EmoticonRewriter`（`core/src/rewriter/emoticon.rs`）が引く。読みの完全一致だけ。絵文字は「えもじ」（20 個）、「えもじえがお」（16 個）などの読みと、「わらい」「さくら」「おすし」など少しの読みにだけついている。ショートコードはない。
- **Rewriter の候補の位置と学習**: `Conversion::add_rewriter_candidates` が、辞書の候補を base_cost の昇順に並べた `rewriter_anchor` 番目（既定 1）+1 のコストで足す（`core/src/converter/conversion.rs`、`options.rs` の `DEFAULT_REWRITER_ANCHOR = 1`）。学習は `(Rewriter の名前, 書式ID)` で行う（`core/src/ranker/learning.rs` の `rewriter_key`）。
- **ローマ字入力の `:`**: 同梱のローマ字表（`input/assets/romaji.tsv`）は `:` を `：`（全角）にする。数字は半角のまま。日本語のモードで `10:30` と続けて打つと、1 つの合成の中で `10：30` になる。
- **かな入力（JIS）の `:` のキー**: `input/src/kana_jis.rs` の表は `def(JisKey::Colon, ':', 'け', None)`。刻印は `:`、Shift なしは「け」、**Shift ありは何も出ない**（`push` は「シフトで文字が出ないキーは何もしない」）。英字のキーも刻印（`a`〜`z`）を持つ。殻は、かな入力のときに修飾キー（Shift 以外）のない JIS の位置のキーを `.jis(番号)` にする（`KeyCodes.swift`）。
- **殻の状態（日本語のモード）**: `InputStateMachine` の状態は `idle`、`composing`、`converting`、`asciiRun` の 4 つ。`asciiRun` は Shift+英字で始まる一時的な英字の列で、ショートコードの状態はこれと同じ形で足せる。
- **Ctrl/Cmd/Option 付きのキー**: `hasCommandModifiers`（Ctrl、Option、Command のどれか）なら、idle ではアプリに渡す（`[.passThrough]`）。合成中・変換中・asciiRun では、表示中の文字列を確定してから渡す（`handleComposing` の先頭 `commitDisplay() + [.passThrough]`）。その前に `boundAction`（キー割り当て）を引くが、`.space` は引かれない（`default: nil`）ので、Ctrl+Cmd+Space は必ずこの経路に入る。
- **`.passThrough` の実行**: `IkariInputController.run(_:)` は `.commit(text)` を `client.insertText` で実行し、`.passThrough` があれば `handle` の戻り値を false にする。つまり変換中の Ctrl+Cmd+Space は「同じ `handle` の呼び出しの中で insertText してから、イベントをアプリに返す」。
- **候補ウィンドウ**: 自前の `NSPanel`。行の高さは固定 26pt。proto の `Candidate` には `annotation` の欄があるが、今は空。
- **入力メニュー**: `InputMenuModel.build(state:)`（純関数）が項目を決め、`MenuBuilder` が `NSMenu` に写す。
- **データの流れ**: 外部のデータは `scripts/fetch-data.sh` が URL・版・sha256 を固定して `data/raw/` に取り、`build-dict.sh`（dict-builder）が `data/build/dict/` に作り、`install-data.sh` が `~/Library/Application Support/ikari-ime/dict/` に置く。

### 1.2 ADR 0026（提案）から前提にすること（2026-10-18 のブランチを読んだ）
- D1: 英語のモードの殻は、打鍵をすべてアプリに素通しにする（`handle` が false）。変換中の文字列も候補も出さない。
- §5.2: `handle` の順番は、英数・かなキーの受け止め → secure の判定 → secure なら素通し → **英語のモードなら記録に回して素通し** → 日本語のモードなら今の経路。英語のモードの経路はエンジンを同期で呼ばず、落ちうる IMK の呼び出し（`string(from:)` など）を使わない（§9）。日本語 → 英語の切り替えでは、合成中なら今の表示のまま確定する。
- §5.5: 英語のモードで打った印字できる文字を「たまり」に足し、区切り（Return、Tab、矢印、修飾キー付き、モードの切り替え、`deactivateServer`、2000 文字）で `CommitText`（読みは空）としてエンジンの確定履歴に送る。

- D9 と §8: 届いた文字が ASCII 以外で読みにならない文字なら、そのまま確定する。かなが文字として届いたら読みに足す。かな入力の設定でも、届いた文字が ASCII でないときはキーコードより文字を優先する。
- D8: 統計の除外アプリ（`stats.exclude`。既定はパスワード管理とターミナル）。

## 2. 問題の定義と守る条件

- 解きたいこと: (1) 名前（`eyes`）から絵文字を、手をホームポジションから離さずに出す。どのモードでも同じ打ち方で。(2) 名前を知らない絵文字を、見て選ぶ。
- 守る条件:
  - **今の入力を壊さない**。**ショートコードを無視して打てば、そのモードの今の結果と同じになる**こと（Q3 の答えの形）。英語のモードは ABC と同じ打ち心地（ADR 0026 P1）、日本語のモードは今の合成と変換。
  - **入力を正とする**。第 1 候補は打ったそのもの。打っていない内容を確定しない。
  - **候補はデータから作る**。名前や読みに対応しない文字を足さない。
  - **サジェストはしない**。打っている途中に候補を自動で出さない（spec「便利な変換」）。候補を出すのは、閉じの `:`（名前が完結した明示）と、明示のキー（Tab、↓、日本語のモードの Space）のときだけ。
  - **モードで動きを揃える**。違うのは「無視したときにどうなるか」だけで、それは各モードの今の動きに合わせる。
  - 英語のモードの経路を重くしない（ADR 0026 §9。エンジンを同期で呼ばない）。
  - こまめに確定するのがコンセプト。仕組みを大きくしない。

## 3. ショートコード

### 3.1 どこで打つか（Q1 決定）
- **英語のモード、日本語のモードのローマ字入力、かな入力の、どれでも打てる**（2026-10-18 ユーザー決定。「かな入力だろうと何だろうと使えるようにする」）。
- 設計の方針: **状態と候補の作り方は 1 つ（`ShortcodeMachine`）にし、モードごとに違うのは (1) 入り方、(2) 名前の文字の読み方、(3) 打ち直しの行き先、(4) 無視したときのキーの扱い、の 4 つだけにする**。(4) は「そのモードの今の動き」に合わせるので、差はモードの約束から決まり、新しい規則を作らない。

| | 英語のモード（0026） | ローマ字入力 | かな入力（JIS） |
| --- | --- | --- | --- |
| 入り方 | 語の頭の `:`（§3.2） | 合成の先頭（idle）の `:` | 合成の先頭（idle）の **Shift+けのキー**（Q15 決定）。かなを文字として受けている場合は `:` の文字 |
| 名前の文字の読み方 | 届いた文字 | 届いた文字 | キーの位置を JIS 配列の英字として読む（`a`〜`z`、数字、`-`。Shift で `_`、`+`）。届いたのが文字なら文字 |
| 打ち直しの行き先 | 文字列をそのまま確定し、残りのキーはアプリへ（素通し） | 打鍵を今の idle からの処理に順に流す（`：あs` の合成になる） | 打鍵を今の idle からの処理に順に流す（かなの合成になる。Shift+け は今どおり何も出さない） |
| 無視したときのキー | 確定してキーをアプリへ（素通し） | 確定して、そのキーで新しい合成を始める（今の変換中と同じ `continueAfterCommit`） | 同左 |

### 3.2 `shortcode` の状態に入る条件
共通（すべて満たすときだけ。満たさなければ今どおり）:
1. secure でない（secure では今どおり。0026 D5 が入れば素通し）。
2. 設定 `emoji.shortcode` が `on`、かつ前面のアプリが `emoji.shortcode_exclude` にない（§8.1。既定はターミナル）。
3. 名前の表を受け取っている（データがないか、まだ届いていなければ入らない）。
4. Ctrl・Option・Command が付いていない。キーリピート（`isARepeat`）でない。

モードごと:
- **英語のモード**: キーが `:`（US 配列の Shift+; を含む）で、**語の頭である**。語の頭とは、ADR 0026 §5.5 のたまりの最後の文字が (a) ない（区切りのあと。直前が分からない）、(b) 空白・改行、(c) `(`、`[`、`{` のどれか。
  - 英数字、`/`、`:`、`"`、`'` などのあとでは入らない。`10:30`、`https://`、`Note:`、`{"a":` は素通しのまま。
  - たまりを使い、周辺テキストは読まない（0026 §9 の約束）。
  - (a) を入る側に倒すのは、入っても無視すれば同じ文字列になるから（§3.6）。逆に倒すと、クリックしてから打つ `:eyes:` が効かない。
- **ローマ字入力**: idle（変換の確定の直後も含む）で、届いた文字が `:`。合成の途中の `:` は今どおり `：`（`10:30`、`chuui:` は変わらない）。
- **かな入力**: idle で、(a) **Shift+けのキー**（`.jis(Colon)` に Shift。今は何も出ないキーなので、今の入力と重ならない）、または (b) `:` が文字として届いた（キーボードが文字を送る場合。0026 D9 の判定で `.character(":")` になる）。(a) を基本にし、(b) も受ける（Q15 決定）。

### 3.3 `shortcode(name)` の状態（打っている途中。変換中の文字列は `:` + name）

| キー | 動き（全モード共通。違いは「打ち直し」の行き先だけ） |
| --- | --- |
| 名前の文字（`a-z 0-9 _ + -`。かな入力はキーの刻印で読む） | 足した名前がどれかの名前の前方に一致すれば、名前に足す（`:ey`）。**一致しなければ打ち直す**（そのキーを含めて、§3.1 の表の行き先へ）。**英語のモードだけ（B52）: 前方一致しなくても、名前の文字が続く間は状態を保つ**（`:eyx` のあと Backspace で直せる）。名前が 64 文字を超えるキーで打ち直す |
| 閉じの `:`（かな入力は けのキー。Shift の有無を問わない） | 名前が**完全に一致**すれば、候補を出す（§3.4 の `shortcodeChoice`）。一致しなければ打ち直す（英語のモードでは、保っていたタイポの名前もここで `:eyxs:` として確定される） |
| Tab、↓（日本語のモードでは Space も） | 前方一致の候補を出す（Q4）。名前が空（`:` だけ）か、前方一致が 1 つもなければ打ち直す（Tab・↓ もアプリへ渡す） |
| BackSpace | 名前の最後の 1 文字を消す。`:` だけのときは、変換中の文字列を消して元の状態に戻る（キーは消費する。今の「`:` を打って消した」と同じ結果） |
| Esc | 打ち直す（英語のモードでは文字列を確定して Esc を渡す。日本語のモードでは合成に戻る＝今の Esc の前の状態） |
| Space（英語のモード）、Enter、そのほかの文字（英大文字、記号、かな） | 打ち直す（そのキーを含めて） |
| 矢印、Ctrl/Option/Command 付き | 打ち直したうえで、そのモードの今の動き（英語は確定して渡す。日本語は表示を確定して渡す） |
| モードの切り替え、secure になる、`deactivateServer`、クリック（`commitComposition`） | 今の表示（`:ey`）のまま確定する（今の合成の扱いと同じ） |

- **「打ち直す」は、`shortcode` の間に受けたキー（`KeyInput` の列）を、ショートコードを切った状態で、そのモードのふつうの経路に順に流すこと**。新しい変換の規則は作らない。英語のモードでは、過去のキーをアプリに渡し直せないので、`:` + 名前を文字列として確定し、今のキーだけアプリに渡す（アプリに届く文字列は素通しと同じ）。
- ローマ字入力の打ち直しの例: `:ash` → 3 打目で `：あs` の合成。以後はふつうの合成。

### 3.4 `shortcodeChoice(candidates, selected)` の状態（候補を出している。変換中の文字列は選んでいる候補）

| キー | 英語のモード | 日本語のモード（ローマ字・かな） |
| --- | --- | --- |
| ↓、Tab | 次の候補 | 次の候補 |
| ↑、Shift+Tab | 前の候補 | 前の候補 |
| Space | 選んでいる候補を確定し、Space をアプリへ | 次の候補（今の変換と同じ。Shift+Space は前） |
| 数字 1〜9 | 選んでいる候補を確定し、数字をアプリへ | その番号の候補を確定（今の変換と同じ） |
| Enter | 選んでいる候補を確定する。**第 1 候補のままなら、Enter もアプリに渡す**（Slack ならそのまま送信。今と同じ）。絵文字を選んでいたら Enter は消費（Q14） | 選んでいる候補を確定（Enter は消費。今と同じ） |
| BackSpace | 候補を閉じ、閉じの `:` を消して `shortcode(name)` に戻る | 同左 |
| Esc | 第 1 候補（そのままの入力）を確定し、候補を閉じる。Esc は消費 | 候補を閉じて `shortcode(name)` に戻る（今の変換の Esc が読みに戻るのと同じ） |
| そのほかの印字できる文字 | 選んでいる候補を確定し、キーをアプリへ | 選んでいる候補を確定し、そのキーで新しい合成（`continueAfterCommit`） |
| ←→、Ctrl/Option/Command 付き | 確定してキーをアプリへ | 確定してキーをアプリへ（今の変換と同じ） |
| モードの切り替え、secure、`deactivateServer`、クリック | 選んでいる候補を確定 | 同左 |

- 候補ウィンドウは日本語のモードと同じもの（ADR 0014）を使う。絵文字の行の右に名前（`:eyes:`）を薄く出す。←→ の文節の操作はしない（1 文節）。
- 第 1 候補の「そのままの入力」は、**変換中の文字列に見えていた半角の `:eyes:`**。日本語のモードでも全角の `：えやｓ：` にはしない（見えていたものを正とする。Q16 決定）。

### 3.5 候補の並び
- 閉じの `:`（完全一致）: 1. そのままの入力（`:eyes:`）、2. 完全一致の絵文字。名前は emoji-data の中で一意なので、絵文字は 1 つ。
- 前方一致（Tab、↓、日本語のモードの Space。Q4）: 1. そのままの入力（`:ey`）、2. 完全一致の絵文字（あれば）、3. 前方一致の残り。名前の短い順、同じ長さなら名前の順。
- 学習で並びを変えない（段階1。§7）。
- 件数と見せ方は今の候補ウィンドウのまま（ADR 0014）。`:s` + Tab のように短いと数百件になるが、殻の中の配列をページで見せるだけ。

### 3.6 他の入力を壊さない条件
| モード | 入力 | 今（または 0026 の素通し） | この ADR のあと | 理由 |
| --- | --- | --- | --- | --- |
| 英語 | `10:30`、`https://`、`Note: ` | そのまま | 変わらない | `:` が語の頭でない |
| 英語 | ` :)` | ` :)` | 同じ。`:` が一瞬 変換中の文字列になり、`)` で打ち直し | `)` は名前の文字でない |
| 英語 | ` :eyes: ` を無視して打つ | ` :eyes: ` | 同じ。閉じの `:` で候補が出て、Space で `:eyes:` を確定して Space を渡す | 第 1 候補がそのままの入力 |
| 英語 | ` :eyes:` + Enter（Slack） | 送信（Slack が `:eyes:` を 👀 にする） | 同じ | 第 1 候補のままの Enter は渡す |
| 英語 | ` :eyes:` + ↓ + Enter | ― | 👀 を確定。Enter は消費 | 絵文字を選んだ |
| 英語 | Ruby の ` :foo,`、Markdown の表 ` :---` | そのまま | 同じ。` :foo,` は `,` で打ち直し（B52。前は `:fo` で打ち直し）。` :---` は `-` が名前の文字なので次の非名前文字（空白など）か確定で打ち直し | 名前の文字でない文字が来る |
| 英語 | Slack のカスタム絵文字 ` :party_parrot:` | 素通し | B52: 閉じの `:` で完全一致しないので打ち直し（`:party_parrot:` が入る）。それまでは下線なしの `:party_parrot` が見える | Unicode の絵文字ではない |
| ローマ字 | `10:30`、`https://`、`chuui:` を続けて | `10：30` など | 変わらない | `:` が合成の途中 |
| ローマ字 | 確定 → `:ashita` | `：あした` | 2 打ほど `:a` と見えてから `：あs` に戻り、以後 `：あした` | 打ち直し |
| ローマ字 | 確定 → `:` → Enter | `：` | `：` | Enter で打ち直してから確定 |
| ローマ字 | 確定 → `:eyes:` → `desu` | `：えやｓ：です` | `:eyes:` を確定して `です` の合成 | 第 1 候補は見えていた半角（Q16） |
| かな | `け` を打つ | け | 変わらない | Shift なしの けのキーは今どおり |
| かな | Shift+けのキー | 何も出ない | `shortcode` に入る（`:` と見える） | 今は何も出ないキー |
| かな | Shift+けのキー → E、Y のキー → けのキー | `いんけ`（Shift+け は何も出ない） | `:ey` と見え、けのキーで `ey` が完全一致しないので打ち直し、`いんけ` の合成 | 打ち直しの行き先は かなの合成 |
| かな | Shift+けのキー → E、Y、E、S のキー → けのキー | `いんいとけ` | 候補 1 `:eyes:`、2 👀 | 完全一致 |
| 全部 | ターミナル、Vim | 今どおり | 変わらない（既定で除外。§8.1） | 1 打鍵ずつアプリが意味を持つ |

- **差が出るのは見え方だけ**: 英語のモードでは、語の頭の `:` から確定までの間、文字はアプリに届かず ikari の変換中の文字列（下線つき）として見える。アプリの自前の補完（Slack の `:` のポップアップなど）は、その間は動かないかもしれない（未確認。§10 の S2）。ローマ字入力では、先頭の `：` を打つと数打の間 英字で見えてから かなに戻る（Q5）。

### 3.7 確定と文脈
- 確定は `client.insertText`。日本語のモードでは、絵文字を選んだ確定もそのままの入力の確定も、`CommitText`（読みは `:` + 名前、表記は確定した文字列）で確定履歴に送る（変換を通さない確定と同じ扱い）。学習には送らない（§7）。
- 英語のモードでは、確定した文字列を 0026 §5.5 のたまりに足す（0026 の経路のまま）。
- secure では入らないので、パスワード欄で変換中の文字列が残ることはない。

### 3.8 打鍵の統計（0026 D7）との関係
- `shortcode` の間に打ったキーも、そのモードの打鍵として記録に回す（物理的に打ったキーなので）。記録するかの判定は 0026 §6.5 のまま。

### 3.9 ADR 0026 に足してほしいこと（境界）
1. **D1 と §4.2 P1 の例外**: 「英語のモードの殻は打鍵をすべて素通しにする。ただし、ADR 0027 のショートコードの状態に入っている間と、入る `:` の打鍵は、`ShortcodeMachine` に渡し、変換中の文字列と候補を出す」。`handle` の 5 番目を「記録 → `ShortcodeMachine.handle` → 何も返さなければ素通し」にする。
2. **§5.5 のたまり**: たまりの最後の文字を `ShortcodeMachine` が読めるようにする（語の頭の判定）。ショートコードで確定した文字列もたまりに足す。
3. **§5.2 のモードの切り替え、D5 の secure、`deactivateServer`**: 英語のモードでも、変換中の文字列（ショートコード）があれば、今の表示のまま確定する。
4. **§9 の約束（英語の経路でエンジンを同期で呼ばない）を、ショートコードも守る**。名前と絵文字の表はセッションの開始時に非同期で受け取る（§9.2）。
5. **D9 と §8.1（直接入力の判定）**: かな入力の設定で `:` が文字として届いたとき、`.character(":")` として状態機械に渡す（ASCII なので D9 の「読みにならない文字はそのまま確定」には入らない、と明記してほしい）。
6. 除外の設定: `emoji.shortcode_exclude`（既定はターミナル）は、0026 の `stats.exclude` と同じ書式にする。中身は別。
7. タスクの番号: 絵文字は B46 以降を使う（B43〜B45 は 0026）。

## 4. 日本語の読みから絵文字（め → 👀。段階2）

### 4.1 「候補は辞書から作り、読みに対応しない文字を足さない」との関係
- 守る決定の対象は、**読みにない文字を表記に足すこと**（「ことだよね」→「ことだよね〜」）と、**読みと合わない表記を LM に作らせること**（user-feedback.md §1.1、§1.3）。
- 絵文字が「読みに対応する」と言えるのは、**その読みの語の別の表記**として出すとき（「め」の語「目」の別の表記が 👀）。これは既にある「ほし → ★☆」「かお → 顔文字」と同じ扱いになる。
- **CLDR の注釈は表記（目、寿司、笑顔）で読みを持たない**。読みをどこから取るかで、原則に合うかが分かれる。

### 4.2 選択肢
| 案 | 内容 | 原則との関係 | 悪い点 |
| --- | --- | --- | --- |
| R0 | 今の `emoticons.tsv`（えもじ、えもじえがお など、自作）だけ | 合う | 量が少ない |
| **R1（採用。段階2。Q8）** | 辞書の候補の表記が CLDR の tts と一致したら、その候補の**別の表記**として絵文字を足す（め → 目 → 👀、すし → すし → 🍣）。読みは辞書の語のもの | **合う** | 候補が増える。「火」→ 🔥 のように意図しない場面にも出る |
| R2 | CLDR の表記を、ビルドのときに Sudachi で読みに直して、読みの表を作る | 誤った読み（目 → もく）で出しうる。**読みに対応しない候補になりうる** | 読みの誤りを人が直す必要 |
| R3 | キーワード（tts 以外も）まで使う | R1 と同じ | 「顔」1 語に 175 個がつく |

- 採るのは **R1、tts だけ**（Q8 決定）。1 つの語に足される絵文字は高々 1 個。
- **並ぶ位置は 3 つ目以降**（Q9 決定。2026-10-18）。**学習でも 2 位まで**（1 位にしない。Q8 決定。2026-10-18）。
  - Q9 との関係: Q9 は「最初に出す位置」（学習の前。元の推奨の「4 位以降」を 3 つ目以降に改めたもの）で、Q8 の「学習でも 2 位まで」は「学習で上がる上限」。元の推奨（4 位以降、学習でも 2 位まで）も同じ 2 つを分けていて、ユーザーが改めたのは最初の位置の数だけなので、矛盾しないと読む。1 回選んだあとに 2 位に上がりうる。
- R1 は段階2（ショートコードを使ってみてから。Q8 決定）。設定 `emoji.reading` の既定はオフ。

## 6. 絵文字パレット

### 6.1 S1-0 で分かったこと（2026-10-18。ユーザーが実機で確かめた）
- 何も打っていないときの Ctrl+Cmd+Space と、地球儀キー+E で、文字ビューアから絵文字を入力できた。**ikari を選んだままで標準の文字ビューアは使える**。
- 「てすと」と打った変換中に Ctrl+Cmd+Space を押すと、「てすと」が確定されるだけで、文字ビューアは出ない。
- 未報告: (c) 入力メニューの「絵文字と記号を表示」、項目 2（候補ウィンドウの絵文字の見え方）、項目 3（文字ビューアの日本語の検索）、どのアプリで (d) を試したか。

### 6.2 変換中の Ctrl+Cmd+Space で文字ビューアが出ない原因（**仮説。確かめていない**）
- **コードで確かめた事実**: 合成中・変換中の Ctrl+Cmd+Space は、`handleComposing`（または `handleConverting`）の先頭で `commitDisplay() + [.passThrough]` になる（§1.1）。`run(_:)` は同じ `handle` の呼び出しの中で `insertText` してから false を返す。ikari の側は「確定してからアプリに渡す」を意図どおりにしている。「確定された」はこの経路の結果と合う。
- **仮説 H1（いちばん有力と考えるが推測）**: AppKit は、変換中の文字列があるときだけ、キーのイベントをメニューのショートカット（キー等価）より先に入力メソッドへ渡す。入力メソッドが false を返すと、イベントはテキストビューの `keyDown` の経路（`interpretKeyEvents`）に進み、メニューのショートカットの処理には戻らない。そのため「編集」メニューの「絵文字と記号」が動かない。何も打っていないときは、メニューのショートカットが先に処理されるので効く。
- **仮説 H2（推測）**: false を返したイベントはメニューにも届いているが、その時点でアプリの側はまだ変換中の文字列があると見て、項目を無効にしている（`insertText` の反映の順序）。
- **仮説 H3（推測）**: アプリによって違う（(d) を試したアプリが 1 つなら、ほかでは出る可能性）。
- **確かめ方**: **スパイク S1-1 で確かめる**（実装のときの A1 ではなく）。理由: 直し方が「入力メソッドから文字ビューアを呼べるか」（S1-1 の A）で決まり、それは P1（入力メニューの項目）と同じ問いなので、1 回の検証版でまとめて確かめられる。手順は §10。
  - ログ（キーコードと修飾キーと状態だけ。文字は書かない）で、何も打っていないときに Ctrl+Cmd+Space が ikari の `handle` に届くか、変換中に届くかを見る。何も打っていないときに届かず、変換中だけ届けば H1 と合う。
  - 変換中の Ctrl+Cmd+Space を「確定してから `NSApp.orderFrontCharacterPalette(nil)` を呼ぶ（イベントは消費）」にした版で、文字ビューアが出るか。出れば H1・H2 のどちらでもこの直し方で足りる。
  - ビルドもインストールも要らない確かめ（S1-0 の追加 (e)）: 変換中に Ctrl+Cmd+Space を押して確定されたあと、**もう一度** Ctrl+Cmd+Space を押すと文字ビューアが出るか。出るなら、直すまでの回避策になる。
- 直し方の案（S1-1 のあとで決める）:
  - F1: 合成中・変換中の Ctrl+Cmd+Space（と、キー割り当ての `palette.emoji`）は、確定してから ikari が文字ビューアを呼び、イベントは消費する。
  - F2: 直さない（2 回押す）。S1-1 の A が入力メソッドから効かなかったときの代わり。

### 6.3 選択肢と決定
| 案 | 内容 | 判断 |
| --- | --- | --- |
| P0 | 標準の呼び方のまま（何も打っていないときは効く。S1-0） | 済み。変換中だけ足りない |

## 7. 学習

- **段階1 のショートコードは学習を使わない**。並びは「そのままの入力、完全一致、前方一致（名前の短い順）」で決まる。完全一致は 2 位に固定で、前方一致は明示のキーで見るものなので、学習の効きが小さい。英語のモードの経路でエンジンを同期で呼ばない約束（0026 §9）も守れる。
- 前方一致の並びに学習が要ると分かったら、殻が確定を片道でエンジンに送り、エンジンが選んだ回数を返す形で足す（候補を消さない。そのままの入力を 1 位から動かさない）。
- R1（段階2）の絵文字は、日本語の変換の候補なので、今の学習（Rewriter の扱い）に乗る。上限は学習で 2 位まで（Q8 決定。§4.2）。
- LM は使わない。

## 9. 設計（境界と契約）

### 9.1 境界
- 殻（`IkariShellCore`）:
  - `ShortcodeTable`: 名前 → 絵文字。前方一致と完全一致。純粋。
  - `ShortcodeMachine`: §3.3・§3.4 の状態。純粋。モードごとの差は `ShortcodeMode` で渡す。
  - `InputStateMachine`（日本語のモード）と、0026 の英語のモードの経路が、`ShortcodeMachine` に委ねる。
- 殻（`IkariIME`）: 表の取得とキャッシュ、候補ウィンドウ（名前を右に薄く）、文字ビューアの呼び出し、入力メニュー。
- エンジン: `engine` の dispatch が表の要求に答える。`core::emoji::EmojiTable` が `emoji.tsv` を読む。段階2 で表記 → 絵文字（R1。`Conversion` の候補に足す）。
- データ: `dict-builder` の emoji → `data/build/dict/emoji.tsv`。
- **候補を作るのは殻**（段階1 は学習を使わないので、エンジンに並べ替えを頼む理由がない。英語のモードの経路でエンジンを同期で呼ばない）。**データを読むのはエンジン**（データの場所と監視はエンジンが持っている。殻から `data/` を読まない）。
- 依存の向きは今のまま（殻 → XPC → エンジン → core）。
- `ShortcodeMachine` は 1 つで、英語・ローマ字・かなの差（§3.1 の表）は引数（`ShortcodeMode`: 名前の文字の読み方と、無視したときのキーの扱い）で渡す。打ち直しそのものは呼ぶ側（`InputStateMachine` か英語の経路）が持つ（`ShortcodeMachine` は「打ち直してほしいキーの列」を返すだけ）。

### 9.2 proto（追加だけ。`schema_version` は 1 のまま）

message EmojiTableReply { repeated EmojiEntry entries = 1; string data_label = 2; }   // 名前の昇順。データがなければ空

- 確定履歴は、日本語のモードでは今の `CommitText`、英語のモードでは 0026 の経路で送る。

### 9.3 core と engine
- `core/src/emoji/`（新しいモジュール。契約コミットで入れた）: `EmojiTable::from_tsv(&str) -> Result<EmojiTable, EmojiError>`、`EmojiTable::empty()`、`EmojiTable::shortcodes(&self) -> &[(String, String)]`（名前の昇順）、`EMOJI_TSV_FILE_NAME`（`"emoji.tsv"`）。`EmojiError` は `BadLine { line }` と `ConflictingName { name }`。パースの仕様はテストの雛形（`#[ignore = "B47-D"]`）のコメントに書いた。段階2 で `EmojiTable::by_surface(&self, surface: &str) -> Option<&str>`。

### 9.4 殻

### 9.5 結果（B48 の実装。英語のモード。2026-10-18）
- 判断は `IkariShellCore` の純関数に置いた（`ShortcodeEnglish.swift`）: `EnglishMode.handleText(_:environment:)` が `ShortcodeMachine`（`.english`）に委譲し、結果を `EnglishTextOutcome`（`actions: [KeyAction]`、`passKey`、区切りで取り出したたまり）にする。コントローラは `actions` を `run` で実行し、`passKey` なら `handle` が false を返すだけ。`flushShortcode()` がモードの切り替え・secure・`deactivateServer`・`commitComposition`・`inputControllerWillClose`・英数かなキーの前の確定。
- 語の頭は `EnglishMode.isWordStart(after:)`（たまりの最後の文字。ない、空白・改行、`(`、`[`、`{` で入る）。入る条件は `emoji.shortcode`、除外アプリ、secure でない、リピートでない、語の頭。修飾キーと表が空かは機械が断る。
- 打ち直しは、見えていた `:` + 名前を `.commit` で確定して今のキーだけ渡す。確定した文字列は `EnglishMode.appendCommitted` でたまりに足す（`CommitText` は既存の区切りの流れ。読みは空）。
- 契約の変更: B44 のスタブ `EnglishShortcodeResult`（`.notHandled` だけ）を削除し、`EnglishMode` に `shortcode` を足した。`ShortcodeMachine` は変えていない。候補ウィンドウのモデル作り（9 件ずつのページ）は `InputStateMachine` の private 関数と同じ内容を `ShortcodeChoosing.panelModel` に複製した（日本語のモードを触らないため。統合後に一本化してよい）。
- テスト: `ShortcodeEnglishTests.swift`（36 件。§3.6 の英語の行、§3.4 の英語の列、入る条件、確定）。
- 実機で未確認: アプリ自前の `:` の補完（Slack など）との相互作用、Enter を渡したときの送信（§10 の S2）。

#### B51: 打っている途中は下線なし（2026-10-18。ユーザーの要望）
- 英語のモードで `:` から名前を打っている間（`.typing`）の変換中の文字列は、下線なし。最後の `:` で候補が出たとき、Tab・↓ で候補を出したとき（`.choosing`）は下線つき（IME の状態に見せるのは候補が出てから）。日本語のモードのショートコード、日本語の合成・変換中の下線は変えない。
- `MarkedText.underlined`（既定 true）を足し、`EnglishMode.handleText` の `.typing` だけ false にした。`MarkedTextAttributes` は false のとき `underlineStyle` を付けず、`markedClauseSegment` だけ付ける（アプリが変換中の文字列と認識するため）。
- 実機で確かめること（コードでは分からない。アプリが下線を描くことがある）: TextEdit、VS Code、Chrome、Slack で、`:ey` の途中が下線なしに見えるか、最後の `:` で下線つきになるか、確定・取り消しが今までどおりか。

#### B52: 途中のタイポを直せる（2026-10-18。ユーザーの指摘）
- 英語のモードだけ、名前の文字（`a-z 0-9 _ + -`）が続く間は前方一致しなくても `typing` を保つ（`ShortcodeMachine.handleTyping` の `mode == .english` の分岐）。上限は `ShortcodeMachine.maxNameLength`（64）で、超えるキーで打ち直す。B51 で打っている途中は下線なしなので、保っても見た目は変わらない。日本語のモード（ローマ字・かな）は変えていない（`:ashita` が `：あした` になる仕組みのまま）。
- 閉じの `:`・Tab・↓・Space・非名前文字・Esc は機械の既存の分岐のまま（完全一致しなければ打ち直し、前方一致が無ければ Tab・↓ も打ち直し）。
- 副作用: ` :---` や ` :foo` のように名前の文字だけが続くと、次の非名前文字かフラッシュまで変換中の文字列が残る。
- テスト: `ShortcodeEnglishTests.swift` に B52 の 7 件ほど（タイポ → Backspace → 候補、タイポのまま閉じる、Tab・↓、顔文字、上限、取り消し）。
- 実機で確かめること: A1-14 (9)。

## 13. 却下した案（要約）
- 閉じの `:` ですぐ絵文字で確定する（前の版の推奨）: Q3 で改められた。そのままの入力を第 1 候補にする。
- 日本語のモードだけで打つ（前の版の推奨）: Q1 で、すべてのモードで使うと決まった。
- モードごとに別の状態機械を作る: 規則が 2〜3 組になる。1 つの `ShortcodeMachine` に、モードの差を引数で渡す。
- 英語のモードの Space で前方一致の候補を出す: 英語の Space は語の区切りで、無視すれば今どおり、を壊す。Tab と ↓ にした。英語のモードで数字キーで候補を選ぶのも同じ理由で採らない。
- かな入力で、Shift なしの けのキーを `:` として扱う: 「け」が打てなくなる。
- 打っている途中に前方一致の候補を自動で出す（Slack のポップアップ）: サジェストはしない（spec）。
- エンジンでショートコードの候補を作る（前の版の `ConvertMode`）: 英語の経路でエンジンを同期で呼ぶことになる。段階1 は学習を使わないので要らない。
- CLDR の表記を Sudachi で読みに直す（R2）、キーワードをすべて使う（R3）: §4.2。
- ikari 独自のパレット（P3）、最近使った絵文字の候補（P2）: §6.3。

## 追記（2026-10-24。#264）小さい文字の候補（`emoji.small_letters`）

Mozc の small_letter_rewriter 相当。英語のモードのショートコードの口（`:name:`）に、上付き・下付き・単位の記号の候補を足す。ユーザー決定（2026-10-24）: 入力は `:m2:` 形、範囲は単位の記号も含む、設定は `emoji.small_letters`（既定オフ）。

- 閉じの `:` のとき、名前が絵文字の表に**なければ**、規則で候補を作る（表が先。`:eyes:` は今までどおり）。候補は「そのままの入力」→ 上付き・下付き → 単位の記号の順。
- `<英字>?<数字>+` → 英字 + 上付きの数字（`:m2:` → m²、`:x10:` → x¹⁰、`:2:` → ²）。`<英字>?_<文字>+` → 英字 + 下付き（`:m_2:` → m₂、`:x_n:` → xₙ。数字、`+ -`、下付きがある英字 a e h i j k l m n o p r s t u v x）。小さくできない文字を含む名前は候補なし。
- 単位の記号（U+33xx）: `:m2:` → ㎡、`:cm:` → ㎝、`:kg:` → ㎏ など（`SmallLetters.swift` の表）。
- 英語のモードだけ（日本語のモードは、前方一致が切れると打ち直すため、`:m2` まで打てない。必要になったら別に決める）。`emoji.shortcode` がオフなら働かない。設定アプリの「絵文字のショートコード」に項目を足した。
- 実装: `macos/Sources/IkariShellCore/SmallLetters.swift`（純粋）、`ShortcodeMachine.smallLetters`、`Settings.emojiSmallLetters`。
