# ADR 0053: 文節削除の「元に戻す」（ikari が覚えて書き戻す。既定 Ctrl+Z）と、英語のモードでの文節削除

- 状態: 採用（「元に戻す」を ikari に足すこと、既定のキー Ctrl+Z、削除の直後だけ受け取ること、キーを設定で変えられること、範囲は文節削除だけ: 2026-11-06 ユーザー決定）。**§10 の Q1〜Q3 は提案**（英語のモードでの文節削除、変換中の取り消し、英字の直前での素通し）
- 日付: 2026-11-06
- 対象: shell-core（`keymap.rs`、`machine/clause_delete.rs`、`machine/mod.rs`、`controller/mod.rs` の英語のモードの口、`scenarios/clause-undo.json`）、プリセットの TSV 3 つ、Swift の `allCases`（設定画面の並び）、`docs/phase2-contract.md` §4。proto と engine と core は変えない
- 前提: origin/feat/clause-delete = 0fae486（PR #199）。ADR 0050（文節ごとの削除）、ADR 0026（英語のモード）、ADR 0041（shell-core の契約）、ADR 0042（判断は Rust）
- タスク: #193
- 判断の置き場所: **すべて Rust（shell-core）**。何を覚えるか、書き戻してよいかの検査、覚えを捨てる条件、英語のモードで文節削除のキーを扱うかは shell-core が決める。Swift は既存の `Commit`（`insertText(text, replacementRange: NSNotFound)` の 1 回）を実行するだけで、新しい動作も判断も足さない（変更は設定画面の並びの 1 項目だけ）

---

## 0. 現状の把握

- 確定後の削除は `ShellAction::DeleteText { range }`。Swift の `ClientAccess.deleteText` は `insertText("", replacementRange:)` を試し、文書の長さが減らなければ `setMarkedText("", replacementRange:)` → `insertText("")` で確定する（PR #199 の a8036d0。TextEdit で前者が無視されるため）。プレビューからの削除は `Restore { text: "", replacing }`。
- 実機（TextEdit、2026-11-06）: 消した直後の Cmd+Z で、消した文字は戻らず、その手前に打った文字列が消える。アプリの「元に戻す」の履歴に、この削除が別の 1 段として残らない。
- `ShellAction::Commit { text }` は Swift で `client.insertText(text, replacementRange: NSNotFound)`（`ClientAccess.insert`）。**キャレットの位置への挿入で、ikari のふだんの確定と同じ経路**。どのアプリでも確定が入る以上、TextEdit でも効く。学習・確定履歴への送信は shell-core が別に送るもので、この動作には付いていない。
- 削除のあとのキャレット: 確定後の即時の削除では、キャレットは消した範囲の始まりに来る（消した範囲はキャレットの直前だから）。プレビューで対象を動かしてから消したときも、変換中の文字列を空で確定するので、始まりに来る（推測。§8 の U1 で確かめる）。
- IMK にはキャレットを動かす API がない（ADR 0050 D10、スパイク S3 は未実施）。
- 英語のモード（ADR 0026 D1・§5.2）は打鍵をすべて素通しにし、例外はショートコードの状態だけ。**英語の経路ではエンジンを同期で呼ばない**（英語の打鍵がすべて ikari を通るので、遅れを出さないため。同 §519 の表）。`controller::handle_english` の順は secure → `mode.*` → ショートコードの口 → たまりに足して素通し。状態機械（`InputStateMachine`）は英語のモードの間、常に `Idle`。
- 3 つのプリセットに `ctrl+z` の割り当てはない。

## 1. 問題の定義

1. 文節削除は 1 回で数文字を消すので、押し間違えたときの損が大きい。アプリの「元に戻す」に頼れない（TextEdit で戻らず、別の文字が消える）。
2. 書き戻しに `replacementRange` を使うと、削除と同じく無視するアプリがある。範囲を使わない書き戻しが要る。
3. キャレットがずれた後（クリック、ほかのアプリの操作）に書き戻すと、違う場所に文字が入る。ikari はマウスの操作を知らない。
4. 英語のモードでは文節削除のキーが素通しになる。日本語の文を英語のモードで直すときに使えない。

## 2. 決定の要約

| # | 決定 |
|---|---|
| U1 | 操作を 1 つ足す。`clause.undo`（既定 `ctrl+z`。3 つのプリセットすべて）。`keymap.clause.undo` で変えられ、`none` で外せる（ユーザー決定） |
| U2 | **覚えがあるときだけ**そのキーを受け取る。覚えがなければ、割り当てがないのと同じ（今の扱いでアプリへ渡す、または今の状態の規則で扱う） |
| U3 | 覚えは**連続した文節削除の段の列**（スタック）。文節削除のたびに 1 段積み、`clause.undo` のたびに 1 段戻す。やり直し（redo）は持たない |
| U4 | 確定後の段の書き戻しは、**キャレットの位置への挿入**（`ShellAction::Commit { text: 消した文字 }`。`replacementRange` を使わない）。書き戻しの前に、キャレットと前後の文字が「消した直後のまま」かを周辺テキストで確かめ、違えば覚えを捨ててキーをアプリへ渡す（§3.2） |
| U5 | 書き戻したあとのキャレットは、**書き戻した文字の後ろ**。即時の削除なら消す前の位置と同じ。プレビューで離れた単位を消したときは、消す前のキャレットには戻らない（動かす API がない） |
| U6 | 読みの入力中の段は、**読みの状態（かなと未確定のローマ字）に戻す**（文字としてではなく）。変換中の段は、**読みの入力中（その変換の読み全体）に戻す**（選んだ候補と区切りは戻らない。§10 の Q2）。再変換の中の削除は段を積まない（Esc で元の表記に戻せるため） |
| U7 | 覚えを捨てる条件: 文節削除と `clause.undo` とプレビューの中の操作以外のキー、確定、フォーカスの変化（`deactivate`、`commitComposition`）、入力先の切り替え、secure になる、モードの切り替え、設定の読み直し。**時間では捨てない**（§4） |
| U8 | アプリの「元に戻す」（Cmd+Z）は ikari が受け取らない（今どおり）。Cmd+Z を押したら覚えは捨てる（U7 の「ほかのキー」）。ikari の書き戻しとアプリの履歴を合わせようとしない（§5） |
| U9 | 英語のモードでも、文節削除（`clause.delete`、`clause.delete_preview`）と `clause.undo` のキーだけは状態機械へ渡し、日本語のモードの確定後と同じ規則で扱う。**英語の文（キャレットの直前が英字）は、エンジンを呼ばずに素通し**し、アプリの Option+Delete（単語の削除）に任せる。英語の文の「文節」は ikari が決めず、アプリの単語にする（§6。§10 の Q1・Q3） |
| U10 | 契約: `KeymapAction::ClauseUndo`（`clause.undo`）を足す。**ShellAction、proto、engine、設定の値は変えない** |

## 3. 取り消しの仕組み

### 3.1 覚える内容（`shell-core/src/machine/clause_delete.rs` の型。外には出さない）

```rust
/// 文節削除の 1 段（ADR 0053 §3）
enum UndoStep {
    /// 確定後。`removed` を `start` に書き戻す
    Committed {
        removed: String,          // 消した文字（表示の文字列そのまま）
        start: Utf16Len,          // 消した範囲の始まり（UTF-16。消したあとのキャレットの予想）
        left: String,             // 消したあとの、start の左の文字（切り出した文の中だけ。ADR 0050 §3.3 の文）
        right: String,            // 消したあとの、start の右の文字（同上）
        document_length: Option<Utf16Len>, // 消したあとの文書の長さの予想（消す前が取れたときだけ）
    },
    /// 読みの入力中。消す前の合成器の中身に戻す
    Composing { kana: String, pending: String, after: (String, String) },
    /// 変換中。消す前の変換の読み全体に戻す（読みの入力中として）
    Converting { reading: String, conversion_id: u64, layout_rev: u32 },
}
// InputStateMachine に `clause_undo: Vec<UndoStep>` を足す
```

- 位置は UTF-16（`Utf16Range` と同じ単位。ADR 0050 §4 の書記素の範囲を、削除のときに `Sentence::utf16_range` で変えた値）。`left`・`right` は文の中だけなので、上限は ADR 0050 の 64 文字で、新しい値は要らない。
- 積むのは削除を返すとき（`DeleteText`、プレビューの Backspace の `Restore { text: "" }`、読みの削除、`RemoveSegments`）。Swift が実際に消せたかは shell-core には分からないので、**積むのは楽観的に行い、正しさは書き戻しの前の検査（§3.2）で守る**。

### 3.2 確定後の段の書き戻し

`clause.undo` を受けたら、段の列の末尾を見る。

1. 周辺テキスト（`left`、`right`、`caret`、`document_length`）を取る。
2. 次がすべて成り立つときだけ書き戻す:
   - `caret` が取れ、`caret.length == 0`、`caret.location == start`。
   - 周辺の `left` の末尾が段の `left` と一致する（周辺の `left` が短く文書の先頭なら、重なる部分で一致）。周辺の `right` の先頭が段の `right` と一致する。
   - 両方が取れるなら `document_length` が段の予想と等しい。
3. 成り立てば `[Commit { text: removed }]` を返し、段を 1 つ除く。**学習・確定履歴・入力の統計には送らない**（ADR 0050 D9 と同じく、削除と書き戻しは変換の証拠ではない）。
4. 成り立たなければ、**段の列を全部捨て、`PassThrough`**（キーはアプリへ。キャレットが動いた、消せていなかった、別の文書になった、のどれか）。

- `Commit` を使う理由: キャレットへの挿入は ikari のふだんの確定と同じ経路なので、確定が入るアプリならどこでも効く（TextEdit で `replacementRange` が無視される問題を避けられる）。`Commit` を流用しても Swift の意味は変わらない（`insertText(text, NSNotFound)` のまま）。専用の動作（`InsertAtCaret`）を足す案は §7.2。
- 文の途中（右に文字が残る）で消したときも、キャレットへの挿入なので同じ。右の文字は動かない。
- 連続した即時の削除（Option+Delete を 3 回）では、段の `start` が順に左へずれる。1 段戻すとキャレットは前の段の `start` に来るので、続けて戻せる（2 の検査がそのまま通る）。

### 3.3 読みの入力中・変換中の段

- **読みの入力中**: 今の状態が「消したあとの状態」（`after` の合成器の中身。空にしたなら `Idle`）と同じときだけ、合成器を `kana`・`pending` に戻し、`refresh_composing` と同じ動作（`SetMarkedText`、`Prefetch`）を返す。違えば段の列を捨てて、キーを今の状態の規則で扱う。文字として書き戻さない理由: まだ文書に入っていない読みなので、読みのまま戻すのが「消す前」と同じ（打ち直しが要らない）。
- **変換中**（文節のモード、全体の候補から入ったものを含む）: 今の変換が段の `conversion_id`・`layout_rev` と同じとき（全部を消して `Idle` になったなら `Idle` のとき）、変換を `Cancel` し、**読みの入力中（`reading` 全体）に戻す**。選んだ候補、区切り、字種変換は戻らない。利用者は Space で変換し直す。完全に元の文節の状態に戻す案（エンジンに 1 段の控えを持たせる）は §7.3 と §10 の Q2。
- **再変換の中**（`ConversionOrigin::Reconversion`）の削除は段を積まない。Esc で元の表記（消した文節も）に戻せる（ADR 0050 §3.2）。`clause.undo` は割り当てがないのと同じ扱いになる。
- 状態をまたぐ並び（読みの削除で空になって `Idle` → 確定後の削除）でも、段の列の末尾から順に戻す。それぞれの検査が状態の食い違いを止める。

### 3.4 キーの扱い（`dispatch`）

- `bound_action` が `ClauseUndo` を返し、段の列が空でないときだけ §3.2・§3.3 へ。空なら、割り当てがなかったものとして今の分岐を続ける（idle なら `handle_idle` の Ctrl の素通し）。
- `ctrl+z` は文字キーと Ctrl なので、idle で引くのは `reconvert` の引き方（Ctrl / Option / Command を伴う文字キー）と同じ。読みの入力中と変換中でも引く（実装で `KeyChord::for_lookup` の対象を確かめる）。キーリピートでも 1 回ずつ戻す。
- どの配列でも動く: 割り当ては今の操作と同じく文字で引く。`z` の位置が違う配列では、その配列の `z` になる（ほかの `ctrl+…` の操作と同じ）。

## 4. 覚えを捨てる条件

| 事象 | 扱い | 理由 |
|---|---|---|
| `clause.delete`、`clause.delete_preview`、プレビューの中の ←/→・Backspace・Esc | 捨てない（削除は段を積む） | 連続した削除をまとめて戻せるように |
| `clause.undo` | 1 段除く（検査に落ちたら全部捨てる） | §3.2 |
| それ以外のキー（文字、Space、Enter、矢印、Cmd+Z を含む修飾つきのキー、プレビューを抜けたあとのキー） | 処理の前に全部捨てる | 「削除の直後だけ」（ユーザー決定）。打ったあとに戻すと、打った文字の位置がずれる |
| 確定（どの経路でも） | 捨てる | 上と同じ。確定はキーから来るので、実際は上で捨てている |
| `deactivate`、`commitComposition`、入力先の切り替え（`activate` で別のクライアント） | 捨てる | 別の文書・別の位置になりうる |
| secure になる（`set_secure(true)`） | 捨てる | パスワード欄の前後の文字を持ち続けない |
| モードの切り替え（`mode.*`、`InputModeChanged`） | 捨てる | 別の操作の流れになる |
| 設定の読み直し（`reconfigure`） | 捨てる | 割り当てが替わりうる |
| 時間 | **捨てない** | マウスのクリックなどキーを伴わない変化は、時間ではなく §3.2 の検査で止める。新しい値（計測の要る値）を足さない |

- マウスでキャレットを動かしてから `ctrl+z` を押すと、検査に落ち、キーはアプリに渡る（覚えも捨てる）。同じ位置に戻してから押したときは書き戻す（文書が消した直後のままなら、戻して困ることはない）。

## 5. アプリ自身の「元に戻す」との関係

- ikari は Cmd+Z を受け取らない。ikari の `clause.undo` とアプリの履歴は別のもので、同期しない。
- 書き戻しはアプリから見るとふつうの確定（文字の挿入）なので、アプリの履歴に挿入として残る。書き戻したあとの Cmd+Z は、アプリの規則でその挿入を取り消す（書き戻した文字が消える）か、手前の打鍵とまとめて取り消す（TextEdit で見た動き）。どちらになるかはアプリ次第で、ikari は揃えない（§8 の U1 で記録だけする）。
- Cmd+Z を押した時点で ikari の覚えは捨てる（§4）ので、Cmd+Z → Ctrl+Z で二重に戻ることはない。
- 「削除の取り消しは Ctrl+Z、それ以外は Cmd+Z」という使い分けを、設定画面の項目の説明に 1 行書く（Swift の UI の文言。判断ではない）。
- アプリの単語の削除（ikari が素通しにした Option+Delete。英語の文など）は、アプリが自分の履歴に積むので、Cmd+Z で戻る。ikari は段を積まない（`clause.undo` はアプリに渡る）。

## 6. 英語のモードでの文節削除（ユーザー要望 2026-11-06）

### 6.1 英語の文の「文節」

- 英語には文節がない。単語は空白で切れていて、macOS のアプリは Option+Delete で単語を消す（多くのアプリで同じ動き。利用者の手が覚えている）。
- ADR 0050 の最小文字数（既定 3、書記素）は、助詞のような短い文節を単独の単位にしないための下限で、英語に当てると `a`・`is`・`to` が隣とまとまり、アプリの単語の削除と食い違う。英語の単語には意味がない。

### 6.2 案の比較

| 案 | 中身 | 良い点 | 悪い点 |
|---|---|---|---|
| **A（推奨）** | 英語のモードでも、文節削除と `clause.undo` のキーだけ状態機械へ渡し、日本語のモードの確定後と同じ規則で扱う。キャレットの直前が英字なら、エンジンを呼ばずに素通し（アプリの単語の削除） | 消す対象は「文書の文字」で、入力のモードとは関係がない、という一つの規則で済む。英語の文はアプリの動きのまま。新しい区切りの規則を作らない | 英語の経路で、このキーに限りエンジンを同期で呼ぶ（ADR 0026 §5.2 の例外を 1 つ足す）。日本語の文のときだけ、再変換と同じ待ち（p99 2.7 ms、上限つき） |
| B | A に加えて、英語の文は ikari が単語に区切って消す（Unicode の単語の境界。最小文字数は数えない） | アプリによらず同じ範囲が消える。ikari の取り消しが英語でも使える | アプリの単語の削除の置き換えで、区切りの規則が ikari とアプリの 2 つになる（記号、`don't`、URL などで食い違う）。消せないアプリでの動きが変わる |
| C | 足さない。英語のモードでは今どおり素通し | 英語の経路が単純なまま | 日本語の文を英語のモードで直すときに使えない（要望に応えない） |

- 推奨は **A**。理由: 要望の場面は「英語のモードのまま、日本語の文を直す」と読める（推測。§10 の Q1 で確かめる）。英語の文には、アプリの単語の削除がすでにあり、置き換える利点が小さい。
- 英語のモードの遅れの約束（ADR 0026 §5.2）は、打鍵ごとの経路の話で、このキーは文字を打つ経路ではない。英字の直前ならエンジンを呼ばないので、英語の文での遅れは増えない。

### 6.3 英字の直前の判定（両方のモードに入れる）

- キャレットの直前から ASCII の空白（改行は含めない）を飛ばした最初の文字が、ASCII の英数字か記号なら、`Reconvert` を送らずに `PassThrough`。
- 日本語のモードにも入れる。今は英字だけの文を `Reconvert` の `Empty` で断っているが、「今日は meeting｜」のような混ざった文では、再変換の区切りで英字と日本語をまとめて消しうる。直前が英字ならアプリの単語の削除のほうが合う。日本語のモードの動きが変わるので §10 の Q3 で確かめる。
- プレビュー（`clause.delete_preview`）も同じ判定で素通しにする。

### 6.4 英語のモードの口（`controller::handle_english`）

- 順を secure → `mode.*` → **文節のキー** → ショートコードの口 → たまりに足して素通し、にする。
- 「文節のキー」は、(1) 状態機械がプレビューのモードの中なら、すべてのキー（プレビューの規則で扱う）、(2) 英語のショートコードの状態でないときの `clause.delete`・`clause.delete_preview`、(3) 段の列が空でないときの `clause.undo`。状態機械に `handles_clause_key(&KeyInput) -> bool` を足し、当たれば `machine.handle` に渡す。キー割り当ての引き方は日本語のモードと同じ（`english_key` で変えたキー）。
- 消す前に英語の文脈のたまりを確定履歴へ送る（`flush`）。削除で取り消さない（ADR 0050 D9 と同じ。記録は消さない）。
- 英語のモードの間、状態機械は `Idle` なので、読みの入力中・変換中の段はない（モードの切り替えで捨てている）。

## 7. 検討した案

### 7.1 アプリの「元に戻す」に任せる
- 何も足さない。TextEdit で消した文字が戻らず、手前の文が消える（実機）。ユーザー決定で採らない。

### 7.2 書き戻しの動作
- **案 A（採用）**: 既存の `Commit`（キャレットへの挿入）。契約を変えない。確定が入るアプリなら効く。
- **案 B**: `Restore { text, replacing: {start, 0} }`（`replacementRange` で位置を指定）。位置を指定できるが、TextEdit で `replacementRange` を無視したのと同じ問題がありうる。Swift が `markedRange` と比べてログを出す（意味が違う）。採らない。
- **案 C**: 専用の `InsertAtCaret { text }`。意味ははっきりするが、Swift の実行は `Commit` と同じ 1 行で、違いがない。`Commit` の意味（確定して印を消す）に将来なにか足すときに分ける（YAGNI）。

### 7.3 変換中の取り消し
- **案 A（採用。§10 の Q2）**: 読みの入力中（読み全体）に戻す。エンジンを変えない。Backspace で読みに戻るのと同じ形。
- **案 B**: エンジンに、`RemoveSegments` の前の `Segmented` の控えを 1 段（連続した分）持たせ、`RestoreSegments { conversion_id, layout_rev }` で戻す。選んだ候補と区切りまで元どおりになるが、proto に要求 1 つ、engine と core に控えの管理が要る（レーン B が要る）。こまめに確定する方針では変換は短く、選び直しは数打鍵なので、今は採らない。
- **案 C**: 取り消さない（変換中は `clause.undo` を素通し）。押し間違えの損が読み全体の打ち直しになるので採らない。

### 7.4 時間で覚えを捨てる
- 一定の時間で捨てる。キーを伴わない変化（クリック）への備えになるが、§3.2 の検査で足りる。時間の値は計測なしに決められない（値は計測で決める方針）。採らない。

### 7.5 段を 1 つだけ覚える
- 直前の 1 回だけ戻す。連続で 3 回消したときに 1 回分しか戻らない。段の列にしても検査は同じで、手間が増えない。採らない。

## 9. 契約、シナリオ、レーン

### 9.1 契約のコミット（リードまたは code-editor 1 つ）

```rust
// shell-core/src/keymap.rs
pub enum KeymapAction {
    // …今の 17 個…
    /// 文節削除を 1 段戻す（ADR 0053）。削除の直後だけ受け取る。既定は `ctrl+z`
    ClauseUndo,
}
// ALL は 18 個。name(): "clause.undo"
```

- 3 つのプリセットの TSV に `ctrl+z	clause.undo`。`settings/defaults.rs` の `KEYMAP_ACTIONS`、Swift の `allCases`（設定画面の並び。表示名「文節の削除を元に戻す」）を同じ順で足す。`docs/phase2-contract.md` §4 の表に行を足し、本文に「削除の直後だけ受け取る。それ以外はアプリへ渡す」を書く。
- ShellAction、proto（`shell.proto`、`engine.proto`、`settings.proto`）、設定の値は変えない。
- 既定の動きは今と同じ（`dispatch` はまだ `ClauseUndo` を扱わない。割り当てがあっても今の扱い）。

### 9.2 シナリオの先書き（`shell-core/scenarios/clause-undo.json`。新規）

1. idle: 「俺は正しい｜」→ Option+Delete（`DeleteText`「正しい」）→ Ctrl+Z（周辺テキストは消したあと）→ `Commit { text: "正しい" }`。
2. idle: Option+Delete を 2 回 → Ctrl+Z を 2 回 → 順に戻る。3 回目の Ctrl+Z は `PassThrough`。
3. idle: Option+Delete → 文字キー → Ctrl+Z は `PassThrough`（覚えを捨てた）。
4. idle: Option+Delete → 周辺テキストのキャレットが違う（クリックで動いた）→ Ctrl+Z は `PassThrough`、続く Ctrl+Z も `PassThrough`。
5. idle: Option+Delete → 周辺テキストの left が消したあとと違う（消せていなかった）→ `PassThrough`。
6. idle: 覚えなしの Ctrl+Z → `PassThrough`（今と同じ）。
7. プレビュー（確定後）: 入る → ← → Backspace → Ctrl+Z → 対象の文字の `Commit`。
8. 読みの入力中: 「きょうはあめがふる」→ Option+Delete → Ctrl+Z → 元の読みの `SetMarkedText` と `Prefetch`。読みを全部消して idle になったあとも戻る。
9. 変換中（文節のモード）: フォーカスの文節を消す → Ctrl+Z → `Cancel` と、読み全体の読みの入力中。再変換の中では Ctrl+Z は今の扱い。
10. `deactivate`、`commitComposition`、secure、`mode.*` のあとの Ctrl+Z は `PassThrough`。
11. `keymap.clause.undo = none`: Option+Delete のあとの Ctrl+Z は `PassThrough`。別のキーに替えられる。
12. 英語のモード（controller のシナリオ）: 日本語の文で Option+Delete → `DeleteText`、Ctrl+Z → `Commit`。英字の直前の Option+Delete → エンジンを呼ばずに `PassThrough`。ショートコードの状態の中の Option+Delete は今の扱い。
13. 日本語のモード: 「今日は meeting｜」の Option+Delete → エンジンを呼ばずに `PassThrough`（§10 の Q3 が推奨どおりのとき）。

### 9.4 懸念点

1. **楽観的に積む**: Swift が消せなかったことを shell-core は知らない。§3.2 の検査で、違う場所に書き戻すことは防げるが、「消せていないのに Ctrl+Z を奪う」ことはない（検査に落ちて素通し）。検査の材料（`caret`、left/right）が不正確なアプリは U1 で見つける。
2. **書き戻しの書式**: キャレットへの挿入なので、リッチテキストの書式（太字など）は挿入位置の書式になる。消した文字の書式は戻らない。
3. **Ctrl+Z をアプリが使う場面**: 削除の直後に限って奪うので、ターミナルの Ctrl+Z（中断）などは、文節削除のできないアプリ（周辺テキストがない）では起こらない。Emacs のキー割り当てを使うアプリでは、削除の直後の Ctrl+Z だけ ikari が受け取る。
4. **英語のモードの例外**: 英語の経路でエンジンを同期で呼ぶ場面が 1 つ増える（日本語の文の直前で文節のキーを押したときだけ）。ADR 0026 の約束の例外として、この ADR と ADR 0026 の参照に書く。
5. **変換中の取り消し**（案 A）は選んだ候補が戻らない。不満が出たら §7.3 の案 B に替える。

## 10. ユーザーに聞くこと（推奨つき）

- **Q1. 英語のモードでの文節削除の中身**: (a) 英語のモードでも日本語の文は日本語のモードと同じに消す。英語の文（直前が英字）はアプリの単語の削除に任せる（ikari は奪わない。Ctrl+Z もアプリへ）、(b) 英語の文も ikari が単語の単位で消す（ikari の Ctrl+Z で戻せるが、アプリの単語の削除と範囲が食い違いうる）、(c) 足さない。**推奨は (a)**（§6.2）。
- **Q2. 変換中に消した文節の取り消し**: (a) 読みの入力中（読み全体）に戻す。選んだ候補と区切りは戻らない、(b) 選んだ候補と区切りまで元どおりに戻す（エンジンに控えを持たせる。実装が 1 レーン増える）。**推奨は (a)**（変換は短く、選び直しは数打鍵。§7.3）。
- **Q3. キャレットの直前が英字のときの Option+Delete（日本語のモードを含む）**: (a) ikari は文節の削除をせず、アプリの単語の削除に任せる（「今日は meeting｜」で `meeting` だけがアプリの規則で消える）、(b) 今どおり再変換の区切りで消す（英字と日本語がまとめて消えうる）。**推奨は (a)**（§6.3）。
