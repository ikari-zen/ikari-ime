- 状態: 承認（2026-10-14。§9 の Q1〜Q7 はすべて「はい」。実装済み、§11）
- 日付: 2026-10-14

- 根拠: [eval/reports/phase3-learning-no-context.md](../../eval/reports/phase3-learning-no-context.md)（試作と測定。試作のコードはコミットしていない）。シナリオの下書き `eval/scenarios/b23-naoru.tsv`、`b23-susumeru.tsv`、`b23-same-context.tsv`

## 0. 現状の把握

### 0.1 学習の式（ADR 0002 §8.4 と今のコード）
- （2026-11-10。ADR 0057）記録の規則が変わった: 1 位以外を選んだ確定は 4 回分、1 位のままの確定は 1 回分として数える。
- 特徴量 f ごとに `share = n(読み, f, 表記) / (N(読み, f) + 1)` を求め、`Σ_f w_f × share × 3000` を加点する。word（セグメント）の一致は ×0.5。1候補あたり 6000 まで（2026-11-10 に 10500 へ上げた。ADR 0057）。半減期 90 日。
- 重み: Unconditional 0.2、Prev 1.0、PrevContent 0.7、Bag 合計 0.8、Topic 0.8（`core/src/user/features.rs`）。
- 確定のたびに、その時の文脈の全特徴量と Unconditional の両方に数える（1位をそのまま確定した場合も）。Unconditional は「その読みでこの人が選んだ表記の割合」になる。
- LearningGuard（2026-10-12、0ecc12e。phase2-q.md §6）: 学習の加点のうち Unconditional の部分（`context_free_bonus`）で前に出た候補が、文脈の証拠（左文脈の連接、文書内キャッシュ、プロファイル、話題の差分の合計）の弱い候補なら、文脈の最良の候補の直後に戻す。LM（zenz）は Guard のあとに働き、制限されない。

### 0.2 原因: 文脈の記録がないと、学習は何回選んでも 900 までしか効かない
文脈の特徴量が記録と一致しないとき、効くのは Unconditional だけで、加点は `0.2 × k/(k+1) × 3000 ×（1 + 0.5）` になる。k = 1, 2, 3 で 450、600、675（B18 の測定と一致）、上限は 900（1語の候補なら 600）。
なおった の差は 2201（治った 8208、直った 10409）なので、**回数を重ねても届かない**。「3 回では足りない」のではなく、何回でも足りない。

### 0.3 0.2 の経緯
- ADR 0002 §8.1 の表で「重み（初期値）」として決めた値。評価で調整した記録はない（phase1-gates.md は a-02 が通ることだけを確かめた）。
- 低くした理由は ADR 0002 §8.4 の最後の項: 「Unconditional の重みを低くしているので、技術文書で品詞を選んだ記録は、小説の文脈ではほとんど効かない」。
- その後、フェーズ2 で LearningGuard を入れ、この原則を**重みではなく規則で**守るようにした（文脈の証拠がある候補を、文脈によらない加点で覆さない）。a-03 と a-04 は Guard を入れる前から通っていた（phase2-q.md §5）。0.2 は、Guard がない時代の守り方が残ったもの。

### 0.4 実機の左文脈は空でないことが多い
エンジンは、周辺テキストが取れればその左側を、取れなければセッションの確定履歴（32 件まで）を左文脈にする（`engine/src/session.rs` の `build_context`）。ユーザーの言う「文脈なし」の多くは、**左文脈はあるが、その読みの記録と一致する特徴量がない**状態と考えられる。左文脈が空のときだけ学習を強くする案（§2 の B）は、この状態に効かない。

### 0.5 LearningGuard の証拠と LM（レポート §2.3、§2.4）
- 風邪が + なおった では、文脈の証拠が 治った を 3230 支持する（Guard が守る）。敵の攻撃を受けて兵士は・ボスが + ひんし も同じ（3865、2616）。
- 今から風呂に入ってくるけど + すすめられる では、話題スコアが 勧・薦 を 1331 支持する。これは話題の雑音（[ADR 0009](0009-verb-notation.md) §0.2-4）だが、Guard にとっては文脈の証拠なので、学習では覆さない。意味のある差（事故で → 瀕死 1428）と大きさが近く、Guard の閾値で分けることはできない。
- LM は空の文脈の なおった で 直った に +1501 を足す（合計の差 3702）。了解です。・さっき見たら のあとでは、差は 1002、1614 に縮む。

### 0.6 今のコードの不具合（重みを上げると表に出る。レポート §3）
- **F1**: `context_free_bonus` は上限（6000）をかける前の Unconditional の加点を返す。同じ文脈で何度も選んで加点が上限で切られると、Guard は切られた分まで「文脈によらない」とみなして引き、学習した候補を戻してしまう。重み 0.2 では差が 900 以下で表に出ないが、重みを上げると、同じ文脈で選んだ表記が1位から落ちる（LM なしの m-a02 で失敗 6 → 9〜11）。
- **F2**: 上限が phrase と word の合計にかかるため、ゲームを + はじめてしった で 始めて知った を選ぶと 1 回目で上限に届く。一方、共有する語「知った」の word の加点は 初めて知った にも付き、回数とともに増える。**main（LM あり）でも、3 回選ぶと 初めて知った に戻る**（m-a02、LM あり。spec の a-02 の「同じ文脈では、選んだ表記が1位になる」に反する）。

## 3. 規則（提案）

### 3.1 重み（back-off）
- 学習の表（phrase の表と、word の読みごとの表）ごとに、今の文脈の特徴量のうち Unconditional 以外のどれかに、その読みの記録があるかを見る。
  - 1つもなければ、その表の Unconditional の重みを `unconditional_backoff_weight`（1.0）にする。「この文脈についての記録がないので、この人がその読みで選んできた割合に戻る」。
  - 1つでもあれば、今の 0.2（`unconditional_weight`）のまま。文脈が一致した記録（合計の重み 最大 3.3）が判断する。
- 左文脈が空のときは、Unconditional 以外の特徴量がないので、いつも 1.0 になる。
- `LearningConfig` に `unconditional_weight`（0.2）と `unconditional_backoff_weight`（1.0）を足し、`--ranker-config` の `learning.*` で変えられるようにする。`unconditional_backoff_weight` を 0.2 にすれば今の振る舞いに戻る。
- 特徴量の作り方と、学習ファイルに書くもの（`features.rs` の `UNCONDITIONAL_WEIGHT` を含む）は変えない。重みは Ranker の側で決める。

### 3.2 F1（LearningGuard に渡す値）
- `LearningRanker::context_free_bonus` は、候補ごとに `max(0, 全体の加点 − 文脈の特徴量だけの加点)` を返す。どちらも上限をかけたあとの値。
- 文脈の特徴量だけで上限に届いた候補は、文脈によらない部分が 0 になり、Guard の対象にならない（文脈が一致した記録は制限しない、という phase2-q.md §6 の規則どおり）。
- back-off で Unconditional の重みが 1.0 になった表でも、その分はすべて「文脈によらない部分」として Guard に渡る。

### 3.3 F2（上限のかけ方）
- 候補ごとに、phrase の加点と word の加点をそれぞれ 6000 で切ってから足す（合計は 12000 まで）。
- 上限の意味（学習の1つの種類の加点が、ほかの判断を際限なく覆さない）は残る。

### 3.4 例（LM あり。レポート §4.2）

| 入力 | main | 提案 |
| --- | --- | --- |
| 毎回違う文脈で 直った を 1 回選んだあと、了解です。+ なおった | 治った | 直った |
| 同じく、さっき見たら + なおった | 治った | 直った |
| 5 回選んだあと、（空）+ なおった | 治った | 直った（4 回までは 治った） |
| 同じく、風邪が + なおった | 治った | 治った |
| 進められる を 1 回選んだあと、今から風呂に入ってくるけど + すすめられる | 勧められる | 進められる |
| ゲームを で 始めて知った を 3 回選んだあと、同じ文脈 | 初めて知った（不具合 F2） | 始めて知った |

## 4. 評価（レポート §4）
- シナリオ: m-naoru、m-real、m-susumeru2、m-mixed、m-a02、m-hinshi と a-02〜a-04（LM あり・なし）。提案（C10gs。A10gs とすべて同じ）の失敗は、LM なしで m-naoru 32 → 16、m-real 16 → 8、LM ありで 24 → 13、16 → 12、m-susumeru2 6 → 3、m-hinshi 18 → 9、m-a02 4 → 1（残る 1 は学習前の probe）。a-02〜a-04 は LM あり・なしとも 0。
- 対照の probe は、どの構成でも1位が変わらなかった。
- 使いながら学習する流し方（1つの読みに 30 件前後の別々の文脈がある、厳しい条件。使い込んだ状態の再現でもある）: 提案（C10gs）は、r-ext が LM なしで 1004 → 1007（+5 -2）、LM ありで 1095 → 1093（+2 -4）、r-ext2 が LM なしで 997 → 998（+3 -2）、r-verbs が LM なしで 85 → 87、LM ありで 112 → 110（恥を + かく → 書く、階段を + のぼる → 昇る）。常に 1.0 にする A10gs は、r-ext の LM ありで 1090（+4 -9）。落ちるのは、文脈の証拠が弱く、ほかの文脈で別の表記を多く選んだ読み。
- 既存の評価セット（homophones、ext、hiragana など）は学習を使わないので変わらない（snapshot で確かめる。§7）。
- 速さ: F1 は「全体の加点」と「文脈の特徴量だけの加点」の 2 つを使う。全体の加点は `rank` で求めたものを使い回せるので、学習の記録を数える回数は今（`rank` と `context_free_bonus` の 2 回）と同じにできる（試作は 3 回数えている）。

## 5. 直らないもの（既知の限界）

| 入力 | 提案のあと | 理由と、何が要るか |
| --- | --- | --- |
| 今から風呂に入ってくるけど + すすめられる（LM なし） | 勧められる | 話題スコアの雑音が文脈の証拠になり、Guard が学習を止める（基本原則どおり）。話題の雑音は [ADR 0009](0009-verb-notation.md) §5 の課題 |
| 左文脈が空の なおった（LM あり） | 4 回までは 治った | LM の差分（+1501）は Guard のあとで制限されない。学習が LM を覆す設計にするかは別の判断（§9 Q4） |
| なおったけど（なおった だけを学習した場合） | 治ったけど（2 位） | 別の読みには word の記録（×0.5）しか効かない。なおったけど を 1 回選べば phrase の記録ができる |
| 風邪が で 治った、文脈なしで 直った を選ぶ人の、バグが + なおった | 治った | 直前の語の特徴量（Prev）が「が」で一致し、風邪が の記録が効く。助詞の Prev が広く一致する問題で、本 ADR の範囲外 |

## 6. 結果
- 得るもの: 文脈がないとき・文脈が学習の記録と関係ないときに、この人がその読みで選んできた表記が出る。報告の なおった、すすめられる が直る。同じ文脈で何度も選んだ表記が1位から落ちる不具合（F2）が直る。spec の原則を、重みではなく LearningGuard の規則で守る形に揃う。
- 失うもの: 文脈の証拠が弱い入力で、ほかの文脈で多く選んだ表記が勝つことが少し増える（r-ext で -2〜-4 件、r-verbs の LM ありで -2 件。同時に +2〜+5 件）。1 回の確定で切り替わる場面が増える（ただし Guard と LM の判断は残る）。学習の Ranker に、表ごとの条件が1つ増える。
- 既存の学習ファイルの記録にも、入れた日から新しい重みがかかる（Unconditional の記録はもうあるので、作り直しは要らない）。
- ADR 0002 §8.4 の最後の項（Unconditional の重みを低くして、別の文脈の選択を効かせない）は、承認されたら一部を本 ADR で置き換える。文脈の記録がある場面では今どおり 0.2、記録のない場面では back-off で 1.0 にし、文脈の証拠は LearningGuard が守る。

## 7. 実装の進め方（レーン 1 つ。core の学習だけ）
1. F2（上限を phrase と word に分ける）と F1（`context_free_bonus` の数え方）を入れ、単体テストを足す。b23-same-context.tsv が LM あり・なしとも通ること（今の main は LM ありで落ちる）。この段で重みは 0.2 のまま。
2. back-off（§3.1）を入れる。単体テスト: 記録のない文脈で 1.0、記録のある文脈で 0.2、左文脈が空で 1.0、`unconditional_backoff_weight = 0.2` で今と同じ。`ranker/learning.rs` の `a02_learning_does_not_override_other_contexts` の「別の文脈の加点 × 3 < 同じ文脈の加点」は、別の文脈（その話は）に記録がなければ back-off がかかるので、見直す（同じ文脈の加点の方が大きいことは残す）。
3. シナリオ: b23-naoru、b23-susumeru、b23-same-context を `eval/scripts/snapshot.sh` の SCENARIOS と `eval/tests/scenario_lm.rs` に足す。あわせて、`--scenario` が `--lm-deadline-ms` を使うようにする（今は既定の締め切りで LM が間に合ったり間に合わなかったりして、結果が揺れる。レポート §1.2）。
4. `eval/scripts/snapshot.sh` で全セットが変わらないこと、シナリオの結果を確かめる。LM ありは Mac で。
5. ADR 0002 の索引の備考に「§8.4 の Unconditional の扱いは ADR 0013 で一部置き換え」と書く。

## 8. 懸念点
- シナリオと値は、報告の 2 つの読みと既存の評価セットから作った。1 回で切り替わることが、普段の使い方で煩わしくないかは、実機で使ってみないと分からない（A1 の確認に足す）。
- r-ext の流し方は、同じ読みに 30 件前後の別々の文脈を混ぜる、実際より厳しい条件。実際の使い方の副作用は、これより小さいと見込むが、測ってはいない。
- back-off の条件は「今の文脈の特徴量のどれかに記録があるか」なので、使い込むほど、助詞の Prev（が、を、たら）や話題の番号がどこかの記録と一致して 0.2 に戻る場面が増える。使い込んだ状態に近い r-ext の流し方でも、報告の型の入力（m-real）でも効いていたが、実機で効かなくなったと感じたら、条件を Prev 以外の特徴量に限ることを考える。
- F2 で、文脈が一致した学習の加点は最大 12000 になる。文脈が一致した記録は「この文脈でこれを選んだ」ものなので、今の考え方の範囲だが、LM の判断（最大 6000）を覆す場面は増えうる。
- LM ありの数値は、締め切りを 3000ms に固定した試作の値。実機は先行計算があるが、締め切りに間に合わないときは LM なしの順位になる（どちらも §4 に載せた）。

## 9. ユーザーの判断が要る点
- **Q1（方針）**: 文脈の記録がないときは、その読みでこれまで選んだ表記がもっと効くようにしてよいか。文脈の証拠がある入力（風邪が + なおった、戦闘の文脈の ひんし）は LearningGuard が守る。Claude の推奨: する。
- **Q2（強さ）**: back-off のときの Unconditional の重みを 1.0 にするか 0.6 にするか。1.0: 毎回違う文脈で 1 回選べば切り替わる（LM ありの空の文脈は 5 回）。0.6: 1〜2 回（LM ありの空の文脈は何回でも切り替わらない）。Claude の推奨: 1.0。
- **Q3（いつ効かせるか）**: 今の文脈にその読みの記録が1つもないときだけ効かせる（案 C）か、常に効かせる（案 A）か。報告の入力ではどちらも同じ。C は LM ありの副作用が小さい（r-ext で +2 -4、A は +4 -9）。A は定数を1つ変えるだけで済む。Claude の推奨: C。
- **Q4（LM との関係）**: 左文脈が空のときの なおった は、LM が 治った を推すので 5 回かかる。学習が LM の判断を覆せるようにするか（学習の加点の一部を LM のあとに置くなど）。Claude の推奨: 今はしない（学習 → Guard → LM の並びは phase2-q.md §6 で決めたもの。変えるなら別の ADR）。
- **Q5（風呂の文脈）**: LM なしでは、話題スコアの雑音が文脈の証拠として学習を止める。基本原則どおりとして、このままにするか。Claude の推奨: このまま（雑音そのものは [ADR 0009](0009-verb-notation.md) §5 の課題として直す）。
- **Q6（不具合の直し方）**: F1、F2 を B23 の実装に含めてよいか（F2 は main でも LM ありで a-02 の型が崩れる不具合）。Claude の推奨: 含める。F2 は「上限を phrase と word に分ける」。
- **Q7（評価の期待）**: `eval/scenarios/b23-*.tsv` の期待（とくに、了解です。・さっき見たら のあとは 直った、風邪が・けががすっかり のあとは 治った）が使い方に合っているか。

## 10. 決定（2026-10-14）

ユーザーが §9 の Q1〜Q7 にすべて「はい」（推奨どおり）と答えた。

| 項目 | 決定 |
| --- | --- |
