# ADR 0033: 地名のデータ（町字の語彙と postal.tsv）を GitHub Actions で作って配り、アプリは成果物だけを取る

- 状態: 提案（2026-10-24。決定はすべて「案」。§12 のユーザーの判断を待つ）
- 日付: 2026-10-24
- 対象: issue #257。新しいワークフロー（`.github/workflows/`）、成果物を置く公開リポジトリ（新設の案）、`scripts/fetch-data.sh`、`scripts/install-data.sh`、取得の道具（新設）、エンジンの見回り（`engine/src/data.rs`）、設定アプリ、`THIRD_PARTY_NOTICES.md`
- 前提: main = 0e28308。ADR 0004 §2・§8（配置と Sandbox）、ADR 0005 §2・§6（設定アプリ、殻、エンジンの経路）、ADR 0030 §6（PDL1.0）、ADR 0032 §3・§7（postal.tsv）、spec の「基本原則」「辞書の更新」、NFR-17・NFR-41・NFR-43
- この ADR ではコードを変えない。事実は researcher の調査（2026-10-24。要約で、逐語の全文は未確認）とコードの確認による。確かめていないことは「推測」「要確認」と書く

## 0. 現状（分かったこと）

### 0.1 データと作り方
- 町字の語彙（大字・町名と住所の連なり）は、`dict-builder` の `town` が lex.csv にし、`build-dict.sh` が **notcore と同じ扱いで `system.dict` に混ぜる**（`--notcore-lex`、`--chain-lex`）。`vectors.bin` も町字の lex を含めて作る。**町字の語彙だけの別ファイルはない**。
- 辞書の一式は `grammar.bin`（約 72MB）、`system.dict`（約 224MB）、`vectors.bin`（約 333MB）。手元の `data/build/dict/` で測った大きさ（非圧縮。圧縮後は未計測）。作るには SudachiDict の raw（手元で約 1.1GB）と chiVe（手元で約 1.9GB）が要る。
- `postal.tsv` は `town` が町字マスターと変換表から作る（約 22MB、115,125 種、読み込み約 91ms。ADR 0032 §3.1）。`town` は Sudachi の lex も入力に取る。
- `fetch-data.sh` は ABR の 2 つを sha256 で固定して取る（更新されたら捨てて止まる）。`build-dict.sh` は `dict.new` に作ってから `dict` → `dict.prev` → 入れ替え。`install-data.sh` は 1 ファイルずつ一時ファイル + rename で `~/Library/Application Support/ikari-ime/dict/` に入れる。
- 形式の版: `dict-format` の `FORMAT_VERSION = 2`（辞書）、`VECTORS_FORMAT_VERSION = 1`、`postal.tsv` はヘッダの `v1`。辞書は版が違うと読み込みで拒む。

### 0.2 エンジンの読み直し（`engine/src/data.rs`、`stack/src/lib.rs`）
- 見回り（1 秒に 1 回まで）が見るのは `user_dict.tsv`、`profile.tsv`、`postal.tsv`、`emoji.tsv` の mtime と大きさだけ。**`system.dict` などの差し替えは見ない**。
- 組み立て直し（`build_stack_with`）は毎回 `dict_dir` から辞書を開き直す。使い回すのは学習、LM、郵便番号の表だけ（`Reuse`）。差し替えは `Arc` の入れ替えで、変換は古い Stack のまま進む。
- よって `postal.tsv` は置き換えれば今でも反映される。辞書の一式は、組み立て直しの合図さえあれば反映できる（合図は今ない）。

### 0.3 権限
- エンジン: App Sandbox、`network.*` なし、Application Support の一時例外だけ。設定アプリ: Sandbox なし、権限のキーなし（「通信するコードを持たない」方針。ADR 0005 §6.2）。`build.sh` が署名後に `network.*` がないことを検査する。
- spec NFR-17: 殻とエンジンは通信しない。例外は辞書の自動更新で、**独立した更新用プロセス**がダウンロードだけを行い、ユーザーが有効・無効を選べる。

### 0.4 GitHub と ABR（調査の要約）
- 町字マスター: 固定 URL、認証なし、約 11.5MB、HEAD で ETag と Last-Modified が取れる。版番号なし。更新頻度の公式の記載は見つからない。
- 変換表: ArcGIS の項目 API の `modified` で更新が分かる。説明文に「原則として月 1 回」。約 6.4MB。
- ABR は「参考情報。更新頻度等の保証なし。予告なく変更・提供中止がありうる」。
- GitHub Release: 1 ファイル 2GiB 未満、総量・帯域の上限なし。Actions: ジョブ最長 6 時間。公開リポジトリは標準ランナーが無料で、60 日間動きがないとスケジュール実行が止まる（ドキュメントの記述は公開リポジトリについて）。
- このリポジトリは **非公開**。非公開のリポジトリの Release は、認証なしでは取れないと推測している（ドキュメントに明記なし。未確認）。

### 0.5 ライセンス（ユーザーの判断。2026-10-24）
- ABR の 2 つは PDL1.0。**出典と、加工したこと・その主体を明記すれば、加工したものを公開してよい**とユーザーが原文を読んで判断した（問い合わせは要らない）。日本郵便のデータそのものは使わない。
- 辞書の一式を配るなら、SudachiDict と chiVe（どちらも Apache License 2.0）の派生物も配ることになる。Apache 2.0 はライセンスの写しと NOTICE を添えれば再配布できる（一般的な条件。各配布物の LICENSE・LEGAL の中身は実装で確かめる）。

## 1. 決定の要約（案）

| 項目 | 決定（案） |
| --- | --- |
| 全体 | **Actions が作る、アプリ（の更新用の道具）は取って確かめて入れ替えるだけ**。端末では作らない。spec「辞書の更新」の「端末でビルドする」を、この形に改める（§10） |
| 置き場所 | ワークフローは**このリポジトリ（非公開のまま）**に置き、成果物は**新設の公開リポジトリ `ikari-zen/ikari-ime-data`（名前は案）の Release** に出す。アプリは認証なしの固定 URL で取る（§2） |
| 町字の語彙の形 | **辞書の一式（grammar・system・vectors）をそのまま配る**（案 T1）。町字の語彙を別の層に分ける（T2）はしない。ただし Actions で作れるか（時間・メモリ・ディスク・圧縮後の大きさ）を段階 1 のスパイクで測り、無理なら T2 の ADR を起こす（§3） |
| 成果物の形 | 部品（`dict`、`postal`）ごとに、**ファイルを 1 つずつ gzip にして並べる**。tar・zip にしない。全体で `manifest.json` 1 つ、`NOTICE.md` 1 つ（§4） |
| 形式が合わないとき | 道具は manifest の形式の版を、自分が読める版と比べ、合わない部品は入れない（今のまま使う）。エンジンも読み込みで拒む（二重） |
| Actions | 週 1 回 + 手動。元データと作る側のコードの変化を見て、変わった部品だけ作る。検証を通ったら**自動で Release**（人の承認なし。§12 Q3）。失敗・検証落ちはこのリポジトリに issue を立てる（§5） |
| 取る道具 | 殻・エンジン・設定アプリには通信させない。**別の小さな実行ファイル（Rust の CLI。名前は案 `ikari-data`）**が取る。設定アプリはボタンでこれを起こすだけ（§6） |
| 入れ替え | `dict.new` に揃えてからディレクトリごと rename（`dict` → `dict.prev`）。最後に `dict/MANIFEST.json` を置き、エンジンはその変化を合図に組み立て直す。取れない・壊れていれば今の版のまま（§7） |
| 手元で作った辞書 | `install-data.sh` で入れた辞書があるときは、道具は**上書きしない**（「手元の版を使用中」と出す）。ユーザーが選んだときだけ Release の版に戻す（§7.3） |
| ABR が止まったら | 最後の版を使い続ける。Actions は issue で知らせる（§8） |
| 段階 | 1 = Actions と Release（手で取るスクリプト）、2 = 設定アプリの「更新を確認」、3 = 自動の取得（§11） |

## 2. 成果物の置き場所

| 案 | 良い点 | 悪い点 |
| --- | --- | --- |
| **A. ワークフローはこのリポジトリ、成果物は公開の別リポジトリの Release**（推奨） | アプリは認証なしの固定 URL で取れる（トークンを端末に置かない）。コード・ワークフロー・評価セットは今のリポジトリに 1 つ。ビルドのコードを公開しなくてよい。非公開のリポジトリには 60 日の停止の記述がない（§0.4。未確認）うえ、コミットが多い | 公開リポジトリに書くトークン（fine-grained、そのリポジトリの contents:write だけ）を secret に置き、期限（最長 1 年の見込み。要確認）で入れ替える。非公開のリポジトリの Actions は無料枠の分数を使う（週 1 回の確認は数分。辞書を作る回の分数は未計測。§11 段階 1 で測る） |
| A'. 公開の別リポジトリにワークフローも置き、非公開のコードをトークンで取る | 公開リポジトリなので分数が無料 | 非公開のコードを読むトークンを公開リポジトリの Actions に置く。ワークフローと作る側のコードが別のリポジトリに分かれ、変更が 2 か所。60 日の停止の対処が要る |
| B. このリポジトリを公開にする | 仕組みが最も簡単（同じリポジトリの Release） | 公開は配布の判断そのもの（NFR-41）で、文書・履歴に個人の情報が混ざっていないかの点検が要る。この ADR の範囲を超える |
| C. 非公開のまま、アプリが GitHub API + トークンで取る | 新しいリポジトリが要らない | 端末に読み取りのトークンを置く（期限・漏れ・入れ替え）。将来ほかの人に配れない |
| D. GitHub Pages | 静的な URL | git のファイルは 100MB の上限があり、辞書（224MB、333MB）が入らない。非公開のリポジトリからの Pages は有料の計画が要る（推測。未確認） |

- **推奨は A**。理由: 端末に秘密を置かず、将来の配布（NFR-41 の「公開する場合は GitHub Releases」）にそのまま続く。作る側のコードは今の場所から動かさない。
- 公開リポジトリには、Release のほかに README（出典・加工・主体の表記、成果物の説明）と NOTICE だけを置く。コミットは Release を出すときに `latest/manifest.json` を更新する 1 つだけ（Actions が直接コミットする。main の保護の決まりはこのリポジトリのもので、データのリポジトリには適用しない案。§12 Q1 に含める）。
- 60 日の停止: ワークフローは非公開のリポジトリにあるので、公開リポジトリの停止は効かない（推測。ドキュメントの記述が公開リポジトリについてだけなので）。もし止まっても、アプリは最後の版で動き続ける（§8）。ワークフローは毎回の成功・失敗を残すので、止まったことは「最後の確認の日付」が古くなることで分かる（設定アプリに出す。段階 2）。

## 3. 町字の語彙をどの形で配るか

町字の語彙は `system.dict` と `vectors.bin` に混ざっている（§0.1）ので、「町字の部分だけを配る」形は今ない。

| 案 | 良い点 | 悪い点 |
| --- | --- | --- |
| **T1. 辞書の一式を Actions で作って配る**（推奨） | 作り方は `build-dict.sh` のまま。変換の結果は手元で作ったものと同じ（評価の差が出ない）。エンジンの変更は「合図で組み立て直す」だけ。spec「辞書の更新」（SudachiDict の新版を追う）も、後で同じ経路に乗る | 大きい（非圧縮 約 630MB。圧縮後は未計測）。町字マスターが変わるたびに一式を取る（頻度は不明）。Actions で Sudachi と chiVe（手元で計 約 3GB）を取り、作る時間・メモリが足りるか未確認（ランナーの大きさは公開・非公開で違う。要確認） |
| T2. 町字の語彙を別の層（`town.dict` など）に分ける | 成果物が小さい（数 MB の見込み） | エンジンに層を足し、連なりが Core の同じ行より優先する（ADR 0030 §12）、d2s の絞り込み、ベクトルを、層でも同じに保つ必要がある。評価の差を詰める実装と測定が大きい |
| T3. 町字の語彙は配らず、`postal.tsv` だけ配る | 最も小さく、今すぐできる | ユーザーの方針（Actions が town と postal.tsv の両方を作る）に合わない。新しい町名が辞書に入らない |

- **推奨は T1**。ただし実行できるかは測っていない。段階 1 のはじめに「Actions で一式を作る」スパイクで、時間、メモリの最大、ディスク、圧縮後の大きさを測る。6 時間・ランナーのディスクに収まらない、または圧縮後が 1 回の取得として重すぎる（目安はユーザーに確認）なら、T2 の ADR を起こす。
- **`postal` は T1 の結果を待たずに先に出せる**（作るのに要るのは Sudachi の lex と ABR の 2 つ。chiVe は要らない）。段階 1 は postal を先、辞書を後に分ける（§11）。

## 4. 成果物の形

### 4.1 ファイル（1 つの Release）
```
manifest.json                 ← 全体の目録（下の 4.2）
NOTICE.md                     ← 出典、加工の内容、加工の主体（ikari-ime）、Apache 2.0 の表記（§4.3）
LICENSES/…                    ← SudachiDict の LICENSE・LEGAL、chiVe の LICENSE（辞書を含む Release のとき）
postal.tsv.gz
grammar.bin.gz  system.dict.gz  vectors.bin.gz    ← 辞書の部品（変わったときだけ。変わらない Release では前の Release を指す）
```
- **1 つの zip にしない理由**: 部品の大きさが 2 桁違い、変わる頻度も違う（変換表は月 1 回、町字マスターは不明、辞書は町字マスターか作る側のコードが変わったとき）。部品ごとに分ければ、変わった部品だけを取れる。tar・zip を開かないので、取ったものの中のパスを信用する処理（ディレクトリの外に書く攻撃）がない。gzip は macOS の標準の道具で開ける（段階 1 の手のスクリプトで使える）。
- 部品が変わらない Release では、manifest がその部品の「出した Release のタグ」を指し、ファイルを複製しない。

### 4.2 `manifest.json`（契約。段階 1 の契約コミットで型と検証を `dict-format` に置く）
- `schema`: manifest 自体の版（1）。
- `release`: タグ（例: `data-20261024-<短いコミット>`）、作った日時（UTC）、作った側のコミット。
- `components.postal` / `components.dict`: 部品ごとに
  - `format`: 形式の版（postal = 1、dict = 2、vectors = 1）。
  - `files`: 名前、gzip 前後の大きさ、gzip 前後の sha256、置いてある Release のタグ。
  - `sources`: 元データごとに URL、ETag、Last-Modified、ArcGIS の `modified`、取った zip の sha256、郵便番号データの版（`metadata.txt`）、Sudachi・chiVe の版。
  - `builder`: `dict-builder`・`dict-format`・ポリシーのツリーの ID（今の `BUILD_INFO` と同じ考え）。
  - `stats`: `TownReport` の数（結べない行、畳めない行、行数、郵便番号の種類）と、評価の結果（§5.3 の 1 位の数）。
- **形式が合わないとき**: 道具は自分がビルドされたときの `dict-format` の定数（読める版）と比べ、合わない部品は入れない。設定アプリには「アプリの更新が要る」と出す。古いアプリは新しい形式の成果物を読まない。形式を上げるときに、古い形式の成果物をいつまで並べて出すかは、その形式を上げる ADR で決める（今は利用者 1 人なので決めない）。

### 4.3 NOTICE（PDL1.0）
- 文言は `THIRD_PARTY_NOTICES.md` の ABR の 2 節（出典、加工の内容、主体 = ikari-ime、「国や日本郵便が作成した未加工のデータではない」）をもとに、取得日と元データの日付を Release ごとに埋める。
- 同じ文言を、公開リポジトリの README と Release の本文にも書く（Release の頁は公開の配布そのものなので）。
- `THIRD_PARTY_NOTICES.md` の「使用方法」を「Actions が加工して公開リポジトリの Release に置き、アプリが取る」に改める。

## 5. Actions の流れ

### 5.1 きっかけ
- `schedule`（週 1 回。曜日・時刻は実装で決める）と `workflow_dispatch`（手動。入力で「検証の落ちを許す」を選べる。§5.3）。

### 5.2 手順
1. **確かめる（毎回。数分）**: 町字マスターは HEAD の ETag と Last-Modified、変換表は ArcGIS の項目 API の `modified`。公開リポジトリの `latest/manifest.json` の `sources` と比べる。作る側のツリーの ID も比べる。**どれも同じなら終わる**（何も出さない）。
2. **取る**: `fetch-data.sh` に「固定しない」取り方（例: `--unpinned abr,postal`。sha256 を確かめず、取ったものの sha256 を出す）を足して使う。Sudachi と chiVe は今の固定のまま。大きいものは `actions/cache` に（鍵は固定の sha256）。ランナーの一時ディレクトリに置く（手元の共有の `data/raw` とは関係しない）。
3. **作る**: 町字マスターか作る側のコードが変わったら、`dict` と `postal` の両方。変換表だけが変わったら `postal` だけ。どちらも `build-dict.sh` / `town` をそのまま呼ぶ。
4. **検証する**（§5.3）。
5. **出す**: 公開リポジトリに Release を作り、ファイルと manifest を上げ、`latest/manifest.json` を更新する。

### 5.3 検証（落ちたら出さずに issue）
- `TownReport` の数を前の manifest と比べる。結べない行・畳めない行・行数・郵便番号の種類が、前の版から大きく変わったら止める。**閾値は計測で決める**（手元の 2 つの版の差を測り、段階 1 の PR でユーザーに確認する。計測のない値は入れない）。
- 読み込みのテスト: 作った `postal.tsv` を `PostalTable::load` で、辞書を `dict-builder --verify` と Stack の組み立てで読む。
- 評価: LM なしで `ikari-eval` を、`address-chain.tsv`、`abr-towns.tsv`、郵便番号のセット、ほか全セット（`eval/scripts/snapshot.sh` の 1 位の数）で回す。前の manifest の数より 1 位が減ったセットがあれば止める。新しい町名で正しく順位が変わることもあるので、手動の実行で「落ちを許す」を選べるようにする（人が issue を見て判断する）。LM ありの評価は Actions ではしない（モデルの取得と時間。手元で見る）。
- ファイルの大きさの上限（2GiB 未満）と gzip の往復。

### 5.4 自動で出すか、PR を通すか
- **自動で Release にする**（推奨。§12 Q3）。理由: main への直接コミットの禁止はコードのための決まりで、データの Release は main に何も書かない。PR を通すと月 1 回は人の操作が要り、「アプリが取りに行けば最新」という目的が人の手で止まる。検証（§5.3）を通らないものは出さない。
- `fetch-data.sh` の固定の sha256 は、Actions は書き換えない（手元の再現用。人が要るときに PR で上げる）。

### 5.5 知らせ方
- 失敗（取得の失敗、ABR の 404、検証の落ち、トークンの期限切れ）は、このリポジトリに issue を立てる（ラベル `data-update`。同じ種類の issue が開いていればコメントを足す）。成功は知らせない（Release の一覧で分かる）。

## 6. だれが取るか

| 案 | 判断 |
| --- | --- |
| エンジンが取る | 却下。NFR-17。エンジンに `network.client` を足すと、変換の経路のプロセスが外部とつながる |
| 殻が取る | 却下。NFR-17。殻は全アプリのキー入力を扱う。遅延や失敗が入力に響く |
| 設定アプリが取る | 却下。設定アプリは「通信するコードを持たない」として Sandbox を外した（ADR 0005 §6.2）。ここに通信を足すと、その前提が崩れる |
| **別の実行ファイル `ikari-data`（Rust の CLI）**（推奨） | spec の「独立した更新用プロセス」。manifest の型と検証を `dict-format` と共有でき、Actions の検証（§5.3）と同じコードを使える。`cargo test` で試せる |
| シェルのスクリプト | 段階 1 の手の取得だけに使う（`scripts/fetch-release-data.sh` など）。アプリには入れない |

- 置き場所: `ikari.app/Contents/Helpers/ikari-data`（ADR 0005 の `Helpers/` に並べる）。CLI として手で叩いてもよい。
- 権限: App Sandbox に入れ、`network.client` と Application Support の一時例外（エンジンと同じ）だけを付ける。`build.sh` の検査に「`network.*` は `ikari-data` だけ」を足す。HTTP の部分（小さい crate か macOS の `curl`）は実装で決める。足した crate は `THIRD_PARTY_NOTICES.md` に書く。
- 取得元の URL はビルドに埋め込み、設定やユーザーのデータから変えられないようにする（spec「辞書の更新」の安全策）。送るのは GET だけで、利用状況を付けない。
- 段階 2 では設定アプリの「更新を確認」が `ikari-data check` / `update` を起こし、結果（今の版、最新の版、最後に確かめた日時、エラー）を表示する。設定アプリは通信しない。

## 7. 確かめ方、入れ替え、反映、戻し方

### 7.1 確かめ方
- HTTPS の固定の URL から `manifest.json` を取り、各ファイルの gzip 前・後の sha256 と大きさを確かめる。形式の版を確かめる（§4.2）。
- 署名（manifest に Actions の秘密鍵で ed25519 の署名を付け、公開鍵をアプリに埋める）は**段階 1〜3 では付けない**。sha256 は壊れたファイルを防ぐが、GitHub の側が乗っ取られた場合は防がない。利用者が作者 1 人の今は、作る側のコードも同じ GitHub にあるので、署名で守れる範囲が小さい。**ほかの人に配る前には署名を必須にする**（そのときの ADR の条件として残す）。
- 取ったファイルは信用しない入力として扱う。読む側（Sandbox のエンジン）がすでに形式を確かめる（辞書の版の拒否、`postal.tsv` の行の検査）。

### 7.2 入れ替え（原子的に、前の版を残す）
- 取ったものは `~/Library/Application Support/ikari-ime/updates/`（新設。作業用と状態 `state.json`）に置く。
- **辞書**: `dict.new/` に新しい 3 ファイルを置き、部品にない今のファイル（`emoji.tsv` など）は `dict/` からハードリンクかコピーで足し、最後に `MANIFEST.json` を書く。`dict` → `dict.prev`、`dict.new` → `dict` の rename（`build-dict.sh` と同じ手順）。エンジンが mmap している古いファイルは、閉じるまで生きる。
- **postal**: 1 ファイルなので、一時ファイル + rename（`install-data.sh` と同じ）。前の版は `postal.tsv.prev`。`dict/MANIFEST.json` の部品の行を更新する。
- 途中で失敗したら `dict.new` を消し、今の版のまま。
- 戻す: `ikari-data rollback` が `dict.prev` と入れ替える。戻した Release のタグは `state.json` に「飛ばす」として残し、自動の取得（段階 3）が同じ版を入れ直さない。

### 7.3 手元で作った辞書との関係
- `install-data.sh` は `dict/MANIFEST.json` に `origin = local`（と `BUILD_INFO` の要約）を書くように直す。
- `ikari-data` は `origin = local` の部品を上書きしない（設定アプリに「手元の版を使用中」と出す）。ユーザーが「Release の版に戻す」を選んだとき（`ikari-data update --replace-local`）だけ入れる。理由: 開発で手元の辞書を試しているときに、取得が黙って上書きすると、評価や実機の確認の前提が崩れる。

### 7.4 エンジンへの反映
- 見回り（`DataWatch`）に `dict/MANIFEST.json` の mtime と大きさを足す。変わったら、辞書を開き直して組み立て直す（`Reuse` は今のまま。学習・LM・郵便の表を使い回す。postal の部品が変わったときは `reuse.postal = None`）。
- 混ざりを防ぐ: 辞書の 3 ファイルは同じディレクトリの rename で一度に変わり、合図の `MANIFEST.json` は最後に書く。組み立て直しの途中で入れ替わったとき（古い grammar と新しい system を開くなど）に気づけるよう、読み込みで 3 ファイルの組が同じビルドのものかを確かめる（どのヘッダで確かめられるかは要確認。なければ契約で足す）。合わなければ組み立て直しを捨て、古い Stack で続け、次の見回りでやり直す。
- 段階 1（エンジンの変更の前）は、辞書の差し替えは次にエンジンが起きたときに効く（今の `install-data.sh` と同じと推測。要確認）。

## 8. ABR が止まったとき・変わったとき
- 取れない（404、形式の変化で `town` が失敗、検証の落ち）なら、Release を出さず issue を立てる（§5.5）。アプリは最後の版を使い続ける。何もしなくても変換は今のまま動く。
- アプリの側の失敗（通信できない、sha が合わない、形式が合わない）も、今の版のまま。設定アプリに理由を出す（段階 2）。自動の取得（段階 3）は失敗を記録して次の回に回し、通知はしない（入力の邪魔をしない）。
- ABR が提供をやめたら、最後の版のまま止め、代わりの元データを別の ADR で考える。

## 9. ユーザーデータと共有の `data/` の決まりとの整合
- Actions は使い捨てのランナーで動き、手元の `data/raw`・`data/build` に触れない。
- `ikari-data` が書くのは `~/Library/Application Support/ikari-ime/` の `dict/`、`dict.new/`、`dict.prev/`、`updates/` だけ。学習、ユーザー辞書、プロファイル、`settings.tsv` には触れない（ADR 0005 §2 の書き手の決まりのまま）。`dict/` の書き手は `install-data.sh` と `ikari-data` の 2 つになるが、§7.3 で上書きの向きを決める。
- 配置は ADR 0004 §2 に `updates/`、`dict.prev/`、`dict/MANIFEST.json` を足す。

## 10. 基本原則と spec との関係
- **入力の結果が変わる**: 辞書の更新は変換の候補を変える。これは spec「辞書の更新」で決めた機能（自動更新は既定で有効、ユーザーが選べる）で、補完ではない。段階 3 の既定値は spec に従うが、段階 3 の issue を始める前にユーザーにもう一度確かめる。
- **spec の改め**（承認されたら spec を直す）: 「辞書の更新」の安全策のうち、(1)「ダウンロードと辞書のビルドはアイドル時かつ電源接続中」→ ビルドは Actions、端末はダウンロードだけ（辞書の部品は電源接続中だけ。段階 3）。(2)「取得元は SudachiDict の公式リリースに固定」→ 取得元はこのプロジェクトの公開リポジトリの Release に固定（SudachiDict の版は Actions が固定で取る）。(3)「切り替える前に評価セットを実行」→ Actions が出す前に実行（§5.3）。端末では評価しない。
- NFR-17 は変えない（殻とエンジンは通信しない。通信は独立した `ikari-data` だけ）。

## 11. 段階（1 タスク 1 ブランチの issue に切れる形）

**段階の見直し（ユーザー決定 2026-10-24）**: このリポジトリが公開されるまで、アプリは認証なしで Release を取れない（非公開の Release は read 権限が要る。推測、未確認）。そこで、**非公開のままできる段階 1 を先に進め、アプリが自分で取る段階 2・3 はリポジトリの公開後にする**。
- 段階 1 の置き場所は、**このリポジトリの Release（非公開）**。作者が `gh release download`（作者の `gh` の認証）で手で取って入れる。利用者が作者 1 人のうちは足りる。
- 段階 1 の 1（公開リポジトリとトークン）は、**公開の時期に合わせて決める**（公開するリポジトリごと公開になるなら、別リポジトリは要らない。§2、§12 Q1）。段階 1 の 6（手の取得）は、`gh` の認証を使う形で作る。
- 段階 1 の 4（スパイク）の結果（圧縮後の大きさ）が出てから、§12 Q2・Q3 を決める。

### 段階 1: Actions が作って Release に出す（手で取って入れる）
1. **公開リポジトリとトークン**（ユーザーの操作。公開の時期に合わせる。上の見直しのとおり、段階 1 では要らない）: リポジトリを作り、README と NOTICE を置き、fine-grained のトークンを secret に入れる。
2. **契約**: `manifest.json` の型と検証（`dict-format`）、`MANIFEST.json` の `origin`、`fetch-data.sh --unpinned` の形。
3. **postal のワークフロー**: 確かめる → 取る → `postal` を作る → 検証（閾値は計測して PR で確認） → Release。失敗の issue。
4. **スパイク: Actions で辞書の一式を作る**（捨てるワークフロー）。時間、メモリ、ディスク、圧縮後の大きさを測り、この ADR に追記する。T1 で進めるかをここで決める（§3）。
5. **dict のワークフロー**: 4 で進めるとなれば、`dict` の部品と評価（snapshot の 1 位）を足す。
6. **手の取得**: `scripts/fetch-release-data.sh`（manifest と sha256 を確かめ、§7.2 の手順で入れる。`--dry-run`）と、`install-data.sh` の `origin = local`。
7. `THIRD_PARTY_NOTICES.md` の「使用方法」と、spec「辞書の更新」の改め。

### 段階 2: 設定アプリの「更新を確認」
1. **`ikari-data`（Rust の CLI）**: `check`、`update`、`rollback`、`status`。段階 1 のスクリプトと同じ手順。単体のテスト（壊れた sha、形式の違い、途中の失敗で今の版が残る）。
2. **エンジンの合図**: `DataWatch` に `dict/MANIFEST.json`、組の確認（§7.4）。
3. **バンドルと権限**: `Helpers/ikari-data`、entitlements、`build.sh` の検査。
4. **設定アプリ**: 「このソフトについて」か新しい欄に、版、最後に確かめた日時、「更新を確認」「前の版に戻す」「Release の版に戻す」。

### 段階 3: 自動の取得
1. LaunchAgent（週 1 回。`SMAppService` か `~/Library/LaunchAgents` かは issue で決める）で `ikari-data update --auto`。辞書の部品は電源接続中だけ。設定 `update.auto`（既定は §10）。
2. 失敗の記録と、設定アプリでの表示。

## 12. ユーザーに聞くこと（推奨つき）
- **Q1. 成果物の置き場所**: 推奨は **A（ワークフローはこのリポジトリ、成果物は新設の公開リポジトリ `ikari-zen/ikari-ime-data` の Release）**。公開リポジトリの作成と、そこに書くトークン（期限つき）の発行はユーザーの操作が要る。データのリポジトリには、Actions が Release とその目録の更新を直接コミットしてよいか（PR を通さない）もあわせて決めたい（推奨: 直接でよい。コードではないため）。
- **Q2. 町字の語彙の配り方**: 推奨は **T1（辞書の一式を配る）**。1 回の取得は数百 MB になりうる（圧縮後は未計測。町字マスターが変わったときだけ）。段階 1 のスパイクで測り、重すぎれば T2（別の層）の ADR を起こす。受け入れられる 1 回の大きさの目安があれば知りたい。
- **Q3. Release を自動で出すか**: 推奨は **検証（§5.3）を通ったら自動で出す**。検証に落ちたら出さずに issue。別の案は「Actions は下書き（pre-release）までにし、ユーザーが公開する」（月 1 回ほど人の操作が要る）。

## 13. 懸念・要確認
- Actions で辞書の一式を作れるか（時間、メモリ、ディスク、分数の無料枠。アカウントの計画は未確認）。段階 1 の 4 で測る。
- 非公開のリポジトリのスケジュール実行が 60 日で止まらないこと（ドキュメントの記述からの推測）。
- ABR の HEAD・ArcGIS の `modified` が、中身が変わったときに確実に変わるか。変わらずに中身だけ変わる場合に備え、月 1 回は取って sha256 で比べる（案。実装で決める）。
- 辞書の 3 ファイルが同じビルドのものかを、どのヘッダで確かめられるか（§7.4）。
- 部品が混ざる時期（新しい postal と古い辞書）: 町字マスターが変われば両方を作り直すので、同じ Release の中では揃う。片方だけ取りそこねたときは、§3.1 の ADR 0032 のとおり害は小さい（郵便番号の候補が出ないことがある）と推測。
- トークンの期限切れでワークフローが止まる。issue で分かる。
