# ADR 0071: Windows の設定画面の方式を「通信を止められるか」で選び直す（WebView2 を採らず WinUI 3 を推奨）。取得する部品 `ikari-data` を、通信してよい唯一の部品として決める

- 状態: 提案
- 日付: 2026-11-16
- 対象: Windows の設定画面（未作成。`windows/settings/`）、取得する部品 `ikari-data`（未作成）、`shell-ffi`（設定画面が呼ぶ口）、設定アプリ（macOS。ボタンと表示だけ）。この ADR ではコードを変えない
- 前提: main = 94f65ae。[ADR 0066](0066-security-premises.md) §6（通信しないの定義と 3 層の守り。同梱する他社の部品の通信も数える）、[ADR 0067](0067-windows-install-layout-and-launch-chain.md)（置き場所と起動）、[ADR 0068](0068-ipc-endpoints.md) §4（設定の口）、ADR 0040 §2.5（設定画面の方式はスパイクで決める）、ADR 0062（候補窓は WinUI 3、C#、パッケージなし・自己完結。2026-11-14 に本決定）、ADR 0033 §6（`ikari-data` の案）、ADR 0058（inbox と束）、ADR 0060（URL の取得はボタンを押したときだけ、sha256 なしは警告で許可）、#248、#249、#322（設定画面のスパイク）
- ユーザーの決定（2026-11-16）: WebView2 が設定画面に適しているかは決定済みとせず、この設計の中で評価して決める
- 判断の置き場所: 設定の中身は今のとおり Rust（`shell-core` の `settings` と `bridge`）。取得の判断（どこから、何を確かめるか）は Rust（`ikari-data`）。設定画面は、描くことと、ボタンで部品を起こすことだけ（UI であるため）

---

## 1. 分かったこと

### 1.1 WebView2（Microsoft Learn。2026-11-16 に見た）
- 「Data and privacy in WebView2」: WebView2 は、Windows の診断データの設定がどうであっても、**必須の診断データを集める**。アプリの開発者は、診断データの収集の全体を制御できない、と書いてある。アプリから止められるのは 2 つ: SmartScreen（`IsReputationCheckingRequired`。既定はオン）と、クラッシュのダンプの Microsoft への送信（`IsCustomCrashReportingEnabled`）。
- 「Distribute your app and the WebView2 Runtime」: 配り方は 2 つ。
  - Evergreen: Windows 11 に入っている共有のランタイム。Microsoft の更新の仕組みが、新しい版を自動で落とす（アプリは版を選べない）。
  - Fixed Version: アプリが特定の版を同梱する。自動では更新されない。250MB を超える。版を上げて配り直すのはアプリの役目。
- ランタイムの実体は、別の実行ファイル（`msedgewebview2.exe`）のプロセス群で動く。

### 1.2 リポジトリ
- 設定画面のスパイク（ブランチ `spike/w4-s0-settings-ui`。#322）は、WebView2（wry + tao）と Slint の 2 つを作った。**動かしたことはない**（手順書の冒頭）。WinUI 3 を作らなかった理由は「C# と .NET のビルドとランタイムの配布が増える」。この理由は、そのあと候補窓が WinUI 3 に決まった（ADR 0062）ので、もう当てはまらない。
- Slint のライセンスは、GPL-3.0、表示つきの無償、商用の 3 択（スパイクの手順書）。
- 設定の中身を C の ABI で呼ぶ口（`shell-ffi` の `ikari_settings_*`）は、macOS の設定アプリのためにすでにある。
- 今の `Cargo.lock` に、HTTP・TLS の crate は無い。開発用の取得（`cargo xtask data fetch`）は、外の `curl` を起動し、sha256 を照らす（`docs/proxy-download.md`）。
- モデルは、アプリに埋めた既知の sha256 の表で確かめる（`resource`）。`ikari-data` はまだ無い。

## 2. 決定 1: 設定画面の方式は、WebView2 を採らない。推奨は WinUI 3

### 2.1 比べる軸（セキュリティの軸を先に置く）

| 軸 | WebView2（Evergreen） | WebView2（Fixed Version） | WinUI 3（C#。候補窓と同じ） | Slint（Rust） |
| --- | --- | --- | --- | --- |
| **その部品が自分から通信するか**（ADR 0066 §6.1） | する。必須の診断データは止められない（§1.1）。更新も自動 | 診断データは同じ。更新の通信は無い見込み（推測） | しない見込み（推測。§6 で確かめる） | しない（通信の手段を持たないことを、依存の検査で確かめられる） |
| **ファイアウォール規則が届くか**（L2） | 届かない。実体は共有の別の実行ファイルで、そこを止めるとほかのアプリも止まる | 自分のフォルダの `msedgewebview2.exe` に規則をかけられる見込み（推測） | 届く（自分の exe） | 届く |
| **画面の攻撃面** | HTML とスクリプトの実行環境。画面に出す文字（ユーザー辞書の語、アプリの名前、モデルの名前）の扱いを 1 か所誤ると、スクリプトが画面の権限（設定の変更、学習の消去、取得の起動）で動く | 同じ | 文字を文字として出す部品。スクリプトの実行環境は無い | 同じ |
| **脆弱性の修正の届き方** | Microsoft が自動で届ける | **ikari が配り直す**。ブラウザの実行環境の修正を、自動の更新を持たない ikari が追うことになる | .NET と Windows App SDK の修正を、ikari が配り直す（候補窓ですでに負っている） | crate の更新 |
| 新しく増える配布物・言語 | ランタイムは OS に入っている | 250MB 超 | **増えない**（候補窓の一式を共有） | crate。ライセンスの選択が要る |
| 設定の中身（Rust）との境界 | 文字列のやり取り（JS ↔ Rust） | 同じ | C の ABI（`shell-ffi`。macOS の Swift と同じ形） | なし |
| 画面の入力欄で ikari が使えるか、見た目、読み上げ | 未確認 | 未確認 | 未確認（OS の標準の部品） | 未確認 |

### 2.2 決定
- **WebView2 は採らない。** Evergreen は、止められない通信を持ち、規則も届かない（ADR 0066 §6.1 の 3 つ目に当たる）。Fixed Version は、規則をかければ止められる見込みはあるが、ブラウザの実行環境の脆弱性の修正を ikari が追い続けることになり、配布物も大きい。どちらも、設定画面のためには釣り合わない。
- **推奨は WinUI 3（C#、パッケージなし・自己完結。候補窓と同じ一式）。** 新しい部品と供給の経路が増えない。画面は OS の標準の部品で、文字を文字として出す。規則が届く。Rust との境界は、macOS の設定アプリと同じ `shell-ffi`。
- **WinUI 3 が実機の確認（§6）で通らなければ、Slint。** そのときは、ライセンスの選び方をユーザーに聞く。
- 本決定は、WinUI 3 の最小の画面を VM で確かめてから（§6）。スパイクの WebView2 と Slint の実装は、比べる基準として残してよい（main には入れない）。

### 2.3 どの方式でも守ること
- 設定画面は通信しない。通信の手段を使うコードを持たない（.NET の通信のライブラリは、自己完結の配布に含まれるが、呼ばない。規則と実機の記録で受ける）。
- 画面に出す文字（ユーザー辞書、学習の一覧、アプリの名前、モデルの名前、エンジンから来た理由の語）は、信用しない入力として、文字としてだけ出す。リンクにしない。
- 設定に、実行物のパスと通信の先を持たせない（P5）。モデルの選択は ID（`lm.model`）だけ。取得した URL は、記録として残すだけで、あとから自動で取り直すのに使わない。
- 高い権限では動かない（ADR 0067 §4.3）。エンジンとは設定の口だけで話す（ADR 0068 §4）。

## 3. 決定 2: 取得する部品 `ikari-data`

### 3.1 位置づけ
- **ikari の中で、ネットワークに出てよいのは `ikari-data` だけ。** 別の実行ファイルにし、通信の検査（ADR 0066 §6.2 の L1）の対象から、名前で外す。ファイアウォールの送信ブロックの規則は入れない。
- **起動するのは、利用者の操作だけ。** 設定画面のボタン、または利用者が手で打つコマンド。自動起動、定期の実行、常駐、起動のたびの確認は持たない。1 回の操作で 1 回起動し、1 つの取得をして終わる。
- 0.x と 1.0.0 の範囲: モデルの取得（プリセットと自由指定の URL）。作者が配る束（辞書、表）の取得と「更新を確認」は、束を配り始めるとき（ADR 0033）に足す。そのときも、確認はボタンを押したときだけ（NFR-17 の例外は広げない）。
- 高い権限では動かない。

### 3.2 何を送り、何を受けるか
- 送るのは、取得の要求（GET）だけ。行き先は、(a) アプリに埋めたプリセットの表の URL、(b) 利用者が入力した URL。
- **https だけ。** 転送も https だけで、回数に上限を置く。プリセットは配布元が別のホストへ転送することがあるので、転送先のホストは縛らず、中身を sha256 で確かめる。
- 要求に、利用者や機械を見分けられるものを付けない（識別子、版より細かい情報、Cookie、問い合わせの文字列の追加）。取得のほかの通信（利用の統計、失敗の報告）をしない。
- 受けたものは、大きさの上限（ADR 0060 §4 のモデルの上限と同じ値を使う）と、締め切りの中でだけ受ける。超えたら捨てる。
- プリセットは、表の sha256 と合わなければ捨てる。自由指定は、sha256 を指定されたら照らし、無ければ警告を出して進む（ADR 0060 の決定のまま）。確認の画面でホストを出す（同）。

### 3.3 どこに書くか
- 書くのは、データの場所の `inbox/<名前>.partial/` だけ。全部そろってから、束の形（ADR 0058 §4）にして名前を替える。`dict/`、`models/`、設定、学習、ユーザー辞書には触れない。**取り込むのはエンジン**（検証、入れ替え。ADR 0058）で、モデルを読むのは檻の中の子（ADR 0072）。
- ファイルの名前は、表の名前か、Rust が決めた名前。URL や応答のヘッダから取らない。
- 取得しても、使うモデルは切り替えない（ADR 0060 §2）。
- 同じ利用者のプログラムが `ikari-data` を勝手に起動しても、できるのは inbox にファイルを置くことだけ（自分で置くのと同じ。P3）。

### 3.4 通信の実装
- **推奨: OS に付いている `curl` を、絶対パスで起動する**（Windows は system32 の `curl.exe`、macOS は `/usr/bin/curl`。場所は OS の API から決め、PATH から探さない）。
  - 理由: (1) TLS の実装と証明書の扱いを、ikari の依存に入れずに済む（供給の経路が増えない。修正は OS の更新で届く）。(2) 開発用の取得と、プロキシの手順（`docs/proxy-download.md`）が、すでに curl の動きを前提にしている。
  - 渡す引数は Rust が全部決める: https だけ（転送も）、転送の回数、大きさの上限、締め切り、出力先。**利用者の `~/.curlrc` は読ませない**（`-q`。利用者に書けるファイルが、出力先などを変えられるため）。
  - プロキシ: 環境変数（`https_proxy` など）は curl にそのまま効かせる。これは R5（製品は環境変数で挙動を変えない）の、文書に書いた例外にする（取得の部品だけ。プロキシの下の利用者のため。#249）。プロキシの ID とパスワードを、ikari は保存しない。
- 別の案: Rust の HTTP と TLS の crate を `ikari-data` に入れる。OS の curl の版の差に左右されないが、TLS の実装が ikari の依存になり、その脆弱性の修正を ikari が配ることになる（自動の更新を持たないので遅れる）。

### 3.5 macOS
- 置き場所は `ikari.app/Contents/Helpers/`。App Sandbox に入れ、通信（クライアント）と、データの場所の例外だけを付ける（ADR 0033 §6 の案のまま）。「通信の権限を持つのは `ikari-data` だけ」を、ビルドの検査に足す。
- 設定アプリは通信しない（ADR 0005 §6.2 のまま）。ボタンで `ikari-data` を起こし、進み具合を表示する。

## 4. 検討した案

- **WebView2（Evergreen）にし、通信は Microsoft の部品のものとして約束の外に置く**: OS に入っている部品なので「OS の通信」と見る考え方はある。ただし、その部品を動かすのは ikari で、ikari を入れなければ起きない通信になる。ADR 0066 §6.1 の 3 つ目（同梱または起動する他社の部品の通信は数える）と合わない。ユーザーが ADR 0066 の Q3 で「数えない」を選ぶなら、この案は残る。その場合でも、画面の攻撃面（§2.1 の 3 行目）は残る。
- **設定画面を作らず、設定ファイルを手で書いてもらう**: 攻撃面は最小。ADR 0040 §2.3（設定画面を 1.0.0 に含める。macOS と同じレベル）に反する。
- **設定画面が自分で取得する**: 部品が 1 つ減る。画面のプロセスが通信の手段を持つことになり、「通信してよいのは 1 つだけ」を検査で言えなくなる。採らない。
- **エンジンが取得する**: NFR-17 に反する。採らない。

## 5. 結果

- ADR 0040 §2.5 の比較に、セキュリティの軸（§2.1）が足され、WebView2 が外れる。候補窓と設定画面が同じ一式（WinUI 3）になれば、Windows の画面の言語は C# の 1 つにそろう。
- `ikari-data` の範囲と守りが決まり、ADR 0060 の段階 5（URL からの取得）と #248 の前提になる。
- 実装の issue（承認のあとに切る）: WinUI 3 の設定画面の最小の確認（§6）、`ikari-data` の契約（引数、終了コード、進み具合の出し方）、通信の権限の検査（macOS）と通信の手段の検査（Windows）。
- 失うもの: WebView2 で得られたはずの、CSS の自由な見た目。スパイクで作った WebView2 の実装は、使わない見込み。

## 6. 推測と、確かめること（VM）

- WinUI 3 と .NET の実行時が、自分から通信しないこと（送信を記録して、設定画面と候補窓を動かす。ADR 0066 §6.2 の L3）。
- WinUI 3 の最小の設定画面（スパイクと同じ 6 種類の設定）で、画面の入力欄に ikari 自身で日本語を打てること、ダークとライト、高 DPI、キーボードだけの操作、読み上げ。
- 自己完結の一式を、候補窓と設定画面で共有できること（同じフォルダの一式を 2 つの exe が使う形）。できなければ、配る大きさが増える。
- Windows 11 に付いている `curl.exe` が、要る引数（https だけに絞る、大きさの上限、`-q`）を受けること。受けない版があれば、§3.4 の別の案に下がる。
- WebView2 の Fixed Version に規則をかけたとき、手元の内容だけなら動くか（採らない見込みなので、確かめなくてよい）。

## 7. ユーザーに聞くこと

- **Q1. 設定画面の方式。** WebView2 は採らず、WinUI 3（候補窓と同じ一式）を第一候補にして VM で確かめる。通らなければ Slint。**推奨: WinUI 3。** 理由は、止められない通信が無いこと、規則が届くこと、新しい部品が増えないこと。
- **Q2. 取得の通信は、OS に付いている curl を起動する（§3.4）。** 代わりの案は、Rust の HTTP・TLS の crate を `ikari-data` に入れる。**推奨: OS の curl。** TLS の実装を ikari の依存にしないため。
- **Q3. 1.0.0 までの取得の範囲は、モデルだけ。「更新を確認」のボタンは、作者が束を配り始めるときに足す（§3.1）。** #248 の「自動の確認の有無」は、持たない、とする。**推奨: この範囲。**
