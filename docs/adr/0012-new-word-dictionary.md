## 0. 現状の把握（確かめた事実）

### 0.1 ユーザーの報告と要望（2026-10-14）
- 「ぬまる」で「沼る」に変換されない。新語の辞書を入れたい。
- 「くばねてぃす」で Kubernetes、「りなっくす」で Linux、「らいふれい」で Liferay のように、IT の語を英字で出したい。ユーザー辞書に全部を登録するのは面倒。
- 今すぐの回避はユーザー辞書（FR-11）で足りる。`ikari user-dict add ぬまる 沼る 動詞:五段-ラ行` で 沼る／沼った／沼ってる／沼りそう／沼らない がすべて1位になる（リードが確認）。

### 0.2 今の辞書
- SudachiDict 20260723 の small + core（Core）。1,567,571 エントリ、`system.dict` 105.4MB。chiVe 1.3 mc90（SudachiDict 20240109-core で学習）の語彙を `lemma_rank` に使う（ADR 0002 §22）。
- 公式の最新は v20260723.1（2026-09-24。中身の差は確かめていない）。リリースは 2025-11、2026-01、04、07、09 と続いている。
- **Core にない新語は、同じ版の Full（notcore_lex.csv）にある。** 沼る（五段-ラ行の全17行。沼っ、沼ら、沼り、沼ろう…）、メロい（形容詞の全12行）、チルい、陰キャ、陽キャ、ぴえん、親ガチャ、推し変、同担、Liferay、GitHub、JavaScript、TypeScript、MySQL、Kotlin、JSON、YAML、nginx。
- notcore は 1,251,396 行。**96% が固有名詞**（1,198,877 行）。普通名詞 47,245、動詞 275 行（約17語）、形容詞 35 行、感動詞 24。固有名詞を除くと 52,519 行。
- 新語は chiVe の語彙にない（沼る、メロい、チルい、陰キャ、黒歴史、ぴえん、親ガチャ）。`lemma_rank` は「語彙にない」を最下位の扱いにして **+5,227** を足す。chiVe は 2024 年の Core で分かち書きした語彙なので、**新しい語は構造的に「まれな語」として扱われる。**

### 0.5 Core にあるのに出ない「最近の語」
- 推し活（コスト 17000）、蛙化現象（17504）、サブスク（15000）、タイパ、ガクチカ（10000）、自撮り は Core にあるが、1位にならない（お死活、変えるか減少、サブ空く、タイ派、額地下、地鳥）。コストが高く、chiVe にもない（`lemma_rank`）。**新語の問題の半分は「辞書にない」ではなく「コスト」**で、辞書を足しても直らない（§10-3）。

### 0.6 IT の英字表記の今
- Sudachi にも英字の行がある（small 5,765、core 38,521、notcore 67,082 行）。ただし大半は一般の英単語や社名（about、Business、home run、setlist、Hewlett-Packard Japan）。**英字を一律に上げると、ビジネス → Business のように崩れる。**
- Sudachi の英字の行の読みには揺れと誤りがある: GIT=ジーアイティー、Swift=スウィフト、Azure=アズレ（notcore）、RUST=ラスト、golang=ゴー。小文字の表記（git、nginx、react）は `ascii_lower`（+10000）で後ろに回る。
- 英字とカタカナの両方があるとき、今はカタカナが1位（りなっくす → リナックス 7411、Linux 9480。差は `ascii_other` の +3000 から来る）。プロファイル「IT」でも順は変わらない（両方に加点される）。
- Full をそのまま入れると、ascii の行の雑音が上位に来ることがある（くばねてぃす → 1位「くばねTISS」。TISS/ティス は notcore の固有名詞）。

## 2. 追加の層の設計

### 2.1 置き場所と読み込み
- `data/build/dict/extension.dict`（インストール後は `~/Library/Application Support/ikari-ime/dict/extension.dict`）。形式は system.dict v2 と同じで、ヘッダの `kind` に新しい値（拡張）を使う。grammar_id は Core の grammar.bin と同じ値にする（`DictionarySet::push` が違えば拒否する。今の仕組みのまま守られる）。
- `stack` の読み込みで、slot 0 = システム辞書、slot 1 = 追加の層、slot 2 = IT の語彙集、slot 3 = ユーザー辞書、の順に `DictionarySet` に入れる。ファイルがなければ今と同じ（追加の層なし）で動く。既定で有効（B20-4）、設定で切れる。

### 2.2 変換にだけ使う（文脈の解析に使わない）
- **判断の根拠（§3 の (a)）**: Full をそのまま system.dict に入れると、homophones-ext の dev が 778 → 776、test が 198 → 197 に下がった。崩れた4件はすべて、**左文脈の語が Full の固有名詞1語になり（コインロッカー、地場産業、少年マンガ、品質管理）、話題と文書内キャッシュの手がかりが消えた**もの（硬貨 → 硬化、振興 → 進行、週刊 → 収監、工程 → 肯定）。chiVe は Core の分かち書きで学習しているので、その lemma にはベクトルがない。
- 追加の層の**表記の索引（surface_index）を空にする**。文脈の解析（`common_prefix_search_surface`）は全 slot を回すが、空の索引からは何も返らないので、**解析は Core のときと同じになる**。core のコードの変更は要らない。試作では、固有名詞を含めても含めなくても、文脈つきのセット（homophones-ext、context-compound）のケースごとの1位が Core と一致した（§3）。
- ベクトル: `DictionarySet::lemma` は slot 0 以外の lemma 番号を返さないので、追加の語には話題のベクトルが付かない（今の仕組みのまま）。
- 失うもの: 追加の語は、左文脈の中では1語として解析されない（沼る は 沼 + る などに分かれる）。確定後の再変換（ADR 0006）で 沼る を選び直すとき、読みの逆引きが Core の語で行われる。

### 2.3 grammar.bin を変えない
- Full をそのまま入れると grammar.bin も変わる（品詞の数は同じ 1,558 だが、代表の左右ID、`user_cost`（品詞ごとのコストの10パーセンタイル）、活用規則の支持数が変わる）。`user_cost` が変わると、**ユーザー辞書の語のコストまで変わる**（試作: 固有名詞で登録した Kubernetes が 3845 → 4948、名詞の 社内用 が 2183 → 2073）。
- 追加の層は Core の grammar.bin を使い、品詞の統計と活用規則の導出に**数えない**。試作では grammar.bin が Core とバイト単位で一致した。
- Core の品詞表にない品詞の行は捨てる（数をレポートに出す。notcore 20260723 では 0 件だった）。
- 左右ID は Sudachi の行のものをそのまま使う（同じ matrix.def）。活用形も Sudachi が全形を行として持っているので、展開は要らない。

### 2.4 重複と除外
- system.dict と (読み, 表記, 左ID, 右ID, 品詞) が同じ行は追加の層に入れない（Core の行を正とする）。
- 固定の規則（`ExclusionRule`。波ダッシュ、飾りの記号、和語の途中のハイフン）とポリシーの述語は、system.dict と同じに当てる。

### 2.5 コスト（改訂。前の版の「出典の値 0」を直す）
- 述語はそのまま当てる（`ascii_lower`、`ascii_other`、`katakana_variant`、`proper_noun`、`variant_surface`、異字同訓の表…）。
- **`lemma_rank` は、chiVe の語彙にない追加の語には当てない。** 新しい語は chiVe（2024 年の Core で分かち書き）が知らないので、「新しい」と「まれ」を区別できない。当てると 沼る、メロい が負ける（前の版 §5.3）。
- **前の版の試作（出典の値 0）には見落としがあった。** 頻度上位 3000 語を単独で変換すると、2語の1位が崩れた: たいせい → タイ製（体制 は2位）、たいふう → タイ風（台風 は2位）。Core では「タイ＋製」の2語の経路（7164）だったものが、notcore に1語の普通名詞 タイ製（コスト 6940）があり、`lemma_rank` を外したので 体制（5712）より安くなった（5330）。
- 一律の出典の値（全行に +X）では直らない:

  | 出典の値 | 頻度上位 3000 語の1位の崩れ | new-words の新語（19件） | 既存のセット |
  | --- | --- | --- | --- |
  | 0 | 2（タイ製、タイ風） | 18 | adverbs +1（効果測定） |
  | 500 | 0 | 17（同担 → どう端） | 効果測定 の改善が消える |
  | 1000〜3000 | 0 | 17〜14（チルい、親ガチャ も落ちる） | **adverbs −1**（もういちど → もう一℃。追加の層の1語 もう一度 が ADR 0008 の「覆う名詞」になり、もう＋一度 が重くなったうえで、追加の語そのものが値の分だけ負ける） |

- **採る形: `extension_peer`**（新しい述語、値 +3000）。追加の層の行で、**同じ読みの Core の行の lemma のどれかが chiVe の頻度3万位以内**のときだけ足す。「新しい語が、同じ読みのよく使われる語を押しのけない」ことを直接表す。試作（3万位、+3000）では、頻度上位 3000 語の1位の崩れ 0、自然な入力 120 件の崩れ 0、新語 18/19、既存のセットはケースごとに Core と同じ（効果測定 の改善だけ）。

  | 順位の上限、値 | 頻度上位 3000 語の1位の崩れ | 1ページ目に追加の語が入る入力 | 新語（19件） |
  | --- | --- | --- | --- |
  | 3万位、+2000 | 0 | 22 | 18 |
  | **3万位、+3000** | 0 | 18 | 18 |

### 3.3 推奨と理由（分解を検討する前の版。3.4 で改訂）
- **推奨は (c')。** 固有名詞の 120 万行は、得をする入力が少ない（30 件のうち 1位が 3〜7 件増える）のに対し、毎日打つ語の候補の一覧に知らない名前が入る（(b) で 3000 語のうち 1,190、(b') でも 117）。雑音は打つ語の数に比例して毎日見えるが、得は「その名前を打つ日」だけ。ikari の「こまめに確定する」使い方では、1ページ目の雑音の方が効く。
- 固有名詞の得の大半は別の手段で取れる: IT の製品名は語彙集（§4）、よく使う名前はユーザー辞書、たまに使う名前は確定後の再変換。
- (a) は採らない: 文脈の手がかりが崩れ（既存のセットで −3）、ユーザー辞書の語の重さが変わり、新語も (c) より出ない。
- 固有名詞を入れたい場合は (b') が現実的な形（1位の崩れは 3000 語で 0、自然な入力で 1）。ただし 東乃宇宙 のような崩れと、1ページ目の雑音、約 95 MB と起動直後の 130 ms は残る。入れるなら「作品名だけ」「人名だけ」のように品詞（固有名詞の下位分類）で絞る形を、別に測ることになる（§11-2）。

## 4. IT の語（語彙集）

### 4.1 出どころと作り方（B20-5）
- どの辞書にも Kubernetes がない。Sudachi の英字の行は読みの誤りがあり、一般語と混ざっている。jawiki には IT の語が多いが、読みの誤り（YAML=やめる）と CC BY-SA の元データの問題がある。
- **手で作る語彙集**にする。Claude が下書きし（`core/assets/packs/it.tsv`。言語、フレームワーク、データベース、クラウド、コンテナ、監視、OS、開発ツール、AI、業務のサービス、Liferay まわり。323 行、309 語）、ユーザーが確認して足し削りする（docs/tasks.md A2-13、eval/sets/REVIEW.md の語彙集の節）。下書きは Claude の知識だけで書き、外部の辞書の行は写していない。
- spec の「辞書のデータ構造」にある「分野別の語彙パック」に当たる。

### 4.2 形式
- タブ区切りの6列: 読み、英字の表記、品詞、形、分野、注記。1行目は `#ikari-pack	id=it	schema=1	name=…`。行頭が `#` の行は注釈（除外を推奨する語もこの形で残す）。
- 品詞はユーザー辞書の簡略品詞（固有名詞、組織、名詞）。
- **カタカナの表記は書かない。読みから作る**（ひらがなをカタカナにしたもの）。B20-3 の「ユーザーが打った読みのとおりの表記」をそのまま表し、カタカナの綴りの揺れ（クバネティス／クーバネティス）を語彙集で選ばずに済む。読みが複数ある語は行を分ける（くばねてぃす、くーばねてぃす、くーべねてぃす、くばねてす）。
- 形:
  - `kana`（243 行）: 読みのカタカナを1位、英字を2位。
  - `latin`（80 行）: 英字だけ。略語（AWS、API、SQL）と、文字の名前を読みに含む語（まいえすきゅーえる → MySQL、のーどじぇいえす → Node.js、えんじんえっくす → nginx）。マイエスキューエル のようなカタカナは誰も書かないため。この分け方はユーザーの確認事項（§11-3）。
    - **B32 で改めた点（[ADR 0020](0020-english-spelling-first-candidate.md) §12、2026-10-16 ユーザー決定）**: 形 `latin` の語もカタカナを1位にする（まいえすきゅーえる → マイエスキューエル、MySQL は2位）。語彙集はカタカナの項目を作らないままで、`CompositeRanker` の最後の段が読みのカタカナの候補を足して1位にする。1回英字を選べば英字が1位に戻る（ADR 0020 E4）。上の「形 `latin` は英字1位」「カタカナは出さない」は、この点で置き換わった。
- 読みに対応しない文字を足す表記は入れない（ぽすぐれ → PostgreSQL は入れない。読み ぽすとぐれす → Postgres は入れる）。基本原則「入力を正とする」。

### 4.3 順位の付け方（B20-3）
- 語彙集の項目は、ユーザー辞書と同じ作り方（`UserDictionary::build` の品詞の代表左右ID と `user_cost`）で `InMemoryDictionary` にする。形 `kana` の行からは2つの項目を作る:
  1. 読みのカタカナ: コスト `user_cost`
  2. 英字: コスト `user_cost` ＋ **`pack_latin_offset`（100）**
- 形 `latin` の行は英字の項目だけ（コスト `user_cost`）。
- `user_cost` は品詞のコストの10パーセンタイルで、同じ読みの Core の候補より十分に安い（りなっくす: リナックス 3845、Linux 3945。Core の リナックス は 7411、Linux は 9480）。Core に同じ表記があれば（Linux、Docker）、`DictionarySet` の重複の除去で安い方（語彙集）が残る。
- **差（100）の決め方**: 0 より大きく（カタカナが1位）、**1回英字を選んだときの学習の加点より小さく**する。今の学習（ADR 0002 §8.4）では、文脈の特徴量が一致しないときに効くのは `Unconditional`（重み 0.2）だけで、1回選ぶと 0.2 × 1/(1+1) × 3000 = **300**。試作では、差 100 と 200 は1回選ぶと英字が1位になり、300 と 500 はならなかった。文脈が一致すれば加点はもっと大きい。B23 で文脈がないときの重みを上げても、加点は増える向きなので崩れない。
- 学習が効く範囲（試作で確かめた）: 単独で りなっくす → Linux を1回選ぶと、次から単独の りなっくす は Linux が1位（文脈を変えても1位）。文の中（りなっくすのかーねる）で Linuxのカーネル を選ぶと、単独でも別の文（りなっくすのせってい）でも Linux が1位。ただし**単独で選んだ学習は、文の中の同じ語には効かない**（りなっくすのせってい は リナックスの設定 のまま）。これは語彙集に限らず今の学習の性質で、Core の語でも同じだった（§10-7）。
- 文脈の解析: 語彙集の項目は表記の索引に入る（ユーザー辞書と同じ）。左文脈の「Kubernetesの」を1語として読める。
- ユーザー辞書の語として見せない（設定アプリの一覧に出さない。エクスポートの対象にしない）。

- **実装で変えた点（2026-10-15、B20 の実装）**: 英字のコストは「語彙集のカタカナの user_cost + 100」ではなく、「カタカナの文頭から文末までの合計（語彙集とシステム辞書の安い方。コスト、ペナルティ、BOS と EOS への連接の和）+ 100」にした。Core に安いカタカナの語があると（パール 2262 に対し Perl 3945）、+100 では1回英字を選んでも1位にならなかったため。定数は `PACK_LATIN_OFFSET = 100`（core/src/user/dictionary/pack.rs）。
- **除外した語（ユーザー決定 2026-10-15）**: なくすと（Nuxt）、すべると（Svelte）、きばな（Kibana）、めいぶん（Maven）、へるむ（Helm）、らむだ（Lambda）、じら（Jira）、とれろ（Trello）。日常の語の1位を奪うため。やめる・での も除外（2026-10-14）。

## 7. 検討した案

- **案A（当初の採用。§11.3 の最終決定で「Full に置き換え＋分解＋新語の規則＋d2s」に置き換わった）**: Full のうち固有名詞を除いた差分を、変換にだけ使う追加の層として足す（`extension_peer` つき）。IT は手で作る語彙集（カタカナ1位・英字2位）。
- **案B: system.dict を Full に置き換える（§3 の (a)）**: 文脈の解析が変わって既存のセットで3件崩れ、守りの文脈の3件も崩れた。ユーザー辞書の語のコストが動く。新語も (c) より出ない。system.dict が 105 → 225 MB。採らない。
- **案B2: 固有名詞を含めて追加の層に入れる（§3 の (b)、(b')）**: §3.3。推奨しないが、ユーザーの判断（§11-2）。
- **案C: jawiki-kana-kanji-dict を固有名詞の層として足す**: 沼る、メロい の要望に効かない（名詞だけ）。46% は Full と重なり、残りの多くはまれな固有名詞。読みの誤り（YAML=やめる、GIT=ひっと）が「入力を正とする」に反する。元データは CC BY-SA で、生成物の MIT は作者の解釈。取得元が増える。採らない。
- **案D: dic-nico-intersection-pixiv をスラングの層として足す**: 2024-04 から更新がなく、最近の語がない。品詞がすべて固有名詞で、動詞も活用しない。採らない。
- **案E: Mozc UT**: 名詞だけで、ID が Mozc の品詞。採らない。
- **案F: skk-dev/dict、mecab-ipadic-NEologd**: SKK は GPL で新語がない。NEologd は 2020 年で止まっている。採らない。
- **案G: 新語は全部ユーザー辞書に任せる**: 「全部を登録するのは面倒」という要望に応えない。
- **案H: 英字の表記を一律に上げる（`ascii_other` を下げる）**: Business、home run、about などの一般の英単語が上がる。B20-3 とも合わない。採らない。
- **案I: 追加語のコストを「基準 − α×長さ + 出典」にする（参考の報告の案）**: 長さの項の根拠が試作で見つからなかった。採らない。
- **案J: 追加の行を system.dict に入れ、エントリに「解析に使わない」の印を持たせる（形式 v3）**: 形式の版を上げ、system.dict と vectors.bin を作り直すことになる。採らない。
- **案K: 追加の層の全行に一律の出典の値（`source_extension`）を足す（前の版）**: §2.5 のとおり、どの値でも 体制／同担／もう一度 のどれかが崩れる。`extension_peer` に置き換える。
- **案L: 英字を1位にする（R2）、カタカナを語彙集に書く（R6）**: §4.4。

## 8. 結果（入れたら変わること）
- 得るもの: 沼る、メロい などの新しい用言とスラングの名詞が、ユーザー辞書なしで出る。IT の語は、打った読みのカタカナが1位、英字が2位に出て、1回英字を選べば英字が1位になる。文脈の解析と既存の評価は Core のときと変わらない。
- 失うもの、増えるもの: ファイルが1つ増える（extension.dict は約 3.3 MB）。追加の語は左文脈の中では1語として解析されない（§2.2）。ポリシーに述語が1つ増える（`extension_peer`）。日常の語と読みが重なる IT の語は、2位が英字になる（らすと → Rust）。今 Docker、Ubuntu のように英字が1位の語は、カタカナが1位になる（B20-3 のとおり）。

## 9. 実装の進め方（承認後。1タスク1ブランチ）
1. **契約コミット**: dict-format に `DICT_KIND_EXTENSION` と「表記の索引を作らない」指定を足す。`DictionarySet` の slot の並び（system、extension、pack、user）を定数にする。ユーザー辞書の slot を 1 と決め打ちしている箇所を洗い出す。語彙集の形式（§4.2）の型と、`pack_latin_offset` の定数。
2. **レーン1（dict-builder）**: `--extension-lex` と既存の grammar.bin を受けて extension.dict を作るサブコマンド。固有名詞の除外、重複の除去、品詞の照合、`extension_peer`、未知の lemma の `lemma_rank` の扱い、レポート。fetch-data.sh と build-dict.sh と install-data.sh。
3. **レーン2（core / stack）**: 追加の層と語彙集の読み込み、設定（どちらも既定で有効。B20-4）。語彙集はユーザー辞書の実装（`UserDictionary::build` と同じ作り方）を使い、形 `kana` の行からカタカナと英字の2項目を作る。テスト: 語彙集の全行で「カタカナ1位・英字2位（latin は英字1位）」、1回英字を選ぶと英字が1位、日常の語（頻度上位の語）の1位が変わらない。
4. **レーン3（eval）**: `ikari-eval` が語彙集（とユーザー辞書）を読めるようにする（今は辞書を直接受け取り、ユーザー辞書を読まない。§10-6）。snapshot に new-words.tsv と、頻度上位の語の1位の変化の検査を足す。
5. **データ**: `core/assets/packs/it.tsv` はユーザーの確認（A2-13）が済んだものを使う。
6. **統合**: `scripts/check.sh`、snapshot（全セットで1位が悪化しないこと）、`new-words.tsv` の dev で `extension_peer` の値を確かめる。A1 に実機の確認（ぬまる、くばねてぃす → クバネティス、Kubernetes、Kubernetes を1回選んだあと）を足す。
7. **分解（§12。どの案でも）**: `ikari-dict-builder vectors` に `--lex`（分割の列）を足し、chiVe にない lemma に部分の平均のベクトルを付ける。(c') を選ぶときは、追加の層の lemma にもベクトルを引けるようにする（`DictionarySet::lemma` が slot 1 の lemma 番号も返す。vectors.bin を追加の層の分も持つか、追加の層用の vectors を別に作る）。
8. **(a) を選ぶとき**: 1〜3 のうち追加の層の部分は要らない（notcore を system.dict の入力に足すだけ）。代わりに、dict-builder に「notcore の行」の印を持たせ、新語の規則（固有名詞以外に `lemma_rank` を当てない、`extension_peer`）と、品詞の統計を Core の行だけで数える（§13 の U1）を入れる。

## 10. 懸念点と、ついでに気づいたこと
1. **ぬまる の1位は「ぬ○」だった**（Core でも Full でも）。助動詞「ぬ」の連体形 + 「○」（読み まる、普通名詞、コスト 4095）。追加の層で 沼る が勝つので今回は目立たないが、記号の表記の普通名詞が漢字の語に勝つ構造は残る。別のタスクで調べる。
2. **`ikari user-dict check` が今の Core の辞書で失敗する**（「形容詞: 終止形から 未然形-一般 を導く活用規則がありません」）。本件とは別に調べる。
3. **Core にあるのに出ない最近の語**（推し活、蛙化現象、サブスク、タイパ、ガクチカ、自撮り。§0.5）は、辞書を足しても直らない。別のタスクで dev を使って調べる。
4. `extension_peer` の順位の上限と値（3万位、+3000）は試作の値。実装のときに dev で確かめ直す。追加の語は ADR 0008 の「覆う名詞」として効くので、値を変えるときは adverbs.tsv を必ず見る（§2.5 の もう一℃）。
5. 追加の語の再変換（ADR 0006）と、学習（表記・読み・品詞の文字列で保存するので、追加の層を外しても壊れない）は、実装のときに確かめる。
6. **`ikari-eval` はユーザー辞書を読まない**（`eval/src/setup.rs` は辞書を直接受け取る）。今の snapshot はユーザー辞書の効果を見ていない。語彙集を入れる前に eval が読めるようにする（§9-4）。
7. **単独で選んだ学習が、文の中の同じ語に効かない**（語彙集に限らない。Core の りなっくす で Linux を単独で3回選んでも、りなっくすのせってい は リナックスの設定 のまま、得点も変わらない）。文の中で選んだ学習は単独にも効く。学習の効き方は B23（ADR 0013）の担当に知らせる。語彙集の差（100）は、この性質が直っても崩れない（加点が増える向き）。
8. **差（100）は学習の重みに依存する**。学習の `Unconditional` の重み（0.2）や `base_bonus`（3000）を下げる変更をするときは、「1回英字を選べば英字が1位」のテスト（§9-3）で気づけるようにする。
9. 試作の new-words.tsv の期待と、語彙集は下書き（REVIEW.md の確認待ち）。

## 11. ユーザーの判断が要る点

1. **B20-1・2（Full と固有名詞）**: §3.4、§3.5 の検証をもとに、次のどれにするか（どれでも分解は入れる）。
   - **(a)+分解＋新語の規則＋d2s（推奨）**: Full を system.dict にし、同じ読みに固有名詞以外の語がある固有名詞と、読みの短い固有名詞を外す（ユーザーの案を広げたもの）。大谷翔平、鬼滅の刃 などは入る（1位ではなく2〜5位。1回選べば学習で上がる）。よく打つ語の 0.4% で1ページ目に知らない名前、LM ありで1位の崩れ 0。Ado、YOASOBI など約 2.3 万組は外れる
   - **(c')+分解**: 固有名詞を入れない。雑音 0
   - ユーザーの言葉どおりの d1（普通名詞だけを見る）でもよいか（d2s より、よく打つ語の雑音が 13 → 40 語）
2. 固有名詞の重さ: Core の固有名詞と同じ（推奨。大谷翔平 は3位）か、軽くする（大谷翔平、鬼滅の刃、藤井聡太 が1位になるが、ひがしのそら → 東乃宇宙、さよならのかわりに → サヨナラのかわりに の1位の崩れが LM ありでも出る）か。
3. **語彙集の形 `latin`**: 略語（AWS、API、SQL）と、文字の名前を読みに含む語（まいえすきゅーえる → MySQL、のーどじぇいえす → Node.js、えんじんえっくす → nginx）は、カタカナを出さずに英字を1位にしてよいか。B20-3 の「打った読みのとおり」の例外になる（エーダブリューエス、マイエスキューエル を1位にしない）。
4. **語彙集の中身の確認**（A2-13）: 要らない語、足りない語（仕事で使う製品名）、読み、綴り。とくに日常の語と読みが重なる語（らすと → Rust、かーる → curl、すらっく → Slack、ずーむ → Zoom、のーど → Node）を入れるか。除外を推奨する2行（やめる → YAML、での → Deno）を外してよいか。
5. B20-4 の「最初から有効」は、追加の層と IT の語彙集の両方の意味でよいか（この ADR は両方を既定で有効にしている）。
6. **new-words.tsv の期待の確認**（A2-12。IT の期待を B20-3 に合わせてカタカナにした）。
7. **ユーザー辞書の語のコスト**（§13）: 品詞の統計を Core の行だけで数える案（U1）でよいか。(a) を選ぶときに要る（(c') では今のままで変わらない）。
8. **分解の範囲**（§12）: 分割のない新語（陰キャ、沼る、推し変）には付かない。これでよいか（付けるなら別の手段が要る）。

### 11.2 ユーザーの問い「新語は AI で文脈を解析できないということか」への答え（2026-10-14）
- ikari の文脈の使い方は3つある。(1) zenz（LM）: 左文脈を**文字列のまま**読むので、どの案でも新語を含む文脈を使える。(2) 話題（chiVe のベクトル）と学習の特徴量: 左文脈を辞書で語に分けて使う。(3) 文書内キャッシュ: 確定した語を覚える。
- 追加の層の案（(b')、(c')）では、(2) の左文脈の解析に追加の語を使わない。沼った と打ったあとの文脈は 沼＋っ＋た のように Core の語で分けて読まれる。zenz は文字列で読むので影響しない。
- (a) では (2) にも Full の語を使うが、Full の語の多く（陰キャ、沼る など分割のない新語を含む）には chiVe のベクトルがない。分解（§12）で、分割のある長い語（コインロッカー、少年マンガ、品質管理）にはベクトルが付く。分割のない新語は、どの案でもベクトルを持たない（話題の手がかりにはならないが、zenz は使う）。
- 測った結果では、文脈つきの評価（homophones-ext、context-compound）は、(c')+分解 も (a)+分解 も Core より良いか同じだった（§3.4.1）。

### 11.1 ユーザーの回答（2026-10-14）
- §11-3（略語と、文字の名前を読みに含む語は英字を1位。形 `latin`）: はい
- §11-4（語彙集の中身）: はい。らすと → Rust、かーる → curl、すらっく → Slack は残す（2位に英字）。やめる と での は除外する
- §11-5（最初から有効）: はい。追加の層と語彙集の両方を既定で有効にする
- §11-1・2（追加の層の範囲。(a)、(b)、(b')、(c')）: 未決定。ユーザーの問い「新語は AI で文脈を解析できないということか」に答えたうえで決める
- 語彙集（A2-13）と new-words.tsv（A2-12）の中身の確認は、あとでユーザーが行う

## 12. chiVe にない語のベクトルを、Sudachi の分割から作る（設計。2026-10-14 のユーザー決定「分解してベクトルを作る作戦」）

### 12.1 問題
- 話題（TopicRanker）と学習の Topic の特徴量は、chiVe（SudachiDict 2024 年の Core で分かち書きして学習）のベクトルを lemma ごとに引く。Core にない長い語（コインロッカー、地場産業、少年マンガ、品質管理）には chiVe のベクトルがない。
- 左文脈の側: Full で左文脈を解析すると、これらが1語になり、話題の手がかりが消える（§2.2 の4件の崩れ）。
- 候補の側: 1語の項目にベクトルがないと、Core の分割の経路（黒＋歴史）が持っていた話題の加点を失う。chiVe にない語に `lemma_rank` を当てない規則（§2.5）と組み合わせたとき、文脈があると 黒歴史 → クロ歴史、品質管理 → ひんしつ管理、神対応 → 加味対応、地場産業 → 地場三行 に崩れた（文脈つきの複合語 16 件で 13 → 8。分解で 12 に戻る。[レポート](../../eval/reports/phase3-full-dictionary.md) §3）。

### 12.2 作り方
- `vectors.bin` を作るとき（`ikari-dict-builder vectors`）、chiVe に完全一致しない lemma について、Sudachi の lex.csv の分割の列をたどって部分の lemma を求め、**部分の chiVe ベクトル（単位ベクトル）の平均を正規化して**その lemma のベクトルにする（量子化は今と同じ）。
- 分割の列: B 単位（16 列目）、なければ A 単位（15 列目）。値は「small_lex、core_lex、notcore_lex をこの順に連結したときの 0 始まりの行番号」を `/` で区切ったもの（例: Full の コインロッカー の行の `199094/265396` は コイン と ロッカー の行）。`U` で始まる値（ユーザー辞書の参照）は使わない。
- 部分の lemma は、参照先の行の正規化表記（12 列目）。部分が chiVe にないときは、その部分の A 分割を1段たどる（深さ 2 まで）。**部分が1つでも chiVe にない語には付けない**（一部の部分だけの平均は、語の意味から外れやすい）。
- 分割を持たない語（陰キャ、推し変、沼る、メロい。Sudachi では1単位）には付かない。これらは今と同じくベクトルなし。
- 入力: `vectors` サブコマンドに、辞書を作ったときと同じ `--lex` を渡す（分割の列を読むため）。辞書の形式（system.dict v2、vectors.bin）は変えない。lemma 番号ごとに行を持つ今の vectors.bin の形のまま、行が増えるだけ。

### 12.3 試作の結果（`ikari-dict-builder vectors` の写しを改造。§5.1）
| 辞書 | ベクトルを持つ lemma | vectors.bin |
| --- | --- | --- |
| Core（今） | 24.6%（214,229） | 67 MB |
| Core ＋ 分解 | 52.1%（453,326） | 139 MB |
| Full | 13.0%（242,818） | 80 MB |
| Full ＋ 分解 | 58.4%（1,089,259） | 334 MB |

- 分解は Core の語にも効く（Core の 239,097 lemma に付く）。Core ＋ 分解 だけで ext dev が 778 → 780（答案用紙に＋かいとう → 解答、長さを＋はかる → 測る）。悪化は 0。
- メモリ（ext のセット全体を流したときの最大 RSS）はほぼ変わらない（Full 244 → 245 MB）。vectors.bin は mmap で、触った行だけが載るため。
- 追加の層（(b')、(c')）で候補の側に分解のベクトルを使うには、追加の層の lemma にもベクトルを引けるようにする必要がある（今は `DictionarySet::lemma` が slot 0 以外の lemma 番号を返さない。§2.2）。試作は1つのファイルで行ったので、この変更をしたときの値になっている。(a) では system.dict の lemma なので変更は要らない。

### 12.4 却下した作り方
- 部分の一部しか chiVe にないときも平均を付ける: 語の意味から外れやすい（ガチャ がなければ 親 だけのベクトルになる）。
- 文字の n-gram からベクトルを作る（fastText 風）: chiVe は語の単位のベクトルしか配っていない。学習し直しになる。
- 分割をたどらず、表記の部分一致で chiVe の語を探す: 読みの境界と合わない（コインロッカー → コイ＋ン…）。Sudachi の分割は辞書の作り手が付けたもので確か。

## 13. ユーザー辞書の語のコストを、辞書の版によらず決める

### 13.1 今の仕組みと問題
- ユーザー辞書の語のコストは、grammar.bin の品詞ごとの `user_cost`（その品詞の行のコストの 10 パーセンタイル）。動詞と形容詞は活用形ごとの品詞に展開され、それぞれの `user_cost` を使う。
- Full を system.dict にすると、固有名詞の品詞に 120 万行が加わり、`user_cost` が動く。試作: 固有名詞で登録した Kubernetes 3845 → 4948、名詞の 社内用 2183 → 2073、人名の 古後太郎 3858 → 3360。

### 13.2 案
| 案 | 内容 | 版によらないか | 副作用 |
| --- | --- | --- | --- |
| **U1（推奨）Core の行だけで数える** | `user_cost` と代表の左右ID を、Core（small と core）の行だけで数える。notcore の行は辞書には入れるが、品詞の統計に数えない | Core と Full の選び方にはよらない（試作で grammar.bin が Core とバイト単位で一致し、上の3語のコストが Core と同じになった）。Sudachi の版を上げたときは、Core の中の変化だけで動く | Full の品詞の分布とずれる（固有名詞の 10 パーセンタイルは Full の方が低い）。ユーザー辞書の語は今と同じ強さのままになるので、変換の結果は変わらない |
| U2 固定の表 | `core/assets/user_pos.tsv` に品詞ごとの値を書く | 版によらない | 動詞・形容詞は活用形ごとの品詞（数十）に値が要る。Sudachi がコストの尺度を変えたとき、手で直す |
| U3 今のまま | ― | Full にすると動く | 固有名詞で登録した語が +1,103 重くなる |

- U1 を推奨する。版を上げたときに `user_cost` がどれだけ動いたかを、辞書のビルドのレポート（`--policy-report`）に品詞ごとに出し、更新の手順（spec「辞書の更新」）の評価で確かめる。

## 14. (a) で左文脈の解析に Full を使う影響（分解以外）

- **解析が変わる文脈の量**: 既存の全評価セットと自然な入力の左文脈 1,548 文のうち **42 文（2.7%）** で解析が変わった。ほとんどは複合語が1語になるもの（ユーザー辞書、形態素解析、辞書登録、新聞記者、開発チーム、環境問題、少子化対策、基本的人権、地域医療、品質管理、コインロッカー）。逆に分かれるものが1件（手作業 → 手＋作業）。
- **英字の未知語**: 辞書にない英字の語が、Full の英字の固有名詞に分けられる（「ikari」→ i ＋ k ＋ ari。ari は人名）。Core では1つの未知語だった。直前の語の特徴量が ari になる。
- **話題**: 分解のベクトルがあれば、1語になった複合語は部分の平均を持つので手がかりは残る（§12。ext dev は Core より +3）。
- **学習の特徴量**（ADR 0002 §8.4、ADR 0013）: `Prev`（直前の語）、`PrevContent`、`Bag`（近くの内容語の集合）、`Topic`（クラスタ）は、左文脈の解析の語から作る。解析が変わる 2.7% の文脈では、**切り替える前に記録した学習の特徴量と一致しなくなる**（例: 「ユーザー辞書に」の直前の語が 辞書 → ユーザー辞書）。学習の記録は表記と読みと特徴量の文字列で保存されるので壊れはしないが、その文脈では文脈つきの学習が効かず、ADR 0013 の back-off（文脈の記録がないときは文脈なしの重み 1.0）に落ちる。切り替えたあとに選び直せば、新しい特徴量で記録される。利用者は作者1人で、学習の量はまだ少ないので、影響は小さいと見る。
- **性能、起動、メモリ**: §3.4.1 の表（warm の p99 は変わらず、起動直後の最初の変換が約 120〜180 ms 遅い）。
- **ユーザー辞書の語のコスト**: §13（U1 で解消）。
- **文節の区切り（segments.tsv）**: 変わらなかった（144 → 145 は 効果測定 が1語になった分）。再変換の読みの推定は測っていない（実装のときに `ikari-eval reading` で確かめる）。

### 11.3 ユーザーの最終決定（2026-10-14）。実装は次の指示から（週のリミットが近いため、今回は意図の記録のみ）→ 2026-10-15 に実装済み
1. **方針: Full に置き換え＋分解＋新語の規則＋d2s**（§3.4、§3.5）
2. 固有名詞の重さは Core の固有名詞と同じにする（大谷翔平は3位、選べば学習で上がる）
3. Ado、YOASOBI など約 2.3 万組が外れてもよい。理由: 固有名詞はなくてもそこまで困らない。ふつうの語を打つときに名前が出てくるほうがストレス。例に出る名前は英字で、ユーザーは英字で書こうとするだろうから、候補に出なくて困ることは少ない
4. ユーザー辞書の語のコストは Core の行だけで数える（U1）。分割のない新語（沼る、陰キャ）にベクトルが付かないのはそのまま
- B20-3〜5 と §11-3〜5 は §11.1 のとおり。語彙集（A2-13）と new-words.tsv（A2-12）の確認はユーザーがあとで行う
- 実装は 1 タスク 1 ブランチで、§9 の進め方（辞書のビルド、分解のベクトル、新語の規則、d2s、U1、語彙集、eval のユーザー辞書対応）。完了後に辞書の作り直しとインストール
