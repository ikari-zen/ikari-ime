# ADR 0072: LM の檻を段に分ける。配る前に要る段、自由指定のモデルに要る段、エンジンから llama.cpp を外すこと、自己診断の守り

- 状態: 承認（2026-11-16 ユーザー決定。質問はすべて推奨どおり。実機などの確認が済んでいない決定は、確認が済むまで仮。末尾の「決定済み」を見る）
- 日付: 2026-11-16
- 対象: `lm/src/host/`（子の起動、権限の絞り方）、`engine`（子が無いときの動き、モデルの解決）、エンジンのビルドの feature（llama.cpp を入れるか）、インストーラ（規則）、ADR 0065 の自己診断（未マージ）。この ADR ではコードを変えない
- 前提: main = 94f65ae。[ADR 0066](0066-security-premises.md)（P5、敵 E2）、[ADR 0067](0067-windows-install-layout-and-launch-chain.md) §4.3（起動の規則）、[ADR 0068](0068-ipc-endpoints.md) §6.1（子に渡すハンドル）、ADR 0060（一部承認。§4.1 の檻の要件、Q4 の別プロセス、Q2 の「通らないモデルも警告つきで使える」）、ADR 0059（Vulkan）、ADR 0065（LM の既定を自己診断で決める。提案。ブランチ `docs/adr-0065-lm-self-diagnosis`）、#424（隔離の測り直し）、#413（S5）
- ADR 0060 と 0065 を置き換えない。0060 の「隔離は測ってから有効にする」「まだ決まっていないこと」の 3・4 に、順序と条件を足す
- 判断の置き場所: Rust（`lm` が子の権限を絞る。`engine` がどの段で起動するかを選ぶ）。Swift に足す判断はない

---

## 1. 現状（分かったこと。ADR 0060 の「Q4 の本実装」と `docs/architecture.md` §2.2）

- LM の推論は、別プロセス `ikari-lm-host` が持つ（両 OS。#423）。入るのは採点の要求（左文脈、読み、候補の文字列）、出るのは数値と、装置の固定の語だけ。親は、子から来た文字を検査してからログに書く。
- **隔離は、両 OS とも有効になっていない。**
  - macOS: 子はエンジンの App Sandbox を引き継ぐ。ネットワークには出られないが、エンジンと同じく、データのフォルダ全体（学習、ユーザー辞書、設定）を読み書きできる。
  - Windows: Job Object（親が終われば子も終わる）だけ。ファイルにもネットワークにも、利用者と同じに届く。子に渡るハンドルも限定していない（S5）。
- 隔離をかけたときの計測は、macOS の広い包みで 2 回だけ。遅い側が悪くなり、原因は確かめていない。この結果では決められない（ADR 0060、#424）。Windows の AppContainer は、起動のコードがまだ無い。
- 製品のエンジンには llama.cpp が入ったまま。**子が隣に無ければ、エンジンと同じプロセスでモデルを読む**（ADR 0060 の「まだ決まっていないこと」の 3）。
- 今、製品が読むモデルは、アプリに埋めた既知の sha256 のものだけ。自由指定（ファイル、URL）は未実装。
- GGUF そのものは重みのデータで、通信もファイルの操作もしない。起きうるのは、細工されたファイルが、llama.cpp（C++）や GPU のドライバの不具合を突くこと（ADR 0060 §4.1）。

## 2. 問題

- 「モデルは檻に入れる。勝手な通信やファイルの操作は許さない」（ユーザー決定）に対して、今あるのは「別プロセス」までで、檻の中身が無い。
- 隔離の計測が終わるまで何もしない、だと、配る時点で子は利用者と同じ権限を持つ。一方、計測の要らない安い絞り方がいくつかある。
- 自由指定のモデル（敵 E2 の入口）を、檻の前に出してはならない。どの段がそろえば出してよいかが決まっていない。
- 子が無いときにエンジンが自分でモデルを読む道は、檻を素通りする。

## 3. 決定 1: 檻を 3 つの段に分ける

| 段 | 中身 | 止めるもの | 残るもの | 要る計測 |
| --- | --- | --- | --- | --- |
| 段 0（今） | 別プロセス。落ちても固まっても、エンジンは LM なしで動く | 子の中の不具合が、エンジンを落とすこと | 乗っ取られた子は、利用者と同じことができる（Windows）。データのフォルダを読み書きできる（macOS） | — |
| **段 1（安い絞り）** | Windows: 渡すハンドルを標準入出力だけにする（S5）。Job Object で、子がさらにプロセスを作ること、クリップボードやほかの窓に触れることを禁じる。ファイアウォールの送信ブロックの規則（ADR 0066 §6.2）。子を低い整合性で起動する（利用者のファイルに**書けなく**なる）。macOS: 今のまま（引き継いだ Sandbox。ネットワークなし） | 通信（規則の範囲で）、ほかのプロセスの起動、利用者のファイルの書き換え（Windows） | 利用者のファイルを**読める**（Windows）。同じ機械の中の、ほかのプログラムの口につなげる。macOS は段 0 と同じ（データのフォルダを読み書きできる） | 低い整合性で GPU（Vulkan）が使えるか、速さが変わらないか |
| **段 2（本物の檻）** | Windows: AppContainer（能力なし）。読めるのは、モデルのファイルと、自分の実行ファイルのフォルダだけ。macOS: 子に専用の Sandbox（ネットワークなし、書き込みなし、読めるのはモデルと実行ファイルだけ） | 通信、決まったファイル以外の読み書き、ほかのプロセスの口 | 入ってきた採点の要求（左文脈と読み）は、子に見える。出せるのは数値だけ | 起動と採点の速さ、GPU が使えるか（#424） |

- どの段でも変わらないこと: 子の場所はエンジンの隣の絶対パス。入るのは文字列、出るのは数値と固定の語。子の返事は信用しない。続けて失敗したら諦める（ADR 0060）。
- どの段でも、モデルが返す数値は候補の並びを変えられる。候補は辞書からしか作らず、LM の重みには上限がある（今の作り）ので、モデルが出せる害は「並びが悪くなる」まで。
- 段 1 の各項目は、互いに独立に入れられる。計測で通らなかった項目（たとえば、低い整合性で GPU が使えない）は、外して理由を書く。

## 4. 決定 2: どの段がそろえば、何を出してよいか

1. **ビルド済みを配る条件は、段 1。** プリセット（既知の sha256）のモデルだけを読む間は、段 1 で配ってよい。プリセットは、作者が評価に使った、中身の決まったファイルで、敵（E2）の入口ではない。
2. **自由指定のモデル（ファイル、URL）は、段 2 が有効な OS でだけ出す。** 段 2 が無い OS では、自由指定の画面とコマンドを出さない（ADR 0060 の段階 4・5 の前提にする）。
3. **段 2 が遅くても、自由指定のモデルは段 2 で動かす。プリセットは段 1 のまま動かしてよい。** 隔離で遅くなる（#424 の計測のとおりなら、時間切れが増える）ことは、自由指定の警告（ADR 0060 Q2）に足す。プリセットまで段 2 にするかは、#424 の計測のあとに決める。
   - 理由: 速さのためにプリセットの檻を待たせると、自由指定がいつまでも出せない。危ないのは自由指定の方なので、そちらにだけ強い檻をかける形を先に成り立たせる。
4. 段 2 で GPU が使えない OS では、自由指定のモデルは CPU だけで動かす（遅い。警告に書く）。

## 5. 決定 3: 製品のエンジンから llama.cpp を外す

- **製品のビルドでは、エンジン（`ikari-engine-host.exe`、macOS のエンジン）に llama.cpp を入れない。子が隣に無い・起動できないときは、LM なしで動く。**
- 理由: (1) 子が無いときにエンジンがモデルを読む道は、檻を素通りする。子の実行ファイルを消すだけで、その道に入る。(2) エンジンは、学習と辞書を持つ、いちばん守りたいプロセス。細工されたファイルを読む C++ のコードを、そこに置かない。(3) 配る物は、子を必ず同梱するので、ふつうの利用者には違いが無い。
- 評価と CLI（`ikari-eval`、`ikari`）は、今のまま同じプロセスで読めてよい（開発の道具）。
- ADR 0060 の「まだ決まっていないこと」の 3 への答え。

## 6. 決定 4: モデルのファイルと、落ち続けの防止

- 子に渡すモデルのパスは、エンジンが決める（データの場所の `models/` の下で、ID から作る。ID は文字の種類を検査する）。設定や manifest に書かれたパスを、そのまま開かない（P5）。
- 段 2 では、子が読めるのはそのファイル 1 つ。エンジンが、起動の前に、そのファイルにだけ読み取りを許す。
- 読み込みの印（`models/.loading`。ADR 0060 §4）で、同じモデルで落ち続けることを止める。印が残っていたら、選択を既定に戻す。
- モデルの大きさの上限（ADR 0060 §4。値は実測で決める）は、子に渡す前に、エンジンが見る。

## 7. 決定 5: 自己診断（ADR 0065）の守り

ADR 0065 は、利用者の機械で推論の速さを測って、LM の既定を決める（提案）。セキュリティの面で足す規則は次のとおり。大きな危険は見当たらない。

1. **測るのに使う入力は、コードに置いた作文だけ**（ADR 0065 §4.2 のとおり）。利用者が打った文、学習、周辺テキストを使わない。
2. **結果は手元にだけ置く。** 通信しない（ADR 0065 の決定 0-4）。書き出しにも含めない（同 §4.4）。機械の特徴（GPU の要約、速さ）が入るので、ログに出すのは数値と固定の語だけ（同 §4.5）。
3. **自己診断は、取得を起こさない。** 判定がオンにするのは、すでに入っているモデルだけ。モデルが無ければ、測らない（同 §5.1）。
4. **結果のファイルは信用しない入力として読む**（[ADR 0073](0073-secret-input-and-user-data.md) §5）。範囲の外の数値、知らない語は「結果なし」にして測り直す。同じ利用者のプログラムがファイルを書き換えたり消したりしても、起きるのは、既定のオン・オフが変わることと、測り直しが 1 回走ることだけ。
5. **測り直しは、同時に 1 つだけ。** 設定の口の「もう一度測る」を続けて送られても、重ねて走らせない。打っている間は測らない（同 §4.3）ので、入力は止まらない。
6. 自己診断は、製品と同じ子（同じ段の檻）で測る。檻の段を変えたら、測り直す（同 §4.4 の「測り直す条件」に、檻の段を足す）。

## 8. 検討した案

- **段 2 がそろうまで、配らない**: いちばん安全。Windows の AppContainer の起動のコードと、GPU が使えるかの確認が要り、配布が計測待ちになる。プリセットだけなら敵の入口が無いので、段 1 で配る方を採る。
- **段 1 を飛ばして、段 2 だけを作る**: 作るものは減る。段 2 が計測で通らなかった OS に、何も残らない。段 1 は計測がほぼ要らないので、先に入れる。
- **自由指定のモデルも段 1 で出し、警告に任せる**: 利用者は早く使える。ユーザーの決定（勝手な通信やファイルの操作は許さない）に、段 1 は届いていない（ファイルを読める）。採らない。
- **エンジンに llama.cpp を残し、子が無いときの逃げ道にする**: 配置が壊れても LM が動く。§5 の理由で採らない。
- **GGUF を読む前に、Rust の検査器で形を確かめる**: 明らかに壊れたファイルは落とせるが、llama.cpp の読み方と少しでも違えば、守りにならない。檻の代わりにはしない（足すのは自由）。

## 9. 結果

- 配る条件（段 1）と、自由指定を出す条件（段 2）が分かれ、#424 の計測が配布を止めなくなる。
- ADR 0060 の段階 4・5（ファイルからの取り込み、URL からの取得）は、段 2 のある OS から始まる。
- 実装の issue（承認のあとに切る）: 段 1 の各項目（S5 を含む）、製品のエンジンのビルドから llama.cpp を外す、段 2 の起動のコード（Windows）と専用の Sandbox（macOS）、段ごとの計測（#424 に足す）。
- 失うもの: 子の実行ファイルが欠けた配置では、LM が動かない（今は動く）。段 2 が遅い OS では、自由指定のモデルは遅い。

## 10. 推測（確かめていないもの。#424 と実機の項目にする）

- Windows で、低い整合性の子が Vulkan（GPU）を使えるか。使えなければ、段 1 から低い整合性を外すか、GPU を諦めるかを、数字を見て決める。
- Windows の AppContainer の中で、Vulkan のドライバが読み込めるか。
- Vulkan は、利用者ごとの設定（レジストリ、環境変数）から追加の DLL を読むことがある。子は高い権限で動かないので、権限の境界は越えない（ADR 0066 の P3 の範囲）。段 2 でこの読み込みがどうなるかは確かめていない。
- macOS で、エンジンの Sandbox の中から、さらに狭い Sandbox の子を起動する形が、配布用（ad-hoc）の署名で成り立つか。**→ エンジンが自分で起動する形は成り立たない。別の起動元を挟めば成り立つ（§13）。**
- Job Object の制限と、候補窓の Job Object（ADR 0062 §5.4）の入れ子が、両立するか。

## 13. 実測: macOS の段 2（専用の Sandbox）（2026-11-17、開発機）

§3 の「macOS: 子に専用の Sandbox」が作れるかを、捨てる試験用の実行ファイルで確かめた。製品のアプリ、エンジン、利用者のデータには触れていない（smoke、インストールはしていない）。ここに書くのは見た事実と数字だけ。

### 13.1 条件

- 機械: 作者の開発機（Apple シリコン、macOS 27.2）。モデルは zenz-v3.2 small Q5_K_M（作業用の場所に写したもの）。子は、このブランチの `ikari-lm-host`（Metal つき）。
- 署名はすべて ad-hoc（`codesign -s - -o runtime`。配布物と同じ）。識別子は試験用（`…cagetest.*`）。
- 「エンジン役」は、App Sandbox（network なし、作業用の場所だけを一時例外で読み書き）を持つ試験用の親。1 つは単体の実行ファイル、1 つは試験用のアプリの中の XPC サービス（製品のエンジンと同じ形）。
- 採点は、短い入力 3 候補を 21 回。数字は参考値（1〜3 回）。

### 13.2 子に専用の entitlement を付ける形（エンジンが `posix_spawn` する）

| 子の entitlement | Sandbox の親から起動 | Sandbox なしの親から起動 |
| --- | --- | --- |
| なし（今の製品） | 動く。親の Sandbox を引き継ぐ | — |
| `app-sandbox` ＋ `inherit` | 動く。親の Sandbox を引き継ぐだけ（狭くならない） | — |
| `app-sandbox` だけ（専用） | **起動の直後に SIGTRAP で終わる**（CPU・GPU、パス・fd のどれでも） | 動く。自分の Sandbox に入る |
| `app-sandbox` だけ、Info.plist を埋めない | — | SIGTRAP（ADR 0076 §3.3 と同じ。`-sectcreate __TEXT __info_plist` で埋めると動く） |

- 子が自分で絞る（`sandbox_init`）形: Sandbox の中のプロセスからは `EPERM` で失敗する。Sandbox なしの親の子なら成功する（`deny default` の SBPL で、ファイル、通信、プロセスの起動がすべて止まった）。
- 結論: **今の形（エンジンが自分の子として起動する）のままでは、子をエンジンより狭い Sandbox に入れられない。** 子の Sandbox は、Sandbox の外のプロセスが起動したときにだけ、自分の entitlement で決まる。

### 13.3 モデルの渡し方

- 専用の Sandbox の子は、モデルを**パスでは読めない**（`null result from llama cpp`。ファイルを開く段で拒まれる）。
- 親が開いたファイルを fd 3 に付けて渡し、`--model /dev/fd/3` で読ませると、**読める**（llama.cpp の読み込みも、mmap も、そのまま動いた。子のコードの変更は要らない）。Sandbox の拡張（sandbox extension）は使っていない（要らなかった）。
- 引き継ぎの子でも、fd の渡し方は同じく動く。

### 13.4 Metal（GPU）と速さ

| 形 | 準備完了（Ready）まで | 採点の最初 / 中央値 / 最大 |
| --- | --- | --- |
| Sandbox なし（対照） | 73〜428ms | 16〜18 / 10〜12 / 11〜18ms |
| 引き継ぎ（今の製品の形） | 75〜387ms | 16〜41 / 13〜22 / 14〜34ms |
| 専用の Sandbox（fd で渡す） | 83〜153ms | 16〜31 / 14〜17 / 26〜37ms |
| 専用の Sandbox、CPU だけ | 107〜137ms | 17〜28 / 13〜15 / 13〜67ms |

- 専用の Sandbox の下でも Metal に載る（`dev=gpu`、`devices=mtl:Gpu,cpu`）。NLL は、同じ装置なら形に関わらず一致した。
- **子の実行ファイルが変わったあとの最初の 1 回だけ**、Ready まで約 4〜5 秒、最初の採点が約 0.37 秒かかる（どの形でも起きる。Sandbox なしでも起きた。表の数字はこの 1 回を除いたもの）。2 回目からは上の表の速さ。Metal のキャッシュは Sandbox の外に置き場所を足さなくても効いた（キャッシュがどこにあるかは確かめていない）。今の締め切り（Ready 60 秒）には収まる。

### 13.5 別の起動元を挟む形（試験用のアプリで確かめた）

- 試験用のアプリに、エンジン役（App Sandbox の XPC サービス）と「檻役」（`app-sandbox` だけの XPC サービス）を並べた。
- **エンジン役から、隣の XPC サービスを名前で探すと失敗する**（`Connection invalid`。XPC サービスは、アプリ本体からしか探せない）。
- アプリ本体（Sandbox なし。製品の殻に当たる）が、檻役から匿名の口（`xpc_endpoint`）をもらい、エンジン役に渡すと、エンジン役は檻役につながる。エンジン役が、パイプ 2 本とモデルの fd を檻役に渡し、檻役が `ikari-lm-host` を起動すると、**子は檻役の Sandbox を引き継ぐ**（子自身に entitlement は要らない）。採点の枠はパイプのまま（今の取り決めのまま）動いた。
- 速さ: 檻役への頼みから起動まで 0.3〜0.9ms。Ready まで 77〜107ms（実行ファイルが変わった最初は 4.3 秒）。採点の中央値 13〜22ms。GPU・CPU とも動いた。
- **エンジン役から、檻の子に signal を送れない**（`kill` が拒まれる。自分の子ではないため）。止めるのは、パイプを閉じる（子は標準入力の終わりで自分で終わる）か、檻役に頼むかになる。
- Sandbox なしの親（殻）が、専用の entitlement の子を直接起動する形も動く（§13.2 の右の列、§13.4 の 3 行目）。

### 13.6 檻の子に届くもの（試験用の小さな子で確かめた）

| 試したこと | 引き継ぎ（今の形） | 専用の Sandbox（§13.5） |
| --- | --- | --- |
| 渡された fd のモデル | 読める | 読める |
| パスでモデル（エンジンが読める場所） | 読める | 拒まれる |
| エンジンが読み書きできる場所への書き込み | **できる** | 拒まれる |
| 利用者のほかのファイル | 拒まれる | 拒まれる |
| 外への TCP 接続 | 拒まれる | 拒まれる |
| 自分のコンテナ（`~/Library/Containers/<識別子>/`）への書き込み | エンジンのコンテナに書ける | 檻役のコンテナに書ける |
| システムの読み取り（`/etc` など）、署名された実行ファイルの起動 | できる | できる |

- 試験用の親の一時例外は作業用の場所だけにしたので、製品のエンジン（データのフォルダを読み書きできる）とは、引き継ぎの列の「書き込み」の場所が違う。製品では、引き継ぎの子はデータのフォルダを読み書きできる（§1）。
- 専用の Sandbox でも、自分のコンテナへの書き込みと、システムの読み取りと、プロセスの起動は残る（App Sandbox の既定）。§3 の「書き込みなし」は、コンテナの分だけ満たさない。これも止めたいなら、Sandbox なしの起動元の子が `sandbox_init` で自分を絞る形（§13.2）が要る（Metal がその下で動くかは確かめていない）。

### 13.7 ここから言えること（推測を含む。決定ではない）

- 段 2 の macOS は、「子の実行ファイルに entitlement を付ける」だけでは作れない。起動元を Sandbox の外か、別の Sandbox の XPC サービスにする必要がある。どちらも、殻とエンジンの間の取り決め（口や fd の受け渡し）を変える。そのため、このレーンでは実装していない（リードへの質問）。
- 案 A（檻役の XPC サービス）: 殻が匿名の口を仲立ちするだけ。起動と回収は檻役（Rust で書ける。libxpc の C の API）。エンジンからは kill できないので、回収は檻役に寄せる。
- 案 B（殻が起動する）: 殻（Sandbox なし）の Rust（`shell-ffi`）が専用の entitlement の子を起動し、パイプとモデルの fd をエンジンに渡す。kill は殻ができる。殻が落ちると子の回収の持ち主が変わる。
- 案 C（確かめていない）: 利用者の LaunchAgent として檻役を置き、エンジンに mach-lookup の一時例外を足す。インストールの手順が増える。
