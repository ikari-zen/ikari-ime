# ADR 0039: 辞書にない外来語（普通名詞のカタカナ語）を Wikipedia 日本語版の本文から集めて、辞書に足す

- 状態: 承認（2026-10-29。§0.4 の方針 1〜3 と §9 の Q1〜Q5 をユーザーが承認。一覧の公開は §11 R2 の一次情報の確認のあと）
- 日付: 2026-10-29
- 対象: 語の収集（オフラインの道具。新しい `dict-builder` のサブコマンド）、語の一覧から辞書の行を作る段（新しいサブコマンド）、`scripts/build-dict.sh`、`THIRD_PARTY_NOTICES.md`、評価セット。core・engine・殻は変えない

- タスク: #113（#100 の根本対策）

## 0. 現状の把握（researcher の調査と既存の ADR。確認済み）

### 0.1 辞書にない語
- ばーじょにんぐ → バージョニング、しゃーでぃんぐ → シャーディング など、IT の複合的なカタカナ語が辞書（Sudachi Full = small + core + notcore）にない。ロードバランサー、マイクロサービスは C 単位で載っている。
- Sudachi の元は UniDic と NEologd の一部（公式 README）。複合語を載せない方針の明文は見つからない。**収集の漏れと見るのが自然（推測）**。
- ADR 0037 の K1 だけでは、疑似の未知語 8698 件のうち直せる対象は約 900 件で、本物の未知語（ばーじょにんぐ）は疑似の分布の端ではなく中央にある（S0 §0・§7）。K1 は「辞書にない語が残る場合の保険」で、語彙を増やす本 ADR と補い合う（ADR 0037 §11）。
- Mozc（Google 日本語入力の元）は、辞書のカタカナ語を Web のデータの処理で集めている。ランタイムの未知語の扱いは、ikari の「末尾にカタカナの候補を足す」と近い（researcher の調査）。つまり差は**辞書の語彙の出どころ**にある。

### 0.2 出どころの候補（researcher の調査。2026-10-29）
| 出どころ | 分かったこと |
| --- | --- |
| Wikipedia 日本語版のタイトル | カタカナだけ（3 字以上）234,796 件、うち Sudachi にない 135,573 件（約 58%）。**ほとんど固有名詞**。バージョニング、シャーディングは**タイトルにない**（セマンティックバージョニング のような複合はある） |
| Wikipedia 日本語版の本文 | 本文のダンプは約 4.76GB（圧縮）。未取得。本文の頻度でなら、タイトルにない普通名詞も拾える見込み（推測） |
| jawiki-kana-kanji-dict | ADR 0012 案C で不採用（元データ CC BY-SA、読みの誤り YAML=やめる など） |
| Mozc UT | 出力のライセンスが Mixed（GPL の元を含む）。名詞だけ、ID は Mozc のもの（ADR 0012 案E） |
| Common Crawl | 利用条件は「第三者の著作権を尊重する」旨。中身の権利は個々のサイトにある |

- 法的な位置づけは断定しない。「語の表記と頻度は事実の情報」という見方が多いこと、著作権法 30 条の 4（情報解析）が関わりうることは、一次情報で確かめていない（§11 の R2）。

### 0.3 辞書に足す形の既存の型
- Sudachi の普通名詞のカタカナ語で最も多い組は、左右 ID 5139、コスト 15000（931 行）。新語に付ける値の手本になる（値は §2.5 の掃引で決める）。
- ABR の町名（ADR 0030）は、`dict-builder town` が Sudachi の CSV と同じ形の `town_lex.csv` を作り、`build-dict.sh` が `--lex` と `--notcore-lex` に渡す。`--notcore-lex` の行は、品詞の統計と活用規則に数えず、chiVe にない語に `lemma_rank` を当てず、同じ読みによく使われる Core の語があるときだけ `extension_peer` を足す（ADR 0012 §2.5・§11.3。`dict-builder/src/policy.rs`）。
- 帰属表示は `THIRD_PARTY_NOTICES.md` に節を足し、設定アプリの「このソフトについて」に出る（ADR 0030 §6。既存の仕組み）。
- 辞書（system.dict）は利用者の手元で `data/raw` から作り、`data/build/dict` に出す。バンドルには含めない。

### 0.4 ユーザーの承認済みの方針（2026-10-29）
1. 配布物に入れるのは**語（表記）と頻度だけ**。本文の文は持たない。帰属表示は THIRD_PARTY_NOTICES.md に書く。
2. **固有名詞（種名・人名・作品名など）は入れない**。普通名詞の外来語が対象。
3. 頻度の下限は**掃引で決める**。値は先に実測し、ユーザーに確認してから入れる。
- あわせて: 読みはカタカナ → ひらがなの機械的な変換だけで付ける。品質は、再現率（Sudachi の普通名詞のカタカナ語を伏せて、集めた語がどれだけ戻るか）と、混入率（非語・固有名詞）で測る。

## 1. 問題の定義

- 本質は、**辞書の語彙が「よく書かれているのに辞書にないカタカナ語」を持たない**こと。ランタイムの工夫（K1）は、辞書の分割の経路と競うだけで、辞書の語ほど安定して 1 位にならない（S0: 対象 900 件に限りがある）。
- 足す語は「入力を正とする」の内側にある: 読みはカタカナの表記そのもの（ひらがなにしただけ）で、読みに対応しない文字を足さない。辞書から候補を作り、LM は並べ替えにだけ使う、という決定とも合う。
- 制約:
  - ほかの人が使う前提で、**データの出どころとライセンスを明記**できること。再現できること（同じ版のダンプから同じ一覧ができる）。
  - 固有名詞を入れない（方針 2）。固有名詞の雑音がよく打つ語の候補を埋める害は ADR 0012 §3 で測った。
  - 全セットで 1 位が悪化しない（ADR 0037 §6.5 と同じ基準。LM あり・なし、dev・test、AJIMEE）。
  - 利用者の手元で数 GB のダンプを取らせない（辞書のビルドは今の約 30 秒の桁に保つ）。

## 2. 決定（提案）

### 2.1 出どころ: Wikipedia 日本語版の本文（ダンプ）
- **推奨は Wikipedia 日本語版の本文**（pages-articles のダンプ）。理由:
  1. **ライセンスと帰属がはっきりしている**（CC BY-SA。帰属の書き方の手引きがある）。Common Crawl のように、ページごとに権利者が違うものではない。
  2. **版が固定でき、再現できる**（日付つきのダンプ。sha256 を記録できる）。
  3. **IT と学術の用語が本文に多い見込み**（データベース、分散システムの記事など。推測）。タイトルだけではバージョニングを拾えないことは分かっている（§0.2）ので、本文の頻度を使う。
  4. 量が手ごろ（圧縮で約 4.76GB）。Common Crawl より、取得と処理の手間が桁で小さい（推測。Common Crawl の日本語の量は測っていない）。
- 弱み: 百科事典の文体なので、口語・スラングの新しい外来語は少ない（推測）。今回の対象（IT の普通名詞）に足りるかは PoC の再現率で測る（§6）。
- **集めるのはメンテナー（または将来 CI）で、利用者ではない**。利用者に届くのは語と頻度の一覧だけ（§2.7）。

### 2.2 集める手順（collect）
1. ダンプの記事（標準の名前空間、リダイレクトを除く）の本文から、ウィキの記法・テンプレート・表・脚注・リンク先の名前を除いて地の文を取り出す。
2. 地の文から、**カタカナの最長の連なり**（ァ〜ヴ と ー。・ と ＝ で区切る）を取り出す。形態素解析はしない（Sudachi で分けると、辞書にない語ほど既知の語に割れて消えるため）。
3. 連なりごとに、**出現の回数（tf）と、出た記事の数（df）**を数える。df は 1 つの記事の繰り返し（記事の主題の名前など）に強い。
4. 出力: 語の一覧（§5.1 の形式）。文や記事の名前は出さない。全体の記事数とダンプの版・sha256 をヘッダに書く。

### 2.3 絞り方（webwords。辞書を作るときに当てる。理由ごとに件数をレポートに出す。ADR 0030 の TownReport と同じ）
- **F1 辞書にある語を除く**: Sudachi（small + core + notcore）と ABR の語に同じ表記があれば足さない（品詞によらず）。
- **F2 頻度の下限**: df の下限（と、必要なら tf の下限）。**値は掃引で決める**（方針 3。§6.2）。
- **F3 形の規則**: 読みが短い語（下限の字数は掃引の軸）、ー で始まる、小書きで始まる、同じ字の繰り返しだけ（ドドドド）、反復の読み（`is_reduplication`。擬音語・擬態語）、ヵ ヶ ヷ〜ヺ を含む連なりを除く。
- **F4 固有名詞を除く**（方針 2）。次を重ねる。どれも PoC で効きと誤り（普通名詞を落とす率）を測ってから採る:
  - F4a: 同じ表記の日本語版の記事があり、その Wikidata の項目（CC0）の「分類（P31）」が、人、組織、作品、分類群（種名）、地名、製品・商標などの固有のもの、のとき除く（R3）。
  - F4b: 本文での並びの手がかり（直後に さん・氏・社・州・市・科・属・目 が続く割合など）が高いとき除く。手がかりの表と閾値は PoC で決める。
  - F4c: Sudachi の固有名詞と、表記の部分（連なりの頭や末尾）が一致し、残りも固有名詞のもの（人名 + 人名 など）を除く。
- **F5 既知の語の連なりを除くか**（Q4）: 連なりが Sudachi の普通名詞のカタカナ語だけに分けられるもの（マイクロサービスアーキテクチャ = マイクロサービス + アーキテクチャ）は、今でも辞書の経路で出せる。足すと一覧が膨らむが、得は小さい見込み（推測）。**PoC で「足したとき 1 位が変わる割合」を測り、決めるのは Q4**。
- 読みが違えば別の語（サーバ / サーバー、ヴァージョン / バージョン）。どれも読みのとおりの表記なので、F1〜F5 を通ったものはすべて入れる。並べ替えは既存の `katakana_variant` に任せる。

### 2.4 読みの付け方
- **表記のカタカナをひらがなにするだけ**（ヴ → ゔ。ー はそのまま。小書きもそのまま）。英語の綴りからの読みの推定はしない。読みと表記が必ず対応するので、jawiki-kana-kanji-dict の読みの誤り（YAML=やめる。ADR 0012 §0.3）は構造的に起きない。
- 揺れ（ヴァージョン / バージョン）は、どちらも Wikipedia で書かれていれば、どちらも足す（打った読みのとおり。ユーザーの決定 B20-3 と B32）。

### 2.5 辞書への入れ方
- **ABR の町名と同じ形**: 新しいサブコマンドが Sudachi の CSV と同じ形の `webwords_lex.csv` を作り、`build-dict.sh` が `--lex` と `--notcore-lex` に渡す。system.dict の形式、grammar.bin、core のコードは変えない。
  - `--notcore-lex` に入れるので、新語の規則（ADR 0012 §2.5・§11.3）がそのまま効く: 品詞の統計（`user_cost`、代表の左右 ID）に数えない → ユーザー辞書の語のコストが変わらない。chiVe にないので `lemma_rank` を当てない。同じ読みによく使われる Core の語があれば `extension_peer`（+3000）。
- **品詞**: `名詞,普通名詞,一般,*,*,*`。サ変可能（シャーディングする）かは本文から判定しない（「する」は別の語としてつながる）。
- **左右 ID**: Sudachi の同じ品詞で表記がカタカナだけの行の最頻の組を、ビルドのときに数えて使う（今の版では 5139。固定の数値を持たない。ADR 0030 §4 と同じ）。
- **コスト**: 掃引で決める。軸は (1) 一律の値（出発点は Sudachi の最頻値 15000）、(2) df の段に応じた値（df が大きいほど安い。段の数と幅は PoC の分布から）。どちらを採るかも掃引の結果で決める。**計測していない値は入れない**（値は PR に明示し、ユーザーに確認）。
- ベクトル: 分解（ADR 0012 §12）は Sudachi の A/B 分割に頼るので、新しい語には付かない。沼る・陰キャ と同じ扱い（ADR 0012 §11.3 の 4）。

### 2.6 更新の頻度
- **Sudachi の版を上げるときに合わせて、作り直す**（推奨。Q5）。Sudachi が新しい版で同じ語を足したら F1 で自然に消える。ダンプは月に 2 回ほど出るが、毎回は追わない（得に対して評価の手間が大きい）。
- 作り直したときは、前の一覧との差（増えた語・消えた語）をレポートに出し、§6 の評価を流してから入れ替える。spec「辞書の更新」の決定（切り替える前に評価セットを流す、旧版を残す）に従う。

### 2.7 配布物と帰属表示
- **配布するのは語の一覧（表記、tf、df）だけ**（方針 1）。本文、文、記事の名前、リンクは持たない。読みは持たない（ビルドのときに表記から作る）。
- 置き場所は**リポジトリ**（推奨。Q2）。例: `dict-builder/assets/webwords/katakana.tsv`（名前は契約のコミットで決める）。大きさは数万行・数 MB 以内の見込み（推測。PoC で測る）。`build-dict.sh` が読むので、利用者はダンプを取らない。
- ライセンスの表示: 安全側として、**一覧のファイルに「Wikipedia 日本語版をもとに ikari-ime が作成。ファイル単位で CC BY-SA 4.0」と書く**（推奨。Q2）。語と頻度が著作物かは断定しない（§0.2）。コード（Apache-2.0）とはファイルで分ける。
- `THIRD_PARTY_NOTICES.md` に節を足す: 出典（ダンプの名前と日付）、ライセンス、加工の内容（地の文のカタカナの連なりを数え、§2.3 で絞り、語と頻度だけを残した。文は含まない）、使い方（`build-dict.sh` が辞書に加える。一覧のほかに Wikipedia の内容は同梱しない）。
- 辞書（system.dict）は今と同じく利用者の手元で作り、バンドルに含めない。将来、辞書の一式を配るとき（ADR 0033、#99）は、配布物に同じ帰属表示を付ける。

## 3. 検討した案

| 案 | 内容 | 得 | 害・手間 | 判断 |
| --- | --- | --- | --- | --- |
| **W1 Wikipedia 本文の一部（PoC）→ 全体（本番）** | 分割ダンプの数ファイルで PoC。再現率が標本の量で伸びるなら全体に広げる | ライセンスが明確、再現できる、IT の用語が多い見込み。PoC が小さく速い | 口語・スラングは少ない（推測）。固有名詞を除く手間 | **採る**（§2.1、§7） |
| W2 Wikipedia のダンプ全体を最初から | 4.76GB を取って全部を数える | 頻度が最も安定 | PoC の前に取得と処理の時間を払う。絞り方が決まる前に全量を回すと、作り直しのたびに重い | W1 の本番の形として残す。最初からはやらない |
| W3 Common Crawl | Web の大量のテキストから数える | 口語・新しい語・ブログの IT 用語まで拾える | 量が桁違い（取得と処理が重い）。スパム・機械生成の文が多い。権利がページごとで、帰属の書き方が決まらない。再現の手間 | 採らない（今は）。W1 で IT の語が足りないと分かったら、別の ADR で |
| W4 Wikipedia のタイトルだけ | 234,796 件のタイトルから選ぶ | 取得が軽い。表記が整っている | ほとんど固有名詞（方針 2 に反する）。バージョニング、シャーディングがない（§0.2） | 採らない。F4a（固有名詞の判定）の材料としては使う |
| W5 既存の生成物（Mozc UT 型、jawiki-kana-kanji-dict） | 他者が Wikipedia などから作った辞書を取り込む | 手間が最小 | 出力のライセンスが Mixed（GPL を含む）、または元の CC BY-SA の解釈が作者のもの。読みの誤り、固有名詞が中心、ID が Mozc のもの（ADR 0012 案C・案E） | 採らない |
| W6 集めない（K1 と語彙集とユーザー辞書に任せる） | ランタイムの K1、手で作る `it.tsv`、ユーザー辞書 | 新しいデータとライセンスの扱いが要らない | K1 の対象は約 900 件で限りがある（S0）。語彙集は人手で増え続ける。「全部を登録するのは面倒」（ADR 0012 §0.1）に応えない | 採らない。K1 は保険として並行 |
| W7 Wiktionary 日本語版の見出し（補助） | 外来語の見出しを取る | 普通名詞が中心で、品詞が付いている | 件数が少なく、新しい IT 用語は薄い見込み（推測。数えていない）。CC BY-SA | 今は採らない。F4 の誤りが大きいときの補助として要調査（R6） |

## 4. 結果（採ったときに変わること）

- 得るもの: 本文でよく書かれる外来語（バージョニング など）が辞書の語になり、K1 に頼らず、LM あり・なしの両方で 1 位を取りやすくなる（推測。§6 で測る）。語彙集（`it.tsv`）の手入れが減る。
- 失う恐れ: 短い読みや、和語と同じ読みのカタカナ語が、よく打つ語の候補の 1 ページ目に入る（ADR 0012 §3 の雑音と同じ型）。固有名詞の取りこぼし（F4 をすり抜けた名前）。辞書のビルドに 1 段増える。
- 変えないこと: system.dict の形式、grammar.bin、core・engine・殻、LM、学習、K1 の式。
- 新しく持つもの: 語の一覧のファイル（CC BY-SA 4.0 の表示つき）と、その作り直しの手順。

## 5. 契約（実装に入るときに先に入れるもの）

### 5.1 語の一覧の形式（レーン間で共有する）
- UTF-8、タブ区切り。1 行目はヘッダ:
  `#ikari-webwords	schema=1	source=jawiki-<ダンプの日付>	sha256=<ダンプの sha256>	articles=<記事数>	license=CC-BY-SA-4.0`
- 2 行目以降: `表記	tf	df`。表記はカタカナの連なり（F1〜F5 を当てる前。絞りはビルドのときに当てるので、下限を変えても集め直さなくてよい）。
- ただし配布する一覧には、集めた段で、掃引の範囲の最も低い下限より少ない語は入れない（ファイルを小さくするため。値は PoC の後に決める）。並びは表記のコードポイント順（差分を読みやすくする）。

### 5.2 レーンとファイルの境界
| レーン | 持つファイル | 入力 → 出力 | 契約で固めるもの |
| --- | --- | --- | --- |
| A 収集 | `dict-builder/src/collect.rs`（新規） | ダンプ（bz2）→ 語の一覧（§5.1） | §5.1 の形式。オフラインの道具で、`build-dict.sh` からは呼ばない |
| B 絞りと行の生成 | `dict-builder/src/webwords.rs`（新規） | 語の一覧 + Sudachi の CSV + ABR の lex（任意）+ F4a の表（任意）→ `webwords_lex.csv` と理由ごとの件数のレポート | 引数（`--words`、`--lex`、`--min-df`、`--min-len`、`--cost` など）とレポートの項目。品詞と ID の決め方（§2.5） |
| C ビルドの組み込み | `scripts/build-dict.sh`、`scripts/fetch-data.sh`（F4a の表を取るとき）、`THIRD_PARTY_NOTICES.md`、一覧のファイル | 一覧があれば B を呼び、`--lex` と `--notcore-lex` に足す。なければ今と同じ（ログに出す） | 掃引用の上書き（`--webwords-cost` など。ADR 0030 の `--town-cost` と同じ形）。BUILD_INFO に一覧の sha256 |
| D 評価 | `eval/sets/`（新しいセット）、`eval/reports/`、`eval/scripts/`（捨てるスクリプト） | §6 | 評価セットの期待はユーザーの確認後 |

- A と B は同じ crate の別のファイルで、共有するのは §5.1 の形式だけ。`dict-builder/src/main.rs` のサブコマンドの登録は契約のコミットで先に入れ、レーンでは触らない。
- 契約のコミットで入れるもの: §5.1 の形式の説明（`dict-builder` の doc コメント）、2 つのサブコマンドの引数（中身は「未実装」のエラーを返す）、`build-dict.sh` の引数の受け口（既定は何もしない）。

## 6. 評価の設計

### 6.1 PoC で測るもの（辞書を作り直さずに測れるもの）
- **再現率（leave-one-out の逆）**: Sudachi の普通名詞のカタカナ語（表記も読みもカタカナ、3 字以上）を「伏せた」とみなし、集めた一覧（F1 を当てず、F2〜F4 を当てたもの）にどれだけ入るか。下限の値ごとの曲線にする。ADR 0037 の疑似の未知語 8698 件（主の群 1740、対象 900）でも同じく数える。
- **混入率**: 一覧のうち Sudachi にない語（F1 の後）から、下限の段ごとに層に分けて抜き取り、「普通名詞の外来語 / 固有名詞 / 非語（断片・連結・誤字） / その他」に分ける。標本の大きさと、誰が判定するかは Q3。
- **F4 の効き**: F4a〜c それぞれで、除いた語のうち固有名詞の割合（効き）と、Sudachi の普通名詞を誤って除いた割合（誤り）。
- **標本の量と再現率**: 分割ダンプの 1・2・4 ファイルで再現率を出し、伸び方を見る。飽和していれば全量は要らない。伸び続けるなら W2（全体）に広げる。
- **本物の未知語**: ばーじょにんぐ、しゃーでぃんぐ が一覧に入るか、その df。

### 6.2 掃引（辞書を作り直して測る）
- 軸: F2 の df の下限、F3 の読みの字数の下限、§2.5 のコスト（一律 / df の段）、F5 の有無。格子の範囲は §6.1 の分布から決める。「足さない」を必ず含める。
- **狙う群**: (1) ADR 0037 の leave-one-out の辞書（S0 と同じ作り方）に、絞った辞書を基準に F1 を当てた一覧を足し、対象 900 件のうち 1 位になる数（leave-one-out の逆を辞書の上で測る形）。(2) `katakana-like.tsv` の カタカナ語(分割負け)。(3) 新しいセット `webwords.tsv`（一覧から選んだ本物の未知語。公開の一般的な語だけ。期待はユーザーの確認後。Q3 と同じ確認の場で）。
- **守る群**: `eval/sets/*.tsv` の全セット（snapshot が流すもの）と AJIMEE。LM なし（`--ranker full`）と LM あり（zenz-v3.2 small、`--lm-budget-ms 2000 --lm-deadline-ms 2000`、時間切れ 0）。
- **雑音**: ADR 0012 §5.1 の頻度上位 3000 語（単独）で、1 位が変わった数と、1 ページ目に新しく足した語が入った数（R5: リポジトリで再現できるかを確かめる）。
- **大きさと時間**: system.dict の増分、`build-dict.sh` の時間の増分（今は約 30 秒の桁）、収集の時間（オフライン）、warm p99 と起動直後の最初の変換。
- K1（ADR 0037）の既定値がまだ決まっていなければ、K1 なしと、K1 の採る候補の両方で測る（2 つの変更が同じ候補の順位を動かすため）。

### 6.3 採る・採らないの基準
- **不採用**: 既存のどのセット（LM あり・なし、dev・test、AJIMEE）でも 1 位が基準より悪化した点（ADR 0037 §6.5 と同じ）。雑音（頻度上位 3000 語の 1 位の変化）が 0 でない点。
- **採る点の選び方**: 不採用でない点のうち、(1) 狙う群の 1 位が最も多い、(2) 同じなら混入率が低い、(3) それも同じなら一覧が小さい方。混入率の上限は、§6.1 の結果を示してユーザーが決める（今は決めない）。
- 結果は eval/reports に 1 本書き、索引（eval/reports/README.md）に足す。

## 7. 実装の進め方（1 タスク 1 ブランチ）

1. **要調査（researcher）**: §11 の R1〜R6。特に R1（分割ダンプの大きさ）と R2（帰属の書き方）。
2. **PoC（捨てるコード。`eval/scripts/` か scratchpad）**: 分割ダンプの 1 ファイル（全量は取らない）から §2.2 の手順で一覧を作り、§6.1 を測る。続けて 2・4 ファイル。ダンプは scratchpad に置き、`data/raw` と `data/build/dict` は触らない。結果を eval/reports に書き、この ADR に追記して、F2〜F5 の範囲と W2 に広げるかをユーザーに聞く。
3. **契約のコミット**（§5）。
4. **並行実装**: レーン A（収集）と B（絞りと行の生成）を worktree で並行。C（ビルドの組み込み）は B の後。既定は「一覧がなければ今と同じ」で入れる。
5. **掃引**（§6.2〜6.3）。結果を eval/reports に。
6. **採る値を既定にする PR**: 一覧のファイル、`THIRD_PARTY_NOTICES.md` の節、値（ユーザーの確認の後。PR に明示）。辞書を作り直してインストール。

## 8. 懸念点

- **英語由来の読みの揺れ**: Wikipedia の表記（バージョニング）と、ユーザーが打つ読み（ばーじょにんぐ / ゔぁーじょにんぐ）がずれると、足した語に届かない。機械の変換では読みは表記の 1 通りだけなので、書かれていない揺れは拾えない。K1 が保険になる。
- **表記の誤り・まれな揺れ**: 誤字や個人の揺れも、df の下限を超えれば入る。下限と F3 で抑え、混入率で測る。
- **固有名詞のすり抜け**: カタカナの人名・地名・種名は Wikipedia に非常に多い（カタカナのタイトルの約 58% が辞書になく、そのほとんどが固有名詞）。F4 の効きが足りないと、方針 2 を守れない。F4 は PoC で効きを測ってから採り、足りなければ一覧を小さくする（下限を上げる）側に倒す。
- **連なりの切り方**: 「・」を使わない複合語（セマンティックバージョニング）は 1 つの連なりになる。部分の語（バージョニング）が単独で書かれていなければ拾えない。形態素解析に頼らずに部分に分ける方法がないので、今は入れない。PoC で、連なりの中にだけ出る語がどれだけあるかを数える（推測では多くない）。
- **ライセンスの解釈**: 語と頻度の一覧が CC BY-SA の継承の対象になるかは断定しない。ファイル単位で CC BY-SA 4.0 と表示する安全側の扱い（§2.7）でも、Apache-2.0 のリポジトリに別のライセンスのファイルが入ることになる（Q2）。辞書の一式を配るとき（#99）に、system.dict にも表示が要るかは R2 で確かめる。
- **文体の偏り**: 百科事典の文体なので、日常やチャットの外来語（新しいスラング）は薄い。#113 の対象（IT の普通名詞）に足りるかを再現率で確かめる。
- **K1 との重なり**: 本 ADR で語が辞書に入ると、K1 の対象（辞書にない語）が減る。両方の既定値を決めるときは、片方を固定して測り直す（§6.2）。
- **ダンプの処理**: ウィキの記法の除去を自前で書く（外部の道具のライセンスを持ち込まない）。完全な除去は難しいので、テンプレートの名前や表の断片が連なりとして混ざる恐れがある。混入率で測る。

## 9. ユーザーに聞くこと

- **Q1. 出どころを Wikipedia 日本語版の本文（ダンプ）にしてよいか。PoC は分割ダンプの一部から始め、全量は再現率の伸びを見てから決める。** 推奨: はい。Common Crawl は権利と量の扱いが重く、タイトルだけはほとんど固有名詞で、既存の生成物はライセンスか読みに問題がある（§3）。
- **Q2. 語の一覧（表記、tf、df）をリポジトリに置き、ファイル単位で「Wikipedia 日本語版をもとに作成、CC BY-SA 4.0」と表示してよいか。** 推奨: はい。利用者がダンプを取らずに済み、表示は安全側にする。代わりの案は、一覧を Release に置いて `fetch-data.sh` で取る形（ADR 0033 の型。リポジトリにライセンスの違うファイルが入らないが、取得元が 1 つ増える）。
- **Q3. 混入率の判定（抜き取った語を「普通名詞 / 固有名詞 / 非語」に分ける）を、エージェントが下書きし、ユーザーが抜き取りで確かめる形にしてよいか。標本の大きさは PoC の分布を見てから提案する。** 推奨: はい。判定は人の判断が要るので、下書きと確認を分ける。新しい評価セット `webwords.tsv` の期待も同じ場で確かめる。
- **Q4. 既知のカタカナ語だけでできた連なり（マイクロサービスアーキテクチャ）を足すか。** 推奨: PoC で「足したときに 1 位が変わる割合」を測ってから決める。今の見込みは「足さない」（今でも辞書の経路で出せる語で、一覧が膨らむため）。
- **Q5. 一覧の作り直しを、Sudachi の版を上げるときに合わせてよいか。** 推奨: はい。毎回のダンプは追わない（評価の手間に見合わない）。

## 10. 決定（2026-10-29 ユーザー承認）

- §0.4 の方針 1〜3 は承認済み。
- Q1〜Q5 は、すべて推奨どおり承認（出どころは Wikipedia 日本語版の本文。一覧は表記・tf・df をリポジトリに置き CC BY-SA 4.0 と表示。混入率の判定はエージェントが下書きしてユーザーが抜き取りで確認。既知語だけの連なりは PoC で測ってから決める。一覧の作り直しは Sudachi の版上げに合わせる）。
- 条件: **配布物に入れる前に、§11 R2（CC BY-SA と GFDL の帰属の書き方、著作権法 30 条の 4）を一次情報で確かめる。** 確かめるまでは、一覧を PoC の作業用に使うだけで、リポジトリにも配布物にも入れない。

## 12. 改訂（2026-10-29。R2 の結果と、Q2 の変更）

R2（Wikipedia 由来の語の一覧の権利。法的助言ではない）を一次情報で確かめた。

**分かったこと**
- 著作権法 30 条の4 の2号（情報解析）は、大量の情報から言語の要素を抽出して解析する利用を認める（e-Gov 法令 API で条文を確認）。ただし書きは「著作権者の利益を不当に害することとなる場合は除く」。語の頻度表を作る**作成**は、これに当たりうると読める。
- Wikimedia 利用規約 §7: 本文は CC BY-SA 4.0 と GFDL の併記で、再利用者は片方を選べる。帰属は、記事へのリンク、安定した複製へのリンク、執筆者の一覧のうちから選べる。同じ節に「寄稿した事実は帰属表示なしで自由に再利用される」とある。
- CC BY-SA 4.0 の第4条は、データベース権の対象になる場合、内容の実質的な部分を含む自分のデータベースを翻案物とする。
- 先行例: jawiki-kana-kanji-dict は生成物を MIT で配る（作者が「軽微利用」と考えると明記。個人の見解）。mozcdic-ut-jawiki は CC BY-SA と表示する。

**確認できなかったこと**
- 配布が 30 条の4 に含まれるか（文化庁の解説 PDF の本文を読めなかった）。
- 語の一覧が複製・翻案にあたるかの公的な見解や判例。
- ShareAlike が、一覧を使って作った辞書（system.dict）のバイナリに及ぶか。

**決定（2026-10-29 ユーザー承認）**
- **Q2 を変更する: 語の一覧は、リポジトリに置かず、Release の資産として置く**（ADR 0033 の型。`fetch-data.sh` で取る）。ライセンスが混ざる範囲を Release の資産だけにして、リポジトリ全体の Apache-2.0 を保つ。表示は §2 のとおり CC BY-SA 4.0 とし、帰属を `THIRD_PARTY_NOTICES.md` に書く。
- §2 の「置き場所はリポジトリ」は、この節で上書きする。
- 一覧と辞書の継承の問いは、確認できていない。配布物（Release、ビルド済みバイナリ）に入れる前に、残る問いを §10 の条件として再び確かめる（PoC の間は作業用に使うだけ）。

## 補足（2026-11-06）

- 判定できない語の方針（固有名詞は区分つきで入れる、迷う語は入れない）、判定の規則、コストの掃引、配布と生成のパイプラインは [ADR 0054](0054-web-words-classify-and-build.md) に決めた。本 ADR の §0.4 方針 2、§2.3 F4、§2.5、§5.1 は 0054 で上書きする。
- 訂正（0054 §9）: §0.1 の Mozc の記述は、README が「辞書を Web のデータの処理で作った」とだけ書くもので、カタカナ語に限る記述も Wikipedia の記述もない。§12 の「jawiki-kana-kanji-dict は生成物を MIT で配る」は誤りで、ライセンスの表示は CC BY-SA へのリンク。
