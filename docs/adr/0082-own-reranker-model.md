# ADR 0082: 独自の AI モデルの役割、合格の基準、撤退の条件

- 状態: 提案（中間の関門の不合格の線と §4 の撤退の扱いは 2026-11-26 のユーザー決定。§7 の質問は未回答）
- 日付: 2026-11-26
- 対象: LM（`lm/`、`engine/`）、評価（`eval/`）、版の節目（#99）。この ADR ではコードを変えない
- 前提: [ADR 0003](0003-topic-ranker-decision.md)（zenz-v3.2 small を使う）、[ADR 0072](0072-lm-cage-levels.md)（LM の檻）、[ADR 0080](0080-bundle-model-and-dictionary.md)（モデルと辞書の同梱）
- 判断の置き場所: 評価と合否の測定は Rust（`ikari-eval`）。合否の決定はユーザー
- 関連: #99、#97、#159、#440

## 1. 背景

- このソフト専用の独自の AI モデル（今より小さいモデル。別のリポジトリで作る）を組み込めたら 1.0.0 とする（2026-11-25 ユーザー決定）。
- 何ができれば「組み込めた」と言えるか、できなかったらどうするかが決まっていない。これが無いと、モデルを待って止める issue を決められず、止めたものを再開する条件も無い。
- このリポジトリに書くのは、役割、境界、合格の基準、撤退の条件だけとする。モデルの構造と学習の方法は、別のリポジトリで扱う（2026-11-26 ユーザー決定）。

## 2. 決定: 役割と境界

- 独自モデルは、今の LM と同じく、**辞書から作った候補の並べ替えだけ**を担う。候補を作らず、補完せず、読みに対応しない文字を足さない（spec「基本原則」）。
- 候補の生成（辞書、文節の区切り、連接、学習、ユーザー辞書）は今のまま。**辞書に無い語、区切りの誤り、連接のコストが原因の誤変換、候補の不足は、独自モデルでは直らない。** これらはモデルを待たずに直す。
- 処理はすべて手元で行う（通信しない）。
- 今の LM の呼び出しの口（[`lm/src/scorer.rs`](../../lm/src/scorer.rs) の `LmScorer`: 前置きと候補の列を渡し、候補ごとの点を受ける）を出発点にする。口の形を変える必要が出たら、別の ADR で決める。
- モデルを動かす部品を替える場合の、檻（ADR 0072）の要否と依存の増減は、その部品が決まった時点の ADR で決める。この ADR は、檻や llama.cpp が不要になる前提を置かない。

## 3. 決定: 合格の基準

比べる相手は、**今の zenz-v3.2 small**。同じコード、同じ辞書、同じ評価の入力、学習なしで測る。

**合格は、数値の線ではなく総合判断とする。** 数値で決めるのは不合格の線だけで、不合格でないことは、合格を意味しない（2026-11-26 ユーザー決定）。判定は 2 回行う。

1. **中間の関門**: 続けるか打ち切るかを決める（§3.1）。時期は、モデルを作り始める前に決める。
2. **組み込みの判定**: 製品に組み込み、1.0.0 の対象にするかを決める（§3.2）。

どちらも、測った数値をユーザーが見て決める。**独自モデルの結果を見てから、線を動かさない。**

### 3.1 中間の関門の不合格の線

測る値:

- **精度の変化**: 1 位の正解数の割合が、zenz に対して何 % 変わったか（zenz の正解率が 80% なら、10% の低下は 72%、20% の低下は 64%）。割合を数える評価の入力は §7 Q4。
- **速度の変化**: LM 1 回の時間の p99 が、zenz に対して何 % 短くなったか（zenz が 100ms なら、30% の向上は 70ms、10% の低下は 110ms）。

| 精度 ＼ 速度 | 30% 以上の向上 | 0% 以上 30% 未満の向上 | 10% 未満の低下 | 10% 以上の低下 |
| --- | --- | --- | --- | --- |
| 10% 以上の向上 | 総合判断 | 総合判断 | 総合判断 | 不合格 |
| 0% 以上 10% 未満の向上 | 総合判断 | 総合判断 | 総合判断 | 不合格 |
| 10% 未満の低下 | 総合判断 | 総合判断 | 不合格 | 不合格 |
| 10% 以上 20% 以下の低下 | 総合判断 | 不合格 | 不合格 | 不合格 |
| 20% を超える低下 | 不合格 | 不合格 | 不合格 | 不合格 |

表のもとになる条件:

- 精度と速度の両方が低下したら不合格。
- 精度が 10% 以上低下し、速度の向上が 30% 未満なら不合格。
- 精度の低下の下限は 20%、速度の低下の下限は 10%。どれだけ片方が良くても、これを超えて悪くなれば不合格（速度は 10% ちょうども不合格）。

測定の揺れの幅（「低下」と数え始める大きさ）は、今の zenz を測るときに決める。

### 3.2 組み込みの判定

- 不合格の線は、§3.1 と同じ形にし、**数値は中間の関門の結果を見てから決める**（2026-11-26 ユーザー決定）。
- 総合判断で見るもの: 下の表。

| 見るもの | 内容 |
| --- | --- |
| 精度 | `eval/sets/` の全セットと AJIMEE-Bench の 1 位。悪化した例と改善した例の全件 |
| 文法の守り | 否定と文法の例は 100%（今の受け入れ条件と同じ） |
| 過学習でないこと | 学習に使わない評価の入力での 1 位（§7 Q2） |
| 速さ | 製品の締め切りでの時間切れの割合、1 回の p99 と最悪値（NFR-06）、冷えた最初の 1 回 |
| 機械 | macOS は基準機（NFR-07）。Windows は CPU でも測る（§7 Q3） |
| 大きさ | 配るファイルの大きさと、読み込んだときのメモリ。zenz より小さいこと |
| 利用条件 | 重み、初期値、学習データ、教師の出力。配布物に同梱して再配布でき、条件を THIRD_PARTY_NOTICES に書けること |

- 学習のデータには、`eval/sets/` と AJIMEE-Bench の文を入れない。入れていないことを、確かめられる形で示す。
- 利用者の入力や学習の記録は、学習のデータにも評価にも使わない。

## 4. 決定: 不合格のとき

- **1.0.0 は未定義とする**（2026-11-26 ユーザー決定）。今の zenz のまま 1.0.0 とする道は、この ADR では置かない。
- **Windows 版の公開は 0.2.0**（独自モデルの結果に依存しない）。
- 配布は、zenz を同梱した 0.x で続ける（ADR 0080 のレーンは、独自モデルがあってもなくても要る）。
- 作り直すか、やめるかは、そのときの数値を見てユーザーが決める。

## 5. 待つ間に止めるもの、止めないもの

**止めない**

- 辞書、区切り、連接、候補の生成の修正（§2 のとおり、モデルでは直らない）
- 評価の仕組みと評価の入力（合否の判定に要る）
- 遅延の原因の測定と、端末ごとの性能の予算（#97、#159 の切り分け。基準の線の材料になる）
- 配布（ADR 0080）と 0.2.0 の Windows に要るもの（vc_redist を含む。0.2.0 は今の LM の構成で出す）
- セキュリティの対応（LM の檻を含む。今の版の利用者に関わる）
- 入力、画面、学習、ユーザー辞書

**止める候補**（組み込みの判定か打ち切りまで、新しく始めない）

- zenz や llama.cpp に固有の、大きい改修や速さの作り込み（不具合の修正は除く）
- zenz の別の大きさの評価（#440）、モデルを選ぶ機能の拡張（ADR 0060 の自由指定）
- NPU など、特定の装置向けの加速の実装

個々の issue の振り分けは、この ADR の承認のあとに行う。

## 6. 検討した案

| 案 | 採らない理由 |
| --- | --- |
| 基準を決めずに作り始める | 合否が後付けになる。止めた issue を再開する条件が無い |
| 不合格なら zenz のまま 1.0.0 | 1.0.0 の節目の決定（2026-11-25）と合わない。不合格のときの 1.0.0 は、今は決めない |
| モデルの構造や学習の方法もこの ADR に書く | 別のリポジトリで扱う（§1） |

## 7. ユーザーに決めてもらうこと

- **Q2. 学習に使わない評価の入力**: 推奨は「リポジトリに置かない評価の入力を新しく作り、モデルを作り始める前に固定する」。公開している `eval/sets/` だけでは、混入を見分けにくい。
- **Q3. Windows の速さを測る機械**: 推奨は「開発用の VM は下限の目安にとどめ、合否は GPU なしの実機の CPU 1 台で測る」。機械はユーザーが指定する。
- **Q4. 精度の割合を数える評価の入力**: セットによって LM の効き方が大きく違い、同じ % でも重さが変わる。今の zenz と LM なしを入力ごとに測ってから提案する。

## 8. 次にすること

1. 今の zenz-v3.2 small を、§3 の軸で測り、レポートを `eval/reports/` に置く。
2. その数値をもとに、§7 Q4 の入力と測定の揺れの幅を提案する。
3. 承認のあと、open の issue を §5 で振り分ける。
