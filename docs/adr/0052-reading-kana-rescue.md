# ADR 0052: 読みそのままの平仮名と片仮名を、並べ替えのあとで 30 位以内に引き上げる（救済）

- 状態: 採用（2026-11-05 ユーザー決定。§の「ユーザーに聞くこと」3 点はすべて推奨どおり。実装までリードに任せる）
- 日付: 2026-11-05
- 対象: `core/src/converter/conversion.rs`（最初のプールの並べ替えのあと）、`core/src/converter/segment.rs`（`pin_first` のあと）、`core/src/converter/options.rs`（上限の項目と `--ranker-config` の入口）、`core/src/converter/tests.rs`、`core/src/converter/segment_tests.rs`、`eval/sets/kana-rescue.tsv`（新規）、`eval/scripts/snapshot.sh`（セットを足すだけ）。Ranker（`lm/`、学習）、辞書、ラティス、shell-core、Swift は変えない
- 前提: main = dfc32fb。ADR 0048 §2-2・§4・§7（プールの並びと LM の採点上限、かなの固定 2 件）、ADR 0037 §11・§12（K1 を採らなかった経緯）
- タスク: #207（ばーじょにんぐ で、平仮名が 32 位、片仮名が 30〜32 位）
- ユーザーの決定（2026-11-05）: **並べ替えのあとの引き上げ（案 B）**で行う。読みそのままの平仮名・片仮名が **30 位より後ろにあるときだけ** 30 位に引き上げ、30 位以内にあるものは順位をそのままにする。LM の並びが主で、救済は最後の手段。「バー叙任具」を出さない対策は #113（語彙の追加）で、ここには含めない
- 判断の置き場所: Rust の core（`Conversion` が候補の順位を持つ。`pin_first` と同じ層）。OS の API も UI も関わらない

## 0. 現状の把握

- 最初の変換は `build_first_pool` で、A* の 30 件 → 予約枠 → Rewriter → ひらがな → カタカナ → 英字の置き換え の順にプールを作り、`rank_and_append` で Ranker（文法、学習、話題、LM など。`CompositeRanker`）に渡し、score の安定ソートをして `generated` の末尾に足す。続きのページ（`extend_chunk`）は 9 件ずつ別に rank する。
- ひらがな・カタカナの候補のコストは「A* の先頭 30 件の最大 + 1」（`KANA_COST_BASIS_POOL`。ADR 0048 §4）。LM なし（または時間切れ）では、プールが 30 件を超える読みで、かなはほぼ 31・32 位に来る。
- 読みそのままの平仮名・片仮名は、表記がほかの候補と重ならない限り**必ず最初のプールに入る**（`seen` に無ければ足す。重なったときは、同じ表記の辞書の候補が既にプールにある）。続きのページには来ない。
- LM の採点上限は、明示しなければプール全体（`pool_size + word_reserve + 2`。ADR 0048 §2-2、§7 の固定 2 件）。かなは既定で LM の集合に入っている（#207 の 2026-11-05 の測り直しで確認済み）。
- 文節のモードは文節ごとに `build_first_pool` を通り、その後に `pin_first`（元の表記を 0 番に置く。再変換も同じ）が `generated` の先頭に 1 件を入れる。
- ADR 0037 の K1（未知語のカタカナのコストを読みの長さで下げる）は、守る側を壊さずに ばーじょにんぐ を動かせず、採らなかった（§12）。

## 1. 問題の定義

- ばーじょにんぐ（文脈なし、LM あり）で、片仮名が 30 位、平仮名が 32 位。辞書にない長い外来語では、誤った複合の候補（バー叙任具 など）が 30 件を埋め、読みそのものが 4 ページ目の後ろに押される。LM は効いているが、誤った複合に勝てない。
- 読みそのままの平仮名・片仮名は、どんな読みでもユーザーの入力そのもの（入力を正とする）で、選べる場所に必ずあるべき。ただし 1 ページ目である必要はない（ユーザー確認）。
- 本質は「LM の並びの結果に、読みそのものの最低の位置の保証がない」こと。コストで競わせる道（K1）は守る側を壊すと分かっているので、並びの結果に対する位置の規則で保証する。

## 2. 決定の要約（提案）

1. **対象**: 表記が「読み（`lattice.key()`。正規化済みのひらがな）」と同じ候補と、「読みをカタカナにしたもの（`hiragana_to_katakana`）」と同じ候補。origin は問わない（辞書の候補が同じ表記なら、それが対象）。
2. **いつ**: 最初のプールを rank して並べたあと、`generated` に足す前（学習・LM を含む Ranker の結果のあと）。上限を `N`（既定 30）とし、対象が `N` 位（1 始まり）より後ろにあるときだけ動かす。`N` 位以内にあるものは動かさない（§3）。
3. **どこへ**: 動かす対象が k 件（1 か 2）なら、`N - k + 1` 〜 `N` 位に差し込む。そこにいた候補とその後ろは、k 位ずつ後ろにずれる。**押し出された候補は消さない**（31 位、32 位に移るだけ）。
4. **両方が後ろにあるとき**: 2 件を `N - 1` 位と `N` 位に、**rank のあとの相対順（LM の並び）のまま**置く（§3.2）。
5. **片方だけが後ろで、もう片方がちょうど `N` 位にあるとき**: 後ろの 1 件を `N - 1` 位に入れる（`N` 位の対象を押し出さない）。
6. **score は書き換えない**。位置だけを変える（score の意味を「Ranker の点」のまま保つ）。
7. **上限 `N`** は `ConvertOptions` の項目にし、既定 30 は固定の定数。`--ranker-config` の `convert.kana_rescue_rank` で評価と切り戻しのために変えられる（0 = 無効）。設定画面・`settings.tsv` には出さない（§4）。
8. 文節のモードと再変換でも、文節ごとに同じ規則をかける。`pin_first` のあとにもう一度かける（§6）。
9. Ranker、LM の採点の対象と順、学習の記録は変えない。

## 3. 引き上げの規則

### 3.1 手順（`generated` に足す前の、並べ終えた最初のプール `pool` について）

1. `pool` の中で対象（平仮名・片仮名）の位置を探す。位置が `N` 以下なら、その対象は「範囲内」。`N` より大きければ「後ろ」。
2. 「後ろ」の対象が無ければ何もしない（大半の読み。プールが `N` 件以下の読みもここ）。
3. 「後ろ」の対象を `pool` から取り除く（相対順を保つ）。
4. 差し込む位置（0 始まり）を `N - k` にする（k = 取り除いた件数）。ただし、その位置から `N - 1` までに「範囲内」の対象があるときは、その数だけ前にずらす（§2-5。k = 1 で、もう片方がちょうど `N` 位にある場合だけ起きる）。
5. 取り除いた対象を、その位置に相対順のまま差し込む。

この規則は冪等（もう一度かけても変わらない）。`N` 位より前の候補は、位置 `N - k` より前なら一切動かない。

### 3.2 両方が後ろにあるときの順序

| 案 | 内容 | 判断 |
|---|---|---|
| **R1 rank のあとの相対順のまま** | LM（または学習・コスト）が上に置いた方を `N - 1` 位に | **採る（推奨）**。LM の並びが主という決定に合う。外来語の読みでは片仮名が上に来ることが多い |
| R2 平仮名 → 片仮名の固定 | 常に平仮名が `N - 1` 位 | 採らない。LM の判断を捨てる理由がない |
| R3 片仮名 → 平仮名の固定 | 外来語を想定して片仮名を先に | 採らない。和語の読みで平仮名の方が自然な場合を捨てる |

### 3.3 押し出された候補

- 位置 `N - k + 1` 〜 `N` にいた候補は、`N + 1` 〜 `N + k` 位に移る。プールから消さず、`seen` もそのまま。
- 1 ページ 9 件の既定では、29〜32 位はどれも 4 ページ目（28〜36 位）なので、**見えるページは変わらない**。`page_size` を変えた利用者では、ページの境目をまたぐことがある（受け入れる。押し出しは最大 2 位）。

## 4. 30 という数の扱い

- 30 はユーザーが要件として決めた数（#207。「30 位以内」）で、掃引で決める重みではない。「値は計測で決める」の対象は、精度と時間の兼ね合いを持つ値（加点、閾値、時間切れ）で、ここは要件の値である。ただし §7 で「動いた件数と、29・30 位から押し出された候補」を数えて報告し、ユーザーが数字を見られるようにする。
- `KANA_COST_BASIS_POOL`（かなのコストの基準の 30 件）とは別の定数にする。意味が違う（片方はコストの基準、片方は位置の保証）ので、片方を変えたときにもう片方が動かないように。
- 設定画面に出さない理由: 利用者が決める値ではなく、要件の値。`--ranker-config`（評価と切り戻し用）で足りる。ADR 0048 の `pool_size` と同じ扱い。
- `N` を `pool_size` より大きくしても害はない（プールが `N` 件以下なら何もしない）。`N` を小さくすると、最初の画面のかなを強く押し上げる「補完に近い」動きになるので、既定は 30 から動かさない。

## 5. 基本原則との整合

- **候補は辞書から作り、LM は並べ替えにだけ使う**: 候補を足さない（かなは今も必ずプールにある）。LM の点も採点の対象も変えない。救済は LM ではなく、LM の並びのあとにかける位置の規則で、上位 `N - k` 件の LM の判断には触れない。
- **入力を正とする / 補完をしない**: 平仮名・片仮名は入力そのもので、読みに無い文字を足さない。救済は「入力そのものを、選べる場所に必ず置く」ためのもので、入力の結果を変えない（ユーザーが選ばなければ確定されない）。1 位や 1 ページ目には上げない（思考を止める誤った 1 位を作らない）。
- **学習は支援であって決定ではない / 学習で上げた候補を下げない**: Ranker のあとにかけるので、学習で `N - k` 位より上に上げた候補は動かない。学習で上げた候補がちょうど 29・30 位にあるときだけ、最大 2 位下がる（同じ 4 ページ目の中）。学習でかなを選んできた利用者では、かなは既に上にあるので救済は働かない。救済で動いたことは学習に記録しない（確定のイベントは今のまま `generated[index]` の候補）。
- **こまめに確定（長文のために複雑にしない）**: 数十件の並びに対する O(件数) の処理で、時間は無視できる。

## 6. ほかの場面での扱い

| 場面 | 扱い |
|---|---|
| ページ送り（`extend_chunk`） | かけない。かなは最初のプールにしか来ないので、最初のプールで保証が終わる。`generated` は返したあとに変えないという約束（`page` の説明）も守られる |
| 文節のモード | 文節ごとの `build_first_pool` で、その文節の読みについてかける。`pin_first` が先頭に 1 件を入れて 30 位のかなを 31 位に押すことがあるので、`pin_first` のあとにもう一度かける（冪等なので二度かけて問題ない）。`pin_first` で 0 番にした候補は動かない（差し込みは `N` 位の近くだけ） |
| 再変換 | 文節のモードと同じ経路（`pin_first` で元の表記を 0 番に）なので、同じ扱い |
| LM の時間切れ・LM なし | 同じ規則。かなは 31・32 位に来やすいので、プールが 30 件を超える読みでは、ほぼ毎回 29・30 位に動く（見えるページは変わらない。§3.3） |
| secure（パスワード欄など） | 変わらない（学習しないだけで、候補の並びの規則は同じ） |
| 英字の置き換え・Rewriter | 対象外（読みそのものではない）。押し出される側にはなりうる |

## 7. 評価

1. **新しいセット** `eval/sets/kana-rescue.tsv`: 読みごとに、期待を平仮名にしたケースと片仮名にしたケースの 2 行を持つ（`ikari-eval` は期待の表記の順位を出すので、両方の順位が取れる）。
   - ばーじょにんぐ（文脈なし、文脈「APIの」。ADR 0037 §6.4 と同じ公開の一般的な文）。
   - 同じ型の公開の語を数件。見つけ方は issue185 のセットと同じ: 辞書にない外来語の長い読み（katakana-like.tsv、new-words.tsv の読みと、Sudachi にない一般的な IT の語）を `ikari-eval --ranker full`（LM なし・学習なし）で流し、かなが 30 位より後ろのものを選ぶ。不自然な語・個人的な文は入れない。
   - 合否は 1 位ではなく **順位が 30 以下**。セットのヘッダにそう書き、snapshot の 1 位の集計とは別に、順位の列で確かめる（`max_rank` の既定 50 で足りる）。
2. **流し方**: (i) LM なし、(ii) LM あり締め切り 3000ms（時間切れ 0）、(iii) LM あり実機の締め切り。学習なし（評価に実機の学習を含めない）。
3. **全セットで 1 位が悪化しないこと**: `eval/scripts/snapshot.sh --compare <main>`（LM あり・なし、`--ajimee`）。規則上 1 位は動かない（`N` = 30 なら 1〜28 位は動かない）ので、1 位の悪化は 0 件のはず。1 件でも出たら実装の誤り。
4. **順位の変化を数える**: 全セットで、期待の順位が 29・30 位から 31・32 位に下がったケースの数と、かなが動いたケースの数を報告に出す（押し出しの実害を数字で見る）。
5. 結果は `eval/reports/kana-rescue-<日付>.md` に置き、索引に足す。

## 8. 検討した案

| 案 | 却下の理由 |
|---|---|
| A かなのコストを上げる（基準を「最大 + 1」より前に） | ADR 0037 の K1 と同じ道で、LM なしの並びを全体に動かし、守る側を壊す。1 ページ目を 1 枠使う読みが出る。ユーザーが案 B を選んだ |
| Ranker の最後の段に置く（score を「30 位の score − 1」にする） | 並びの位置は `Conversion` が持つ（`pin_first` と同じ）。Ranker は塊の点を付ける役で、位置の保証を持たせると、塊ごとの rank（続きのページ）で意味を持たない規則が Ranker に入る。score を書き換えると、score の意味（Ranker の点）が崩れ、表示・調査で読み違える |
| 1 ページ目（9 位以内）まで上げる | ユーザー確認で不要（30 位以内でよい）。補完に近く、誤った 1 ページ目の枠を作る |
| かなを常に 30 位に置く（範囲内でも動かす） | ユーザーの仕様の追記に反する（30 位以内なら順位はそのまま） |
| 続きのページにもかける | かなは最初のプールにしか来ないので不要。返したページを変えない約束にも触れる |
| 救済した候補に印（新しい項目）を付ける | 使う所が無い（YAGNI）。調査はかなの origin と順位で足りる |

## 11. 懸念点

- `zenz.max_candidates` を明示して小さくした場合（評価と切り戻し用）、プールの並びでかなは後ろの方（予約枠、Rewriter のあと）なので、LM の採点から外れうる。既定では外れない（§10 のテストで守る）。明示の上書きは実験用なので、これを保証の対象にしない。
- 29・30 位の候補（学習で上げたものを含む）が最大 2 位下がる。既定のページの大きさでは同じページの中（§3.3）。
- 1 位の誤り（バー叙任具）は直らない。#113 で扱う。
- `generated` が score の昇順でなくなる（29・30 位の score が 31・32 位より小さいことがある）。score の昇順を前提にしている所が無いか、実装で確かめる（調べた範囲では、`generated` を並べ直す所は `pin_first` だけ）。

## 12. ユーザーに聞くこと

1. **両方が 30 位より後ろのとき、29・30 位に LM の並びの順のまま置く**（R1）でよいか。推奨: R1。平仮名を先、片仮名を先と固定する理由がない。
2. **30 は既定の定数とし、`--ranker-config` の `convert.kana_rescue_rank` で変えられる（0 = 無効）が、設定画面には出さない**、でよいか。推奨: はい（要件の値で、利用者が決める値ではない。掃引はせず、§7 で動いた件数を報告する）。
3. **文節のモードと再変換でも、文節ごとに同じ救済をかける**、でよいか。推奨: はい（「どんな読みでも」の要望に合い、短い文節では 30 件を超えずほぼ働かない）。
