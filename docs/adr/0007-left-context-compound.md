# ADR 0007: 左文脈の最後の語と候補が1語の複合語になるときの加点

- 状態: 承認（2026-10-13。§12.1 を参照）
- 日付: 2026-10-13
- 対象: core の `LeftContextRanker`（`core/src/ranker/left_context.rs`）。tasks.md の B3（「化」が助詞の「か」に負ける）のうち文脈のあるもの、B4（器／機、板／版、次／時）。ユーザーが「案 A」として設計を承認したもの
- 根拠: [eval/reports/phase3-context-compound.md](../../eval/reports/phase3-context-compound.md)（本 ADR のスパイク）、fix/suffix-ka のレーンのレポート phase3-suffix（未マージ。原因の測定 §2.3、案 B の測定 §6）
- 前提: main = f9ebf3a。ADR 0002 §22（LeftContextRanker の導入）、ADR 0003 §3.1（追認）・§3.2（GrammarGuard）、ADR 0006 §16.5（読みの逆引き表）。LM なしのコンテナで測った

---

## 0. 現状の把握

### 0.1 起きていること
確定した語のあとに、接尾の1文字を打つと、同じ読みの別の漢字が1位になる（LM なし、`ikari --context <文脈> <読み>`）。

| 文脈 + 読み | 1位 | 期待（順位） |
| --- | --- | --- |
| 洗濯 + き | 器 | 機（9位） |
| 最新 + ばん、日本語 + ばん | 板 | 版（2位） |
| 午後三 + じ | 次 | 時（2位） |
| 自動 + か | 家 | 化（3位） |

### 0.2 原因（phase3-suffix §2.3 で測った）
- 決めているのは `LeftContextRanker`。左文脈の最後の語から候補の最初の語への連接コストのうち、絶対値が 1000 を超えた分を 4 倍にして足し、1候補あたり ±6000 で止める（ADR 0002 §22）。**名詞で始まる候補は増幅しない**（同音異義語の名詞どうしを乱さないため）。
- 器・板・次・家 は Sudachi の品詞が `接尾辞` なので、名詞のあとの連接（-4895 など）が増幅されて上限の -6000 が付く。機・版・時 は `名詞,普通名詞,助数詞可能` で、増幅されない（0）。経路のコストだけなら、3 件とも期待の方が1位。
- 同じ働き（名詞に付く1文字の漢字）が、品詞の分け方の違いだけで最大 6000 の差になっている。辞書のポリシー（語ごとの加算）では、文脈のない入力まで同じだけ動くので直せない（phase3-suffix §2.3）。

### 0.3 手がかり
洗濯機、最新版、自動化 はどれも辞書に1語の項目がある。洗濯器、最新板、自動家 はない。**左の語と候補をつないだ表記が辞書の1語になるか**は、品詞の分け方によらない手がかりになる。

### 0.4 コードの現状（設計に効く事実）
- `RankInput` は `analysis.tokens`（左文脈の解析結果。表記、語ID、品詞）と `dict`（`Dictionary`）を持つ。
- `Dictionary::common_prefix_search_surface` で表記から項目を引ける（32 文字以下）。`DictionarySet` はシステム辞書とユーザー辞書の両方を引く。`InMemoryDictionary`（ユーザー辞書）も実装している。
- `Dictionary::reading(id)` は語の読みを返す。システム辞書は逆引き表（約 32.5 MiB、release で 0.11〜0.18 秒）を最初の呼び出しで作る（`OnceLock`）。エンジンは起動のあとに裏で作る（`warm_reading_index`。ADR 0006 §16.5）。
- `CompositeRanker` は `left_context` の差分を「文法の差分」として数える。負の差分を受けた候補は GrammarGuard の「文法候補」になり、内容語（話題など）の加点で追い越されない。LearningGuard では「文脈の証拠」になり、学習の文脈に依らない加点で覆されない。

## 1. 決定の要約

| 項目 | 決定 |
| --- | --- |
| 置き場所 | `LeftContextRanker` の中に、連接の増幅のあとの段として足す（新しい Ranker は作らない）。§2 |
| 当てる条件 | 左文脈の最後のトークンが名詞で、候補が1つの辞書の語で、`左の表記 + 候補の表記` が辞書の1項目（名詞,普通名詞 か 地名）の表記と一致し、その読みが `左の語の読み + 候補の読み` と一致する。§3.1 |
| 当たった複合語が複数 | cost + penalty がいちばん小さい複合語と同じ lemma の候補だけに加点する。§3.2 |
| 加点 | 連接の差分を上限（-6000）まで引き上げたうえで、さらに `compound_bonus`（3000）を足す。§3.3 |
| 複数の語に分かれた候補 | 対象にしない（測った悪化が大きい）。§5 |
| 速さ | Ranker の 1回が p99 4 µs → 25 µs。変換の p99 予算 2 ms に対して無視できる。§4 |
| 学習、ユーザー辞書 | 学習の記録は変えない。ユーザー辞書の語にも同じ規則が効く。§6 |
| 案 B（LeftContextRanker の名詞の除外を変える） | 採らない。§9 |

スパイクの結果（LM なし。最終形、`compound_bonus` 3000）: katakana-suffix 128 → **131**（改善 3、悪化 0）、homophones-ext dev 776 → **778**、test 197 → **198**（改善 3、悪化 0）、homophones / hiragana / segments / シナリオ / CLI golden は変化なし。セットにない入力 135 件で、1位が期待に変わったもの 34 件、悪くなったもの 2 件（§7）。

## 2. 置き場所

**`LeftContextRanker` の中に置く。** 理由:
- 手がかりは「左文脈の最後の語」で、連接の増幅と同じものを見る。左文脈がない、secure、文頭（BOS が `bos_eos_id`）で働かないという前提も同じ。
- `CompositeRanker` が `left_context` の差分を文法の差分として数えるので、複合語の加点も GrammarGuard と LearningGuard の「文脈の証拠」になる（§6.1）。別の Ranker にすると、Guard の分類（`GRAMMAR_RANKER`）を2つに広げる変更が要る。
- 同じ候補に対して「連接の差分を上限まで引き上げる」（§3.3）には、連接の差分と同じ場所で計算する必要がある。

設定は `left_context.compound_bonus`（既定 3000。0 で無効）を足す。ほかの条件（品詞、読み）は規則としてコードに固定し、つまみにしない（ADR 0002 §20 の「汎用の規則言語を作らない」と同じ考え）。

## 3. 規則

### 3.1 当たる条件
左文脈の解析結果の最後のトークンを `left`、候補を `cand` とする。次をすべて満たすとき、`cand` に複合語 `C` が当たったとする。

1. `left` の品詞1が `名詞`（固有名詞を含む。代名詞は品詞1が別なので含まない）。
   - **[ADR 0029 で改訂]** 品詞が `形状詞,一般` か `形状詞,タリ` の語も `left` に数える（最適 + かい → 最適解）。`形状詞,助動詞語幹` は数えない。
2. `cand.origin == Dictionary` で、`cand.segments` がちょうど 1 つで、その語が辞書の語（`word` が `Some`）。1文字に限らない（電話 + ばんごう → 番号 も対象）。
3. `C` は、表記が `left.surface + cand.surface` と完全に一致する辞書の項目（`common_prefix_search_surface` で一致の長さが全体のもの）。`IME_EXCLUDED` の項目は除く。
4. `C` の品詞が `名詞,普通名詞,*` か `名詞,固有名詞,地名,*`（§12 Q2）。人名（犬都、猫都、一児 などの名）と、そのほかの固有名詞は除く。
5. `C` の読みが、`L + cand の読み` と一致する。`L` は、表記が `left.surface` と同じ項目の読みのどれか（`common_prefix_search_surface(left.surface)` の各項目の `reading`）。

条件を足した理由（スパイクで、条件がないときに出た失敗。phase3-context-compound §2.1、§4.2）:

| 条件 | ないときの失敗 |
| --- | --- |
| 1（左が名詞） | できる + かぎり → 限り（できる限り）、苔むした + いし → いし、屋外では + しよう → しよう |
| 4（普通名詞と地名） | 犬 / 猫 / 人 + と → 都（犬都、猫都、人都。名詞,固有名詞,人名,名） |
| 5（読み） | 私 + たち → 立（私立 シリツ）、三日 + ほど → 程（日 + 程 = 日程） |
| 5 を「解析器が選んだ左の語の読み」1つにする | 日本 + ご（ニッポン と解析）、店 + いん（ミセ）、国 + さい が直らない。だから同じ表記のどの読みでもよい形にした |

### 3.2 当たった複合語が複数あるとき
1回の `rank` の中で、当たった候補ごとに `C` の `cost + penalty`（変換で使うコスト）を求め、**いちばん小さい複合語と同じ lemma を持つ候補だけ**に加点する。

- 理由: 年 + かん では 年間、年鑑、年刊、年官 が、目 + じ では 目次、目地、目路 が当たる。全部に加点すると、経路の安い珍しい語（官、路）が勝った。いちばん安い複合語に絞ると 年間、目次、部下、学科、情報化 になった。
- lemma で比べる理由: 子供 + たち では 子供たち と 子供達 が当たる（lemma は同じ）。両方に加点するので、表記の好み（公用文の たち）は今までどおり KanaStyleRanker と経路のコストで決まる。

### 3.3 加点の大きさ
当たった候補の差分を

```
delta = min(連接の差分, -max_total) - compound_bonus      // max_total = 6000、compound_bonus = 3000
```

にする（当たらない候補は今までどおり `連接の差分`）。

- 連接の差分を上限まで引き上げるのは、0.2 の品詞による差（接尾辞は上限、名詞は 0）を、複合語が当たった候補について消すため。そのうえで `compound_bonus` だけ、当たらない候補より前に出す。
- 1候補あたりの差分の絶対値は最大 9000（今の上限 6000 + 3000）。
- 値の決め方: dev（katakana-suffix、homophones-ext、hiragana、homophones）では 250〜8000 で結果が同じだった。セットにない入力（phase3-context-compound §4.3）で、4.1 の改善がすべて出る最小の値が 3000（500 では 大学生、年間、時間 など 8 件、2000 では 地下、選手権 が直らない）。悪化（§7）は 500 でも同じだけ起きるので、値を小さくしても防げない。test は値を決めたあとに1回だけ流した。
- 加算の形（`連接の差分 - bonus`）も測った。6000 以上で dev は同じ結果になるが、名詞の候補と接尾辞の候補で加点の合計が違うまま（接尾辞は最大 -12000）で、目 + じ が直らなかった。上限までそろえる形を選んだ。

### 3.4 働かない場合
- 左文脈がない、secure、文頭のとき（今の LeftContextRanker と同じ）。
- `compound_bonus = 0` のとき。
- 最後のトークンが名詞でないとき。表記の検索はしない（コストもかからない）。

## 4. 速さ

スパイクで、`LeftContextRanker::rank` 1回の時間を測った（katakana-suffix と homophones-ext の全件 × 20 回、27552 回。Linux のコンテナ、4 コア）。

| | p50 | p99 | p99.9 |
| --- | ---: | ---: | ---: |
| 今 | 1.6 µs | 4.1〜4.6 µs | 30 µs |
| 本 ADR の規則 | 2.9〜3.1 µs | 24〜26 µs | 55〜57 µs |

- 表記の検索は、1回の `rank` で、1語の候補の異なる表記ごとに 1 回（候補の表記と読みの組でキャッシュする）。左の語の読みは 1 回だけ求める。平均 2.0 回だった。
- 変換全体の warm p99（snapshot）は 0.21〜0.51 ms で、基準の揺れ（0.19〜0.44 ms）と区別できない。目標の p99 2 ms に対して、増える分は約 20 µs。
- **逆引き表**: 条件 5 は `Dictionary::reading` を使うので、逆引き表がまだなければ最初の呼び出しで作る（release で 0.11〜0.30 秒。eval では最初のケースに乗った）。エンジンは起動のあとに裏で作るので、起動の直後の 1 回だけ待つことがある（再変換と同じ。ADR 0006 §16.5）。待たせたくなければ、「作ってあれば読みを返し、なければ None」を返す口を `Dictionary` に足し、まだのときは複合語の段を飛ばす。実装のレーンで決めてよい（§10）。

## 5. 複数の文字、複数の語の候補

- **1語なら長さは問わない**: 電話 + ばんごう → 番号（電話番号）、新 + せいひん → 製品（新製品）、株式 + がいしゃ → 会社（株式会社）も条件を満たす（どれも今も1位なので、結果は変わらない）。
- **複数の語に分かれた候補は対象にしない**: 最初の語で調べる形を測ると、dev の homophones-ext が 776 → 769（cb 1000）、757（4000）、732（8000）と大きく悪化した（拘束形の分割 こう章、か体、そうゾウ が上がる）。条件 1〜5 を付けても 774（6000。課程 → 家弟、週間 → 秋館 など）。
- このため **自動 + かする**（化 + する）は直らない（今も 1位は 化する）。自動 + か → 化 は直る。

## 6. ほかの仕組みとの関係

### 6.1 LeftContextRanker の連接の増幅と上限
- **[ADR 0029 で改訂]** 増幅の対象から `接尾辞,名詞的`（助数詞を除く）も外した。複合語が当たった候補は、下のとおり上限まで引き上げてから加点する（変わらない）。
- 名詞で始まる候補を増幅しない規則（ADR 0002 §22）は変えない。複合語が当たった候補だけ、連接の差分を上限まで引き上げる（§3.3）。当たらない名詞の候補は今までどおり 0。
- 上限（`max_total` 6000）は変えない。複合語の加点はその外に `compound_bonus` として足す。

### 6.2 GrammarGuard と LearningGuard
- 当たった候補の差分は負なので、GrammarGuard の「文法候補」になる。話題やプロファイルの加点が、洗濯 + き の 機 を 器 や 記 で追い越すことはない。
- LearningGuard では「文脈の証拠」になる。学習の文脈に依らない加点（ほかの文脈で 器 を何度も選んだ）では覆らない。文脈つきの学習（左の語が 洗濯 のときに 器 を選んだ）は今までどおり効く（基本原則「学習は支援であって決定ではない」と同じ扱い）。

### 6.3 学習
- 記録するもの（`LearningStore::record`）は変えない。確定した候補と、そのときの左文脈から作る特徴量のまま。
- 複合語の加点は辞書から毎回計算し、学習ファイルには入れない。

### 6.4 ユーザー辞書
- `DictionarySet` の表記の検索と `reading` はユーザー辞書の語も返すので、**ユーザーが登録した複合語にも同じ規則が効く**。スパイクで、`にほんごばん 日本語版 名詞` を登録すると 日本語 + ばん が 板 → 版 になった。
- ユーザー辞書の品詞は `core/assets/user_pos.tsv` で Sudachi の品詞に対応している。「名詞」「サ変名詞」「短縮よみ」は 名詞,普通名詞、「地名」は 名詞,固有名詞,地名 なので当たる。「固有名詞」「組織」「人名」「姓」「名」は当たらない（§12 Q4）。
- 左の語がユーザー辞書の語（例: 製品名）でも、その語との複合語を登録していれば当たる。

### 6.5 LM（zenz）
- LM は Ranker の並びの最後で、Guard の外にある（ADR 0003）。複合語の加点で前に出た候補を、LM がさらに並べ替えることはありうる。LM ありの評価はこのコンテナでは測っていない。実装のあと、手元の Mac で snapshot（`--lm`）を取って確かめる（§10）。

## 7. 壊しうる入力（セットにないもの）

評価セットでは悪化が出なかったが、セットにない自然な入力で調べた（phase3-context-compound §4。135 件）。

### 7.1 悪くなるもの
| 入力 | 今 | 本 ADR | 原因 |
| --- | --- | --- | --- |
| 水 + と | と | 都 | 水都（スイト。名詞,普通名詞）。水 に スイ の読みがある |
| 人 + ごと | ごと | 事 | 人事（ヒトゴト）。表記としては正しいが、ごと を期待する人もいる |

- 型は「**名詞を確定したあと、助詞だけ**を変換する」とき、`名詞 + 同じ読みの漢字1文字` の複合語が辞書にあると、助詞が負ける。複数の語に分かれる入力（水 + とおゆ）は対象外なので変わらない。
- `compound_bonus` を 500 にしても同じだけ起きる（引き上げの部分だけで負ける）。値では防げない。

### 7.2 間違いのまま（今も間違い）
本 + と → 途（今は 都。本途）、人 + じ → 事（今は 寺）、中 + し → 士（今は 史）、東京 + と → 都（今は 兎。地名を含めた場合）。

### 7.3 直らないもの
- 日本語 + ばん、午後三 + じ: 日本語版、三時 の項目が辞書にない（日本語版 はユーザー辞書に登録すれば直る）。
- 本当 + か、無理 + か、大丈夫 + か（今も 家 や 化 が 1位）: か を助詞にしたいのに、助詞の候補が上に来ない。本 ADR とは別の原因（phase3-suffix §2.1、§6。LM の範囲）。本 ADR では変わらない（本当化 などの項目がない）。
- 自動 + かする（§5）。

### 7.4 変わらないことを確かめたもの
子供 / 私 / 人 + たち（たち のまま）、彼 / 学生 / 子 + ら、予定 / 時間 / 計画 + どおり、会社 / 東京 + の、会社 / 東京 + に、父 / 犬 / 猫 / 人 + と、田中 + さん、鈴木 + くん、先生 + がた など。

## 8. 評価

- 既存のセットで 1位が悪化しないこと（`eval/scripts/snapshot.sh --compare`）。スパイクでは、katakana-suffix +3、homophones-ext +3、ほかは変化なし。
- **セットにケースを足す**（実装のレーン）。§7 の入力を、期待とともに `eval/sets/` に入れる。悪化の型（名詞 + 助詞だけ、名詞 + 終助詞 か）を含める。phase3-suffix §6 でも、名詞 + 終助詞 か のケースがセットにないことが指摘されている。期待の正しさはユーザーの確認が要る（REVIEW.md に「未確認」として足す。§12 Q5）。

## 9. 検討した案

| 案 | 結果 | 採らない理由 |
| --- | --- | --- |
| **案 B-1**: LeftContextRanker で接尾辞も増幅しない（phase3-suffix §6） | katakana +4（器、板×2、次）、-2（論理 + てき → 敵（test）、拡張 + せい → せい） | 悪化がある。接尾辞の加点は 的、性、者 などで正しく効いている |
| **案 B-2**: 名詞,普通名詞,助数詞可能 も増幅する（同） | katakana +1（次 → 時）、ext dev -2（しゅうかん の 4 件が入れ替わる） | 悪化がある。品詞で分けると、同じ品詞の中の正しい比較を崩す |
| 辞書のポリシーで 機、版、時 を加点する | ― | LeftContextRanker の差 6000 を打ち消すには 6500 以上が要り、文脈のない入力でも同じだけ動く（phase3-suffix §2.3） |
| 左文脈の末尾 1〜4 文字（トークンの区切りによらない） | dev は同じ（105 / 778）、hiragana -1（できる + かぎり → 限り） | 左の語が名詞かどうかを見られない。トークンで十分 |
| 複数の語の候補の最初の語で調べる | ext dev 732〜774 | §5 |
| 加点を足すだけ（上限への引き上げなし） | dev は 6000 以上で同じ | 目 + じ が直らない。接尾辞と名詞で合計が違うまま（§3.3） |

## 11. 基本原則との整合
- **入力を正とする**: 候補は今までどおり辞書から作り、読みに対応しない文字を足さない。並べ方だけを変える。
- **学習は支援であって決定ではない**: 学習の記録と効き方は変えない。複合語の加点は文脈の証拠として扱い、学習の文脈に依らない加点で覆さない（今の LeftContextRanker と同じ）。
- **こまめに確定する**: 確定した語を錨にして次の語を決める、という ikari の考え（spec「名前とモチーフ」）に沿う。長文のための仕組みは足さない。

## 12. ユーザーの判断が要る点

| # | 判断すること | 推奨 | 理由 |
| --- | --- | --- | --- |
| Q1 | 本 ADR の規則（§3）を採るか | **採る** | 測ったセットで悪化 0、改善 6。セットにない入力で 34 件が良くなり、悪くなるのは 2 件（§7.1） |
| Q2 | 複合語に地名（京都市、大阪府、千葉県、東京都）を含めるか | **含める** | 京都 + し → 市、大阪 + ふ → 府 などが直る。人名は含めない（犬都、一児 で崩れる）。代わりに 東京 + と が 都 になる（今は 兎 で、どちらにしても と ではない） |
| Q3 | §7.1 の悪化（水 + と → 都、人 + ごと → 事）を受け入れるか | **受け入れる** | 名詞を確定してから助詞だけを変換する入力で起きる。値では防げず、防ぐ規則（助詞の候補があれば加点しない）は、か が助詞の候補でもあるので 自動 + か → 化 も止めてしまう。LM があれば直る見込み（未確認） |
| Q4 | ユーザー辞書に「固有名詞」「組織」で登録した語も複合語として扱うか | **扱う**（人名、姓、名 は除く） | 登録した語はユーザーが使う語。製品名 + 版 のような登録を活かせる。システム辞書の固有名詞と扱いが変わるが、ユーザー辞書の語は数が少なく、珍しい語の誤爆の心配が小さい |
| Q5 | §7 の入力（約 40 件、悪化の型を含む）を評価セットに足し、期待をユーザーが確認するか | **足す。抜き取りで確認してもらう** | セットに 名詞 + 助詞だけ、名詞 + 終助詞 か の型がなく、同じ型の規則の副作用を見逃す（phase3-suffix §6） |
| Q6 | `compound_bonus` の値 | **3000** | dev では 250〜8000 が同じ。セットにない入力で、改善がすべて出る最小の値（§3.3）。値を下げても §7.1 は減らない |

### 12.1 決定（2026-10-13 ユーザー）
Q1〜Q6 は、すべて推奨のとおりに承認された。
- Q1 §3 の規則を採る
- Q2 地名の複合語を含める。人名は含めない
- Q3 §7.1 の悪化（水 + と → 都、人 + ごと → 事）を受け入れる
- Q4 ユーザー辞書の「固有名詞」「組織」の語も複合語として扱う（人名、姓、名 は除く）
- Q5 §7 の入力を評価セットに足し、期待をユーザーが抜き取りで確認する（docs/tasks.md の A2）
- Q6 `compound_bonus` は 3000

実装は §10 のとおり、1 つのレーンで行う。

### 13.2 実装で決めたこと
- **ユーザー辞書の語の見分け方**（§12.1 Q4）: 項目の `WordId.dict` が slot 0（システム辞書）でなければユーザー辞書の語とし、`名詞,固有名詞,*`（人名を除く）も複合語に数える。ユーザー辞書の「固有名詞」「組織」は `名詞,固有名詞,一般` なので当たり、「人名」「姓」「名」は `名詞,固有名詞,人名,*` なので当たらない。システム辞書の `名詞,固有名詞,一般` は今までどおり数えない。
- **左の語の読み**（条件 5）: 表記が左の語と同じ項目の読みを全部使う。`IME_EXCLUDED` の項目の読みも使う（解析には使う項目なので）。
- **いちばん安い複合語が同じコストで複数あるとき**（§3.2）: 候補の並びで先に当たったものを採る（決定的）。lemma が引けない辞書では、複合語の表記を lemma の代わりにする。
- **検索の回数**: 1回の `rank` で、左の語の読みを 1 回、1語の候補の（表記, 読み）ごとに表記の検索を 1 回。左の語が名詞でなければ、どちらもしない。
- **逆引き表を待たない口**（§4、§10）: **足さなかった**。測ると、逆引き表のないプロセスで、名詞の左文脈のある最初の変換が 0.26〜0.30 秒かかる（CLI の 1回の実行。名詞でない文脈は 6〜8 ms で main と同じ）。エンジンは起動と辞書の組み直しのあとに裏で表を作る（`warm_dictionary`）ので、待つのは起動直後の約 0.3 秒の間に名詞の文脈で変換したときの 1 回だけ（再変換と同じ扱い。ADR 0006 §16.5）。待たない口を足すと、CLI と eval では表を先に作らない限り規則が効かなくなり、評価と実機の結果がずれる。
