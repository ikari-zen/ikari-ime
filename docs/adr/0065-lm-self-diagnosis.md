## 0. ユーザーの決定（2026-11-15。この ADR の出発点。覆さない）

1. LM は基本的に入る前提。CPU だけで LM が締め切りに間に合わない低スペックな機械は、サポートの範囲外にする。作者は Windows の高性能な実機を持たない。N150 の VM（2 vCPU）は動作確認用。Mac の VM は使わない（ADR 0040）。
2. Windows の LM の既定は、**利用者の機械の自己診断で決める**。下限 X を「温まった推論 1 回の p90 が X ms 以下」と定義する。
3. X の根拠は、**Mac の Metal に人工の遅延を足す検証**（推論の時間 → LM が付く率の曲線。打鍵の間隔の分布で）で作る。VM の数字は「X を満たさない機械の例」と「縮退の確認」に使い、目標値の根拠にしない。
4. 利用者の機械での自己診断は通信しない（NFR-17）。
5. 締め切りの既定（300ms）は変えない。`engine.lm_deadline_ms` は設定アプリで変えられる今のまま。CPU のときの案内は #426 のまま。
6. 1.0.0 の条件は、LM が付く率そのものではなく、(1) X が文書にある、(2) 自己診断と既定の自動判定がある、(3) X 未満の機械で縮退を確かめた、(4) X 以上の機械の質は Mac の評価で代表させる、の 4 つ。

## 1. 現状（分かったこと。コード、文書、実測で確かめたもの）

### 1.1 既定の LM
- Windows: `windows/engine-host/src/run.rs` の `ENABLE_LM_DEFAULT = false`（コメントは ADR 0040 §2.6）。`EngineConfig.enable_lm` に入る。
- macOS: `macos/Sources/IkariEngineService/main.swift` が `config.enableLm = true`。shell-core の設定の既定も `engine_lm: true`（`shell-core/src/settings/defaults.rs`）。→ **Windows では、設定アプリの既定（オン）とエンジンの既定（オフ）がすでに食い違っている。**
- エンジンは `settings.lm.unwrap_or(cfg.enable_lm)` で決める（`engine/src/lib.rs` の `Engine::open_with`）。`engine/src/settings.rs` の `Settings.lm` は `Option<bool>` で、**「書かれていない」と「オン・オフを書いた」を区別できる**。`engine.lm_gpu` も同じ（既定は真）。`engine.lm_deadline_ms` は既定 300、範囲 50〜2000。
- 設定アプリの書き込みは、変えたキーだけを書き（`shell-core/src/settings/values.rs` の `plan`）、`reset` は行を消す（`file.rs` の `update_text`）。今は `engine.lm` を「書かれていない」に戻す操作が設定アプリに無い。

### 1.2 締め切りと LM が使える時間
- Space の待ちの予算は `30ms + 6ms × 読みの字数`、上限 300ms（`shell-core/src/timeouts.rs`）。先行計算の中で LM を待つ上限は 300ms（`LmBudget.max` = `engine.lm_deadline_ms`）。Space の時点で計算中なら、Space から最大 30ms 待つ（ADR 0021 L1、`engine.convert_wait_ms`）。
- LM が使える時間は「最後の打鍵（Prefetch）から Space まで」（ADR 0021 §2.1）。
- LM のワーカーは 1 つで、溜まった要求は最新の 1 件だけ処理する（`lm/src/ranker.rs`）。走り出した推論を止める処理は見当たらない（#429。`lm/src/llama.rs` の中は未確認）。
- `LmTrace.infer_micros` は、1 回の先行計算の中の推論の時間を**足し合わせる**（`lm/src/trace.rs`。2 文節以上なら複数回の和になる）。

### 1.3 実測（数字だけ）
| 項目 | p5 | p10 | p25 | p50 | p75 | p90 | p95 | p99 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 作者の Mac の Space までの間（変換の開始と、直前の Prefetch の時刻の差。n=9345、32 日、10 秒以上は除外） | 77 | 91 | 117 | 136 | 198 | 310 | 421 | 779 |
| 打鍵の間隔（同じ読みの中の Prefetch から次の Prefetch。ADR 0021 §2.1、4.3 日、2026-10） | — | 116 | — | 280 | — | 595 | 799 | 1526 |

- 長さによる差はほぼない（p10 / p50: 3 字以下 86 / 150、4〜7 字 84 / 138、8 字以上 87 / 139）。
- 作者の Mac の実機の LM（Metal）: 先行計算の `lm_infer_us` は p50 48 / p90 93 / p99 175ms（n=3191）、変換の時点は p50 52 / p90 97 / p99 132ms（n=415）。変換の時間切れは 0.24%。
- 同じ Mac の評価（静かな機械、`ikari-eval`）: 推論込みの変換 1 回は p50 19 / p90 23ms。全セットの 1 位は LM なし 73.8%、LM あり 82.0%（Fable の設計レビュー C1・C2）。

### 1.4 推測（確かめていないもの）
- 実機の `lm_infer_us` の p90（93ms）が評価の p90（23ms）より大きいのは、(a) 2 文節以上の和（§1.2）、(b) 実機の左文脈（40 字の窓が埋まっている）、(c) ほかのアプリの負荷、のどれか、または全部。内訳は分からない。**静かな機械で決まった入力を測る自己診断は、実際の使用の時間より小さく出る**と見ておく（§10 の懸念 1）。
- 推論の時間を一定の T とし、待ち（#429）と LM 以外の計算を無視すると、LM が付く率は おおよそ P(Space までの間 + 30ms ≥ T)。上の分布から読むと、T = 100ms で約 96%、120ms で約 90%、150ms で約 73%、175ms（VM の GPU の p50）で約 46%、300ms を超える CPU（433ms）では締め切りで切られてほぼ 0。**T が打鍵の間隔（p10 116ms）を超えると、古い推論の残りを待つ分（#429）だけ、これより悪くなる。** この見積もりは §3 の検証で置き換える。

## 2. 問題の定義

- Windows 1.0.0 の LM の既定オフ（ADR 0040 §2.3・§9 の Q1、ADR 0059 §0 の 4）は、決定 0-1「LM は基本的に入る」と合わない。LM なしは 1 位が約 8 ポイント低い（§1.3）。既定のまま出すと、Windows の利用者の多くは縮退した質を既定として受け取る。
- 一方で、既定を固定でオンにすると、X に届かない機械（VM のような）では、LM が付いたり付かなかったりして並びが揺れ、CPU と電力だけを使う。並びが揺れると、利用者は候補の位置を覚えられない（思考を止める）。
- 作者は速い Windows の機械を持たないので、「どの機械ならオンにしてよいか」を作者が機械の名前で決めることはできない。決められるのは「推論の時間がいくつなら LM が効くか」で、これは打鍵の間隔（OS によらない）と推論の時間の関係なので、Mac で作れる。

## 3. 決定 1: X の定義と決め方

### 3.1 定義
- **X は「自己診断の推論 1 回の p90」に対する上限**。自己診断（§4）の決まった入力・回数・暖機の扱いで測った値で比べる。実際の使用の時間（`lm_infer_us`）では比べない（入力と負荷で変わり、機械どうしで比べられないため）。
- 推論 1 回 = `LmScorer` の 1 回の採点（プロンプトの decode と候補のバッチの decode）。別プロセスの往復を含む（製品と同じ経路。ADR 0060 Q4 で往復の追加は p50 で 0.1ms 以下）。LM 以外の変換の時間は含めない。
- GPU と CPU は区別しない。**その機械で実際に LM が動く装置**で測る（`engine.lm_gpu` と、GPU から CPU への切り替わりの結果。ADR 0059 §2.4、ADR 0060 Q4）。装置が変わったら測り直す（§4.4）。
- X は締め切り（`engine.lm_deadline_ms`）と独立。締め切りを変えても X は変えない（決定 0-5）。

### 3.2 区分（新しい定数を足さない）
| 区分 | 条件 | 既定の自動判定（§5） |
| --- | --- | --- |
| 快適 | p90 ≤ X | LM オン |
| ぎりぎり | p50 ≤ X < p90 | LM オフ（理由を出す。設定でオンにできる） |
| 対象外 | p50 > X | LM オフ（理由を出す） |

- 「ぎりぎり」を p50 で切るのは、境目の値をもう 1 つ決めないため（値が増えると、それぞれに計測の根拠が要る）。「ぎりぎり」を自動でオフにするのは、決定 0-2（X を満たさなければオフ）のとおり。§11 の Q2 で確認する。

### 3.3 仮置きの X
- **X = 100ms（仮置き。計測なし）。** 候補の範囲は Space までの間の p10（91ms）〜 p50（136ms）。下寄りに置く理由: (a) §1.4 の見積もりで T = 100ms なら付く率は約 96% で、待ち（#429）と実際の使用の負荷（§1.4）の分の余裕を残せる。(b) X を高く間違えると、LM が付いたり付かなかったりする機械でオンになり、並びが揺れる。低く間違えると、LM が効く機械でオフになるが、入力は止まらず、利用者は設定でオンにできる。後者のほうが原則（入力に忠実、思考を止めない）に近い。
- この値で、N150 の VM は GPU でも CPU でも「対象外」（p50 175、433 > 100）。決定 0-1 の「低スペックはサポート外」と合う。

### 3.4 測ってから決める手順（Mac の人工の遅延の検証）
**口（検証用。製品は使わない）**
- `lm` に、採点の結果を返す前に待つ包み（`DelayedScorer` の案）を足す。待ちの形は 2 つ: 倍率 `k`（実際にかかった時間の `k − 1` 倍を足す。遅い機械は長い入力ほど遅い、を真似る）と、固定の `d` ms。
- 指定は `ikari-eval` の `--ranker-config` の `zenz.debug_infer_scale` と `zenz.debug_infer_extra_ms`（案）。製品のエンジンは `zenz.*` を読まない（ADR 0060 Q4 の `zenz.host_*` と同じ扱い）ので、利用者の設定からは届かない。
- 包みは、別プロセスの子の中ではなく親の側に置く（往復を含めて遅くなる。子の取り決めを変えない）。

**再生の評価（新しい。`ikari-eval` のモード）**
- 評価セットの各行で、読みを 1 文字ずつ Prefetch し（間隔は §1.3 の打鍵の間隔の分布から引く）、最後の Prefetch のあと Space までの間（§1.3 の分布から引く）を空けて Convert する。製品と同じ `Engine`（先行計算、待ち行列、Space から 30ms の待ち）を通す。乱数の種は固定し、結果に書く。
- 分布は分位数の表（数字だけ）を `eval/` に置き、分位数の間は直線で補う。実機のログそのものは使わない。新しく作者のログを集計し直すときは、ユーザーに聞く。
- 出すもの: `LmReport.verdict`（ADR 0061）の内訳（付いた、時間切れ、先行計算が遅れた、など）、LM が付いた率、1 位、Space から 1 ページ目までの時間の p50 / p99。

**掃引**
- `k` ∈ {1, 2, 3, 4, 5, 6, 8, 10}（仮置き）。それぞれの `k` で、(i) 自己診断（§4 と同じ関数）の p50 / p90、(ii) 再生の評価の付く率と 1 位、を同じ包みのもとで測る。→ 横軸「自己診断の p90」、縦軸「付く率」「1 位」の曲線。
- 固定の `d` でも 3 点ほど流し、倍率と形が大きく違わないかを見る（違えば、どちらに寄せるかを報告に書く）。
- セットは全セット（`eval/scripts/snapshot.sh` と同じ構成）。時間がかかりすぎるなら homophones-ext と AJIMEE で曲線を引き、端の 2 点だけ全セット。
- 静かな機械で 2 回ずつ、負荷平均を記録する（ADR 0021 §2.4 のとおり、負荷で揺れる）。

**判定の基準（仮置き）**
- **X = 付く率が 80% 以上を保つ、自己診断の p90 の最大値**（5ms 刻みで丸める）。1 位は確認に使う: X の点の 1 位が「LM なし + LM の利得の 8 割」以上であること（§1.3 の数字なら 73.8 + 0.8 × 8.2 ≈ 80.4%）。両者が食い違えば、報告に書いてユーザーに聞く。
- 80% は計測なしの仮置き（§11 の Q1）。作者の Mac の実機は、ADR 0021 の推定で約 87%（当時）。
- 報告は `eval/reports/lm-x-sweep-<日付>.md`。索引（`eval/reports/README.md`）に足す。
- この再生の評価は、#429 の完了の条件（「人工の遅延を足した条件で、古い推論が新しい推論を待たせるか実測する」）にも使う。`verdict` の内訳と Space の時点の待ちで分かる。

## 4. 決定 2: 自己診断

### 4.1 誰が
- **エンジン**（`engine` の新しいモジュール。案 `engine/src/lm_diag.rs`）。LM の子と LM のワーカーを持ち、ワーカーが空いているかが分かるのはエンジンだけ。別の CLI で測ると、モデルを 2 つ目のプロセスで読み、利用者の入力とぶつかる。
- 測る関数はライブラリにし、`ikari-eval` からも呼べるようにする（§3.4 の掃引の (i) と同じ関数で測るため）。

### 4.2 何を、何回
- 入力: **決まった 8 件**（仮置き）。読みの長さは 2、3、4、5、6、6、8、10 字（実際の使用は 6 字以下が多い。Fable C2）。左文脈は 40 字（製品の窓の上限。実際の使用で窓が埋まる場面に合わせる）。文はコードに置く作文で、個人の文や公開でない文は使わない。候補は、その機械の辞書から製品と同じ手順で作る（`zenz.max_candidates` = 32 まで）。
- 回数: 暖機として 2 回捨て、8 件 × 4 巡 = 32 回を測る（仮置き）。p50・p90・p99 は最近傍の順位で取る（32 回の p90 は 29 番目）。
- 打ち切り: 測った最初の 8 回の中央値が 2X を超えたら、そこで「対象外」とする（遅い機械で長く LM を占有しないため。CPU の 433ms なら約 4 秒で終わる）。
- 「温まった」: モデルの読み込みと、エンジンの起動時の暖機（ADR 0059 §6）が済んで、`Ready` のあと。アイドルの解放で読み直したら、読み直しの暖機が済むまで測らない。

### 4.3 いつ、どう LM を譲るか（思考を止めない）
- **自動で測る時**: LM が「自動」（`engine.lm` が書かれていない）で、有効な結果（§4.4）が無いとき、LM が `Ready` になったあと。
- **譲り方**: 1 回ずつ、LM のワーカーが空いていて、どのセッションにも直近 1 秒（仮置き）Prefetch と Convert が無いときだけ、1 回分の採点を頼む。打っている間は測らない。走り出した 1 回は止めない（#429 と同じ。止める仕組みが入ったら、測る側から先に止める）。→ 最悪で、利用者の Prefetch が 1 回分の推論を待つ。それでも変換は締め切りで LM なしで返る（入力は止まらない）。
- **設定アプリの「もう一度測る」**: 同じ関数を同じ譲り方で動かす。返事はすぐに「測っています」を返し、設定アプリは状態を問い合わせて表示を替える（管理の要求を長く待たせない）。
- 起動のたびには測らない（§9）。

### 4.4 結果の保存と、測り直す条件
- 保存先: `<データ>/lm-diagnosis.tsv`（エンジンが書く。`settings.tsv` には書かない）。中身は数字と固定の語だけ: 形式の版、エンジンの版、モデルの識別（既知のモデルの表の名前）、装置（`gpu` / `cpu`）とデバイスの要約（ADR 0060 Q4 で検査済みの文字だけ）、GPU の扱い（`engine.lm_gpu` の実効値）、n、p50・p90・p99（µs）、打ち切ったか。区分は保存せず、読むたびに X から決める（X を変えても測り直さずに済む）。
- エクスポートとインポート（#92）には含めない（機械に固有）。ユーザーデータのリセットでは消してよい。
- **測り直す条件**（どれかが保存した値と違えば無効）: 形式の版、エンジンの版（llama.cpp の版も替わりうる）、モデル、装置とデバイスの要約、GPU の扱い。これで「モデルや GPU を変えた」「GPU が失敗して CPU に切り替わった」「更新した」を拾う。
- 自動の結果が「快適」以外のときは、次のエンジンの起動で 1 回だけ自動で測り直し、良いほうを使う（たまたま負荷が高かった 1 回で LM を失わないため。回数は仮置き）。そのあとは、上の条件か「もう一度測る」まで測らない。

### 4.5 出し方
- エンジンのログに 1 行（`lm_diag verdict=comfortable|marginal|unsupported n= p50_us= p90_us= p99_us= x_us= dev= cut=0|1`。数と固定の語だけ。ADR 0034 の範囲）。
- `HelloReply` と、新しい管理の要求の返事に、区分、理由の語、数字（p50・p90・X）、測っている最中か、を入れる（§6 の契約）。
- 設定アプリの LM の欄（#426 の案内のそば）に、区分と理由の文、「もう一度測る」を出す。**数字は、開発者の表示（`developer.lm_status`、ADR 0061）がオンのときだけ出す**（#426 と同じく、ふつうの利用者には数字を見せない。issue に貼りたい人は開発者の表示をオンにする）。文は shell-core が作り、両 OS で同じ。§11 の Q3 で確認する。
- 文の例（案）: 快適「この機械では言語モデルが間に合います。」、ぎりぎり「この機械では言語モデルが間に合わないことがあるため、オフにしています。設定でオンにできます。」、対象外「この機械では言語モデルが間に合わないため、オフにしています。LM なしでも変換できます。」、測っている最中「この機械の速さを測っています。」。

## 5. 決定 3: 既定の自動判定

### 5.1 規則
| `engine.lm` | 有効な結果 | LM |
| --- | --- | --- |
| 書かれている（オン・オフ） | 関係ない | **書かれたとおり**。自動判定は上書きしない。自動では測らない（「もう一度測る」は情報として使える） |
| 書かれていない | 快適 | オン |
| 書かれていない | ぎりぎり・対象外 | オフ。モデルを読まない。理由を出す |
| 書かれていない | 無い（初回、測り直しの条件） | **仮にオンで使い**、測り終えたら上の 2 行に従う（オフなら、その場で LM を止めて解放する） |
| （モデルが無い・照合に通らない） | — | 今のまま LM なし（`LM_FAILED`）。測らない |

- 自動判定は `engine.lm_gpu` も変えない。GPU で X を満たさなくても、CPU に替えて試すことはしない（CPU のほうが遅い。ADR 0059 §6、ADR 0060 Q4 の Mac の CPU の子は GPU の約 2 倍）。
- **判定の結果は設定ファイルに書かない。** `lm-diagnosis.tsv`（測った数）と、そこから決める区分を、エンジンが持つ。利用者が設定アプリでオン・オフを選んだときだけ `engine.lm` が書かれる。
- 設定アプリには「自動（推奨）」に戻す操作を足す（`engine.lm` の行を消す。今の `reset` と同じ）。表示は「自動: 今はオン（快適）」のように、実効の値と理由を出す。Windows で、設定アプリの既定（オン）とエンジンの既定が食い違う問題（§1.1）は、設定アプリが実効の値をエンジンの返事から出すことで解く。
- 初回に「仮にオン」にする理由: 決定 0-1（LM は基本的に入る）と、測るにはどのみちモデルを読む必要があること。遅い機械では、測り終えるまでの数秒〜数十秒、LM が付いたり付かなかったりするが、入力は締め切りで止まらない。

### 5.2 方針の置き場所
- エンジンに「既定の方針」を渡す: `On`（macOS。今と同じ）、`Off`（テスト、LM なしの構成）、`Diagnose`（Windows）。Rust の側の引数にし、proto の `EngineConfig` は変えない（macOS の FFI と Swift を触らない）。Windows の engine-host は `ENABLE_LM_DEFAULT = false` を `Diagnose` に置き換える。
- **macOS の既定は変えない**（`On`）。macOS では自動では測らない（Metal で X を満たす見込み。§1.3 の評価の p90 は 23ms。推測: 自己診断でもこの近くに出る）。設定アプリの「もう一度測る」は macOS でも使え、結果を出すだけで既定は変えない。Intel の Mac などで macOS でも自動判定が要るかは、利用者の報告が来てから決める（今は根拠がない）。

## 6. 決定 4: 縮退

### 6.1 X 未満の機械で起きること
- 自動のとき: LM はオフ（モデルを読まない）。変換は LM なしで返る。設定アプリに理由が出る。#426 の CPU の案内は LM がオンのときだけなので出ない（自己診断の理由が代わりになる）。
- 利用者が `engine.lm` をオンにしたとき: 今と同じく、LM は締め切りまでに付けば使い、間に合わなければ LM なしで返る（NFR-04）。CPU なら #426 の案内が出る。
- 測っている最中: §4.3 のとおり、打っている間は測らない。

### 6.2 VM で確かめる項目（`docs/windows-real-device-check.md` に足す案。番号は 41 から）
1. **項目 41: 自己診断と自動判定**（LM を自動のまま）。新しいデータのフォルダで起動し、変換しながら待つ。`lm_diag` の行（`verdict=unsupported`、`cut=`）、`lm-diagnosis.tsv` の中身（数字だけ）、設定アプリの理由の文、LM がオフになったこと（`lm_load` の行、モデルが解放されたこと）。測っている間と測ったあとで、打鍵と変換が止まらないこと。
2. **項目 42: 明示したオンを上書きしない**。`engine.lm` を `on` にして起こし直す。LM が使われ続け、自動では測らないこと。GPU と CPU（`engine.lm_gpu` `off`）の両方で、Space から 1 ページ目までの時間（候補が出るまで固まらないか）、`LmReport` の内訳（開発者の表示）、LM が付いた率の目安。
3. **項目 43: 測り直しの条件**。`engine.lm_gpu` を替える、`backends\ggml-vulkan.dll` を外す（CPU に落ちる）、`lm-diagnosis.tsv` を消す。それぞれで測り直すこと。替えないで起こし直したときは測らないこと（「快適」以外の初回の 1 回の測り直しを除く）。
4. **項目 44: 「もう一度測る」と入力の同時**。設定アプリで「もう一度測る」を押してから、すぐにメモ帳で打つ。打鍵が止まらず、測るのが打鍵の間は止まり、打ち終えて約 1 秒後に進むこと。
5. **項目 45: アイドルの解放のあと**。`engine.lm` を `on`、`engine.idle_unload_secs` を短くして解放させ、次の変換。読み直しの間も変換が止まらないこと。読み直しの直後には測らないこと（§4.2）。

### 6.3 #429 との関係
- X は、#429 の今の状態（走り出した推論を止めない）で、再生の評価（§3.4）から決める。待ちの影響は曲線に入っている。
- #429 で中断が入ったら、同じ掃引を流し直し、曲線が良くなれば X を上げるかをユーザーに聞く。X の決定は #429 を待たない。
- 自己診断の 1 回は、中断が入ったら、利用者の要求より先に止める対象にする（§4.3）。

## 7. 決定 5: 1.0.0 との関係

### 7.1 ADR 0040 と 0059 のどこを上書きするか（本文は書き換えない）

1. X が文書にある（この ADR の追記と、README）。
2. 自己診断と既定の自動判定が Windows のビルドに入っている（§4、§5）。

4. X 以上の機械の質は、Mac の評価の数字（全セットの 1 位、LM あり）で代表させる、と文書に書く。

### 7.3 README と文書の書き方
- README の「確かめた環境と、確かめていないこと」に、機械の名前ではなく定義で書く（案）: 「言語モデル（LM）は、同梱の自己診断で、温まった推論 1 回の p90 が X ms 以下と測れた機械で、既定でオンになります。満たさない機械でも、LM なしで変換できます（設定でオンにもできます）。作者が確かめた Windows の機械は、この条件を満たさない機械（低スペックの VM）だけです。満たす機械の変換の質は、macOS（Apple Silicon、Metal）の評価の数字で代表させています。」

## 9. 検討して採らなかった案

| 案 | 採らなかった理由 |
| --- | --- |
| 機械の名前・GPU の型番の許可リスト | 作者が確かめられない機械を並べることになる。表の保守が続き、載っていない機械は判断できない。決定 0-2 は数字で決める |
| 常に LM をオンにして、遅ければ利用者に任せる | X に届かない機械で並びが揺れ、CPU と電力を使う（§2）。利用者は原因が分からない。決定 0-2 と合わない |
| 起動のたびに測る | 起動のたびに LM を数秒占有し、ノートの機械では電力を使う。結果はモデル・装置・版が変わらない限りほぼ同じ。測り直しの条件（§4.4）で足りる |
| 実際の使用の推論の時間（`lm_infer_us`）を集めて判定する（受け身の診断） | LM を余計に使わない利点はあるが、入力（読みの長さ、文脈、文節の数）と使い方で値が変わり、X を機械どうしで比べられない。判定まで打ち続ける必要がある。Mac の実機でも p90 93ms と評価の 23ms で大きく違う（§1.3） |
| ベータの利用者の報告を 1.0.0 の条件にする | 作者が待つしかない条件になる。送信の仕組みは作らない（NFR-17）。報告は来た分だけ参考にする |
| 時間貸しの Windows + GPU で測る | 費用と手間がかかり、1 台の数字で X は決まらない。X の根拠は打鍵の間隔と推論の時間の関係で、Mac で作れる（§2）。Mac の曲線で足りないと分かってから検討する |
| 別の CLI（`ikari-lm-diagnose.exe` など）で測る | モデルを 2 つ目のプロセスで読み、利用者の入力とぶつかる。エンジンが LM の空きを知っているので、エンジンの中で譲りながら測るほうが入力を止めない |
| 判定の結果を `settings.tsv` の `engine.lm` に書く | 利用者が選んだ値と、自動で決めた値が区別できなくなる。機械を替えても（設定を持ち出しても）古い判定が残る。入力に忠実・勝手に変えない、と合わない |
| 「ぎりぎり」をオンにする | LM が効く場面はあるが、決定 0-2 は X を満たさなければオフ。設定でオンにできるので、選ぶのは利用者にする（§11 の Q2） |
| 初回の判定までは仮にオフ | 安全側だが、速い機械でも最初の数秒〜数十秒、LM なしになる。測るためにモデルを読むのは同じなので、仮にオンで使う |

## 10. 懸念と前提

1. **自己診断は静かな機械の決まった入力の値で、実際の使用より小さく出る**（§1.4。Mac で約 4 倍の差。内訳は未確認）。X は再生の評価で「自己診断の p90」の目盛りに合わせて決めるので、目盛りの中では一貫する。ただし、実際の使用で負荷が高い機械（ほかのアプリが重い）では、快適と出ても付く率が下がりうる。掃引の報告に、作者の Mac で自己診断と実機の `lm_infer_us` の比も書く。
2. 倍率の包みが、遅い機械の振る舞い（GPU の起動の固定費、メモリの帯域）を真似られる保証はない。固定の `d` との比較（§3.4）で、形の違いの大きさだけは見る。
3. 打鍵の間隔の分布は 2026-10 の 4.3 日分（ADR 0021）で、作者 1 人。Space までの間は 32 日分で、これも作者 1 人。ほかの人の打ち方（遅い人は有利、速い人は不利）は反映していない。
4. 32 回の p90 は粗い（29 番目の値）。区分の境目にいる機械では、測るたびに区分が変わりうる。§4.4 の「快適以外なら 1 回だけ測り直して良いほう」で、オンの側に倒す。
5. 測っている 1 回は止められない（#429）。CPU の遅い機械では、利用者の Prefetch が最悪で約 1 秒（CPU の p99 906ms）待つ。打鍵の間は測らない、と、最初の 8 回の打ち切りで、起きる回数を減らす。
6. 初回の「仮にオン」で、遅い機械では最初の数十秒、並びが揺れる。
7. ADR 0061 の `LmReport` と開発者の表示に、区分を足すかは 4 のレーンで決める（足さなくても §4.5 で足りる）。

## 11. ユーザーに聞く点（推奨つき）

### Q1. X の決め方: 仮置き X = 100ms、判定の基準「付く率 80% 以上を保つ最大の p90」で掃引し、X の最終値は掃引の報告を見てから決める、でよいか
- 推奨: **はい**。80% も計測なしの仮置きで、報告の曲線を見て替えてよい。掃引の前に X を決めると、決定 0-3（Mac の検証で作る）と合わない。

### Q2. X を満たさない機械（「ぎりぎり」も含む）で、LM を自動でオフにしてよいか。初回の判定までは仮にオンで使ってよいか
- 推奨: **はい（両方）**。自動のオフは設定ファイルに書かず、利用者がオンを選べば上書きしない（§5.1）。「ぎりぎり」は理由の文で「設定でオンにできます」と出す。

### Q3. 診断の出し方: 設定アプリの LM の欄（#426 の案内のそば）に、区分と理由の文、「もう一度測る」「自動に戻す」を出し、数字（p50・p90・X）は開発者の表示（`developer.lm_status`）がオンのときだけ出す、でよいか
- 推奨: **はい**。#426 で「ふつうの利用者には数字を出さない」としたのと揃える。issue に結果を貼りたい人は、開発者の表示をオンにすれば数字が見える。
