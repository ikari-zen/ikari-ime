# ADR 0066: セキュリティの前提。だれを敵と見て、何を約束し、何を約束しないか。信頼の根と「通信しない」の守り方

- 状態: 承認（2026-11-16 ユーザー決定。質問はすべて推奨どおり。末尾の「決定済み」を見る）
- 日付: 2026-11-16
- 対象: 方針だけ（コードは変えない）。この ADR の規則は、ADR 0067〜0073（置き場所と起動、プロセス間の口、配布、更新、設定画面と取得、LM、秘密の入力とデータ）の前提になる。全体の地図は [security-design.md](../security-design.md)
- 前提: main = 94f65ae。2026-11-10 の公開前レビュー（#276）と 2026-11-15 の Windows のレビューの脅威の想定、spec NFR-17〜NFR-20、ADR 0004 §8（macOS の Sandbox と署名要件）、ADR 0040 §2.7（署名なしで配り始める）、ADR 0060（モデルは檻に入れる）、ADR 0063 Q2（インストール先は Program Files）
- 判断の置き場所: 規則は OS に依存しない。守る仕組みは Rust（`pipe`、`windows/tip`、`windows/engine-host`、`lm`、`shell-core`）とインストーラ。Swift に足す判断はない
- 既存の指摘の詳細はこの文書に書かない（番号 S1〜S5 だけで参照する。#411〜#413）

---

## 1. なぜ先に決めるか

ikari は打鍵のすべてを受け取り、Windows ではすべてのアプリのプロセスに DLL が入る。個々の対策（パイプの相手の照合、檻、ファイアウォール規則）は入り始めているが、**「だれから何を守るのか」が文書に無い**ので、領域ごとに答えが変わりうる。特に次の 2 つは、どの領域も寄りかかっている。

- インストール先は管理者だけが書ける、という前提（S1 の照合、LM の子の場所、`backends\` の DLL、TIP の資源がこれに頼る）。
- 同じ利用者の権限で動く別のプログラムを、どこまで敵と見るか。

## 2. 守るもの

| # | 守るもの | 補足 |
| --- | --- | --- |
| A1 | 打鍵、読み、左文脈、確定した文 | すべてのアプリの分が ikari を通る |
| A2 | 秘密の入力（パスワード欄など） | 記録も学習もしない（NFR-18） |
| A3 | 学習、ユーザー辞書、設定、ログ | 利用者の書きぐせと語彙が入っている |
| A4 | 利用者の権限でのコードの実行 | ikari の実行物を差し替えられると、すべてのアプリの中で動く |
| A5 | 利用者より高い権限 | TIP は管理者で動くアプリにも読み込まれる。ikari が昇格の足場になってはならない |
| A6 | 「通信しない」という約束 | 利用者が ikari を選ぶ理由の 1 つ（NFR-17） |

## 3. 敵と、信頼するもの

| # | 敵 | 例 |
| --- | --- | --- |
| E1 | 配布の経路に手を入れる者 | Release の差し替え、偽の配布サイト、CI や依存の汚染 |
| E2 | 悪意のあるファイル | 細工したモデル・辞書の束・取り込みファイル・設定ファイルを、利用者に置かせる |
| E3 | 同じ利用者の権限で動く別のプログラム | マルウェア、行儀の悪いアプリ。パイプの名前の先取り、偽の受け口、データのフォルダの書き換え |
| E4 | 同じ機械の、別の利用者（管理者でない） | 共用の PC、端末サービス |
| E5 | ネットワークの途中にいる者 | モデルの取得のとき |

信頼するもの: OS、管理者と SYSTEM、利用者自身。作者のビルドの経路は信頼の対象だが、E1 から守る側でもある（ADR 0069）。

## 4. 決定 1: 約束の線

**P1. ikari は権限の境界を広げない（必ず守る）。** 利用者の権限のプログラムが、ikari を使って、管理者・SYSTEM・別の利用者の権限やデータに届くことがあってはならない。高い権限のプロセスの中の ikari は、低い権限の者が書けるもの（ファイル、パイプ、環境変数、レジストリの HKCU）を信用しない。

**P2. OS が守っているものを、ikari が抜け道にしない（必ず守る）。**
- macOS は、ほかのアプリの打鍵を読むのに利用者の許可（入力監視）を求める。ikari は許可なしで打鍵を受けるので、E3 が ikari の口から打鍵や学習を読めてはならない。→ 相手の確認（署名要件、ad-hoc では cdhash とパス）を、macOS では**防御の本体**として扱う。
- Windows は、高い権限のアプリの打鍵を、低い権限のプログラムから見えなくしている。→ 高い権限のアプリの入力を、ふつうの権限のエンジンに運ばない（素通し。決定済み。ADR 0067）。
- 別の利用者（E4）からは、パイプもデータも開けない。

**P3. Windows で、同じ権限の E3 から打鍵を守るとは約束しない。ただし安い守りは入れる。** 分かっていること: Windows では、同じ利用者の同じ権限のプログラムは、許可なしでキーボードのフックを置け、利用者のファイルを読め、ほかのプロセスにコードを入れられる。ikari がどう作っても、E3 は ikari を通らずに同じものを取れる。ここに「守る」と書くと嘘になる。入れる守りは次の範囲。
- 名前の先取りを防ぐ、相手の実行ファイルのパスを照らす、DACL を絞る（S1、S3、S4）。目的は、コードを入れる手間をかけない相手を止めることと、誤った接続（古い版、開発用のビルド）を止めること。
- この守りが破られても P1・P2 は破られない作りにする（例: 設定の口の相手の確認が破られても、高い権限には届かない）。

**P4. 配る物が本物であることを、署名なしでも確かめられるようにする（E1）。** ADR 0069。

**P5. データは実行物にならない（E2）。** 利用者が書ける場所から読むものは、すべて信用しない入力として読む。そこから実行ファイル、DLL、スクリプト、実行物のパスを取らない。壊れた・細工された入力では、落ちずに「使わない」に倒す。モデルは檻の中で動かす（ADR 0060、0072）。

**P6. 取得の通信は、内容を確かめてから使う（E5）。** https、sha256（あれば）、大きさの上限。ADR 0071。

### 約束しないこと（SECURITY.md に書く）
- 管理者、SYSTEM、OS そのものが敵の場合。
- Windows で、同じ利用者の同じ権限で動くマルウェアから、打鍵と学習データを守ること（P3）。
- アプリが秘密の欄だと知らせない入力欄（NFR-18 の限界。Windows の分は ADR 0073）。
- 利用者が警告を越えて入れた、自由指定のモデルの質（ADR 0060 Q2）。害は檻の中に閉じ込める。

## 5. 決定 2: 信頼の根（置き場所の規則）

| # | 規則 | 今との差（確認した） |
| --- | --- | --- |
| R1 | **実行物は、管理者だけが書ける場所に置く。** Windows は Program Files（ADR 0063 Q2）。インストーラは、置いたあとに ACL を確かめる（ADR 0067） | 製品のインストーラはまだ無い。開発用の導入は利用者が書ける場所（開発用と明示する。ADR 0067）。macOS の `~/Library/Input Methods` は利用者が書けるので、この規則を満たさない（ADR 0069 で扱う） |
| R2 | **実行物の場所は、自分の実行ファイルのパスから決める。** 環境変数、カレントディレクトリ、PATH、HKCU の値から決めない | エンジンの相手（`peer.rs`）、LM の子、`backends\`、TIP の資源は、すでにこの形 |
| R3 | **データの場所（利用者が書ける）から読むものは、信用しない入力。** P5 のとおり | 辞書の読み込みに未対応の項目が残る（#275）。ADR 0073 |
| R4 | **高い権限のプロセスの中では、利用者が書ける場所を読まない・書かない・つながない。** | 素通しの決定がある（2026-11-15）。作りは ADR 0067 |
| R5 | **製品のビルドは、環境変数で挙動を変えない。** データの場所、計測、GPU の切り替えなどの口は、開発用のビルドと CLI・評価だけに残す | 今は `IKARI_USER_DIR`（TIP、engine-host）、`IKARI_TIP_LATENCY`、`IKARI_LM_GPU` が製品のビルドでも読まれる。engine-host には引数 `--data-dir` がある |
| R6 | **1 つの口に、1 つの役割。** 止める、設定を変える、変換する、を同じ口に混ぜない。相手の確認は口ごとに決める（ADR 0068） | エンジンと設定のパイプは別。インストーラがエンジンを止める口は未決（ADR 0064 §6.2） |

## 6. 決定 3: 「通信しない」の定義と守り方

### 6.1 定義
- **ikari のどのプロセスも、利用者の操作なしにネットワークへ出ない。** 操作があって出てよいのは、取得する部品（`ikari-data`。ADR 0071）だけ。キー入力を扱う部品（TIP、殻）、エンジン、LM の子、候補窓、設定画面は、操作があっても出ない。
- OS の部品が ikari と関係なく行う通信（Windows Update、Defender や SmartScreen が ikari のファイルを調べる、エラー報告）は、ikari の約束の外。ただし、ikari の側で止められるもの（エラー報告のダンプ。ADR 0073）は止め、止められないものは文書に書く。
- **ikari が同梱または起動する他社の部品の通信は、ikari の通信として数える。** 止められない通信を持つ部品は、製品に入れない（設定画面の方式の評価に使う。ADR 0071）。

### 6.2 三重に守る

| 層 | 何をするか | 届く範囲 | 限界 |
| --- | --- | --- | --- |
| L1 持たない | 通信の手段をコードに入れない。依存に HTTP・TLS・ソケットの crate が無いこと、できた実行ファイルが通信の DLL（`ws2_32`、`winhttp`、`wininet` など）を取り込んでいないことを、CI で検査する | すべての部品。**TIP を守れるのはこの層だけ**（アプリのプロセスの中なので、OS の規則をかけられない） | .NET の自己完結の配布（候補窓）は、使わなくても通信のライブラリを同梱する。L2 と L3 で受ける |
| L2 OS で禁じる | Windows: インストーラが、ファイアウォールの送信ブロックの規則を、実行ファイルのパスごとに入れる（`ikari-engine-host.exe`、`ikari-lm-host.exe`、`ikari-candidate.exe`、設定画面の exe）。削除のときに消す（決定済み。ADR 0067 で手順）。macOS: エンジンと LM の子は App Sandbox でネットワークの権限なし（済み）。LM の子は、隔離を有効にしたら、それ自体で通信できない（ADR 0072） | 自分の exe | (1) TIP にはかけられない。(2) 規則は管理者が変えられる。別のファイアウォール製品が Windows の規則を無効にしていると効かない。(3) パスに結びつくので、別の場所に置いた exe には効かない。(4) 別の実行ファイルで動く子（他社のランタイム）には効かない。(5) macOS の殻と設定アプリは Sandbox の外なので、L1 だけ |
| L3 確かめる | 版を出す前に、実機で送信を記録し、起動・入力・設定画面・更新の間に ikari のプロセスからの送信が無いことを見る（`docs/windows-real-device-check.md` に項目を足す） | 全体 | 見た範囲だけ |

- 分かったこと: 今の `Cargo.lock` に、HTTP・TLS・非同期のソケットの crate は入っていない（`reqwest`、`ureq`、`hyper`、`rustls`、`tokio`、`mio`、`socket2` が 0 件）。取得は `xtask` が外の `curl` を呼んでいる（製品ではない）。
- 取得する部品を足すときは、別の実行ファイルにし、L1 の検査の対象から名前で外す（「通信してよいのは `ikari-data` だけ」を検査の文にする）。

## 7. 検討した案

- **E3 を完全な敵として、すべての口で相手を認証する（共有の秘密、鍵）**: 秘密を置く場所は利用者のファイルで、E3 は読める。署名が無いので、コードの身元で縛ることもできない。守れないものを守ると書くことになる。採らない。署名が付いたら（NFR-42）、パスの照合を署名の照合に替えられるよう、照合は 1 か所（`peer.rs` の形）に保つ。
- **E3 を敵と見ない（同じ利用者はすべて信頼）**: macOS では OS が守っているもの（打鍵）を ikari が漏らすことになる（P2 に反する）。Windows でも、名前の先取りや誤った接続を止める安い守りを捨てる理由がない。採らない。
- **「通信しない」を、OS の部品の通信まで含めて約束する**: ikari からは止められない。約束できる範囲を狭く正確に書く方を採る。
- **ファイアウォール規則を採らず、エンジンを AppContainer に入れる**: エンジンは利用者のデータのフォルダ全体と名前付きパイプを使うので、AppContainer の設計（フォルダとパイプの ACL、TIP からの接続）が大きい。1.0.0 は規則、AppContainer は LM の子だけ（2026-11-15 の方針。ADR 0072）。

## 8. 結果

- 以後の ADR は、対策ごとに「どの約束（P1〜P6）のためか」「破られたとき何が残るか」を書く。
- 高い権限のアプリでの素通し（R4）と、環境変数の口を閉じること（R5）は、実装の issue になる。
- `SECURITY.md` の「設計上の約束」は、ビルド済みを配るとき（`docs/publish-checklist.md` §4）に、§4 と §6.1 の文で書き直す（原案は security-design.md）。
- 失うもの: Windows の同じ権限のマルウェアに対して、ikari は追加の守りを名乗らない。利用者によっては物足りなく見える。正確さを優先する。

## 9. 推測（確かめていないもの）

- Windows ファイアウォールの送信ブロックの規則が、ループバック（同じ機械の中の TCP）にも効くかは確かめていない。ikari はループバックを使わないので、設計には影響しない。
- 別のファイアウォール製品が入っている機械で、インストーラが入れた規則がどう扱われるかは確かめていない。
- .NET とWindows App SDK の実行時が、自分から通信することは無い見込み（L3 で確かめる。ADR 0071）。

## 10. ユーザーに聞くこと

### 決定済み（ユーザー、2026-11-16。すべて推奨どおり）

- **Q1**: 約束の線は §4 のとおり。Windows では、同じ利用者の同じ権限のマルウェアから打鍵を守るとは約束せず、`SECURITY.md` にそう書く。P1・P2 は必ず守る。
- **Q2**: 製品のビルドでは、環境変数の口を閉じる（R5）。
- **Q3**: 同梱または起動する他社の部品の通信を、ikari の通信として数える（§6.1）。

### （記録）決定の前の問い

- **Q1. 約束の線（§4）。** Windows では「同じ利用者の同じ権限のマルウェアから打鍵を守る」とは約束せず、`SECURITY.md` にそう書く。権限の境界（P1）と、OS が守っているもの（P2）は必ず守る。**推奨: この線にする。** 守れないことを書かない方が、利用者の判断を誤らせない。
- **Q2. 製品のビルドでは、環境変数の口を閉じる（R5）。** `IKARI_USER_DIR` などは、CLI・評価・開発用のビルドだけで読む。製品でデータの場所を変えたい人は、当面は変えられない（要望が出たら、管理者だけが書ける場所の設定として設計する）。**推奨: 閉じる。**
- **Q3. 「通信しない」に、同梱する他社の部品の通信を数える（§6.1 の 3 つ目）。** これを採ると、止められない通信を持つ部品（設定画面の方式の候補を含む）は製品に入れられない。**推奨: 数える。**
