# ADR 0056: 周辺テキストが取れないアプリでの確定後の文節削除（奪わず、アプリに渡す）

- 状態: 却下（2026-11-07 ユーザー決定。変更なし。Q1 は「奪わない」、Q2 は (a)、Q3 は不要）
- 日付: 2026-11-07
- 対象: なし（コードは変えない。ADR 0050 の D5 と §12 Q1 は変えない）
- 前提: main = f703e54。ADR 0050（文節ごとの削除。D5 と §12 の Q1）、ADR 0053（取り消し。英字の直前の素通し）、ADR 0006 §9.5（拒否リスト）、ADR 0042（判断は Rust）
- タスク: #193 の続き（実機の報告 2026-11-07）

---

## 0. 現状の把握

### 0.1 分かったこと（コードと実機で確かめた）

- 実機（2026-11-07）: 確定の直後、キャレットが文末にある状態の Option+Delete が、メモでは文節を消し、VS Code では**文がまるごと消えた**。macOS の単語の削除は、空白のない日本語では句読点までをひとまとまりに消す。
- 確定後の削除は `committed_target`（`shell-core/src/machine/clause_delete.rs`）で対象を作り、作れなければ `idle_delete` が `PassThrough` を返す（ADR 0050 D5）。断る条件は次のとおりで、**どれも同じ `None` で、理由を区別していない**:
  - 拒否リスト（`clause::CLAUSE_DELETE_DENIED_BUNDLES` = Terminal と iTerm2）
  - `surrounding()` が `None`（Swift の `surroundingText()` は、`selectedRange` が `NSNotFound` か、左の 2000 文字の読み出しが nil のとき nil）
  - `caret` が `None`、選択が空でない、`is_available` が偽（左が空で文書の長さが 0）、`left_matches_caret` が偽（位置の検査）
  - 直前が英字（`ends_with_ascii`。ADR 0053 §6.3）
  - 切り出した文が空、`Reconvert` の失敗・時間切れ、区切りが文と食い違う
- shell-core は、**ikari が確定した文字列を覚えていない**。確定は `commit_converting`（文節の表記の列 `segments` がその場にある）、`commit_text`（1 文節）、ショートコードなどの口で `ShellAction::Commit` を返し、確定履歴はエンジンへ送るだけ（`CommitText`、`CommitSegments`。再変換の `pieces_from_history` はエンジンの側）。
- Swift から取れるもの（`ClientAccess.swift`）: `selectedRange`、`markedRange`、`length`、`string(from:actualRange:)`、`insertText(_:replacementRange:)`、`setMarkedText`。**キャレットを動かす API と、キーを合成して送る API は IMK にない**（ADR 0050 D10）。マウスのクリックは、変換中の文字列がない間は IMK に届かない。
- VS Code では、IMK の `attributes(forCharacterIndex:)` が絶対位置ではなく相対位置で答える（ADR 0004 の S0-3。`caretRects` の注記）。

### 0.2 推測（確かめていない）

- VS Code で文節削除が断られた理由は、次のどれかと考えられる。H1: `selectedRange` が `NSNotFound`（周辺テキストなし）。H2: Monaco の隠れた入力欄が短く、左が空で長さ 0（`is_available` が偽）。H3: 相対位置で `left_matches_caret` が偽。H4: Option+Delete が IMK の keyDown に届かず、アプリが先に処理した。H5: `Reconvert` の時間切れ。
- 断った理由のログは出していないので、どれかは確かめていない。VS Code が周辺テキストを返さない可能性が高い、というのは推測である。
- Chrome の URL 欄、Claude のデスクトップアプリの入力欄、Slack も、H1〜H3 のどれかに当たるかもしれない（推測）。

## 1. 問題の定義

1. 周辺テキストが取れないアプリで、確定後の Option+Delete を断ってアプリに渡すと、日本語の文ではアプリの単語の削除が**文をまるごと消す**。これは「意図しない大きな削除」で、方針の 2（ユーザーの意図に忠実）に反する。
2. 一方で、ikari が奪って何もしない（段階 1）のは、押しても何も起きない。ユーザーが Option+Delete で何を望んでいたかは ikari には分からず、何もしないことも、ユーザーの意図に反するおそれがある。
3. 覚えた文字で消す（段階 2）には、キャレットがまだその直後にあることを確かめる手段が要る。クリックは IMK に見えないので、キーの情報だけでは確かめられない。違う位置を消すおそれがある。

## 2. 決定

周辺テキストが取れないアプリでは、確定後の Option+Delete を**奪わず、今までどおりアプリに渡す**（`PassThrough`）。

| # | 決定 |
|---|---|
| D1 | 周辺テキストが取れないアプリでは、確定後の Option+Delete を `PassThrough` する（今のまま。奪わない） |
| D2 | 覚えがないとき（クリック、矢印、貼り付けのあと）も `PassThrough` する（§8 の Q2 は (a)） |
| D3 | 段階 1（奪って何もしない）と段階 2（確定した文字を覚え、読み戻しで一致したときだけ消す）は、やらない |
| D4 | ADR 0050 の D5 と §12 の Q1 は変えない（今のまま維持） |
| D5 | 結果として、VS Code などでは文節削除は働かず、アプリ自身の単語の削除が働く。日本語の文は文全体が消えることがある。**既知の制限として受け入れる** |

- 周辺テキストがあるアプリ（メモなど）は、今までどおり文節削除が働く。この決定で変わるのは、周辺テキストが取れないアプリだけ。
- 理由（ユーザー決定。2026-11-07）: 奪って何もしないのは、ユーザーの意図に反するおそれがある。段階 2 は違う位置を消すおそれがあり、リスクが高い。どちらも ikari が判断するより、ユーザーが判断する。

## 3. 実機で分かったこと（2026-11-07）

- メモ: 確定の直後の Option+Delete で文節が消えた。
- VS Code: 素通し（今の動作）で、アプリの単語の削除が文を全部消した。
- 原因: 0.2 のとおり推測。断った理由のログがないため、確かめていない。

## 4. 検討した案

| 案 | 中身 | 良い点 | 悪い点 | 結論 |
|---|---|---|---|---|
| 1 | 段階 1: 周辺テキストが取れないときは、覚えがあれば奪って何もしない（`Consume`） | 文がまるごと消えない | 押しても何も起きない。ユーザーの意図に反するおそれ。覚えの有無で線引きする仕組みが要る | **却下**（ユーザー決定。2026-11-07） |
| 2 | 段階 2: ikari の確定を覚え、キャレットの直前を読み戻して一致したときだけ消す（許可リストのアプリだけ） | VS Code などで文節削除が使える可能性 | 読み戻しでは削除の座標まで確かめられない。クリックのあとに違う位置を消すおそれ。覚えを保つ口、読み戻しの契約、取り消しの扱いを足す | **却下**（ユーザー決定。リスクが高く、ユーザーが判断） |
| 3 | 今のまま `PassThrough` | 変えない。ikari は文書を消す新しい経路を持たない | 日本語の文がアプリの単語の削除でまとめて消えることがある | **採用**（§2） |

- 案 1 と案 2 の設計（覚えの型、断りの理由の分類、読み戻しの関数など）は、この ADR には残さない。見直すときは、コミット c33986d の版を出発点にする。
- 案 1 の亜種（日本語のモードなら、覚えがなくても奪う）は、§8 の Q2 の (b) として検討し、採らなかった。

## 5. 結果

### 得たもの

- ikari が、文書を消す新しい経路を持たない。コードの変更がない。
- 押したキーを ikari が止めないので、アプリの単語の削除など、アプリ側の操作はそのまま使える。

### 失ったもの（既知の制限）

- 周辺テキストが取れないアプリ（VS Code など。ほかは未確認）では、確定直後の Option+Delete で文節の削除が働かない。アプリ自身の単語の削除が使われ、日本語の文は文全体が消えることがある。
- 「断った理由を区別する型」は作らない。診断ログは別のタスクで、必要な理由の名前を決める。
- 使い方の注意として文書に書くかどうかは、この ADR では決めない（ユーザーの判断）。

## 6. 将来見直す条件

次のどれかが分かったときに、見直す。見直すときは、新しい ADR を起こし、この ADR は Superseded にする。

- アプリが周辺テキストを返すようになった（VS Code などで `selectedRange` と `string(from:)` が使える）。
- キャレットの位置を、クリックのあとでも確実に確かめられる手段が分かった（IMK 以外の API を含む）。
- 段階 2 で違う位置を消さないことを、実機で確かめられる方法が分かった。

## 7. 残るリスク

1. 周辺テキストが取れないアプリで、日本語の文がアプリの単語の削除で文全体が消える（D5）。
2. H1〜H5 のどれが原因かは未確認。原因が H4（キーが IMK に届かない）なら、この決定とは別の問題になる。

## 8. ユーザーへの質問（回答つき）

- **Q1. 周辺テキストが取れないアプリで、ikari が確定した直後の Option+Delete**
  - (a) キーを奪って何もしない（段階 1）
  - (b) 今どおりアプリへ渡す（文がまるごと消えうる）
  - **回答（2026-11-07）: (b) 奪わない。今までどおりアプリに渡す。** 何もしないのは、ユーザーの意図に反するおそれがある。ADR 0050 の D5・§12 Q1 は変えない。
- **Q2. 覚えがない（クリック、貼り付け、矢印のあと）ときの、周辺テキストが取れないアプリでの Option+Delete**
  - (a) 今どおりアプリへ渡す
  - (b) 日本語のモードなら奪って何もしない（英語のモードはアプリへ渡す）
  - **回答（2026-11-07）: (a)。** 日本語のモードのまま英語のコードを直す人の、単語の削除を奪わない。
- **Q3. 段階 2（覚えと読み戻しで実際に消す）**
  - (a) 確かめたアプリだけで有効にする（許可リスト）
  - (b) 読み戻しが一致すれば、どのアプリでも消す
  - (c) 段階 2 はしない
  - **回答（2026-11-07）: 不要（(c) 段階 2 はしない）。** 違う位置を消すおそれがあり、リスクが高いため。
