# ADR 0031: キーマップ（入力配列）エンジンの方式。第 1 段階（キーの入れ替え）は hidutil、第 2 段階以降（Mod-Tap、レイヤー、薙刀式）は IME と別の常駐エンジン（キーボードの占有 + CGEventPost。root）で作る

- 状態: 承認（2026-10-23。§9 の 3 つは推奨どおり）
- 日付: 2026-10-23
- 対象: 新しいキーマップの層（OS のレベル。ikari の殻とエンジンの外）、設定アプリ（配列の選択）、配布（常駐の登録と承認）。issue #227（まとめ）、#199（入力配列）、#201（キーボードごとの切り替え）。この ADR ではコードを変えない
- 前提: main = bbd29cb。spec の方針の 3 本柱（柱 3: 速さは入力配列とショートカットで出す）、[ADR 0026](0026-english-mode-and-key-stats.md) D5（secure の間は素通しで記録しない）
- 根拠: スパイク S1（ブランチ `spike/imk-keyup-log`）、S2'（`spike/hid-seize-remap`）、S3（#228、`spike/naginata-overlap`）の実機・コードの結果。数値は #227 のコメント（2026-10-23）から。私は実機に触っていない

## 1. コンテキスト

### 1.1 求めること（ユーザーの決定。#227、2026-10-22〜23）
- 段階: 第 1 = キーの入れ替え（大西配列。US QWERTY で確かめる）、第 2 = Mod-Tap、レイヤー、Layer-Tap、Tap Dance、第 3 = 薙刀式（ZMK と同じ挙動）、第 4 = GUI（Vial のような使い心地）。
- みんなに使ってもらう機能にする。**OS のレベルで変える**（パスワード欄でも効かせる）。Karabiner-Elements は使わない方針（実験してから最終決定）。

### 1.2 分かったこと（実機のログ）
| 項目 | 結果 | 出どころ |
|---|---|---|
| IMK の keyUp | recognizedEvents に keyUp を足しても **0 件**。flagsChanged（修飾キー）とリピートの keyDown は届く | S1（1546 行） |
| IMK の keyboardType | 全件 0。どのキーボードからの打鍵か分からない | S1 |
| hidutil | root も許可も不要。Safari / Chrome のパスワード欄で a↔s が効いた | S2' |
| 占有 + CGEventPost | Bluetooth のキーボードの占有に **root が要る**（非 root は `kIOReturnNotPrivileged`）。入力監視の許可も要る。パスワード欄で効いた。secure の間も打鍵を受け取れた。遅延 p50 0.13ms / p95 0.6ms（起動直後の 1 打鍵だけ約 50ms）。`kill -9` のあと、キーボードは普通に使え、再占有もできた | S2' |
| 仮想キーボード（IOHIDUserDevice） | entitlement なしは作れない。entitlement つきの署名は起動直後に OS が kill。Apple の承認が要る | S2' |
| リピート | root で動かすと root の設定（375ms / 90ms）になり、ユーザーの設定（450ms / 30ms）と違った | S2' |
| 薙刀式の判定 | 時間ではなく押している間の重なりだけ（T/Y の長押しを除く）。keyUp を落とすと以後の判定が狂う | S3 |

### 1.3 未確認
- hidutil の設定が、抜き差し・スリープ・再起動のあとに残るか（A6、A7）。キーボードごとの指定（`--matching` で VendorID / ProductID）が効くか。
- 2 キーの重なりの順序（B5）、押しっぱなしで kill したとき（キーが押されたままにならないか）、ikari の英語のモードと ABC での確認。
- root の常駐を、ユーザーの Mac に配る方法（LaunchDaemon の署名・承認）。
- 変換（HID 0x8A）と無変換（0x8B）を、占有しないとき macOS がどう扱うか。

## 2. 決定（案）

| # | 決めること | 決定（案） |
|---|---|---|
| D1 | 第 1 段階の方式 | **hidutil の UserKeyMapping**。ユーザーの権限で動く小さな常駐（LaunchAgent。root 不要）が、ログイン時と、キーボードがつながったときに設定を入れ直す。入れ直しが要るかは A6・A7 の結果で決め、要らなければ常駐を作らない |
| D2 | 第 2 段階以降の方式 | **IME と別のプロセスのキーボードエンジン**。指定したキーボードだけを IOHIDManager で占有し、keyDown / keyUp と時刻から自分で作り直して CGEventPost で送る。Bluetooth のために root で動かす（LaunchDaemon） |
| D3 | IME の中でやる案 | **やらない**。IMK は keyUp を渡さない（S1）。パスワード欄では ikari が素通しになる（ADR 0026 D5） |
| D4 | Karabiner-Elements | **使わない**ことを確定する（§3.2 の理由）。ユーザーに Karabiner の設定を配る形もとらない |
| D5 | 配列の定義 | 1 つの定義（キーの名前は HID の usage で書く。人が読み書きできるテキスト）を、第 1 段階では hidutil の表に変換し、第 2 段階ではエンジンが読む。段階が上がっても定義を書き直さない。書式の細部は第 1 段階の契約で決める |
| D6 | キーボードごと（#201） | 第 1 段階は hidutil の `--matching`（未確認。A6・A7 と一緒に確かめる）。第 2 段階は「占有するキーボード」を選ぶことでそのまま決まる。**ファームウェアで配列を変えているキーボード（作者の ZMK）は既定で対象外** |
| D7 | ikari との関係 | 依存は一方向。キーマップの層は ikari を知らない。ikari は、変わったあとのキーを今までどおり受ける（ZMK で変えた打鍵を受けるのと同じ）。ikari のショートカット（キーコードで見るもの）は、入れ替えたキーの位置に移る |

## 3. 検討した案

### 3.1 第 1 段階（キーの入れ替え）
| 案 | 長所 | 短所 | 判断 |
|---|---|---|---|
| **A1 hidutil** | 許可も root も要らない。パスワード欄で効いた（実測）。IME の外なので、ikari・ABC・ほかの IME のどれでも同じ | 永続しない見込み（推測。A6・A7 で確かめる）。入れ直しの常駐が要るかもしれない。1 対 1 の入れ替えだけ | **採用** |
| A2 .keylayout（キーボードレイアウトのファイル） | 許可なし。OS 標準の仕組み | IME を使っている間のレイアウトは、IME 側の指定（ASCII を打てるレイアウトの上書き）と絡む（推測、未確認）。キーボードごとに分けられない。キーコードは変わらないので、キーコードで見るショートカットとずれる（推測） | 不採用。hidutil で足りた |
| A3 IME の中で変換 | 実装が ikari の中で閉じる | パスワード欄で効かない（secure の間は素通し。macOS が入力ソースを替える）。ikari 以外の入力ソースで効かない | 不採用（ユーザーの決定「OS のレベル」に反する） |

### 3.2 第 2 段階以降（keyUp と時間が要るもの）
| 案 | 長所 | 短所 | 判断 |
|---|---|---|---|
| **B1 占有 + CGEventPost（root の常駐）** | パスワード欄で効いた。secure の間も受け取れた。遅延は十分に小さい。キーボードごとに対象を選べる | Bluetooth で root が要る。全部の打鍵（パスワードを含む）を root のプロセスが見る。配布に署名・承認の手間（§5） | **採用** |
| B2 IME の中（IMK） | 許可が要らない | keyUp が来ない（実測）。パスワード欄で効かない | 不可 |
| B3 IME + IOHIDManager で keyUp だけ聞く | root が要らない（推測） | keyDown（IMK）と keyUp（HID）の 2 経路の順序がずれうる（推測）。パスワード欄と ikari 以外で効かない | 不採用 |
| B4 CGEventTap（ユーザー権限の横取り） | root が要らない見込み（推測） | secure の間はキーを受け取れないと見られる（推測、未測定）。そうならパスワード欄で効かない | 不採用。ただし S5 で secure の間の受信だけ測り、受け取れるなら B1 と比べ直す |
| B5 仮想キーボード（IOHIDUserDevice / DriverKit） | 送ったキーが本物のキーボードと同じに見える | entitlement なしは作れない、つきは OS が kill（実測）。Apple の承認が要る | 不可 |
| B6 Karabiner-Elements | 完成している。Mod-Tap などもある | 方針で使わない。占有が Karabiner と衝突する。薙刀式の重なり判定（S3）を入れられない。「みんな」に別アプリを入れてもらう前提になる | 不採用（D4） |

## 4. 安全策（第 2 段階のエンジン。決定（案））
1. **落ちたとき**: 占有はプロセスが終われば OS が外す（`kill -9` で実測）。launchd で自動で再起動する。起動のたびと終了の前に、送ったまま離していないキー（特に修飾キー）の keyUp を送る（押しっぱなしの kill は未確認。S5 で確かめる）。非常口のキー（スパイクの 左Control+左Shift+Escape）は残す。**内蔵キーボードは既定で占有しない**（エンジンが壊れても打てる手段を残す）。
2. **secure input**: secure の間も配列は変える（パスワード欄で効かせるのが目的）。ただし **打鍵を記録しない、ファイル・ログ・ほかのプロセスに打鍵の中身を出さない**（ADR 0026 D5 と同じ考え）。ログはキーの種類と時刻の統計だけにし、文字は出さない。ikari のエンジンと打鍵の中身をやりとりしない（D7）。
3. **リピート**: 占有したキーボードは OS が自動のリピートをしないので（S2' でエンジンが自分で作っていた）、エンジンが作る。間隔は **ログインしているユーザーの設定**（キーのリピートと、リピート入力認識までの時間）を読み、変わったら追う。root の設定は使わない。
4. **キーの対応表の漏れ**: 占有すると、表にないキーは失われる。HID の usage → macOS のキーコードの表を、キーボードが宣言する全キーについて持つ。**変換（0x8A）と無変換（0x8B）を入れる**。macOS がこの 2 つを占有しないときにどう扱うかを先に測り（S5）、同じ動きにする。表にないキーが来たら、ログに usage だけ出して捨てる（推測で別のキーにしない）。
5. **値**: Mod-Tap、Tap Dance のタイムアウトなどの時間の値は、実機で測ってから決める（PR で値を明示してユーザーに確認）。

## 5. 配布と範囲（選択肢と推奨。決めない）

### 5.1 root の常駐の配り方（推測を含む）
- macOS の SMAppService で、アプリに入れた LaunchDaemon を登録できる（推測。macOS 13 以降の仕組み。未試行）。ユーザーはシステム設定の「ログイン項目」で許可し、入力監視の許可も別に要る。
- 作者の Mac だけなら、今の Apple Development の署名で動く見込み（推測）。**ほかの人に配るには、Developer ID の署名と公証が要る**（推測。Gatekeeper の通常の扱い）。費用と手間がかかる。
- root で全打鍵を見るプロセスなので、ほかの人に入れてもらうには、ソースの公開と、何を送り何を記録しないかの説明が要る。

### 5.2 範囲・名前・リポジトリ
第 2 段階以降は「日本語 IME」ではなく「OS 全体のキーボードエンジン」になる。

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| R1 同じリポジトリ、同じ名前 | `ikari-ime` に入れ、ikari の機能として出す | 手間が最小 | 範囲がぼやける。IME を使わない人に届きにくい。root の常駐が IME の配布物に入る |
| **R2 同じリポジトリ、別の製品として始め、配る前に分ける** | 今はこのリポジトリに独立のディレクトリ（別のバイナリ、別の名前の候補）で作る。ikari のコードに依存しない。ほかの人に配る段階（Developer ID が要る時点）でリポジトリを分ける | 今の CI、check.sh、エージェントの運用をそのまま使える。境界を先に守るので、分けるのが安い | 分けるまでの間、リポジトリの名前と中身が合わない |
| R3 今すぐ別のリポジトリ | 名前もリポジトリも最初から分ける | 範囲が明確。配布と権限の説明が IME と混ざらない | CI、フック、エージェントの指示を二重に持つ。第 1 段階（小さい）のためには重い |

推奨は R2。第 1 段階（hidutil）は小さく root も要らないので、ikari の設定アプリから選べる形でもよい。名前は第 2 段階の着手前に決めればよい。

## 6. issue の切り方（決定（案））
- **#227**: まとめの issue のまま（この ADR と段階の一覧）。
- **S4（新、user-needed）**: hidutil の永続性（抜き差し、スリープ、再起動。A6・A7）、`--matching` のキーボードごとの指定、変換・無変換を占有しないときの macOS の動き。第 1 段階の前提。
- **第 1 段階（新）**: 配列の定義の書式（契約）、hidutil への変換、設定アプリでの選択、（S4 の結果しだいで）入れ直しの常駐。大西配列を US QWERTY で確かめる。
- **#199**: 大西配列の部分は第 1 段階の issue に移す。**#199 は薙刀式（第 3 段階）の issue に絞って題を改める**（ZMK の送り方 A・B・C の整理と S3 の結果が、ここにあるため）。
- **#201**: 第 1 段階で hidutil のキーボードごとの指定が効けば、そこで閉じる。効かなければ、第 2 段階のエンジン（占有するキーボードを選ぶ）で閉じる。依存先を第 1 段階の issue に替える。
- **S5（新、第 2 段階のスパイク）**: SMAppService での LaunchDaemon の登録と承認（作者の Mac）、押しっぱなしの kill、2 キーの重なりの順序（B5）、ユーザーのリピートの設定、CGEventTap が secure の間に受け取れるか（B4 の確認）。
- **第 2 段階（新）、第 4 段階（新、GUI）**: S5 のあと、別の ADR で書式と GUI を決めてから起こす。
- spike のブランチ（`spike/imk-keyup-log`、`spike/hid-seize-remap`）と #228 はマージしない。S5 は `spike/hid-seize-remap` を元にしてよい。

## 7. 結果
- 第 1 段階は root も許可もなしで、ikari 以外の入力ソースとパスワード欄でも効く。代わりに、永続性は OS の挙動に頼る（S4 で確かめる）。
- 第 2 段階以降は、root の常駐という重い前提を受け入れる。代わりに keyUp と正確な時刻が取れ、薙刀式（S3 の移植）と Mod-Tap を、パスワード欄を含めて同じ動きにできる。
- ikari 本体（殻とエンジン）は変わらない。キーマップの層が ikari に依存しないので、別の製品として分けられる。
- 「ikari が有効なときだけ効く」案（#227 の当初の問い）はなくなった。

## 9. ユーザーに聞くこと
1. **第 2 段階で root の常駐（LaunchDaemon）を入れてよいか。** Bluetooth のキーボードを占有するには root が要る（実測）。ほかの方法（仮想キーボード、Karabiner）は使えないか方針外。推奨: 受け入れる。まず作者の Mac だけで S5 を行い、ほかの人に配るのは Developer ID の署名と公証を用意してから。
2. **範囲・リポジトリ（§5.2）。** 推奨: R2（今はこのリポジトリで独立した製品として作り、ほかの人に配る前に分ける。名前は第 2 段階の前に決める）。
3. **#199 と #201 の扱い（§6）。** 推奨: #199 を薙刀式（第 3 段階）に絞り、大西配列とキーボードごとの指定は第 1 段階の新しい issue に移す。#201 は第 1 段階の hidutil のキーボードごとの指定が効けばそこで閉じる。

**ユーザーの回答（2026-10-23）**: 1・2・3 とも推奨どおり承認。第 2 段階の root の常駐は受け入れる（まず作者の Mac だけで S5。配る前に Developer ID の署名と公証）。範囲・リポジトリは R2。#199 は薙刀式に絞り、大西配列とキーボードごとの指定は第 1 段階の新しい issue に移す。
