# ADR 0077: macOS の LM の檻の段 2（専用の Sandbox）の形。檻役の XPC サービスを置き、殻が口を仲立ちする

- 状態: 承認（2026-11-17 ユーザー決定（Fable の指摘つき）。Q1〜Q3 はリードの推奨どおりで、条件が付いた。§11 を見る）
- 日付: 2026-11-17
- 対象: `lm/src/host/`（子の起動の口を 2 つにする。檻役との取り決め）、新しい bin `ikari-lm-cage`（檻役。Rust）、`ikari-lm-host`（親が終わったら自分も終わる）、`engine` / `engine-ffi`（檻役の口を受け取る。モデルを fd で渡す）、`macos/Sources/IkariXPC`・`IkariEngineService`・`IkariSmoke`（口の受け渡し）、`macos/scripts/build.sh` とテンプレート（新しい XPC サービスの束と署名）、`docs/architecture.md` §2 と表。この ADR ではコードを変えない
- 前提: origin/lane/d3-mac = 7a78dc7。[ADR 0072](0072-lm-cage-levels.md)（段の分け方、§4 の出してよい条件、§13 の実測）、[ADR 0060](0060-user-selectable-lm-model.md) Q4（別プロセス、落ちてもエンジンは生き残る）、[ADR 0004](0004-phase2-macos.md) §5.1（殻とエンジンの XPC）、[ADR 0068](0068-ipc-endpoints.md)（口の一覧と相手の確認）、[ADR 0069](0069-distribution-authenticity.md) §6（ad-hoc の配布）、`docs/architecture.md` §2 と「LM の子」の行
- 判断の置き場所: Rust。いつ起動し、いつ止め、何回で諦めるかは今までどおり `lm/src/host`（エンジン）。檻役（`ikari-lm-cage`。Rust）は、決まった実行ファイルを決まった引数で起動し、止めて回収するだけで、判断を持たない。Swift に足すのは、XPC サービスを名前で探して口をエンジンに渡すことだけ（XPC サービスはアプリ本体からしか探せない。OS の制約。§13.5）
- ほかの ADR との関係: 0072 §3 の「macOS: 専用の Sandbox（書き込みなし）」を、実測に合わせて改める（§5。Q2）。0072 §4.3 の「プリセットまで段 2 にするかは計測のあと」に答える（§6。Q3）。0060 Q4 と 0072 §5 は変えない

## 1. 現状（分かったこと。ADR 0072 §13 の実測）

- 今の製品: 殻（`ikari.app`。Sandbox なし）→ XPC → エンジン（`IkariEngine.xpc`。App Sandbox）→ `posix_spawn` → `ikari-lm-host`（entitlement なし。エンジンの Sandbox を引き継ぐ）。取り決めは標準入出力のパイプ（`lm::host::proto`）。起動、締め切り、kill と wait、連続失敗の数え方はエンジンの `lm/src/host/scorer.rs` と `os/apple.rs`。
- エンジンが自分の子として起動する形のままでは、子をエンジンより狭い Sandbox に入れられない（子に `app-sandbox` だけを付けると起動の直後に SIGTRAP、`inherit` は狭くならない、子の `sandbox_init` は EPERM）。
- 別の起動元なら張れる。A) 檻役の XPC サービス（`app-sandbox` だけ）が起動した子は、檻役の Sandbox を引き継ぐ（子に entitlement は要らない）。エンジンは隣の XPC サービスを名前で探せない（`Connection invalid`）ので、殻が匿名の口（`xpc_endpoint`）を仲立ちする。エンジンから檻の子へ signal は送れない。B) Sandbox なしの殻が、専用の entitlement の子を直に起動する。C) LaunchAgent と mach-lookup の例外（未検証）。
- モデルは、親が開いた fd を 3 に付けて `--model /dev/fd/3` で渡せば読める（子のコードの変更は要らない）。Metal は専用の Sandbox でも動く。速さは引き継ぎの形とほぼ同じ（Ready 77〜153ms、採点の中央値 13〜22ms。実行ファイルが変わった最初の 1 回だけ Ready まで約 4〜5 秒）。
- 専用の Sandbox でも、自分のコンテナへの書き込み、システムの読み取り、プロセスの起動は残る（App Sandbox の既定）。

## 2. 問題

- 段 2 が無いと、macOS で自由指定のモデル（ADR 0072 §4.2）を出せない。今の子はデータのフォルダ（学習、ユーザー辞書、設定）を読み書きできる。
- 段 2 を作るには起動元を変えるしかなく、殻とエンジンの取り決め、監督（誰が子を見張り、止めるか）、束の作りと署名、smoke が変わる。どの形にするかを決める。

## 3. 決定 1（Q1）: 形は A。檻役の XPC サービス `IkariLMCage.xpc` を置く

```
ikari.app（殻。Sandbox なし）
  ├─ XPC（今の Envelope の口）──────────────→ IkariEngine.xpc（App Sandbox。エンジン。llama.cpp なし）
  │    ＋ 檻役の匿名の口を渡すメソッドを 1 つ足す         │ 匿名の口で檻役へ: 「起動」（パイプ 2 本とモデルの fd、GPU の別）/「止める」
  └─ XPC（名前で探す。口をもらうだけ）──→ IkariLMCage.xpc（app-sandbox だけ。例外なし。檻役）
                                                     └─ posix_spawn → ikari-lm-host（檻役の Sandbox を引き継ぐ。entitlement なし）
                                                           標準入出力のパイプはエンジンにつながったまま（今の取り決めのまま）
```

### 3.1 役割（依存は一方向: 殻 → エンジン、殻 → 檻役、エンジン → 檻役）

| 役 | すること | しないこと |
| --- | --- | --- |
| 殻（Swift の `IkariXPC`） | 檻役に名前でつなぎ、匿名の口をもらう。エンジンへの `Hello` のたびと、檻役との接続が切れて取り直したあとに、口をエンジンに渡す | LM の起動・停止・状態を知らない。口の中身を見ない |
| エンジン（Rust の `lm/src/host`） | 今までどおりすべての判断（起動の時期、締め切り、止める、連続失敗の数え方、CPU への切り替え、アイドルの解放）。パイプを作り、モデルを開き（パスはエンジンが決める。ADR 0072 §6）、fd を檻役に渡す | 子を自分で起動しない（製品のビルド）。子に signal を送らない |
| 檻役（Rust の bin `ikari-lm-cage`） | 1 本の接続につき子を 1 つまで、檻役の全体でも上限の数まで起動する（§3.2 の起動の規則）。実行ファイルは自分の束の中の `ikari-lm-host` の絶対パスだけ、引数は GPU の別（列挙）から自分で組む。「止める」で SIGKILL して回収してから返事。接続が切れたら（エンジンが落ちた、エンジンが捨てた）子を止めて回収する。子がいる間は終わらない（トランザクションを持つ） | 判断を持たない。任意の引数・パス・環境変数を受けない。エンジン以外からの「起動」を受けない。設定も状態もコンテナから読まない |
| 子（`ikari-lm-host`） | 今のまま。足すのは、親（檻役）が終わったら自分も終わる見張り（固まった子が残らないように） | — |

### 3.2 取り決めへの影響

- **殻とエンジンの XPC**: Envelope の口（`handle(Data)`）は変えない。NSXPC のプロトコルに、檻役の口（`xpc_endpoint_t`。`NSXPCInterface.setXPCType` で渡す）を受けるメソッドを 1 つ足す。古い殻は呼ばないだけなので、エンジンは「口が無い → LM なし」で動く。`schema_version` は上げない（Envelope は変わらない）。
- **エンジンと檻役**: 新しい口。取り決め（辞書のキー、「起動」「止める」、返事の固定の語）は Rust の 1 つのモジュール（`lm::host::cage`）に置き、エンジンの側と檻役の側の両方がそれを使う。版を持たせ、違えば起動の失敗に数える。
- **エンジンと子**: 変えない（`lm::host::proto` の枠、`PROTOCOL_VERSION`）。モデルの渡し方だけ、macOS は常に fd 3 にする。
- **相手の確認**: 檻役の名前の口は殻（と開発の smoke）だけ、匿名の口はエンジンだけを受ける（libxpc の署名要件の確認。要件の出どころは今の `SigningRequirements` に足す）。team の署名ではチーム ID と識別子、ad-hoc では識別子の一致（今のエンジンと同じ強さ。ADR 0069 §1 の限界のまま）。
- **エンジンの側も、もらった口の先が本物の檻役かを、署名要件で確かめる**（2026-11-17 決定の条件 1）。確かめるまでは、モデルの fd も採点の入力（左文脈）も渡さない。理由: 口は殻から来るので、殻が偽の口を渡すと、エンジンはモデルと左文脈を偽の相手に渡してしまう。確かめに失敗したら、その口を捨てて「檻なし」（LM なし）にする。
- **檻役の子の起動の規則**（2026-11-17 決定の条件 2〜4）:
  - `posix_spawn` に `POSIX_SPAWN_CLOEXEC_DEFAULT` を付け、子に付ける fd は 0・1（パイプ）と 3（モデル）だけにする。ほかの fd（XPC、ログ、檻役が開いたもの）は子に渡らない。
  - 子の環境変数は固定の空にする（檻役の環境も、エンジンから来た値も渡さない）。
  - 子の数は、接続ごとの 1 つに加えて、**檻役の全体で上限を置く**（接続を何本も張られても、子が増え続けないため）。上限の値は契約のレーンで決め、PR に書いてユーザーに確かめる。
  - 檻役は、設定も状態も、自分のコンテナから読まない（子がコンテナに書いたものを、檻役が読む道を作らない。§5）。
- `docs/architecture.md` §2 の図と「LM の子」の行、ADR 0068 の口の一覧に、檻役の 2 つの口を足す（実装の PR で）。

### 3.3 監督と再起動（Windows は engine-host が Job Object で見張る。macOS は「判断はエンジン、実行は檻役」に分ける）

| 起きたこと | 何が起きるか | 数え方（今の規則のまま） |
| --- | --- | --- |
| 子が落ちる | エンジンはパイプの終わりで気づく。檻役が回収する | 起動の失敗に数える。次の要求で起動し直す |
| 子が固まる | エンジンが締め切りで檻役に「止める」。檻役は SIGKILL と回収のあとで返事（今の kill と wait と同じ順。GPU のメモリが空いてから次を起こす）。返事が来なければ接続を捨てる（檻役が止める） | 今と同じ |
| エンジンが落ちる | 檻役との接続が切れ、檻役が子を止める。子も標準入力の終わりで終わる | — |
| 檻役が落ちる | エンジンの接続が切れる（起動の失敗に数える）。子は見張りで自分で終わる。殻は檻役との接続の切断に気づき、口を取り直して、次の要求でエンジンに渡す | 1 回の失敗 |
| 殻が落ちる・入れ替わる | エンジンと檻役の接続はそのまま使える。殻が戻れば `Hello` で新しい口が来る（エンジンは今の接続が生きていればそのまま使う） | — |
| 口が来ない（古い殻、smoke の一部） | LM なし。エンジンが自分で起動する道には入らない（ADR 0072 §5 と同じ考え） | 数えない（状態として「檻なし」） |

- LM が落ちてもエンジンが生き残る性質（ADR 0060 Q4）は変わらない。檻役が落ちても、エンジンは LM なしの順位で返し続ける。

### 3.4 束、署名、配布（ADR 0069。公証なし）

- `ikari.app/Contents/XPCServices/IkariLMCage.xpc/`。`ikari-lm-host` はエンジンの束からこちらへ移す（エンジンの束には llama.cpp が無くなる）。
- 檻役の entitlement は `com.apple.security.app-sandbox` だけ（network なし、一時例外なし）。子は entitlement なし。Info.plist は束の `Contents/Info.plist`（§13.2 の「埋めないと SIGTRAP」は単体の実行ファイルの話で、束なら要らない。実装で確かめる）。
- 署名の順は内から外（`ikari-lm-host` → 檻役 → エンジン → 殻）。team と ad-hoc（`--distribution` を含む）で同じ構成。§13 の実測は ad-hoc で通っている。
- `build.sh` の検査に足す: 檻役に app-sandbox があり network と一時例外が無い、子に entitlement が無い、エンジンの束に `ikari-lm-host` が無い、檻役の署名要件が殻とエンジンを指す。
- 檻役は Rust の bin（cargo で作り、`build.sh` が束に入れる）。新しい XCFramework は作らない（#154 の鮮度の検査が増えない）。libxpc のハンドラは block を要るので、依存に `block2` を足す（`deny.toml` の確認が要る）。エンジンの側の libxpc の呼び出しも同じモジュールに置く。

### 3.4.1 増える攻撃面と、相手の確認の限界（2026-11-17 決定の条件 5）

- 増えるもの: 檻役の bin の中の libxpc の呼び出しと、`block2` の unsafe と、その依存（`deny.toml` と依存の監査の対象に入る）。
- 檻役を止められる・落とせる者がいても、害は「LM なし」まで（エンジンは LM なしの順位で返し続ける。§3.3）。
- ad-hoc の署名では、相手の確認は識別子の一致だけ（チーム ID が無い）。同じ利用者のプログラムが同じ識別子で署名したものを作れば、確かめを通りうる。ADR 0069 §1 の限界と同じで、この ADR では強くならない。

### 3.5 Swift の増え方

- `IkariXPC`: 檻役につないで口をもらい、エンジンに渡す（切れたら取り直す）。数十行。理由: XPC サービスを名前で探せるのはアプリ本体だけ（OS の制約）。
- `IkariEngineService`: 受けた口を FFI（`ikari_engine_attach_lm_cage` のような 1 関数）でエンジンに渡す。十数行。
- `IkariSmoke`: `IkariXPC` の同じ関数を呼ぶ。
- 判断は増えない（いつ渡すかは「`Hello` のたび」と「取り直したあと」の 2 つだけで、輸送の規則）。

### 3.6 テストの方法

- `cargo test`（macOS）: 檻役の取り決めの往復を、プロセスの中の匿名の口で流す（束も署名も要らない）。偽の子（`ikari-lm-host-fake`）で、起動、止める、接続を捨てたときの回収、檻役が落ちたときの子の終わり、版違いを確かめる。今の `scorer.rs` のテスト（連続失敗、CPU への切り替え）は、起動の口を差し替えて両方で流す。
- `build.sh` の検査（§3.4）。check.sh に入る。
- smoke（ユーザーの了承が要る）: LM の状態が「檻あり」で Ready になること、採点が返ること。子が読めない・書けないことの確認は、配らない試験用の子（`macos/tools/lm-host-sandbox` の続き）で手で行い、製品の束には入れない。

## 4. 検討した案（Q1）

| 軸 | A 檻役の XPC（推奨） | B 殻が起動する | C LaunchAgent |
| --- | --- | --- | --- |
| 殻とエンジンの取り決め | 殻 → エンジンの向きのメソッドを 1 つ足すだけ | エンジン → 殻の頼み（起動、止める、fd の受け渡し）という逆向きの流れが増える | 殻は変わらない。エンジンの entitlement に mach-lookup の例外が増える |
| 起動元の権限 | 檻役自身が Sandbox の中（エンジンが乗っ取られても、頼めるのはエンジンより狭いもの） | Sandbox の外の殻が、エンジンの頼みで実行ファイルを起こす（Sandbox の外への橋になる） | 利用者の権限の常駐。橋になる |
| 監督 | 判断はエンジン、実行は檻役。接続の寿命に子を結ぶ | 入力の要の殻が、子の回収を持つ。殻の入れ替えで持ち主が変わる | launchd。インストールの手順と後片付けが増える |
| 新しく作るもの | 束 1 つ、Rust の bin 1 つ、`block2` | 束は増えない。殻の Rust と Swift の口が増える | plist、登録と解除、例外 |
| コンテナの書き込みを後で止める道（Q2） | 檻役を Sandbox の外にする必要があり、A の利点が消える | そのまま `sandbox_init` を試せる | 同じく試せる |
| 確かめ | §13.5 で ad-hoc で通った | §13.2 で通った | 未検証 |

- B を採らない理由: Sandbox の外の殻が、Sandbox の中のエンジンの頼みで実行ファイルを起こす形は、檻を作るために檻の外への道を作ることになる。殻とエンジンの取り決めに逆向きの頼みが入り、殻（入力の要）に監督が載る。利点（kill を殻ができる、Q2 の道が残る）は、A の「接続の寿命で止める」と、Q2 を今は採らないこと（§5）で要らなくなる。
- C を採らない理由: 未検証で、エンジンの Sandbox を広げる例外と、常駐とインストールの手順が増える。ADR 0069 §6 の置き場所の確認とも絡む。
- 檻役を Swift で書く案: 今の `IkariEngineService` と同じ形（Swift が XPC、Rust が FFI）にそろうが、新しい XCFramework と鮮度の検査が増え、判断を持たない役に 2 言語が要る。採らない。

## 5. 決定 2（Q2）: コンテナへの書き込みは、今は止めない。ADR 0072 §3 の macOS の段 2 を「App Sandbox の既定」と書き改める

- 段 2 の macOS が止めるもの: 通信、データのフォルダとほかの利用者のファイルの読み書き、パスでのモデルの読み取り。**残るもの 3 つ**: 檻役のコンテナへの書き込み、システムの読み取り、プロセスの起動（どれも檻役の Sandbox の中）。ADR 0072 §3 の表の「書き込みなし」を、この形に書き改める（2026-11-17 に書き改めた）。
- **残る害**（正直に書く）:
  - 乗っ取られた子は、採点の入力（左文脈）を檻役のコンテナに書き残せる。外には出せない（通信なし）が、コンテナに残る。
  - 前のモデル（前の子）がコンテナに置いたファイルを、次の子が読める。自由指定のモデルが置いたものを、あとで別のモデルが読める。
  - 推測: コンテナは同じ利用者のほかのプログラムからも読める（macOS がコンテナを守る範囲は確かめていない）。
- 理由: (1) 止めるには、Sandbox の外の起動元の子が `sandbox_init` で自分を絞る形が要り、§4 の A の利点（起動元も Sandbox の中）が消える。(2) `sandbox_init` と独自の規則の書き方は Apple が公開・保証していない API で、OS の更新で Metal が通らなくなる心配を、毎回の確認で負うことになる。(3) 残るものは檻役のコンテナの中に閉じ、守りたいデータ（学習、辞書、設定）と通信には届かない。
- 安く足せるもの（実装のときに測って決める。値は計測で）: 檻役が子を起こすたびに、子が書いたものをコンテナから消すか、書ける大きさに上限（`RLIMIT_FSIZE`）をかける。`RLIMIT_FSIZE` は 1 つのファイルの大きさの上限で、ファイルの数を増やした合計は止めない（ディスクを埋めることは止められない）。
- **勧め（決定ではない）**: 自由指定のモデルを使ったあとと、モデルを替えたときに、檻役のコンテナ（子が書ける場所）を消す形。Metal のキャッシュがコンテナの中にあると、消すたびに最初の 1 回が遅くなる（§1 の 4〜5 秒）ので、キャッシュの場所を測ってから決める（§10）。
- 止める方に改めるときの実測の条件（今はしない）: Sandbox なしの試験用の親から、`deny default` を基にした規則で子が自分を絞り、(a) Metal に載る、(b) Ready と採点の中央値が §13.4 の専用の Sandbox の 1.5 倍以内、(c) NLL が一致、(d) コンテナを含むファイルの書き込みが拒まれる、を 2 つの版の macOS で確かめる。

## 6. 決定 3（Q3）: macOS では、プリセットも自由指定も段 2 で動かす。製品のエンジンが自分で子を起こす道は持たない

- ADR 0072 §4.3 は「プリセットは段 1 のままでよい。段 2 にするかは計測のあと」とした。§13.4 で、専用の Sandbox の速さは引き継ぎの形とほぼ同じだった（遅くならない）。道を 2 つ持つ分のテストと、段を下げる道を持つ理由が無いので、macOS ではプリセットも段 2 にする。
- 檻役に届かない（口が無い、檻役が起動できない）ときは、プリセットでも LM なし。段 1（エンジンが自分で起こす）に落ちる道は製品に置かない。エンジンが自分で起動する口（`os/apple.rs` の今の `spawn`）は、テストと開発のビルド（dev-knobs）だけに残す。
- **OS で非対称になる**: Windows のプリセットは段 2 から段 1 に落とせる（ADR 0072 §12.8 の 1）が、macOS は落とさない。理由: Windows の段 1 には実のある絞り（低い整合性、Job、渡すハンドルの限定）があるが、macOS の段 1 は段 0 と同じで、子がデータのフォルダを読み書きできるため。
- **檻役が単一の故障点になる**（壊れると macOS の LM は全部止まる。§9）。静かに質が落ちないように、「檻なし」の状態を設定画面とログ（固定の語）に出す。
- 自由指定のモデルを macOS で出す条件（ADR 0072 §4.2 の「段 2 のある OS」）は、「この ADR の実装がマージされ、§8 の実機の確認が済んでいること」とする。実行のときは、檻役に届かなければ自由指定のモデルは使わない（警告を出して LM なし）。
- Windows（AppContainer）には影響しない。段 2 の起動の口を `lm/src/host` で差し替えられる形にしておくので、Windows の段 2 も同じ場所に入る。

## 8. 実機の確認（smoke と、利用者の ikari のプロセスを止めるものは、ユーザーの了承が要る）

1. team と ad-hoc の両方で入れ、ふだんの入力で LM が効く（候補の並び）。入れ替えたあと、開いているアプリを起動し直す。
2. アクティビティモニタで、`ikari-lm-host` が Sandbox の中で、檻役の識別子の下にいる。データのフォルダ（`~/Library/Application Support/ikari-ime/`）を開いていない。
3. 入れ替えの直後の最初の 1 回（Ready まで 4〜5 秒）が、締め切り（60 秒）に収まり、入力が止まらない。
4. （了承が要る）`ikari-lm-host` を止める → エンジンは生き残り、次の要求で起動し直す。檻役を止める → 同じく戻る。
5. 殻の入れ替え（再インストール）、スリープからの復帰のあとに LM が戻る。**配布の前に必ず確かめる**（2026-11-17 決定）。
6. 配布の置き場所（ADR 0069 §6、#241 の `/Library/Input Methods`）でも檻役が起動する。**配布の前に必ず確かめる**（同）。
7. （了承が要る）smoke が「檻あり」で通る。
8. 檻役の分のメモリ（常駐の増え方）を記録する。

## 9. 結果

- macOS に段 2 ができ、自由指定のモデルを出す条件の片方がそろう。エンジンの束から llama.cpp が無くなる。
- 失うもの: 束が 1 つ増え、殻とエンジンの間に口が 1 つ増える。エンジンは檻の子を直に止められず、檻役を通す。檻役が壊れると、macOS の LM は全部止まる（プリセットも）。檻役のコンテナへの書き込みは残る。

## 10. 推測（確かめていないもの）

- NSXPC の `setXPCType` で、匿名の口がエンジンまで届く（§13.5 は試験用のアプリで渡せたが、今の殻の NSXPC の口では試していない）。
- 束の Info.plist があれば、檻役に `-sectcreate` は要らない。
- 檻役は、子がいてトランザクションを持つ間、launchd に終わらされない。
- Metal のキャッシュの置き場所（§5 の「安く足せるもの」と、コンテナを消す勧めに要る）。檻役のコンテナの中か外か、消したときに最初の 1 回がどれだけ遅くなるかを測る。
- 檻役のコンテナを、同じ利用者のほかのプログラムが読めるか（§5 の残る害）。
- エンジンの側から、匿名の口の相手の署名要件を確かめられること（§3.2 の条件 1。libxpc の相手の確認は、口を受ける側で試した形だけで、つなぐ側からは試していない）。

## 11. ユーザーの決定（2026-11-17。ユーザー（Fable の指摘つき）。リードの推奨どおり、条件つき）

- **Q1（リードの通し番号では Q3）**: 形 A（檻役の XPC サービス）を採る。条件: (1) エンジンの側も、もらった口の先が本物の檻役かを署名要件で確かめる（偽の口にモデルの fd と左文脈を渡さない）。(2) 子の起動は `POSIX_SPAWN_CLOEXEC_DEFAULT` にして 0・1・3 だけを付け、環境変数は固定の空にする。(3) 子の数は接続ごとでなく全体でも上限を置く。(4) 檻役は設定も状態もコンテナから読まない。(5) 増える攻撃面と、ad-hoc の署名での相手の確認の限界を書く。→ §3.1、§3.2、§3.4.1。
- **Q2（同 Q4）**: コンテナの書き込みは今は止めない。残るもの 3 つと残る害を書き、`RLIMIT_FSIZE` が合計を止めないことと、コンテナを消す形の勧めを書く（Metal のキャッシュの場所を測ってから決める）。→ §5、§10。
- **Q3（同 Q5）**: プリセットも段 2 で動かし、檻に届かなければ LM なし（段 1 に落とさない）。OS で非対称になる理由を書き、「檻なし」を設定画面とログに出す。§8 の 5・6 は配布の前に必ず確かめる。→ §6、§8。

### （記録）決定の前の問い

- **Q1. 形は A（檻役の XPC サービス。殻が口を仲立ちし、判断はエンジン、起動と回収は檻役）でよいか。** B は Sandbox の外への橋を作り、C は未検証で手順が増える。**推奨: A。**
- **Q2. 檻役のコンテナへの書き込みは今は止めず、ADR 0072 §3 の macOS の段 2 を「App Sandbox の既定」と書き改めてよいか。** 止めるには公開されていない API と Sandbox の外の起動元が要る。**推奨: 止めない（安い上限は測って足す）。**
- **Q3. macOS ではプリセットも段 2 で動かし、檻役に届かないときは段 1 に落とさず LM なしにしてよいか。** 速さの差は実測でほぼ無い。**推奨: そうする。自由指定は §8 の確認のあとに出す。**
