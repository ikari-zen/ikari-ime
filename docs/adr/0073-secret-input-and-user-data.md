# ADR 0073: 秘密の入力と利用者のデータ。Windows のパスワード欄の扱いと限界、データのフォルダの権限、ログとエラー報告、利用者が書ける場所から読むものの守り

- 状態: 承認（2026-11-16 ユーザー決定。質問はすべて推奨どおり。実機などの確認が済んでいない決定は、確認が済むまで仮。末尾の「決定済み」を見る）
- 日付: 2026-11-16
- 対象: `windows/tip/src/secure.rs` と `com/`（secure の手がかり、デバッグの出力）、`core/src/user/util.rs`（Windows のフォルダの権限）、`engine/src/diag.rs`（`app=`）、`windows/engine-host`（エラー報告からの除外）、利用者が書ける場所のファイルを読む箇所（`core/src/dict/`、`shell-core/src/settings/`、`resource`、`import`）、spec の NFR-18、`SECURITY.md`。この ADR ではコードを変えない
- 前提: main = 94f65ae。[ADR 0066](0066-security-premises.md)（P1・P2・P5、R3・R4）、[ADR 0067](0067-windows-install-layout-and-launch-chain.md)（高い権限では素通し。開発用の口）、[ADR 0068](0068-ipc-endpoints.md) §4（書き出しと取り込み）、spec NFR-18・NFR-19・NFR-24、ADR 0034（診断ログ）、ADR 0051（異常終了の記録）、ADR 0058（束の検証）、#275（公開後に直す指摘）、#369（Chromium のパスワード欄）、#398（ログの `app=`）
- 判断の置き場所: Rust。secure のときに何をしないかは `shell-core`（両 OS 共通。今のまま）。Windows で足すのは、手がかりを読む層と、権限・除外の OS の呼び出しだけ

---

## 1. 現状（分かったこと）

- **secure の見分け（Windows）**: TIP は、入力スコープ（パスワード、PIN、Chromium が返す `IS_PRIVATE`）と、文脈の「キーボードが無効」の印を読み、どれかがあれば secure として `shell-core` に伝える（`windows/tip/src/secure.rs`）。入力スコープが付いていない欄、読めない欄は、通常として扱う。
- **secure のときの動き（両 OS 共通）**: 合成しない、周辺テキストを読まない、エンジンに送らない、学習と診断に回さない、ログにアプリの名前も書かない（`shell-core`、`engine/src/diag.rs`）。
- **spec の NFR-18** は、macOS の判定（`IsSecureEventInputEnabled()`）と、その限界だけを書いている。Windows の記述が無い。
- **英語のモード**: 打鍵はアプリに素通しにし、打った文字を文脈としてためて、エンジンの確定の履歴に入れる（学習はしない。`docs/architecture.md`）。secure の欄では何も記録しない。
- **データのフォルダ**: macOS とその他の Unix は、本人だけ（0700、ファイルは 0600）に直す。Windows は、プロファイルの ACL に任せている（`core/src/user/util.rs`）。
- **ログ**: `engine.log` は番号と固定の語だけ（NFR-19）。例外は `app=` で、macOS は Bundle ID、**Windows は実行ファイルの名前**（英数字と `.` `-` だけなら、そのまま書く。#398）。
- **デバッグの出力**: TIP は `OutputDebugString` に、固定の文と数値（入力スコープの数値の並び、版など）を出す。入力の文字は出せない型にしてある。製品のビルドと開発用のビルドで、出し分けてはいない。
- **異常終了**: 記録するのは、終わり方と panic の場所だけ（ADR 0051）。Windows では、エラーの画面を出さない設定にしている（`runmark`）。OS のエラー報告にダンプが送られるかどうかは、扱っていない。
- **利用者が書ける場所から読むもの**のうち、未対応と分かっているもの（#275）: 辞書の索引のキーの数に上限が無い、辞書を開くときに索引を検証しない、設定などの TSV に読む量の上限が無い、取り込みでリンクや FIFO を拒まない。

## 2. 決定 1: 秘密の入力

1. **secure のときにしないこと（両 OS 共通の約束として、1 か所に書く）**: 合成しない。周辺テキストを読まない。**入力の中身は**、エンジン、LM、候補窓に送らない。secure であるという印（`BeginSession` の `secure`）だけは、エンジンに送る（エンジン側でも学習などを止める二重の守り。アプリの識別子は空にして送り、ログにも書かない。secure の `BeginSession` と `EndSession` の行も書かない）。学習、確定の履歴、英語の文脈、統計、診断ログに入れない。アプリの名前もログに書かない。共通のシナリオ（`shell-core/scenarios/`）に、この一覧を守る場面があることを確かめ、足りなければ足す。
2. **Windows の手がかりは、今の 2 つ（入力スコープ、キーボードが無効の印）のまま**にする。名前や見た目から「パスワード欄らしい」と推し量る仕組みは足さない（外れたときに、ふつうの欄で変換できなくなる。入力に忠実、の方針）。
3. **素通しのプロセス**（高い権限、ストアのアプリ。ADR 0067 §5）では、secure かどうかを見るまでもなく、何も読まず、何も送らない。
4. **限界を spec の NFR-18 に、Windows の分として書く**（実装の PR で直す）。守れない欄:
   - 入力スコープを付けない欄（独自に描く入力欄、ゲーム、古いアプリの一部）。
   - 端末の中のパスワードの入力（`ssh`、`sudo` など。端末は欄の種類を知らせない。macOS でも、エコーを切った端末は同じ）。
   - リモートデスクトップや仮想マシンの窓の中の欄（手元の IME からは、相手の欄の種類が見えない）。
   - ブラウザのプライベートウィンドウ（パスワード欄でないかぎり、通常の欄と同じに見える）。
5. **守れない欄で起きること**を、`SECURITY.md` に書く: 日本語のモードでは、打った読みと選んだ表記が学習に入る。英語のモードでは、打った文字が、エンジンのメモリの中の文脈に入る（保存はしない）。どちらも、ログには書かれない。
6. 実機の確認（`docs/windows-real-device-check.md` の項目 32）の結果で、見分けられなかった欄の一覧を、同じ文書に足す。

2026-11-22 のユーザー決定: secure のときも、secure であるという印だけはエンジンに送り続ける。アプリの識別子は送らず、secure の `BeginSession` と `EndSession` は診断ログに行を書かない（上の 1 の文をこれに合わせた）。

## 3. 決定 2: 利用者のデータの置き場所と権限

1. **Windows でも、データのフォルダを本人だけにする。** 作るときに、継承を受けない ACL（本人、SYSTEM、管理者）を付ける。既にあって広ければ、直す（Unix の 0700 と同じ扱い）。別の利用者（E4）から読めないことを、OS の既定に任せず、ikari が確かめる（P2）。
2. **高い権限の部品は、このフォルダに触れない**（R4。インストーラも。ADR 0067 §3.3）。フォルダの中のリンクやジャンクションで行き先を曲げられても、動くのは利用者の権限の部品だけなので、利用者の権限を超えない。
3. **保存のときに暗号化はしない。** 鍵を置く場所が同じ利用者の場所になり、同じ利用者のプログラム（E3）には意味が無い。機械の盗難には、OS のディスクの暗号化が受け持つ。学習のデータは、原文を持たない形のまま（NFR-19）。
4. **書き出したファイル**は、利用者が選んだ場所に置かれ、ikari の守りの外に出る。画面に「語彙と選んだ表記が入っています」と出す（文は `shell-core`）。
5. **削除**: 既定ではデータを残す（ADR 0063 Q3）。消すのは、その利用者の権限で動く部分（ADR 0067 §3.3）。ほかの利用者のデータは残る。
6. macOS は今のまま（0700、エンジンは Sandbox。書き出しの経路は #274）。

## 4. 決定 3: ログ、デバッグの出力、エラー報告

1. **`app=`（Windows）**: 実行ファイルの名前をそのまま書かず、**ikari が知っている名前の表にあるものだけを書き、ほかは `other`** にする（利用者が付けた名前に、個人の語が入りうる。#398）。表は Rust に置く。macOS の Bundle ID は今のまま（アプリの作り手が付けた識別子）。
2. **`OutputDebugString` は、製品のビルドでは出さない**（開発用の口。ADR 0067 §6 の feature に入れる）。固定の文と数値だけでも、製品が外に出すものは少ない方がよい。
3. **往復時間の計測のログ（`tip-latency.log`）も、開発用のビルドだけ**（ADR 0067 §6）。
4. **エラー報告（Windows）**: エンジン、LM の子、候補窓、設定画面が落ちたとき、OS のエラー報告がメモリのダンプを Microsoft に送りうる。エンジンのメモリには、読み、文脈、学習が入っている。**ikari の実行ファイルを、OS のエラー報告の対象から外す**（インストーラが機械全体の除外に登録する。ADR 0066 §6.1 の「止められるものは止める」）。落ちたことの記録は、今の仕組み（ADR 0051。終わり方と場所だけ）で足りるとする。
5. **止められないもの**: TIP が入っているアプリが落ちたときのダンプは、そのアプリのもので、ikari からは止められない。TIP のメモリには、合成中の読みと、直前に読んだ周辺テキストが入っている。`SECURITY.md` に書く。TIP は、要らなくなった周辺テキストを長く持たない（今の作りを保つ）。
6. 起動の失敗の記録（`start-failure.log`）には、データの場所のパス（利用者の名前を含みうる）が入りうる。手元のファイルなのでそのままにし、issue に貼るための道具（`diag-report`）の側で、パスを伏せる。

## 5. 決定 4: 利用者が書ける場所から読むものの守り（P5・R3）

| 読むもの | 読む者 | 今の守り | 足すこと |
| --- | --- | --- | --- |
| モデル（GGUF） | LM の子（檻。ADR 0072） | 既知の sha256、または警告つきの自由指定 | ADR 0072 |
| 辞書（`system.dict` など。mmap と索引） | **エンジン（檻の外）** | 形式の版、エントリごとの範囲の検査、束の検証と試しの変換（ADR 0058） | 索引のキーの数と確保の量に上限。開くときの索引の検証（費用を測ってから。#275） |
| 束（inbox）と manifest | エンジン | 大きさ、sha256、形式の版、パスの脱出の検査（`resource`） | 作者の Release の束は署名（ADR 0069 §5） |
| 設定（`settings.tsv`） | TIP、エンジン、設定画面 | キーと値の検証、知らないキーは無視 | 読む量の上限（#275）。高い権限の TIP は読まない（ADR 0067 §5） |
| 学習、ユーザー辞書、プロファイル | エンジン | 形式の検査、壊れたら退避（#271） | 読む量の上限 |
| 取り込みファイル（JSONL） | エンジン、CLI | スキーマ、正規化、50MB（NFR-24） | リンクと FIFO の拒否、1 行の長さの上限（#275） |
| LM の自己診断の結果（ADR 0065 の案） | エンジン | — | 数値の範囲の検査。壊れていれば「結果なし」として測り直す。最悪でも、LM の既定のオン・オフが変わるだけにとどめる |
| TIP の資源（キー割り当ての表） | TIP | DLL の隣（管理者だけが書ける場所） | 信頼してよい（R1）。それでも、壊れていたら既定の表で動く |

- 規則: (1) 読む前に大きさを見る。(2) 壊れた・細工された入力では、落ちずに「使わない」に倒し、理由の種類だけを記録する。(3) 読んだ値から、実行物のパス、通信の先、別のファイルのパスを取らない。(4) 同じ入力で起動のたびに落ちる、を繰り返さない（モデルは読み込みの印で止める。ADR 0060 §4。辞書は、開けなければ常駐して「準備できていない」を返す今の形）。
- **辞書の 2 項目（キーの数の上限、索引の検証）は、束をほかの人から受け取る道（`ikari-data`、作者の Release の束）を出す前に直す。** それまでは、辞書は利用者が自分で作るので、敵（E2）の入口が無い。#275 の優先度を、その時点で上げる。
- 利用者が書ける場所の入力を読むパーサ（パイプの枠、設定、学習、manifest、辞書の見出し、LM の子の取り決め）に、でたらめな入力を流すテスト（fuzz）を足す。CI で常に流すか、版を出す前だけ流すかは、[security-design.md](../security-design.md) の検査の節で決める。

## 6. 検討した案

- **secure を広く推し量る（欄の名前、直前の文字、アプリの種類）**: 守れる欄は増えるが、外れたときに、ふつうの欄で変換が止まる。入力の結果を変える機能は既定でオフ、の方針に合わない。採らない。
- **利用者が手で切り替える「記録しないモード」**: 守れない欄（端末など）で、利用者が自分で学習と文脈を止められる。新しい機能なので、この ADR では決めない。要望として issue に残すかを聞く（Q3）。
- **学習を暗号化する**: §3 の 3 のとおり。
- **エラー報告から外さず、ダンプを受け取って不具合の調査に使う**: 作者はダンプを受け取る窓口を持っていない。送られる先は Microsoft だけで、得るものが無い。
- **`app=` を Windows では書かない**: 個人の語は入らなくなるが、アプリごとの不具合の切り分けに使えなくなる。知っている名前だけ書く形を採る。

## 7. 結果

- spec の NFR-18 に Windows の判定と限界が入る。`SECURITY.md` に、守れない欄と、そこで起きることが入る（実装の PR で）。
- 実装の issue（承認のあとに切る）: Windows のフォルダの ACL、`app=` の表、デバッグの出力を開発用の口へ、エラー報告からの除外、読む量の上限と辞書の 2 項目（#275 から切り出す）、fuzz。
- 失うもの: 知らないアプリの名前がログに出なくなり、そのアプリでの不具合は、利用者に名前を聞くことになる。落ちたときのダンプは、作者にも Microsoft にも渡らない。

## 8. 推測（確かめていないもの）

- OS のエラー報告から実行ファイルを外す口（機械全体の除外の登録）が、Windows 11 で期待どおりに効くこと。`runmark` の今の設定（エラーの画面を出さない）で、報告そのものが止まっているかどうかも、確かめていない。
- Win32 の標準のパスワード欄（`ES_PASSWORD`）が、TIP から見て入力スコープを返すか（項目 32 の (a)）。
- プロファイルの下のフォルダの ACL が、実際の機械で本人・SYSTEM・管理者だけになっているか（既定はそうなっている見込み）。
- 辞書の索引の検証にかかる時間（#275 は「約 37MB で数十 ms」と見積もっているが、測っていない）。

## 9. ユーザーに聞くこと

### 決定済み（ユーザー、2026-11-16。すべて推奨どおり）

- **Q1**: Windows のログの `app=` は、ikari が知っている名前だけを書き、ほかは `other`。
- **Q2**: ikari の実行ファイルを、OS のエラー報告の対象から外す。**効き方は VM で確かめるまで仮。**
- **Q3**: 手で切り替える「記録しないモード」は、要望として issue に残す（起票はリード。実装は頼まれてから）。
- **確認が済むまで仮のもの**: OS のエラー報告からの除外が効くかは、VM で確かめる（§8）。効かなければ、限界として書く。

### （記録）決定の前の問い

- **Q1. Windows のログの `app=` は、ikari が知っている名前だけを書き、ほかは `other` にする（§4 の 1）。** #398 でユーザーの判断待ちになっている点。**推奨: 知っている名前だけ。**
- **Q2. ikari の実行ファイルを、OS のエラー報告の対象から外す（§4 の 4）。** 落ちたときのダンプは、どこにも送られなくなる。**推奨: 外す。**
- **Q3. 守れない欄（端末など）のための、手で切り替える「記録しないモード」を、要望として issue に残すか（§6）。** 実装は頼まれてから。**推奨: issue に残す。**
