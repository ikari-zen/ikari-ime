# ADR 0069: 配る物の真正性。署名なしの配布で、本物をどう見分けられるようにするか。ビルドと公開の経路、macOS の未署名の配布、リソースの束の署名

- 状態: 承認（2026-11-16 ユーザー決定。質問はすべて推奨どおり。実機などの確認が済んでいない決定は、確認が済むまで仮。末尾の「決定済み」を見る）
- 日付: 2026-11-16
- 対象: リリース用の workflow（未作成。`.github/workflows/`）、`.github/workflows/codeql.yml`、依存の検査（`deny.toml` を足す）、`macos/scripts/build.sh`（配布用のビルドの形）、`macos/Sources/IkariXPC/Identifiers.swift`（ad-hoc の要件と Smoke）、`resource`（束の署名の検証）、README・`SECURITY.md`・`docs/publish-checklist.md` §4（案内）。この ADR ではコードを変えない
- 前提: main = 94f65ae。[ADR 0066](0066-security-premises.md)（P4、敵 E1）、ADR 0040 §2.7（署名なしで配り始める）、ADR 0004 §8（署名要件）、ADR 0058 §6.2（束の署名は、Release を配るときに必須）、#99（0.x の未署名の配布）、#241（未署名のアプリを開く手順）、#40（ad-hoc の分岐と Smoke）、#275（公開後に直す指摘）
- ユーザーの決定（2026-11-16）: 「署名は公開してから」は Authenticode と公証のことだけ。作者の鍵や GitHub の証明による成果物の証明は、この設計で扱う。macOS の未署名の配布も範囲に入れる（配布、更新、#40）
- 判断の置き場所: 束の署名の検証は Rust（`resource`）。ビルドと公開は CI の定義。Swift に足す判断はない（#40 は、配布用のビルドから Smoke を外すだけ）

---

## 1. 現状（分かったこと）

- 公開のリリース用の workflow は無い。CI の `windows-artifact` は、実機（VM）に持ち込むための成果物を作るもの。
- CI（`ci.yml`）は、権限が `contents: read`、Action は SHA で固定、落としてくる道具（gitleaks、Vulkan SDK）は sha256 で照合している。`codeql.yml` だけ、Action がタグ指定で、`security-events: write` を持つ。
- 依存の検査は、週 1 回の `cargo audit` と Dependabot。`cargo-deny` は無い。Rust のツールチェーンの版は固定していない（`rust-toolchain` のファイルが無い）。
- macOS の配布は、Apple Silicon では少なくとも ad-hoc の署名が要る。`build.sh --signing adhoc` がある。ad-hoc のとき、設定アプリと殻のブリッジは cdhash とパスで相手を固定する（#269）。エンジンが殻を確かめる要件は、識別子の一致だけ（`Identifiers.swift`。殻と Smoke の識別子）。Smoke はバンドルに同梱される（`build.sh`）。
- macOS の置き場所は `~/Library/Input Methods`（利用者が書ける。`macos/scripts/lib.sh`）。
- リソースの束（ADR 0058）の manifest には、空の `signature` の欄がある。検証のコードは無い。モデルは、アプリに埋めた既知の sha256 の表で確かめる（済み）。
- 0.1.0 では、辞書は利用者の手元で作り、モデルは配布元から取る（#99）。作者が束を配るのは、その先（ADR 0033）。

## 2. 問題

- 署名が無いと、OS は「だれが作ったか」を示さない。利用者が本物かどうかを判断する材料は、**どこから取ったか**と、**作者が別に示す証拠**だけになる。
- 証拠を Release のページに置くだけでは、アカウントや CI を乗っ取った者が、物と証拠を一緒に差し替えられる。
- 配る物は、作者の機械ではなく、だれでも経過を見られる場所で作られているべきだが、その経路（workflow、依存、道具）の守りが、まだ決まっていない。
- 作者は 1 人で、AI エージェントがブランチと PR を扱う。リリースを出せる者を絞る決まりが要る。

## 3. 決定 1: 利用者の側。本物を見分けるための材料

1. **配布元は 1 つだけ**: GitHub の `ikari-zen/ikari-ime` の Releases。ほかの場所（ミラー、まとめサイト、パッケージの集積所）のものは、作者が README に書くまで公式でない。README と `SECURITY.md` の先頭に書く。
2. **Release ごとに 3 つの証拠を付ける。**

| 証拠 | 何が分かるか | 何が分からないか |
| --- | --- | --- |
| `SHA256SUMS`（すべての成果物の sha256） | 途中で壊れていない、ページの物と同じ | ページごと差し替えられた場合 |
| GitHub の成果物の証明（attestation。`gh attestation verify <ファイル> -R ikari-zen/ikari-ime`） | そのファイルが、このリポジトリの、どのコミットの、どの workflow で作られたか。記録は公開の台帳に残る | リポジトリに書き込める者が、悪意のあるコミットから正規の workflow で作った場合（ただしコミットが記録に残る） |
| 作者の鍵による `SHA256SUMS` の署名（minisign の形。§5） | 作者が、手元の鍵でその一覧を認めた | 作者の機械と鍵が盗まれた場合 |

   3 つ目は、アカウントと CI が乗っ取られても見分けられるようにするためのもの。鍵は CI に置かない。
3. **Release は、公開したら変えられない設定にする**（GitHub の immutable releases）。公開の前は下書きにし、作者が中身を見てから公開する。
4. **確かめ方を README に書く。** ふつうの利用者向けには「公式の Release のページから取る」と sha256 の比べ方（Windows は `certutil`、macOS は `shasum`）。確かめたい人向けに、証明と署名の確かめ方。
5. **OS の警告についての案内（正直に書く）。**
   - Windows の SmartScreen: 出る画面と、進め方を書く（実機で記録したものを。`docs/windows-real-device-check.md` の項目 31）。
   - Windows の Smart App Control（SAC）: 有効な機械では、署名の無い ikari は動かない見込みで、アプリごとの例外は置けない（§9 の推測。実機で確かめる）。**「SAC が有効な機械では、署名が付くまで ikari は使えません」と書く。SAC を切る手順は ikari の文書に書かず、勧めない**（切ると、その機械のほかの守りが下がる）。
   - macOS の Gatekeeper: #241 で確かめた手順だけを書く。隔離の印を消すコマンドや、Gatekeeper 全体を切る方法は書かない。
   - ウイルス対策ソフトの誤検知: 作者に知らせてもらう。除外の設定は勧めない。**ikari の文書は、OS やウイルス対策の守りを切るよう求めない**、と `SECURITY.md` に書く（偽物の案内と見分ける材料になる）。
6. **インストーラは、足りないものをネットワークから取らない**（ADR 0067 §3.3）。Release の 1 つのファイルで完結する。

## 4. 決定 2: 作者の側。ビルドと公開の経路

### 4.1 リリースの workflow
- **配る物は、GitHub のランナーで、タグから作る。作者や利用者の機械で作ったものは配らない。** macOS（ad-hoc）も Windows も同じ。
- **タグを打つことと、Release を公開することは、ユーザーだけが行う。** AI エージェントは行わない（リポジトリを公開にする操作と同じ扱い。`docs/publish-checklist.md` §2）。GitHub の設定でも、リリースのタグ（`v*`）を作れる者を絞り、タグの付け替えと削除を禁じる。
- workflow の規則:
  - job ごとに権限を分ける。ビルドは `contents: read` だけ。証明を作る job だけ `id-token: write` と `attestations: write`。下書きの Release を作る job だけ `contents: write`。
  - Action はすべてコミットの SHA で固定する（`codeql.yml` も直す。#275）。公開の job では、GitHub 自身の Action だけを使う。
  - ビルドの job に秘密の値（secrets）を渡さない。
  - **リリースのビルドは、キャッシュを読まない**（PR の workflow が書いたキャッシュを通じて、リリースに手を入れられないようにする）。
  - `cargo build --locked`。Rust のツールチェーンの版を固定する（`rust-toolchain.toml`）。落としてくる道具（インストーラの道具、Vulkan SDK、.NET SDK）は、版と sha256 で固定する。NuGet は lock ファイルで固定する。
  - ビルド機のパスを成果物に残さない（`--remap-path-prefix`。#275）。
  - 開発用の口の入っていないビルドであることを確かめる（ADR 0067 §6）。取り込む DLL の検査（ADR 0067 §4.4）、通信の手段を持たないことの検査（ADR 0066 §6.2）も、ここで流す。
- 同じ入力から同じバイト列ができること（再現できるビルド）は、今は目標にしない。証明で「どのコミットから作ったか」が分かれば足りる、とする。

### 4.2 依存
- `cargo-deny` を足す（既知の脆弱性、取得元を crates.io だけに限る、ライセンス。CI で流す）。週 1 回の `cargo audit` と Dependabot は今のまま。
- 配る物に入る他社の部品（llama.cpp、Vulkan のバックエンド、.NET と Windows App SDK、設定画面の方式で要るもの）は、版と取得元を 1 つの表にして `THIRD_PARTY_NOTICES.md` に書き、版を上げるのは PR にする。脆弱性の知らせを受けたときの動きは ADR 0070。
- 依存の中身を人が読んで認める仕組み（`cargo vet` など）は採らない（1 人では続かない）。

### 4.3 リポジトリとアカウント
- `docs/publish-checklist.md` §3 の未了の項目（main への直接の push の禁止、force push と削除の禁止、秘密の走査と push の保護、非公開の脆弱性の報告）を、ビルド済みを配る前に済ませる。
- 作者のアカウントは、2 要素の認証を物理の鍵かパスキーにする。リポジトリに書ける長く有効なトークンを置かない。エージェントが使う資格情報では、タグと Release を作れないようにする（できる範囲で。GitHub の設定で絞れない分は、決まりとフックで守る）。

## 5. 決定 3: 作者の鍵と、リソースの束の署名（ADR 0058 §6.2 の整理）

- 署名の形は、どちらも minisign（Ed25519）。検証だけの小さな実装で済み、通信の手段を持ち込まない（ADR 0066 §6.2 の L1）。GitHub の証明をプログラムが確かめる形は採らない（検証に TLS などの大きな依存が要る）。
- **鍵は用途ごとに分ける。**

| 鍵 | 何に署名するか | だれが確かめるか | 置き場所 |
| --- | --- | --- | --- |
| リリースの鍵 | Release の `SHA256SUMS` | 人（確かめたい利用者） | 作者の手元（CI に置かない）。公開鍵は README、`SECURITY.md`、リポジトリに置く |
| データの鍵 | 作者が配るリソースの束（`origin = release`）の manifest | プログラム（エンジン、取得する部品） | 束を配り始めるとき（ADR 0033）に決める。公開鍵はアプリに埋め、**2 つまで受ける**（鍵の入れ替えのため） |

- ADR 0058 §6.2 は変えない: 利用者が自分で作った束（`origin = export`）と開発者の束（`origin = local`）は、署名なしで受ける。作者の Release の束（`origin = release`）は、配り始めるときから署名を必須にする。**0.1.0 では束を配らないので、データの鍵はまだ要らない。**
- 束の署名が守るのは、運ぶ途中と配布元の乗っ取りだけ。手元の改ざんには効かない（inbox に置ける者は、辞書のフォルダにも書ける）。署名があっても、辞書と表は信用しない入力として読む（P5。ADR 0073）。
- 鍵をなくした・盗まれたときの動きは ADR 0070。

## 6. 決定 4: macOS の未署名（ad-hoc）の配布

1. **配布用のビルドに Smoke を入れない。** エンジンが殻を確かめる要件から、Smoke の識別子を外す（#40）。Smoke は、開発と CI のビルドだけに入れる。
2. **ad-hoc のときの相手の確認は、今の形を保つ**（ブリッジは cdhash とパス。#269）。エンジンの XPC サービスは、バンドルの中にあり、そのバンドルのアプリからしか見えない（OS の仕組み）ので、要件が識別子だけでも、外のプログラムからはつなげない（§9 の推測。確かめる）。
3. **置き場所**: 今の `~/Library/Input Methods` は利用者が書けるので、同じ利用者のプログラムがバンドルごと差し替えられる（R1 を満たさない。cdhash の固定は、差し替えられたバンドルの中では偽物どうしで合ってしまう）。macOS は打鍵の読み取りを許可で守っているので、差し替えられた入力メソッドは、その許可なしで打鍵を受ける道になる（P2）。**配布版は `/Library/Input Methods`（管理者だけが書ける）に入れる形を、#241 の実機の確認で一緒に試し、動けば既定にする。** 動かなければ、今の場所のまま、この限界を `SECURITY.md` に書く。
   - **追記（2026-11-22、[ADR 0080](0080-bundle-model-and-dictionary.md) §5.4・§12 Q1 のユーザー決定で改訂）**: dmg の案内は `~/Library/Input Methods` だけにし、`/Library/Input Methods` を並べて既定にする案は取りやめた（#241 でも試さない）。これに伴い、同じ利用者権限の別プログラムによる束および同梱データの差し替え限界を受け入れ、`SECURITY.md` に明記する。
4. 配布の形（zip か dmg か pkg か）と、開く手順は #241。3 を採ると、管理者のパスワードを求める入れ方になる。
5. 配布用のビルドでも、エンジンと LM の子に App Sandbox（ネットワークなし）がかかっていることを、リリースの workflow で確かめる（`codesign -d --entitlements` の出力を照らす）。

## 7. 検討した案

- **sha256 だけ**: アカウントの乗っ取りに効かない。M6 の指摘のとおり、足りない。
- **GitHub の証明だけ（作者の鍵を持たない）**: 鍵の管理が要らない。ただし、信頼の置き場所が GitHub のアカウントと CI の 1 つだけになる。作者の鍵は、それと独立した 2 つ目の置き場所になる。手間は、リリースごとに手元で 1 回の署名。採る（Q1）。
- **リリースの鍵を CI の secret に置く**: 手間は無くなるが、CI が乗っ取られれば鍵も使われる。証明と同じものを二重に持つだけになる。採らない。
- **SAC を切る手順を案内する**: 入れられる人は増える。ikari のために、その機械の守りを下げさせることになる。採らない（Q2）。
- **再現できるビルドを目標にする**: 第三者が同じ物を作って確かめられる。llama.cpp、.NET、インストーラを含めて揃える手間が大きい。今は採らない。
- **パッケージの集積所（winget、Homebrew）で配る**: 多くは署名を求めるか、別の審査がある。署名が付いてから考える。

## 8. 結果

- `docs/publish-checklist.md` §4（ビルド済みの配布を作るとき）に、この ADR の項目（リリースの workflow、3 つの証拠、案内、鍵）を足す。実装の PR で直す。
- `SECURITY.md` の「ビルド済みのアプリは配布していません」を、配布元と確かめ方に書き直す（原案は [security-design.md](../security-design.md)）。
- 実装の issue（承認のあとに切る）: リリースの workflow、`cargo-deny`、`codeql.yml` の固定、ツールチェーンの固定、Smoke を外す（#40）、macOS の置き場所の実機の確認（#241 に足す）、README の案内。
- 失うもの: リリースのたびに、ユーザーの手作業（タグ、署名、下書きの確認と公開）が要る。SAC が有効な機械の利用者は、署名が付くまで使えない。

## 9. 推測（確かめていないもの）

- SAC が、署名の無い実行ファイルと DLL を止めること、アプリごとの例外を置けないこと、一度切ると戻せるかどうか。公式の文書では確かめていない（利用者の質問の場の答えは食い違っている）。VM で確かめる（項目 31）。
- macOS で、バンドルの中の XPC サービスに、外のプログラムがつなげないこと。
- ad-hoc の署名でも、App Sandbox の entitlement が同じに効くこと。
- `/Library/Input Methods` に置いた入力メソッドが、今の作り（バンドルの中の XPC サービス、設定アプリ、利用者ごとのデータの場所）のまま動くこと。
- GitHub の設定で、エージェントが使う資格情報からタグと Release の作成だけを外せるか。

## 10. ユーザーに聞くこと

### 決定済み（ユーザー、2026-11-16。すべて推奨どおり）

- **Q1**: 作者の鍵（リリースの鍵）を作り、リリースごとに手元で `SHA256SUMS` に署名する。
- **Q2**: Smart App Control が有効な機械には「署名が付くまで使えない」と書き、切る手順は案内しない。
- **Q3**: macOS の配布版の置き場所は `/Library/Input Methods`。**#241 の実機の確認で動けば既定にする（それまで仮）。動かなければ、今の場所のまま限界を `SECURITY.md` に書く。**
- **確認が済むまで仮のもの**: macOS の配布版の置き場所（`/Library/Input Methods`）は、#241 の実機の確認で動くことを確かめてから既定にする。Smart App Control の動き（§9）は VM で確かめ、案内の文を合わせる。

### （記録）決定の前の問い

- **Q1. 作者の鍵（リリースの鍵）を作り、リリースごとに手元で `SHA256SUMS` に署名する（§3 の 3 つ目、§5）。** 手間は 1 回の署名と、鍵の保管。**推奨: 作る。** アカウントや CI が乗っ取られても、利用者が見分けられる材料が残る。
- **Q2. SAC が有効な機械には「署名が付くまで使えない」と書き、切る手順は案内しない（§3 の 5）。** **推奨: 案内しない。**
- **Q3. macOS の配布版の置き場所を `/Library/Input Methods` にする（§6 の 3）。** 入れるときに管理者のパスワードが要る。#241 の実機の確認で動くことを確かめてから決める。**推奨: 動けば既定にする。**
