# ADR 0064: Windows で、エンジンがセッションを（接続, セッション）で区別する。版が違う殻とエンジンは Windows では共存し、版の違いでエンジンを止めるのは macOS の殻だけにする

- 状態: 提案
- 日付: 2026-11-14
- 対象: `engine`（`lib.rs` の `Engine::handle` の入口、`session.rs`、`dispatch.rs`、`cache.rs` の変換の表、先行計算と `lookahead`・`ctx_trace` のキー）、`windows/engine-host/src/lib.rs`（`serve`）、`shell-core/src/engine/mod.rs`（`EngineLink::hello`）、`shell-core/src/controller/`（`restart_engine`）、`shell-core` の `ShellConfig`、`windows/tip/src/com/host.rs`（`create_shell`）、`shell-ffi`（既定値だけ）、`windows/engine-host/tests/`、ADR 0063 §1.2・§3 の 5・6 の記述
- 前提: main = 37740c3。アーキテクチャレビュー（2026-11-14）の指摘 1・2・12（高・高・中）。ADR 0046（E4・E5。ほかのアプリからは借りない）、ADR 0063（TIP の DLL の更新。古い TIP と新しいエンジンが共存する）、ADR 0040 §2.2（TIP の中で `shell-core` を動かす。エンジンは 1 つ）、ADR 0004 §5.2（macOS: 入れ替えた直後に古いエンジンを止める）
- タスク: #390（セッションの ID の衝突）、#391（誰がエンジンを止めてよいか）
- 判断の置き場所: Rust。セッションのキーは `engine`（どの接続から来たかを入口で受ける）、版の扱いは `shell-core`（殻の入口が設定で選ぶ）。Swift と TIP の COM の層には判断を足さない（TIP は `ShellConfig` に値を 1 つ入れるだけ、macOS は `shell-ffi` の既定値で今と同じ）
- 範囲外: パイプの書き込みの締め切り（#392。別の ADR）、設定の変更の伝わり方の全体（W4-s。ここでは「Windows の殻はエンジンを止めない」だけを決める）、パイプの相手の確認（W5・W6）、0.1.0 のあとの互換の約束（未決。#396）
- この ADR ではコードを変えない。値（締め切り、上限）を新しく決めない。新しい値が要るときは計測で決める（§5）

## 1. 現状（分かったこと。2026-11-14 に main = 37740c3 のコードで確かめた）

### 1.1 セッションの ID
- 殻（`Shell`）は、ID を自分で 1 から振る。`last_session_id: 0` から始め（`shell-core/src/controller/mod.rs:195`）、`next_session_id` が 1 ずつ足す（`:366-369`）。アプリの名前ごとに ID を覚えて使い回す（`session_id_for`、`:371-386`。ADR 0046 E4、最大 64 件）。
- macOS は、殻のプロセス（`ikari.app`）の中に `Shell` が 1 つだけある（`AppContext.shared.driver`。`macos/Sources/IkariIME/IkariInputController.swift:11`）。すべてのアプリの入力が 1 つの `Shell` を通るので、ID はぶつからない。
- Windows の TIP は、**スレッドごとに** テキストサービスを持ち（`windows/tip/src/com/service.rs:1`）、`ActivateEx` のたびに `host::create_shell()` で新しい `Shell` を作る（`service.rs:451`、`host.rs:88-109`）。アプリの名前は**そのプロセスの exe の名前**（`host.rs:63-71`）で、1 つの `Shell` の中では変わらない。
- したがって、**どの TIP の `Shell` も、最初のセッションに ID 1 を振る**（名前が空でなければ、そのあともずっと 1）。メモ帳も Edge も explorer の各スレッドも、エンジンには「セッション 1」として届く。
- engine-host は、接続ごとにスレッドとハンドラを作るが、ハンドラは受けた枠をそのまま共有の `Engine::handle` に渡す（`windows/engine-host/src/lib.rs:31-36`）。接続ごとの名前空間はない。なお `pipe::Server::serve` は**接続ごとにハンドラを作る口**（`make_handler: FnMut() -> H`。`pipe/src/server.rs:40-43`）を持っているので、接続ごとの状態は今の形の上に置ける。
- エンジンは `session_id` だけをキーに、確定履歴と secure（`engine/src/session.rs:33-74`）、先行計算・`lookahead`・`ctx_trace`・変換の表（`drop_session_state`、`:88-93`）を持つ。同じ ID で secure が違う `BeginSession` が来ると、履歴を捨てて作り直す（`:59-71`）。`EndSession` は、その ID を休止にし、先行計算などを捨てる（`:76-86`）。
- 変換の ID は、エンジンが全体で 1 つの数で振る（`engine/src/convert.rs:391`）。番号はぶつからないが、どの接続の変換かは見ていない。
- テストは衝突を見ていない。複数の接続のテストは、接続ごとに別の ID を手で渡している（`windows/engine-host/tests/serve.rs:65-80`、`pipe_convert.rs:138-141`）。
- **ここから言えること（事実の組み合わせ）**: Windows では、(a) あるアプリで確定した文が別のアプリの左文脈になり（ADR 0046 E5 に反する）、(b) 片方のアプリから出ると（`EndSession`）もう片方のセッションが休止になって `UNKNOWN_SESSION` → 送り直しになり（`shell-core/src/engine/mod.rs:552-560`）、(c) 片方がパスワード欄に入ると、もう片方の履歴が消える。
- **推測**: 実機で見えている「変換の質のぶれ」や `UNKNOWN_SESSION` の後の送り直しの一部は、これが原因かもしれない。実機のログでは確かめていない。

### 1.2 版が違うときの動き
- `EngineLink::hello` は、返事の `engine_version` が自分の `shell_version` と**文字列で違えば**、`Shutdown(VERSION_MISMATCH)` を送って終了の通知を最大 1 秒待ち、もう一度 `Hello` する。2 回目も違えば `Unavailable`（`shell-core/src/engine/mod.rs:164-188`、`:588-617`、`SHUTDOWN_WAIT` は `:61`）。両 OS で同じコード。
- 版の文字列は、どちらも workspace の `CARGO_PKG_VERSION`（エンジンは `engine/src/session.rs:26`、TIP は `windows/tip/src/com/host.rs:93`）。
- エンジンは、`schema_version` が違っても `Shutdown` だけは受ける（`engine/src/dispatch.rs:153-162`）。受けると、保存して Ack を返すだけ（`engine/src/convert.rs:594-598`。注記「プロセスを終わらせるのは XPC サービスの役目」）。
- macOS の XPC サービスは、返事のあと exit する（同じ注記）。殻とエンジンは同じバンドルで一緒に入れ替わるので、古いエンジンを追い出す正しい動き（ADR 0004 §5.2）。
- Windows の engine-host は、`Shutdown` を受けても**終わらない**。`Shutdown` の枠を見る処理が engine-host にない（`windows/engine-host/src/` を検索。`ikari_pipe::Shutdown` は受け口を閉じる trait で、別物）。
- 殻は、設定の `engine.*` が変わったと気づいたときも、`Shutdown(SETTINGS_CHANGED)` を送ってから `Hello` で起こし直す（`shell-core/src/controller/mod.rs:703-727`）。TIP が N 個あれば、それぞれが別の時刻に送る（レビューの指摘 3）。
- ADR 0063 §1.2 は「`Hello` は版の文字列を運ぶが、比べてはいない」と書いている。**これは事実と違う**（上のとおり殻が比べている）。§3 の 5 は「インストーラが `Shutdown`（版が違っても受ける）で止める」、§3 の 6 は「古い TIP と新しいエンジンが話すのは普通に起きる」としている。
- **ここから言えること**: 今の Windows では、版の違う TIP がアプリに入るたびに `Shutdown` を送り（学習の保存が走る）、背景のスレッドが最大 1 秒待ち、LM の状態を取れない（変換は続く）。engine-host を「`Shutdown` で終わる」ように直すと、**古い TIP が、新しいエンジンを、アプリに入るたびに落とす**（サインアウトまで続く）。片方を直すともう片方が壊れる。

## 2. 問題
1. Windows では、殻が「アプリ × スレッド」の数だけあり、どの殻も ID を 1 から振るので、エンジンの中でセッションが混ざる。決定済みの不変条件（文脈は同じアプリの中だけ。ADR 0046）が、アプリを 2 つ開くだけで破れる。
2. 「版が違えばエンジンを止めて起こし直す」は、殻とエンジンが一緒に入れ替わる macOS の前提。Windows では、古い TIP と新しいエンジンがサインアウトまで共存する（ADR 0063）。誰がエンジンを止めてよいかが決まっていない。
3. どちらも、Mac で回るテストが見ていない（殻が 1 つの前提で書かれている）。

## 4. 決定 1: セッションを区別するキー

### 4.1 案の比較
| 案 | 内容 | 良い点 | 問題 |
|---|---|---|---|
| **K1（推奨）: エンジンが接続を区別する** | engine-host は接続ごとに `Engine` から「接続の口」（仮の名前 `Connection`。エンジンが振る番号を持つ）を取り、そこに枠を渡す。エンジンの中のキーは（接続, `session_id`） | 殻を信じなくても混ざらない（壊れた殻、古い殻、悪意のない誤りでも）。proto も殻も変えない。切断のときに、その接続の状態を確実に片づけられる（D2）。`pipe::Server` がすでに接続ごとのハンドラを作るので、engine-host の変更は数行（§1.1） | エンジンの中の表（セッション、先行計算、`lookahead`、`ctx_trace`、変換）のキーを全部替える。数は多いが機械的。ログの `session=` が接続をまたいで同じ番号になる（`conn=` を足すかは §7.2） |
| K2: TIP がぶつからない ID を振る | `Shell` の ID の上位ビットに、プロセスの番号とスレッドの通し番号を入れる | 変更が小さい（`shell-core` の 1 か所と TIP の値）。当面の止血に向く | 殻が正しく振ることに頼る。古い TIP（直す前の版）とは混ざったまま。切断のときの片づけは別に要る（今は 30 分の休止で残る）。エンジンから見た「同じアプリ」の境目が殻の実装に埋もれる |
| K3: エンジンが ID を払い出す | `BeginSession` の返事で ID を返し、殻はそれを使う | エンジンが一意を保証する | 契約の変更が大きい（macOS の殻も変わる）。返事を待つ往復が `BeginSession` に増える（今は片道の `post`。`shell-core/src/engine/mod.rs:190-195`）。ADR 0046 E4 の「アプリの名前で ID を使い回す」を、エンジンの側で作り直すことになる |

- 推奨の理由: K1 は「殻が複数でも正しいか」をエンジンの入口 1 か所で保証し、macOS の動作を変えない。K2 は殻の実装に頼り、K3 は両 OS の契約を変える。
- K1 のあとも、殻が振る ID は今のまま（1 から）。殻の中の `session_id_for`（アプリの名前 → ID）も今のまま。

### 4.2 Windows の「同じアプリ」の単位（ユーザーに聞く点）
ADR 0046 は「アプリを行き来しても、同じアプリの履歴を保つ」（E4）と「ほかのアプリからは借りない」（E5）を決めた。macOS の「アプリ」は Bundle ID。Windows で何を同じアプリとみなすかは決まっていない。

| 単位 | 内容 | 良い点 | 問題 |
|---|---|---|---|
| **U1（推奨）: 接続（TIP の 1 つのスレッドの `Shell`）** | K1 のキーそのもの | 追加の仕組みがない。殻の申告（exe の名前）に頼らない。フォーカスを別のアプリに移して戻っても、その `Shell` は残っているので履歴が続く（E4 の主な場面は満たす） | アプリを閉じて開き直すと履歴が切れる（macOS では 30 分残る）。同じプロセスの別のスレッド（explorer の窓など）は別のアプリ扱いになる |
| U2: プロセス | キーに相手のプロセスの番号を足す（同じプロセスの接続をまとめる） | 同じプロセスの別スレッドで履歴が続く | engine-host が相手の番号を取る口が要る（今の `pipe` はクライアントの側で相手の番号を取るだけ。`pipe/src/os/windows.rs:611`。サーバーの側にはない）。U1 との差は、複数の UI スレッドを持つアプリでだけ出る（推測） |
| U3: exe の名前 | 殻が送る名前（`client_bundle_id`）で、接続をまたいでまとめる | macOS の Bundle ID にいちばん近い。開き直しても履歴が続く | 殻の申告に頼る（K1 の利点が薄れる）。名前は利用者が付けられ、同じ名前の別のプログラムが混ざる。今エンジンは名前を「ログに書く語」としてだけ持ち、キーにしていない（`engine/src/session.rs:34-36`。指摘 13 と関係） |

- 推奨の理由: U1 は、ほかのアプリの文を混ぜない（E5）側に倒れ、仕組みを足さない。開き直しで切れる損は、「こまめに確定する」方針（短い確定）では小さいと見る（推測。測っていない）。U2・U3 は、U1 で困る場面が出てから足せる（キーの形は K1 のまま）。

### 4.3 移行の影響
- **macOS は変えない**: `engine-ffi` は今の `Engine::handle` を呼ぶ。`handle` は「既定の接続」（番号 0 の固定）に渡すだけにする。殻は 1 つなので、キーは今と同じ集合になる。XPC の接続が切れたときの片づけ（D2）は、macOS では今どおり行わない（既定の接続は切れない）。
- **Windows**: engine-host の `serve` が、接続ごとに `Connection` を取ってハンドラに入れる。接続が終わると `Connection` が落ち（`Drop`）、その接続のセッションと状態を捨てる。
- 切断と再接続（エンジンの再起動ではなく、パイプだけが切れて同じエンジンにつなぎ直す場合）は、新しい接続になるので履歴が切れる。殻は `UNKNOWN_SESSION` を受けて `BeginSession` を送り直す（今の道。`shell-core/src/engine/mod.rs:552-560`）。入力は止まらない。
- 設定のパイプ（`windows/engine-host/src/settings_pipe.rs`）からの管理の要求は、セッションに結びつかないので変えない。
- セッションの上限（`SESSION_LIMIT = 256`、`engine/src/lib.rs:98`）は、全体の数のまま。Windows で同時に何本の接続がつながるかは測っていないので、上限の数え方（全体か、接続ごとか）は実機で接続の数を測ってから見直す（§5）。

### 4.4 テストの案（Mac で回る）
1. **エンジンの単体**（`engine/src/tests/`）: 2 つの `Connection` が同じ `session_id = 1` を使う。
   - A で確定 → B で変換したとき、B の左文脈に A の確定が入らない（`ctx_trace` か、文脈の組み立ての結果で見る）。
   - A の `EndSession` のあとも、B の `Convert` が `UNKNOWN_SESSION` にならない。
   - A が secure の `BeginSession` を送っても、B の履歴が残る。
   - A が作った変換の ID で、B が `Page`・`Commit` を送っても受けない（D2）。
   - A の `Connection` を落とすと、A のセッションと先行計算が消え、B は残る。
2. **engine-host の結合**（`windows/engine-host/tests/serve.rs`）: 今の「接続ごとに別の ID」のテストに加えて、**2 本の接続が同じ ID を使う**テストを足す（メモリ上の流れ `pipe/src/mem.rs`）。
3. **殻を 2 つ、1 つのエンジンにつなぐ土台**: `Shell` を 2 つ作り、メモリ上の流れで同じ engine-host の `serve` につなぐ（TIP の輸送 `PipeTransport` を使う）。キーの列を流して、確定の文が混ざらないことを見る。ここで作る土台を、決定 2 のテストと、#392 のテスト（相手が読まなくなる）でも使う。
4. **macOS の回帰**: 既存のエンジンのテスト（`handle` 経由）と、共通のシナリオ（`shell-core/scenarios/`）がそのまま通ること。

## 5. 値について
- この ADR は新しい値を決めない。休止の長さ（`paused_session_ttl`）、`SESSION_LIMIT`、`SHUTDOWN_WAIT`、`Hello` の待ちは今のまま。
- 見直す必要が出たら、実機で測ってから決め、PR でユーザーに確認する（例: Windows で同時につながる接続の数を測って `SESSION_LIMIT` の数え方を決める）。

## 6. 決定 2: 版が違うときと、エンジンを止めてよいのは誰か

### 6.1 案の比較
| 案 | 内容 | 良い点 | 問題 |
|---|---|---|---|
| **V1（推奨）: 止めて起こし直すかを、殻の入口が選ぶ** | `ShellConfig` に「エンジンを持つか」（仮の名前 `engine_owner: bool`）を足す。`true`（macOS）は今と同じ。`false`（Windows の TIP）は、版が違っても `Shutdown` を送らず、返事をそのまま使う（版の違いは殻の診断ログに 1 行）。`SETTINGS_CHANGED` の起こし直しも `false` では送らない | 片方を直すともう片方が壊れる関係を、殻の性質で断つ。macOS の動きは変えない。ADR 0063 の「古い TIP と新しいエンジンの共存」とそのまま合う。`schema_version` の照合（D7）は残るので、互換を壊したときはエンジンなしの候補に落ちる（固まらない） | Windows では、殻が古いエンジンを追い出せなくなる。追い出すのはインストーラの役目になる（D6）。設定の `engine.*` の変更が、W4-s で反映の道を作るまで効かない（今も効いていない。§1.2） |
| V2: エンジンが「受けられる殻の範囲」を返す | `HelloReply` に範囲を足し、殻はそれで続けるか決める | 版の違いを細かく扱える | 0.1.0 のあとの互換の約束（#396、未決）が先に要る。今は `schema_version` が 1 つだけで、範囲を書く材料がない |
| V3: 何もしない（更新のたびにサインアウトを必須にする） | 今の動きのまま | 作業がない | engine-host を `Shutdown` で終わるように直せない（直すと古い TIP が新しいエンジンを落とし続ける）。ADR 0063 の目標「再起動なしで新しいアプリから新しい版」を弱める。今も、版の違う TIP がアプリに入るたびに保存と 1 秒の待ちが走る |

- 推奨の理由: V1 は「エンジンを止めてよいのは、エンジンと一緒に入れ替わる者だけ」という規則にそろう。macOS の殻はエンジンと同じバンドルなので止めてよい。Windows の TIP は版がずれるので止めない。

### 6.2 Windows でエンジンを止めてよい者（D5・D6）
| 誰 | いつ | 道 |
|---|---|---|
| インストーラ | 更新（エンジンの exe を置き換える前）、削除 | エンジンのパイプとは別の口（推奨。W5 の ADR で決める。候補は、名前つきのイベント、設定のパイプの管理の要求、プロセスの終了の要求。どれも推測で、実機で確かめていない） |
| engine-host 自身 | ログオフ（`windows/engine-host/src/endsession.rs`）、起動の失敗 | 今の道 |
| TIP（殻） | **止めない** | — |
| 設定画面 | `engine.*` の変更の反映 | W4-s で決める（engine-host が自分で読み直すか、自分で起こし直す案がレビューの指摘 3 の A）。この ADR では「TIP は止めない」だけを決める |

- エンジンのパイプの `Shutdown` を Windows でも「終わる」にする案（ADR 0063 §3 の 5 の書き方）は採らない。V1 のあとは送る殻がなくなるが、誤りのある殻（または V1 より前の版の TIP。Windows 版はまだ配っていないので、今は開発の機械にしかない）からの 1 通でエンジンが止まる道を残さないため。止める口を別にすれば、相手の確認（W5・W6）もその口にだけかければよい。

### 6.3 移行の影響
- **macOS は変えない**: `shell-ffi` が `ShellConfig` を作るときに `engine_owner = true` を入れる。Swift（`ShellABI`）は変えない。
- **Windows**: `windows/tip/src/com/host.rs` の `create_shell` が `engine_owner = false` を入れる。`EngineLink::hello` は、`false` のとき版の違いを記録して返事を返す（`observed_engine_version` は今も残している。`shell-core/src/engine/mod.rs:177`）。`restart_engine` は、`false` のとき `Shutdown` を送らず、LM の状態の取り直し（`Hello`）だけにする。
- 版の違いをエンジンのログにも出すか（ADR 0063 §7 の手順 5 の問い）: `Hello` の行に殻の版を書く案がある。版の文字列は個人の情報ではない。必要かは ADR 0063 のスパイクの結果で決める（この ADR では決めない）。
- 新しい TIP と古いエンジン（インストーラがエンジンを置き換える前の短い間）も、同じく共存する。`schema_version` が違えば、エンジンなしの候補に落ちる。

### 6.4 テストの案（Mac で回る）
1. **殻の単体**（`shell-core`）: 偽の輸送で、違う `engine_version` を返す。
   - `engine_owner = true`: `Shutdown(VERSION_MISMATCH)` を送り、もう一度 `Hello` する（今の動き。既存のテストがあれば、それが通ること）。
   - `engine_owner = false`: `Shutdown` を送らず、1 回の `Hello` で続ける。変換の要求がそのまま流れる。
   - `engine_owner = false` で `engine.*` を変えた設定を読ませると、`Shutdown(SETTINGS_CHANGED)` を送らない。
2. **版の混在**（§4.4 の 3 の土台）: `shell_version` が違う 2 つの `Shell`（例: エンジンと同じ版と、`0.0.0-old`）を 1 つの engine-host につなぎ、交互に変換する。両方が候補を受け、エンジンが止まらず、`Shutdown` の枠が 1 つも届かないこと。
3. **engine-host**: エンジンのパイプで `Shutdown` を受けても、受け口が閉じず、ほかの接続の変換が続くこと（今の動きを固定するテスト）。
4. **`schema_version` の違い**: `schema_version = 2` の枠を送る殻は `SCHEMA_MISMATCH` を受け、エンジンなしの候補で動く（既存の道。固まらない）。

## 7. 結果
### 7.1 得るもの
- Windows でも ADR 0046 の「文脈は同じアプリの中だけ」が守られる。片方のアプリの出入りやパスワード欄が、もう片方に響かない。
- engine-host を安心して「止める口」で止められるようになり、ADR 0063 の更新の手順（古い TIP と新しいエンジンの共存）と食い違わない。
- 「殻が複数でも正しいか」を Mac のテストで確かめる土台ができる（レビューの指摘 12）。

### 7.2 費用と残ること
- エンジンの中の表のキーを全部替える（機械的だが行数は多い）。エンジンのテストの書き換えが要る。
- ログの `session=` は接続をまたいで同じ番号になる。結ぶときに `conn=<番号>` を足すか（番号だけで文字は出さない。NFR-19 の範囲）は、実装の PR で決める。
- Windows では、アプリを開き直すと文脈の履歴が切れる（U1 の場合）。
- 設定の `engine.*` の変更の反映は W4-s まで効かない（今と同じ）。

### 7.3 ADR 0063 の直し（D8。この ADR の承認と同じ PR で）
- §1.2 の「`Hello` は `shell_version`、返事は `engine_version` の文字列を運ぶが、比べてはいない」を、「`shell-core` の `hello` は文字列を比べ、違えば `Shutdown` を送って起こし直す（macOS の前提。ADR 0004 §5.2）。Windows の engine-host は `Shutdown` で終わらないので、今は保存が走るだけ。Windows の扱いは ADR 0064」に直す。
- §3 の 5 の「インストーラが止めて（`Shutdown`。版が違っても受ける）」を、「インストーラが止めて（止める口は W5 のインストーラの ADR。ADR 0064 §6.2）」に直す。
- §3 の 6 に「Windows の TIP は版の違いでエンジンを止めない（ADR 0064 の D4・D5）」を 1 文足す。

## 8. 実装の進め方（承認のあと）
1. 契約: `engine` に `Connection`（接続の口）の型とシグネチャ、`ShellConfig` に `engine_owner` を足す（スタブ）。`shell-ffi` と TIP の既定値。
2. レーン A（engine、engine-host）: キーの置き換え（D1・D2）と、§4.4 の 1・2。
3. レーン B（shell-core、TIP）: D4・D5 と、§6.4 の 1。
4. 統合: §4.4 の 3 と §6.4 の 2 の土台とテスト。ADR 0063 の直し（§7.3）。`scripts/check.sh`。
- 実機（VM）: メモ帳と Edge を並べて打ち、エンジンのログの `session=`（と `conn=`）で混ざらないことを見る。版の違う TIP を入れて、エンジンが止まらないことを見る（ADR 0063 §7 の手順 5・7 と一緒に）。

## 9. ユーザーに聞く点
- **Q1. Windows の「同じアプリ」の単位**（§4.2）: U1 接続（TIP の 1 つのスレッド。アプリを閉じると履歴が切れる）／U2 プロセス／U3 exe の名前（開き直しても 30 分続くが、殻の申告に頼る）。**推奨: U1**。困る場面が出たら U2・U3 を足せる。
- **Q2. 版が違うときの扱い**（§6.1）: V1（macOS の殻だけが止めて起こし直す。Windows の TIP は共存し、`Shutdown` を一切送らない）／V2（互換の範囲。#396 のあと）／V3（今のまま、更新のたびにサインアウト）。**推奨: V1**。あわせて ADR 0063 の 3 か所を事実に合わせて直す（§7.3）。
- **Q3. Windows でエンジンを止める道**（§6.2）: エンジンのパイプの `Shutdown` は「保存だけ」のままにし、インストーラが止める口は別にする（中身は W5 の ADR）／パイプの `Shutdown` で終わるようにする。**推奨: 別の口**（誤った 1 通でエンジンが止まる道を残さない）。
