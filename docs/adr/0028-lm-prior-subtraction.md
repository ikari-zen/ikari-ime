## 0. 要点

1. 同音語の選び誤りのうち、決め手のある 94 件では正解がすべて LM のプールにある。足りないのは重み。(3) の 54 件では、文脈は LM を正解の側へ動かしている（43 件）が、**文脈なしでの LM の好み（頻度の事前分布）が勝つ**（調査 §3.2、§4.3）。
2. 辞書のコスト（Sudachi のコストと chiVe の頻度）は、すでに頻度を持っている。LM の加点にも文脈なしの頻度が入っているので、**頻度を二重に数えている**。文脈なしの好みを β 倍して引けば、LM の加点は「文脈が足した分」に近づく（β=1 で、文脈ありと文脈なしの確率の比。PMI に近い形）。
3. 式: 文脈があるとき、`LM の加点 = L文脈(s) − β × L文脈なし(s)` を、最小が 0 になるようにずらして足す。L は今と同じ `clamp(α × (NLL − 最小の NLL) × 1000, 0, 6000)`。文脈がない、または条件（§3.2）に当たるときは今のまま。
4. 時間: 採点が 2 回になる。**文脈ありを先に採点し、文脈なしは後**。文脈なしが間に合わなければ、今の式（β=0）で返す。LM が付く変換の割合はほぼ下げない作りにする（下がりうる経路は §3.4）。文脈なしの採点は読みとプロフィールだけで決まるので、プロンプトをキーにした小さなキャッシュで使い回す（ディスクには書かない）。
5. 並びの位置は変えない（学習 → Guard → LM → B40 → B32）。変わるのは LM の段が足す値だけ。
6. スパイク（`spike/b41-lm-prior`）で、β と条件を **dev だけで**選び、test で 1 回だけ確かめる。測るもの: 全セットの 1 位（LM あり 12 セットと AJIMEE）、snapshot、LM の時間（p50/p99、時間切れ、文脈なしが付いた割合）、実機の打鍵の間隔から見積もる「Space までに間に合う割合」、学習のシナリオ。**測定は B42 のマージのあとの評価セットで行う**。
7. 止める条件の数値（精度の正味、間に合う割合）は案を §5.5 に置き、ユーザーに聞く（§8）。

## 1. 現状（コードで確かめたこと）

### 1.1 加点の式と位置
- `lm/src/ranker.rs` の `ZenzRanker::apply`: 採点した候補ごとに `d = clamp(round(alpha × (NLL − 最小の NLL) × 1000), 0, max_total)` を score に足す。既定は `alpha` 1.0、`max_total` 6000（`lm/src/config.rs`）。採点の対象外（プールの 33 件目以降）は採点した中で最悪の d、Rewriter の候補は base_cost が最小の候補の d。
- プロンプト（`lm/src/prompt.rs`）: `[EE03 プロフィール][EE04 話題] [EE02 左文脈の末尾 40 文字] EE00 読み（カタカナ） EE01`。話題は解析窓の内容語から最大 3 語。空の部分はタグごと省く。

## 2. 問題

- 文脈が決め手を持っていても、zenz small の頻度の好み（使用、構成、対象、完成 など）が勝つ。LM なしなら正解だったものを LM が崩す件もある（点＋たいしょう、決して＋ようい、怪我人を＋かいほう、世界の＋しゅうまつ など。調査 §4.3）。
- LM の重みを一律に上げる案は正味マイナス（調査 §6、lm-regression §4）。モデルを替える案は後回しのユーザー決定のまま（xsmall は −65。調査 §6.1）。
- 守る条件: 候補は辞書から作り、LM は並べ替えだけ。読みに対応しない候補を出さない。LM は zenz-v3.2 small のみ。LM が付く変換の割合（約 87〜88%）を下げない。

## 3. 決定（提案）

**文脈があるときだけ、LM の加点から「文脈なしのプロンプトでの LM の加点」を β 倍して引く。文脈なしの採点は文脈ありの後に行い、間に合わなければ今の式で返す。β と効かせる条件はスパイクで dev だけを使って選ぶ。**

### 3.1 式
採点する候補の集合 S（今と同じ。プールの先頭 32 件、Rewriter を除く）について:

```
Lc(s) = clamp(round(α × (NLLc(s) − min_S NLLc) × 1000), 0, M)     文脈ありのプロンプト（今の加点）
Lp(s) = clamp(round(α × (NLLp(s) − min_S NLLp) × 1000), 0, M)     文脈なしのプロンプト
d(s)  = Lc(s) − round(β × Lp(s))      条件（§3.2）を満たすとき
d(s)  = Lc(s)                          それ以外（今のまま）
d'(s) = d(s) − min_S d                 最小を 0 にする（今と同じく、加点は 0 以上）
```

- α = 1.0、M = `max_total` 6000 は変えない。
- **文脈なしのプロンプト**: 文脈ありのプロンプトから、左文脈（EE02）と話題（EE04）を外したもの。プロフィール（EE03）は残す（シミュレーションと同じ形）。プロフィールも外す形は dev の比べる対象の 1 つにする（§5.2）。
- 文脈なしの NLL がない候補（キャッシュにも採点の結果にもない）は Lp = 0 とする。Lp = 0 は「LM の事前の好みがいちばん強い」扱いで、引く量が 0。**引かないほうに倒す**（何も分からない候補を持ち上げない）。
- 採点の対象外の候補は d' の最大、Rewriter の候補は base_cost が最小の候補の d'（今と同じ規則を d' に当てる）。
- 加点の幅: d' の最大は M ＋ β × M まで広がる（β=0.75 なら 10500）。今の幅（M）に収める上限（`min(d', M)`。以下 C5）を付けるかは、学習のシナリオと dev で決める。

### 3.2 効かせる条件
条件はすべて、変換 1 回（読みと文脈）について決める。どれかに当たったら β を使わない（今の式）。

| # | 条件（当たったら引かない） | 狙う崩れ（§1.3） | スパイクで試す値 |
| --- | --- | --- | --- |
| C1 | 左文脈（プロンプトに入る末尾 40 文字）が N 文字未満 | 1 語の短い文脈のあとの語（本＋と、水＋と）、助数詞（三＋しゅう） | N ∈ {1（文脈が空のときだけ引かない。シミュレーションと同じ）, 2, 3, 4} |
| C2 | 読みが M 文字未満 | 1 文字の語（と → 途、こ → 湖） | M ∈ {1, 2} |
| C3 | 左文脈の最後の語が数詞（ADR 0019 §2.2 の規則 C と同じ判定） | 助数詞（三＋しゅう → 州） | あり／なし |
| C4 | 異字同訓（直して → 治して、測ろう → 計ろう、図る → 謀る） | verbs 3、ext 数件 | **今回は作らない**。実行時に異字同訓の表（kun.tsv）を引く口がなく、判定が重い。C1〜C3 のあとに崩れが残ったら、改めて考える |

- 候補ごとに β を変える条件（候補の長さなど）は置かない。同じ変換の中で候補ごとに引く・引かないが分かれると、引かなかった候補が一律に不利になるため。
- C1 は C2・C3 の大半を覆う可能性がある（counters は 25 / 32 件が文脈 1 文字）。dev で効かない条件は入れない（使われない条件を残さない）。

### 3.3 採点の順と、文脈なしの採点のキャッシュ
- **1 つの要求に 2 つのプロンプトを入れる**。ワーカーは「最新の要求だけ」を処理するので、2 つの要求に分けると後の要求が前の要求を置き換えてしまう。
- ワーカーは次の順に採点する。
  1. 文脈ありのプロンプトで S を採点する（今と同じ）。結果をすぐ返す（1 通目）。
  2. 文脈なしのプロンプトで、キャッシュにない候補だけを採点する。その前に新しい要求が来ていれば、文脈なしの採点はやめて新しい要求に移る（打鍵が速いとき、使われない計算をしない）。終わったらキャッシュに入れ、2 通目を返す。
- キャッシュ: キーは文脈なしのプロンプト（＝プロフィール＋読み）、値は表記 → NLL。LRU で 256 プロンプト（1 プロンプト 32 候補として数百 KB）。表記ごとに足していくので、プールが文脈で少し変わっても、足りない表記だけを採点する。
  - モデルを替えたら（`model_kind`、モデルのファイル）消す。アイドルの解放（NFR-11）では消さない（同じモデルなら値は同じ）。
  - **ディスクには書かない**（読みを残さない。NFR-19 の考え方。プロセスが終われば消える）。
- 先行計算: 今の先行計算（打鍵ごとの Prefetch）がそのまま両方を回す。読みが伸びるたびに文脈なしのプロンプトも変わるので、キャッシュが効くのは「同じ読みをまた打つ」とき（同じ語を何度も打つ、Space で末尾の n が ん になって読みが変わったあとの再採点、文脈の番号が変わったあとの再採点）。実機での当たりの率は分からない（§7）。
- 2 回目の採点を軽くする手（スパイクで測る）: (a) 文脈なしは、LM の前の順位の上位 K 件だけを採点する（K ∈ {32, 16}。残りは Lp = 0）。ADR 0021 §2.5 では、16 候補にしても 1 位は 11 セットで −1 件だった。(b) 2 つのプロンプトを 1 回の decode にまとめる（`llama.rs` でシーケンスを 2 系統にする）。(b) は採点の作りが変わり、ADR 0021 が L4 を見送った理由（`llama.rs` が複雑になる）と同じ懸念があるので、(a) で足りないときだけ試す。

### 3.4 締め切りに間に合わないとき
`rank()` は今と同じく、締め切り（変換 1 回につき 1 つ）までの残りだけ待つ。

| 状況 | 扱い |
| --- | --- |
| 文脈ありが間に合わない | 今と同じ（LM なし。遅れて届いた結果は `late` に残す） |
| 文脈ありは届き、文脈なしがキャッシュにある | §3.1 の式 |
| 文脈ありは届き、文脈なしは計算中 | 文脈ありが届いてから最大 G ms だけ待つ（締め切りを超えない）。間に合わなければ **今の式（β=0）** で返す。文脈なしの結果は届いたらキャッシュに入れる |
| 文脈なしだけがある | 使わない（文脈なしの加点だけを引くと、LM の頻度の好みを逆向きに足すことになる） |
| `late` に当たった | 文脈ありは `late` の値。文脈なしはキャッシュにあれば使い、なければ β=0 |

- G（文脈なしを待つ上限）は、スパイクで測った文脈なしの採点の時間から決める。初めの値の案は 50ms（窓 0 の採点 26.6ms の約 2 倍）。
- **LM が付く変換の割合が下がりうる経路**: 先行計算の `rank()` が文脈なしを待つ間に Space が来ると、Space の時点で計算中になる（ADR 0021 の L1 で最大 30ms 待つ）。L1 の 30ms は文脈なしの採点（26.6ms）とほぼ同じ長さなので、多くは待って当たる見込みだが、Space の表示がその分遅れる。待っても終わらなければ、その変換は LM なしになる。この割合を §5.3 で見積もる。
- エンジンの側で「文脈ありの結果をまずキャッシュに置き、文脈なしが届いたら差し替える」形（2 段の公開）にすれば、Space が文脈なしを待つことはなくなる。ただし engine の `cache.rs` に状態が増える。§5.3 の見積もりで割合の低下が線を超えたときだけ考える（§4 の案 T3）。

### 3.5 学習、規則 S（B40）、英字の規則（B32）との順序
- **順序は変えない**: 学習（ADR 0013）→ Guard → LM（この ADR の式）→ B40 → B32。
- 学習: 学習は LM の前にあるので、学習の加点の値は変わらない。変わるのは、LM が学習を覆す量。加点の幅が M から最大 (1+β)M に広がると、LM が学習を覆しやすくなる。ユーザーが頻度の高い表記（使用）を学習で選んでいるとき、引いた分だけ LM が珍しい表記（試用）に寄せる。spec の基本原則（学習は支援であって決定ではない）とは矛盾しないが、ADR 0003 §6-11 の「LM が学習で上げた候補を覆さないこと」を確かめる対象になる。学習のシナリオ（LM あり）で崩れが出たら、幅の上限（C5）を付ける。
- B40（ADR 0024）: B40 は LM の直前の score と LM の後の 1 位を比べる。この ADR は LM の段の中の値だけを変えるので、B40 はそのまま働く。引くことで「サ変でない名詞＋する」が 1 位に上がっても、B40 が戻す。
- B32（ADR 0020）: 最後の段で、1 位が英字ならカタカナを繰り上げる。この ADR の後に当たるので、「カタカナ 1 位、英字 2 位」は変わらない。2 位以下の順は変わりうる。
- GrammarGuard、LearningGuard: LM の前で働くので変わらない（LM は今も Guard の対象外。ADR 0003 §2.1）。

### 3.6 改める既存の決定（承認されたら）
- ADR 0002 §13.2 の「加点は `α × (NLL − min NLL) × 1000`」に、「文脈があり、§3.2 の条件に当たらないときは、文脈なしのプロンプトでの加点を β 倍して引く」を足す（本文は書き換えず、索引の備考に書く。ほかの ADR と同じ扱い）。
- ADR 0003 §2.1 の「Zenz を最後に置き、最終的な順位を決めさせる」の位置は変えない。LM が並びに持ち込むものを「文脈を条件にした確率」から「文脈が足した分（頻度の好みの一部を除いたもの）」に改める。頻度は辞書のコストと話題が受け持つ。

## 4. 検討した案

| 案 | 内容 | 判断 |
| --- | --- | --- |
| **P（採用）** | 文脈があるときだけ、文脈なしの加点を β 倍して引く。文脈ありを先に採点し、文脈なしが間に合わなければ今の式 | シミュレーションで正味 +21〜+31。モデルも候補も変えない。間に合わなくても今の式に戻るだけ |
| K | LM の重みを一律に上げる（α を上げる） | **やらない**。正味 −21〜−25（歪みを除いても −4〜−8。調査 §6）。lm-regression §4 と同じ向き |
| W | LM の重みを一律に下げる | **やらない**。LM が直す入力を失う（ADR 0024 §5 で alpha 0.5 が正味 −38） |
| T1 | 文脈なしの採点を、文脈ありの前に行う | **やらない**。文脈なしだけ届いても使えないので、間に合わないときに何も残らない |
| T2 | 2 つのプロンプトを別の要求で送る | **やらない**。ワーカーは最新の要求だけを処理するので、後の要求が前を置き換える |
| T3 | エンジンの先行計算の結果を 2 段で公開する（文脈ありで一度置き、文脈なしが届いたら差し替える） | **今は作らない**。engine の `cache.rs` に状態が増える。§5.3 で LM が付く割合の低下が線を超えたときに考える |
| T4 | 文脈なしの採点を、アイドル時に次の読みを予測して先に済ませる | **やらない**。次に打つ読みの予測が要る（ADR 0021 の L7 と同じ理由で見送る） |
| T5 | 文脈なしの好みを、LM ではなく辞書の頻度（chiVe など）で近似して引く | **やらない**。引きたいのは zenz 自身の好みで、辞書の頻度とは一致しない。辞書の頻度はすでに base_cost に入っている |
| T6 | 文脈なしの好みを表にして、辞書の作成時に焼き込む（読み → 表記 → NLL） | **今は作らない**。読みと表記の組が多く、作成の時間と容量が大きい。実行時のキャッシュで足りるかをまず測る |
| M | モデルを足す・替える（大きいモデル） | 後回し（ユーザー決定のまま）。この ADR の結果を見てから（調査 §8 #7） |
| C4 | 異字同訓を判定して引かない | 今回は作らない（§3.2） |

### 5.2 精度の測り方（β と条件は dev だけで選ぶ）

  1. β ∈ {0.25, 0.5, 0.75, 1.0}（条件は C1 の N=1 だけ。シミュレーションと同じ形）。

### 5.3 応答時間の測り方

- (c) 実機の見積もり（L0 のログを読むだけ。インストールしない）: ADR 0021 §8 と同じ組み立てで、変換ごとに「最後の打鍵から Space まで」と「先行計算の所要」を対応させ、先行計算の所要に (a) で測った文脈なしの時間（読みの長さごと。キャッシュなし）を足したとき、(i) Space の前に文脈ありが終わる割合（＝LM が付く割合。今 88%）、(ii) 文脈なしまで終わる割合、(iii) Space の時点で計算中になり L1 で待つ割合と、その待ちの p50・p99、(iv) L1 で待っても終わらず LM なしになる割合を数える。2 文節以上（17.5%）は文脈なしも 2 回と数える。

## 8. ユーザーに聞くこと

### Q1. 精度の止める線（§5.5 の S1、S2、S4）
- 背景: 効果はシミュレーションで正味 +21〜+31（13 セット 2221 件。0.9〜1.4 ポイント）。β は test を含めて選んだ値なので、スパイクでは dev だけで選び直す。dev で選ぶと test の効きは小さくなるのがふつう。
- 例: シミュレーションの ext-test（262 件）は +3〜+5。
- 選択肢:
  - (a) 案のとおり: dev の正味 +10 未満、test の正味 0 以下、AJIMEE −3 件以下で止める。
  - (b) きびしく: dev +15 未満、test +3 未満、AJIMEE −1 件以下で止める。test は 440 件ほどなので、+3 は揺れと区別しにくい。
  - (c) ゆるく: dev がプラスなら test を見て決める。
- **推奨: (a)**。test の件数が少ないので、test には「悪くならない」ことだけを求め、効果の大きさは dev で見る。

### Q2. 応答時間の止める線（§5.5 の S5、S7）
- 背景: 採点が 2 回になる（キャッシュに当たらないとき）。文脈なしは文脈ありの後に回し、間に合わなければ今の式に戻すので、LM が付く割合はほぼ下がらない作りにしてある。ただし、先行計算が文脈なしを待つ間に Space が来ると、Space の表示が最大 30ms 遅れる（L1）。
- 例: 実機（L0 のログ）では、先行計算の p50 39.8ms、p90 52.6ms。最後の打鍵から Space までは p10 98ms。文脈なしの採点（約 27ms）を足しても、多くは Space の前に終わる見込み（見積もり）。
- 選択肢:
  - (a) 案のとおり: LM が付く割合 87% 未満、または L1 で待つ割合が +3 ポイントを超えたら止める。
  - (b) Space の遅れを許さない: L1 で待つ割合が増えたら止める（増えるなら、先行計算の 2 段の公開 T3 を作る）。
  - (c) 遅れを許す: LM が付く割合だけを見る。
- **推奨: (a)**。ADR 0021 の約 87% を守り、遅れが出る変換を少数に限る。

### Q3. スパイクの版を、実機のふだんの入力で試すか
- 背景: §5.3 (c) は、ログの打鍵の間隔からの見積もり。実際に β を効かせた版を使えば、間に合う割合と、変換の手応え（珍しい語が上がりすぎないか）を直に見られる。インストールは聞かずに行ってよい決まりだが、ふだんの変換の振る舞いが変わる。
- 選択肢:
  - (a) 評価とログの見積もりで止める条件を見たあと、通ったときだけ、本実装（`feat/b41-lm-prior`）の版を数日使ってもらう。
  - (b) スパイクの版をすぐ実機に入れて、測定と並行して使ってもらう。
  - (c) 実機では試さず、評価だけで採否を決める。
- **推奨: (a)**。評価で止める版を実機に入れない。使ってもらう版には、L0 のログに文脈なしが付いたかの固定の語を足す（読みと候補は書かない）。

### Q4. β を設定アプリに出すか
- 背景: β と条件は ranker-config のキーにする。ユーザーが変えたいかどうかで、設定アプリに出すかが決まる。
- 選択肢:
  - (a) 出さない。既定の値だけにする（変えたくなったら言ってもらう）。
  - (b) 「LM の頻度の好みを抑える」のような切り替え（入／切）を出す。
  - (c) β の値を出す。
- **推奨: (a)**。使われるか分からない設定を先に作らない。手応えが合わなければ、既定の値を直す。

## 9. 決定（ユーザー、2026-10-17）
§8 の Q1〜Q4 はすべて推奨どおり。
- Q1: (a)。dev の正味 +10 未満、test の正味 0 以下、AJIMEE −3 件以下のどれかで止める。
- Q2: (a)。LM が付く割合 87% 未満、または L1 で待つ割合が +3 ポイントを超えたら止める。
- Q3: (a)。評価とログの見積もりで止める条件を見て、通ったときだけ、本実装（`feat/b41-lm-prior`）の版を数日使ってもらう。スパイクの版は実機に入れない。

### 10.7 未確認のこと・限界
- S5・S7 は見積もり。e（実機の文脈なしの採点の時間）が分からず、幅が線をまたぐ。L0 のログは約 1 日（変換 404 回）。実機で測ってはいない（実機に入れていない）。
- 実機でのキャッシュの当たりは分からない。評価のキャッシュありは 95%（同じ読みが続く）で、実機の値ではない。
- 先行計算の 2 段の公開（T3）、2 つのプロンプトを 1 回の decode にまとめる手は作っていない。
- AJIMEE が崩れた理由の切り分けはしていない（崩れた件の一覧から見た事実の記述だけ）。読みの長さの上限など、AJIMEE に効く条件は試していない（試すなら dev ではなく AJIMEE を見て選ぶことになるので、選び方の見直しが要る）。
- 12 セットの基準は同じバイナリの β=0（B42 のあとの main = a8a4e11 のセット）。調査 §6 のシミュレーション（全体で +21〜+31）に対し、dev は +13〜+17、test は +4。差の原因は調べていない（β を test を含めて選んだこと、上位 30 件だけの並べ替えだったことが候補）。
- 評価の AJIMEE は `--ranker topic`（基準の構成）で、実機の `full` ではない。
- 実機の入力（長い文脈、英語まじり）での手応えは測っていない。

## 11. 停止の決定（ユーザー、2026-10-18）

- main の変換は変えない。スパイクのコードは `spike/b41-lm-prior` に残し、main に入れない。
- ADR 0002 §13.2 と ADR 0003 §2.1 は、改める前のまま有効。
- 再開を考える条件: 長い文脈の評価セット（B39）ができたとき。そのときは、AJIMEE の崩れの原因の切り分けから始める。
