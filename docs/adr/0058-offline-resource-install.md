# ADR 0058: リソース（辞書・モデルなど）を「inbox に置く」だけで入れる・更新する。隔離環境用の取得は、持ち込める束を作る

- 状態: 承認（2026-11-10。ユーザーが推奨どおりに承認: Q1 署名は 0.2 では付けず manifest に空の欄だけ持つ、Q2 自動で取り込む（エンジンが裏で）、Q3 inbox は作った辞書・表・モデルだけを受ける。Q3 により #247 は、元データと外来語の一覧を運ぶ範囲を外し、export が辞書を作る形に書き直す）
- 日付: 2026-11-10
- 対象: 新しい crate（名前は案 `ikari-resource`。束の目録・検証・入れ替え）、`engine/src/data.rs`（見回り）、`engine/src/lib.rs`（起動）、`stack`（組み立て直し）、`xtask/src/data/`（取得の固定表、`export`）、設定アプリ（状態の表示と「前の版に戻す」）
- 前提: main = 27e3808。ADR 0004 §2・§8（配置と Sandbox）、ADR 0005 §6.2（設定アプリは通信しない）、ADR 0033（Release で配る案。提案のまま）、ADR 0042（判断は Rust）、spec「辞書の更新」、NFR-17、`docs/proxy-download.md`
- タスク: #246（オフライン導入）、#247（隔離環境用の取得）。#248（設定画面からの取得）の前提。全体は #162
- 判断の置き場所: Rust（新しい crate とエンジン）。Swift は、状態の表示、inbox を Finder で開くボタン、「前の版に戻す」の要求を送るだけ（UI であるため）

## 0. ユーザーの決定（2026-10-31、2026-11-10）

1. 全リソースに、オフラインで入れる・更新する手順を用意する。特定のフォルダにファイルを置けば、インストールも更新もできる（「置くとインストールが走る」）。
2. 隔離環境用に、ダウンロードのスクリプトを別に用意する。つながる環境でダウンロードし、特定のフォルダに置くと、インストールが走る。

## 1. 現状（分かったこと）

### 1.1 リソースと置き場所
`~/Library/Application Support/ikari-ime/` の下に、次がある（実機の配置と researcher の調査）。

| リソース | ファイル | 大きさ | 作り方 |
| --- | --- | --- | --- |
| 辞書の一式 | `dict/grammar.bin`、`dict/system.dict`、`dict/vectors.bin`、`dict/BUILD_INFO` | 68MB + 227MB + 321MB | `dict-builder`（`scripts/lib.sh`、`build-dict.sh`）。元データは SudachiDict、chiVe、ABR、外来語の一覧 |
| 郵便番号の表 | `dict/postal.tsv` | 21MB | `town`（ABR） |
| 絵文字の表 | `dict/emoji.tsv` | 44KB | emoji-data から |
| モデル | `models/zenz-v3.2-small-Q5_K_M.gguf` | 70MB | 配布元のまま（`engine/src/lib.rs` の `MODEL_FILE_NAME`） |

- 取得元と sha256 の固定は `xtask/src/data/fetch.rs` の定数（元データとモデル）。`scripts/lib.sh` にも版の定数がある。
- **ビルド済みの辞書を配る場所は、まだない**（ADR 0033 は提案のまま）。辞書は、元データを取って手元で作るしかない。

### 1.2 読み込みと反映
- `system.dict`、`grammar.bin`、`vectors.bin` は mmap。エンジンの起動時と、Stack の組み立て直し（`stack/src/lib.rs` の `build_stack_with`）のたびに、`dict/` を開き直す。
- 見回り（1 秒に 1 回まで。`engine/src/data.rs`）が見るのは、`user_dict.tsv`、`profile.tsv`、`dict/postal.tsv`、`dict/emoji.tsv` だけ。辞書の 3 ファイルの差し替えは見ない。→ **今は、辞書は再起動で反映、postal と emoji は置き換えれば反映**。
- モデルのパスは起動時に決まり、`model.is_file()` が偽ならその起動は LM なし（`engine/src/lib.rs:207-208`）。LM のワーカーは最初の要求で読み、アイドル 300 秒で解放し、次の要求で読み直す（`lm/src/ranker.rs:441-470`）。→ rename で置き換えたモデルは、解放のあとの読み込みで効く。起動時になかったモデルは再起動が要る。

### 1.3 検証
- sha256 を確かめるのは取得のとき（`xtask/src/data/fetch.rs`、`sha256.rs`）だけ。エンジンは実行時に sha256 を見ない。
- 辞書は、ヘッダの magic、`FORMAT_VERSION=2`（`dict-format/src/lib.rs`）、大きさ、`grammar_id` の一致（`core/src/dict/system.rs:92-101`）、`vectors.bin` の `dict_id` の一致（`core/src/vectors/mmap.rs:41`）を見る。本体のハッシュは見ない。壊れた辞書は error になり、クラッシュしない。ただし**起動時に開けないとエンジンは起動に失敗する**（`engine/src/lib.rs:231`）。起動後の開き直しの失敗は、古い Stack のまま続ける（`reload_failed`）。
- 壊れた gguf は読み込みが Err になり、LM なしで続ける（`load_retry` の間は再試行しない）。gguf の中身は llama.cpp 任せで、こちらは検査していない。

### 1.4 権限
- エンジン: App Sandbox、network なし、Application Support の `ikari-ime/` に読み書きの一時例外（`macos/scripts/templates/engine.entitlements`）。→ inbox を読み、`dict/` を rename できるはず。**Sandbox の中のエンジンがディレクトリを rename した前例はない（未確認）**。
- 設定アプリ: Sandbox なし、通信するコードを持たない（ADR 0005 §6.2）。
- 前例: `xtask/src/data/install.rs:181-204` は「同じディレクトリの一時ファイルに書いて rename」（Sandbox の外）。

## 2. 目標と、目標にしないもの

- 目標: (1) ネットワークのない Mac で、決まったフォルダに束を置くだけで、辞書・郵便番号の表・絵文字の表・モデルを入れる・更新する。(2) 壊れた・途中で切れた・形式の合わない・古い束は入れず、今の版のまま動き続ける。(3) 入れ替え中も入力を止めない。前の版に戻せる。(4) つながる Mac で、持ち込める束を 1 コマンドで作る（#247）。(5) 同じ取り込みの経路を、#248 のダウンロードがそのまま使う。(6) Windows でも同じ設計にできる。
- 目標にしない: 端末で辞書を作ること（§13 Q3 で確かめる）、Release での配布そのもの（ADR 0033）、自動の更新の確認（#248 の先）。

| manifest | ADR 0033 §4.2 と**同じ型**にし、`kind`（辞書・表・モデル）と `origin`、空の `signature` 欄を足す。型と検証は新しい crate に置き、エンジン、xtask、`ikari-data` が共有する（§5） |

## 4. inbox と束

### 4.1 置き場所
- `<データのディレクトリ>/inbox/`。データのディレクトリは今と同じ（`IKARI_USER_DIR` で変えられる）。Windows は `%LOCALAPPDATA%\ikari-ime\inbox\` を想定（§14）。
- エンジンが起動時に作る（なければ）。`~/Library` は Finder で隠れているので、設定アプリに「取り込み用のフォルダを開く」ボタンを置く。
- inbox は `dict/` と同じボリュームにあるので、束のファイルは **rename で移せる**（コピーしない。340MB の書き込みがない。ディスクの余りも 1 世代分で済む）。

### 4.2 束の形
```
inbox/
  ikari-resources-20261110/      ← 束（名前は自由。export が日付で付ける）
    manifest.json
    grammar.bin
    system.dict
    vectors.bin
    postal.tsv                   ← 入れたい部品だけ入れればよい
    zenz-v3.2-small-Q5_K_M.gguf
  rejected/                      ← エンジンが作る（§8.3）
  status.json                    ← エンジンが書く
```
- 部品（component）ごとに入れ替える。束には一部の部品だけでもよい（例: `postal.tsv` だけ）。
- ファイルは束のディレクトリの直下だけ。名前に `/`、`\`、`..` を含むもの、manifest にないファイル、**シンボリックリンク**は拒む（lstat で見る。rename するとリンクのまま移ってしまうため）。
- **アーカイブを受けない理由**: 展開はパスを信用する処理（ディレクトリの外に書く）を持ち込む。Sandbox のエンジンに展開の crate を足す。展開先の分だけディスクが 2 倍要る。USB で運ぶならディレクトリのまま運べ、zip で受け取った人は Finder で開ける。要望が出たら、tar（圧縮なし）を後で足す。
- **gzip を受けない理由**: ADR 0033 の Release は部品を gzip で置く案だが、展開は取る側（`ikari-data`）が行い、inbox に置くのは展開後とする。inbox の形を 1 つに保つため。

### 4.3 束が「揃った」と見なす条件
- Finder や USB のコピーは、manifest を先に書き終えることも、ファイルを途中まで書いた状態で見えることもある（順番は保証されない）。そこで、次をすべて満たしたら揃ったと見なす。
  1. `manifest.json` が読めて、型が通る。
  2. 載っているファイルがすべてあり、大きさが manifest と同じ。
  3. 2 回の見回り（2 秒以上あけて）で、全ファイルの大きさと mtime が変わらない。
- 揃ってから sha256 が合わなければ、壊れていると見なして拒む（§8.3）。Finder がコピーの前に大きさを先に確保するか（大きさが先に合ってしまうか）は未確認。スパイクで確かめ（§12 S0）、先に確保するなら「変わらない時間」を延ばす。
- `export` と `ikari-data` は、`<名前>.partial/` に書いてから rename するので、自分で置いた束は途中の状態が見えない。`.partial` で終わるディレクトリは見ない。

## 5. manifest

### 5.1 形（ADR 0033 §4.2 を土台に、足すもの）
```json
{
  "schema": 1,
  "created": "2026-11-10T03:00:00Z",
  "origin": "export",
  "release": null,
  "components": {
    "dict":  { "kind": "dict",  "format": 2, "files": [{"name": "system.dict", "size": 0, "sha256": "…"}, …],
               "builder": {…BUILD_INFO と同じ考え…}, "sources": {…元データの版と sha256…} },
    "postal": { "kind": "table", "format": 1, "files": [{"name": "postal.tsv", …}] },
    "emoji":  { "kind": "table", "format": 1, "files": [{"name": "emoji.tsv", …}] },
    "model":  { "kind": "model", "format": 1, "files": [{"name": "zenz-v3.2-small-Q5_K_M.gguf", …}] }
  },
  "signature": null
}
```
- ADR 0033 §4.2 との違い: (1) `kind` を足す（モデルは辞書でない）。(2) `origin`（`export` = 利用者の手元で作った、`release` = 作者の Release、`local` = 開発者の `install-data.sh`）。(3) 空の `signature`（§6.2）。(4) inbox の束では `files` は展開後の大きさと sha256 だけ（gzip の値は Release の manifest にだけ持つ。同じ型の任意の欄）。
- `sources` には元データの出所（URL、版、sha256）を書く。**元データ（取得するもの）と成果物（入れるもの）は、`sources` と `files` で分ける**。inbox が入れるのは `files` だけ。
- 入れ替えが終わったら、エンジンはその部品の manifest を `dict/MANIFEST.json`（モデルは `models/MANIFEST.json`）に書く。次の束と比べる（§6.3）ためと、設定アプリで今の版を出すため。

### 5.2 置き場所と、固定表との関係
- 型、読み、検証は新しい crate（案 `ikari-resource`）に置く。依存は `dict-format`（形式の版の定数）だけ。エンジン、xtask、`ikari-data`（後で）がこれを使う。ADR 0033 §4.2 は「`dict-format` に置く」としたが、モデルや表を含むので、辞書の形式の crate から分ける（ADR 0033 の該当行は、承認されたらこの ADR で上書きする）。
- **固定表の統合の方針**: 
  - 元データの取得元と sha256（`xtask/src/data/fetch.rs`）は、xtask に残す。開発の道具の中のもので、製品は使わない。
  - **配布元のまま入れる成果物（今はモデルだけ）の sha256 は、新しい crate に移し**、xtask はそこから読む（1 か所にする）。エンジンが「既知のモデル」の表として使う（§6.1）。
  - `scripts/lib.sh` の定数は今のまま（`check.sh` が一致を確かめる仕組みを続ける）。`fetch-data.sh` は xtask を呼ぶ薄いものなので変えない。
- manifest を作るのは `export`（§9）と、後で ADR 0033 の Actions。作るコードも同じ crate に置く（大きさと sha256 を数えて書く）。

## 6. 検証

### 6.1 すべての束に（入れ替えの前に、全部通ったものだけ）
1. 束の形（§4.2）と manifest の型。知らない `schema`、知らない `kind` は拒む。
2. 全ファイルの大きさと sha256 が manifest と一致。
3. 形式の版が、このアプリが読める版と一致（`dict-format` の定数。表は 1）。合わなければ「アプリの更新が要る」を理由に拒む。
4. 部品ごとの検査:
   - **辞書**: 3 ファイルがそろっている（一部だけの辞書は拒む）。`dict.new/` で**試しに Stack を組み立てる**（ヘッダ、`grammar_id`、`dict_id` の照合はここで効く）。組み立てたら、決まった読み（数件）を変換して、候補が出ることを確かめる。通らなければ拒む。
   - **表**（postal、emoji）: 今の読み込みのコードで全行を読み、行の検査を通る。
   - **モデル**: sha256 が、アプリに埋めた既知のモデルの表にあるもの。表にないモデルは拒む。理由: gguf の中身は llama.cpp のパーサに渡り、こちらは検査していない。モデルの更新は、spec のとおりアプリの更新と一緒に起きる（モデルを替えれば再調整が要る。NFR-33、NFR-38）ので、表に載っていないモデルを入れる場面がない。
5. ディスクの余りが、入れる部品の大きさ + 余裕（値は実装で測って決める）以上。

### 6.2 署名（推奨: 0.2 では付けない。欄だけ持つ）
- 利用者が自分で作った束（`origin = export`）には、作者は署名できない。署名で守れるのは、作者の Release から来る束（`origin = release`）だけ。
- inbox に置ける人は、`dict/` にも直接書ける（同じユーザーの同じフォルダ）。署名は、手元の改ざんに対しては守りを足さない。守るのは「運ぶ途中」と「取得元の乗っ取り」。
- そこで、0.2（オフライン導入と export）では付けない。manifest に空の `signature` 欄を持ち、**ADR 0033 の Release を他の人に配るとき**（ADR 0033 §7.1 の条件）に、`origin = release` の束には署名を必須にする（minisign の形。検証だけの crate を足す）。どの鍵で、紛失のときにどうするかは、その ADR で決める。§13 Q1 で確かめる。
- 署名がない間に守れるのは、途中で切れた・壊れた・版の合わないファイルまで。意図的に細工された辞書は、mmap と fst のパーサに渡る（試しの組み立てで落ちる形のものは防げるが、すべてではない）。これは今の `install-data.sh` と同じ範囲で、悪くはならない。

### 6.3 古い束
- 同じ部品の `dict/MANIFEST.json` があり、束の部品の sha256 がすべて同じなら、何もしない（束は消す。結果は「同じ版」）。
- 束の `created` が今の版より古いなら、拒む（理由: 古い版）。古い版に戻すのは「前の版に戻す」（§7.4）で行う。今の版に MANIFEST がない（`install-data.sh` で入れた辞書）ときは、比べずに入れる。

## 7. 入れ替え

### 7.1 原則
- **置き換える先のファイルを開いて書かない**。新しいファイルは別の名前で用意し、rename で入れ替える。mmap 中のファイルを上書き・切り詰めると SIGBUS になるが、rename なら古い inode は閉じるまで生きる。
- 担い手はエンジンだけ（`dict/`、`models/` の書き手を増やさない）。`install-data.sh` は開発者の道具として残す（§12 で、inbox に置く形に替えるかを後で決める）。

### 7.2 部品ごとの手順と、反映

| 部品 | 手順 | 反映 |
| --- | --- | --- |
| 辞書 | 1. `dict.new/` を作り、束の 3 ファイルを rename で移す。今の `dict/` にあって束にない部品（`postal.tsv`、`emoji.tsv`、`MANIFEST.json` の他の行）は、ハードリンク（できなければコピー）で足す。2. 試しの組み立てと変換（§6.1）。3. journal に「入れ替え中」を書く。4. 前の `dict.prev/` を消し、`dict` → `dict.prev`、`dict.new` → `dict` の rename。5. `dict/MANIFEST.json` を書く。6. 2 で組み立てた Stack に切り替える。journal を消す | **再起動は要らない**。2 の Stack は `dict.new/` のファイルを mmap しており、rename のあとも同じ inode を指す。切り替えは要求と要求の間（今の組み立て直しと同じ）。学習、LM、表は `Reuse` で使い回す |
| postal、emoji | `dict/postal.tsv.new` に rename で移す → 検査 → `postal.tsv` → `postal.tsv.prev`、`.new` → `postal.tsv` | 再起動は要らない。今の見回りが変化を見て読み直す |
| モデル | `models/<名前>.new` に移す → sha256 の表 → `<名前>` → `<名前>.prev`、`.new` → `<名前>` | 読み込み済みなら、次の解放（アイドル 300 秒）のあとから新しい版。すぐ効かせるなら LM のワーカーに解放を頼む（その口があるかは要確認）。**起動時にモデルがなかった場合**、今は再起動が要る。組み立て直しのときに `model.is_file()` を見直すように変える（契約）と、再起動なしで LM ありになる |

- 辞書の入れ替えで、2 つの Stack が少しの間並ぶ。mmap なので、増えるのは触れたページとヒープの分（未計測。§12 S0 で測る）。
- 手順 4 の 2 つの rename の間で落ちると、`dict/` がない状態になる。journal（`inbox/.journal.json`。部品と段階）を見て、次の起動で先に進める（`dict.new` があれば `dict` にする）か戻す。macOS の `renamex_np(RENAME_SWAP)` なら 1 回で入れ替えられるが、Windows にないので、journal で両方を同じに扱う。

### 7.3 失敗したとき
- 手順のどこで失敗しても、`dict/` は今の版のまま（手順 4 の前なら触っていない。4 の途中なら journal で直す）。`dict.new/` に移したファイルは `inbox/rejected/<束>/` に戻す。
- 起動後の失敗は、今の `reload_failed` と同じく、古い Stack で続ける。

### 7.4 前の版に戻す
- 設定アプリの「前の版に戻す」が、エンジンに要求（小さい IPC。部品の名前だけ）を送る。エンジンは `dict` と `dict.prev` を、§7.2 と同じ手順（試しの組み立て → journal → rename）で入れ替える。戻したあとの `dict.prev` は戻す前の版になるので、もう一度押せば元に戻る（2 世代を行き来する）。
- `.prev` は 1 世代だけ。辞書 2 世代でおよそ 1.2GB。

## 8. きっかけと担い手

### 8.1 推奨: エンジンの見回りが inbox を見て、別のスレッドで自動で取り込む（案 a'）
- 見回り（今の 1 秒に 1 回）に、inbox のディレクトリの mtime と、束ごとの §4.3 の判定を足す。揃った束があれば、取り込みのスレッドを 1 つ起こす（同時に 1 つ）。
- 重い処理（sha256、試しの組み立て）は取り込みのスレッドで行い、要求を処理する流れを止めない。最後の Stack の切り替えだけが、要求と要求の間に入る。sha256 の時間（約 700MB）は未計測（§12 S0）。
- 起動時: `dict/` があれば、いつもどおり起動してから見回りに任せる（起動を遅くしない）。**`dict/` がなく、inbox に辞書の束があるときだけ**、その場で取り込んでから組み立てる（初めての導入。どのみち入力できない）。
- 理由: ユーザーの決定「置くとインストールが走る」にそのまま合う。判断と書き込みがすべて Rust のエンジンの中にあり、Windows でも同じ。Sandbox の中で完結し、新しい権限が要らない。

### 8.2 検討した担い手
| 案 | 長所 | 短所 |
| --- | --- | --- |
| a. 起動時だけ inbox を見る | 単純 | 340MB の検証と組み立てで起動が遅れ、その間は入力できない。置いても、次の起動まで何も起きない |
| **a'. 見回り + 別のスレッド（推奨）** | 上のとおり | 見回りに inbox の判定が増える。コピーの途中を見分ける条件（§4.3）が要る |
| b. 設定アプリの「取り込む」ボタンからエンジンへ要求 | 途中のコピーを見分けなくてよい（押したときは置き終わっている） | 「置くだけ」にならない。手順が 1 つ増える。中身は a' と同じコードなので、後から足すのは容易 |
| c. 別の実行ファイル `ikari-data` が入れ替え、エンジンを再起動 | xtask と同じコードを使える | `dict/` の書き手が 2 つになる。エンジンを再起動させる合図が今ない。`ikari-data` に Application Support の一時例外が要る。再起動の間は入力が止まる |

- b は §13 Q2 の「手動」を選んだときの形。a' を選んでも、設定アプリに「今すぐ取り込む」を足すのは同じコードで済む（足すかは使ってから決める）。

### 8.3 結果の知らせ
- `inbox/status.json` に、束ごとの最後の結果（取り込んだ・同じ版・拒んだ、その理由、日時）を書く。設定アプリ（Sandbox なし）はこれを読んで出す。エンジンのログにも残す。
- 拒んだ束は `inbox/rejected/<束>-<日時>/` に移し、`reason.txt` を置く（同じ束を何度も検証しないため）。古い拒否の掃除は、件数で（値は実装で決める）。
- 通知（バナー）は出さない（入力の邪魔をしない。ADR 0033 §8 と同じ）。

## 9. 隔離環境用の取得（#247）

### 9.1 推奨: `cargo xtask data export --out <dir>`（0.2）
- つながる Mac で、リポジトリから流す。中身は、今の取得（固定の URL と sha256）→ 辞書のビルド → 表のビルド → 成果物を `<dir>/<束>.partial/` に集め、manifest を書いて rename。`--only dict --only postal --only model` で部品を選べる。
- 出力の束をそのまま USB で運び、隔離環境の inbox に置く。
- `fetch-data.sh` との関係: `export` は同じ取得のコード（xtask）を呼ぶ。プロキシは `docs/proxy-download.md` と同じ（curl の環境変数）。新しい取得の経路は作らない。
- 理由: 今は Release がない（§1.1）ので、辞書は誰かが手元で作るしかない。作るにはリポジトリとツールチェーンが要り、それを持つのは xtask。OS に依存しないので Windows でも使える（ADR 0042）。
- 利用者が自分の手元で作るので、作者が辞書を再配布することにはならない（ADR 0033 の配布の判断を待たずに出せる）。

### 9.2 後で: `ikari-data export`（ADR 0033 の Release ができたら）
- アプリの中の `ikari-data` が、Release から部品を取り、gzip を展開して、束にする。リポジトリもツールチェーンも要らない。#248 と同じコード（出力先が inbox か、指定のフォルダかの違いだけ）。

### 9.3 検討した案
- シェルのスクリプト: Windows で使えない。manifest を作るコードを Rust と二重に持つ。却下。
- 元データ（SudachiDict の zip、chiVe など）を運び、隔離環境で辞書を作る: アプリに `dict-builder` とポリシーを入れ、端末で数十秒の重い処理を走らせることになる。ADR 0033 の「端末では作らない」と逆。§13 Q3 で確かめる。

## 10. 設定画面からの取得（#248）とのつなぎ
- 設定アプリのボタンは `ikari-data`（`Helpers/`。Sandbox に入れ、`network.client` と inbox への書き込みだけ）を起こす。`ikari-data` は取って、gzip を展開し、sha256 を確かめ（取りそこねを早く知るため）、`inbox/<束>.partial/` から `inbox/<束>/` に rename する。**ここまで**。
- 検証と入れ替えは、オフラインと同じエンジンのコード（§6、§7）。`ikari-data` の sha256 の確認は早く知るためで、エンジンは改めて全部を確かめる（`ikari-data` を信用しない）。
- 設定アプリは通信しない（ADR 0005 §6.2 のまま）。状態は `status.json` を読む。

## 11. NFR-17 の例外の範囲（#248 を始める前にユーザーに聞く）
- この ADR の範囲（#246、#247）では、製品は通信しない。`export` は開発の道具（xtask）で、製品ではない。
- #248 で通信できるのは `ikari-data` だけ。通信先の推奨は「このプロジェクトの Release（GitHub の固定の URL）だけ」。ビルドに埋め、設定やユーザーのデータから変えられないようにする。送るのは GET だけ。
- 決めることが残る: モデル（zenz）を Release に置けない場合に、`ikari-data` が配布元（Hugging Face）にも行ってよいか。spec の NFR-17 は「モデルの更新はユーザーが手動で置く」としているので、行かない（モデルは export か手で置く）のが今の spec に沿う。#248 の ADR で聞く。

## 12. テスト方針と実装の段階

### 12.1 テスト
- **新しい crate の単体テスト**（一時ディレクトリ。`cargo test` に入る）: 途中で切れた（大きさが足りない）、sha256 が合わない、形式の版が違う、一式の一部だけ、`grammar_id` / `dict_id` が合わない組、知らないモデル、名前に `..`、シンボリックリンク、manifest にないファイル、古い `created`、同じ版、ディスクが足りない（余りの見積もりを差し替えて）。手順の各段で失敗を差し込み、`dict/` が今の版のままか、journal で直ることを確かめる。
- **mmap 中の入れ替え**: Stack を組み立てて変換しながら、入れ替え → 古い Stack でも新しい Stack でも変換が続く。
- **エンジンの統合テスト**: inbox に束を置く → 見回り → 新しい辞書で変換。辞書のない起動 + inbox の束で起動できる。「前の版に戻す」の要求。
- **ネットワークを切った状態**: 製品の殻・エンジンに `network.*` がないことは `build.sh` が確かめている（今のまま）。オフラインの導入は、そもそも通信しない（テストはエンジンのテストでよい）。`export` は、通信できないときに分かる理由で止まり、`.partial` を残さないこと。
- **プロキシ**: `export` は `docs/proxy-download.md` の手順（ローカルのプロキシ）で一度確かめ、手順に足す。
- **実機**: スパイク（S0）と、段階ごとに 1 回、`export` → USB 相当のコピー（Finder）→ inbox → 変換、を手順の記録に残す。smoke はユーザーの了解を取ってから。

### 12.2 段階（1 タスク 1 ブランチ。issue は task-keeper が切る）
- **S0. スパイク（捨てるコード。実機）**: Sandbox の中のエンジンで、(1) inbox → `dict.new/` の rename、`dict` のディレクトリの rename、ハードリンク、(2) mmap 中のディレクトリの rename のあとも変換が続くか、(3) Finder で 700MB をコピーしたときに、大きさが先に確保されるか、(4) 700MB の sha256 と試しの組み立ての時間、2 つの Stack が並ぶときのメモリ。結果をこの ADR に追記する。→ 新しい issue
- **#246-1 契約**: 新しい crate の manifest の型、検証の結果の型、journal の形、`inbox/status.json` の形、エンジンの「前の版に戻す」の要求（proto）。モデルの sha256 の表を移す。→ #246 の子の issue
- **#246-2 エンジン**: 見回り、取り込みのスレッド、入れ替え、起動時の回復、初めての導入、`model.is_file()` の見直し。→ #246
- **#246-3 設定アプリ**: 状態の表示、「取り込み用のフォルダを開く」、「前の版に戻す」。→ 新しい issue
- **#247 export**: `cargo xtask data export`。手順の文書（`docs/` に隔離環境の手順。README からリンク）。→ #247
- **#248**: ADR 0033 の Release と NFR-17 の範囲が決まってから。`ikari-data` の取得 → inbox。→ #248
- 後で決める: `install-data.sh` を「inbox に置く」形に替えるか（書き手を 1 つにできるが、開発中の素早い入れ替えが遅くなる）。#246-2 のあとで使ってから決める。

## 13. ユーザーに聞くこと（推奨つき）

### Q1. 束に、作者の署名を付けるか
- 推奨: **0.2 では付けない。manifest に空の欄だけ持ち、作者が Release で他の人に配るときに、Release の束だけ署名を必須にする**。
- 理由: 利用者が自分で作った束には、作者は署名できない。inbox に置ける人は辞書のフォルダにも直接書けるので、手元の改ざんには署名が効かない。効くのは「Release を取る途中」と「Release の置き場所の乗っ取り」なので、Release を配るときに付ければ足りる。
- 付けない間に防げるもの: 途中で切れた・壊れた・版が合わないファイル。防げないもの: わざと細工されたファイル（今の `install-data.sh` と同じ）。モデルは、アプリが知っている sha256 だけを入れるので、細工されたモデルは入らない。
- 別の案「今から署名を必須にする」: 自分で作る束（export）が使えなくなる（作者の鍵が要る）。鍵を持ち続ける手間と、なくしたときの対処（古いアプリが新しい束を受けなくなる）が今から生じる。

### Q2. いつ、だれが取り込むか（自動か手動か）
- 推奨: **自動。エンジンが、置かれた束を見つけて、入力を止めずに裏で取り込む**（§8.1）。辞書もモデルも再起動は要らない。辞書がまだないときだけ、起動の中で取り込む。
- 長所: 決定どおり「置くだけ」。設定アプリを開く必要がない。短所: コピーの途中を見分けるための条件（数秒、大きさが変わらない）が要り、コピーが遅い USB では、取り込みが数秒遅れて始まる。
- 別の案「手動: 置いたあと、設定アプリの『取り込む』を押す」: 途中のコピーを見分けなくてよく、いつ入れ替わるかが分かりやすい。短所は手順が 1 つ増えること。中身は同じコードなので、自動を選んでも、ボタンは後から足せる。

### Q3. inbox が受けるのは「作った辞書」だけでよいか（元データを受けて端末で作らない）
- 推奨: **作った辞書（と表、モデル）だけを受ける**。辞書は、つながる側の `export` が作る（§9.1）。
- 長所: アプリに辞書を作る道具を入れなくてよい。隔離環境で重い処理（数十秒、メモリ）が走らない。ADR 0033 の「端末では作らない」と同じ向き。短所: 0.2 では、つながる側に、リポジトリと Rust のツールチェーンが要る（README の 0.1.0 の手順と同じ）。ツールなしで束を作れるのは、ADR 0033 の Release ができてから（`ikari-data export`）。
- 別の案「元データを運び、隔離環境で作る」: つながる側は取るだけで済むが、アプリに `dict-builder` を入れ、端末で辞書を作る仕組みを持つことになる。外来語の一覧（#247 の対象）も、元データとして運ぶことになる。

## 14. Windows への持ち越し
- 置き場所は `%LOCALAPPDATA%\ikari-ime\inbox\`、束と manifest と検証は同じ crate。
- **Windows では、mmap 中のファイルを含むディレクトリの rename や、古い版の削除が失敗することがある**（推測。Rust の `File::open` は削除の共有を許すが、ディレクトリの rename と mmap の組は未確認）。失敗したら、版つきのディレクトリ（`dict-<id>/`）と「今の版」を指すファイルの形に替える案を、Windows の ADR で検討する。今の macOS では `dict/` の形を変えない（`install-data.sh`、CLI の `--dict`、ADR 0004 §2 の配置がそのまま使える）。
- 見回り、取り込みのスレッド、journal は OS に依存しない。

## 15. 懸念・要確認
- Sandbox の中でのディレクトリの rename、ハードリンク（S0）。できなければ、ファイルごとの rename と journal に替える（一式の組は `grammar_id`、`dict_id` で守られるので、混ざっても起動で落ちるだけ。journal で直す）。
- Finder のコピーの途中の見え方（S0）。
- LM のワーカーにすぐ解放を頼む口があるか（なければ、次の解放を待つ。急がない）。
- `dict/MANIFEST.json` は ADR 0033 §7.3 の `origin` と同じファイルにする。ADR 0033 §7.3 の「`origin = local` は上書きしない」は、inbox では当てはめない（置くのはユーザーの明示の操作のため）。`ikari-data` の自動の取得（ADR 0033 段階 3）でだけ効かせる。
- spec「辞書の更新」の「自動更新を無効にした場合でも、ユーザーが手動で新版を置いて同じ手順で更新できる」は、この ADR で実現する。「切り替える前に評価セットを実行」は、端末では試しの変換（数件）に替える（評価セットはアプリに入っていない。ADR 0033 §10 と同じ改め）。承認されたら spec を直す。
