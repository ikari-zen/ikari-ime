# ADR 0003: 話題スコアの方式と既定の Ranker 構成

- 状態: 承認（2026-10-11。§7.1〜§7.3 の決定を参照）
- 日付: 2026-10-11
- 対象: ADR 0002 §13.3 の比較実験の結論。ADR 0002 §22（統合担当の変更）の扱い。フェーズ2に持ち越す課題
- 根拠: `eval/reports/phase1-topic.md`（本 ADR のために実施した実験）、`phase1-quality.md`、`phase1-gates.md`、`phase1-ajimee.md`

## 0. 実験で分かったこと（要点）

| 項目 | 結果（ext test 181件 / AJIMEE 200件） |
| --- | --- |
| Topic（chiVe）の効果 | ext 30.9% → 58.6%（R2 → R3、p=3e-12）。AJIMEE は +1.5 ポイントで小さい。遅延の増加はほぼ 0（warm p99 0.08ms） |
| zenz の効果（Topic に追加） | ext: xsmall 71.3%、small 76.2%。**small は R3 より悪くなったケースが 0 件**。AJIMEE（待ち 300ms）: xsmall 45.0%、small 51.0% |
| Topic と LM の関係 | 補い合う。Topic なしの LM（R5、65.7%）は Topic ありの LM（R6、76.2%）より明らかに低い（p=4e-6） |
| small と xsmall | ext は 76.2% 対 71.3%（p=0.078、境界的）。dev は 78.7% 対 72.2%、AJIMEE は 51.0% 対 45.0%（p=5e-4）。**一貫して small が上** |
| 短い読みの遅延（ext、読み込み直後を除く） | xsmall: p50 7.0ms、p99 約 11ms（**NFR-02 の 16ms に収まる**）。small: p50 17.0ms、p99 約 21ms（**16ms は超えるが、NFR-04 の 30ms には収まる**） |
| 長い読みの遅延（AJIMEE） | 読みの長さにほぼ比例する。読みが41文字以上だと、small の中央値は 155ms、xsmall は 54ms。**30ms の同期待ちでは、どちらも長文に間に合わない** |
| 読み込み直後 | LM ありの構成では、先頭の2〜3件の変換が 35〜41ms（上限を長くすると最大 92ms）かかり、**上限の 30ms を超えたうえ、LM の結果も使われなかった** |
| 文法の回帰 | **Topic の既定値の変更後、test の `ext-neg-10`（サーバーを再起動 + しよう）で「使用」が1位になった**。LM ありでは正しい。dev では見えなかった |

| メモリ（最大 RSS） | LM なし 約 80MiB、xsmall 約 215MiB、small 約 360MiB（AJIMEE では 約 450MiB） |

## 1. 決定の要約

| 項目 | 決定 |
| --- | --- |
| Topic（chiVe） | **常に使う**。LM が使えないときの代わり（NFR-15）でもある。ただし **GrammarGuard（§3.2）を入れることを条件にする** |
| zenz | **常に使う。モデルは読みの長さで選ぶ**。読みが10文字以下なら small、11文字以上なら xsmall。長い読みでは、xsmall の1位と2位の差が 1000 未満で、時間が残っているときだけ small も使う |
| 待ち時間 | **変換1回あたりの締め切り**（30ms）にする。今は `rank()` の呼び出しごとの待ちで、これはフェーズ2で直す |
| 「迷ったときだけ LM」（LM なしの margin で呼ぶかを決める） | 既定にはしない。省電力モードの候補として残す |
| §22 の LeftContextRanker | 追認する |
| §22 の Topic の既定値 | **条件付きで追認する**（GrammarGuard を必須にする） |
| §22 の述語の追加 | 追認する。ADR 0002 の「述語は8個」を、追加の手続きに改める |
| EOS 連接の重みを下げる案 | **保留**。フェーズ2の最初の実験にする |
| 話題 kind の目標値 | 回帰の下限は ext test で LM あり ≥ 72%、LM なし ≥ 54%。否定と文法は全構成で 100%。目標はフェーズ3で 80% |

## 2. 既定の Ranker 構成

### 2.1 並び（フェーズ2の常駐エンジンの既定）
```
LeftContext → DocumentCache → Learning → Profile → Topic → GrammarGuard（新設） → Zenz
```
- **Topic を常に使う理由**:
  - 遅延がほぼ 0 で、ext の1位正解率を 28 ポイント上げる。
  - LM と補い合う（R6 は R3 より悪くなったケースが 0 件）。
  - LM が読み込み中、時間切れ、GPU が混んでいるときの順位（NFR-15 の「n-gram の結果」に当たる）として使う。
- **Zenz を最後に置く理由**: LM は文脈の文を見ており、文法も分かる（ext-neg-10 を LM が正しく直した）。GrammarGuard の制限の対象外にし、最終的な順位を決めさせる。
  - 追記（2026-10-16。[ADR 0024](0024-lm-keeps-rule-s.md)）: 「Guard で制限しない」は、規則 S（[ADR 0016](0016-rare-homophones.md)）が守った1位を LM が覆す1点だけ改めた。LM の後の最後の段が、その1位を戻す。ほかの LM の変更は制限しない。
- **学習を LM より前に置く**: 学習の加点は、ユーザーが明示的に選んだもの。LM がこれを覆さないことを確かめるシナリオテストを、フェーズ2の課題にする（§6-11）。

### 2.2 zenz のモデルの選び方（NFR-04、NFR-10 との整合）

| 読みの長さ | 使うモデル | 根拠（実測） |
| --- | --- | --- |
| 10文字以下（FR-04 のこまめな確定の大半。ext は全件がここ） | **small** | ext で xsmall より +4.9 ポイント（dev では +6.5）。p99 約 21ms で NFR-04 の 30ms に収まる |
| 11文字以上 | **xsmall**。その1位と2位の差が 1000 未満で、締め切りまで時間が残っているときだけ small も使う | AJIMEE で、small を 26.5% に絞って 49.0%（small 単独は 51.0%、xsmall 単独は 45.0%） |

- **NFR-02（16ms）との関係**:
  - small は p50 が 17ms なので、スペースを押してから計算すると 16ms を超える。
  - NFR-04 は「先行計算が間に合わない時は 30ms まで LM を待つ」と定めているので、この超過は要件の範囲内。
  - フェーズ2で入力中の先行計算（NFR-03）を入れれば、1文字打つ間隔（100ms 以上）で small の計算は終わるので、通常は 16ms 以内に表示できる見込み。
  - **フェーズ2の計測で先行計算が成り立たないと分かったら、短い読みも xsmall にする**（xsmall は p99 11ms で、同期でも 16ms に収まる。−5 ポイント前後の差を受け入れる）。
- **NFR-10 との関係**:
  - NFR-10 は「常用は 0.5〜1B 級まで、3B 級は迷ったときだけ」と定めている。zenz の small（91M）と xsmall（26M）は常用の上限よりはるかに小さいので、どちらを常用しても NFR-10 の範囲内。
  - 「迷ったときだけ大きいモデル」の考え方は、長い読みの xsmall → small に当てはめる。短い読みでは、small を直接呼ぶ方が速く、正解率も高い（phase1-topic.md §4.5）。
- **「LM なしで迷ったときだけ LM」を既定にしない理由**:
  - 短い読みで省ける呼び出しは 30% 程度で、−0.5 ポイント。
  - 長い読みでは誤りを検出できない（46.0% 対 51.0%）。
  - 省電力（NFR-13 の考え方）の選択肢として、設定で切り替えられるようにするかは、フェーズ3で決める。
- **長い読みについて**: 30ms の同期待ちでは間に合わない（AJIMEE の 28〜89% が 30ms を超える）。**長い入力の LM は先行計算が前提**で、間に合わなければ Topic の結果を出す（FR-04: 長文を壊さない）。

### 2.3 待ち時間の扱いを直す（フェーズ2で必須）
- 今は `ZenzRanker::rank()` の呼び出しごとに 30ms 待つ。Converter は1つの変換で rank を複数回呼びうる（最初のプールと追加の塊）。
- さらに、モデルの読み込み中には、上限の 30ms を超えて 35〜41ms かかった（最大 92ms）。
- **締め切りは変換1回あたりにし**、Converter が `convert()` の開始時刻から残り時間を Ranker に渡す。

## 3. ADR 0002 §22 の各変更の扱い

### 3.1 LeftContextRanker: **追認する**
- 根拠:
  - test で否定ケースが R1 の 1/3 から R2 の 3/3 になった。文法ケースは LM ありの全構成で 5/5。
  - dev での範囲の絞り込みの記録（phase1-quality.md §2.1）が、副作用（希少な名詞、拘束形の分割）を確かめている。
- 位置付け: Sudachi の単語コストが解析用で、変換で比べるには尺度が合わないことへの**対症療法**。辞書のコストを変換用に推定し直す（取り込んだ文章や LM の蒸留から）ことができたら、外せるかどうかを見直す。適用範囲（名詞で始まらない、1語、1000 を超えた分）は変えない。

### 3.2 Topic の既定値（`min_content` 1、`weight` 10000、`max_total` 5000）: **条件付きで追認する**
- 精度への効果は大きく、test で確かめられた（+27.7 ポイント、p=3e-12）。評価セットの文脈が1〜2語であることは、こまめに確定する実際の入力（spec の想定）とも合う。ADR 0002 §13.1 の「内容語3個未満なら加点しない」を撤回する。
- ただし **test の ext-neg-10 で、話題の加点が文法を覆した**。spec の「文法で決まる箇所は上書きしない」に反する。LM ありなら正しくなるが、LM が使えないとき（読み込み中、時間切れ、GPU が混んでいる）に同じ誤りが出る。
- **条件: GrammarGuard を入れる**（フェーズ2の最初の作業。フェーズ2の殻で LM なしの経路を使う前に必須）。
  - 「文法候補」を、LeftContextRanker が負の差分（加点）を付けた候補とする。
  - それ以外の候補が、**内容語に基づく加点（DocumentCache、Profile、Topic の合計）によって**最良の文法候補を追い越すことを禁じる。違反したら、その候補の score を「最良の文法候補の score + 1」まで戻す。
  - 内容語の加点の前から既に上にいた候補は、そのままにする。
  - 学習と LM の差分は制限しない（学習は利用者の明示的な選択、LM は文法を見ている）。
  - 受け入れ条件: ext-neg-10 が R3 で1位になる。dev と test の否定・文法ケースが 100%。話題 kind の低下が 0.5 ポイント以内。
  - これは ADR 0002 §9.2-5 で保留した「強い規則」を、プロファイルだけでなく Topic と DocumentCache にも広げたもの。

### 3.3 述語の追加（wave_dash、variant_surface、lemma_rank）: **追認する**
- それぞれ、実辞書の誤り（`なった〜`、`浜死`、頻度の低い lemma）を dev で確かめて足したもの。AJIMEE でも +8〜10 ポイントの効果があった（phase1-ajimee.md）。
- ADR 0002 §4.1 と §20 の「述語は8つで足りる」は、**「述語はコードで追加する。追加するときは、dev 分割での比較の記録と、BuildReport の該当件数を残す」という手続き**に改める。汎用の規則言語を作らない方針は変えない。
- `rare_lemma` は `lemma_rank` に含まれるので、フェーズ2の整理で削除する（使われていない述語を残さない）。

### 3.4 EOS 連接の重みを下げる案: **保留（フェーズ2の最初の実験にする）**
- 仮説: こまめに確定する使い方では、変換の単位の終わりは文の終わりではないので、EOS への連接（例: サ変名詞 → EOS が -1334）が誤った手がかりになっている。`使用` 対 `しよう` の分析（phase1-quality.md §1.1）と合う。
- 保留する理由:
  1. 今は調整の手段がない。N-best の探索の順位に効くので、Ranker ではなく lattice と nbest の変更になる。
  2. EOS 連接は「ここで語が終わってよいか」（連用形などの中途の形を下げる）という正しい情報も持っており、下げると中途の形が上がる恐れがある。
  3. 根拠がまだ1件の型だけ。
- 実験の設計:
  - `eos_weight` ∈ {1.0, 0.5, 0.25, 0} を探索側に入れる。
  - dev で話題 kind が +1 ポイント以上、否定・文法が 100%、AJIMEE が下がらないときだけ採用する。
  - LeftContextRanker と効果が重なるかどうかも見る（EOS で直るなら、LeftContext の倍率を下げられる可能性がある）。

## 4. 話題 kind の目標値

| 区分 | 回帰の下限（フェーズ2以降に eval で確かめる） | 根拠 |
| --- | --- | --- |
| ext test、話題 kind、既定の構成（Topic + zenz、§2.2） | **≥ 72%** | 実測 75.1%（small）から −3 ポイント |
| ext test、話題 kind、LM なしの経路（Topic + GrammarGuard） | **≥ 54%** | 実測 57.2% から −3 ポイント |
| 否定・文法ケース（全構成、dev と test） | **100%** | spec の制約。GrammarGuard の受け入れ条件 |
| AJIMEE、既定の構成（先行計算が間に合った場合 = 待ち時間を十分にとった計測） | **≥ 45%** | 長さで切り替える方針の合成値 46〜49% |
| AJIMEE、LM なし | **≥ 19%** | 実測 21.0% |
| `homophones.tsv` | 12/14 以上、フェーズ1の結果からの回帰 0 | phase1-gates.md |

- **目標（フェーズ3）**: ext test の話題 kind 80%。手段は、取り込み（初期学習）と学習、h-08 で効かなかったプロファイルを zenz v3 の条件（ プロファイル、 話題）で渡すこと。
- **注意（数値の信頼性）**:
  - test の否定は3件、文法は5件しかなく、100% の判定には弱い。**フェーズ2の初めに、否定・文法の test を各30件以上に増やす**。
  - ext は LLM（Claude）が作った文脈で、ユーザーによる1割の抜き取り確認（ADR 0002 §21.1-5）が済むまでは、数値を暫定とする。LLM が作った文は LM に有利な偏りを持ちうるので、取り込んだ自分の文章の評価用2割でも確かめる。
  - dev と test の差は、Topic だけの構成で 6 ポイント、LM ありでは 1〜2.5 ポイント。差が大きいのは、dev で重みを調整した Topic の方。調整は dev だけで行う運用を続ける。

## 5. 却下した案

| 案 | 却下した理由 |
| --- | --- |
| xsmall だけを使う | 短い読みで small より 5〜6.5 ポイント低い。small も NFR-04 の範囲で動く |
| 読みの長さに関係なく small | 長い読みでは 30ms を大きく超え（41文字以上で中央値 155ms）、xsmall を前段にした方が効率的 |
| 短い読みで xsmall → small の順に呼ぶ | 直列に呼ぶと small 単独より遅く（約 24ms 対 17ms）、正解率も small 単独を超えない |
| 待ち時間の上限を延ばす（50 / 100 / 300ms） | 短い読みでは正解率が変わらない（時間切れが読み込み直後だけのため）。長い読みは、待つのではなく先行計算で解く |
| Topic なしで LM だけを使う | Topic と補い合う効果を失う（65.7% 対 76.2%）。LM が使えないときの代わりもなくなる |
| Topic の既定値を ADR 0002 §13.1 に戻す | 精度を 28 ポイント失う。問題は「文法を覆すこと」で、GrammarGuard で直接解く |

## 6. フェーズ2（macOS の殻、常駐エンジン、IPC）に持ち越す課題

1. **GrammarGuard**（§3.2）。Topic の既定値を追認するための条件。
2. **変換1回あたりの締め切り**（§2.3）。今は `rank()` の呼び出しごとの待ちで、1つの変換で複数回呼ばれうる。
3. **入力中の先行計算（NFR-03）**。キーは (読み, 文脈の末尾)。表示した後に LM の結果が届いても、第一候補は差し替えない（NFR-05）。遅れて届いた結果は表示前にだけ使う。長い読みの LM は、これが前提になる。
4. **モデルの事前読み込みと暖機**。エンジンの起動時と、アイドル解放（NFR-11）から読み直したときに、ダミーの推論で Metal を初期化する。今は最初の2〜3回の変換が 30ms を超え、LM も効かない。
5. **長さによるモデルの選択と xsmall → small**（§2.2）。今の `ZenzRanker` は1つのモデルしか持たない。
6. **EOS 連接の重みの実験**（§3.4）。
7. **変換の質の残り**:
   - 数字の書式の正規化（期待 `３年` に対して出力 `三年`。AJIMEE）
   - lemma もカタカナの低コストな語（`ココ`）の述語
   - 助詞で始まる分割（`は借る`、`今日そう`）
   - 頻度の高い同音語への偏り（使用 / 仕様、時期 / 次期）
8. **時間切れ率まわりの不足**（コードは変えていない）:
   - 6125e72 には、同じ要求が処理中のときに重ねて送らない経路で、率が 1.0 になることを確かめるテストがある（`timeout_leaves_scores_untouched_and_late_result_is_reused`）。
   - 不足しているのは、(a) ワーカーに送れなかった経路（`!sent`）、(b) 処理中の要求に多数の呼び出しが重なる場合に、率が 1.0 を超えないことのテスト。
   - eval のレポートの「要求」の欄は、今は `rank()` の呼び出し数を表しているので、「呼び出し」に名前を改める。
9. **GPU の競合と電源（NFR-12、NFR-13）**: 他のアプリが GPU を使っているときの遅延と時間切れ率を測る。バッテリー駆動のときに「迷ったときだけ LM」へ切り替えるかを決める。
10. **メモリの配分（NFR-09）**: 実測は LM なしで約 80MiB、small で約 360MiB、両方のモデルを持つと約 500MiB と推定される。殻とエンジンの予算の分け方を決める。
11. **学習と LM の関係**: LM が、学習で上げた候補を覆さないこと。a-02 のシナリオを LM ありで流すテストを足す。
12. **評価セット**: 否定・文法の test を各30件以上にする。ユーザーの1割の確認を済ませる。取り込んだ文章の評価用2割での確認を、定期の評価に組み込む。
13. **ビルドと配布**: llama.cpp（MIT）をエンジン（XPC サービス）に静的リンクする。cmake と Metal のビルド手順を整え、THIRD_PARTY_NOTICES に llama.cpp を足す。zenz は CC BY-SA 4.0 として表記する（ADR 0002 §21.1-1）。
14. **プロファイルの効果**（h-08 は3位のまま）: プロファイルを zenz v3 の条件（）で渡して効果を測る。
15. **IPC と状態の持ち方**: `Conversion` と LM のワーカーをエンジン側に持ち、secure の入力欄では LM を呼ばない（実装済み）ことを、IPC 越しでも保つ。

## 7. ユーザーの判断が必要な点

1. **短い読みに small を常用すること**（§2.2）。先行計算がないと 16ms を超える（NFR-04 の範囲内）。メモリは約 360MiB（両方のモデルで約 500MiB）。代わりに xsmall だけにすると、正解率が約5ポイント下がる代わりに、同期でも 16ms に収まる。
2. **Topic の既定値を、GrammarGuard を条件に追認すること**（§3.2）。それまでの間、LM なしの経路では「話題が文法を覆す」誤りが起こりうる。
3. **話題 kind の回帰の下限と、フェーズ3の目標値**（§4）。
4. **ext の1割の抜き取り確認**（ADR 0002 §21.1-5）。済むまでは、この ADR の数値を暫定とする。
5. **バッテリー駆動のときの LM の使い方**（常に使うか、迷ったときだけにするか）。フェーズ3で決める案でよいか。

### 7.2 長文の扱い（2026-10-11、ユーザー）
- このIMEのコンセプト（こまめに確定する。FR-04）に合わせ、**長文の一括変換を速く正確にすることは目標にしない**。
- 長文でも変換はできる（FR-04 の「壊さない」は守る）。そのうえで、**長文では少し待ってもよい**。LM の待ち時間（30ms）は短い読みにだけ当てはめ、長い読みでは読みの長さに応じて延ばす。
  - 初期値の案: 待ち時間 = max(30ms, 読み1文字あたり 6ms)、上限 300ms。AJIMEE では small を 300ms 待つと 51.0% になる（30ms では 22.0%）。具体的な値は、フェーズ2で実際に使って調整する。
- zenz-v2.5 medium など古いモデルは追わない。

### 7.3 基本原則との照合（2026-10-12、ユーザー）
spec に「基本原則」（ユーザーの入力を正とする、学習は支援であって決定ではない）を追加したのに合わせて、次のことを決めた。
- **LM の生成で作った表記を候補に足す案（phase1-lm-compare §4、§6.2）は採らない。** 生成した表記は読みと一致する保証がなく、「入力を正とする」（FR-06）に反しうるため。また、こまめに確定する使い方では得が約3ポイントしかない。候補は辞書から作り、LM は並べ替えにだけ使う。
- 辞書のエントリを完全に除外する処理（`ascii_lower`、`numeric_surface`）は、大きなペナルティに改め、候補には残す（フェーズ2のレーンQ）。
- 「その場の文脈と食い違うときは、学習が文脈の判断を覆さない」を規則にし、テストで保証する（フェーズ2のレーンQ）。
