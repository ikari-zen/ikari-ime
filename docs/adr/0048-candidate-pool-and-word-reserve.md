# ADR 0048: LM に渡す候補を増やし、合成の区間を辞書の 1 語で覆う候補を残す（行き値 → 閾値）

- 状態: 提案（2026-11-04。(a) と (c) の両方を採ることはユーザーが決定。値は掃引のあとで決める）
- 日付: 2026-11-04
- 対象: `core/src/nbest.rs`（ノードを必ず通る A* を 1 つ足す）、`core/src/converter/conversion.rs`（最初のプールの作り方）、`core/src/converter/options.rs`（設定 2 項目と `--ranker-config` の入口）、`stack/src/assemble.rs`（設定の適用と、LM の採点上限の決め方）、`eval/sets/`（#185 の例のセット）。`lm/` のコード、辞書、連接の補正、Swift は変えない
- 前提: main = 738777a。ADR 0001 §4.6（N-best とプール）、ADR 0002 §13.2（LM の加算）、ADR 0021 §1.1・§2.5（採点の対象と時間）
- タスク: #185（文脈ありの長い読みで「閾値以上なら…」が「行き値以上なら…」に負ける）
- 判断の置き場所: Rust の core（変換のプールの作り方）と stack（設定の組み立て）。OS の API も UI も関わらない

---

## 0. 現状の把握
- 最初の変換は、A* から表記の重複を除いて `pool_size`（30）件を取り、Rewriter・ひらがな・カタカナ・英字の置き換えを足して、まとめて rank する（`build_first_pool`）。続きのページは `chunk_size`（9）件ずつ別に rank する。A* の展開は 1 回の生成あたり `max_astar_pops`（20000）まで。文節のモードも、文節ごとに同じ `build_first_pool` を通る。
- `pool_size` を外から変える入口はない（エンジンも CLI も `ConvertOptions::default()`）。
- LM（zenz）は、渡された並びの先頭から Rewriter を除いて `zenz.max_candidates`（32）件を採点する。採点されない候補には、採点した中で最悪の加算が付く（`lm/src/ranker.rs` の `apply`）。並びは CompositeRanker の中で並べ替えないので、プールの順（A* の順 → Rewriter → かな → 英字）がそのまま採点の優先順になる。今は辞書 30 + かな 2 = 32 でちょうど収まる。
- ひらがな・カタカナの候補のコストは「辞書の候補の最大のコスト + 1」（プールの大きさに依存する）。

## 1. 問題の定義
左文脈があると、解析器が BOS の連接を変え（文脈の末尾「して」→ 行き（動詞連用形））、A* の上位が 行き + 値（接尾辞）の合成の経路で埋まる。正解の「閾値以上なら…」は 13 位から 40 位以降に落ちてプールに入らず、LM は採点できない。LM に直接採点させると、文脈の長さによらず正解が 1 位（NLL の差 1.2〜2.5）。

つまり、**LM は正しく、LM の手前の打ち切りが正解を捨てている**。方針（候補は辞書から作り LM は並べ替えるだけ、LM で直るものは辞書・接続の補正で直さない）から、直すのは打ち切りの側である。`zenz.max_candidates` だけを上げても、プールが 30 件なので効かない（#185 で 200 にしても変わらなかったのはこのため）。

## 2. 決定の要約（提案）
1. **(a) プールを広げる**: `pool_size` を `--ranker-config` の `convert.pool_size` で変えられるようにし、既定は掃引で決める（§6）。
2. **LM の採点上限はプール全体に合わせる**: `zenz.max_candidates` を明示しないときは、stack が `pool_size + word_reserve + 2`（かな 2 件）にする。明示したときはその値（掃引と切り戻し用）。
3. **(c) 合成の区間を辞書の 1 語で覆う候補を残す（語の予約枠）**: A* のプールの候補で、2 つ以上の辞書の語の合成で覆われた区間を、辞書の 1 語のノードが同じ区間でちょうど覆えるなら、その 1 語を必ず通る最良の経路を、A* の順位に関わらずプールに足す。上限は `convert.word_reserve` 件（0 で無効）。定義は §3。
4. ひらがな・カタカナのコストの基準は、今と同じ「A* の先頭 30 件の最大」に固定する（`pool_size` を変えても、LM なしでかなの位置が動かないように）。
5. 予約枠の候補は辞書の経路（`CandidateOrigin::Dictionary`）で、コストは経路のコストのまま。**加点はしない**。LM なしの並びは、予約枠の候補が下の方に増えるだけで、上位は変わらない。
6. (b)（解析器の連接の補正で合成の経路を弱める）は採らない（§5）。

## 3. 語の予約枠（(c)）の定義
「辞書の 1 語（合成でない）」は、文全体ではなく**区間ごと**に判定する（長い読みでは、どの候補も複数の語でできているため）。

1. **合成の区間**: A* から取ったプールの候補を上から見て、連続する 2 つ以上のセグメント `[a, b)` で、どれも辞書の語（`word` が Some）で、**品詞1 が 助詞・助動詞 でない**もの（`pos.rs` の `pos1`）。語を作る部品（名詞、動詞の連用形、接尾辞、接頭辞など）の組み合わせだけを「合成」とみなす。名詞 + 助詞（きょう + は）は対象にしない。
2. **覆う 1 語**: ラティスで `start == a && end == b` の辞書のノード（未知語は除く）。複数あればノードのコストが最小の 1 つ。
3. **既にあるものは足さない**: プールのどれかの候補が、同じ区間に同じ語（同じ `WordId`）の 1 セグメントを持っていれば、その区間は飛ばす（LM が既に採点できる）。
4. **経路**: そのノードを必ず通る最良の経路を `NBest::through`（§7）で 1 本取る。表記が既に出ていれば捨てる（`seen`）。
5. 上から順に見て、`word_reserve` 件に達したら止める。合成の区間の数え方は、短い区間を先に（同じ候補の中で、セグメント 2 つの区間 → 3 つ → …）。
6. #185 の例では、合成の区間は 行き + 値（いきち）、覆う 1 語は 閾値。

A* の展開との関係: `NBest::through` は、ノードの区間と重なるほかのノードへ進む状態を積まないだけの A* で、ヒューリスティック（前向きの `best`）は下界のまま使えるので正しい。区間の後ろ側では `best` が正確でなくなるぶん、展開は増える。予約枠の探索は全体で 1 つの予算 `max_astar_pops` を分け合い（主の A* とは別の予算）、使い切ったら残りの区間はあきらめる。変換 1 回の A* の展開は、最大で今の約 2 倍。

## 4. ほかの候補との共存
| 候補 | 扱い |
|---|---|
| Rewriter | 今のとおり。アンカーの基準（辞書の候補のコストの昇順の n 番目）は A* の候補だけで作り、予約枠の候補は入れない（日付などの位置を動かさない） |
| ひらがな・カタカナ | コストの基準は A* の先頭 30 件の最大 + 1（§2-4）。カタカナ語らしい読みの補正（#271）も同じ基準 |
| 英字の置き換え（ADR 0020） | 予約枠を含むプール全体から作る（今と同じ規則） |
| プールの並び（= LM の採点の優先順） | A* の `pool_size` 件 → 予約枠 → Rewriter → ひらがな → カタカナ → 英字の置き換え。上限をプール全体に合わせる（§2-2）ので、英字の置き換え以外は採点される |
| 続きのページ（`extend_chunk`） | 変えない。予約枠で出した表記は `seen` に入るので、後の A* でも重ならない |
| 文節のモード | 文節ごとの `build_first_pool` で同じ規則がかかる（文節の EOS の連接は `NBest::through` でも同じ `end_left_id`） |

## 5. 検討した案
| 案 | 却下・保留の理由 |
|---|---|
| (a) だけ（プールを広げるだけ） | 押し下げの深さが文脈しだいで、何件にすれば足りるかに上限がない（#185 は 40 位以降）。LM の時間はプールに比例するので、深さを件数で追うと時間で詰まる |
| (c) だけ | 合成以外の理由（連接の補正、文脈の押し下げ全般）で落ちた正解は拾えない。ユーザーが両方を採ると決めた |
| (b) 解析器の連接の補正で、辞書にない合成の経路を弱める | 辞書・接続の補正で直す形で、「LM で直るものは直さない」に反する。補正は LM なしの並びも変え、ほかの正しい合成（接尾辞つきの語）を壊しうる |
| 予約枠の候補に加点する | LM なしの並びを変える。予約枠は「LM に見せる」ための仕組みで、選ぶのは LM（候補は辞書から、LM は並べ替え） |
| 予約枠を `pool_size` の内側に取る（A* の件数を減らす） | A* の下位に正解がある場合を捨てる。(a) と (c) の効きを分けて測れない |
| 1 語の判定を文全体でする | 長い読みでは文全体が 1 語の候補はなく、効かない |
| 合成の部品に助詞・助動詞も含める | 名詞 + 助詞 の区間ごとに 1 語の候補（今日は → 教派 など）が増え、LM の時間を食う。必要なら掃引で比べる（§6 の追加の条件） |
| 前向き・後ろ向きの Viterbi で「ノードを通る最良」を求める | 後ろ向きの最小コストと経路の復元を新しく持つ必要がある。`NBest` の制約版なら既存の探索と予算の仕組みをそのまま使える |
| `pool_size` を設定ファイル（`settings.tsv`）に出す | 利用者が決める値ではない（LM の時間と精度の兼ね合いは実装側が決める）。`--ranker-config` で評価と切り戻しができれば足りる |

## 6. LM の時間の見積もりと、計測で決める値
### 6.1 見積もり（推測。§6.3 で測る）
- ADR 0021 §2.5（読み 21 文字、窓 40）: 32 候補で p50 32.3ms・p95 52.9ms、16 候補で 21.1ms。差から、**候補 1 件あたり約 0.7ms**（21 文字の場合）、固定分（プロンプト）約 10ms。読みが長いほど 1 件あたりは重くなる。
- 締め切りは `max(30ms, 6ms × 文字数)`、上限 300ms。21 文字で 126ms、32 文字で 192ms。

| 採点件数 | 21 文字の p50 の見積もり | 締め切り（21 文字）に対して |
|---|---|---|
| 32（今） | 約 32ms | 余裕あり |
| 64 | 約 55ms | 余裕あり |
| 100 | 約 80ms | p95 が近づく |

- 危ないのは**短い読み**（締め切り 30ms。5 文字以下）で同音語が多いとき。採点件数が増えると時間切れ（LM なしの結果）が増えうる。打っている間の先行計算も同じだけ重くなる（GPU の負荷、電池）。
- A* の展開（LM なし）は、`pool_size` と予約枠の探索のぶん増える。上限は今の約 2 倍（§3）。

### 6.2 決める値（**未決。掃引してから決める**）
| 値 | 候補 | 今 |
|---|---|---|
| `convert.pool_size` | 30、45、60、90 | 30 |
| `convert.word_reserve` | 0、4、8 | （なし。0 と同じ） |
| `zenz.max_candidates` | 既定はプール全体（§2-2）。比較用に 32 固定も流す | 32 |

### 6.3 評価の流し方
1. 段階 1（予約枠だけ）: `pool_size=30` で `word_reserve` を 0、4、8。段階 2（プール）: 段階 1 で選んだ `word_reserve` で `pool_size` を 30、45、60、90。予約枠の効きとプールの効きを分けて見る。
2. 各条件を、(i) LM なし、(ii) LM あり締め切り 3000ms（時間切れ 0 を確かめる。精度の上限）、(iii) LM あり実機の締め切り（`lm_budget`。暖めてから）の 3 通りで流す。
3. セット: 全評価セット（`eval/scripts/snapshot.sh`）と AJIMEE、#185 の例のセット（新しく足す。§8 のレーン C）。学習なし（評価に実機の学習を含めない）。
4. 合否: 全セットと AJIMEE で 1 位の悪化を数える（基準は今の main）。#185 のセットが (ii) と (iii) で直る。(i) は 1 位が変わらないこと（変われば §2-4・§2-5 の前提が崩れている）。
5. 時間: 変換の時間（LM なし）の p50/p95、LM の採点の時間の p50/p95、時間切れの率を、読みの長さの帯（〜5 文字、6〜12、13〜20、21〜）ごとに出す。短い帯で時間切れが増える値は採らない。
6. 結果は `eval/reports/candidate-pool-sweep-<日付>.md` に置き、索引に足す。値は数字をユーザーに見せて決める。

## 7. 契約（シグネチャ）
```rust
// core/src/nbest.rs
impl NBest {
    /// `with_end` と同じ。ただし、出す経路はノード `through` を必ず通る
    /// （`through` の区間と重なるほかのノードへは進まない）。コストの昇順は保つ
    pub fn through(lattice: &Lattice, grammar: &dyn Grammar, end_left_id: u16, through: u32) -> Self;
}

// core/src/converter/options.rs
pub struct ConvertOptions {
    // …既存…
    /// 語の予約枠の上限（ADR 0048 §3）。0 = 無効
    pub word_reserve: usize,
}
impl ConvertOptions {
    /// `convert.pool_size`、`convert.word_reserve` で上書きする。この接頭辞で未知のキーや数でない値ならエラー
    pub fn with_pool_kv(self, kv: &BTreeMap<String, String>) -> Result<Self, RankerConfigError>;
    /// LM が採点すべき最初のプールの件数（`pool_size + word_reserve + 2`）。stack が `zenz.max_candidates` の既定に使う
    pub fn first_pool_capacity(&self) -> usize;
}

// core/src/converter/conversion.rs（crate 内）
/// §3 の規則で予約枠の候補を作る。`pool` は A* から取った候補だけ
fn reserve_word_candidates(&mut self, pool: &[Candidate]) -> Vec<Candidate>;
```
- `word_reserve` の既定は掃引までは 0（今と同じ動き）。`pool_size` の既定も 30 のまま。値は §6 のあとで別のコミットで変える。
- stack: `convert.` の接頭辞を `with_pool_kv` に渡す。`zenz.max_candidates` が kv に無ければ `first_pool_capacity()` を ZenzConfig に入れる。ほかの Ranker に渡す kv（`other_kv`）から `convert.` を除く。

## 9. リスク
- LM の時間: 採点件数に比例して増える。短い読みの時間切れと、打っている間の GPU の負荷（電池・発熱）。§6.3-5 の帯ごとの数字で判断する。
- 予約枠の候補は、まれな 1 語（同音の専門語）を LM に見せる。LM が誤って選べば、今は出ない誤変換が 1 位になりうる。予約枠は加点しないので、LM なしでは起きない。
- LM なしの並びで、予約枠の候補は A* の 31 位以降の候補より前に出ることがある（同じ rank の塊に入るため）。コストの単調さが少し崩れるが、今のかなの候補と同じ種類のずれ。
- `NBest::through` は区間の後ろ側でヒューリスティックが緩く、長い読みで展開が増える。予算で打ち切るので遅延の上限は保つが、打ち切られると予約枠が出ない。
- 合成の区間の定義（助詞・助動詞を除く）は #185 の 1 例から作った。ほかの型の押し下げ（合成でないもの）は (a) に頼る。

## 10. ユーザーに聞くこと
1. (c) の「辞書の 1 語（合成でない）」を、**区間ごと**に「上位の候補が 2 語以上の合成（助詞・助動詞を含まない）で覆う区間を、辞書の 1 語で覆える」と解釈してよいか（推奨: この解釈。文全体で 1 語を求めると長い読みで効かない）。
2. 掃引の合否で、1 位の悪化を 0 件に限るか、ADR 0047 のように悪化と改善の件数を並べて判断するか（推奨: 並べて判断。プールを広げると LM の判断が増え、悪化 0 の値は無い見込み）。
3. 値（`pool_size`、`word_reserve`）は §6 の掃引のあとで数字を見せて決める。今は決めない。
