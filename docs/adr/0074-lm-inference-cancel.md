# ADR 0074: 古くなった LM の推論を止める（先行計算の取り消し）

- 状態: 承認（2026-11-16。§10 の Q1〜Q3 はすべて推奨どおり）
- 日付: 2026-11-16
- 対象: `engine`（`PrefetchQueue`、先行計算のスレッドの `run_job`、自己診断）、`lm`（`LmScorer`、`ZenzRanker` のワーカー、`llama.rs` の `nll`、`host/` の取り決めと親子の両側）、ADR 0068 の LM の子の口の許可リスト。この ADR ではコードを変えない
- 前提: `feat/security-impl` = f417f41。ADR 0021（先行計算、Space から待つ）、ADR 0060 Q4（推論は別プロセス `ikari-lm-host`）、ADR 0061（`LmTrace`、開発者の表示）、ADR 0065（自己診断、再生の評価 §3.4、§6.3 の「#429 で中断が入ったら X を測り直す」）、ADR 0068（口ごとの許可リスト、S5）、ADR 0072（檻の段、製品のエンジンに llama.cpp を入れない §5）
- タスク: #429。再現テストはブランチ `lane/s429` の `#[ignore]` 付きの 2 つ（`lm/src/ranker/tests.rs` の `a_running_stale_inference_does_not_delay_the_newest_request`、`engine/src/tests/lm_host.rs` の `a_running_stale_inference_does_not_delay_the_newest_reading`）
- 判断の置き場所: Rust。「もう要らない」と決めるのは `engine`（どの読みが最新かを知っているのはエンジンだけ）。`lm` は印を見て止めるだけで、何を止めるかを決めない。Swift と Windows の殻に足すものはない

---

## 1. 現状（分かったこと。コードと `lane/s429` の再現テスト）

止まる場所が 3 つあり、どれも「走り出したら最後まで」になっている。

1. **同じプロセスの経路**: LM のワーカーは 1 本。`s.nll()`（`lm/src/ranker.rs:578`）が終わるまで戻らない。溜まった要求から最新を選ぶ処理（541-547）は、次の `nll` の前にしか働かない。`lm/src/llama.rs` の `nll` は、プロンプトの decode と、候補のバッチの decode（候補が多ければ複数回）をするだけで、途中で止める確認がない。`llama-cpp-2` 0.1.161 は abort callback を包んでいない（`llama-cpp-sys-2` には `llama_set_abort_callback` がある）。
2. **別プロセスの経路**: `HostScorer::nll` は子の返事を同じスレッドで待つ（`recv_timeout`、上限 30 秒）。取り決め（`lm/src/host/proto.rs`、版 1）の親 → 子は `Score` だけで、中止を伝えられない。子の `serve` は要求を 1 つずつ処理する。ただし子は**入力を別スレッドで読んでいる**（`serve.rs` の `READER_THREAD_NAME`）ので、推論の最中にも次の枠は受け取れる。
3. **先行計算のスレッド**: 1 本（`engine/src/workers.rs` の `prefetch_loop` → `run_job`）。`PrefetchQueue::submit` が置き換えるのは**待っている**依頼だけで、走っている依頼には触れない。走っている `run_job` は、`rank` が返事か締め切り（`lm_budget.max`）を待つ間、止まる。さらに `convert_until` → `page_until` → `prefill` と、`rank` を何度か呼ぶ。
4. Space の時点で最新の読みの先行計算が計算中なら、`convert_wait` まで待つ。間に合わなければ LM なしで変換する（`engine/src/convert.rs:360-380`）。入力は止まらない。

- 実測（`lane/s429`、推論 300ms の設定）: 最後の読みの Prefetch から Convert の返事まで約 570〜590ms（推論約 2 回分）。古い推論の残りを待っている。
- llama.cpp（`llama-cpp-sys-2` 0.1.161 の同梱の版）の abort callback を実装している装置は、CPU と Metal（コマンドバッファの間で見る）。**Vulkan の実装には abort callback が見当たらない**（`ggml/src` を `abort_callback` で探した結果。実機では未確認）。

## 2. 問題

- 推論が打鍵の間隔より長い機械（Windows の Vulkan、CPU。ADR 0059、0065）では、最後の読みの推論が、もう要らない読みの推論の残りを待つ。最悪で推論の約 2 回分。これは ADR 0065 の LM が付く率をそのまま下げる。
- 止めるには、(1) 止める合図を誰が出すか、(2) 合図を LM の推論まで（別プロセスなら子まで）どう運ぶか、(3) 推論のどこで止めるか、(4) 古い先行計算のジョブ自体をどう終わらせるか、を決める必要がある。(4) を決めないと、LM を止めても、古いジョブが次の `rank` で LM に要求を出し直す。

## 3. 決定 1（Q1）: 中止は「要求ごとの取り消しの印」で伝える

- `lm` に取り消しの印 `CancelToken` を置く（共有のフラグ。立てるのは 1 回だけ。`cancel()` と `is_cancelled()`）。**印は先行計算のジョブ 1 つに 1 つ**作り、そのジョブが出す LM の要求すべてが同じ印を持つ。
- `LmScorer::nll` に印を渡す（引数を足す。既定の実装で印を無視する別のメソッドは作らない。実装は `llama`、`host`、テストの偽物だけなので、全部が印を意識する形にする）。
- 止まったときは新しい誤り `LmError::Cancelled` を返す。**取り消しは失敗として数えない**（推論の失敗の数、`HostHealth` の連続失敗、子を捨てる判定のどれにも入れない。入れると、打っているだけで子を諦めてしまう）。数は別に `cancelled` として数え、`LmTrace` と開発者の表示（ADR 0061）に足す。ログは固定の語と数だけ（`lm_cancel=`）。
- エンジンから `rank` へは、**スレッドに結びつけた範囲**で渡す。`run_job` が始めに `lm::cancel::scope(token)` を開き、`ZenzRanker::rank` がそれを読んで要求に付ける。今の `lm_trace`（`lm/src/trace.rs` の thread_local。`run_job` が `lm_trace::begin()` してから使う）と同じ形にする。`rank` は呼んだスレッドで返事を待つので、この形で取り違えは起きない。
- ワーカーの動き: 取り出した要求の印がもう立っていれば、推論せずに捨てる。推論が `Cancelled` で戻ったら、返事の送り口を落とす（待っている `rank` は `Disconnected` ですぐ戻る）。`late`（遅れて届いた結果の取り置き）には入れない。

### 3.1 別プロセスの経路: 取り決めに `Cancel { id }` を足し、版を 2 にする

- 親 → 子に `Cancel { id }`（新しい札。中身は u64 だけ）。意味は「`id` とそれより古い要求は要らない」。子 → 親の `Failed` の種類に `Cancelled` を足す。
- **返事は要求 1 つに 1 枚のまま**（今の取り決めの約束を崩さない）。取り消された要求にも、子は `Scores` か `Failed{Cancelled}` を 1 枚返す。
- 子: 読み取りのスレッドが `Cancel` を受けたら、共有の「ここまで取り消し済み」の番号を上げる（枠を本体に回さない）。本体は、要求を取り出したときと、推論の止めどころ（§4）で番号を見る。
- 親（`HostScorer::nll`）: 待っている間に印が立ったら、`Cancel { id }` を書き込み用のスレッドに渡し、**子の返事を待たずに** `Cancelled` で戻る。そのため、印に「立ったときに呼ぶもの」を 1 つ登録できるようにし、`HostScorer` は待ちの間だけ「`Cancel` を送る、自分の受け口を起こす」を登録する。一定の間隔で印を見に行く作りにはしない（新しい値を持ち込まないため）。
- 親は、取り消した id を覚えておき、次の要求の返事を待つ間にその id の返事が来たら読み捨てる。覚えていない id の返事は今どおり「壊れた子」として扱う。
- **版を 2 に上げる影響**:
  - 互換: 子はエンジンの隣に置き、一緒に入れ替える前提（`proto.rs` の冒頭）。版が違えば親は子を使わず LM なしで動く（今の作り）。版 1 の子に `Cancel` が送られることはない。混ざるのは壊れた配置だけで、その時も入力は止まらない。
  - 子の読み取りスレッド: もう別スレッドで読んでいるので、増えるのは番号の更新だけ。本体の 1 つずつの処理は変えない。
  - セキュリティ（ADR 0068、0072）: LM の子の口の許可リストに `Cancel` を 1 つ足す（運ぶのは番号だけ。子から出るものは数値と固定の語のまま）。渡すハンドル（S5）、檻の段、子の権限は変わらない。ADR 0068 の表は実装の PR で直す。

## 4. 決定 2（Q2）: まず decode の間で止める。decode の最中に止める（abort callback）は、実測の結果を見て後で決める

- **段階 1（この ADR で決める）**: 印を見る場所は、(a) ワーカーが要求を取り出したとき、(b) プロンプトの decode の前、(c) プロンプトの decode のあと（候補の前）、(d) 候補のバッチの decode の間。どれも安全な Rust だけで書け、どの装置（CPU、Metal、Vulkan）でも同じに効く。
  - 効き目の見込み（推測）: 止まるのは「今の decode の残り」まで。decode が 2 回なら、古い推論の残りを待つ時間は平均で約半分になる。正確な割合は §8 のスパイクで測る。
  - 加えて、古いジョブの `rank` はすぐ戻る（§6）。新しいジョブは、LM が今の decode を終える間に、LM を使わない部分（辞書の引き、文節）を先に進められる。
- **段階 2（保留）**: `llama-cpp-sys-2` の `llama_set_abort_callback` を unsafe の FFI で呼び、decode の最中に止める。段階 1 の実測で、目標の機械で待ちが残りすぎると分かったときだけ、別の ADR の追記で決める。
  - 保留の理由: (1) Windows の既定は Vulkan（ADR 0059）で、Vulkan には abort callback の実装が見当たらない。最優先の Windows で効くのは CPU のときだけになる見込み。(2) 安全な包みが無いので、コールバックと、それが読むフラグの寿命をこちらで保証する unsafe が増える（`llama.rs:280` の `transmute` に続いて 2 つ目の寿命の約束）。(3) 段階 1 の効き目を測る前に複雑さを先払いしない。
  - 檻との関係（ADR 0072）: 製品では llama.cpp は子にしか入らない（§5）ので、unsafe の不具合で落ちるのは子で、エンジンは LM なしで動き続ける。檻の段も変わらない。重みは「子が落ちて LM が一時止まる」までで、セキュリティの境界は動かない。それでも、段階 2 を入れるときは、Metal と CPU で止めたあとの次の推論が正しい値を返すこと（KV の掃除）を確かめる。

## 5. 決定 3（Q3）: 中止を出すのはエンジン。`PrefetchQueue` が新しい依頼を受けたとき、走っているジョブの印を立てる

- `PrefetchQueue` が、`next` で渡した依頼（走っている依頼）の印を持つ。`finish` で外す。
- **`submit` で、走っている依頼の印を立てる。** ただし、走っている依頼と同じ `CacheKey`（同じセッション、同じ読み、同じ文脈）なら立てない（同じ結果を捨てないため）。
- セッションをまたいでも立てる（推奨。§10 の Q1）。理由: ワーカーは 1 本で、`next` はすでにセッションをまたいで最新の依頼から処理する。古いセッションの依頼を走らせ続けると、今打っているセッションが同じ待ちに遭う。
- `forget_session`（そのセッションのとき）、`clear`、`close` でも立てる。
- 自己診断（ADR 0065 §4.3）: 測る 1 回にも印を付け、Prefetch か Convert が来たら立てる。止めた 1 回は記録しない（測り直しの数に入れない）。ADR 0065 の「止める仕組みが入ったら、測る側から先に止める」の実装。
- Convert（Space）が自分で出す LM の要求には印を付けない（範囲を開かない）。利用者が待っているものは止めない。

## 6. 決定 4（Q4）: 先行計算のスレッドは 1 本のまま。古いジョブは印を見て自分で終わる

- `run_job` は、`convert_until`、`page_until`、`prefill` の間で印を見る。立っていれば、`entry.abandon()` して戻る（`set_ready` しない。`prefetch_done` のログには固定の語で取り消しを残す）。
- `ZenzRanker::rank` は、範囲の印が立っていれば要求を出さずに戻る（`declined` とは別に `cancelled` で数える。時間切れには数えない）。これで、古いジョブが次の `rank` で LM に要求を出し直すことはない。
- 捨てた `entry` を誰かが待っていても（今の流れでは、Convert が待つのは最新の読みの `entry`）、今の「捨てられたもの」の道（LM なしでその場で変換）に入るだけで、入力は止まらない。

## 7. 方針との関係

- 入力を正とする / LM は並べ替えだけ: 変わるのは「古い読みの並べ替えを最後までやるか」だけ。候補の作り方、LM の重み、締め切り、Convert の動きは変えない。止めても、最悪は今と同じ「LM なしで変換」。
- 値は計測で決める: **この ADR は新しい値（間隔、締め切り、加点）を持ち込まない。** 印を一定の間隔で見に行く作りを避けたのはこのため。段階 2 の要否の基準だけは実測のあとにユーザーが決める（§10 の Q2）。
- こまめに確定するのがコンセプト: 打鍵が速く、推論が遅い機械ほど効く。長文のための仕組みではない。

## 8. スパイク（段階 1 の効き目と、段階 2 の要否を決める前に）

- 捨てるコードで、`LlamaScorer::nll` の decode ごとの時間（プロンプト、候補のバッチそれぞれ）と、バッチの数をログに出す。入力は評価のセット（`eval/sets/`）の作文だけ（実機の学習や利用者の文は使わない）。
- 測る装置: Mac の Metal、Mac の CPU、N150 の VM の Vulkan と CPU（ADR 0059 と同じ機械）。
- 出すもの: 推論 1 回の中の decode の時間の割合、止めどころの間の最長の時間。これで「古い推論の残り」の期待値を、段階 1 と段階 2 で見積もる。
- Vulkan で abort callback が本当に効かないかも、同じ VM で 1 回確かめる（コールバックを登録し、呼ばれるかをログに出す）。

### 8.1 実測（2026-11-21。#486）

詳細は `eval/reports/lm-decode-abort-486-2026-11-21.md`。入力は `eval/sets/homophones-ext.tsv`。モデルは zenz-v3.2-small Q5_K_M。

- **候補のバッチは、どの推論でも 1 回**（推論 1 回あたり decode はプロンプト 1 回 + バッチ 1 回）。
- **推論 1 回の中身**（p50）:

| 装置 | 推論 1 回 | プロンプト | 候補のバッチ |
|---|---|---|---|
| Mac CPU | 40〜50ms | 9〜12ms | 28〜33ms |
| Mac Metal | 約 32ms | 約 10ms | 約 18ms |
| N150 VM の CPU | 451ms | 108ms（24%） | 313ms（69%） |
| N150 VM の Vulkan（内蔵 GPU） | 177ms | 約 60ms（33%） | 約 96ms（55%） |

- **GPU（Metal、Vulkan）では decode の関数はすぐ戻り、実時間は最初の `get_logits_ith`（同期点）に出る。** 段階 1 の止めどころ (b)(c)(d) は、実質、同期点を過ぎた後に見ることになる。
- **abort callback（N150 VM、200 トークン）:**
  - CPU: グラフのノードごとに 249 回呼ばれ、2ms 後に印を立てると約 15ms で止まる（decode 全体は約 670ms）。
  - **Vulkan: 1 回の decode で 2 回しか呼ばれない。2ms 後に印を立てても止まらず（rc=0）、最後まで走る（約 195ms）。入口で最初から立てておいたときだけ止まる。** Metal も同じ（Mac で確認）。**§4 の見込みが実機で確かめられた。**
- 見積もり: GPU では、古い推論の残りは、段階 1 でも最大でバッチ 1 回分（Vulkan で約 100ms、Metal で約 18ms）。段階 2（abort callback）が効くのは CPU のときだけ。Q2（段階 2 を今は入れない）の材料になる。


## 9. 効き目の測り方と完了の条件

1. `lane/s429` の 2 つの再現テストの `#[ignore]` を外して通す。テストの偽の採点は、遅延を decode に見立てた区切りに分け、区切りで印を見る。判定の上限（今は推論の 1.5 回分）は、段階 1 の見込み（自分の推論 + 区切り 1 つ分）に合わせて直し、理由をテストに書く。
2. 取り消しのテストを足す: 取り消しが `HostHealth` の失敗に数えられない、取り消した id の返事を読み捨てる、版 1 の子は使わない、同じ `CacheKey` の `submit` では止めない、Convert の要求は止めない。
3. ADR 0065 §3.4 の再生の評価（人工の遅延を足して、打鍵の間隔と Space までの間を再生する）を、中断の前後で流し、LM が付く率の曲線を比べる。ADR 0065 §6.3 のとおり、曲線が良くなれば X を上げるかをユーザーに聞く。
4. **変換の 1 位が悪化しないこと**: 評価（`ikari-eval`）は締め切りなしで 1 つずつ採点するので、取り消しは起きず、順位は変わらない見込み。`eval/scripts/snapshot.sh` で全セットの 1 位が同じであることを確かめる。
5. `scripts/check.sh`（フル）と、`scripts/check.sh --real --perf`。

## 10. ユーザーの判断が要る点

### 決定済み（ユーザー、2026-11-16。すべて推奨どおり）

- **Q1**: セッション（別のアプリ）をまたいでも止める。
- **Q2**: decode の最中に止める（abort callback、unsafe の FFI）は今は入れない。§8 のスパイクのあとに、入れるかと基準を決める。
  - **2026-11-21 ユーザー決定（§8.1 の実測のあと。推奨どおり）: 入れない。** GPU（Vulkan、Metal）では abort callback が途中で止まらず、効くのは CPU だけで、unsafe の寿命の約束が増える割に合わない。見直すのは、CPU が主の機械で古い推論の残りが実害になると分かったとき。
- **Q3**: 子との取り決めを版 2 にし、ADR 0068 の LM の子の許可リストに `Cancel`（番号だけ）を足す（ADR 0068 の末尾の追記）。版 1 との互換は持たない。

### （記録）決定の前の問い

- **Q1: セッションをまたいで止めてよいか。** 推奨: またいで止める（§5）。別のアプリに移ったあとの古いアプリの先行計算は捨てる。代案: 同じセッションのときだけ止める（別のアプリに移った直後は、今の待ちが残る）。
- **Q2: decode の最中に止める（段階 2、unsafe の FFI）を今は入れない、でよいか。** 推奨: 入れない。段階 1 とスパイクの結果（N150 の VM で、古い推論の残りの待ちの p90 など）を見て、入れるかと基準をそのとき決める。Vulkan では効かない見込みであることも判断の材料。
- **Q3: 取り決めの版を 2 に上げ、ADR 0068 の LM の子の許可リストに `Cancel` を足してよいか。** 推奨: 足す。運ぶのは番号だけで、檻と権限は変わらない。版 1 との互換は持たない（子とエンジンは一緒に入れ替える前提）。

## 11. 検討した案

- **Q1: `LmScorer` に `cancel()` の入口を足す**: 推論を持つのはワーカーのスレッドで、`nll` は `&mut self` で走る。別のスレッドから同じ scorer の `cancel()` を呼ぶには、scorer を共有できる形に作り直す必要があり、所有の作りが崩れる。印を要求に持たせれば、scorer は今の 1 スレッドの持ち物のまま。採らない。
- **Q1: `RankInput` に印の欄を足し、`convert_until` などの引数で運ぶ**: 明示的で読みやすい。`core` の変換の API（`convert_until`、`page_until`、`prefill`、`RankInput`）と呼び出し元をすべて変えることになる。`lm_trace` が同じ道（スレッドの範囲）ですでに通っているので、そちらに揃える。範囲の外（評価、CLI、Convert）では印が無い = 止めない、が既定になるのも都合がよい。
- **Q2: 段階 2 から入れる**: 効き目は大きい見込みだが、最優先の Windows の Vulkan で効かない見込みで、unsafe の寿命の約束が増える。§4 の理由で後にする。
- **Q2: 推論を細かく分ける（候補 1 つずつ decode する）**: 止めどころは増えるが、バッチにまとめる今の速さを失う。採らない。
- **Q3: LM のワーカーが、新しい要求が届いた時点で走っている推論を止める**: `lm` の中だけで済み、評価や CLI にも効く。ただし (1) 何が要らないかを LM の層が決めることになる（判断はエンジンに置く）。(2) 古いジョブが次の `rank` で出す要求が、新しいジョブの推論を止め返す（Q4 をエンジンで解かない限り、行ったり来たりする）。(3) まだ待っている送り主（別のセッション、自己診断）を区別できない。採らない。
- **Q4: 先行計算のスレッドを 2 本にする**: LM のワーカーは 1 本なので、LM の待ちは減らない。並行の管理（同じセッションの 2 つのジョブ、`running` の数）が増える。採らない。

## 12. 実装の進め方（承認のあと）

1. **契約コミット**: `lm::CancelToken`（印と、立ったときに呼ぶものの登録）、`lm::cancel::scope`、`LmError::Cancelled`、`LmScorer::nll` の引数、`proto.rs` の版 2（`Cancel`、`FailKind::Cancelled`）、`PrefetchQueue` の走っている依頼の印。中身はスタブ。
2. **並行実装**（持つファイルを分ける）:
   - レーン A（同じプロセス）: `lm/src/ranker.rs`、`lm/src/llama.rs`、`lm/src/trace.rs`、`lm/src/ranker/tests.rs`。
   - レーン B（別プロセス）: `lm/src/host/`（`proto.rs`、`scorer.rs`、`serve.rs`）。
   - レーン C（エンジン）: `engine/src/cache.rs`、`engine/src/workers.rs`、`engine/src/tests/`、自己診断の呼び出し（ADR 0065 の実装が入っていれば）。
3. **統合**: 再現テストの `#[ignore]` を外す、§9 を流す。ADR 0068 の表と `docs/architecture.md` の LM の節を直す。
4. §8 のスパイクは、契約と並行して別に行い、結果は `eval/reports/` に置いて、段階 2 の判断の材料にする。

## 13. 懸念と前提

- Vulkan に abort callback が無いことは、ソースを探した結果で、実機では確かめていない（§8 で確かめる）。
- 段階 1 の効き目（約半分）は推測。プロンプトの decode と候補の decode の時間の割合で変わる。
- `run_job` の中で印を見る場所は「`rank` の呼び出しの前」と「段の間」。辞書の引きなど LM でない計算の途中では止めない（短いので）。
- 同じ `CacheKey` の再依頼を止めない判定は、呼び出し元がすでに重複を除いているなら不要になる。実装のときに確かめる。
