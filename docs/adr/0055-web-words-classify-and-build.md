### 0.3 ユーザーの決定（2026-11-06）
1. **ライセンスは「条件つきで進める」**。根拠: 著作権法 30 条の 4 第 2 号（情報解析）と、CC BY-SA 4.0 が権利制限の適用される利用には条件を課さないこと（researcher の調べ。法的な助言ではない）。条件:
   - 語と出現頻度の一覧は、CC BY-SA 4.0 の表示つきで **GitHub の Release の資産**にする（0039 §12 と同じ）。
   - **辞書（system.dict）は利用者の手元で生成する**（今と同じ）。
   - `THIRD_PARTY_NOTICES.md` に、出典（版）、加工（語と頻度のみ）、ライセンス、「本文は同梱しない」を書く（§5.3）。
   - **ビルド済みの辞書を配る段（#99）で、もう一度確かめる。**
2. **判定できない語の方針**:
   - 固有名詞ではないと判定できた語（記事がなくても、固有名詞の目印に当たらない外来語）は、**普通名詞として入れる**。
   - 固有名詞と判定できた語は、**固有名詞の品詞の ID を付けて入れる**。
   - 固有名詞かどうか迷う語（記事はあるが分類が取れないもの）は、**入れない**。
- 決定 2 は、0039 §0.4 の方針 2（固有名詞は入れない）を改める。0039 §2.3 の F4（固有名詞を除く）は、本 ADR の「区分」（§2）に置き換わる。

## 1. 問題の定義

- PoC で、普通名詞を足す得（ばーじょにんぐ が 1 位）と安全（悪化 0）は見えた。残る問題は 2 つ:
  1. **混入の 6 割が固有名詞**で、本文だけの手がかりでは分けられない（F4b・F4c は誤りの方が大きい）。分けないまま入れると、固有名詞が普通名詞の ID とコストで入り、品詞と並びの前提がずれる。
  2. **固有名詞を入れるなら、普通名詞とは別のコストが要る**（連接が安いため。§0.2）。
- 制約: 判定は再現できること（同じ版のダンプから同じ一覧）。利用者に GB の取得をさせない。値（下限、コスト、ID）は掃引で決め、守る群の悪化 0 を条件にする。Wikipedia の本文は配らない。

## 2. 判定の規則（区分）

### 2.1 入力
- 語の一覧（`collect` の出力）: 表記、tf、df、手がかりの回数（cue）。
- jawiki の SQL ダンプ（同じ日付）: `page`（名前空間 0 の題、リダイレクトの印）、`redirect`（リダイレクトの行き先。§11 R1）、`page_props`（`wikibase_item` と、曖昧さ回避の印 `disambiguation`）、`categorylinks` + `linktarget`（記事の直接のカテゴリの名前）。
- **リダイレクトの扱い**（researcher の調査 R1、2026-11-06）:
  - `redirect` の行き先は ID ではなく**題で引く**。(名前空間 0, 題) を `page` の題の表で ID にする。題は `_` を空白に直してから引く。
  - `page` のリダイレクト印だけで判定せず、**`redirect` の行を併用する**。印があって行がない記事が 0.4%ある。
  - 行き先がまたリダイレクトのときは、**最大 3 段たどる**。
  - 行がない場合と、3 段で記事に着かない場合は**迷う**（2026-11-06 ユーザー決定。§0.4 の末尾）。
  - 曖昧さ回避は `page_props` の `disambiguation` で取れる（名前空間 0 で約 9.2 万件）。行 4 はこの印で判定する。
- カテゴリの規則表（リポジトリの新しいファイル。§2.3）と、Sudachi の CSV（同じ版）。

### 2.2 区分（上から順に当てる。理由ごとの件数をレポートに出す。ADR 0030 の TownReport と同じ型）
| 順 | 条件 | 区分 | 入れ方 |
| --- | --- | --- | --- |
| 0 | Sudachi（small + core + notcore）と ABR の語に同じ表記がある（F1） | 既知 | 入れない |
| 1 | 形の規則（F3。0039 §2.3 のまま）に当たる | 形 | 入れない |
| 2 | 同じ表記の記事（名前空間 0）がない（リダイレクトでもない）、かつ固有名詞の目印（§2.4）に当たらない | **普通名詞** | `名詞,普通名詞,一般` |
| 3 | 記事がない、かつ目印に当たる | 迷う | 入れない |
| 4 | 記事がある（リダイレクトは行き先の記事で判定）、かつ曖昧さ回避のページ | 迷う | 入れない |
| 5 | 記事のカテゴリが、規則表の「人名」に当たる | **固有名詞・人名** | `名詞,固有名詞,人名,一般` |
| 6 | 同「地名」に当たる | **固有名詞・地名** | `名詞,固有名詞,地名,一般` |
| 7 | 同「固有名詞一般」（組織、作品、製品、種名、団体、出来事など）に当たる | **固有名詞・一般** | `名詞,固有名詞,一般` |
| 8 | 同「普通名詞」（概念、技術、用語、手法など）に当たり、5〜7 のどれにも当たらない | **普通名詞** | `名詞,普通名詞,一般` |
| 9 | 5〜8 の 2 つ以上の固有名詞の区分に当たる、または普通名詞と固有名詞の両方に当たる、またはどれにも当たらない | 迷う | 入れない |

- 「同じ表記の記事」は、題を NFKC にせず、そのまま（全角の中黒などを含む）比べる。題の括弧の補足（「…（ソフトウェア）」）だけを外した形も同じ表記とみなす（同じ語の別の意味があるので、行 9 の両方に当たる判定に入る）。
- 区分 5〜7 の「どの固有名詞か」が分からない（固有名詞の目印だけがある）語は、迷う語として入れない（固有名詞一般に寄せない）。
- 記事がない語は、普通名詞の連結（ソロアルバム）が多い（PoC §6）。連結を足すかは F5（0039 Q4。§4.2 の軸）で扱い、区分では区別しない。

### 2.3 カテゴリの規則表
- ファイル: `dict-builder/webwords/categories.tsv`（リポジトリ。ikari-ime の作成物で Apache-2.0。カテゴリの名前の一部を照合の型として持つだけで、Wikipedia の内容は持たない）。列は `型の種類（完全一致 / 末尾 / 先頭 / 正規表現）	型	区分`。
- 見るのは**記事の直接のカテゴリだけ**（カテゴリの木はたどらない。再現と速さのため。足りなければ §11 R2 で測ってから広げる）。
- 型の例（初版の候補。効きは §4.1 で測ってから採る）: 人名 = `存命人物`、末尾 `年生`・`年没`、末尾 `の人物`。地名 = 末尾 `の市町村`・`の都市`・`の島`・`の河川`・`の山`・`の州`。固有名詞一般 = 末尾 `の企業`・`の団体`・`の楽曲`・`のアルバム`・`の映画`・`の漫画`・`のゲームソフト`・`の製品`・`科`・`属`。普通名詞 = 末尾 `の技術`・`の概念`・`の用語`・`の手法`、`ソフトウェア工学`、`データ構造`、`アルゴリズム`。
- **5 本の型を足した**（researcher の調査 R2 とユーザー決定、2026-11-06）: 競走馬（固有名詞一般）、サラブレッド（同）、の行政区画（地名）、のコムーネ（地名）、生没年不詳（人名）。迷う語は **18,081 語から 16,114 語に減る**。初版の表は `dict-builder/webwords/categories.tsv`（契約のコミットで入れた）。
- **保守用のカテゴリは照合から外す**（スタブ、Wikidata、ページ、記事、マジックリンクなど。記事の内容の分類ではない）。表のコメントと、`dict-builder/src/webwords/rules.rs` のテストで固定する。
- **C4（木をたどる）は、保守用のカテゴリを除いた残りの迷う語を測ってから決める**。
- 表の変更は PR で行い、§4.1 の代理の測定（効きと誤り）をレポートに出す。

### 2.4 固有名詞の目印（記事のない語に当てる）
- 候補: F4b（本文の直後の手がかりの割合 cue/tf）、F4c（Sudachi の固有名詞だけの表記に分けられる）、F4d（連なりの頭か末尾が Sudachi のカタカナの人名・地名と一致し、その部分が 3 字以上）。
- 目印に当たった語は「迷う」で入れない（普通名詞を落とすだけで、固有名詞は混ざらない）。PoC では F4b・F4c の誤り（普通名詞を落とす率）が 3〜5% あるので、**どの目印を採るか、F4b の閾値をいくつにするかは、§4.1 の代理の測定で決める**（落とす普通名詞の数と、混ざる固有名詞の数を並べて、ユーザーに確認する）。

## 4. ID とコストの決め方（掃引）

### 4.1 判定の代理の測定（辞書を作らずに測る）
- **正解の代理**: Sudachi にあるカタカナの語（3 字以上）を、品詞で「普通名詞」「固有名詞・人名」「地名」「一般」に分けたもの。§2.2 の行 0（F1）を外して区分を当て、区分ごとの適合率と再現率を出す（混同行列）。
- 目印（§2.4）とカテゴリの規則表（§2.3）は、この表で**固有名詞を普通名詞に入れる誤り**（混ざる）と、**普通名詞を迷うに落とす誤り**（失う）を並べて採る。
- 加えて、Sudachi にない語の区分ごとに、0039 Q3 の形で抜き取りの下書き（エージェント）と確認（ユーザー）を行う。PoC と同じ FNV-1a64 の種で、区分と df の段ごとに 30 語。人名は報告に載せない。

### 4.2 段 1: 普通名詞（固有名詞は足さない）
- 軸: df の下限 {5, 10, 20}、F5 {あり, なし}、左右 ID {品詞の最頻（今は 5144）, 「同じ品詞でコストが掃引の範囲にある行」の最頻（今は 5139）}、コスト {11000, 12000, …, 17000} と df の段つき（PoC の 17000/14000/11000 の型）、「足さない」。
- ID は**固定の数値を持たず**、ビルドのときに Sudachi の行から上の規則で数える（ADR 0030 §4 と同じ）。
- 狙う群: (1) LOO の 8,698 件の 1 位、(2) katakana-like の カタカナ語(分割負け)、(3) 新しいセット `eval/sets/webwords.tsv`（公開の一般的な語。期待はユーザーの確認後）。
- 守る群: snapshot の全セットと AJIMEE（LM なし `--ranker full`、LM あり zenz-v3.2 small・時間切れ 0）、S0 の守る群 6,999 読み、ADR 0030 §4 の phr（普通の名詞の連なり 11,000 件の横取り）。
- LM ありは、LM なしで悪化 0 の点のうち上位 3 点だけを流す（時間のため）。

### 4.3 段 2: 固有名詞（段 1 の採る点を固定して足す）
- 区分ごとの ID: Sudachi の同じ品詞でカタカナだけの行の最頻の組を数える（今の版では 人名 4787/4788、地名 4791/4792、一般 4785 の見込み）。
- **出発点のコストは、連接の差で補正する**: 区分 p の補正 Δp = Σ（頻出の前後の文脈 c について） w(c) ×（conn(c, 普通名詞の ID) − conn(c, p の ID)）。文脈は BOS・EOS と、Sudachi の頻出の前後の ID の上位 N（N は 50 を出発点にし、Δp が N で動かなくなる大きさにする）、w(c) はその頻度。出発点 = 段 1 のコスト + Δp。
- 軸: 出発点 + {−2000, 0, +2000, +4000, +6000}、区分ごとに「足さない」。`proper_noun`・`place_name`・`lemma_rank`・d2s・#223 の後ろ回しは**そのまま効かせて**測る（ポリシーは変えない。最終のコストで比べる）。
- 狙う群: 固有名詞の LOO（Sudachi のカタカナの固有名詞から乱数で 3,000 語を伏せた辞書に、区分つきの一覧を足して 1 位に戻る数。S0 と同じ作り方）。
- 守る群: 段 1 と同じ。加えて「**普通名詞の 1 位を固有名詞が取った読み**」の数を出す（同じ読みの普通名詞が辞書にある・足した読みで、足した固有名詞が 1 位になった件数。0 であることを条件にする）。

### 4.4 採る・採らない
- **不採用**: 守る群のどこかで 1 位が基準より悪化した点（LM なし・あり）。段 2 は「普通名詞の 1 位を取った読み」が 0 でない点も。
- 採る点: 不採用でない点のうち、(1) 狙う群の 1 位が多い、(2) 同じなら混入が少ない、(3) それも同じなら一覧が小さい。**値は PR に明示し、ユーザーの確認のあとで既定にする**。
- どの区分も、悪化 0 の点がなければ「足さない」を採る（その区分は入れない）。

### 4.5 決めた値（段 1。2026-11-06 ユーザー承認）

掃引（PR #222、`eval/reports/webwords-sweep-2026-11-06.md`。df の下限 {5, 10, 20} × 基準コスト {9000, 11000〜17000} の 24 点。全 eval/sets と AJIMEE の 7,358 件、leave-one-out、守る群 6,999 読み、LM あり）の結果から、次を既定にした。

| 値 | 既定 | 根拠 |
| --- | --- | --- |
| df の下限 | 5 | 10 は しゃーでぃんぐ（df 6）が、20 は ばーじょにんぐ（df 16）も入らない |
| 普通名詞のコストの基準 | 15000（実コスト: df 5〜19 が 17000、20〜99 が 14000、100 以上が 11000） | 全セットの悪化は 24 点とも 0。守る群は 13000 以下で 1〜3 件落ち、14000 以上で 0。LM ありは 16000 で悪化 2。1000 の余裕を取って 15000 |
| 辞書の増加 | +4.3MB（47,575 行）を許容 | df 5 の追加行数 |

- 置き場所: `dict-builder/src/webwords/types.rs` の `MIN_DF_FLOOR`、`lex.rs` の `DEFAULT_COMMON_COST` と `COST_TIERS`。`webwords lex` の `--min-df`・`--cost`、`cargo xtask dict`・`scripts/build-dict.sh` の `--webwords-min-df`・`--webwords-cost` は、省略するとこの値。設定（`webwords.*`）は持たない（辞書をビルドするときの値で、実行時の設定ではない）。
- 一覧がなければ、今と同じ辞書を作る性質は変えない（`consts.rs`・`lib.sh` の URL と sha256 は、一覧を Release に置くまで空）。
- 配る一覧の大きさの見込み（§5.2）は、実測で 125,719 行・4.4MB・xz で 0.73MB（固有名詞を含む）。
- F5 を外す案は未測定（掃引の報告 §4.3、§6）。

## 5. データの取得と生成のパイプライン

### 5.1 メンテナー（ikari-ime の作者、将来は CI）
1. `cargo xtask webwords fetch --dump <日付>`: dumps.wikimedia.org から pages-articles（分割の全ファイル）と SQL ダンプ（§2.1）を、空の作業用ディレクトリに取る。sha1 を dumpstatus.json と照合し、sha256 を記録する。`data/raw` には置かない。
2. `dict-builder webwords collect`: 本文から連なりを数える（0039 §2.2。PoC の追加の条件「題が一覧で終わる記事と曖昧さ回避を除く」を採る）。
3. `dict-builder webwords classify`: §2.2 の行 0〜9 を当て、区分を付ける。迷う・既知・形の語は出力しない。df は配る下限（掃引の最小 = 5）より小さい語を出さない。理由ごとの件数と §4.1 の代理の測定をレポートに出す。
4. 出力: `webwords-<ダンプの日付>.tsv`（§5.2）と、`webwords-<日付>-report.md`。
5. 一覧を `xz -9e` で圧縮し、GitHub の Release（ADR 0033 の型。タグは `webwords-<日付>`）に資産として置く。`xtask/src/data/consts.rs`（と `scripts/lib.sh`）に URL・版・sha256 を固定する。
- 本文と SQL ダンプは配らない。作業用のディレクトリは、Release に置いたあと消す（sha256 は一覧のヘッダとレポートに残る）。

### 5.2 一覧の形式（schema=2。0039 §5.1 を上書きする）
- UTF-8、タブ区切り。1 行目:
  `#ikari-webwords	schema=2	source=jawiki-<日付>	sha256=<pages-articles の各ファイルの sha256 をつないだものの sha256>	articles=<数えた記事数>	sudachi=<F1 に使った版>	rules=<categories.tsv の sha256>	license=CC-BY-SA-4.0	attribution=Wikipedia 日本語版の執筆者（https://ja.wikipedia.org/）`
- 2 行目以降: `表記	tf	df	区分`。区分は `common`、`proper.person`、`proper.place`、`proper.general` の 4 つだけ。並びは表記のコードポイント順。
- 記事の名前、カテゴリの名前、文、リンクは持たない。読みは持たない（ビルドのときに表記から作る）。
- 大きさの見込み: **約 9 万行、約 3.2MB、xz で約 0.5MB**（researcher の調査 R3、2026-11-06。PoC の df≥5 の 265,733 行から F1 の 144,459 と F3 の 1,134 を除いた約 12 万語（候補）のうち、迷う語を除いたもの）。

### 5.3 利用者の手元（辞書を作る段）
1. `scripts/fetch-data.sh --only webwords`（実体は `xtask/src/data/fetch.rs`）が Release から一覧を取り、sha256 を確かめて `data/raw/webwords/` に置く。既定の取得物に含める。
2. `scripts/build-dict.sh`（実体は `xtask/src/dict.rs`）が、一覧があれば `dict-builder webwords lex` を呼ぶ: F1 をその場の Sudachi でもう一度当て（版が一覧のヘッダと違えばログに出す）、F2（df の下限）、F5 を当て、区分ごとの品詞・ID・コストで `data/build/webwords_lex.csv` を作る。読みは表記のカタカナをそのまま（Sudachi の lex の読みの列）。
3. `--lex` と `--notcore-lex` に渡す（ABR の町名と同じ）。BUILD_INFO に一覧の sha256 と、`webwords.*` の値を書く。一覧がなければ、今と同じ辞書を作る（ログに出す）。
4. 掃引用の上書き: `--webwords-min-df`、`--webwords-cost`、`--webwords-proper-offset <区分>=<値>`、`--no-webwords`（ADR 0030 の `--town-cost` と同じ形）。
- system.dict はこれまでどおり利用者の手元で作り、アプリのバンドルに含めない。

### 5.4 THIRD_PARTY_NOTICES.md の文面（案。「辞書データ」の節に足す）

```md
### Wikipedia 日本語版（外来語の語と出現頻度の一覧）

- **ライセンス**: クリエイティブ・コモンズ 表示-継承 4.0 国際（CC BY-SA 4.0）。https://creativecommons.org/licenses/by-sa/4.0/deed.ja
- **出典**: ウィキペディア日本語版（https://ja.wikipedia.org/）の執筆者。データベースダンプ jawiki-<日付>（pages-articles、page、redirect、page_props、categorylinks、linktarget。https://dumps.wikimedia.org/jawiki/<日付>/）。各記事の執筆者は、各記事の履歴を参照
- **加工**: ikari-ime が、上のダンプの記事の本文から片仮名の連なりを取り出し、語ごとの出現回数と出現した記事の数を数え、記事の有無とカテゴリから普通名詞と固有名詞（人名・地名・一般）の別を付け、辞書にある語と迷う語を除いた一覧（`webwords-<日付>.tsv`）を作成した。一覧が含むのは、語（表記）、出現回数、記事の数、区分だけである。記事の本文、文、記事の名前、カテゴリの名前は含まない
- **使用方法**: 一覧は ikari-ime の GitHub の Release に、CC BY-SA 4.0 の表示つきで置く。`scripts/fetch-data.sh --only webwords` で `data/raw/webwords/` に置き、dict-builder の `webwords lex` が利用者の手元で辞書（`system.dict`）に語を加える。Wikipedia の本文は同梱しない。辞書は `~/Library/Application Support/ikari-ime/dict/` に置かれる（バンドルには含めない）
```

- 法の解釈（30 条の 4）は文面に書かない（ADR にだけ書く。断定しないため）。
- `fetch-data.sh` の取得物の表の注にも、出典とライセンスを 1 行で書く（ADR 0030 §6 と同じ）。
- Rust の新しい依存（bz2 の展開など）を足すときは、「Rust依存クレート」の節にも足す（クレートは契約のコミットで選ぶ）。

## 6. Sudachi を新しい版に更新したときの再実行

0039 §2.6（Sudachi の版上げに合わせて作り直す。0039 Q5 で承認）の具体的な手順:
1. Sudachi の版を上げる PR の中で、その時点で最新の jawiki のダンプの日付を選ぶ（毎回のダンプは追わない）。
2. §5.1 の 1〜4 を、新しい Sudachi で流す（F1 は新しい版で当たる。Sudachi が足した語は自然に消える）。
3. レポートに、前の一覧との差（区分ごとに増えた語・消えた語・区分が変わった語の数）と、§4.1 の代理の測定を出す。
4. 抜き取りの下書き（エージェント）と確認（ユーザー）を、増えた語から行う（0039 Q3 の形）。
5. 採っている点と、その前後（コスト ±2000、df の下限 1 段）で §4.2〜4.3 の守る群を流す。採っている点で悪化 0 なら値を変えない。悪化が出たら §4 の掃引をやり直し、値を PR に明示してユーザーに確認する。
6. Release に新しいタグで置き、`consts.rs`・`lib.sh` の URL と sha256、`THIRD_PARTY_NOTICES.md` のダンプの日付を変える。前の一覧の Release は消さない（旧版に戻せるように。spec「辞書の更新」）。
7. `scripts/check.sh`、`eval/scripts/snapshot.sh`（全セットで 1 位が悪化しないこと）、辞書を作り直してインストール。
- カテゴリの規則表だけを変えたとき、または jawiki だけを新しくしたときも、2〜7 を同じく流す。

## 8. 結果（採ったときに変わること）

- 得るもの: 記事のない、またはカテゴリが普通名詞の外来語が辞書に入る（ばーじょにんぐ が 1 位。PoC）。固有名詞は品詞のとおりに入り、ポリシー（`proper_noun`、`place_name`、d2s）の対象になる。
- 失うもの: 迷う語（記事はあるが分類が取れない語）は入らない。カテゴリの規則表の手入れが要る。メンテナーの作業に、0.5GB の SQL ダンプと約 5GB の本文の取得が加わる（利用者には一覧だけ）。
- 変えないこと: system.dict の形式、grammar.bin、core・engine・殻、LM、ポリシーの値。

## 9. 誤りの訂正（2026-11-06。researcher の確認）

- **Mozc の記述（0039 §0.1）**: 0039 は「Mozc は、辞書のカタカナ語を Web のデータの処理で集めている」と書いた。Mozc の README は、辞書を **Web のデータの処理で作った**とだけ書き、**カタカナ語に限る記述も、Wikipedia を使ったという記述もない**。本 ADR と 0039 の出どころ（Wikipedia）は、Mozc の前例に倣ったものではない。
- **jawiki-kana-kanji-dict のライセンスの記述（0012 §0.3 の表と §7 案C、0039 §12）**: 0012 は「生成物も MIT と作者は書く」、0039 は「生成物を MIT で配る」と書いた。リポジトリのライセンスの表示は **CC BY-SA へのリンク**で、生成物が MIT という記述は誤り。0012 案C を採らなかった判断（読みの誤り、固有名詞が中心）は変わらない。
- 0039・0012 の本文は直さず、それぞれの末尾の「補足」にこの節を指す行を置く（PR #125 が 0039 を編集中のため）。

## 10. 懸念点

- **カテゴリの規則表の偏り**: 直接のカテゴリだけでは、カテゴリの付け方が記事によってまちまちで、迷う語が多く残る恐れがある（§11 R2）。迷う語は入れないので、害は「入らない」側に倒れる。
- **記事のない固有名詞**: 記事のない人名・作品名は目印（§2.4）でしか止められず、すり抜けると普通名詞として入る。§4.1 の抜き取りで量を測る。
- **連接の補正の近似**: Δp は頻出の文脈の重み付きの平均で、文脈ごとの差は残る。段 2 の守る群（とくに「普通名詞の 1 位を取った読み」）で確かめる。
- **ライセンスの再確認**: ビルド済みの辞書を配る段（#99）で、ShareAlike が辞書に及ぶか、表示の置き場所を、もう一度確かめる（ユーザー決定 1 の条件）。それまでは、辞書をビルド済みで配らない。
- **ダンプの保存期間**: dumps.wikimedia.org は古いダンプを消す。再現には sha256 しか残らない（ダンプは約 5GB で保存しない）。同じ日付のダンプが要るときは、ミラーを探す（推測。確かめていない）。

## 11. 要調査（researcher への問い。2026-11-06 に答えが出た。§0.4）

- **R1** `redirect.sql` の大きさと、`page` との結び方（リダイレクトの行き先の記事 ID の取り方）。曖昧さ回避の印が `page_props` の `disambiguation` で取れるか。
- **R2** 記事のある Sudachi にない語（PoC の df≥5 の候補）のうち、直接のカテゴリが §2.3 の型の候補のどれかに当たる割合。迷う語の割合（カテゴリの木をたどる案 C4 を検討するかの材料）。
- **R3** schema=2 の一覧の行数と、xz で圧縮した大きさ（df≥5、迷う語を除いたもの）。

## 12. ユーザーに聞くこと（2026-11-06 に Q1〜Q3 とも推奨どおりに決定）

- **Q1. 区分（普通名詞・固有名詞）は、メンテナーが SQL ダンプで判定し、一覧の列として配ってよいか。** 推奨: はい。利用者は一覧（数 MB の見込み）だけを取ればよく、0.5GB の SQL ダンプを取らずに済む。区分はダンプの版で決まるので、手元でやり直す意味がない（§3 案 C6）。
- **Q2. 普通名詞を先に既定にし、固有名詞は段 2 の掃引のあと、別の PR で既定にしてよいか。** 推奨: はい。普通名詞は PoC で得と安全が見えている。固有名詞は連接の補正（§4.3）を測ってからで、まとめると悪化の原因を切り分けにくい。
- **Q3. 本番の一覧は、分割ダンプの全ファイル（全記事）から作り、Wikidata の P31 は今は使わない、でよいか。** 推奨: はい。全記事なら標本の偏り（PoC §1）がなく、再現できる。P31 は迷う語の割合（§11 R2）を見て、多すぎるときだけ、迷う語に絞って別の ADR で検討する。
