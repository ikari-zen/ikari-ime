# ADR 0023: 先読みキャッシュの構想（段階1・2）は、新しい仕組みとしては作らない。段階3は B36 にまとめ、まず測る

- 状態: 承認（2026-10-23。Q1〜Q4、Q6 は推奨どおり。Q5 は B36 の ADR で改めて聞く）
- 日付: 2026-10-16
- 対象: 外部（ChatGPT）の構想レビュー「アイドル時に汎用 SLM で文章を先読み生成し、読み → 表記の Trie キャッシュに入れて、一致した入力に即座に候補として出す」の段階1・2が、ikari-ime にとって有効かの見立て。コードは変えない（調査と測定だけ）
- 前提: main = 7c552a5。spec の基本原則（入力を正とする、学習は支援であって決定ではない）、FR-06（読みの完全一致）、FR-08（次語予測をしない）、NFR-19（内部データに原文を持たない）、[ADR 0002](0002-phase1-architecture.md) §7.2（文書内キャッシュ）・§8（文脈付きの学習）・§11（取り込み）、[ADR 0013](0013-learning-without-context.md)（back-off。案 E を不採用）、ADR 0015（B28。`feat/b28-context-sources` ブランチ。main にない）
- タスク: B38。段階3（アイドル時の SLM 先読み生成）は調査の対象外。ただし段階3に進む判断材料を §6 に短く書く
- 測定: scratchpad の捨てるスクリプトと `ikari-eval`（コミットしていない。§8 に再現の手順）。ユーザーデータは**読むだけ**（学習ファイルのコピーを scratchpad に置いて使った。元のファイルの md5 が測定の前後で同じことを確かめた）。ユーザーの確定の中身（読み、表記）はこの文書に書かない。件数だけ

## 0. 構想の要点（持ち込まれたレビュー）

| 段階 | 内容 | レビューが挙げた測り方 |
| --- | --- | --- |
| 1 | 既存の変換で得た読みと表記の対応をキャッシュする（前方一致の Trie など）。通常の候補と併存させ、確定はユーザーに委ねる | ヒット率、検索時間、誤候補率、メモリ |
| 2 | 確定文から専門用語、文体、頻出の固有名詞、直近のキーワード、選んだ変換の結果を持ち、順位付けに使う（専用の文脈モデルは作らず、辞書・カウンタ・ルール） | 文脈なし比の精度、順位、誤変換率 |
| 3 | アイドル時に SLM で文章を先読み生成する | （今回は対象外） |

レビューの注意点: 表記から読みを一意に復元できない／読みが一致しても正しいとは限らない／文全体の一致はヒットしにくいので読みの接頭辞で持つ／p95・p99 を測る。

ユーザーの問い: 「候補は辞書から作り、LM は並べ替えにだけ使う」を変える価値があるか。まず段階1・2が有効かを調べる。

### 1.2 構造上の穴を1つ見つけた（コードで確認）
学習の加点は、`Conversion::rank_and_append` が**塊ごとに**かける（最初のプール 30 件＋かな＋Rewriter、そのあとは 9 件ずつ）。並べ替えは塊の中だけで、確定済みの列（`generated`）は末尾に足すだけ。したがって、**辞書の候補の 31 位より後ろにある表記は、何回選んでも1ページ目に上がらない**（`core/src/converter/conversion.rs`）。キャッシュの構想が言う「保存した表記を必ず出す」に当たる部分で、今の仕組みに本当にない機能はこれだけ。大きさは §3.1-4 で測った（小さい）。

## 3. 有効性の見立て（測った値）

### 3.1 段階1: 学習ストアを「キャッシュ」とみなしたときのヒット率と、今の順位

方法: 実機の学習ファイル（`learning.tsv`）の usage 層の phrase の記録のうち、Unconditional の特徴量の行（確定1回につき1回数える）から (読み, 表記, 回数) を取り出し、文脈なしの評価セットにした（871 組、確定 1229 回。2026-10-13〜16 の4日分）。`ikari-eval --ranker full`（LM なし、文脈なし）を、空の学習と、学習ファイルのコピーの2通りで流し、確定した表記の順位を見た。

| 項目 | 値 |
| --- | --- |
| 確定の回数 | 1229 |
| そのうち、前と同じ (読み, 表記) の確定（読みの完全一致のキャッシュのヒットの上限） | 358（29.1%） |
| 同じ読みで2通り以上の表記を確定した読み | 29 読み（61 組）。キャッシュは「どちらを出すか」を決められない |
| 確定した表記が1位（確定で重み付け）: 空の学習 → 今の学習 | 972 → **1112**（79.1% → 90.5%） |
| 同じ (読み, 表記) の2回目以降の確定のうち1位: 空の学習 → 今の学習 | 302 → **335**（358 のうち。93.6%） |
| 今の学習でも1位でない組（871 のうち） | 94。内訳: 同じ読みで別の表記も選んでいる 32、1回しか選んでいない 55、2回以上選んだのに1位でない 7 |
| 31 位より後ろ（§1.2 の穴）にある組 | 3（0.3%）。確定の回数では 4 回 |
| 変換の時間（LM なし、convert〜1ページ目） | warm p50 0.095ms、p99 0.341ms（学習あり。空の学習では p99 0.282ms） |

読み取れること:
1. **ヒットの上限（29%）のうち、9割強は今の学習で既に1位**。完全一致のキャッシュで新しく1位にできるのは、多くて残りの 23 回（確定の 1.9%）で、その中には同じ読みで別の表記も選んでいるもの（キャッシュも決められない）が含まれる。
2. **今の学習で1位にならない組の多くは、1回しか選んでいない組（55）**。1回で1位に固定するのは ADR 0013 案 E（不採用）か、学習の重みの調整（ADR 0013 の A1-9 で「1回で切り替わるのが煩わしくないか」を確かめている最中）の話で、キャッシュを足す話ではない。
3. **確定した表記が正しいとは限らない**（レビューの注意点のとおり）。31 位より後ろの3組を1つずつ見た（空の学習、`ikari convert`）。(i) 1組は、ADR 0011 で直す前の誤変換（携帯素解析 の型）を確定したものと見られる。今の変換は正しい表記を1位に出す。(ii) 1組は数字のあとの助数詞（1 + いと → 位と）で、左文脈に数字を入れると1位になる（文脈なしで測ったので後ろに出ただけ）。(iii) 1組は tasks.md の様子見の件（いいか → 位以下）と同じ読みと表記で、2回確定されている。数字を左文脈にしても上位4件に出ない。意図した確定か誤りかは、データからは分からない。学習は1回の確定では1位に固定しないので、(i) を1位に出していない。**キャッシュで1位に出すと、(i) のような直した誤りを戻す**。
4. **§1.2 の穴（プールの外）は 3 組（0.3%）**。うち1組は文脈があれば穴に落ちず、1組は誤確定と見られる。今は直す価値が小さい。
5. **速さ**: LM なしの変換は p99 で 1ms 未満（NFR-02 の 16ms に対して十分）。キャッシュで速くなる余地はない。遅いのは LM（読み1文字 6ms、30〜300ms の締め切りに間に合わない）で、これは B36 の問題。

測定の限界（推測で断言しないための注記）:
- 文脈なし・LM なしで測った。実際の確定は文脈ありで、LM が学習のあとで並べ替える（LM は Guard の対象外）。文脈ありなら学習の文脈の特徴量が効くので、学習側の数字は上がる見込みだが、測っていない。
- 「今の学習」は確定したあとの状態なので、1回しか確定していない組では、その確定自身が加点に入っている（楽観側）。
- 学習ファイルは4日分で、smoke の確定（数件）が混じりうる。
- **確定できたのは候補に出たものだけ**なので、このデータから「辞書の候補に出なかった表記」の割合は分からない（生き残りの偏り）。それは §3.3 で別の方法で見る。

### 3.2 段階2: 既にあるものの効きと、残る利得の場所
- 文脈の効き（「文脈なし比」）は ADR 0015 §0.6 で測ってある: homophones-ext 1266 件で、**文脈なし 48.2% → 直前の文脈あり 86.3%（LM あり）**、LM なしで 598 → 979。段階2の部品（文書内キャッシュ、話題、学習の特徴量）を含めた、今の構成の値。
- 同じ測定で、**利得の大半は「直前の文脈が届くかどうか」**だった。今それを失っているのは、履歴が切れる（P1）と、空を「取れた」とする（P2）こと。直すのは B28 の D1・D2・D5（ユーザーの回答待ち）。
- つまり段階2として新しく作るものより、**B28 で文脈を届ける方が、測れている利得が桁違いに大きい**。段階2の部品（キーワード、選択、専門用語）を足しても、文脈が届かなければ効かない。
- 段階2で本当に足りないものは2つだけと見る（どちらも測っていない）:
  1. **自分の文章での評価**。今の評価セットは LLM の下書きと手作りで、ユーザーの実際の入力の分布ではない。学習ファイルは文脈を持たない（NFR-19）ので、文脈つきの再生はできない。既にある手段は **取り込みの評価用の2割（`ikari-eval --ingest-holdout`）**: ユーザーが自分の文章を取り込めば、その文章の 2 割で、文脈つきの1位を測れる。実機の取り込みの台帳（`ingest_sources.tsv`）は見出しだけで、学習ファイルにも `initial` 層の行はない（取り込みはまだ使われていない）。
  1'. **測定の結果（2026-10-16。自分の文章 9 本。本文は載せない）**。公開済みの自分のブログ記事からコード・URL・表などを除き、538 文に LLM で読みを付けた（取り込めたのは 536 文。辞書で読みを再現できず落ちたのが 91 文）。位置合わせできた 445 文のうち、評価用の 2 割 90 文から 542 ケース、初期学習に 351 文を使った。LM なし、文脈は文書内のみ。同じ入力で 2 回流して数字は一致した。

     | 構成 | 1位正解 | 1位正解率 | MRR |
     | --- | --- | --- | --- |
     | cost（辞書のコストだけ） | 426 | 78.6% | 0.866 |
     | doc（左文脈、かな表記、文書内キャッシュ） | 431 | 79.5% | 0.873 |
     | full（取り込みなし。初期学習の行を除いたコピー） | 446 | 82.3% | 0.888 |
     | full（取り込みあり） | 455 | 83.9% | 0.897 |

     - 取り込みだけの寄与は **+1.6 ポイント（9 ケース）**。doc から取り込みなしの full への +2.8 ポイント（プロファイル、トピック、usage の学習など）のほうが大きい。
     - 限界: 評価用と初期学習用は同じ記事から取った 8:2 なので、話題と語彙が近く、楽観側。LM なし。読みは LLM が付けたもので、人の確認はしていない。ケース数が 542 で、差は小さい。B28 の前後の比較は、同じファイルで測れる。
  2. 文末の文体（です・ます、だ・である）の扱い。同音の候補の並べ替えに関わる場面が少ないと見るが、測っていない。

### 3.3 候補の集合の天井（「候補は辞書から」を変える価値の上限）
段階1・2はどちらも**並べ替えの中**の話で、「候補は辞書から作る」を変えない。方針を変える価値があるかは、「辞書が正解を候補に出せていない割合」で決まる。`ikari-eval reach`（上位 50 件に正解が出るか）と、`ikari-eval --ranker full --max-rank 300` の順位で見た（文脈は各セットのとおり）:

| セット | 件数 | 1位（LM なし、full） | 上位 50 に出ない（`reach`） | 31 位より後ろか候補にない（LM が並べ替えられない） |
| --- | --- | --- | --- | --- |
| homophones-ext | 1266 | 979 | 0 | 0 |
| rare-homophones | 77 | 50 | 0 | 0 |
| hiragana | 140 | 136 | 0 | 0 |
| new-words | 71 | 61 | 1（推し活） | 3 |
| verbs | 121 | 71 | 1 | 1 |
| AJIMEE（1文が数十文字。LM なし、`--max-rank 300`） | 200 | 48 | （300 位までに出ない 49） | **80（40%）** |

- 「31 位より後ろ」は並べ替えたあとの順位で数えた（LM が受け取る最初のプールは、辞書の候補の上位 30 件＋かな＋Rewriter。辞書の順とは少しずれる）。AJIMEE は、LM あり（締め切り 300ms）で 51.0%（[phase1-ajimee.md](../../eval/reports/phase1-ajimee.md)。当時の辞書）で、最初のプールに入る 60% に近い。
- 短い入力（こまめに確定する使い方）では、**正解はほぼ必ず辞書の候補にある**。足りないのは並べ替え（文脈、LM の締め切り）。
- 長い入力（AJIMEE）では、正解の 40% が最初のプールの外か候補にない。ここは辞書の候補の作り方の天井で、LM で候補を作れば上がりうる。ただし長文はコンセプトの外（user-feedback §1.3。長文のために仕組みを複雑にしない）。
- 新語（推し活）は、候補を作る話ではなく辞書の話（ADR 0012、ユーザー辞書）。

## 4. 決定（提案）

| 段階 | 推奨 | 根拠 |
| --- | --- | --- |
| 段階1（読み → 表記のキャッシュ） | **新しい仕組みとしては作らない** | 保存と並べ替えは学習ストアが既にしている（§1.1）。足りない部分（接頭辞の補完、1位に固定）は FR-06・FR-08 と ADR 0013 案 E の不採用に反する（§2）。実データで、完全一致のヒットの9割強は今の学習で既に1位、残りは確定の 1.9% 以下で、その中には誤確定と見られるものが混じる（§3.1）。速さの利得はない（LM なしで p99 < 1ms） |
| §1.2 の穴（プールの外の学習済みの表記） | **今は直さない**。記録だけ残す | 0.3%（3 組）で、1組は文脈があれば穴に落ちず、1組は誤確定と見られる。直すなら、学習済みの表記を辞書の経路で作り直して最初のプールに入れる形（読みに対応し、候補は辞書から、を守る）。§7 の Q2 |
| 段階2（確定文から語・文体・キーワードを持ち、順位に使う） | **新しくは作らない。B28 を先に進める** | 部品は全部ある（§1.1）。測れている利得の大半は文脈が届くかどうかで、それは B28（§3.2）。確定文を保存して抽出する形は NFR-19 に反する（§2） |
| 段階2の測り方 | **まず測る**: 自分の文章での評価（`--ingest-holdout`）を、B28 の実装の前後で取る | 今の評価セットはユーザーの入力の分布ではない（§3.2-1）。測る道具は既にある。足りないのはユーザーの文章（ユーザーにしか用意できない） |
| 段階3 | **B36 にまとめる**。方針を変えるかは、B36 の ADR で実測してからユーザーに聞く | §6 |

一文で: **段階1・2は ikari に既にある（学習ストア、文書内キャッシュ、取り込み、プロファイル）。新しく作る価値は測った範囲で小さく、一部は要件に反する。利得が大きいのは B28（文脈を届ける）と B36（LM を締め切りに間に合わせる）で、構想の段階3は B36 の中で測る。**

## 6. 段階3に進む判断材料（短く）

### 6.1 段階3が現行方針を変える点
| 点 | 今の決定 | 段階3で変わりうること |
| --- | --- | --- |
| 候補の出どころ | 候補は辞書から。LM は並べ替えだけ。LM に読みから文字列を作らせて候補に足す案は取り下げ済み（user-feedback §1.3） | 生成した文の表記を候補に足すなら、この決定を変える。**辞書で読みを再現できた表記だけを使う**（取り込みの強制アライメントと同じ検査。ADR 0002 §11.3）なら、候補は辞書のままで、変わらない |
| モデル | zenz-v3.2 small のみ。足す・替える余地は残す（2026-10-16） | 文を作る汎用の SLM は zenz（かな漢字変換のモデル）と役が違うので、**モデルを足す**ことになる。ADR で実測してユーザーに聞く |
| 予測 | FR-08（次語予測をしない） | 予測した文を「次に出す候補」にすると反する。**並べ替えの手がかりにだけ使う**なら、B36 の C と同じで反しない |
| 資源 | NFR-11（アイドル時はモデルを解放）、NFR-12・13（重い処理は入力を優先、電源接続中） | アイドル時に生成し続けるのは NFR-11 と逆向き。いつ・どれだけ回すかを決める必要がある |
| 原文 | NFR-19 | 生成した文を保存するなら、それはユーザーの文脈から作った文。保存の形を決める必要がある |

### 6.2 段階3の利得の天井（§3.3 から）
- 短い入力では、正解はほぼ必ず辞書の候補にある。**段階3が効くとすれば、並べ替え（どの候補を1位にするか）**で、それは B36 の C と同じ。
- 候補を足すことで上がるのは長い入力（AJIMEE で 40%）だけで、コンセプトの外。
- したがって「候補は辞書から」を変える価値は、測った範囲では**短い入力ではほぼない**。変える判断は、長文の扱いを変える判断とセットになる。

### 6.3 安く測る方法（コードを変えない。B36 で使える）
生成した文を、既存の**取り込み**（`ikari ingest run`。JSONL に表記と読み。強制アライメントで辞書で読める文だけを `initial` 層の学習にする）に流し、評価セットと `--ingest-holdout` の前後を比べる。これは「生成した文を、辞書で読める範囲で順位の手がかりにする」段階3の安全な形と同じ効果を、コードなしで見られる。生成する文の題材と、使う LLM（ローカルかクラウドか。NFR-28 の注意）はユーザーが決める（§7 の Q5）。

## 7. ユーザーに聞くこと

### Q1. 段階1を新しい仕組みとして作らない、でよいか
- 背景: 読み → 表記の保存は学習ストアが既にしていて、並べ替えにも使っている。構想の新しい部分は「接頭辞で引いて続きを出す」（FR-06・FR-08 に反する）と「ヒットしたら1位」（ADR 0013 案 E。測って不採用）。
- 実データ（4日分、確定 1229 回）: 同じ読みと表記の2回目以降の確定は 29%。そのうち 94% は今の学習で既に1位（文脈なし・LM なし）。
- 選択肢: (a) 作らない（推奨）、(b) 完全一致だけのキャッシュを試作して測る（学習と同じものになる見込みで、新しい情報は少ない）。

### Q2. プールの外の学習済みの表記（§1.2）を直すタスクを積むか
- 背景: 辞書の候補の 31 位より後ろの表記は、何回選んでも1ページ目に上がらない（コードの構造）。
- 例: 4日分の学習で 3 組（0.3%）。1組は数字の文脈があれば1位になり（1 + いと → 位と）、1組は直す前の誤変換（携帯素解析 の型）を確定したものと見られる。
- 選択肢: (a) 積まない（推奨。小さく、誤確定を上げる側にも働く）、(b) C（後の工程）に記録だけ残す、(c) 今直す。

### Q3. 段階2は新しく作らず、B28（文脈の読み取り。ADR 0015 の Q1〜Q10）を先に進める、でよいか
- 背景: 文脈が届くと 48% → 86%（homophones-ext、LM あり）。段階2の部品（キーワード、選んだ結果、専門用語、分野）は全部ある。
- 選択肢: (a) B28 を先に（推奨）、(b) 段階2の部品の調整を先に（何を調整するかの根拠がまだない）。

### Q4. 自分の文章での評価を用意してもらえるか
- 背景: 段階2（と B28、B36）の効きを、ユーザーの実際の文章で測る道具（`ikari ingest run` と `ikari-eval --ingest-holdout`）は既にある。足りないのは、ユーザーが書いた文章の取り込みファイル（表記と読みの JSONL。プロンプトは `ikari ingest prompt`）。原文はユーザーの管理するファイルにだけ残る。
- 選択肢: (a) 用意する（推奨。分量と題材はユーザーが決める）、(b) 今は用意しない（評価は今のセットのまま）。

### Q5. 段階3は B36（LM の先読み。ADR 0021 予定）にまとめ、B36 の中で「生成した文を取り込みで学習に入れて測る」安い試作（§6.3）をするか
- 背景: 段階3の「先読み生成した文を順位に使う」は、B36 でユーザーが選んだ C（次に打つ言葉の予測を、候補を足さず順位にだけ使う）と同じ。候補を足す形は、短い入力では天井がほぼない（§3.3）。
- 決めてほしいこと: (i) まとめてよいか（推奨: まとめる）、(ii) 試作で文を作る LLM（ローカルの SLM／クラウドの LLM。クラウドなら業務の文章は送らない）と題材（よく書く分野）。モデルを足すかどうかは、B36 の ADR で実測してから改めて聞く。

### Q6. 学習に残っている誤確定の扱い
- 背景: 確定した表記が正しいとは限らない（§3.1-3）。今の学習は1回の確定では1位に固定しないので、害は出ていない。学習の管理（設定アプリ、`ikari learn`）で個別に消せる。
- 選択肢: (a) 何もしない（推奨。学習の原則が守っている）、(b) 気になる表記があれば、ユーザーが学習の管理で消す（Claude はユーザーデータを書き換えない）。

## 8. 再現（捨てるスクリプト。コミットしていない）
1. `cargo build --release -p ikari-eval`。辞書は `data/build/dict`（main 7c552a5 時点のビルド）。
2. 学習ファイルを scratchpad にコピーする（ユーザー辞書、プロファイル、設定も。元のファイルは読むだけ）。
3. usage 層の phrase の行のうち、feature が `0000000000000000`（Unconditional）の行を (読み, 表記, 回数) にし、`ikari-eval` の TSV（文脈は空、`expected` = 表記、`tags` = 回数）に書き出す。
4. `ikari-eval --ranker full --set <set> --include-unreachable --repeat 1 --max-rank 300 --out-cases <out>` を、`--user-dir` なし（空の学習）と `--user-dir <コピー>` で流し、順位を比べる。
5. 候補の集合の天井: `ikari-eval reach --set eval/sets/<name>.tsv`、AJIMEE は `ikari-eval --set-format ajimee --ranker full --repeat 1 --max-rank 300 --out-cases <out>` の順位の分布。

## 9. 結果（承認された。2026-10-23）
- ユーザーの決定: Q1 (a) 作らない、Q2 (a) 積まない、Q3 (a) B28 を先に、Q4 (a) 自分の文章の取り込みファイルを用意する（分量と題材はユーザーが決める）、Q6 (a) 何もしない。
- コードは変えない。段階1・2のために新しい概念（キャッシュ、Trie）を足さないので、Ranker の構成と学習の形式はそのまま。
- 段階3の検討は B36 に移り、方針（候補は辞書から、LM は zenz small のみ）の見直しは、B36 の実測とユーザーの判断を待つ。
- 失うもの: 長い入力で辞書が候補に出せない正解（AJIMEE の 40%）は、この判断では取りにいかない（コンセプトどおり）。
