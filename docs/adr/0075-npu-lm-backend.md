# ADR 0075: Intel NPU（Core Ultra）で LM を動かす道と、会社 PC で手で動かす測定ツール

- 状態: 承認
- 日付: 2026-11-16（提案）、2026-11-16（承認。§10。撤退の基準の値は仮置きのまま）
- 対象: `lm`（`LmScorer` の新しい実装、`LmDevice`、モデルの形式）、`ikari-lm-host`（子。檻の段 1・段 2）、配布物（ランタイムの DLL とモデルの形式）、CI（Windows のビルドに OpenVINO を足す）。この ADR ではコードを変えない
- 前提: `feat/security-impl2` = 0bd7822。ADR 0042（判断は Rust）、ADR 0059（Windows は Vulkan。N150 の内蔵 GPU で p50 175ms、CPU 433ms）、ADR 0060（モデルの profile、Q4 の別プロセス）、ADR 0065（自己診断の下限 X）、ADR 0072（檻の段。製品のエンジンに llama.cpp を入れない §5）、ADR 0074（推論の取り消し）、spec NFR-17（子は通信しない）。CLAUDE.md の「モデルを足す・替えるときは、ADR で実測して、ユーザーに聞いてから決める」
- 判断の置き場所: Rust（`lm` の新しい scorer と、ikari-lm-host の装置の選択）。Swift と Windows の殻に足す判断はない
- この ADR は「NPU を使う」と決めるものではない。**実測の道具と順番と撤退の基準を決め、数字を見てから採否を決める**ためのもの

---

## 1. 現状（分かったこと）

- LM は zenz-v3.2-small（GPT-2 系、約 90M、GGUF Q5_K_M 74MB、cc-by-sa-4.0）。推論は別プロセス `ikari-lm-host` の中の llama.cpp（`lm/src/llama.rs`、`llama-cpp-2` 0.1.159）。Windows は Vulkan（feature `vulkan`、動的バックエンド）、macOS は Metal。
- 採点の形（`lm/src/llama.rs` の `nll`）: 左文脈と読みのプロンプト（最大 512 トークン）を 1 度 decode し、KV キャッシュを候補ごとの列に複製して（`copy_kv_cache_seq`）、候補（各 96 トークン未満）をまとめて decode する。**生成はしない**。必要なのは「プロンプト + 候補」の各位置の確率だけ。
- 境界: `LmScorer::nll(prompt, candidates, cancel) -> Vec<f32>`、`LmDevice { Unknown, Cpu, Gpu }`（`lm/src/scorer.rs`）、`ModelKind { ZenzV3, KanakanjiEdge }`（`lm/src/config.rs`。プロンプトの形式だけを表す）、親の側の `HostScorer`（`lm/src/host/scorer.rs`。子との取り決め）。
- 実験の機械: 作者の会社 PC（Intel Core Ultra 系、メモリ 18GB、DirectX 12 FL1.0 のコンピューティング、NPU あり）。**私用では使えないが、自作ツールの導入は許されている**。ほかに NPU のある機械はない（VM は N150 で NPU なし）。
- researcher の調べ（一次の文書。2026-11-16）:
  - llama.cpp に OpenVINO バックエンドがある（`ggml/src/ggml-openvino`、`docs/backend/OPENVINO.md`）。GGUF のまま CPU・GPU・NPU。「作業中」。NPU は stateless だけ。量子化は Q4_0 が主で、Q5_K は実行時に Q8_0_C へ変換、Q6_K は Q4_0_128 へ再量子化。検証済みの表は Llama・Qwen 系で、GPT-2 系は載っていない。未マージの PR が多く、open の issue にメモリの増加（#31129）、モデル非対応（#32291）。
  - OpenVINO の NPU プラグイン: 計算の精度は FP16、量子化は U8、NPU のドライバが要る、コンパイル済みのブロブはドライバと版をまたいで互換が保証されない、モデルのキャッシュが既定で有効、**静的な形が前提**（動的な形の扱いは未確認）。
  - Windows ML は OpenVINOExecutionProvider を EP に挙げる。ORT の OpenVINO EP で NPU を使う条件は未確認。
  - 第三者の zenz の ONNX は v2.5 まで（akku1139/zenz-v2.5-*-onnx）。v3.2 の ONNX・IR は無い。
  - NPU が今の Vulkan より速いという根拠は見つかっていない。

## 2. 問題

- Windows で LM が快適に動く機械を広げたい（ADR 0065 の下限 X。CPU だけでは遅い）。Core Ultra には NPU と内蔵 GPU（Arc）がある。内蔵 GPU は Vulkan ですでに使える。**NPU を足す意味があるのは、NPU が Vulkan より速いか、同じ速さで電力や GPU の取り合いが少ないときだけ**。
- **推測**: 90M のモデルを短い文脈で 1 回ずつ動かす使い方では、NPU は呼び出しの固定費（転送、同期）が勝って、内蔵 GPU より速くならない見込みがある。逆に、静的な形で一度にまとめて流せば、固定費は 1 回で済む。どちらかは測らないと分からない。
- 測れる機械は会社 PC 1 台で、エージェントは触れない。ユーザーが手で 1〜2 回動かして、結果のテキストを貼る形にしないと、実測が始まらない。

## 3. 候補の比較

採点に要るのは「固定の長さの列を 1 回流して、各位置の確率を得る」ことだけで、生成のループも KV キャッシュも要らない（§1）。これが NPU の「stateless・静的な形」と相性がよい。比較の軸はこの点を中心に置く。

| 軸 | A: llama.cpp の OpenVINO バックエンド | B: ONNX Runtime + OpenVINO EP（または Windows ML） | C: OpenVINO を直に使う |
|---|---|---|---|
| モデルの変換 | 要らない（GGUF のまま） | 要る（HF の重み → ONNX。v3.2 は自前で書き出す） | 要る（HF の重み → OpenVINO IR。`ov.convert_model` または optimum-intel） |
| zenz の数値の一致の確かめ方 | 同じ `nll` のまま、装置だけ替えて CPU の llama.cpp と比べる | 書き出した ONNX を CPU で流して llama.cpp と比べ、次に NPU と比べる（2 段） | B と同じ 2 段。OpenVINO の CPU を中間の基準にできる |
| NPU の制約との相性 | **悪い見込み**。NPU は stateless だけで、今の `nll` は KV の複製と複数の列に頼る。GPT-2 系は未検証。Q5_K_M は Q8_0_C に変わる（重みの数値が変わる） | 形を固定して書き出せば合う。EP が NPU で全部を受けるかは未確認（一部が CPU に落ちると遅い） | **よい**。形（列の数 B × 長さ T）を固定した IR を作り、KV なしで 1 回流す。FP16 か INT8 の重みを選べる |
| 配布物とドライバ | llama.cpp の OpenVINO 版 + OpenVINO の DLL 一式。NPU のドライバ | ORT の DLL + OpenVINO EP（中で OpenVINO の DLL 一式）。Windows ML なら EP を OS が取りにいく（通信。版を ikari が決められない） | OpenVINO の DLL 一式（CPU・GPU・NPU のプラグイン、TBB）。NPU のドライバ。モデルは IR（FP16 で約 180MB、INT8 で約 90MB。**推測**、重みの数からの見積もり） |
| 檻（ADR 0072）との関係 | 今の子にそのまま乗る | 子の中で動く。Windows ML の取得の道は NFR-17・段 2 と合わない | 子の中で動く。子が使う DLL が増えるだけ |
| メンテの見通し | 上流が「作業中」で、未マージの PR と open の issue が多い。`llama-cpp-2` に feature が無く、自前でビルドの道を足す | ORT と OpenVINO の 2 つの版を追う。Intel の NPU だけのためなら層が 1 つ余計 | OpenVINO の 1 つを追う。Rust からは C API（`openvino` crate。実行時に読み込む形がある）。トークン化は別に要る（§3.1） |
| ikari のコードへの影響 | `lm` の feature とビルドを足す。`nll` は NPU 向けに書き直しが要る見込み | 新しい `LmScorer`。ONNX の書き出しの道具 | 新しい `LmScorer`（`nll` の中身だけ。境界は今のまま）。`LmDevice` に `Npu`。モデルの profile に「形式」（GGUF / IR） |

### 3.1 トークン化と ModelKind

- `ModelKind` はプロンプトの形式だけを表す（§1）。NPU でも zenz-v3 の形式は同じなので、`ModelKind` は変えない。違うのは**モデルの形式と装置**で、これは ADR 0060 の profile（モデルごとの差を 1 か所に集める）に「形式」を足して表す。
- C と B は、トークン化を llama.cpp の外でする必要がある。スパイクでは、GGUF を語彙だけで読み（llama.cpp の vocab-only の読み込み）、今と同じトークン列を作る。トークンが一致することを先に確かめれば、スコアの差は推論の差だけになる。製品で llama.cpp を残すか（子の中だけなので ADR 0072 §5 には反しない）、Rust でトークン化を持つかは、採用が決まってから決める。

### 3.2 推奨

**C（OpenVINO を直に使う。形を固定した IR、KV なしで 1 回流す）を本命にし、A は「同じ GGUF で NPU に載るか」を安く見る副の測定として 1 回だけ試す。B は採らない。**

- 理由: 採点の形（生成なし、固定の長さで 1 回）が NPU の前提（stateless、静的な形）に素直に合うのは C。Intel の NPU だけが目的なら、ORT は OpenVINO の上に層を 1 つ足すだけで、得るもの（ほかの会社の NPU）は今の範囲の外。Windows ML の EP の取得は、ikari の「通信しない」と合わない。
- A は変換が要らない点が魅力だが、今の `nll`（KV の複製）は NPU の stateless と合わない見込みで、上流も固まっていない。「載るか」だけ見て、載らなければそれで閉じる。
- C の代償: モデルの書き出し（HF の重み → IR）と、トークン化を外に持つこと、モデルが 2 形式（GGUF と IR）になること。**NPU が Vulkan に勝つ数字が出たときだけ払う**。

## 4. スパイク: 会社 PC で手で動かす測定ツール `ikari-npu-probe`

### 4.1 形

- 1 つのフォルダの zip（インストーラなし、管理者の権限なし）。中身は `ikari-npu-probe.exe`、OpenVINO の DLL 一式、llama.cpp の DLL（CPU と Vulkan）、測定の 40 件（`tools/npu-probe/fixtures/`）、README（手順）。
- モデルは別の zip: zenz-v3.2-small の GGUF（Q5_K_M。今の製品と同じ）、IR（FP16 と INT8。形は `[1, 128]` と `[32, 128]` の 2 つで、計 4 組。`tools/npu-probe/README.md` の「契約」）。**渡し方は Google ドライブ経由の zip**（2026-11-16 ユーザー決定。USB は使わない）。作者の私物の機械で zip を作って Google ドライブに置き、会社 PC で取る。zip の sha256 を手順書に書き、会社 PC で照らす（`certutil -hashfile … SHA256`）。モデルは cc-by-sa-4.0 で、Google ドライブは作者だけが見られる置き場にする（公開の再配布にしない）。ツールの zip も同じく Google ドライブ経由で渡す（2026-11-16 ユーザー決定。「zip を Google ドライブ経由で渡す」）。
- ツールは**通信しない**: ネットワークの API を呼ばず、URL を持たない。OpenVINO のテレメトリは、ランタイムの一式に含めない・無効にする（**未確認**。ビルドの時に確かめる。§8）。
- 書くのはツールのフォルダの中だけ: 報告（`report.txt`）、OpenVINO のモデルのキャッシュ（`CACHE_DIR` をツールのフォルダの `cache\` に向ける）。

### 4.2 入力

- `eval/sets/homophones-ext.tsv` から、文脈の長さが散らばるように 40 件（固定）。各件の候補は、今の変換が LM に渡す候補を事前に取り出して埋める（会社 PC で辞書を読まない）。取り出したもの（プロンプト、候補、トークン列、llama.cpp CPU の NLL）は `tools/npu-probe/fixtures/homophones-40.jsonl`。1 件の候補は 30〜32 個、40 件で 1233 個。
- 形（IR の固定の形）: **`input_ids` i64 `[B, 128]` → `logits` f32 `[B, 128, 6000]`、B = 1 と B = 32 の 2 つ**（2026-11-16。T = 128）。1 行 = プロンプト + 候補 1 つを左から詰め、右の残りは `[PAD]` で埋める（GPT-2 は因果なので、右の詰め物は採点の位置に影響しない。attention_mask は持たない）。B = 1 は 1 件で約 31 回、B = 32 は 1 件で 1 回（余りの行は `[PAD]` だけで、出力を読まない）。40 件の `プロンプト + 候補` の最長は 66 トークンで、128 は約 2 倍の余裕。会社 PC の 1 回で B = 1 と B = 32 の両方を測る（リード決定 2026-11-16）。詳細は `tools/npu-probe/README.md` の「契約」。

### 4.5 手順（README に書くこと）

1. 確認だけ（何も入れない）: デバイス マネージャーの「ニューラル プロセッサ」に Intel の NPU（Intel(R) AI Boost）があり、警告が無いこと。**NPU のドライバは入れない・更新しない**（会社 PC の管理の範囲。無ければ NPU の行は「ドライバなし」で終わる。ほかの行は測れる）。
2. Google ドライブから zip を 2 つ取り、sha256 を照らして、任意のフォルダ（例: `%USERPROFILE%\Desktop\ikari-npu-probe`）に展開する。
3. `ikari-npu-probe.exe` を実行する（ダブルクリック可）。所要時間の目安は 10〜20 分（**推測**。NPU のコンパイルが形ごとに数十秒かかる見込み。B = 1 では 1 件に約 31 回流すので、遅い装置ではもっとかかる）。途中で 1 回、自分をもう一度起動する（キャッシュありの初回を測るため。§4.4）。AppContainer の項目を外すときは `ikari-npu-probe.exe --no-appcontainer`（プロファイルを作らない）。
4. 終わったら、画面の要約（10 行前後。§4.4）を目で読んで書き写す。詳細のファイルは持ち出さない。
5. 消す: `ikari-npu-probe.exe --cleanup`（AppContainer のプロファイルを消す。§6）のあと、フォルダを丸ごと削除。ツールはレジストリ、サービス、スタートアップ、PATH に何も書かない（AppContainer のプロファイルの登録だけが例外で、`--cleanup` で消す）。**推測**: NPU のドライバ自身がどこかにキャッシュを持つかは未確認。README には「消したあとに残るものは未確認」と書く。

### 4.6 作る側（エージェント）

- 置き場所: 捨てるコードとして、`spike/npu-probe` ブランチの独立したクレート（ワークスペースに入れない）。製品の `lm` には足さない。
- モデルの書き出し: Python（`openvino`、`optimum-intel`）で HF の zenz-v3.2-small を IR にする。版を固定した 1 回だけの作業で、出来た IR の sha256 を記録する。CI でなく手元の Mac でよい（IR は機械に依らない）。
- ビルド: Windows の CI（`windows-latest`）で、手で起動する専用の job。OpenVINO の Windows 用のアーカイブ（zip）を、版と sha256 を固定して取り、DLL を zip に入れる。Rust からは `openvino` crate を実行時に読み込む形で使えば、ビルドの時に SDK が要らない（**未確認**。要るなら CI に展開して `OPENVINO_*` を指す）。llama.cpp の OpenVINO バックエンド（A）は、上流の llama.cpp を cmake で別にビルドする（`llama-cpp-2` に feature が無いため）。手間の見積もり: C の部分が job 1 本と 1〜2 日、A を足すと半日〜1 日（通らなければ打ち切る）。**推測**。
- 確かめ: `ov-cpu` と `llama-cpu` の一致は、CI（Windows）と手元の Mac で先に通しておく。会社 PC で試すのは NPU と GPU だけが新しい状態にする。

#### 4.6.1 変換と Mac での確かめ（2026-11-16。済み）

- 置き場所: `tools/npu-probe/`（変換と確かめの Python は `convert/`、40 件は `fixtures/`、入出力・トークン化・NLL の詰め方の取り決めは `README.md` の「契約」）。モデルの実物と IR はリポジトリに入れない（`.gitignore`）。
- 変換の道: GGUF（Q5_K_M）→ transformers の GGUF 読み込み（FP32 に戻す）→ `torch.export` → `ov.convert_model` → 形を `[1, 128]` または `[32, 128]` に固定 → FP16（重みの圧縮）と INT8（NNCF の重みだけの圧縮）。TorchScript の trace は transformers 5 のマスクの組み立てで落ちたので使わない。
- 大きさ: IR の FP16 は 189MB、INT8 は 95MB（§3 の表の推測とおおむね同じ）。形は B = 1 と B = 32（ともに L = 128）。sha256 は作り直すたびに変わるので、zip の `SHA256SUMS` を正とする。
- 数値（40 件、候補 1233 個、`llama-cpu` を基準に）: 1 位の一致は FP16・INT8、計算 f32・f16、B = 1・32 のすべてで 40/40。B = 32 は B = 1 と同じ値（詰め方は正しい）。τ の中央値 0.982〜0.987。|NLL の差| の中央値 0.135〜0.184、最大 1.27〜2.05。IR と HF（torch、FP32）の差は中央値 0.001 で、書き出しは正しい。llama.cpp との差は、llama.cpp の CPU の量子化したままの計算と、FP32 に戻した計算の差と見る（**推測**）。
- 所要（参考。Mac の CPU）: 1 件の p50 は B = 1 で 1.1〜2.1 秒、B = 32 で 0.8〜1.8 秒（llama.cpp の CPU は 38ms）。KV なしでは候補ごとにプロンプトを計算し直し、全位置の logits を出すので、計算の量が llama.cpp の 20 倍を超える（**推測**）。B を上げて減るのは呼び出しの固定費だけ。

## 5. 実測の順番と撤退の基準

順番（会社 PC での 1 回目で全部を出すが、読む順はこれ）:

1. **載るか**: `ov-npu` がコンパイルと 1 回の推論に通るか（FP16 と INT8、形ごと）。`llama-ov-npu` が通るか。
2. **速さ**: `ov-npu` の暖機のあとの p50・p99 を、同じ機械の `llama-vulkan` と比べる。初回（コンパイル込み）とキャッシュありの初回。
3. **順位の一致**: `llama-cpu` との 1 位の一致と τ。
4. 1〜3 が通ったときだけ、製品の評価（全セットで 1 位が悪化しない。`eval/scripts/snapshot.sh`）を、IR を `ov-cpu` で流して確かめる（会社 PC は要らない）。

撤退の基準（**値はすべて仮置き**。結果を見てユーザーが決める）:

- `ov-npu` が、どの形でも通らない → NPU は閉じる（Vulkan のまま）。
- 暖機のあとの p50 が、同じ機械の `llama-vulkan` より速くない（仮置き: 0.8 倍以下でなければ）→ NPU は採らない。
- キャッシュありでも、初回が 2 秒を超える（仮置き）→ 起動の直後の体験が悪いので採らない（ブロブがドライバの更新で無効になる点も重くみる）。
- 1 位の一致が 95% 未満（仮置き）、または §5 の 4 で 1 位が悪化 → INT8 なら FP16 で測り直し、それでも駄目なら採らない。
- 檻（§6）: 段 1（低い整合性）で NPU が使えない → 段 1 から外す価値があるほどの速さでなければ採らない。
- A（`llama-ov-npu`）: 通らない、または Q5_K_M の変換で一致が落ちる → A は閉じる（C に影響しない）。

分かった事実（2026-11-16、Mac。§4.6.1）:

- GGUF → HF → IR の変換は通った（撤退の理由にならない）。つまずいたのは TorchScript の trace だけで、`torch.export` で回避した。
- 一致は Mac の CPU で基準を満たす（1 位 40/40。基準は 95%）。NPU（計算 f16）での一致は、Mac の CPU の f16 計算で 40/40 だったが、NPU の実物では未確認。
- KV なしの IR は、Mac の CPU で llama.cpp の 20〜55 倍遅い（B = 1 でも B = 32 でも）。NPU が Vulkan の 0.8 倍以下に届くには、NPU の演算の速さが CPU よりずっと上である必要がある（**推測**）。届かなければ、撤退の前に、計算を減らす形（プロンプトを 1 回だけ流す KV ありの IR、出力を要る位置だけに絞る IR）を試すかをユーザーに聞く。

## 6. セキュリティの見立て

- NPU を使うには、子（`ikari-lm-host`）が NPU のドライバ（ユーザーモードの DLL と、カーネルのドライバへの口）に触れる必要がある。檻の段 1 は低い整合性、段 2 は AppContainer（能力なし）（ADR 0072 §3）。**低い整合性・AppContainer の中で NPU が使えるかは未確認**。Vulkan についても同じ問いが ADR 0072 §10 に残っている。
- 実験の項目にする: ツールは自分を (a) ふつう、(b) 低い整合性、(c) AppContainer（能力なし。モデルとツールのフォルダにだけ読みの許可を付ける）で起動し直し、各装置で 1 件だけ流して成否を書く。(c) は AppContainer のプロファイルを作るので、`--cleanup` で消す（§4.5）。会社 PC の設定は変えない。
- 攻撃面の見立て（**推測**）: 子から触れるドライバが 1 つ増える（GPU のドライバに加えて NPU のドライバ）。子が乗っ取られた場合（ADR 0066 の敵 E2）、カーネルのドライバの不具合を突く入口が増える。段 2 で NPU が使えないなら、「段 2 のときは NPU を使わない」が自然な線引きになる。OpenVINO の DLL 一式も、同梱の他社の部品として ADR 0070（同梱の部品を版ごとに上げる）の対象になる。
- 通信: OpenVINO のランタイムに、利用状況を送る仕組みが含まれるか（テレメトリ）を、ビルドの時に確かめる。含まれるなら外す。子は通信しない（NFR-17）を変えない。

## 7. 方針との関係

- LM は並べ替えだけ。候補は辞書から。NPU でもこれは変わらない（`nll` の中身が替わるだけ）。
- 「モデルを足す・替える」に当たるか: モデルは同じ zenz-v3.2-small で、形式（IR）と装置が増える。数値は変わり得る（FP16・INT8）ので、同じ扱い（実測してユーザーに聞く）にする。
- Windows 最優先の中の一つ。ただし、Windows 1.0.0 の条件にはしない（Vulkan と CPU で配れる）。

## 8. 懸念と前提

- 会社 PC の NPU のドライバの版と、OpenVINO の版の組み合わせが合わないと、NPU の行が全部失敗する。報告にドライバの版を必ず出し、合わなければ OpenVINO の版を替えた 2 本目を作る（ドライバは替えない）。
- OpenVINO の NPU で動的な形が使えるかは未確認。スパイクは静的な形だけで組む。製品で形を少数に固定すると、長い文脈は切り詰めることになる（今も 512 トークンで切る）。
- OpenVINO の DLL 一式の大きさは未確認（**推測**: 100MB を超える）。製品に入れるなら、配布物が今より大きく増える。NPU のある機械だけに入れる分け方は、採用のあとに決める。
- モデルが 2 形式になると、ADR 0060 の自由指定のモデル（GGUF）は NPU では動かない。NPU はプリセットだけ、が自然な範囲。
- OpenVINO のテレメトリの有無と止め方、`openvino` crate の実行時の読み込みでビルドに SDK が要らないかは、ビルドの時に確かめる。
- 会社 PC で動かせるのは 1〜2 回の見込み。1 回で全部の行が出るよう、失敗しても次の行に進む作りにする。

## 9. 検討した案

- **B（ONNX Runtime + OpenVINO EP）**: 将来ほかの会社の NPU（Snapdragon など）に広げるなら有利。今は Intel の NPU だけが対象で、OpenVINO の上に ORT の版の追跡が増える。採らない（ほかの会社の NPU を対象にするときに見直す）。
- **B'（Windows ML）**: EP を OS が取りにいく。ikari が版を固定できず、通信を伴う。採らない。
- **C'（OpenVINO GenAI）**: 生成のための層（ループ、KV、サンプリング）で、採点には要らない部分が大きい。NPU の静的なパイプラインも生成向け。採らない（Runtime を直に使う C を採る）。
- **A だけで進める**: 変換が要らず、今の経路に乗る。§3 の理由（stateless と KV の複製、GPT-2 系が未検証、上流が作業中）で、本命にしない。副の測定として 1 回だけ試す。
- **会社 PC を使わず、資料の数字で決める**: 90M・短文脈での NPU と内蔵 GPU の比較の数字が見つからない（§1）。測らずに決めない。
