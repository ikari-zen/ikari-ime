## 0. 現状の把握（researcher の調査とコード。確認済み）

分かったこと（ログ）:
- LM なしで返った変換は、全ログ 4,735 変換のうち 11.1%。いちばん大きい理由は `miss=context`（370 回、7.8%）。
- `ctx_change`（req=convert）の直後の convert 145 件のうち、`cache=hit` は 0 件。Space で文脈を読み直して番号が進むと、必ず外れる。
- 左文脈の伸び（dleft）は +1〜+7 字。新しいログ 73 件中 66 件で、dleft が直前の確定の文字数とちょうど一致する。right と available だけが変わった例は 0 件（#1 の再集計）。
- 連打の速さは関係ない（最後の先行計算から convert まで、miss 147ms、それ以外 142ms）。

分かったこと（コード）:
- キャッシュのキーは `(session, reading, context_rev)`（`engine/src/cache.rs` の `CacheKey`）。外れたとき、同じ session に同じ reading があれば `MissReason::Context`（`miss_reason`）。
- 外れたら、Convert の文脈でその場で変換し、**LM は使わない**（`convert.rs` の `convert` の `None =>` の枝）。つまり今の外れは「新しい文脈・LM なし」で返る。
- 番号を進めるのは殻の `refreshContext` だけ（`InputStateMachine.swift`）。読み直すのは、合成の 1 打鍵目、2〜3 打鍵目（`contextRefreshKeystrokes = 3`。#1 の暫定の対策で、すでに入っている）、Space の `startConversion`。
- 殻は、確定（`engine.commitText` / `engine.commit`）を、同じ打鍵の先行計算（`engine.prefetch`）より前にエンジンへ送る（`commitDisplay` → `continueAfterCommit`）。エンジンは確定の文字列を受け取っている（`commit_text`、`commit`。`ctx_trace` は今は文字数だけ覚える）。
- 確定の学習は、その変換の `CommitEvent.analysis`（変換を作ったときの文脈の解析）で記録する（`convert.rs` の `commit`、`core/src/converter/conversion.rs`）。

分かったこと（#1 の測定 (a)、2026-10-28）:
- 評価セットの文脈から「直前の確定の単位」を 1 つ取り除くと、取り除かない場合と比べて、1 位が約 17〜23% 変わる。大半は「期待 → 外れ」（LM あり: 文節の近似で 157 対 12、重み付きで 19.1%。LM なし: 107 対 20、重み付きで 14.4%）。
- ただし、この比較は「古い文脈・LM あり」と「新しい文脈・LM あり」の比較。**今の外れで実際に返っているのは「新しい文脈・LM なし」**で、案 1 と比べるべき相手はこちら（§6）。

推測（未確認）:
- 2〜3 打鍵目で読み直しても left が古いまま（66/73）なので、アプリ（多くは VSCode）が確定を周辺テキストに反映するのが、数打鍵ぶん遅れている。Space（確定の 0.1〜5 秒後）では反映済み。

## 1. 問題の定義

- 本質は、**キャッシュを「文脈の番号」で当てていて、「文脈の中身」で当てていない**こと。番号は「殻が読み直した文字列が前と違った」ことしか表さず、違いが「直前に自分で確定した文字がアプリに遅れて入っただけ」なのか、「別の場所にカーソルが動いた」のかを区別しない。
- そのため、ふつうの速さで「確定 → 次の語を打つ → Space」をすると、約 10 回に 1 回、先行計算（LM つき）を捨て、LM なしで返している。
- 制約: Space の応答は NFR-02（16ms）、待つのは NFR-04 の 30ms まで（ADR 0021 L1）。LM を Space の時点で計算し直す余裕はない。値（伸びの上限など）は計測で決める。変換に手を入れたら、全評価セットで 1 位が悪化しないこと（CLAUDE.md）。

## 2. 決定（案 1。方向は 2026-10-29 ユーザー承認）

**Convert で、キーがちょうど当たらないとき、同じ session・同じ reading の先行計算のうち、文脈が「直前の確定の分だけ左に伸びた」関係にある最新の 1 件を当てる。** 文脈の番号は、この当て方では見ない。

当てる条件（すべて満たすとき。G はガードの略）:
- G1: right と available が先行計算のときと同じ。secure では当てない（今どおり、secure は先行計算そのものをしない）。
- G2: Convert の left の末尾 d 字が、そのセッションの**直前の確定の文字列**と一致する。d は 1 以上、`D_max` 以下。
- G3: Convert の left から末尾 d 字を除いた残りと、先行計算の left が、短いほうの長さで末尾が一致する（殻が left を上限の字数で頭から切るので、頭は比べない）。
- G4: 先行計算が LM つきで終わっている（`lm_applied = true`）か、計算中で `convert_wait` 以内に LM つきで終わる。LM なしで終わった先行計算は当てない（測定 (a) の LM なしの行で、古い文脈は新しい文脈より明らかに悪い。LM なしなら今の「新しい文脈・LM なし」のほうがよい）。
- `D_max` は §6 の掃引で決める（今の観測は +1〜+7 字）。

当てたときの扱い:
- 返す候補と順位は、先行計算の結果そのもの（古い left で作った辞書の順位と LM の並べ替え）。
- 確定の学習の文脈は §10 Q3 で決める（推奨は (ii) Convert の文脈で記録する）。

この決定は、§6 の評価（S1）で「今より悪くならない」ことを確かめてから実装する（§8）。悪くなるなら実装せず、§3 の案 4 に切り替えるかをユーザーに聞く。

## 3. 検討した案

| 案 | 内容 | 採らない／採る理由 |
|---|---|---|
| **1（採る）** | Space では左の伸びを許容し、番号ではなく中身（§2 の G1〜G4）で直近の先行計算を当てる | エンジンだけで閉じる（殻・proto を変えない）。Space の応答時間は変わらない。観測の 66/73 を直接救う。副作用は伸びた分（直前の確定）が LM と辞書の文脈から抜けること（§9） |
| 2 | 殻が、番号が止まるまで（アプリが確定を反映するまで）読み直しを続け、先行計算を送り直す | 2〜3 打鍵目の読み直しはすでに入っていて、それでも 66/73 が古い。いつ止まるかはアプリしだいで決められない。打鍵ごとの読み直しは IPC が 4 回ずつ増える。読み直しが Space より後に追いつく場合は救えない。Swift の変更は macOS でしか試せない |

案 1 の中の変種:
- 1b: 辞書の順位は Convert の新しい文脈で作り直し、LM の点だけを先行計算から借りる。古い文脈の害（測定 (a) の LM なしの行）を辞書の側だけ避けられるが、core の変換から LM の点を候補ごとに取り出して付け替える口が要り、LM の側の古さは残る。案 4 のほうが単純に両方を直すので、1b は採らない。

## 6. 評価の設計

### 6.1 通常の評価（必須。差分 0 を確かめる）

`ikari-eval` はエンジンのキャッシュを通らないので、全セット・LM あり／なしで差分は出ないはず。それを確かめる（CLAUDE.md の約束）。

```sh
eval/scripts/snapshot.sh <before>              # main で
eval/scripts/snapshot.sh --compare <before>    # 実装のブランチで。LM ありは --lm <gguf>
```

### 6.2 S1: 左文脈を人工的に縮めて、案 1 と今を比べる（実装の前にやる。捨てるスクリプト）

測定 (a) と同じく、`eval/sets/*.tsv` のうち context が空でないケースで、context の末尾から「確定の単位」を 1 つ取り除いたセット（stale）を作る。単位の切り方は測定 (a) の A（文節の近似）と B（字種の変わり目）の両方。reading と expected は変えない。3 つの腕を流す。

| 腕 | 意味 | セット | LM |
|---|---|---|---|
| X（今） | 外れて、新しい文脈・LM なしで返る | 元のセット | なし |
| Y（案 1） | 古い文脈の先行計算（LM つき）を当てる | stale | あり |
| Z（参考の上限。案 4 が当たったとき） | 新しい文脈の先行計算が当たる | 元のセット | あり |

```sh
# セットごとに。LM ありは測定 (a) と同じく --lm <gguf> --lm-deadline-ms 2000（LM が必ず付く条件。G4 の前提に合わせる）
cargo run --release -p ikari-eval -- --ranker full --repeat 1 --set <元のセット> --out-cases x/<名前>.tsv
CARGO_TARGET_DIR=target/lm cargo run --release -p ikari-eval --features lm-metal -- --ranker full --repeat 1 --lm <gguf> --lm-deadline-ms 2000 --set <stale のセット> --out-cases y/<名前>.tsv
CARGO_TARGET_DIR=target/lm cargo run --release -p ikari-eval --features lm-metal -- --ranker full --repeat 1 --lm <gguf> --lm-deadline-ms 2000 --set <元のセット> --out-cases z/<名前>.tsv
cargo run --release -p ikari-eval -- compare x/<名前>.tsv y/<名前>.tsv   # 案 1 と今の、ケースごとの順位の差
```

出す数:
- Y 対 X の「期待 → 外れ」と「外れ → 期待」の件数を、セットごと、取り除いた単位の長さ（1〜12 字）ごとに。重み付きの率は、測定 (a) と同じく診断ログの `commit_chars` の分布で重み付けする。
- 同じく Z 対 X（案 4 の上限）と、Z 対 Y（案 1 の副作用の大きさ）。
- 単位の長さごとの Y 対 X の差し引きから、`D_max` を決める（差し引きが 0 以上の長さの上限。値はこの結果で決め、PR に表を載せる）。

採る基準（§10 Q2 で確認）:
- 推奨: すべての重み付きで、Y 対 X の「期待 → 外れ」が「外れ → 期待」以下（差し引きで今より悪くならない）。かつ §6.1 の差分 0。
- 「1 位の悪化 0 件」をケースごとに求める基準は、Y と X で文脈と LM の 2 つが同時に違うので、ほぼ確実に満たせない（どちらの向きの入れ替わりも出る）。ケースごとの 0 件は §6.1 に当てる。
- 見込み（推測）: 測定 (a) で、古い文脈は新しい文脈より重み付きで約 19 ポイント悪い（LM あり）。LM の利得は homophones-ext で約 9 ポイント（ADR 0021 §5.1）。この 2 つを足し引きすると、**評価セットの上では Y が X より悪い可能性が高い**。評価セットは文脈が正解を決めるケースを集めているので実利用より厳しい（#1 の推測）が、S1 で悪いと出たら、案 1 は実装せず §10 Q1 に戻る。

## 7. 診断ログで効果を確かめる

- 注記（固定の語と数だけ。NFR-19）: 伸びを許して当たったときは `cache=hit` / `wait_hit` に `grown=<d>` を足す。外れたときは `miss=context` に `grow=` を足す（`no_commit`（伸びが確定と一致しない）、`too_long`（`D_max` 超え）、`not_suffix`（G3）、`right`（G1）、`no_lm`（G4））。
- 集計（`scripts/diag-report.py`）: convert のうち `miss=context` の割合、LM なしの割合、`grown` の割合と d の分布、`grow=` の内訳。
- 基準: 今は `miss=context` 7.8%、LM なし 11.1%（全ログ 4,735 変換）。入れた版で、前回の再集計と同じくらいの量（約 800 変換。数日）を集めて比べる。
- 見込み: 66/73 の型がすべて当たれば、`miss=context` は 7.8% から 1% 前後、LM なしは 11.1% から 4% 前後。#1 の目標の約 2% には、ほかの理由（wait_miss 約 1.2%、miss=none、miss=reading）が残るので、この ADR だけでは届かない。

## 9. 懸念点・リスク

- **伸びた文脈で LM の入力が古い**: LM が見るのは left の末尾 40 字（`zenz.context_chars`）で、当てた変換では、直前の確定（いちばん近い、いちばん効く文脈）がそこに入っていない。辞書の側の文脈の規則（ADR 0007 の複合語の加点など）も同じく古い。大きさは S1 の Z 対 Y で見える。
- **IME が確定した文字を含まない先読みを当てる**: G2 で、伸びが自分の確定と一致するときに限るので、カーソルの移動、貼り付け、アプリの自動整形で文脈が変わった場合は当てない（今どおり外れる）。逆に、確定した文字の直後の続きの入力で、続きの読みがその確定に依存するとき（例: 直前の確定が正解の同音語を決める）は、古い文脈で外す。
- **学習の文脈**: 当てた変換をそのまま確定すると、学習は古い文脈（直前の確定を含まない）で記録される。今の外れでは新しい文脈で記録されているので、何もしないと文脈つきの学習が少し弱くなる（§10 Q3）。
- 文節の操作（←/→、区切り直し）と文節の先読みも、当てた変換の古い文脈のまま動く。順位の差は S1 の範囲に入らない（読み全体の 1 位だけを見る）。
- S1 は評価セットでの近似で、確定の単位の切り方も規則による近似（測定 (a) と同じ限界）。実利用での正しさは、診断ログからは見えない（ログは文字列を出さない）。
- 推測: アプリが確定を遅れて反映する原因（VSCode に偏る）は切り分けていない。別のアプリで違う形のずれ（dleft が負など、#1 の 2 件）があっても、この ADR は扱わない（G で外れ、今どおり）。

## 10. ユーザーに聞くこと

- **Q1. S1 で案 1 が今より悪いと出たときに、案 4（エンジンが先行計算の left に直前の確定を補う）に切り替えてよいか。**
