## 0. 現状の把握

### 0.1 コードの現状（設計に効く事実）
- **変換は読み全体を1文節として扱う**（ADR 0001 §4.7「文節伸縮はしない」）。`Converter::convert_until` は、読み全体のラティスを作り、前向き Viterbi と後ろ向き A*（`NBest`）で取り出したパスを候補にし、Ranker で並べ替える。候補（`Candidate`）は読み全体の表記と、語の分割（`segments: Vec<Segment>`。語ごとの読み、表記、左右ID、`pos_id`）を持つ。
- **表示される第一候補は、Viterbi の最良パスではなく、Ranker が1位にした候補**。Ranker（文脈、学習、プロファイル、話題、LM）と GrammarGuard / LearningGuard は、最初のプール（30件）全体を並べ替える。
- `lattice::build_with_starts` は、BOS の右IDを複数（と追加コスト）受け取れる。**EOS は `grammar.bos_eos_id()` に固定**（`NBest::new`）。区切りを強制する口はない。
- `AnalyzedContext`（左文脈の解析結果）はトークンの列と `bos_right_id` を持つ。左文脈に語を「足す」口はない（解析器は文字列から解析し直す）。
- `ZenzRanker` のプロンプトは「プロフィール、話題、左文脈の末尾、読み」で、**右の文脈は入らない**。候補の表記ごとの NLL で並べる。LM のワーカーは1つで、最新の要求だけを処理し、遅れて届いた結果を1件だけ持つ。
- 学習（`LearningStore::record`）は、確定した候補全体を `phrase`（読み全体）として、2語以上なら語ごとに `word` として記録する。特徴量は確定のときの左文脈（`CommitEvent.analysis`）から作る。
- エンジン（`engine/src/lib.rs`）: `Convert` は先行計算（`Prefetch`）のキャッシュに当たればすぐ返し、計算中なら「開始 + lm_budget(読み)」まで待ち、なければ **LM を使わずに**その場で変換する。返した `Conversion` に `conversion_id` を付けて固定する。確定履歴はセッションごとに32件（`Commit { reading, surface }`）。
- `Envelope.body` の番号は、24〜29 が空いている（Shutdown 23 と ErrorReply 30 の間）。
- 殻（`IkariShellCore`）: 矢印キーは `KeyCodes.keyInput` で `.other` になり、変換中は受け止めて何もしない（`.consume`）。キー割り当て（`Keymap`）は F キーと「Ctrl / Option / Command を伴う文字キー」のときだけ引く。キーの表記に矢印の名前はない（phase2-contract §4.1）。`MarkedText` は「全体の下線 + 先頭から `highlightedLength` の太い下線」だけを表せる。設定アプリのキー割り当ての画面は `KeymapAction.allCases` から作る。
- 殻の `ClientAccess`: `surroundingText()` は `selectedRange()` と `string(from:actualRange:)` で左右を取る。`setMarkedText` と `insertText` は、いつも `replacementRange = NSNotFound`。候補ウィンドウのアンカーは、変換文字列の先頭（`attributes(forCharacterIndex: 0, …)`、だめなら `firstRect`）。
- 辞書（`system.dict` v2）: **エントリは読みを持たない**。読みは読みの fst のキーにしかない。fst には読みの順にエントリの範囲 `(first, count)` が入り、エントリは読みの順に並んでいる（`dict-format/src/dict.rs` の組み立て）。表記の索引（`common_prefix_search_surface`）はある（32文字以下の表記）。`LatticeContextAnalyzer` はこの索引で表記を解析し、語ID つきのトークンを返す。

### 0.2 範囲
- **入れる**: 文節の区切り、文節ごとの候補、文節の移動（フォーカス）、区切り直し（伸縮）、全体の確定、文節単位の学習、確定した文字列を選択しての再変換、評価の追加。
- **入れない**: 合成中（composing）のカーソル移動と途中の挿入、↑↓ での候補の移動（→ ADR 0014 で入れた）、文節ごとの部分確定（Mozc の「先頭の文節だけ確定」）、再変換で右の文脈を使うこと（spec の未決事項「カーソルより右側の文脈」のまま）、複数行の再変換。Windows と Linux の殻（同じ proto と core を使うので、そちらは殻だけを足せばよい）。

## 1. 決定の要約

| 項目 | 決定 |
| --- | --- |
| 最初の区切り | **Ranker が1位にした読み全体の候補**（今の第一候補）の語の並びを、品詞の規則で文節にまとめる（§2）。表示される文字列は今と1文字も変わらない |
| 文節の定義 | 「自立語（または接頭辞）から始まり、付属語・接尾辞・非自立語・名詞の連続を後ろに付けたもの」。複合名詞は1文節 |
| 文節ごとの候補 | その文節の読みだけのラティスを、**左の文節の最後の語の右IDを BOS、右の文節の最初の語の左IDを EOS** にして作り、N-best を Ranker で並べる。Ranker には「左文脈 + 左の文節の表記」を左文脈として渡す。**候補の 0 番は、いま表示している表記に固定する**（NFR-05） |
| LM（zenz） | 最初の全体の並べ替えは今のまま。文節ごとの候補は、**文節ごとに**（左文脈 + 左の文節、読み = その文節）採点する |
| 区切り直し | Shift+←/→ で、フォーカスしている文節 i の長さを 1 文字ずつ変える。**0〜i-1 の文節はそのまま、i 以降は作り直す**（Mozc と同じ）。i の位置から読みの最後までを、区切り i の境界を強制して変換し直し、その1位を文節に分ける |
| 速さ | 文節の候補と区切り直しは、LM を待たない計算でエンジン内 p99 1ms 程度の見込み（短い読み。実測で確かめる）。文節の候補は、変換の直後に裏で LM つきで先に作る（NFR-03 と同じ形） |
| API | core に `Segmented`（区切りと文節ごとの候補の列）を足す。proto は `Envelope.body` の 24〜29 に、文節のページ、区切り直し、区切りの返事、文節の確定、再変換を足す。`ConvertReply` に区切りを足す。**schema_version は 1 のまま**（追加だけ。ADR 0005 §15.1-8） |
| キー | ←/→ で文節の移動、Shift+←/→ で伸縮。**どちらのプリセットも同じ**（MS-IME も macOS も同じ割り当て）。キー割り当ての操作として持ち、設定で上書きできる。Enter で全体を確定、Esc と BackSpace は今どおり読みに戻る |
| 表示 | フォーカスしている文節は太い下線、ほかは細い下線。文節の境目は `NSMarkedClauseSegment` で示す |
| 候補ウィンドウ | （2026-10-28 に取り消し。#86。アンカーは変換文字列の先頭に固定）アンカーを**フォーカスしている文節の先頭**に移す（spec の「先頭に固定」を、フォーカスを変えたときだけ動く、と改める。§16-4） |
| 学習 | 読み全体の確定を今どおり記録し、**ユーザーが変えた文節**を、その文節の左文脈（左の文節を含む）で `phrase` として記録する。こまめな確定で同じ語を打ったときと同じ記録になる |
| 再変換 | キー割り当ての操作 `reconvert`（既定は両プリセットとも Ctrl+Shift+R）。選択範囲の表記から読みを決め（確定履歴 → 表記の解析）、**元の表記を候補の 0 番にした文節の列**で変換中に入る。置き換えは `replacementRange` で、ユーザーが確定したときだけ。Esc は元の文字列に戻す |

## 2. 文節の定義と最初の区切り

### 2.1 区切りの元にする候補
- **区切りは、Ranker が1位にした候補（`generated()[0]`）の `segments`（語の並び）から作る。** 依頼の「Viterbi の最良パス」ではなく、ランキング後の1位を使う。理由:
  1. 表示される文字列が今と同じになる。ADR 0003 の評価の下限（話題 72% など）と、すべての評価セットの1位が、文節の導入で変わらない（これを不変条件としてテストする。§10.1）。
  2. 最良パスと1位が違う場合（文脈や LM が別のパスを1位にした）、最良パスで区切ると、表示と区切りが食い違う。
- 1位が辞書の候補でない（ひらがな、カタカナ、Rewriter の候補。語が1つの未知語セグメント）なら、**読み全体を1文節**にする。

### 2.2 まとめ方（品詞の規則。`core/src/pos.rs` に `segment_role(pos_name) -> SegmentRole` を足す）
語を左から見て、各語の役割で「新しい文節を始めるか、左の文節に付けるか」を決める。品詞名は Sudachi の形（`grammar.pos_name(pos_id)`）。

| 役割 | 該当（品詞1、品詞2） | 振る舞い |
| --- | --- | --- |
| 付属（Attach） | 助詞、助動詞、接尾辞、補助記号 | 左の文節に付ける |
| 補助（Dependent） | `非自立可能`（動詞・形容詞・名詞。「いる」「ほしい」「こと」、そして「切る」「行く」「ある」「いい」も） | 左の語が助詞（接続助詞を除く）・副詞・連体詞・接続詞なら新しい文節を始める（髪を｜切る）。そうでなければ左の文節に付ける（食べて｜いる は 1 文節）。§16.8 |
| 名詞の連続（Compound） | 名詞（非自立可能を除く）。未知語は名詞として扱う | 左の文節の最後の語が名詞・接頭辞・接尾辞（名詞的）なら付ける。そうでなければ新しい文節を始める |
| 接頭辞（Prefix） | 接頭辞 | 新しい文節を始める。次の語はその文節に付ける |
| 自立（Start） | 動詞、形容詞、形状詞、副詞、連体詞、接続詞、感動詞、代名詞、記号（補助記号以外） | 新しい文節を始める。ただし直前が接頭辞なら付ける |

- 例: 初めて｜知った、ユーザー辞書に｜単語を｜登録する、リポジトリ名（1文節）、変換する（1文節）、書いている（1文節）。
- **複合名詞は1文節**（「リポジトリ名」）。日本語の文節の通常の定義で、MS-IME と Mozc も同じ扱い。名の部分だけを選び直すには、Shift+← を2回押して「りぽじとり｜めい」に区切り直す。複合名詞を最初から語ごとに分ける案は §13 と §16-2。
- 先頭の語が付属語でも（読みが助詞から始まる「をしよう」など）、最初の語は文節を始める。
- 区切りは**読みの文字位置**（`Segment.reading` の長さの累計）で持つ。表記ではなく読みで持つので、候補を選び直しても区切りは動かない。

### 2.3 1文節の場合
文節が1つなら、**その文節の候補の列は、読み全体の変換の候補の列そのもの**にする（作り直さない）。こまめな確定ではほとんどの変換が1文節なので、そのときの振る舞い、速さ、候補は今と完全に同じになる。

## 3. 文節ごとの候補

### 3.1 作り方（`core/src/converter/segment.rs`、新設）
文節 i（読みの文字位置 `[s, e)`）の候補を、次の手順で作る。

1. **左文脈**: 解析済みの左文脈（`AnalyzedContext`）に、文節 0〜i-1 の**いま選ばれている候補**の語を、トークンとして後ろに足したもの（`AnalyzedContext::extended(&[Segment], grammar, dict) -> AnalyzedContext` を足す。`char_end` をずらし、`bos_right_id` を最後の語の右IDにする。解析器を通し直さない）。`Context.left_text` にも左の文節の表記をつなぐ（文書内キャッシュと LM のため）。
2. **ラティス**: 文節の読みだけで作る。BOS は 1 の `bos_options()`（文節 0 なら今の左文脈そのもの）。**EOS は右の文節の最初の語の左ID**（最後の文節なら今どおり `bos_eos_id`）。`NBest::new` に終わりの左IDを渡せるようにする（`NBest::with_end(lattice, grammar, end_left_id)`）。右の文節との連接コストは、パスのコストに入る。
3. **候補のプール**: 読み全体のときと同じ手順（`build_first_pool`）。N-best を `pool_size` 件、Rewriter の候補、ひらがな、カタカナ。FR-06（候補の読み = 文節の読み）はラティスの作りで保たれる。
4. **並べ替え**: `RankInput { reading: 文節の読み, context: 1 の文脈, analysis: 1 の解析, … }` で Ranker（Composite。GrammarGuard と LearningGuard を含む）を呼ぶ。Ranker の中身は変えない。
5. **0 番の固定**: いま表示している表記（最初の区切りなら全体の1位から切り出した部分）を、並べ替えのあとで先頭に移す（なければ足す）。**文節に移ったとき、表示中の文字列が変わらない**（NFR-05、基本原則）。
6. 2ページ目以降は、今の `extend_chunk` と同じく差分だけ作る。一度返したページは変えない。

- **右の文脈**: Ranker には渡さない。右の文節との文法的なつながりは、ラティスの EOS（右の文節の最初の語の左ID）として連接コストに入る。
- **左の文節の選択が後から変わったとき**: 文節 i の候補の列は、**最初に作ったときの左の選択**で固定し、作り直さない（返したページを差し替えないため）。左の選択を変えたあとに i の候補が最適でなくなることがあるが、表示は変わらない。区切り直しのときだけ作り直す（§4）。

### 3.2 Ranker を文節単位でどう効かせるか

| Ranker | 文節単位での効き方 |
| --- | --- |
| cost | 文節のラティスのパスのコスト（右の文節への連接を含む） |
| 左文脈（LeftContext） | BOS が左の文節の最後の語になる。「と + しよう」のような、文節の境目の文法がそのまま効く |
| 文書内キャッシュ | 左文脈 + 左の文節の表記。左の文節に出た語も加点の対象になる |
| 学習 | 読み = 文節の読み、特徴量 = 1 の解析から作る。**こまめに確定したときと同じ特徴量**（直前の語が左の文節の最後の語）になるので、こまめな確定の学習がそのまま効き、文節での選び直しの学習もこまめな確定に効く（§6） |
| プロファイル、話題 | 内容語の比較（今のまま）。左文脈が長くなる分、話題が効きやすい |
| LM（zenz） | 文節ごとに採点する（§3.3） |
| GrammarGuard、LearningGuard | 文節の候補の中で今のまま働く（内容語の加点や文脈に依らない学習が、文法や文脈の証拠を覆さない） |

### 3.3 zenz は文節ごとにする
- 最初の表示（全体の1位）は、今のとおり読み全体で採点した結果。
- 文節の候補は、**プロンプトの左文脈 = 左文脈 + 左の文節の表記、読み = 文節の読み**で採点する。`ZenzRanker` は `RankInput` から組み立てるので、変更は要らない（要求のキーはプロンプトで区別される）。
- 全体の文で並べ替える案（文節 i の候補 c ごとに「左の文節 + c + 右の文節」を読み全体で採点する）は採らない。右の文脈が入る利点はあるが、出力の長さが読み全体になり、候補の数だけ長い採点が要る。短い確定が中心なので文節は 1〜3 個で、右の文脈の利点が小さい（§13）。評価（§7）で文節の候補の1位の正解率が足りなければ、見直す。

### 3.4 速さ（NFR-02）
- **Space から最初の表示まで**: 1文節なら今と同じ（先行計算のキャッシュ）。2文節以上なら、文節 0 の1ページ目も要る。**先行計算のジョブが、全体の変換のあとに文節 0 の1ページ目まで作る**（残りの締め切りで LM を使う）。キャッシュに当たれば今と同じ。間に合わなければ、文節 0 の候補を LM なしで作る（文節の読みは全体より短く、ラティスと A* は全体の計算の一部。エンジン内 1ms 未満の見込み）。
- **文節の移動（←/→）**: `ConvertReply` を返したあと、エンジンが文節 1 以降の1ページ目を**裏で LM つきで作る**（セッションごとに最新の1件。今の先行計算の待ち行列と同じ仕組み）。移動の要求は、できていれば返し、計算中なら「開始 + lm_budget(文節の読み)」まで待ち、なければ LM なしで作る。人が → を押すまでの時間（100ms 以上）で、たいてい間に合う。
- **区切り直し（Shift+←/→）**: 先読みしない（押す向きと回数を予測できない）。**LM を待たずに**計算する（`deadline = Some(now)`。先行計算のない `Convert` と同じ扱い）。2ページ目以降には、届いた LM の結果を使ってよい（今の `page` と同じ）。
- 目標: どの操作も、短い読み（10文字以下）で XPC の往復を含めて p99 16ms 以下。エンジン内の性能テスト（`--ignored`）と smoke で測る（§10.1）。

## 4. 区切り直し

### 4.1 振る舞い（Mozc の ResizeSegment にならう）
フォーカスが文節 i（`[s, e)`）にあるとき:
- **Shift+←**: i を1文字縮める（`e-1`）。i が1文字なら何もしない。
- **Shift+→**: i を1文字伸ばす（`e+1`）。i が最後の文節なら何もしない。
- 区切り直しのあとも、フォーカスは i のまま。

### 4.2 作り直し方
1. 文節 0〜i-1 は、**区切りも選んだ候補もそのまま**にする。
2. 新しい境界を `b = s + 新しい長さ` とする。読み `[s, 読みの最後)` を、**位置 b をまたぐ語を使わない**ラティス（`lattice::build_constrained(key, dict, grammar, starts, boundaries: &[u32])`。境界をまたぐ辞書のノードを作らない。1文字の未知語は境界をまたがないので、必ずつながる）で変換し直す。左文脈は §3.1-1 と同じ（左文脈 + 文節 0〜i-1）。Ranker もすべて使う（LM は §3.4 のとおり待たない）。
3. その1位の語の並びを、`[s, b)` は**1つの文節**（品詞の規則で分けない。ユーザーが決めた境界）、`[b, 最後)` は §2.2 の規則で文節に分ける。
4. 文節 i 以降の候補の列は捨て、i 以降の文節は新しい1位を表示する。i の1ページ目は、§3.1 の手順で、右の文節（3 で作った i+1）を EOS にして作り、0 番は 3 の表示に固定する。
5. 区切りの版（`layout_rev`）を1つ上げる。

- **i 以降でユーザーが選んでいた候補は失われる**（Mozc と同じ）。区切り直しの前の選択を引き継ぐ案は、境界が動いた文節では意味が変わるので採らない。
- 縮めて離れた文字は、右の文節の頭に付くとは限らない（3 で i+1 以降の区切りを決め直す）。Mozc と同じ。

## 5. API と proto

### 5.1 core（契約。シグネチャだけを契約コミットに入れる）
```rust
// core/src/converter/segment.rs
pub struct SegmentSpan { pub start: usize, pub end: usize /* 読みの文字位置 */, pub reading: String, pub surface: String /* 0 番 */ }
pub struct SegmentLayout { pub rev: u32, pub spans: Vec<SegmentSpan> }

/// 文節の選択。`Literal` は殻が作った表記（字種変換）で、学習しない
pub enum SegmentChoice { Candidate(usize), Literal(String) }

pub enum SegmentError { StaleLayout, OutOfRange, Empty }

/// 区切りと、文節ごとの候補の列。読み全体の `Conversion` を中に持つ（1文節ならその列をそのまま使う）
pub struct Segmented { /* whole: Conversion, layout, lists: Vec<Option<Conversion>>, origin: SegmentedOrigin */ }

impl Segmented {
    pub fn layout(&self) -> &SegmentLayout;
    /// 文節 `seg` の `index` ページ目。初めて作るとき（だけ）`left` の選択を左文脈に使う
    pub fn page_until(&mut self, seg: usize, index: usize, left: &[SegmentChoice], deadline: Option<Instant>) -> Result<Option<Page<'_>>, SegmentError>;
    /// 確定。変えた文節ごとの CommitEvent と、読み全体の CommitEvent（作れるときだけ）。secure なら空
    pub fn commit(&self, choices: &[SegmentChoice]) -> Result<SegmentCommit, SegmentError>;
}
pub struct SegmentCommit { pub surface: String, pub events: Vec<CommitEvent>, pub history: Vec<Commit> }

impl Converter {
    /// `convert_until` の結果を区切る（§2）。先行計算はこれをキャッシュする
    pub fn segment(&self, whole: Conversion) -> Segmented;
    /// 区切り直し（§4）。解析器が要るので Converter に置く
    pub fn resize(&self, seg: &mut Segmented, index: usize, delta: i32, left: &[SegmentChoice], deadline: Option<Instant>) -> Result<(), SegmentError>;
    /// 再変換（§9）。`hint` は確定履歴
    pub fn reconvert(&self, surface: &str, ctx: &Context, hint: &[Commit], deadline: Option<Instant>) -> Segmented;
}
```
- `Conversion` は変えない（既存の `page_until`、`commit`、eval、CLI はそのまま）。文節は `Segmented` が包む。依存の向きは `Segmented → Conversion` の一方向。
- 区切りの規則（§2.2）は `pos.rs` の純関数にしてテストする。

### 5.2 engine.proto（契約）
```proto
// Envelope.body に追加（24〜29）
SegmentPageRequest segment_page = 24;   SegmentPageReply segment_page_reply = 25;
ResizeSegment resize_segment = 26;      SegmentLayout segment_layout = 27;   // ResizeSegment と Reconvert の返事
CommitSegments commit_segments = 28;    // 返事は Ack
Reconvert reconvert = 29;               // 返事は SegmentLayout

message SegmentInfo { string reading = 1; string surface = 2; }     // surface = その文節の候補の 0 番
message SegmentLayout { uint64 conversion_id = 1; uint32 layout_rev = 2; repeated SegmentInfo segments = 3;
                        uint32 focused = 4; SegmentPageReply focused_page = 5; uint32 engine_micros = 6; }
message SegmentPageRequest { uint64 conversion_id = 1; uint32 layout_rev = 2; uint32 segment = 3; uint32 index = 4;
                             repeated SegmentChoice left = 5; }      // left = 0〜segment-1 の選択。初めて作るときだけ使う
message SegmentPageReply { uint32 segment = 1; uint32 page_index = 2; repeated Candidate candidates = 3; bool has_next = 4;
                           bool lm_applied = 5; uint32 engine_micros = 6; }
message ResizeSegment { uint64 conversion_id = 1; uint32 layout_rev = 2; uint32 segment = 3; sint32 delta = 4;
                        repeated SegmentChoice left = 5; }
message SegmentChoice { uint32 candidate_index = 1; string literal = 2; }   // literal が空でなければ殻が作った表記（学習しない）
message CommitSegments { uint64 conversion_id = 1; uint32 layout_rev = 2; repeated SegmentChoice choices = 3; }
message Reconvert { uint64 session_id = 1; string surface = 2; SurroundingText context = 3; uint32 page_size = 4; }

// 既存に追加
message ConvertReply { ...; SegmentLayout layout = 7; }   // 新しいエンジンは常に入れる。focused = 0
enum CandidateKind { ...; LITERAL = 5; }                  // 再変換で読めなかった部分（元の表記だけ）
enum ErrorCode { ...; STALE_LAYOUT = 7; }                 // layout_rev が古い
```
- **schema_version は 1 のまま**。足すのはメッセージ、フィールド、列挙の値だけで、既存のものの意味は変えない（ADR 0005 §15.1-8 の規則）。`ConvertReply.candidates` は今までどおり読み全体の候補の1ページ目（1文節なら `layout.focused_page` と同じ）。`Commit`（20）も残す（smoke と、古い殻のため）。
  - 新しい殻と古いエンジン: `ConvertReply.layout` がない → 殻は1文節として扱う（今の振る舞い）。新しい要求には `BAD_REQUEST` が返る → 殻は文節の操作を何もしない。版の違いは既存の `Hello` の照合で直る。
- 上限: `SegmentChoice` は文節の数（読みの文字数 256）まで、`literal` は 256 文字まで。`Reconvert.surface` は 64 文字まで（§9.2）。超えたら `BAD_REQUEST`。
- `layout_rev` は区切り直しで上がる。古い版の要求は `STALE_LAYOUT`（殻は同期で待つので普通は起きない。壊れた殻と再送の守り）。

### 5.3 エンジン
- `ConversionTable` の中身を `Arc<Mutex<Segmented>>` にする（`conversion_id` は `Segmented` ごと）。期限と上限は今のまま。
- 先行計算のジョブ: `convert_until` → `Converter::segment` → 2文節以上なら文節 0 の `page_until(0, …)` まで、同じ締め切り（`開始 + lm_budget.max`）で作る。キャッシュのキーは今のまま。
- `Convert` の返事のあと、2文節以上なら、文節 1 以降の1ページ目を作るジョブを先行計算の待ち行列に積む（セッションごとに最新の1件。新しい `Convert` や `Prefetch` で捨てる。§3.4）。
- `CommitSegments`: `Segmented::commit` の `events` を `LearningStore::record` に順に渡す（§6）。`history` を確定履歴に積む。secure なら何もしない（`commit` が空を返す）。
- ログには、種類、所要時間、文節の数、区切り直しの向きだけを書く（読みと表記は書かない。NFR-19）。

### 5.4 先行計算（NFR-03）と NFR-05 との関係
- 先行計算は「全体の1位 → 区切り → 文節 0 の1ページ目」まで。区切りは全体の1位から決まるので、**先行計算が LM つきで1位を変えたなら、区切りもそれに合わせて決まる**（キャッシュに当たったときと当たらなかったときで、区切りが違いうる。どちらも、表示した文字列と区切りは一致する）。
- NFR-05（一度表示した第一候補は差し替えない）は、次の3つで守る。
  1. 最初に表示する文字列は、`ConvertReply` を返した時点の全体の1位で、あとから届いた LM の結果で変えない（今のまま）。
  2. 文節の候補の 0 番は、表示中の表記に固定する（§3.1-5）。文節に移っても、ページを開いても、表示は変わらない。
  3. 返した文節のページは変えない（`Conversion` の性質）。左の選択が変わっても作り直さない（§3.1）。
- 区切り直しで i 以降の表示が変わるのは、**ユーザーの操作の結果**で、NFR-05 の「表示後に勝手に変わるちらつき」には当たらない。

## 6. 学習

### 6.1 記録するもの
`Segmented::commit` は、次の `CommitEvent` を返し、エンジンが今の `LearningStore::record` に渡す（**学習の形式は変えない。schema=1 のまま**）。

| 記録 | 読み | 表記 | 特徴量（左文脈） | 条件 |
| --- | --- | --- | --- | --- |
| 読み全体 | 全体の読み | 文節の表記をつないだもの。語の分割は各文節の候補の語をつないだもの | 変換のときの左文脈 | 今と同じ。どの文節にも Rewriter の候補と `Literal` がないときだけ（日付の文字列を表記で覚えないため） |
| 変えた文節 | 文節の読み | 選んだ表記（Rewriter の候補なら書式。今の規則） | 左文脈 + 左の文節（§3.1-1 の解析） | 0 番以外を選んだ文節、または区切り直しで作った文節のうち、0 番以外を選んだもの。`Literal` は記録しない |

- 変えた文節の記録は、**「リポジトリ」と確定してから「めい」を変換して「銘」を選んだ**ときと同じ行になる。こまめな確定と文節の選び直しが、同じ学習を共有する。
- 変えなかった文節は、個別には記録しない（読み全体の記録と、その `word` 記録で足りる。行数の上限 20万行を、明示的な選択に使う）。
- 「選ばなかった 0 番」を負の例として記録することはしない（今の学習は回数だけで、負の例を持たない。必要になってから考える）。

### 6.2 基本原則との関係
- 学習は加点だけで、候補を消さない。文節の候補の 0 番は表示中の表記に固定するので、学習が表示中の文字列を変えることもない。
- LearningGuard は文節の候補の並べ替えの中でもそのまま働く（文脈に依らない学習の加点が、文脈の証拠を覆さない）。
- 区切りの位置は学習しない（spec「区切り方は学べない」と同じく、v1 では持たない。§13）。

## 8. 殻の操作（macOS）

### 8.1 キー割り当て
- `KeymapAction` に足す: `segment.focus_left`、`segment.focus_right`、`segment.shrink`、`segment.expand`、`reconvert`（§9）。キーの表記（phase2-contract §4.1）に `left`、`right` を足す。
- プリセット（`macos/Resources/keymap/{macos,ms-ime}.tsv`）:

| 操作 | macos（既定） | ms-ime | 効く状態 |
| --- | --- | --- | --- |
| `segment.focus_left` | `left` | `left` | 変換中 |
| `segment.focus_right` | `right` | `right` | 変換中 |
| `segment.shrink` | `shift+left` | `shift+left` | 変換中 |
| `segment.expand` | `shift+right` | `shift+right` | 変換中 |
| `reconvert` | `ctrl+shift+r` | `ctrl+shift+r` | idle（選択があるとき） |

  - 文節の操作は、MS-IME も macOS の日本語入力も ←/→ と Shift+←/→ なので、**プリセットの違いはない**。違いを作る理由がない。
  - 再変換は、Windows の MS-IME では「変換」キーだが、Mac のキーボードには「変換」キーがない（仮想キーコードがない）。macOS の日本語入力の再変換のキーは手元で確かめていない（S0-7）。どちらのプリセットも Ctrl+Shift+R にし、設定で上書きできるようにする（§16-7）。
  - キー割り当ての操作にするのは、ユーザーが自作キーボードを使っており（ADR 0005 §15.2）、矢印がレイヤーの奥にある場合に別のキーへ割り当てられるようにするため。`settings.tsv` の `keymap.<操作>` で上書きでき、設定アプリのキー割り当ての画面に自動で並ぶ（`KeymapAction.allCases`）。
- 引き方: 変換中は矢印のキー（修飾キーの有無を問わず）をキー割り当てで引く。idle では Ctrl / Option / Command を伴う文字キーのときに `reconvert` を引く（今の `scriptAction` と同じ場所）。**idle の矢印はアプリに渡す**（カーソル移動を奪わない）。合成中の矢印は今どおり受け止めて何もしない。
- `KeyInput.Key` に `.left`、`.right` を足し、`KeyCodes` で kVK_LeftArrow（123）と kVK_RightArrow（124）を対応させる。↑↓（125、126）は割り当てない（候補の移動は Space と Shift+Space。§16-11。**ADR 0014 で置き換えた**: ↑↓ は `candidate.next` / `candidate.previous`）。

### 8.2 変換中のキーの振る舞い（ADR 0004 §6.3 の表に足す）

**以下の表は文節のモードの振る舞い**。最初の Space のあとは読み全体の候補を出し、←/→ か Shift+←/→ で文節のモードに入る（§16.6）。

| キー | 1文節 | 2文節以上 |
| --- | --- | --- |
| ←/→ | 何もしない | フォーカスを左右の文節へ（端では止まる）。候補ウィンドウはその文節の候補に替わり、選択はその文節でいま選んでいる候補 |
| Shift+←/→ | 縮める。縮めると2文節になる（伸ばすのは何もしない） | §4 |
| Space / Shift+Space | フォーカスしている文節の次／前の候補（今のページ送りの規則のまま） | 同じ |
| 1〜9 | その候補を選んで**全体を確定**（今と同じ） | フォーカスしている文節にその候補を選び、**全体を確定**（§16-3） |
| Enter | 全体を確定 | 全体を確定（`CommitSegments`） |
| Esc / BackSpace | 読みに戻る（今と同じ） | 読みに戻る（全体。区切りと選択は捨てる） |
| 文字 | 全体を確定して、その文字から合成を始める | 同じ |
| F6〜F10、プリセットの字種キー | 読み全体を字種変換（今と同じ） | **フォーカスしている文節だけ**を字種変換し、`Literal` としてその文節に置く（候補ウィンドウは閉じる。§16-5） |

- 区切りの数が1でも、Shift+← で縮められる（「りぽじとりめい」を1文節で出したあと、名を変えるため）。

### 8.3 変換中の表示
- `MarkedText` を、文節の UTF-16 の長さの列（`segments: [Int]`）と、フォーカスの番号（`focused: Int?`）を持つ形に変える（契約）。1文節なら今と同じ見た目。
- `ClientAccess.setMarkedText` は、文節ごとに `NSAttributedString.Key.markedClauseSegment`（文節の番号）を付け、フォーカスしている文節は太い下線、ほかは細い下線にする。境目の見え方はアプリによるので、S0-2 で確かめる（文節の境目が見えないアプリでも、太い下線でフォーカスは分かる）。
- `selectionRange` は今どおり末尾（キャレットの位置をアプリごとに変えない）。

### 8.4 候補ウィンドウのアンカー
- spec は「アンカーは変換文字列の先頭に固定（打鍵やページ送りで横に動かさない）」。文節の候補は、その文節についての候補なので、先頭に固定すると、右の文節の候補が離れた場所に出る。
- **フォーカスしている文節の先頭に置く**（MS-IME と Mozc と同じ）。動くのは、フォーカスを移したときと、区切り直しでフォーカスしている文節の先頭が動いたとき（左の文節の表示は変わらないので、実際には動かない）だけ。打鍵とページ送りでは今どおり動かない。1文節なら今と同じ位置。spec の該当の行を直す（§16-4）。
- 矩形の取り方: `attributes(forCharacterIndex: 文節の先頭の UTF-16 位置, …)`、だめなら `firstRect(forCharacterRange: markedStart + 位置)`。どちらの位置が変換文字列の中の相対か、S0-3 で確かめる。取れないときは今のフォールバック（`resolveAnchor`）で、変換文字列の先頭を使う。

### 8.5 殻の状態（`ConvertingState`、契約）
- 文節の列（読み、表示中の表記、取得済みのページ、選択の通し番号、`Literal` の表記）、フォーカス、`layoutRev`、元の状態（合成、英数、再変換）を持つ。
- ページの往復と折り返しは、今と同じく取得済みのページを使う（文節ごと）。
- `EngineClient` に足す: `segmentPage(conversionID:layoutRev:segment:index:left:timeout:)`、`resize(conversionID:layoutRev:segment:delta:left:timeout:)`、`commitSegments(conversionID:layoutRev:choices:)`、`reconvert(_:timeout:)`。待ちの上限は `EngineTimeouts.convertTimeout(文節の読みの文字数)`。
- エンジンが使えない、または時間切れ: 今のフォールバック（1文節の、殻だけの候補）。文節の操作は何もしない（区切り直しの時間切れなら、区切りを変えずに今の表示のまま）。

## 9. 確定後の再変換

### 9.1 起動
- idle のときに `reconvert`（既定 Ctrl+Shift+R）を押す。**このキーを押したときだけ**選択範囲を読む（打鍵ごとには問い合わせない）。
- 合成中と変換中は何もしない（受け止める）。secure のときは何もしない（受け止める。NFR-18）。

### 9.2 選択範囲の取り方
1. `client.selectedRange()`。`location == NSNotFound` または `length == 0` なら、何もしない（受け止める）。選択がないときにキャレットの直前の語を自動で選ぶ案は採らない（§13）。
2. `client.string(from: selectedRange, actualRange:)`（`attributedSubstring` の代わりに、今の `ClientAccess` と同じ API を使う）。`nil`、空、`actualRange != selectedRange`（アプリが別の範囲を返した）なら何もしない。
3. **断る条件**: 64 文字を超える、改行を含む、制御文字だけ。左の周辺テキストが取れない（`surroundingText().available == false`。ターミナル、一部の Electron）。どれも何もしない（受け止める。キーをアプリに渡すと、アプリの別の操作が動きうるため）。
4. 左文脈は `selectedRange.location` の手前（今の `surroundingText()` がそのまま返す）。右の文脈は送るが、エンジンは使わない（今のまま）。

### 9.3 読みの求め方（`core/src/converter/reconvert.rs`）
1. **確定履歴**: セッションの確定履歴（新しい順）の中に、表記をつなぐと選択と一致する**連続した項目**があれば、その読みをつなぐ。項目の境目を文節の境界の候補にし、各項目の中は、その読みの N-best から表記が一致するパスを探して語に分ける（`max_astar_pops` の範囲。見つからなければ項目を1文節にする）。履歴は、殻が `Reconvert` を送ったセッションのもの（エンジンが持つ）。
2. **表記の解析**: 1 で決まらなければ、`LatticeContextAnalyzer` と同じ解析（表記の索引と Viterbi。文脈の解析と同じ関数を、選択の文字列だけに使う）で語に分け、**語ごとに読みを引く**。
   - 辞書の語の読み: `Dictionary::reading(id) -> Option<Cow<str>>`（既定は None）を足す。`system.dict` はエントリが読みを持たないので、**読みの fst を一度だけ順に読んで「エントリ番号 → 読み」の逆引き表をメモリに作る**（エントリは読みの順に並び、fst の値の `first` は単調に増える。二分探索で引く）。表はエンジンの起動のあと、LM の warm_up と同じく裏で作る。ユーザー辞書（`InMemoryDictionary`）は読みを持っているのでそのまま返す。
   - 未知語: カタカナの連続はひらがなにした読み、ひらがなはそのまま。英数字は ASCII のまま（今の英数の読みと同じ扱い）。**漢字などの読めない文字は、元の表記だけを候補に持つ文節（`LITERAL`）にする**。全部が読めなければ、再変換を始めない（殻は何もしない）。
3. **読みが一意に決まらないとき**（「今日」きょう／こんにち、「行った」いった／おこなった）: 解析の最良のパスの読みを使う。**読みの候補を並べて選ばせることはしない**。代わりに、
   - 文節の候補の 0 番は、いつも元の表記にする（§9.4）。読みが違っていても、元の文字列は失われない。
   - BackSpace で読みに戻れる（§9.6）。ユーザーは推定した読みを直してから、Space で変換し直せる。ユーザーの入力（直した読み）が正になる。

### 9.4 再変換の区切りと候補
- 区切りは、9.3 で得た語の並びを §2.2 の規則でまとめる（確定履歴の項目の境目は、必ず文節の境界にする）。
- **各文節の候補の 0 番は、その部分の元の表記**（辞書の語でできていれば辞書の候補として、読めなければ `LITERAL`）。最初の表示は、選択していた文字列と1文字も変わらない。
- 文節の候補の作り方、文節の移動、区切り直しは、§3〜§4 と同じ（`Segmented` を使う）。左文脈は選択の手前の周辺テキストだけで、確定履歴は左文脈に使わない（選択が履歴の末尾にあるとは限らないため）。
- 区切り直しで作り直した文節は、変換の1位になる（元の表記ではなくなる）。これはユーザーの操作の結果。

### 9.5 置き換え（replacementRange）
- 始めるとき: `setMarkedText(元の表記, selectionRange: 末尾, replacementRange: selectedRange)`。選択していた文字列が、同じ文字列の変換中の文字列（下線つき）に置き換わる。殻は `selectedRange` を覚える。
- 確定（Enter、数字、文字キー）: `insertText(確定する文字列, replacementRange: NSNotFound)`（変換中の文字列を置き換える。今の確定と同じ）。
- Esc: **元の表記をそのまま確定する**（`insertText(元の表記)`）。文書の中身は再変換の前と同じになる。エンジンへは `Cancel`。
- IMK の `commitComposition`（フォーカスが外れたなど）: 表示中の文字列を確定する（今と同じ）。何も変えていなければ元の文字列のまま。
- 先に確かめること（S0-5）: TextEdit、メモ、Safari、Chrome、VS Code、Slack（Electron）で、`setMarkedText` の `replacementRange` が効くか。効かないアプリ（元の文字列が残り、変換中の文字列が後ろに足される）は、殻の定数の拒否リスト（Bundle ID）に入れて、再変換を始めない。設定のキーにはしない（YAGNI。S0 の結果だけで決まる）。

### 9.6 再変換の中のキー
| キー | 振る舞い |
| --- | --- |
| ←/→、Shift+←/→、Space、数字、Enter、文字、F キー | §8.2 と同じ |
| Esc | 元の表記に戻して終える（§9.5） |
| BackSpace | 推定した読みの合成（composing）に戻る。**この合成の中で Esc を押すと、元の表記に戻して終える**（合成を消すと元の文字列が消えるため）。Enter はかなのまま確定する（ユーザーの明示的な操作） |

### 9.7 学習と文脈への反映
- 確定のとき、**何も変えていなければ**（区切りもすべての文節の選択も元のまま）、`Cancel` を送り、学習しない。
- 変えたときは `CommitSegments`。学習は §6 と同じ規則（読み全体の記録 + 変えた文節）。左文脈は選択の手前の周辺テキスト。**ユーザーが元の表記から別の表記に直した**という、最も強い明示的な選択なので、通常の確定と同じ重みで記録する（usage 層）。
- 確定履歴には積まない（選択の位置は文書の途中でありうるので、「カーソルの手前の確定の列」という履歴の意味が崩れる）。次の変換の左文脈は、今どおり殻が周辺テキストから取り直す。
- secure では始めないので、学習も文脈もない（NFR-18）。

### 10.2 手動のチェックリスト（実機。完了条件に含める）
1. **文節の表示**: 「はじめてしった」で 初めて｜知った の2文節になり、フォーカスの文節が太い下線。TextEdit、メモ、Safari、Chrome、VS Code で、境目とフォーカスが分かる（見え方を記録する）。
2. **移動**: ←/→ で文節を移り、候補ウィンドウがその文節の先頭の下に出て、候補がその文節のものになる。移っても表示中の文字列が変わらない。端で止まる。
3. **選び直し**: 文節 1 で Space を押して別の候補にし、← で戻っても、文節 1 の選択が残る。Enter で全体が確定される。
4. **区切り直し**: 「りぽじとりめい」で Shift+← を2回 → りぽじとり｜めい、→、Space で 名／銘／姪… が選べる。Shift+→ で戻せる。左の文節の選択が区切り直しで変わらない。
5. **学習**: 4 で「銘」を確定したあと、同じ左文脈で「りぽじとりめい」を変換すると「リポジトリ銘」が上位に来る。「リポジトリ」と確定してから「めい」を変換しても上位に来る。別の文脈では効きすぎない。
6. **キー割り当て**: 設定アプリで `segment.shrink` を別のキーに変えて効く。`none` で外せる。idle の ←/→ がアプリのカーソル移動になる（奪わない）。
7. **字種変換**: 2文節のときに F7 で、フォーカスしている文節だけがカタカナになる。
8. **再変換**: TextEdit で確定済みの「品詞」を選んで Ctrl+Shift+R → 変換中になり、表示は「品詞」のまま。Space で瀕死に替え、Enter で置き換わる。Esc で元のまま。BackSpace で「ひんし」の合成に戻り、さらに Esc で「品詞」に戻る。履歴にない文字列（Safari に貼った文）でも読みが推定される。読めない漢字を含む文字列で、その部分が元のまま残る。ターミナルとパスワード欄で何も起きない。改行を含む選択で何も起きない。
9. **replacementRange**: TextEdit、メモ、Safari、Chrome、VS Code、Slack で、置き換えが正しく行われる（元の文字列が残らない、二重にならない、アンドゥで元に戻る）。だめなアプリを記録し、拒否リストに入れる。
10. **速さ**: ふつうに打って Space、←/→、Shift+←/→ が遅れて見えない（ログの所要時間で裏を取る）。
11. **メモリ**: エンジンのメモリの増分（逆引き表）を記録し、500MiB 以下のまま（ADR 0004 §10.2-11）。

## 13. 却下した案

| 案 | 却下した理由 |
| --- | --- |
| 最初の区切りを Viterbi の最良パスから作る | Ranker の1位と食い違うと、表示が今と変わり、評価の1位が下がる。区切りと表示が一致しない（§2.1） |
| 複合名詞を最初から語ごとに分ける（リポジトリ｜名） | 依頼の例は Shift+← が要らなくなるが、短い読みの多くが2文節以上になり、Space の候補が「読み全体」から「先頭の語」に変わる（今の操作感が大きく変わる）。通常の文節の定義から外れる。§16-2 でユーザーに確かめる |
| 文節の候補を、読み全体の候補の列から作る（全体の候補を文節 i の部分で絞る） | 全体の N-best の上位は、ほかの文節の違いで埋まり、文節 i の候補が少ししか出ない。左右の文節を固定した探索の方が、少ない計算で多くの候補が出る |
| zenz で全体の文を採点して文節の候補を並べる | §3.3。出力が読み全体の長さになり、候補ごとに長い採点が要る。短い確定では右の文脈の利点が小さい |
| 文節の候補を、左の選択を変えるたびに作り直す | 表示中の候補の列が入れ替わる（NFR-05 の趣旨に反する）。左の選択の変化で、表示中の文節の 0 番が変わりうる |
| 区切り直しで、i 以降の選択を引き継ぐ | 境界が動いた文節では読みが変わり、引き継ぐ選択の意味がない。Mozc も引き継がない |
| 区切り直しを先読みする（縮める・伸ばすの両方を裏で計算） | 向きと回数を予測できず、LM のワーカー（1つ、最新だけ）を奪い合う。LM なしで 16ms に収まる見込み |
| 区切りの位置を学習する | 区切り方は spec でも学べないとしている。v1 は候補の学習だけで、区切りは毎回 §2 の規則。必要になれば、評価（§7）で区切りの誤りを集めてから考える |
| 文節の状態（フォーカス、選択）をエンジンが持つ | 選択は Space のたびに変わり、毎回 IPC が要る。フォーカスと選択は表示の状態なので殻が持ち、確定と区切り直しのときにだけ選択を送る |
| 2文節以上でも、Space で読み全体の候補を出す（文節の操作をしたときだけ文節にする） | 文節の候補と全体の候補の2つのモードができ、どちらの候補が出ているか分かりにくい。MS-IME と Mozc とも違う |
| 数字キーで、その文節だけを選んで次の文節へ進む | 今の「数字で確定」と変わる。短い確定では直す文節はたいてい1つで、全体の確定の方が打鍵が少ない（§16-3） |
| 再変換で、選択がなければキャレットの直前の語を自動で選ぶ | 何を置き換えるかをユーザーが選んでいない（基本原則「明示的な操作のときだけ置き換える」）。範囲の推定を誤ると、意図しない文字列が変換中になる |
| 再変換で、読みの候補（きょう／こんにち）を並べて選ばせる | 操作が1段増える。元の表記が 0 番にあり、BackSpace で読みを直せるので、読みの誤りで失うものがない |
| 再変換を選択中の Space で始める | idle の Space は打鍵のたびに来るので、そのたびに選択を問い合わせることになる。選択を空白で置き換えたい場合と区別できない |
| 再変換の読みを LLM や外部の辞書で推定する | NFR-17（通信しない）。手元の辞書の表記の索引で足りる |
| 辞書の形式に「エントリ → 読み」の節を足す（最初から） | 形式の版を上げ、辞書を作り直す必要がある。読みの fst から逆引き表を作れば形式を変えずに済む。S0-6 で重すぎると分かったら、この案に切り替える |

| NFR-18、NFR-19 | secure では再変換を始めず、文節の確定も学習しない。ログに読みと表記を書かない。学習の形式は変わらず、原文を持たない |
| NFR-20 | 新しい OS の権限を求めない。選択範囲は IMK のクライアントから取る |

## 16. 判断が必要な点
1. **最初の区切りの元**（§2.1）: 依頼では「Viterbi の最良パス」だったが、**Ranker が1位にした候補の語の並び**から作る。表示と評価の1位が今と変わらない。**推奨: この案**。
2. **複合名詞の扱い**（§2.2）: 1文節にする（「リポジトリ名」は1文節。名だけを直すには Shift+← を2回）。語ごとに分ける案は、例の操作が 2 打鍵減るが、短い読みの Space の候補が「先頭の語」になる。**推奨: 1文節**。評価（§7）の `部分` の打鍵数を見て見直せる。
3. **2文節以上での数字キー**（§8.2）: フォーカスしている文節に選んで、**全体を確定**する（今の「数字で確定」と同じ）。**推奨: この案**。
4. **候補ウィンドウのアンカー**（§8.4）: フォーカスしている文節の先頭に移す。spec の「アンカーは変換文字列の先頭に固定」を「フォーカスしている文節の先頭。打鍵やページ送りでは動かさない」に直してよいか。1文節なら今と同じ。S0-3 で位置が取れなければ、先頭に固定のまま。
5. **2文節以上での字種変換（F6〜F10）**（§8.2）: フォーカスしている文節だけに効かせる（MS-IME と同じ）。字種変換した文節は学習しない。**推奨: この案**。
6. **区切り直しの扱い**（§3.4、§4）: LM を待たずに計算する（表示のあとに LM の結果で変えない）。i 以降の選択は失われる。**推奨: この案**。
7. **再変換のキー**（§8.1）: 両プリセットとも Ctrl+Shift+R（Mac には「変換」キーがないため、プリセットで分けない）。設定で上書きできる。S0-7 で macOS の日本語入力の割り当てが分かれば、macOS 風をそれに合わせる案もある。
8. **再変換の断る条件と Esc**（§9.2、§9.6）: 64 文字まで、改行なし、左の周辺テキストが取れること。Esc は元の表記に戻す。BackSpace は推定した読みの合成に戻り、その中の Esc も元に戻す。
9. **文節の学習**（§6）: 読み全体の記録（今と同じ）に加えて、ユーザーが変えた文節だけを、その文節の左文脈で記録する。再変換で変えた結果も同じ重みで記録する。
10. **読みの逆引き**（§9.3）: 読みの fst からメモリ上に逆引き表を作る（辞書の形式を変えない）。S0-6 で重すぎれば、辞書の形式に節を足す案に切り替える。
11. **↑↓ キー**: 割り当てない（候補の移動は Space と Shift+Space のまま）。**【置き換え済み: ADR 0014（2026-10-15）。↑↓ は次／前の候補で、文節のモードには入らない】**
12. **評価の判定**（§7.2）: 既存のセットで文節の UI の平均打鍵数が今の UI を超えないことを完了条件にする。区切りの F1 と再変換の読みの一致率は、最初の実測を見てから基準を決める。

**見つかった問題と、それを受けた決定**:
- Chrome や VS Code（Electron）では、Esc で元に戻したあとに Cmd+Z を押すと、変換中の下線つきの表示がアプリの「元に戻す」で復活する。殻は何も入力していない状態なので、Enter がアプリに渡り、チャット欄ではメッセージが送られてしまう（ユーザーの報告）。
  1. Esc で元に戻すときは、元の文字列を `insertText(元の文字列, replacementRange: 変換中の範囲)` の1回の確定で書き戻す。変換中の状態を、アプリの元に戻す履歴に残しにくくする。
  2. **取り残された変換中の文字列を守る**: 殻が何も入力していない状態で Enter（と Esc）を受けたとき、`client.markedRange()` が有効な範囲を返すなら、その文字列を `insertText` で確定するだけにしてキーを消費する（アプリに渡さない）。再変換に限らず、どの経路で取り残された下線でも、意図しない送信を防ぐ。

### 16.4 契約コミットでの本文からの変更（2026-10-13）
契約の置き場所は [phase2-contract.md §6](../phase2-contract.md)。本文（§5.1、§8、§9、§11.2）との違いは次のとおり。
- `Converter::reconvert` は `Result<Segmented, SegmentError>` を返す（読める部分がなければ `Empty`。§9.3 の「始めない」を型で表す）。
- `Segmented` に `whole()` / `whole_mut()` / `origin()` を足した（`ConvertReply.candidates` と旧式の `PageRequest`、`Commit` が読み全体の変換を使うため）。
- §16.1-3 に合わせ、2文節以上の数字キーは選ぶだけで次の文節へ進む（§8.2 の表の「全体を確定」は取り下げ）。エンジンに送るものは変わらない（確定は `CommitSegments`）。
- §16.1-7 に合わせ、`reconvert` は割り当てられる操作の 1 つ（`KeymapAction.reconvert`）。再変換の選択範囲は `handle(_:surrounding:selection:)` でコントローラが渡す（`SelectedText`）。
- §16.3: `KeyAction.restore`（Esc で 1 回の `insertText`）と `KeyAction.resolveStrayMarkedText`（取り残された変換中の文字列を守る）を契約に置いた。中身は S のレーン。
- 候補ウィンドウのアンカーの矩形は、`attributes(forCharacterIndex:)` に変換文字列の中の相対位置を渡して取る（S0-3。`firstRect` は使わない）。

### 16.5 実装の結果（2026-10-13、統合）
4 レーン（C コア、E エンジン、V 評価、S 殻）をマージし、実辞書で評価した。数値の全体は [eval/reports/phase3-segments.md](../../eval/reports/phase3-segments.md)。
- **区切りの F1**（`segments.tsv` 145 件）: 全体 0.885（適合率 0.973、再現率 0.811）、dev 0.892、test 0.846。取り逃し（助詞のあとの用言をつなぐ）が主。
- **打鍵数**: 部分と伸縮の dev は文節の UI のほうが少ない（部分 3.66 → 3.26、伸縮 7.56 → 3.12）。
- **完了条件 §16.1-12（既存のセットで平均が今の UI を超えない）**: homophones 2.0000 → 2.0000、homophones-ext 2.0986 → 2.0956、katakana-suffix 2.1593 → 2.0796 は超えない。**hiragana は 2.0000 → 2.0175 で超えた**（1 件、`ときがたつ` → `時が経つ`、2 → 4 打鍵）。4 セット合計では 10 打鍵少ない。原因は、2 文節以上のとき数字キーが確定でなく選ぶだけ（§16.1-3）であること。判断はリードとユーザー（§16.6 で、最初の Space を全体の候補にして解消した）。
- **再変換の読みの一致率**: 324 / 363 = 89.3%（hiragana、homophones、homophones-ext は 100%、katakana-suffix は 71.3%）。漢字だけの複合語 30 組は、解析器が未知語 1 つにするため始められない（`Empty`）。**要調査**（→ §16.6 で原因を確かめて直した: 354 / 363 = 97.5%、始められない 0）。
- **速さ**: 実辞書で、コアの `segment` / 文節の 1 ページ目 / `resize` / `reconvert` の p99 はいずれも 0.3 ms 未満。**エンジン経由の再変換は p99 2.7 ms（目標 2 ms をわずかに超える）、p50 は 0.06 ms**。目標の p99 を満たしていないことを記録する（直すかどうかは未決）。
- **読みの逆引き表**: release で約 0.11〜0.18 秒、約 32.5 MiB。debug では約 1.05 秒（テストの閾値は debug だけ緩めた）。起動のあとに裏で作る（`Dictionary::warm_reading_index`）。
- **smoke**: secure のセッションの再変換は、エンジンが `BAD_REQUEST` で拒否するのが正しい挙動。smoke の期待値をそれに合わせた（実行はリードが行う）。

### 16.6 決定: 最初の Space は全体の候補を出す（2026-10-13、ユーザー）
- 評価（§16.5）で、最初の表示が2文節以上に分かれ、目標が全体の候補の2〜9番目にあるケースの打鍵数が、今の UI より増えた（例: ときがたつ → 時が経つ が 2 → 4 打鍵。hiragana で 2.0000 → 2.0175）。
- **決定**: 変換の始まり（Space）は、今までどおり読み全体の候補を出し、数字キーで確定できる。文節の操作（←/→ でフォーカスを移す、Shift+←/→ で区切り直す）を押したときにだけ、文節のモードに入る。文節のモードの中の数字キーは、§16.1-3 のとおり選ぶだけ。
- 表示: 全体の候補を出している間も、変換文字列には文節の区切り（`markedClauseSegment`）を付けてよい。フォーカスの太い下線は、文節のモードに入ってから付ける。
- 完了条件 §16.1-12 は、この変更のあとで測り直す。

**実装の規則（2026-10-13、殻の状態機械 `InputStateMachine`。エンジンとコアは変えていない）**:
- **全体の候補を出している間**（最初の Space のあと）: 状態は今までの 1 文節の変換と同じ（`ConvertingState.segments` は読み全体の 1 文節）。Space / Shift+Space は全体の候補のページ送り（`Page`）、数字キーと Enter は全体の確定（`Commit`。学習は今と同じ）、F6〜F10 は読み全体の字種変換（文節ごとの字種変換 §16.1-5 は、文節のモードの中だけ）、Esc / BackSpace は読みへ戻る。エンジンが返した 2 文節以上の区切りは `ConvertingState.wholeLayout` に覚えておく。
- **区切りの表示**: 表示している全体の候補が最初の区切りの表記と一致するとき（0 番など）だけ、`markedClauseSegment` で区切りを付ける（フォーカスなし = 全部の文節が細い下線。`MarkedText.focused == nil`）。別の表記を選んでいるときは区切りの付けようがないので、今までの見た目（全体を太い下線）にする。
- **文節のモードに入るキー**: ←/→（`segment.focus_left/right`）と Shift+←/→（`segment.shrink/expand`）。入ったあとの振る舞いは §8.2 のとおり（数字キーは選ぶだけ。確定は Enter の `CommitSegments`）。
  - **→**: フォーカスは先頭の文節にあるものとして扱い、2 番目の文節へ移す（入るキーと移動が 1 打鍵）。**←**: 末尾の文節にフォーカスを置くだけ（表示は変わらない。2026-10-28 に先頭から変更。キャレットが末尾にあるため。#87）。どちらも**表示している表記を変えない**。
  - **全体の候補で 0 番以外（別の表記）を選んでから ←/→ を押したとき**: 各文節の最初のページ（`SegmentPage` の 1 ページ目。取っていなければこのとき取る）の候補を 1 つずつ選んでつなぐと、その表記になる組み合わせがあれば、その選択（順位の小さい組を優先）を引き継いで入る。例: 全体の 2 番「始めてしった」は 始めて（文節 0 の 2 番）+ しった（文節 1 の 2 番）なので、→ で入ると文節 1 にフォーカスし、文節 0 は「始めて」を選んだまま。**組み合わせがない（「はじめて仕った」のように、全体の候補だけにある表記）とき、または組み合わせを探すページの取得に失敗したときも、文節のモードには入る**（2026-10-13 に変更。入れないと ←/→ が効かないように見える）。このとき選択はすべて 0 番で、表示は文節の最初の候補をつないだものに変わる（全体の候補で選んでいた表記は保てない）。表記と矛盾する選択を作らないため、最初のページ以外の候補は組み合わせの探索に使わない。→ でフォーカスを移す文節のページが取れなければ、入らずに何もしない（全体の候補のまま）。
  - **Shift+←/→**: 先頭の文節（フォーカスの初期位置）の区切り直し。区切りの作り直しで文節の選択はすべて 0 番に戻る（§4.2）ので、全体の候補で選んでいた表記は捨てる（区切りを変える操作の結果であって、表記を保つ操作ではない）。区切り直しに失敗したら全体の候補のまま。
  - 1 文節に分かれる読みは、今までどおり（←/→ は何もしない。Shift+← は縮めて 2 文節のモードに入る）。
- **打鍵数への影響**: 全体の候補にある目標は、いつも今の UI と同じ打鍵数で届く。全体の候補にない目標（一部の文節だけを変える）で、先頭の文節を選び直すときは、文節のモードに入る ← の 1 打鍵が増える（最初から文節のモードだった §16.5 の時点より 1 多い。例: Space、←、2、3、Enter）。→ で入る場合（2 番目以降の文節を変える）は増えない。
- **評価**: `ikari-eval ops` の文節の UI をこの規則に合わせた（`eval/src/ops.rs`。全体の候補と文節のモードへの入り方を殻と同じ規則でモデル化）。結果は [phase3-segments.md](../../eval/reports/phase3-segments.md) §3.2。既存のセットで平均の打鍵数が今の UI を超えるものはなくなった（全体の候補にある目標は今の UI と同じ打鍵数のため）。§16.1-12 は達成。

**再変換の残課題1の解決（2026-10-13）**: 漢字だけの複合語（関数名、飛行機、効果的、構造化 など 30 組）で `reconvert` が `Empty` を返す問題。
- **原因**: `LatticeContextAnalyzer` の未知語のノード（同じ文字種の最長の連続を 1 ノードにする）のコストが、長さによらず `cost_per_char`（実辞書で 10000）の 1 回分だった。漢字 3 文字の複合語は辞書の語（飛行機 11443、効果的 12407、関数 + 名 に連接）より安くなり、未知語 1 つ（`word = None`）に解析され、読めないので `Literal` だけになって `Empty` になった。変換のラティス（`lattice.rs`）の未知語は 1 文字ずつなので、解析器だけが食い違っていた。
- **直し方**: `analyze_text`（再変換が表記を語に分ける解析）だけ、未知語のコストを `cost_per_char × 文字数` にした（`UnknownCost::PerChar`）。§9.3-2 の「`LatticeContextAnalyzer` と同じ解析」は、この 1 点だけ違う。左文脈の解析（`analyze`）は今までの付け方（`PerNode`）のまま。
- **1 位は変わらない**（確認した）: 5 セット × 3 構成（cost、topic、full。LM なし）の `--out-cases` の列 1〜7 がバイト単位で一致、`snapshot.sh --compare` も差分 0。
- **結果**: 再変換の読みの一致率 89.3% → 97.5%（354 / 363）、始められない 30 → 0。残る 9 組は 1 文字の語の読み（名、者、的、型、内、外、人、米）と `ユーザー名` で、仕様の範囲（§9.3-3）。実辞書のテスト（`segment_real`）に `refused == 0` の確認を足した。
- **未適用の選択肢**: 左文脈の解析にも `PerChar` を使うと、homophones-ext の正解数が 950 → 973（+23）になる（1 位が変わるのは 30 件。良くなった 44 件、悪くなった 2 件）。1 位が変わるため適用していない。採用はユーザーの判断。詳細は [phase3-segments.md](../../eval/reports/phase3-segments.md) §3.3。

### 16.7 決定: 左文脈の解析でも未知語のコストを文字数に比例させる（2026-10-13、ユーザー）
- §16.6 で再変換の解析（`analyze_text`）に入れた修正を、左文脈の解析（`analyze`）にも入れた。`UnknownCost` を廃し、未知語のコストは常に `cost_per_char × 文字数`。
- 効果（LM なし、full）: homophones-ext の1位正解 950 → 973（+23）。1位が変わったのは30件で、順位が上がったもの44件、下がったもの2件。homophones（12/14）、hiragana（135/140）、katakana-suffix（114/145）は変わらない。
- `scripts/check.sh` 通過。評価の基準（snapshot）は、この変更以後の値に更新する。

### 16.8 修正: 助詞のあとの用言は別の文節にする（2026-10-13）
- 現象: 「かみをきる」が 1 文節（髪を切る）になる。評価の取り逃しの多く（15 件）も、助詞のあとの用言だった。
- 原因: Sudachi は「切る」「行く」「ある」「付く」「いい」など普通の用言を、補助用法と同じ項目（品詞2 が `非自立可能`）にしている。§2.2 の表がこの品詞を一律に付属語にしていたため、助詞のあとの用言が左の文節に付いた。
- 直し: 役割 `Dependent` を足した（`core/src/pos.rs`）。左の語が `closes_phrase`（接続助詞以外の助詞、副詞、連体詞、接続詞）なら新しい文節を始める。区切りだけの変更で、全体の候補の1位と表示は変わらない。
- 結果: F1 0.885 → 0.983（dev 0.892 → 0.980、test 0.846 → 1.000）、悪化したケースなし。数値は [phase3-segments.md](../../eval/reports/phase3-segments.md) §3.1、§5。
- 副作用（許容）: 助詞で終わる語のあとの `ない`、`こと` も文節を始める（本では｜ない、人の｜こと）。

## 追記（2026-10-24。#291）文節のフォーカスは端で反対の端へ回る
文節のモードで、最後の文節で → を押すと先頭の文節へ、先頭の文節で ← を押すと最後の文節へフォーカスが移る（ユーザー要望）。文節が 1 つのときは動かない。全体の候補から文節のモードに入る最初の ←/→ は、今までどおり（← は先頭にフォーカスを置くだけ、→ は 2 番目へ）。
