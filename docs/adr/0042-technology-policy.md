# ADR 0042: 技術選定の方針（言語は Rust を基本にする。境界をまたぐのは必要なときだけ）

- 状態: 承認（2026-10-30。ユーザー決定。§4 の「Rust への移行は最優先」は、2026-11-11 から Windows の実装が最優先に改まった（ADR 0040 §9、CLAUDE.md）。Rust への移行（#138）は完了。本文は書き換えない）
- 日付: 2026-10-30
- 対象: ikari-ime 全体の言語の選び方。個別の移行の設計は ADR 0041（状態機械）、Windows は ADR 0040
- タスク: Rust 移行の親 issue（最優先。CLAUDE.md の「優先順位」）

---

## 1. 方針（ユーザー決定。2026-10-30）

1. **OS に依存しないものは、可能な限り Rust で実装する。** 言語をまたぐとバグが増え、保守のコストが上がるため。Swift など別の言語は、その必要があるときだけ使う。
2. **判断は Rust に置く。** 状態機械、キー割り当て、配置の計算、設定の読み書きと検証、エンジンへのメッセージ作り、診断ログの整形。OS の入口は、OS のイベントを Rust に渡し、Rust が返した動作を実行するだけにする。**入口に判断（分岐）が増えたら、Rust に移す。**
3. **言語をまたぐ境界は、数を減らし、細く保つ。** 基準は「使う言語の数」ではなく「境界の数と太さ」。境界の形（proto か C の構造体か）は、保守負担が小さければ速さで選んでよい（ADR 0041 Q5。2026-10-30 ユーザー決定: 推奨どおり、M0 の計測のあとに決める）。
4. **UI は OS ごとに別に作ってよい。** 設定画面、候補ウィンドウなど、見た目と操作感が大事なものは、その OS に合う言語・部品で、きれいに作る。**保守性を妥協してよいのは、ここだけ。** ただし配置や表示内容の計算は Rust に置き、OS 側は描くだけにする。
5. **ビルド・検証のスクリプトも、シェルに依存しない。** Windows でもビルドできるよう、Windows でも要るもの（check、辞書のビルド、データの取得・配置、評価）は `cargo xtask`（Rust）に寄せる。macOS 専用のもの（署名、install、smoke）はシェルのままでよい。段階的に包み、一度に置き換えない。
6. **大胆に移行してよい。** 作者以外の利用者がまだいない間は、段階的な互換や長い併存期間を持たない（2026-10-30 ユーザー決定）。守るのは、共通のシナリオ（期待の一致）だけ。

## 2. 線引き

| 置き場所 | 内容 |
|---|---|
| Rust | 状態機械、キー割り当て、配置の計算、設定の検証、エンジンとのメッセージ、診断ログ、辞書・評価の道具、ビルドと検証のスクリプト（Windows でも要るもの） |
| OS ごとの言語（薄く） | OS のイベントの受け取りと動作の実行（macOS: InputMethodKit、Windows: TSF の TIP）、secure な入力の判定など OS の API でしか取れないもの |
| OS ごとの言語（UI） | 設定画面、候補ウィンドウ、メニュー |
| シェル | macOS 専用の署名、install、smoke |

macOS の入口を Rust にできるか（`objc2` などで InputMethodKit を使えるか）は未検証。スパイクで確かめ、だめなら Swift の薄い入口にする（ADR 0041 の M0）。

## 3. 例外の扱い
- 例外（Rust にしない理由がある）は、ADR か issue に理由を 1 行で書く。
- 外部の道具で代替が難しいもの（例: 評価の Python の分析スクリプト）は、移行の対象にしない。

## 4. 影響
- Rust への移行は、すべてのタスクのなかで最優先にする（2026-10-30 ユーザー決定）。着手の順序と範囲は ADR 0041 とその親 issue で管理する。
- 既存の Swift 側の新機能の追加は、移行の方針（ADR 0041 §6）に従って止めるか、Rust に先に入れる。
