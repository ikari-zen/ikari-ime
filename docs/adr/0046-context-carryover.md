## 0. 現状の把握（#182 の調査と、コードを読んだ範囲）

- 左文脈の組み立ては `engine/src/session.rs` の `build_context_borrowing`。分かれ方は 3 つ。
  1. 周辺テキストが取れた（`available`）: 入力欄の左の末尾（最大 2000 文字）だけ。**確定履歴は足さない**。左が空でも足さない。
  2. 取れない・同じセッションの履歴あり: 履歴の表記を区切りなしで連結した末尾。
  3. 取れない・履歴なし: 直近 `BORROW_WINDOW`（2 分）以内のほかのセッションの確定（X5。`left_borrowed = true`）。
- 借りる条件（`context_for` の `nothing_here`）は「secure でない・履歴が空・`available` でない」。`available` で左が空の入力欄では借りない。
- セッションの ID は shell-core の `make_client` が振る。**アプリが替わるたびに新しい ID**（`next_session_id`）。A → B → A と戻ると A は新しい ID になり、A の古いセッションは engine の中で休止のまま 30 分後に消える。つまり D1（休止と再開）が効くのは、同じアプリの中で ikari を切り替えたときだけで、アプリを行き来したときには効いていない。
- LM は `left_text` の末尾 40 文字だけを見る（`zenz.context_chars`、`lm/src/ranker.rs` の `build_request_parts`）。話題（chiVe）、文書内キャッシュ、連接（`LeftContextRanker`）は `left_text` 全体と `history` を見る。
- zenz v3 のプロンプトは `[EE03 プロフィール][EE04 話題] EE02 左文脈 [EE07 右文脈] EE00 読み EE01`（`lm/src/prompt.rs`）。左文脈は「同じ文書で直前にある文」として学習されている（ADR 0002 §0.4。azooKey の `ZenzPromptBuilder` で確認した形式）。左文脈の中に「別の文書の境目」を表す印はない。改行が学習データにどれだけあるか、トークナイザがどう扱うかは**確かめていない**。
- 評価: ADR 0015 §0.6 と §4 の測定（homophones-ext 1266 件）。
  - 直前の文脈が届くかどうかがほとんどすべて（LM あり 610 → 1093）。
  - 無関係な文「だけ」が左にあるのはほぼ中立（610 → 617）。
  - **本当の文脈の前に無関係な文（約 150 字）があると害が大きい**（1093 → 950。LM なし 979 → 738）。害の大部分は話題（chiVe）から来る（§4.5）。LM の窓に入る無関係な文字のぶんも残る。
- 評価の scenario（`eval/src/scenario.rs`）とセット（`eval/src/set.rs`）には、`context`（そのまま `left_text`）と `borrowed`（フラグ）しかない。「入力欄の左」と「履歴」と「ほかのアプリの確定」を分けて渡す列がない。eval は engine に依存しないので、engine の組み立てを通らない。

## 1. 問題の定義

ユーザーがチャットで「品詞」の話を送ったあと、次のメッセージで「ひんしを」と打つと、LM は文脈なしで判断して「瀕死を」を 1 位にする。直前に自分で書いた文が、すぐ左にあるのに使われていない。

起きている理由は 2 つ。

1. **入力欄の左が空・短いとき、同じアプリの確定履歴が使われない**。チャットは送ると入力欄が空になる。アプリが周辺テキストを返す（`available`）と、空でも「これが文脈のすべて」として扱い、履歴を捨てる。
2. **アプリを行き来すると、同じアプリの履歴が切れる**。セッションの ID がアプリの切り替えごとに振り直されるため。ブラウザで調べて、エディタに書き、ブラウザに戻ると、ブラウザで書いていた文脈がない。

一方で、測定（ADR 0015 §4）は「**本当の文脈の前に**、関係のない文をつなぐと大きく崩れる」と言っている。足す量と、足す相手（同じアプリか、ほかのアプリか）を絞らないと、直したい場面より多くを壊す。

## 2. 決定の要約（提案）

| # | 決定 |
|---|---|
| E1 | **左が足りないぶんだけ、同じセッションの確定履歴の末尾を左の前に足す**。目標の長さ `carry_fill_chars`（候補は LM の窓と同じ 40。値は掃引で決める）に対して、`available` の左が短いときだけ、足りない文字数ぶんを足す。足した結果は LM の窓を超えないので、プロンプトは今より長くならない |
| E2 | **重なりの除去は「左の全体が履歴の末尾と一致するときだけ」**。左が履歴の末尾（接尾辞）なら、履歴のうち左より前の部分を足す。一致しないとき（確定後の編集、アプリの整形、左が古い、カーソルを動かした、入力欄にもとから文がある）は足さない（安全側） |
| E3 | **つなぎ目**: 足した履歴と、入力欄の左（または読み）のあいだに、**境目だと分かっているときだけ**区切りを入れる。区切りの種類（なし／「。」／改行）は掃引で決める。足した履歴の最後が句読点・閉じ括弧・改行・空白なら何も入れない。同じ入力欄の履歴をそのまま左にする今の経路（取れない入力欄）には入れない（境目かどうか分からない） |
| E4 | **アプリを行き来しても、同じアプリの履歴を保つ**。shell-core が Bundle ID ごとにセッションの ID を覚えて使い回す（最大 64 アプリ。古いものから忘れる）。engine の D1（休止と再開、30 分）がアプリの行き来でも効くようになる |
| E5 | **ほかのアプリの文は、今までどおり「入力欄に何もないとき」だけ借りる（X5 を保つ）**。「何もない」に、`available` で左が空（空白だけを含む）を加える。入力欄の左に文字があるときに、その前へほかのアプリの文を足すこと（X1 の形）はしない。窓 `BORROW_WINDOW` の値はユーザーに聞く（オフラインの評価では測れない。§12 Q1） |
| E6 | **除外とプライバシーの決定は変えない**。`share_context = false` と secure のセッションは、貸さない・借りない（D6）。借りた文脈は学習の文脈に入れない（Q7）。同じセッションの履歴から足したものは、今の「取れない入力欄の履歴」と同じく自分の文脈として扱う（`left_borrowed = false`） |
| E7 | **組み立ては core の純関数 1 つにする**（`compose_left`）。engine と eval が同じ関数を呼ぶ。eval のセットと scenario に `field`・`history`・`recent` の列を足す |
| E8 | 契約の PR では `carry_fill_chars = 0`（今と同じ動き）を既定にし、掃引の PR で既定を替えてユーザーに確認する |

## 3. E1・E2: 足りないぶんを足し、重なりを除く

### 3.1 案の比較

**足す量**

| 案 | 内容 | 良い点 | 問題 |
|---|---|---|---|
| **F1（採用）: 足りないぶんだけ** | 目標 `carry_fill_chars` − 左の文字数 だけ、履歴の末尾から足す | LM のプロンプトは今の最大（40 文字）を超えない（時間が増えない）。話題に入る履歴も最大 40 文字に収まり、ADR 0015 §4 の「前に 150 字」の害の形より小さい。左が十分に長ければ何も変わらない | 目標の値が要る（掃引） |
| F2: 履歴を全部（2000 文字まで）前に足す | 取れない入力欄の今の経路と同じにする | 実装が一番少ない | X1 と同じ形（本当の文脈の前に長い文）。話題に古い文がまるごと入り、測定で −143〜−241 の型の害 |
| F3: LM にだけ足す（話題・連接には足さない） | `Context` に LM 専用の左を別に持つ | 話題の害を入口で止められる | `Context` と LM の契約を増やす。LM なしでは何も得ない。害の大部分が話題だと分かっているが、F1 で話題に入るのは最大 40 文字で、まず測ってから考える（掃引で害が出たら F3 を測る） |

**重なりの除去**

| 案 | 内容 | 良い点 | 問題 |
|---|---|---|---|
| **O1（採用）: 左が履歴の接尾辞のときだけ** | `H.ends_with(L)` のときだけ、`H` の `L` より前を足す。一致しなければ足さない | 誤って二重に足すことも、順序の違う文をつなぐこともない。判定が一行で、境界が明快 | 確定後に少し直した、アプリが整形した、改行を打った、などで足さなくなる（取りこぼし）。取りこぼしは「今と同じ」なので害はない |
| O2: 最長の共通の接尾辞で切る | `L` と `H` の共通の接尾辞の長さ k を求め、`H` の残りを足す | 一部が一致すれば足せる | `L` に履歴にない文（もとからあった文、別の欄の文）が前にあるときも、その前に履歴をつないでしまう（順序が壊れる）。危ない側に倒れる |
| O3: 空白・改行を無視して比べる | 比べる前に両方から空白を除く | 改行を打った入力欄でも足せる | 正規化の規則が増える。取りこぼしの量が分からないうちに入れる理由がない。実際に取りこぼしが目立てば足す |
| O4: 履歴に「入力欄での位置」を持つ | 確定のときの周辺テキストの長さなどを覚えて合わせる | 精確 | 状態が増え、アプリごとの周辺テキストの癖（取れない、古い）にまた依存する |

### 3.2 アルゴリズム（擬似コード）

```
入力:
  field   = Unavailable | Available(L)   // L は入力欄の左（末尾 2000 文字に切ったもの）
  H       = 同じセッションの確定の表記の連結（2000 文字まで）
  R       = ほかのセッションの確定の連結（借りてよいときだけ Some。§5）
  fill    = carry_fill_chars（0 なら足さない）
  J       = carry_joint（None | Period「。」 | Newline「\n」）

compose_left:
  match field
    Unavailable:
      H が空でない          -> left = tail(H, 2000), 出どころ = History      // 今と同じ。区切りなし
      H が空で R あり       -> left = tail(R, 2000) + joint(R), borrowed      // 区切りは E3
      それ以外              -> left = "",            出どころ = Empty
    Available(L):
      L が空白だけ:
        H が空でない        -> left = tail(H, 2000) + joint(H), 出どころ = History  // 送信で空になった入力欄
        H が空で R あり     -> left = tail(R, 2000) + joint(R), borrowed
        それ以外            -> left = L
      deficit = fill - len(L)（負なら 0）
      deficit == 0          -> left = L, 出どころ = Field                    // 十分に長い
      H.ends_with(L) でない -> left = L, 出どころ = Field                    // 一致しない。足さない
      P = H から末尾の L を除いた残り
      P が空                -> left = L                                      // 履歴はすべて見えている
      j = joint(P)          // P の最後が句読点・閉じ括弧・改行・空白なら ""、それ以外は J の文字
      deficit <= len(j)     -> left = L
      left = tail(P, deficit - len(j)) + j + L,  出どころ = FieldWithHistory

joint(X) = X の最後の文字が { 。 ． . ！ ？ ! ? 、 ， 」 』 ） ) 】 改行 空白 } なら "" それ以外は J
```

- `L` が空白だけの `available` は、取れない入力欄と同じに扱う（左には何もない）。違いは、履歴のあとに区切りを入れること（入力欄が空になった＝境目だと分かっている）。右文脈は今どおり `available` の `right` から取る。
- 長さはすべて文字（`char`）で数える。切るのは今の `tail_chars` と同じく文字の単位（語の途中で切れてよい。LM の窓の 40 文字も同じ切り方）。
- `history`（`Context.history`。文書内キャッシュが使う）は今どおり全部を渡す。変えるのは `left_text` だけ。

### 3.4 注意（受け入れる取りこぼしと誤り）

- 例 12 のように、**同じ入力欄の中で、左が短い（入力欄の先頭から数文字）**のときも E2 の一致は成り立つ。このとき P と L のあいだは本当は境目ではない（同じ欄の続き）のに区切りが入る。区切りの有無を見分けるには「入力欄の先頭がどこか」が要るが、周辺テキストの `left` が入力欄の先頭から始まるかは、アプリによって違い、分からない。区切りの掃引（§7）で「なし」と「。」を比べ、この誤りの重さを測る。
- 1 文字だけの左（「を」など）が、偶然、別の欄の履歴の末尾と一致することがある。左に入る文字のほとんどは ikari の確定なので、同じアプリの中ではほぼ正しい。最低の一致の長さは設けない（設けると、送信直後の 1 文字目で効かなくなる）。
- 入力欄に改行や英字（ABC で打った文字）を打つと、一致しなくなり足さない。左に文字があるので、多くは十分な文脈がある。目立つようなら O3 を測る。

## 4. E3: つなぎ目の区切り

| 案 | 内容 | 良い点 | 問題 |
|---|---|---|---|
| J0: なし | 連結するだけ | 今の取れない入力欄の経路と同じ。同じ文の続き（例 12）を壊さない | 「品詞の話をした」+「ひんしを」が 1 文に見える。送信の境目が LM に見えない |
| **J1（初期の候補）: 「。」** | 足した文の最後が句読点などでなければ「。」を入れる | zenz の学習データ（文書の直前の文）で、文の境目はふつう「。」で表れる。公用文の表記の既定とも合う | 例 12 のような同じ文の続きでは、文を切ってしまう |
| J2: 改行 | `\n` を入れる | 「別のメッセージ」に近い | zenz のトークナイザと学習データでの改行の扱いを確かめていない。未知の文字なら害になりうる |
| J3: 区切りのトークン（EE 系の私用の文字） | 文書の境目を表す新しい印 | 意味が明快 | zenz は学習していない。プロンプトの形式を学習時から外す（ADR 0015 D7 の理由と同じ） |

**決定**: 区切りを入れるのは、境目だと分かっている所（足した履歴と入力欄の左のあいだ、空になった入力欄の前、借りた文の後）だけ。種類は J0・J1・J2 を掃引で比べて決める（§7）。J2 は、掃引の前に zenz-v3.2 small の語彙に改行があるかを確かめ、なければ比べない。J3 は採らない。

## 5. E4・E5: アプリをまたぐ文脈

### 5.1 案の比較

| 案 | 内容 | 良い点 | 問題 |
|---|---|---|---|
| **A1（採用）: 同じアプリの ID を使い回す** | shell-core が Bundle ID → セッションの ID を覚える（最大 64。古いものから忘れる）。engine の休止と再開（30 分）がそのまま効く | proto も engine の寿命の決定も変えない。「同じアプリの直前の文」は、ほかのアプリの文より関係が深い | アプリの中で別の入力欄に移っても、同じ履歴が続く（今もアプリを替えなければ同じ）。E2 の一致で、左に文字のある欄には足さない |
| **A2（採用）: X5 の「何もない」に、`available` で左が空を加える** | Electron 系などで、空の入力欄が `available` を返しても借りる | 「ブラウザで調べて、空のエディタに書く」で効く | ほかのアプリの文が LM に入る場面が増える（§6） |
| A3: 左が足りないときに、ほかのアプリの文も前に足す | F1 の材料に、同じセッションの履歴のあと、ほかのアプリの文を足す | 「調べながら、もう文がある文書に書く」でも効く | X1 の形（本当の文脈の前に、ほかのアプリの文）。測定で害が大きい。F1 の上限で量は小さくなるが、まだ測っていない。**今は採らない。掃引で害を測り（§7 の C6）、害が小さければ設定として改めて提案する** |
| A4: 窓 `BORROW_WINDOW` を延ばす | 2 分 → 5 分など | 調べものが数分かかっても届く | オフラインの評価では時間の効きを測れない。実機のログも見ないと決まっている。**値をユーザーに聞く**（Q1） |
| A5: アプリの種類で混ぜる相手を選ぶ（X4） | ブラウザ → エディタは混ぜる、など | 害を絞れる | ADR 0015 と同じく、表を保守する根拠がない。採らない |

### 5.2 別のアプリの話題が流れ込む害の抑え方

1. 入力欄に文字がある、または同じアプリの履歴があるときは、ほかのアプリの文を使わない（X5 を保つ。同じアプリが先）。
2. 借りるのは直近 `BORROW_WINDOW` 以内だけ（値は Q1）。「最近の確定」の保持（10 分）を超えない。
3. 除外するアプリ（パスワード管理、ターミナル。設定で足せる）と secure は、貸さない・借りない（D6）。
4. 借りた文脈は学習の文脈に入れない（Q7 を保つ）。一度の流れ込みが、学習の記録として残らない。
5. 借りた文の後には、E3 の区切りを入れる（別の文書の境目）。

## 6. プライバシー

- 変わること（1）: **ほかのアプリの文が LM のプロンプトに入る場面が増える**。今は「周辺テキストが取れない・履歴なし」だけだったのが、「取れるが左が空」の入力欄にも広がる（A2）。プロンプトは手元の LM にだけ渡り、外には出ない（NFR-17）。画面に出るのは候補だけで、借りた文字そのものは出ない。
- 変わること（2）: **アプリに戻ったとき、そのアプリで 30 分以内に書いた文が文脈に残る**（A1）。今も、アプリを替えなければ 30 分残っている。替えたら切れていたのが、切れなくなる。メモリだけで、保存しない（D8）。
- 変わること（3）: shell-core が、Bundle ID と ID の対応を最大 64 件、メモリに持つ。保存しない。engine には今どおり Bundle ID を渡さない（ログの `app=` は今と同じ）。
- 変えないこと: secure、除外するアプリ（`share_context = false`）、借りた文脈で学習しないこと（Q7）、保存しないこと（D8）、ログに中身を書かないこと。
- 残ること: ブラウザのプライベートウィンドウは見分けられない（Bundle ID が同じ）。気になる人は除外のアプリに入れる。この説明を設定の画面か文書に書くかは、実装の PR で決める。

## 7. 評価の整備と掃引の計画

### 7.1 形式（eval）

- **セット**（`eval/src/set.rs`）と **scenario**（`eval/src/scenario.rs`）に、任意の列を 3 つ足す。
  - `field`: `none`（周辺テキストが取れない）／`available`（`context` の列を入力欄の左とする）。**列がない、または空なら今と同じ**（`context` をそのまま `left_text` にする）。
  - `history`: 同じセッションの確定の表記の連結（1 つの文字列）。
  - `recent`: ほかのセッションの確定の連結（窓の中だとみなす）。空なら借りない。
  - `field` があるときは、eval は `compose_left` で `left_text` と `left_borrowed` を作る。今の `borrowed` の列は、`field` がないときだけ使う（両方あれば読み込みでエラー）。
- 引数: `--carry-fill N`、`--carry-joint none|period|newline`（既定は契約の既定）。
- **派生セット**（`eval/scripts/make_carry_sets.py`。`make_long_context_set.py` と同じ作り方。homophones-ext から作る）

| 名前 | 作り方 | 何を測るか |
|---|---|---|
| C1 carry-empty | field=available, L=空, H=元の文脈 | 送信で空になった入力欄。ext-full（1093）に近づくか。区切りの害（元の文脈は文の途中なので「。」は不利。区切りの最悪の場合） |
| C2 carry-overlap | L=元の文脈, H=関係のある前の文 + 元の文脈 | 重なりの除去と、関係のある前の文の効き |
| C3 carry-unrelated | L=元の文脈, H=別のケースの文脈（無関係・約 150 字）+ 元の文脈 | **害**。ext-mixlong と同じ材料を、F1 の上限で足したとき |
| C4 carry-mismatch | L=元の文脈, H=別のケースの文脈（L で終わらない） | 不変条件。ext-full と 1 件も違わないこと |
| C5 carry-empty-unrelated | L=空, H=別のケースの文脈 | ext-stale と同じ形。文脈なし（610）より悪くならないか |
| C6 borrow-short（A3 の判断用） | L=元の文脈, H=空, R=別のケースの文脈 | A3 を入れたときの害。今回は既定に入れない |

- C2 の「関係のある前の文」と、チャットの形（前のメッセージが完結した文、次のメッセージの頭で同音語）は homophones-ext から作れない。**小さな手書きのセット `eval/sets/carry-chat.tsv`**（50〜100 行。Claude の下書き、ユーザーが確かめる。ADR 0015 Q8 と同じ扱い）を足す。「名詞や動詞など、品詞の話をした」→「ひんしを」をここに入れる。
- **scenario** `eval/scenarios/c182-carryover.tsv`（LM あり・なしで流す）:
  1. available・L 空・H「名詞や動詞など、品詞の話をした」・ひんしを → 品詞を が 1 位（LM あり）。
  2. 同じで field=none → 品詞を が 1 位（今の経路の回帰）。
  3. available・L「次は」・H「名詞や動詞など、品詞の話をした。次は」・ひんしを → 品詞を が 1 位（重なり）。
  4. available・L 空・H 空・R「名詞や動詞など、品詞の話をした」・ひんしを → 品詞を が 1 位（借りる。A2）。続けて同じ R で commit しても、R のない probe の 1 位が変わらない（Q7。b28-borrowed と同じ不変条件）。
  - LM なしの期待は、実装の PR で流して決める（LM なしで 品詞を が 1 位になるかは測っていない）。期待が立たない probe は `not_top1` を使わず、結果だけを報告に書く。
- **単体テスト**: core の `compose_left` に §3.3 の表をそのまま入れる。engine に、`share_context = false` と secure で借りないこと、A2 の条件のテスト。shell-core に、A → B → A で A の ID が戻ること、65 個目で最も古い対応を忘れること。

### 7.2 掃引（LM あり・なし。値は計測で決める）

- 軸: `carry_fill_chars` ∈ {0, 10, 20, 40} × `carry_joint` ∈ {none, period, newline（語彙にあれば）}。LM ありは zenz-v3.2 small、締め切り 3000ms（時間切れを除くため。ADR 0015 §4.7）。LM なしは `--ranker full` の LM を切ったもの。
- セット: C1〜C5、carry-chat、scenario、そして全セット（`eval/scripts/snapshot.sh`）。
- 決め方（案。ユーザーに表を出して決める）:
  1. C4 と全セットの 1 位が、`fill = 0` と比べて悪化しない（必須）。
  2. C5 が文脈なし（ext-empty）より悪くならない（LM あり。必須）。
  3. そのうえで、C1・C2・carry-chat の直った数 − C3 の崩れた数 が最大の組を推奨にする。C3 の崩れが C1・C2 の得を上回る `fill` は採らない。
  4. LM ありと LM なしで推奨が分かれたら、LM ありを優先（ikari の普段の構成）し、LM なしの差を併記する。
- 時間: F1 ではプロンプトが 40 文字を超えないので、LM の応答時間は変わらない見込み。perf の比較（`cargo xtask perf`）を 1 回だけ流して確かめる。
- 測れないもの: `BORROW_WINDOW` と、A1 の効く頻度（時間とアプリの行き来）。実機のログは見ないと決まっているので、Q1 で決める。

## 8. 契約（変更する関数、型、定数、ファイル）

- **core**（新しい `core/src/context_carry.rs`。`lib.rs` から公開）

```rust
pub enum FieldLeft<'a> { Unavailable, Available(&'a str) }
pub enum CarryJoint { None, Period, Newline }
pub struct CarryParams { pub fill_chars: usize, pub joint: CarryJoint }
pub struct LeftSources<'a> {
    pub field: FieldLeft<'a>,
    pub history: &'a str,          // 同じセッションの確定の連結
    pub recent: Option<&'a str>,   // 借りてよいときだけ Some（判定は呼び出し側）
}
pub enum LeftOrigin { Empty, Field, FieldWithHistory, History, Borrowed }
pub struct ComposedLeft { pub text: String, pub borrowed: bool, pub origin: LeftOrigin }
pub fn compose_left(src: &LeftSources<'_>, p: &CarryParams, max_chars: usize) -> ComposedLeft;
```

  - `max_chars` は engine の `MAX_CONTEXT_CHARS`（2000）。`LeftOrigin` はテストと、将来のログの出どころの数え方（ADR 0015 §3.7）のため。今回はログに足さない。
- **engine**
  - `context_limits.rs`: `CARRY_FILL_CHARS: usize = 0`（契約。掃引で替える）、`CARRY_JOINT: CarryJoint = CarryJoint::None`（同）。`ContextLimits` に `carry: CarryParams` を足す。`BORROW_WINDOW` は Q1 の答えで替える（契約では 2 分のまま）。
  - `session.rs`: `build_context_borrowing` の分かれ方を `compose_left` に置き換える（secure の早期の戻りと `right_text` は今のまま）。`context_for` の借りる条件を「secure でない・履歴が空・入力欄が空（取れない、または左が空白だけ）」にする。`borrowed_left` は今のまま（窓と除外の判定）。
- **shell-core**（`controller/mod.rs`）: `session_ids: Vec<(String, u64)>`（Bundle ID → ID。最大 64。使うたびに末尾へ）を持ち、`make_client` はそこから ID を引き、なければ `next_session_id`。値は 64（engine の `SESSION_LIMIT` より小さく、日常に開くアプリの数より大きい。動作に効かない上限なので計測しない）。
- **eval**: §7.1 の列と引数。`make_carry_sets.py`、`carry-chat.tsv`、`c182-carryover.tsv`、`eval/tests/scenario_lm.rs` に scenario を足す、`snapshot.sh` に派生セットを足す。
- 変えないもの: proto（`BeginSession` も `SurroundingText` もそのまま）、Swift、`lm/`（`context_chars = 40`）、学習の形式、`Context` の型（`left_text`、`left_borrowed`、`history` のまま）。

## 9. 実装の進め方

1. 契約の PR（1 つ）: core の型と `compose_left`（§3.3 の単体テストつき）、engine の置き換え（既定 `fill = 0` なので今と同じ動き。ただし E5 の借りる条件の広がりと区切りは `fill` に依らないので、`CARRY_JOINT = None` で今の文字列と同じになることをテストで確かめる）、eval の列と引数。
2. レーンを並行に（worktree）: (a) shell-core の ID の使い回し（E4）、(b) eval の派生セットのスクリプトと carry-chat の下書き、scenario。
3. 掃引の PR: §7.2 を流し、報告を `eval/reports/` に置き、既定の値を替える。ユーザーに表で確認してからマージする。
4. Q1 の答えで `BORROW_WINDOW` を替える（同じ掃引の PR か別の PR）。

## 10. 関係する ADR

- **ADR 0015**: D1（休止と再開）はそのまま。A1 で、アプリの行き来でも効くようになる。D5 の X5 は保ち、「何もない」の定義だけを広げる（A2）。D6・D8・Q7 は変えない。D7（LM の窓 40）は変えない。F1 は窓の中の空きを埋めるだけ。この ADR が採用されたら、0015 の D5 の行に「0046 で改めた」と書く。
- **ADR 0044**（学習の word の加点。マージ済み）: 独立。ただし、足した履歴は学習の文脈（Bag など）の特徴量にもなるので、文脈つきの学習の引き当てが今より増える。a-02、b28-borrowed、0044 のシナリオが変わらないことを全セットの確認に含める。
- **ADR 0045**（直前ボーナス。別ブランチで提案中）: どちらも「ひんしを」の例を直すが、効く場面が違う。0045 は「同じ読みで一度選んだあと」、この ADR は「選ぶ前に、文脈で 1 位にする」。0045 は LM の外の加点で、LearningGuard を通るので、この ADR で左文脈が届くようになると、0045 の加点を左文脈の証拠が止める場面も増える（意図どおり）。なお 0045 の直前の選択は engine 全体で 1 つで、`share_context = false` のアプリの選択も入る形に読める。除外のアプリの扱いを揃えるかは 0045 の側で決める（ここでは決めない）。
- **#178**（左文脈は直前ほど強く）: F1 で足すのは直前の文だけで、量も小さい。#178 の結論で LM の窓や話題の重みが変われば、`carry_fill_chars` を測り直す。

## 11. 懸念

- 区切りの誤り（§3.4 の例 12）と、F1 で話題に入る無関係な文の害は、掃引で測るまで大きさが分からない。害が大きければ `fill` を小さくするか F3（LM にだけ足す）を測る。
- Electron 系の入力欄が本当に「`available` で左が空」になるかは、実機で確かめていない（#182 の推測。ユーザー決定で確かめずに進める）。そうでなくても、A1 と E1 は取れる入力欄の短い左で効く。
- 空の入力欄の先頭にカーソルがあり、右に文がある（文書の頭に書き足す）とき、A2 と §3.2 で、履歴やほかのアプリの文を左に置く。右文脈は今どおり渡る。害は X5 の測定（ほぼ中立）と同じ形とみなす。

## 12. ユーザーに聞くこと

- **Q1. ほかのアプリの文を借りる窓（`BORROW_WINDOW`）**: 2 分（今）／5 分／10 分（保持の上限）。オフラインでは測れない。長いほど「調べてから書く」に届き、無関係な文も届きやすい（ただし借りるのは入力欄に何もないときだけ）。**推奨: 5 分**（#182 の「数分」。保持 10 分の中に収まる）。
- **Q2. アプリをまたぐ共有の広げ方（プライバシー）**: (a) 左が空の `available` の入力欄でも借りる（A2）、(b) アプリに戻ったら、そのアプリの 30 分以内の履歴を続ける（A1）。どちらもメモリだけ、除外のアプリと secure は今どおり。**推奨: 両方入れる**。
- **Q3. 入力欄にすでに文があるときは、ほかのアプリの文を足さない（A3 を今は採らない）でよいか**。「ブラウザで調べて、書きかけの文書に書く」では、ブラウザの文は使われない（同じ文書の文が先）。**推奨: 採らない**。C6 で害を測り、小さければ設定として改めて提案する。
- 値（`carry_fill_chars`、区切りの種類）は、掃引のあとに表で聞く（§7.2）。
