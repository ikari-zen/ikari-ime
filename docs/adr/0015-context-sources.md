## 0. 現状の把握

### 0.1 文脈の通り道
1. **殻が周辺テキストを取る**（`ClientAccess.surroundingText()`）。IMK のクライアントに `selectedRange()` と `markedRange()` を聞き、変換中の文字列（なければ選択）の**手前を最大 2000 文字**、後ろを最大 200 文字、`string(from:actualRange:)` で取る。左が取れなければ `available = false`。`client.length()`（文書の長さ）は右の文脈にだけ使う。
2. 取るのは、合成の始め（最初のかな、Shift＋英字の始め）と変換の始め（Space）。確定までは同じ値を使い回す（`cachedContext`）。secure（`IsSecureEventInputEnabled()`）のときは取らない。
3. **エンジンが文脈を組み立てる**（`Inner::build_context`）。
   - 周辺テキストが `available` なら、左文脈 = アプリの左の末尾 2000 文字、右 = 先頭 2000 文字。
   - そうでなければ、左文脈 = そのセッションの確定履歴（最大 32 件）の表記をつないだものの末尾 2000 文字。
   - どちらの場合も、確定履歴そのもの（`Context.history`）を渡す（文書内キャッシュが使う）。
   - 再変換は周辺テキストだけを使い、履歴は使わない（選択が履歴の末尾にあるとは限らないため。ADR 0006）。
4. **core が左文脈を解析し、部品ごとに別々の量を使う**:

| 使い手 | 使う範囲 | 量（今の値） |
| --- | --- | --- |
| 解析（`LatticeContextAnalyzer`） | 左文脈の末尾を文ごとに解析する | 2000 文字（`CONTEXT_WINDOW_CHARS`） |
| 左文脈の連接・複合語（`LeftContextRanker`、ADR 0007） | 解析の最後の語と文の終わり方 | 直前の 1 語 |
| 文書内キャッシュ（`DocumentCacheRanker`） | 解析窓の内容語と、確定履歴の表記（距離 0） | 窓の全体。500 文字より遠い語は加点が半分 |
| 話題（`TopicRanker`、chiVe） | 解析の内容語の新しい方から | 50 語（`topic.recent_tokens`） |
| LM（zenz-v3.2 small） | 左文脈の**末尾 40 文字**（`zenz.context_chars`）、話題の語 3 つ（解析の内容語を回数→新しさで選ぶ）、属性プロファイル | 40 文字。毎回プロンプト全体を評価し直す（KV キャッシュの使い回しはない）。プロンプトの上限 512 トークン |
| 学習の特徴量（`features.rs`） | Prev（最後の語）、PrevContent（10 語以内の内容語）、Bag（内容語 20）、Topic（内容語 50 のクラスタ） | 同左 |
| 右文脈（`Context.right_text`） | **どこも使っていない**（殻は毎回送っている） | ― |

- LM の 40 文字は、ADR 0002 §0.4 で azooKey の `ZenzPromptBuilder` の形式に合わせた値（zenz の学習時の形式と見なしている）。

### 0.2 セッションの単位と寿命
- IMK はクライアント（入力欄を持つアプリのウィンドウや入力欄）ごとに `IkariInputController` を作る。セッション ID はコントローラごとに 1 つで、コントローラが生きている間は変わらない。
- `activateServer`（ikari に切り替えた、そのアプリに戻った）のたびに `BeginSession` を送る。エンジンはセッションを**作り直し、確定履歴を空にする**（`sessions.insert`）。
- `deactivateServer`（ABC に切り替えた、別のアプリに移った）で `EndSession` を送る。エンジンは**セッションごと消す**。
- secure が変わったときも `BeginSession` を送るので、履歴は消える（これは意図どおり）。
- まとめ: **確定履歴は「最後に ikari を有効にしてから、そのクライアントで確定したもの」だけ**で、最大 32 件。英語を打つために ABC に切り替えて戻ると、それまでの履歴は消える。**アプリをまたいで共有するものはない**。

### 0.3 保存
- 確定履歴はエンジンのメモリだけにある。ディスクには書かない。エンジンが終われば消える。
- 学習ファイル（`learning.tsv`）は、確定のたびに文脈の特徴量（ソルト付きのハッシュ、Topic のクラスタ番号）と読み・表記を数える。原文は持たない（NFR-19）。
- `client_bundle_id` は、エンジンは保存もログもしない（`begin_session` のコメント）。

| アプリ | 打鍵の記録 | 文書の長さ > 0 | 選択の位置 |
| --- | --- | --- | --- |
| TextEdit | 133 | 125 | 正しい位置 |
| VS Code | 1793 | **0** | 数が入る（0 のことも 77 回）。変換中の範囲が (0, n) になることがある |
| Chrome | 1417 | **0** | 同上（0 は 390 回） |
| WezTerm | 3 | 0 | ― |

`s0-0006.log`（2026-10-12、ADR 0006 の S0-4）: VS Code（4 回）と Chrome（2 回）で、文書の長さが 0 なのに、選択範囲の文字列は `string(from:)` で取れ、左の周辺テキストも「取れた」と記録されている（ADR 0006 §16.3 の S0-4）。

分かること・分からないこと:
- VS Code と Chrome は**文書の長さを返さないが、範囲を指定すれば一部の文字列は返す**。どの範囲まで返すか（Chromium は選択の前後の一部だけを手元に持つ、というのは推測）、`surroundingText()` が実際に何文字を返しているかは、**どのログにも記録がない**。→ スパイク S1（§7.1）。
- ターミナル（WezTerm）は取れない。

### 0.5 コードから分かった問題
- **P1 履歴が切れる**: §0.2 のとおり、ABC やほかのアプリに行って戻るたびに履歴が消える。周辺テキストが取れないアプリでは、そのあとの最初の変換は文脈なしになる。英語を混ぜて書くほど切れる。
- **P2 「取れた」ことにして空を送る**: 変換中の範囲の先頭が 0 のとき（VS Code と Chrome は (0, n) を返すことがある）、左は空文字列で `available = true` になる。エンジンは周辺テキストを信じるので、**確定履歴に切り替えず、左文脈が空のまま**変換する。`string(from:)` が nil ではなく空を返すアプリでも同じ。
- **P3 取る範囲**: 手前 2000 文字を 1 回で頼む。アプリが手元に持つ範囲が狭いと nil になり（そのときは履歴に切り替わるので害はない）、本当は取れる近くの文字を捨てている可能性がある（S1 で確かめる）。
- **P4**: 右文脈は送っているが使っていない（害はない。記録だけ）。

### 0.6 文脈の効き（測定。試作。付録 A）
`homophones-ext.tsv`（1266 件。左文脈は中央値 5 文字、9 割が 12 文字以下）の文脈だけを組み替えて、full（LM あり・締め切り 3000ms と、LM なし）の1位を数えた。

| 左文脈 | LM あり | LM なし | 何の代わりか |
| --- | --- | --- | --- |
| なし（ext-empty） | 610（48.2%） | 598 | 履歴が切れた変換（P1、P2） |
| 別のケースの文脈（無関係。ext-stale） | 617（+70 −63） | 589（+64 −73） | 関係のない古い履歴やほかのアプリの文を、左文脈にしてしまった場合 |
| 元の文脈＋「。」＋中立の文（43 文字。ext-far） | 610（+87 −87） | 638（+80 −40） | 手がかりが LM の 40 文字の外にあり、話題・文書内キャッシュ・Bag にだけ届く場合 |
| 元の文脈（ext-full） | **1093（86.3%）** | 979（+393 −12） | 同じ入力欄の直前の文脈が届いた場合 |

（括弧の +/− は「なし」と比べてケースごとに1位が直った数と崩れた数）

英語の文脈（32 件の小さなセット。Claude の下書きで、ユーザーの確認前。付録 A）:

| 左文脈 | LM あり | LM なし |
| --- | --- | --- |
| なし | 14 | 13 |
| 英語の文（例: 「Extract the zip file first, then」＋ かいとう → 解凍） | 15（+2 −1） | 15（+3 −1） |
| 同じ意味の日本語 | 29 | 25 |

読み取れること:
1. **直前の文脈が届くかどうかが、ほとんどすべて**（LM ありで 48% → 86%）。P1・P2 で失っているのはこれ。
2. 関係のない文脈「だけ」を左文脈にしても、LM ありなら害はほとんどない（+7）。LM なしでは −9。ただし**本当の文脈の前に**関係のない文がつながると害が大きい（§4。40 文字で 1093 → 950）。
3. 手がかりが 40 文字より遠いと、LM ありでは効かない（話題などだけでは差が出ない。LM なしでは +40）。→ 長さの測定（§4）。
4. **英語の文脈は、今の zenz small ではほとんど効かない**（+1 / 32）。同じ意味の日本語なら +15。

## 1. 決定の要約（提案）

| # | 項目 | 提案 |
| --- | --- | --- |
| D1 | 同じクライアントの履歴を切らさない | `BeginSession` は、同じ ID で secure が変わらないなら履歴を消さない。`EndSession` はセッションを消さずに「休止」にし、最後に使ってから **30 分**（Q2）保つ。休止中に同じ ID で `BeginSession` が来たら、履歴ごと再開する |
| D2 | 取れていないものを「取れた」と言わない | 殻: 左が空で、かつ `client.length()` が 0（文書の長さを返さないアプリ）なら `available = false` で送る。エンジンは今どおり、取れなければ履歴を使う |
| D3 | 取る範囲 | S1 の結果で決める。アプリが 2000 文字を返さず、近くなら返すと分かったら、殻が 2000 → 200 → 40 文字の順に取り直す |
| D4 | 同じ入力欄の履歴の量 | 件数（32）ではなく文字数（2000。解析の窓と同じ）で持つ（Q3） |
| D5 | **アプリをまたぐ文脈**（方針は決定済み） | エンジンに、全アプリの確定を時刻順に持つ「最近の確定」を 1 つ置く（直近 **10 分**・**2000 文字**。Q4）。混ぜ方は**案 X5**: 同じ入力欄に文脈が**何もない**とき（周辺テキストが取れず、同じ入力欄の履歴も空）に限り、直近 **2 分**以内のほかのアプリの確定の末尾を左文脈にする（Q5）。同じ入力欄に文脈があるときは、ほかのアプリの文を混ぜない。下書きの案 X2（ほかのアプリの文を話題などの「背景」にも足す）は、測定（§4.3）で、無関係な文が話題に混ざると 1266 件中 142 件が崩れ、関係のある文でも LM ありでは ±0 だったので、推奨から外した |
| D6 | 除外 | secure の確定は今どおりどこにも入れない。**除外するアプリ**（パスワード管理、ターミナル。設定で足せる。Q6）の確定は「最近の確定」に入れず、そのアプリでの変換にもほかのアプリの文を渡さない |
| D7 | 文脈の長さ | LM の窓 40 文字、解析の窓 2000 文字、話題の語数 50 語は**変えない**。伸ばすと、前にある無関係な文の害が増え（LM の窓 40 → 160 で 950 → 888）、応答も遅くなる（p50 +8ms）。得は測れる範囲で小さい（遠い手がかりで +28）。話題の語数を 10〜20 に減らす案（無関係な文の害が +13〜+29）は、関係のある長い文脈の評価セットを作ってから決める（§4、Q8） |
| D8 | 保存 | **しない**（メモリだけ）。原文を持たない（NFR-19）。学習の特徴量は、今どおりその入力欄の左文脈だけから作る。D5 でほかのアプリの文を左文脈にした変換は、学習では「文脈なし」として数える（Q7） |
| D9 | 英語モード | **今は作らない**（ADR 0005 §15.2 のまま）。英語の文脈は今の LM でほとんど効かず（§0.6-4）、取れるアプリでは ABC で打った英語も周辺テキストとしてすでに届く。設計（§6）とスパイク S2 の手順を残す。再検討の条件は §6.6（Q9） |
| ― | 変えないもの | 学習の特徴量の作り方、話題・文書内キャッシュの量、再変換の文脈、secure の扱い |

### 2.2 アプリをまたぐ文脈の混ぜ方（方針は決定済み。混ぜ方の案）
| 案 | 内容 | 測定（§0.6、§4） | 判断 |
| --- | --- | --- | --- |
| X1 | 全アプリの確定を 1 本の履歴にして、左文脈にも使う（アプリを区別しない） | 同じ入力欄に文脈があっても、ほかのアプリの文が前につながる。無関係な文（約 150 字）が前につながったときの測定（ext-mixlong、§4.3）: LM あり 1093 → 950（+16 −159）、LM なし 979 → 738（+9 −250） | 不採用。ほかのアプリの文は今の入力の直前の文ではない（Slack の文の続きとして VS Code で変換する）。害が実測で大きい |
| X2 | ほかのアプリの文を「背景」（話題、文書内キャッシュ、LM の話題の語）に足す。同じ入力欄に文脈が何もないときだけ、直近 2 分のほかのアプリの末尾を左文脈にする（下書きの推奨） | 背景の効き（関係のある遠い手がかり。ext-far、§0.6）: LM あり ±0（+87 −87）、LM なし +40。背景の害（無関係な文が話題に混ざる。ext-mixlong を LM の窓 10 文字で測ったもの。§4.3）: 1090 → 959（+11 −142） | 不採用。得るものが測れず、害が大きい。害はほとんど話題（chiVe）から来る（§4.3） |
| X3 | 背景だけに使い、左文脈には使わない | X2 と同じ背景の効きと害 | 不採用。X2 の害だけが残り、「何もないとき」の分を捨てる |
| X4 | アプリの種類（チャット、エディタ、ブラウザ）で混ぜる相手を選ぶ | 測れない（実機のデータがない） | 不採用（今は）。表を保守する手間に見合う根拠がない |
| **X5** | ほかのアプリの文は、同じ入力欄に文脈が何もないときだけ左文脈にする（直近 2 分）。背景には使わない | 関係のある文が届いたとき: 610 → 1093（ext-empty → ext-full。上限）。無関係な文だったとき: 610 → 617（+70 −63。LM なしは 598 → 589） | **採用**。同じ入力欄に文脈があるときは今と何も変わらない（害の入口がない）。何もないときは、関係があれば大きく効き、なければほぼ中立。2 分は「アプリを行き来して同じことを書いている」間を想定（Q5。S1 で確かめる） |

アプリをまたぐ方針から実際に得るものは、X5 の「何もないとき」の分（文脈なし 48% → 関係のある文脈なら最大 86%）。背景に混ぜる形（X2、X3）は、今の話題（chiVe の内容語 50 語）が無関係な語に引っぱられるので採らない。話題の作り方を変えて害が消えるなら（§4.6 の話題の語数、§4.9）、そのとき X2 を測り直す。

## 3. 入力の履歴とアプリをまたぐ文脈の設計（D1〜D6、D8）

### 3.1 セッションの寿命（D1。エンジン）
- `Session` に `paused_at: Option<Instant>` を足す。
- `BeginSession`:
  - 同じ ID のセッションがあり、`secure` が同じなら、履歴を残して `paused_at = None` にする（再開）。
  - `secure` が変わったら、今どおり履歴を空にする（パスワード欄の前後で文脈をつながない）。
  - ないなら作る（今どおり）。
- `EndSession`: セッションを消さず `paused_at = Some(now)` にする。変換の途中の状態（先行計算、文節、変換中）は今どおり捨てる。学習の保存も今どおり。
- 後始末のスレッド（`JANITOR_TICK`、1 秒）が、休止から 30 分（Q2）たったセッションを消す。`SESSION_LIMIT`（256）を超えたら、今どおり古いものから消す。
- コントローラが閉じられた（`inputControllerWillClose`）ときは、その ID は二度と使われないので、時間で消えるのを待つ。

### 3.2 取れていないものを取れたことにしない（D2。殻）
- `surroundingText()` の最後で、左が空で `client.length() == 0` なら `.unavailable` を返す。
  - TextEdit の空の文書では、変換中の文字列が文書に入るので `length()` は 0 にならない。左が空でも `available` のまま（正しく「文頭」として扱う）。
  - VS Code と Chrome は `length()` が 0 なので、左が空なら履歴に切り替わる。

### 3.3 取る範囲（D3。S1 のあと）
- S1 で、VS Code と Chrome が「2000 文字前から」の要求に nil を返し、短い要求には答えると分かったら、殻が 2000 → 200 → 40 文字の順に取り直す。時間も S1 で測る。答えないなら今どおり履歴に任せる。

### 3.4 同じ入力欄の履歴の量（D4。エンジン）
- `HISTORY_LIMIT`（32 件）を、表記の合計 2000 文字（`MAX_CONTEXT_CHARS` と同じ）に置き換える。1 件が 2000 文字を超えることは今もない（`MAX_SURFACE_CHARS`）。

### 3.5 アプリをまたぐ「最近の確定」（D5、D6。エンジン、core、殻）
- **エンジン**: `Inner` に「最近の確定」を 1 つ置く（`RecentCommit { session_id, at, surface }` の列）。確定（`push_history` と同じ場所）のたびに足し、10 分より古いものと、合計 2000 文字を超えた古いものを捨てる（Q4）。
- **左文脈の代わり**（X5。Q5）: `build_context` で、周辺テキストが取れず（D2 で空も「取れない」になる）、今のセッションの履歴も空なら、直近 2 分以内の**ほかのセッション**の確定をつないだ末尾（最大 2000 文字）を `left_text` に入れる。同じ入力欄に何か文脈があれば、ほかのセッションの文は使わない（混ぜない）。
- **core の契約**: `Context` に `left_borrowed: bool`（左文脈がほかの入力欄から借りたものか）を足す。core はこれが true のとき、学習（`LearningRanker` の引き当てと、確定のときの記録）の文脈の特徴量を空にする（ADR 0013 の「記録のない文脈」として扱う。Q7）。話題、LM、連接（`LeftContextRanker`）、文書内キャッシュは、借りた左文脈をふつうの左文脈と同じに使う。
- **除外（D6）**: 殻の設定 `context.shared_exclude`（Bundle ID の一覧）。既定はパスワード管理（1Password、Bitwarden、キーチェーンアクセス）とターミナル（Terminal、iTerm2、WezTerm、Ghostty）（Q6）。殻は `BeginSession` に `share_context = false` を付ける（proto に 1 フィールド足す）。エンジンは、そのセッションの確定を「最近の確定」に入れず、そのセッションの変換にはほかのセッションの文を貸さない。エンジンは Bundle ID を今どおり受け取らず、保存もしない（判定は殻の中だけ）。
- **メモリ**: セッションごとの履歴 2000 文字 × 256 と、「最近の確定」2000 文字で、最大 2 MB 程度。

### 3.6 プライバシー
- 履歴と「最近の確定」はメモリだけ。休止中のセッションは 30 分、「最近の確定」は 10 分で消える。エンジンが終われば消える。ログに中身を書かない。
- **アプリをまたぐので、あるアプリで書いた文が、別のアプリの変換で LM のプロンプトに入ることがある**（その入力欄に文脈が何もないときだけ。X5）。プロンプトは手元の LM にだけ渡り、外には出ない（NFR-17）。画面に出るのは候補だけで、入力していない文字は出さない（基本原則）。
- secure の間は今どおり何も入れない。除外するアプリの確定は、ほかのアプリに渡らず、除外するアプリにもほかのアプリの文を渡さない。
- 学習ファイルには、ほかのアプリの文から作った特徴量を入れない（D8、Q7）。

### 3.7 効果の測り方
- **上限**: §0.6 の「なし」と「元の文脈」の差（LM ありで +483 / 1266。1位 610 → 1093）。
- **実機での割合**: S1 のログで、変換ごとに「周辺テキスト／同じ入力欄の履歴／ほかのアプリから借りた／なし」のどれで文脈を作ったかと、その文字数を数える（中身は書かない）。D1〜D5 の前後で比べ、「文脈なしの変換の割合」がどれだけ減ったかを出す。
- **害の確認**: §0.6 の ext-stale（無関係な文脈だけ）を、X5 の回帰の確認として残す（LM ありで、文脈なしより悪くならないこと）。§4 の ext-mixlong は、D7 を変えるときの確認に残す。
- **既存の評価**: 既存のセットは「最近の確定」が空なので結果は変わらない（`eval/scripts/snapshot.sh` で一致を確かめる）。評価のハーネスには、「左文脈を借りた」ケースを書ける列（`borrowed`）を足し、学習の特徴量が空になることを確かめる（契約のコミットで足す）。

## 4. 文脈の長さ（D7）

### 4.1 何を「長さ」と呼ぶか
文脈の長さのつまみは 3 つある（§0.1）。
| つまみ | 今の値 | 効く部品 |
| --- | --- | --- |
| LM の窓（`zenz.context_chars`） | 40 文字 | zenz のプロンプトの左文脈 |
| 解析の窓（`CONTEXT_WINDOW_CHARS`）と、話題の語数（`topic.recent_tokens`） | 2000 文字、50 語 | 話題（chiVe）、文書内キャッシュ、学習の Bag・Topic、LM の話題の語 3 つ |
| 同じ入力欄の履歴の量（`HISTORY_LIMIT`） | 32 件 | 周辺テキストが取れないときの左文脈（D4 で 2000 文字にする） |

「もっと長くできないか」は、上の 2 つを伸ばすことを指す（3 つ目は D4）。

### 4.2 測り方と、測れないこと
- `homophones-ext.tsv`（1266 件）の左文脈を組み替えたセットで、`--ranker full` の1位を数えた。LM ありは締め切り 3000ms（時間切れ 0 件。精度だけを見るため）。作り方は付録 A。
- 組み替え:
  - **本当の文脈だけ**（ext-full）: 元のまま。
  - **無関係な文が前にある**（ext-mixlong）: ほかのケースの文脈（読みの違うもの）を「。」でつないだ約 150 文字（中央値 160、最大 203 文字）を、本当の文脈の前に置いた。別の話題の文が続いたあとに、今の話題の文を書いている状態の代わり。
  - **遠い手がかり**（ext-far）: 本当の文脈のあとに、中立の文（「それはさておき、今日は少しだけ時間ができたので、続きをここに書いておくことにします。」43 文字）を置いた。手がかりが 40 文字より遠くにある状態の代わり。
  - なし（ext-empty）、無関係な文脈だけ（ext-stale）は §0.6 と同じ。
- **測れないこと**: 評価セットの本当の文脈は短い（中央値 5 文字、9 割が 12 文字以下、最大 41 文字）。AJIMEE（200 件）も中央値 0.5 文字。**「関係のある長い文脈が届いたときに、伸ばして得をするか」を測れるセットが今はない**。測れるのは、短い本当の文脈での窓の効き、前に無関係な文があるときの害、43 文字の向こうの手がかりの効き、の 3 つ。

### 4.5 害はどこから来るか（部品を止めて測った。LM の窓 40）
| 止めたもの | 本当の文脈だけ（LM あり／なし） | 無関係な文が前にある（LM あり／なし） | 同じ設定での差（LM あり／なし） |

- **害のほとんどは話題（chiVe）から来る**。LM なしでは話題を止めると害が消える（720 と 720）。LM ありでも、話題を止めると害は −143 → −61 に減る。残りは LM の窓に無関係な文が入るぶん（本当の文脈が 40 文字より短いとき、窓の残りに無関係な文が入る）。

### 4.6 話題の語数（`topic.recent_tokens`）を減らしたとき（LM の窓 40）
話題（chiVe）は、解析した左文脈の内容語を新しい方から 50 語まで使い、遠いほど軽くする（1 語ごとに 0.97 倍）。この語数だけを変えた。

| --- | --- | --- | --- | --- |
| **50 語（今）** | 1093 / 979 | 950 / 738 | 610 / 638 | 617 / 589 |

| 40 文字 | 20.3〜20.6 | 30.5〜32.5 |
| 80 文字 | 22.3〜23.3 | 31.1〜33.1 |
| 160 文字 | 27.8〜29.3 | 41.9〜45.8 |

- 実際の締め切り（既定。30ms＋読み 1 文字ごとに 6ms、上限 300ms）での時間切れの割合は、同じ設定でも 0.8%〜80% と大きくぶれた。測った時間帯に、ほかの作業（ビルド）が同じ Mac で走っていたため（load average 1〜30）。時間切れの数は**このマシンの混み具合で決まり、窓の長さの比較には使えない**。伸ばすほど締め切りに近づく、ということだけが言える。

### 4.8 読み取れること
1. **今のセットでは、伸ばして得をする場面が見つからない**。本当の文脈が 40 文字に収まる限り、LM の窓を伸ばしても変わらない。遠い手がかりは窓 80 で +28 だが、間に別の文が挟まった状態の話で、すぐ前の文脈（+483）とは桁が違う。
2. **伸ばすと、前にある無関係な文の害が増える**。LM の窓 40 → 160 で −62。応答時間も p50 で +8ms。
3. **害の大部分は話題（chiVe）で、話題は益の大部分でもある**。話題の窓を短くすれば害は減るが、関係のある長い文脈での損を測れない（§4.2）。
4. 実機で「本当の文脈の前に無関係な文がある」状態は、D1（履歴を切らさない）と D4（履歴を 2000 文字）で増える方向にある。同じ入力欄の履歴でも、チャットのように話題が変わる場では起きる。

### 4.9 D7 の提案
- **LM の窓は 40 文字のまま**。伸ばすと、前にある無関係な文の害が増え（80 で −29、160 で −62）、応答も遅くなる（160 で p50 +8ms）。得は、間に別の文が挟まった遠い手がかりでの +28（窓 80）だけ。zenz の学習時の形式（ADR 0002 §0.4）からも離れる。縮める（10〜20）と無関係な文の害は少し減る（+9〜+11）が、本当の文脈だけのセットで −2〜−3 になり、根拠が弱い。
- **解析の窓（2000 文字）と話題の語数（50 語）は、今は変えない**。伸ばす理由は見つからない（今のセットで 41 文字を超える関係のある文脈がない）。話題の語数を 10〜20 に減らすのは有望（§4.6）だが、長い関係のある文脈での損を測れていない。
- **次の一手は、関係のある長い文脈の評価セットを作ること**（別のタスク。Q8）。たとえば、1 つの話題で数百字続く文章の後ろの方で同音語を打つケース（主題の語が 10〜50 語前にある）を、公開の文章や Claude の下書きから作り、ユーザーが確かめる。そのうえで、話題の語数（10 / 20 / 50）と LM の窓（40 / 80）を決め直す。
- D1（履歴を切らさない）と D4（2000 文字）で、同じ入力欄の古い文が前に残る場面は増える。話題の語数を変えるまでは、休止の上限（Q2）で抑える。

## 5. 基本原則との整合
- **入力を正とする**: 文脈は候補の並べ替えにだけ使う。候補は今どおり辞書から作り、読みに対応しない文字を足さない。ほかのアプリの文は、候補にも変換中の文字列にも出ない。
- **学習は支援であって決定ではない**: ほかのアプリから借りた文脈では学習の特徴量を作らない（D8）。学習の記録の意味（「この入力欄のこの文脈で、この表記を選んだ」）を変えない。
- **こまめに確定するのがコンセプト**: 文脈を長くする仕組み（KV キャッシュの使い回し、長い窓）は入れない（D7）。今回の変更は、短く確定したときに直前の文脈を失わないためのもの。
- **LM は zenz small の 1 つだけ**: 英語の文脈のために別のモデル（翻訳、多言語の LM）を足さない（E-D を不採用。D9）。

### 6.1 形
- ikari に入力モードをもう 1 つ足す（Info.plist の `ComponentInputModeDict` に `.Roman` 相当のモード。ADR 0005 §15.2 でなくした「英数モード」の復活）。
- そのモードの殻は、打鍵をすべてアプリにそのまま渡す（`handle(_:client:)` が false を返す）。変換中の文字列（下線）も候補も出さない。
- 渡す前に、印字できる ASCII の文字だけを「英語の確定」として手元の列に足す。Backspace は列の末尾を 1 文字消す。矢印、クリック、Cmd・Ctrl を伴うキー、Return は列を区切る（そこまでを 1 件の確定として送る）。
- 送り先は D1・D5 と同じ。同じ入力欄の履歴と「最近の確定」に入る。新しい proto は要らない（確定の通知に「英語」の印を足すかは実装で決める）。

### 6.2 何が得られるか（測定。§0.6）
- 32 件の小さなセット（Claude の下書き。ユーザーの確認前）で、英語の左文脈は LM あり 14 → 15（+2 −1）、LM なし 13 → 15（+3 −1）。同じ意味の日本語なら 29、25。
- つまり、**拾った英語を左文脈に入れても、今の zenz small ではほとんど効かない**。話題（chiVe）は日本語の語のベクトルなので、英単語は引けない。

### 6.3 今の仕組みで届く英語（E-B）
- TextEdit のように周辺テキストを返すアプリでは、ABC で打った英語も、次に日本語を打つときの周辺テキストに入っている。英語モードを作っても、このアプリでは何も増えない。
- 増えるのは、周辺テキストを返さないアプリ（VS Code、Chrome、ターミナル。§0.4）で英語を打った場合だけ。どのくらいあるかは S1 で数える。

### 6.4 危険
- **秘密を拾う**: secure（`IsSecureEventInputEnabled()`）の間は止めるが、ターミナルで `sudo` のパスワードを打つときに secure にならない設定がある（Terminal の「セキュアなキーボード入力」は既定で切と理解している。S2 で確かめる）。パスワード欄でない欄に打つ API キーやトークンも拾う。メモリだけで 10 分で消え、外には出ないが、LM のプロンプトに入る。
- **すべての英語の打鍵が ikari を通る**: 殻が遅れたり落ちたりすると、英語の入力が止まる。今は ABC なので、ikari が壊れても英語は打てる。

### 6.5 使い勝手とアプリとの相性（実機で確かめていない）
- ABC の機能（長押しでアクセント付きの文字を出す、スペース 2 回でピリオド、自動修正）が、ikari の英語モードでは使えない可能性が高い。
- 英数キーは macOS が ABC に切り替える（ADR 0005 §15.2 の S0-2。殻に届かない）。英語モードに入るには、別のキーを決めるか、ABC を入力ソースから外す必要がある。ABC は macOS が必須にしているので外せない（user-feedback.md §3）。英語の入力ソースが 2 つ並ぶ。
- Vim の操作（VS Code の Vim 拡張）、ゲーム、ショートカットの多いアプリで、打鍵の受け渡しに違いが出ないかは分からない（S2）。

### 6.6 作り直しを考える条件
次のどれかが分かったら、Q9 をもう一度聞く。
1. 英語を含む左文脈で効く LM を使えるようになった（zenz の後の版などで、§0.6 の英語のセットが日本語の文脈に近い数になる）。
2. S1 で、周辺テキストを返さないアプリで英語と日本語を行き来する変換が多く、その直後の変換が「文脈なし」になっている割合が大きいと分かった。
3. ユーザーが、ABC の機能を使わず、英語の入力ソースを ikari に一本化したいと決めた。

## 9. 判断が必要な点（ユーザーに聞く）
各項目に、背景、例、選択肢ごとの影響、推奨と理由を書く。数字は §0.6 と §4 の測定（1266 件の同音語のセット。1位の件数）から。

### Q1. 同じ入力欄の履歴を、ABC やほかのアプリに行って戻っても消さないか（D1、D2）
- **背景**: ikari は、周辺テキスト（カーソルの前の文字）を返さないアプリ（VS Code、Chrome。§0.4）では、そのセッションで確定した文（最大 32 件）を左文脈の代わりにしている。ところが、ABC に切り替えたり、ほかのアプリに移ったりするたびに、この履歴を捨てている（§0.2）。また、VS Code と Chrome は「取れた、中身は空」と返すことがあり、そのときは履歴に切り替えずに文脈なしで変換している（P2）。
- **例**: VS Code で「ログの保存期間を」と確定 → ABC で `retention` と打つ → ikari に戻って「みなおす」。今は文脈なしで変換する。D1 のあとは「ログの保存期間を」が左文脈になる。
- **選択肢と影響**:
  - (a) 消さない・空を取れたことにしない（D1、D2）: 文脈が届く変換が増える。文脈の有無の差は 1266 件で 610 → 1093。カーソルを文書の別の場所に動かしていても、直前の確定を前の文として扱う（無関係なら 610 → 617 で、ほぼ害なし）。
  - (b) 今のまま: 何も変わらない。英語を混ぜるほど、文脈なしの変換が増える。
- **推奨: (a)**。理由: 直前の文脈が届くかどうかが、文脈の効きのほとんど（§0.6）で、害は測れる範囲でほぼない。proto を変えずにエンジンと殻の中だけで済む。

### Q2. 休止した入力欄の履歴を何分残すか（D1）
- **背景**: Q1 で「消さない」にすると、ikari を離れた入力欄の履歴をしばらくメモリに残す。長く残すほど文脈が届く場面は増えるが、話題が変わったあとの古い文が左文脈になりやすい。
- **例**: Slack の同じチャンネルの入力欄で、昼に書いた文が、夕方の変換の左文脈になるか。
- **選択肢と影響**: 10 分（短い中断だけつなぐ）／**30 分**（会議や休憩をはさむ程度）／ずっと（エンジンが動いている限り。256 欄まで）。長いほど §8.2 の「古い文脈が前に残る」リスクが増え、短いほど文脈なしが増える。どちらも今のセットでは差を測れない（S1 の割合で見直す）。
- **推奨: 30 分**。理由: 古い文脈の害は小さい（§0.6）が、話題（chiVe）は前にある無関係な語に弱い（§4.5）ので、無期限にはしない。S1 のあとで見直す前提の仮の値。

### Q3. 同じ入力欄の履歴の量を、件数（32 件）から文字数（2000 文字）にするか（D4）
- **背景**: 今は確定 32 回分を持つ。短い確定（「はい」「です」）が続くと、32 件でも数十文字しかない。解析の窓は 2000 文字。
- **例**: 1 文字ずつ確定する人では、32 件 ≒ 32 文字。長い文を確定する人では、32 件で 2000 文字を超え、末尾 2000 文字に切られる。
- **選択肢と影響**: (a) **2000 文字**: どんな確定の仕方でも、解析の窓いっぱいまで文脈が届く。前に古い文が残る量も増える（Q2 と同じリスク）。(b) 32 件のまま: こまめに確定するほど文脈が短くなる。
- **推奨: (a)**。理由: 「こまめに確定する」コンセプトで文脈が短くなるのは逆向き。解析の窓と同じ単位にすると説明が簡単。

### Q4. アプリをまたぐ「最近の確定」をどれだけ持つか（D5）
- **背景**: アプリをまたいで文脈を取ることは決定済み。そのために、全アプリの確定を時刻順にメモリに持つ。
- **選択肢と影響**: **10 分・2000 文字**／もっと長く（1 時間など）。長いほど、ほかのアプリの文がメモリに長く残る。ただし Q5 の推奨（X5）では、実際に使うのは直近 2 分以内のものだけなので、10 分より長く持っても使い道がない。
- **推奨: 10 分・2000 文字**。理由: 使うのは 2 分以内（Q5）で、S1 の結果で 2 分を延ばすときに余裕が要るぶんだけ持つ。

### Q5. ほかのアプリの文をどう混ぜるか（D5。X1〜X5）
- **背景**: 下書きでは X2（ほかのアプリの文を「背景」として話題などにも混ぜる）を推していたが、測ると、無関係な文が話題に混ざる害が大きく（1266 件中 142 件が崩れる）、関係のある文でも LM ありでは得がなかった（§2.2、§4.5）。
- **例**: Slack で「明日のリリースの手順を確認します」と確定 → 1 分後に VS Code のコミットメッセージ欄（周辺テキストも履歴もない）で「てじゅん」。
  - X5: Slack の文が左文脈になり、「手順」を押す。VS Code に前の文があれば、Slack の文は使わない。
  - X2: さらに、VS Code に前の文があるときも、Slack の文の語を話題に足す。
  - X1: VS Code の前の文の前に、Slack の文がつながる。
- **選択肢と影響**（LM あり。1位の件数）:
  - (a) **X5（何もないときだけ借りる。2 分）**: 関係があれば 610 → 最大 1093、無関係なら 610 → 617。同じ入力欄に文脈があるときは今と同じ。
  - (b) X2（背景にも混ぜる）: X5 の効き＋背景。背景は、関係のある遠い文で ±0、無関係な文で −142 程度（1090 → 959）。
  - (c) X1（1 本の履歴）: 無関係な文が前につながると 1093 → 950。
  - 2 分の値: 長くすると借りる場面は増えるが、無関係な文の割合も増える。
- **推奨: (a) X5、2 分**。理由: 得られるものがほぼすべて「何もないとき」の分で、そこだけに絞ると害の入口がない。2 分は S1 で見直す仮の値。

### Q6. ほかのアプリと文脈を共有しないアプリ（除外）の既定（D6）
- **背景**: 除外したアプリの確定はほかのアプリに渡らず、そのアプリでもほかのアプリの文を借りない（同じ入力欄の履歴は使う）。設定で足したり外したりできる。
- **選択肢と影響**:
  - パスワード管理（1Password、Bitwarden、キーチェーンアクセス）: 外すと、ここで打った秘密に近い文（メモ欄など）が、ほかのアプリの LM のプロンプトに入りうる。
  - ターミナル（Terminal、iTerm2、WezTerm、Ghostty）: 外すと、コマンドの引数などに打った日本語がほかのアプリに渡る。ターミナルは周辺テキストを返さないので、除外すると、ターミナルでの変換は同じ入力欄の履歴だけになる。
  - ほかの候補: パスワードを貼ることがあるアプリ、仕事と私用を分けたいアプリ（メッセージ、メール）。
- **推奨: パスワード管理とターミナルを既定にし、ほかはユーザーが足す**。理由: 秘密を扱う場で、得るものより危険が大きい。ほかのアプリはユーザーの使い方で決まるので、既定にはしない。ほかに必ず入れたいアプリがあれば教えてほしい。

### Q7. 文脈をディスクに保存しない。ほかのアプリから借りた文脈では学習しない（D8）
- **背景**: 履歴と「最近の確定」はメモリだけに置き、エンジンが終われば消える。学習ファイルには今どおり原文を持たない（文脈はソルト付きのハッシュ）。X5 でほかのアプリの文を借りた変換は、学習では「文脈なし」として数える。
- **例**: Slack の文を借りて VS Code で「手順」を選んでも、学習には「VS Code で文脈なしに 手順 を選んだ」と記録する。
- **選択肢と影響**:
  - 保存: (a) **しない**／(b) 原文を保存（再起動のあとも文脈が残るが、NFR-19 に反し、エクスポートやバックアップに文章が残る）／(c) 話題のベクトルだけを保存（得るものが小さい。エンジンはめったに再起動しない）。
  - 学習: (a) **借りた文脈では特徴量を作らない**／(b) 作る（ほかのアプリの語のハッシュが学習ファイルに残り、「この文脈でこれを選んだ」の意味が、別のアプリの文に引っぱられる）。
- **推奨: 保存しない、借りた文脈では学習しない**。理由: NFR-19 と、学習の記録の意味を保つため。

### Q8. 文脈の長さ（D7）
- **背景**: 「もっと文脈を長くできないか。悪影響はあるか」への回答。§4 で、LM の窓（今 40 文字）を 10〜160 文字、解析の窓を 10〜160 文字で測った。
- **例**（LM の窓だけを変えたとき。1266 件。§4.3）:
  - 本当の文脈だけ: 10 字 1090、40 字 1093、80 字 1093、160 字 1093（このセットの文脈は 41 文字まで）。
  - 無関係な文（約 150 字）が前にある: 10 字 959、40 字 950、80 字 921、160 字 888。
  - 遠い手がかり（43 文字の中立の文の向こう）: 40 字 610、80 字 638。
  - 応答時間（p50）: 40 字 約 20ms、160 字 約 28ms。
- **選択肢と影響**:
  - (a) **今のまま**（LM 40 文字、解析 2000 文字、話題 50 語）: 変わらない。
  - (b) LM の窓を 80〜160 に伸ばす: 遠い手がかりで +28。無関係な文が前にあると −29〜−62。応答が p50 で +2〜+8ms、締め切りに近づく。
  - (c) 話題の窓を短くする: §4.6 の結果を参照。無関係な文の害は減るが、長い関係のある文脈で損をするかは測れない。
  - (d) 関係のある長い文脈の評価セットを先に作り、そのうえで (b)(c) を決める（別のタスク）。
- **推奨**: **(a) 今のまま＋(d) 長い文脈の評価セットを作るタスクを積む**。理由: 伸ばす案は、測れる範囲で害（−29〜−62）と遅れ（+2〜+8ms）が得（+28）を上回る。縮める案（話題 10〜20 語）は有望だが、損を測るセットがない。セットの作り方（材料、件数）は、そのタスクの ADR で聞く。

### Q9. 英語モード（IME の英語版）を復活させるか（D9。ADR 0005 §15.2 を変えるか）
- **背景**: 2026-10-12 に、使われていなかった英数モードをなくし、英語は ABC に任せた（ADR 0005 §15.2）。今回の要望は、ikari に英語のモードを足し、候補を出さずにそのまま入力しながら、打った英語を文脈として拾うもの（§6）。

## 付録 C. 右文脈を LM に渡す（P4 の続き。2026-10-24。#270）
