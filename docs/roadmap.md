# ロードマップ

ikari-ime は、macOS で使う日本語入力（IME）です。文脈と確定した語を手がかりに変換候補を並べ、こまめに確定しながら書く使い方を支えます。この文書は、今どこにいて、次に何をしたいか、公開のあとどこへ向かうかを、初めて見る人にも分かるように並べたものです。約束ではなく、見取り図として読んでください。

この文書の用語: 「ADR」は、設計の判断と理由を 1 件ずつ残した記録（[索引](adr/README.md)）です。`#番号` は、このリポジトリの GitHub の Issue 番号です。「ユーザー決定」は、リポジトリの作者が決めたことを指します（CLAUDE.md の「ユーザー」と同じ）。

この文書の状態は、2026 年 10 月下旬（10 月 28 日に優先順位を見直した）時点のものです。2026 年 11 月に、公開の方針（ソースだけを先に公開し、ビルド済みの配布はあとにする）を決めました。時期は書いていません。個々の作業の進み具合は GitHub の Project と milestone が持っていて、この文書は書き直さずに、大きな流れだけを載せます。

## 前提: 3 つの方針

すべての項目は、次の 3 つの方針に沿って決めています。仕様書（`docs/ikari-ime_spec.md`）の「基本原則」が正です。

1. **ユーザーの思考を止めない。** 変換に失敗して手戻りが起きると思考が止まるので、こまめに確定しながら書き進められるようにします。長い文を一度に変換する仕組みは増やしません。
2. **ユーザーの意図に忠実にする。** 入力していない文字を足す「補完」はしません。読みから漢字・日付・絵文字に変わる候補は、ユーザーが選ぶ「変換」なので使います。入力の結果を変える機能（括弧の自動補完など）は既定でオフにします。
3. **速さは補完ではなく、入力配列とショートカットで出す。** 予測変換やサジェストは作りません。キーの配列を変えることと、ユーザーが明示的に押したときだけ働くショートカットで速くします。

候補は辞書から作り、言語モデル（LM）は候補の並べ替えにだけ使います。LM は候補を足しません。

## 優先順位（2026-10-28 にユーザーが決定）

「誤変換をなんとかしたい」を最優先にして、次の順で進めます。各項目の issue には `theme:` のラベルを付けています。

1. **変換の質**（誤変換を直す。LM の先行計算、同音語の選び、日付など機能の候補の順位、確信度）
2. **基盤**（診断ログ、署名と配布、テストの安定、再同期）
3. **評価の自動化**（評価セットの確認、Web の文章での確かめ）
4. **Windows で動かす**（実現性の調査と ADR から）
5. **ショートカット機能**（テンプレート、括弧の補い、学習の取り消しなど。手が空いたときに進める）
6. **入力配列とキー**（キーの入れ替え、キーボードごとの配列、薙刀式、キーマップエンジン。いちばん最後）

以下の「今」は 1〜3、「Windows」は 4、「次」は 5 と 6 にあたります。

### 状態の語

| 状態 | 意味 |
| --- | --- |
| 実装済み | 動いていて、作者が日常で使っている |
| 進行中 | 作っている、または実機で確かめている |
| 予定 | 方針と設計がほぼ決まっているか、設計の決定が次に来る。作業はまだ |
| 検討中 | 採否が未決。試す前の案、または特許など条件の確認が済んでいないもの |

各項目の末尾の ADR は、決定の経緯と詳しい数値が書いてある記録です（[ADR の索引](adr/README.md)）。

## 今: 日常使いで磨く

作者が毎日使いながら、変換の質と動作の安定を上げている段階です。

- **経路が負ける型の直し**（看守役、異常気象、仕様変更、推し活 など）
  - 状態: 実装済み（使い心地を確認中）
  - 辞書を作るときに、部品がどちらもよく使う熟語を優先します。LM なしでも直る語と、文脈があるときだけ直る語があります。
  - ADR: [0035](adr/0035-path-loses-cost-adjust.md)

- **同音語と表記の規則**（異字同訓、形式名詞、まれな同音語、熟語の分割、英字の綴り など）
  - 状態: 実装済み
  - 辞書の作成時の規則と、変換の辺の補正で、よくある取り違いを減らします。
  - ADR: [0009](adr/0009-verb-notation.md)、[0010](adr/0010-verb-kanji-bonus-scope.md)、[0011](adr/0011-compound-over-affix-split.md)、[0016](adr/0016-rare-homophones.md)、[0017](adr/0017-formal-noun-kanji-bonus-scope.md)、[0019](adr/0019-remaining-conversion-errors.md)、[0020](adr/0020-english-spelling-first-candidate.md)

- **動物名などの表記をそろえる**
  - 状態: 進行中（ひらがなを優先する部分は入った。文脈で漢字と表記が変わる残りの例は、LM ありでも直らない）
  - 同じ種類の語が、文の中で表記を揃えるための規則を考えています。残りは決定が要るため、ADR を起こしてから直します。

- **文の区切りと文節の操作**
  - 状態: 実装済み
  - 最初の Space で読み全体の候補、←/→ と Shift+←/→ で文節ごとに選びます。
  - ADR: [0006](adr/0006-segment-editing.md)

- **文脈をどこまで読むか**
  - 状態: 実装済み（一部は実機で確かめ待ち）
  - 入力の履歴を切らさず、同じ入力欄に何もないときだけ、ほかのアプリの文脈を借ります。
  - ADR: [0015](adr/0015-context-sources.md)

- **学習**
  - 状態: 実装済み（学習の効き方）、予定（学習の取り消し、候補を学習から消す）
  - 学習は支援であり、決定ではありません。文脈の記録がないときの効き方は ADR で決めています。取り消しと消去は、設計を先に決めます。
  - ADR: [0013](adr/0013-learning-without-context.md)

- **LM の先行計算**
  - 状態: 進行中（原因が分かって、直し始めた段階）
  - 打っている間に LM を先に動かし、Space の時点で結果が使えるようにしています。人の入力だけで見ると、LM が付かない変換は約 11% で、その大半（約 8〜9%）は、確定の直後に先行計算が古い左文脈で作られていたことが原因でした。合成の最初の数打鍵で左文脈を読み直す直しを入れたので、診断ログで効果を測ります。
  - ADR: [0021](adr/0021-lm-lookahead.md)

- **候補ウィンドウ**
  - 状態: 実装済み（横書き）、予定（縦書き）
  - 横書きは、下に縦に積んだ候補を最初は 3 件、進むと 9 件まで広げます。縦書きは後の工程です。
  - ADR: [0014](adr/0014-candidate-window-layout.md)

- **確信が高い変換は、1 位だけを出す**
  - 状態: 実装済み（既定オン。閾値は暫定で、実利用のログで見直す）
  - 1 位と 2 位の最終スコアの差が閾値以上のとき、最初の Space で 1 位だけを下線つきで出し、候補ウィンドウは出しません。もう一度 Space か ↓ で一覧を出します。閾値は LM なし 5000、LM あり 10000（保守的な案）です。設定 `candidate.hide_when_confident` で止められます。

- **診断ログ**
  - 状態: 実装済み（常時ためている）
  - 変換の直し方、不具合の手がかり、機能の使われ方、性能を、入力した文字を残さずに記録します。パスワード欄では何も書きません。保持は 180 日・100 MB までで、古い分は gzip にして残します。集計は `scripts/diag-report.py` で出します。
  - ADR: [0034](adr/0034-diagnostic-log.md)

- **評価の仕組み**
  - 状態: 実装済み
  - 変換の評価セットと評価コマンド（`ikari-eval`）で、規則を変えたときに 1 位が悪くなっていないかを確かめます。数値の索引は `eval/reports/README.md` にあります。

## 次: ショートカットと入力配列

速く入力する要求には、入力配列とショートカットで応えます。優先順位では、ショートカット機能（テンプレート、括弧の補い、絵文字、学習の取り消し）は手が空いたときに進め、入力配列とキー（キーの入れ替え、キーボードごとの配列、薙刀式、キーマップエンジン）はいちばん最後です。

- **キー割り当てのプリセット**
  - 状態: 実装済み（macOS 風、MS-IME 風、ATOK 風）
  - 字種変換や再変換のキーを、プリセットで切り替えます。キーボード配列によらず動くようにする作業は、別に積んでいます（JIS と US の両方は割り当て済み）。

- **キーの入れ替え（第 1 段階。大西配列）**
  - 状態: 予定
  - macOS の hidutil でキーを入れ替えます。許可も管理者権限も要りません。配列の定義は人が読み書きできるテキストにし、後の段階でも同じ定義を使います。
  - 確かめることが残っています。再起動やキーボードの抜き差しのあとに設定が残るか、キーボードごとに指定できるかです。
  - ADR: [0031](adr/0031-keymap-engine.md)

- **キーボードごとの入力配列の切り替え**
  - 状態: 予定
  - 内蔵キーボードと外付けのキーボードで、配列を分けます。第 1 段階の hidutil の指定で足りるかを先に確かめます。
  - ADR: [0031](adr/0031-keymap-engine.md)

- **薙刀式**（第 3 段階）
  - 状態: 予定（ADR で方式が決まっている。第 2 段階の占有エンジンが要る）
  - 同時押しで文字を打つ配列です。キーを押している間の重なりで判定します。時間では判定しません。
  - ADR: [0031](adr/0031-keymap-engine.md)

- **テンプレート**（定型文の一部を選んだ文字列で差し替えて、ショートカットで入れる）
  - 状態: 予定（設計の段階。ADR はまだない）
  - 作者がもっとも早く欲しい機能です。定型文の中の差し替える場所と、呼び出すキーを決めます。
  - 既定ではオフにする予定です。

- **括弧の補い**（開き括弧を打つと閉じ括弧を足す）
  - 状態: 予定（既定オフ。ADR はまだない）
  - 入力の結果を変える機能なので、ユーザーが設定で入れる形にします。

- **英語のモード**（打鍵を、ikari を通さずそのままアプリに渡す）
  - 状態: 実装済み
  - 英数キーでこのモードに入ります。パスワード欄では日本語と英語のどちらも素通しにし、中身を記録しません。
  - ADR: [0026](adr/0026-english-mode-and-key-stats.md)

- **絵文字のショートコード**（`:eyes:` → 👀）
  - 状態: 実装済み（頭に `:` を打って閉じる入力）、予定（日本語の読みから絵文字を出す段階）
  - 絵文字の一覧はデータとして持ちます。絵文字の一覧を開く操作は、macOS の標準の文字ビューアに任せます。
  - ADR: [0027](adr/0027-emoji-input.md)

- **打鍵と確定の統計**（配列を選ぶための材料）
  - 状態: 予定（設計の段階）
  - 打鍵と確定した文字列の回数を、キーごと・1〜3 文字で数えます。既定ではオフで、2 つのスイッチで止められます。
  - ADR: [0026](adr/0026-english-mode-and-key-stats.md)

## その先: 大きな仕組み

順序と時期は決めていません。前の段階が終わってから、設計を始めます。

- **キーマップエンジン**（Mod-Tap、レイヤー、Tap Dance、GUI で配置を直す）
  - 状態: 予定（方式は決定済み。始める前に、root で動く常駐の確かめが要る）
  - キーボードを占有して、IME の外でキーを送り直す仕組みです。IME の中では、キーを離した動きが届かないため作れません。OS 全体で効くため、パスワード欄でも使えます。
  - 第 1 段階（キーの入れ替え）とは別の常駐になるので、ikari 本体とは分けて作れる形にします。
  - ADR: [0031](adr/0031-keymap-engine.md)

  ```mermaid
  flowchart TD
      K[物理キーボード] --> L1[第 1 段階: hidutil<br/>キーの入れ替え]
      L1 --> M[macOS]
      K --> L2[第 2 段階以降: 占有エンジン<br/>Mod-Tap・レイヤー・薙刀式]
      L2 -->|キーを送り直す| M
      M --> I[ikari（IME）<br/>変換・学習・文脈]
  ```

- **地名の辞書データの配布と自動更新**
  - 状態: 予定（設計は提案の段階。段階 1〜3 に分けている）
  - 町字と郵便番号の表は、今は作者の Mac で作っています。これを GitHub Actions で週 1 回確かめて作り、公開のリポジトリの Release に出します。アプリは、確かめて入れ替える別の道具で成果物だけを取ります。
  - 段階 1: Actions と Release、手で取るスクリプト。段階 2: 設定アプリの「更新を確認」と「前の版に戻す」。段階 3: 週 1 回の自動取得（電源につないでいるときだけ）。
  - 通信するのは別の道具だけで、ikari 本体は通信しません。
  - ADR: [0033](adr/0033-place-data-distribution.md)、元データの扱いは [0030](adr/0030-abr-town-vocabulary.md)

      A[元データ<br/>住所の町字と郵便番号の表] --> B[GitHub Actions<br/>週 1 回。確かめてから作る]

- **郵便番号と住所の変換**
  - 状態: 実装済み（日本語の入力と、英語のモードの `te` + 7 桁。英語のモードの設定は既定オフ）
  - 住所を打つと郵便番号を、郵便番号を打つと住所を候補に出します。読み全体が住所か郵便番号の形のときだけ出し、読みにない文字は足しません。`て` の後ろに郵便番号を打つと、〒つきの候補を出します。
  - 英語のモードでは、`te` + 数字 7 桁を打つと、7 桁目で候補が自動で出ます（下線なし。↑/↓ だけで選ぶ）。`u+` + 16 進（Unicode 表記）も同じ作りです。
  - ADR: [0032](adr/0032-postal-code.md)

- **キーマップの段階を、ikari と別の製品として分ける構成**
  - 状態: 検討中（方針は ADR に書いた。配布の形は未決）
  - ADR: [0031](adr/0031-keymap-engine.md)（§5.2）

### 試して採らなかった案

記録として残します。同じ案を検討するときは、先にここと該当 ADR を読んでください。

- **先読みで文を作る**（ローカル LLM が入力の続きを作る）: 生成した文に正解がほとんど出ず、停止（[0025](adr/0025-pregen-prototype.md)）。
- **候補の数を増やして LM に全部採点させる**: 1 位がほぼ変わらず、時間が約 3 倍になるため不採用（[0035](adr/0035-path-loses-cost-adjust.md)）。
- **学習の結果で LM の好みを差し引く**: 評価で悪化する件が出て、時間の条件にも合わなかったため停止（[0028](adr/0028-lm-prior-subtraction.md)）。
- **先読みの仕組みを新しく作る**（キャッシュの共有、アイドル時の生成）: まず既存の仕組みをログで測り、小さく直す方を選んだため、新しく作るのは見送り（[0021](adr/0021-lm-lookahead.md)、[0023](adr/0023-speculative-cache-stage1-2.md)）。
- **IME の中でキーを入れ替える**: 離したキーの動きが IME に届かず、パスワード欄でも効かないため不可（[0031](adr/0031-keymap-engine.md)）。
- **次に来る語の予測や、入力の補完**: 方針 2 と 3 に反するため、作りません。
