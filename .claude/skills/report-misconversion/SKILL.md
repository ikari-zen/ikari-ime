# 誤変換の報告 → 再現 → 既存の issue を確認 → 追記か起票

実装はしない。ここで行うのは、再現、記録、優先度の設定まで。直すのは別の依頼があってから。**新しい issue を作る前に、必ず既存の issue を確認する。**

## 1. 報告から、読み・期待・実際・左文脈を取る
- **左文脈**: 「文脈は↑」「文脈はこのコメントそのもの」とあれば、**ユーザーが直前に書いた文章そのもの**。聞き返さない。変換する語の直前までの文を使う。
- **読み**: 打ったはずの読みを推定する（例: 「意味ナノに」→ いみなのに）。推定に迷うときだけ、読みを聞く。
- **期待**と**実際の 1 位**を表にする。
- 個人情報（住所、実名など）は issue に書かない。例は公開の語に差し替える。

## 2. CLI で再現する（推測しない）
```sh
target/release/ikari --context "<左文脈>" -n 12 <読み>           # LM あり
target/release/ikari --ranker cost -n 12 <読み>                  # LM なし
target/release/ikari -n 60 <読み> | awk '/^-- page/{p=$3} /<期待>$/{print "page",p+0,$0}'   # 期待の順位（1 ページ 9 件）
```
- バイナリがなければ `cargo build --release -p ikari-cli`。
- 見るのは、(a) 期待の順位、(b) 文脈ありとなしの差、(c) 読みを分けたとき（語だけ、助詞つき）の差。
- 実機の結果と CLI が違うときは、そう書く（例: 実機は LM なしで返った可能性。#1 の型）。再現できなかったと正直に書く。
- 「LM で直るか」は `ikari` CLI だけで決めない（`--lm` の締め切りは読みの文字数 × 6ms で固定）。`cargo run --release -p ikari-eval -- --ranker full --lm <gguf> --lm-deadline-ms 3000 --set <tsv>` で測る。測っていなければ「未測定」と書く。

## 3. 既存の issue を探して、行き先を決める（起票の前に必ず）
本文とコメントまで、open と closed の両方を探す。`<語>` は読み、期待、実際の 1 位を `|` でつなぐ。
```sh
gh issue list --state all --limit 1000 --json number,title,state,stateReason,body,comments \
  --jq '.[] | select(([.title, .body, .comments[].body] | join("\n")) | test("<語>")) | "#\(.number) \(.state) \(.stateReason) \(.title)"'
gh issue list --state all --label <cause:ラベル> --json number,state,title   # ラベルごとに 1 回
```
- 原因別のラベル: `cause:word-cost`（#666 単語コスト）、`cause:vocab`（#667 辞書にない語）、`cause:notation`（#101）、`cause:connection`（#236）、`cause:candidate-cut`（#185）。まとめ先は増減するので、番号は検索結果で確かめる。
- 当たった issue は `gh issue view <番号> --comments` で中身を読む。タイトルだけで同じと決めない。

上から順に当てはめる。
1. **同じ例（読みと期待が同じ）がある** → その issue にコメントで追記する（報告の日付、左文脈、再現結果）。結果が表と違えば、表の行も直す（前の記録は消さず、日付を付けて書き足す）。新しい issue は作らない。
2. **例は無いが、原因を確かめられて、原因別の issue がある** → 本文の表に行を足し、経緯をコメントする（表のない issue は、コメントだけ）。
3. **原因が未確定、または当てはまる issue がない** → 新しい issue を作る（§5、§6）。原因が確かなときだけ `cause:` ラベルを付ける。**推測だけの原因で、まとめ先に入れない**（原因が未確定の #461、#637、#2 などは、まとめていない）。

当たった issue が閉じていたときは、閉じた理由をコメントで確かめる。
- **統合で閉じた** → 統合先に、上の 1 か 2 で追記する。
- **直して閉じたものが再発した** → 元の番号を書いて、新しい issue を作る。再発と言う前に、再現に使ったバイナリが今の main のビルドかを確かめる。
- **ほかの理由（見送り、取りやめなど）** → 追記も起票もせず、ユーザーに伝えて聞く。

## 4. 追記する
- コメントは `gh issue comment <番号>`。「分かったこと」と「推測（未検証）」を分ける。
- 表の列は、その issue の本文に合わせる。#666、#667 は「元、読み、左文脈、期待、実際の 1 位、分かっている原因、LM で直るか、状態」。元の issue がない行の「元」は、`報告 YYYY-MM-DD` とする。左文脈が長いときは、本文の「左文脈」の節に番号（L1 など）で足す。
- **状態**: LM が間に合えば直る型は「凍結」にする（2026-11-03 と 2026-11-26 のユーザー決定）。LM でも直らないもの、未測定のものは凍結にしない。凍結はラベルではなく、この列で管理する。
- **本文の編集は、直前に取得した最新の本文に対して行う**（`gh issue view <番号> --json body --jq .body` をリポジトリの外の一時ファイルに保存 → 編集 → `gh issue edit <番号> --body-file <ファイル>`）。会話の前のほうで読んだ本文を使い回さない。**既存の行や記述は消さない。**
- 追記では、Project の項目と優先度を変えない。上げ下げが要ると考えたら、ユーザーに聞く。

## 5. 新しい issue を作る
`gh issue create --label bug,agent-ok,theme:変換の質`。本文は次の形。
- **問題**（報告の内容、左文脈）／**根拠**（「分かったこと」と「推測（未検証）」を分ける）／**状態**／**ユーザーの確認**／**重要度**／**完了の条件**／**関連**
- 完了の条件には、「評価セットに文脈つきで足す」「全セットで 1 位が悪化しない（`eval/scripts/snapshot.sh`）」を入れる。
- 表記の好みが絡む（片仮名とカタカナなど）ものは、誤変換と決めつけず、方針の確認を「ユーザーの確認」に書く。

## 6. 新しい issue を Project に追加して優先度を付ける（聞かずに行う）
```sh
ID=$(gh project item-add 1 --owner ikari-zen --url <issue の URL> --format json --jq .id)
gh project item-edit --project-id PVT_kwHOFGtZzM4Boz93 --id "$ID" \
  --field-id PVTSSF_lAHOFGtZzM4Boz93zhnSTvY --single-select-option-id <P1=cae6a6be | P2=dc94a990 | P3=053120ee>
```
- 変換精度に関わるものは **P1**（ユーザー決定）。表記の好みが中心のものは P2。

## 7. ユーザーへの報告
次の形で、短く。
- 再現できたか（できなかったときは、何が違うか）。
- 期待の順位（LM あり・なし）。
- **追記か新規か、その理由**（例: 同じ読みと期待が #NNN の表にある）。
- 追記先か起票した issue の URL。新規なら、付けた優先度。
- 分かったことと推測を分ける。聞くことがあれば 1〜2 個、推奨つき。
