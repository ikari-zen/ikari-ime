# 誤変換の報告 → 再現 → issue → Project

実装はしない。ここで行うのは、再現、記録、優先度の設定まで。直すのは別の依頼があってから。

## 1. 報告から、読み・期待・実際・左文脈を取る
- **左文脈**: 「文脈は↑」「文脈はこのコメントそのもの」とあれば、**ユーザーが直前に書いた文章そのもの**。聞き返さない。変換する語の直前までの文を使う。
- **読み**: 打ったはずの読みを推定する（例: 「意味ナノに」→ いみなのに）。推定に迷うときだけ、読みを聞く。
- **期待**と**実際の 1 位**を表にする。
- 個人情報（住所、実名など）は issue に書かない。例は公開の語に差し替える。

## 2. CLI で再現する（推測しない）
```sh
target/release/ikari --context "<左文脈>" -n 12 <読み>           # LM あり
target/release/ikari --ranker cost -n 12 <読み>                  # LM なし
target/release/ikari -n 60 <読み> | awk '/^-- page/{p=$3} /<期待>$/{print "page",p+0,$0}'   # 期待の順位（1 ページ 9 件）
```
- バイナリがなければ `cargo build --release -p ikari-cli`。
- 見るのは、(a) 期待の順位、(b) 文脈ありとなしの差、(c) 読みを分けたとき（語だけ、助詞つき）の差。
- 実機の結果と CLI が違うときは、そう書く（例: 実機は LM なしで返った可能性。#1 の型）。再現できなかったと正直に書く。

## 3. issue を作る
`gh issue create --label bug,agent-ok,theme:変換の質`。本文は次の形。
- **問題**（報告の内容、左文脈）／**根拠**（「分かったこと」と「推測（未検証）」を分ける）／**状態**／**ユーザーの確認**／**重要度**／**完了の条件**／**関連**
- 完了の条件には、「評価セットに文脈つきで足す」「全セットで 1 位が悪化しない（`eval/scripts/snapshot.sh`）」を入れる。
- 表記の好みが絡む（片仮名とカタカナなど）ものは、誤変換と決めつけず、方針の確認を「ユーザーの確認」に書く。

## 4. Project に追加して優先度を付ける（聞かずに行う）
```sh
ID=$(gh project item-add 1 --owner ikari-zen --url <issue の URL> --format json --jq .id)
gh project item-edit --project-id PVT_kwHOFGtZzM4Boz93 --id "$ID" \
  --field-id PVTSSF_lAHOFGtZzM4Boz93zhnSTvY --single-select-option-id <P1=cae6a6be | P2=dc94a990 | P3=053120ee>
```
- 変換精度に関わるものは **P1**（ユーザー決定）。表記の好みが中心のものは P2。

## 5. ユーザーへの報告
次の形で、短く。
- 再現できたか（できなかったときは、何が違うか）。
- 期待の順位（LM あり・なし）。
- 起票した issue の URL と、付けた優先度。
- 分かったことと推測を分ける。聞くことがあれば 1〜2 個、推奨つき。
