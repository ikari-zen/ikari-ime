### 1.1 評価セット（`segments.tsv`）

列: `id, kind, tags, context, reading, expected, expected_segments, target, note, split, source`。

- `expected`: 最初に表示してほしい表記。`expected_segments`: その読みの区切りの正解（読みを `|` で区切る。連結すると `reading`）。区切りは ADR 0006 §2.2 の規則による手作業
- `target`: 一部だけを変えた目標の表記。空なら `expected` が目標
- kind:
  - **区切り**（55）: 最初の区切りの正解率。短い読み、複合名詞（1 文節）、付属語（助詞、助動詞、補助動詞）、接頭辞・接尾辞、数詞、助詞の連なり
  - **部分**（46）: 区切りはそのままで、一部の文節だけを選び直す（紙を切る → 髪を切る）
  - **伸縮**（44）: 複合名詞（最初は 1 文節）の一部だけを選び直す。区切り直し（Shift+←/→）が要る（リポジトリ名 → リポジトリ銘。「リポジトリ」を残して「名」を選び直す）
- dev / test: `FNV-1a64(id) % 5 == 0` が test（既存のセットと同じ規則）。調整は dev だけで行う
- 確認: [REVIEW.md](../sets/REVIEW.md) に 1 割（14 件）の抜き取りリストがある。ユーザーの確認は未了
- 合成の目標が多い（「銘」「自信対策」など、実際には書かない語もある）。測るのは候補の位置と操作の数で、文の自然さではない

### 1.2 区切りの指標

- 境界 = 読みの文字位置の集合（先頭と末尾を除く）。ケースごとに正解の境界と答えの境界を比べ、当たり（tp）、余計（fp）、取り逃し（fn）を数えて全体で足す（マイクロ平均）
- 適合率 = tp / (tp + fp)、再現率 = tp / (tp + fn)、F1 = その調和平均。分母が 0 のときは 1.0（間違っていない）。両方 0 なら F1 = 0
- 完全一致率 = 境界の集合が正解と同じケースの割合（1 文節が正解で 1 文節と答えたものも数える）
- 答えの区切り = `Converter::segment(convert(reading))` の `layout().spans`（ADR 0006 §2。Ranker の 1 位から作る）

### 1.3 打鍵数

読みを入力し終えた状態から、目標の表記を確定するまでの最少の打鍵数。幅優先で状態（区切り、フォーカス、各文節の選択）をたどる。

| 操作 | 打鍵 | 備考 |
| --- | --- | --- |
| Space | 1 | 最初の Space が変換で、**読み全体の候補を出す**（2 文節以上でも。§16.6）。以後は次の候補（`max_rank` = 50 まで） |
| 番号キー 1〜9 | 1 | 表示中のページの候補を選ぶ。**全体の候補の間と、1 文節なら確定**。文節のモードで 2 文節以上なら選んで次の文節へ（§16.1-3） |
| ←/→ | 1 | 文節の移動（文節の UI のみ）。全体の候補の間は、文節のモードに入る（→ は 2 番目の文節へ、← は先頭の文節にフォーカス） |
| Shift+←/→ | 1 | 区切り直し（文節の UI のみ）。直した文節以降の選択は 0 番に戻る（§4.2）。全体の候補の間は先頭の文節の区切り直し |
| Enter | 1 | 全体を確定 |

- **今の UI**: 読み全体の候補を Space でたどる。目標が `rank0` 番（0 始まり）なら `1 + (rank0 / 9) * 9 + 1`。最初のページなら 2 打鍵
- **文節の UI**: 上の操作の全部。1 文節の候補の列は全体の候補そのもの（§2.3）なので、1 文節の最小は今の UI と同じ。
  最初の区切りが 2 文節以上のときは、全体の候補（今の UI と同じ列）から始め、そこから文節のモードに入る。
  全体の候補で k 番目を選んでから ←/→ で入るときは、その表記が各文節の最初のページの候補の組み合わせで作れる場合だけ入れて、選択を引き継ぐ（作れなければ入れない）。
  Shift+←/→ で入るときは、全体の候補の選択を捨てて、先頭の文節の区切り直しになる。殻の `enterSegmentMode` と同じ規則（ADR 0006 §16.6）。
  全体の候補にある目標は今の UI と同じ打鍵数で届くので、文節の UI のほうが多くなることはない
- 平均は、両方の UI で届いたケースだけで取る（同じ集合で比べる）。片方だけで届くケースは別の列に数える
- 近似: 文節の候補の列は、区切りごとに「左の文節はすべて 0 番を選んだ」文脈で一度だけ作る（実際は左の選択が左文脈に入る。ただし `Segmented` は最初に作った列を固定する）。Shift+Space とページの折り返しは使わない
- 探索の上限は 40 打鍵。届かなければ「届かない」

### 1.4 再変換の読みの推定

既存のセット（homophones、homophones-ext、hiragana、katakana-suffix）の `(reading, expected)` の組で、`expected` の各別解の表記だけを `Converter::reconvert` に渡し、推定した読み（文節の読みをつないだもの）が `reading` と一致する率を出す。

- 同じセットの中の同じ `(reading, 表記)` は 1 組に数える（再変換が使うのは表記だけ。ADR 0006 の「約 1500 組」は文脈違いの重複を含む件数で、重複を除くと約 360 組）
- 読みが一意に決まらない語（今日、行った）は、推定が違っても仕様（BackSpace で直せる。ADR 0006 §9.3-3）。率は記録だけにして、基準はユーザーが決める
- 再変換を始められなかった組（`SegmentError::Empty`）は、不一致に数え、別の列にも出す

## 2. 流すコマンド（lane C のマージ後）

辞書は `data/build/dict`（または `IKARI_DICT_DIR`）。いずれも release で流す。`--ranker full` は学習とプロファイルを含む本番の構成（`--user-dir` を省略すると一時ディレクトリ）。LM なしが基準で、LM つきは `--lm <gguf> --features lm-metal` を足して参考に出す。

cargo run --release -p ikari-eval -- segments --ranker full --split dev

  cargo run --release -p ikari-eval -- ops --ranker full --set eval/sets/$set.tsv --split dev

# 再変換の読みの推定（既定の 4 セット）
cargo run --release -p ikari-eval -- reading --ranker full --list 40

- `ops --fail-on-worse` を付けると、文節の UI のほうが多い（または届かない）ケースがあれば終了コード 1

### 3.1 区切り

助詞のあとの用言を別の文節にする直し（原因と直し方は下）のあとの値。「旧」は直す前。

| 種別 | 件数 | 完全一致 | 適合率 | 再現率 | F1 | F1（旧） |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 区切り | 55 | 98.2% (54) | 0.972 | 1.000 | 0.986 | 0.875 |
| 部分 | 46 | 97.8% (45) | 1.000 | 0.979 | 0.989 | 0.907 |
| 伸縮 | 44 | 97.7% (43) | 0.889 | 1.000 | 0.941 | 0.800 |

旧で違った 19 件のうち 16 件が直り、**新しく違うようになったケースはない**（残る 3 件は旧でも違った）。残り 3 件（all）:
- `seg-brk-14` にほんごにゅうりょく: 答えは `にほん|ごにゅうりょく`（1 位の語の並びが 日本 + 語入力 で、名詞の連続の途中に分かれ目がある）
- `seg-stretch-16` こうかそくてい: 答えは `こうか|そくてい`（同様に 1 位の語の並びが 効果 + 測定 で、名詞の連続の途中を分けた。複合名詞を 1 文節にする規則に反する）
- `seg-part-35` かみのけを|あらう: 正解は `かみの|けを|あらう`（1 位が 髪の毛 を 1 語にするので、`かみの|け` に分けられない）

**原因（確認した）**: Sudachi は「切る」「行く」「ある」「付く」「直す」「挙げる」「いい」のような普通の用言を、補助動詞の用法と同じ項目として
品詞2 が `非自立可能` の項目にしている（`かみをきる` の 1 位の並びは 髪 + を + 切る で、切る は `動詞,非自立可能,*,*,五段-ラ行`）。
`segment_role` はこの品詞を一律に付属語（Attach）にしていたので、助詞のあとの用言が左の文節に付いてしまい、「髪を切る」が 1 文節になっていた。
1 位の語の並び（辞書に複数語の項目はない）、Rewriter、かなの候補は関係ない。

**直し方**（`core/src/pos.rs`）: `非自立可能` の名詞・動詞・形容詞を新しい役割 `Dependent` にした。左の語が `closes_phrase`（接続助詞以外の助詞、副詞、連体詞、接続詞）なら
新しい文節を始め、そうでなければ（動詞、助動詞、接続助詞「て」、名詞、接頭辞のあと）今までどおり左に付ける。
`食べている`、`変換する`、`食べ続ける`、`書いてある` は 1 文節のまま。先頭の語が付属語のときの「をしよう」も 1 文節のまま。
区切りだけの変更で、全体の候補の 1 位と表示は変わらない（`segment_real` の不変条件が通る）。

**残る副作用（許容）**: 助詞で終わった語のあとの `ない`（形容詞）や `こと`（名詞）も文節を始めるので、`ほんではない` は `本では|ない`、`ことになる` は `ことに|なる`、`人のこと` は `人の|こと` になる。
`ではない` を 1 文節にしたければ、助詞の連なり（で + は）の例外を足す（未対応。評価セットにこの形はない）。

### 3.3 再変換の読みの推定

漢字だけの複合語が始められない問題を直したあと（2026-10-13。原因と直し方は下）。「旧」は直す前（§16.5 の時点）。

| セット | 組 | 一致（新） | 一致率（新） | 始められない（新） | 一致率（旧） | 始められない（旧） |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| homophones.tsv | 12 | 12 | 100.0% | 0 | 100.0% | 0 |
| homophones-ext.tsv | 98 | 98 | 100.0% | 0 | 100.0% | 0 |
| hiragana.tsv | 117 | 117 | 100.0% | 0 | 100.0% | 0 |
| katakana-suffix.tsv | 136 | 127 | 93.4% | 0 | 71.3% | 30 |
| 全体 | 363 | 354 | **97.5%** | 0 | 89.3% | 30 |

一致しなかった 9 組（すべて katakana-suffix）はいずれも仕様の範囲:
- `ユーザー名`（ゆーざめい → ゆーざーめい）: 辞書の語「ユーザー名」の読みが ゆーざーめい。
- 1 文字だけの語は読みが一意でない: 名（めい → な）、者（しゃ → もの）、的（てき → まと）、型（がた → かた）、内（ない → うち）、外（がい → そと）、人（じん → ひと）、米（こめ → べい）。BackSpace で直せる（§9.3-3）。
- core の実辞書のテスト（`core/tests/segment_real.rs`、1565 件、重複を含む）では、読みの一致 93.9% → 95.8%、元の表記のまま（`Literal`）52、断られた 30 → 0（テストに `refused == 0` の確認を足した）。

**原因（確認した）**: `LatticeContextAnalyzer::analyze_sentence` の未知語のノードのコストが、長さによらず `cost_per_char`（実辞書で 10000）の 1 回分だった。
同じ文字種の最長の連続を 1 ノードにするので、漢字 3 文字の複合語は 10000 になり、辞書の語（飛行機 11443、効果的 12407、関数 7342 + 名 6787 に連接）より安くなる。
その結果 `analyze_text` が未知語 1 つ（`word = None`）を返し、漢字は読めないので全体が `Literal` になって `Empty` になっていた。
変換のラティス（`lattice.rs`）の未知語は 1 文字ずつにコストを付けるので、解析器だけが食い違っていた。

**直し方**: `analyze_text`（再変換が表記を語に分ける解析）だけ、未知語のコストを `cost_per_char × 文字数` にした（`UnknownCost::PerChar`）。左文脈の解析（`analyze`）は今までの付け方（`PerNode`）のまま。

**1 位の不変（確認した）**: 直す前後で、5 セット（homophones、homophones-ext、hiragana、katakana-suffix、segments。全 split、unreachable を含む）× 3 構成（cost、topic、full。LM なし）の `--out-cases` の列 1〜7（id、種別、文脈、読み、期待値、1 位、順位）がバイト単位で一致した。
`eval/scripts/snapshot.sh --compare` も「差分 0（一致）」（homophones、ext、hiragana、シナリオ a-02〜04、CLI golden）。`segments`、`ops` の出力も同一。

**直さなかったこと（判断が要る）**: 同じ未知語のコストを左文脈の解析（`analyze`）にも使うと、左文脈つきの 1 位が変わる。試した結果（LM なし、`--ranker full`/`topic` とも同じ）:
- homophones-ext（1266 件、全 split）の正解数 950 → 973（+23）。1 位が変わったのは 30 件、順位が良くなったのは 44 件、悪くなったのは 2 件。ほかのセット（hiragana、homophones、katakana-suffix、segments）は変わらない。
- 改善のほうが大きいが、依頼の条件（全セットで 1 位が変わらない）に反するので、左文脈の解析には適用していない。適用するなら `analyze` の `UnknownCost::PerNode` を `PerChar` にするだけ（1 行）。採用の判断はリードとユーザー。
